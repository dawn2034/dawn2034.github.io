每日 AI 技术简报｜2026-08-09

今天是周日，arXiv 最新批次仍停留在 8 月 7 日；cs.AI 当日共有 201 项，因此今天不强行制造“8 月 9 日新论文”，而是继续深挖这一批里昨天没有覆盖、但技术含量更高的工作。

今日核心判断

  1. OPSD 正在进入“信用分配”阶段。DASH 的增益不是来自更强 Teacher，而是改变 Teacher–Student divergence 在整条 trajectory 上的分配方式。这与最近 AgentOPSD、ABSeeker 的趋势一致：后训练的下一个问题不是“有没有 dense signal”，而是“signal 应落在哪里”。
  2. 自我进化 Agent 开始出现比较像样的纵向因果证据。FinEvo-Bench 使用配对 state-reset control 和三组随机任务顺序，比“跑到后面越来越好所以叫 self-evolving”的证据强得多；但 Skill-only 反而优于 Memory+Skill，说明复杂记忆系统并不天然更好。
  3. 长上下文 Agent 的关键不是记住更多，而是判断哪段历史仍然具有权威性。When History Lies 显示，外形完全合理但已经过期的历史状态，可以让原本会做对的 Tool Agent 改错 32.1% 的决策。
  4. 让 Agent 学一个内部 World Model 是值得认真跟的方向，但风险也很直接：模型可能开始在自己想象的环境里做 RL。EnvACE 的训练效率思路很漂亮，距离真实、随机、不断变化的外部 API 还有明显距离。
  5. RAG 的“Embedding 默认正确”正在被重新审视。在超长、高度结构化、数字密集的文档中，简单 lexical/structural navigation 可能比 dense retrieval 更可靠；但今天的新论文也恰好说明，不能把这个结果夸大成“Agentic Read 击败 RAG”。
  6. 推荐系统的探索正在从 request 内 diversity 走向 request 间价值。京东 DEGR 有十亿请求级数据和线上 A/B，是今天推荐方向最值得看的一项，但“cross-request context bridge”目前仍更多是行为指标上的推断，而不是显式长期状态建模。

1. DASH：OPSD 的问题可能不是 supervision 不够，而是 supervision horizon 不对

发生了什么

标准 On-Policy Self-Distillation 中，Student 自己 rollout；同一模型在看到 reference solution 后扮演 privileged Teacher，并在 Student 实际访问的 prefix 上提供 token-level distribution supervision。

DASH 发现一个容易被忽略的问题：vanilla OPSD 对每个位置的局部 divergence 基本使用统一显式权重，却没有利用整条 rollout 中 divergence 如何随时间演化。

它定义局部信号 $r_t$，相对该条 trajectory 的平均 divergence 构造 gate：

\[\lambda_t = \sigma[-\kappa(r_t-\bar r)]\]

然后反向聚合：

\[A_t=r_t+\lambda_t A_{t+1}\]

从而让不同 token 获得不同的有效 supervision horizon。它不需要额外 Teacher / Student forward pass，因为直接复用 OPSD 已经计算出来的分布。

Qwen3 三个规模的四随机种子结果中，宏平均：

  • 1.7B：OPSD 41.87 → DASH 45.07；
  • 4B：63.60 → 65.00；
  • 8B：64.80 → 66.40。

三种模型、三个数学 benchmark 上都优于 matched OPSD。

为什么重要

最近几天看到的 AgentOPSD、ABSeeker、TRAJDEBUG，其实都在指向同一个更一般的问题：

\[\boxed{ \text{trajectory supervision} \rightarrow \text{temporal credit assignment} }\]

早期 RLVR 的问题是只有最终 $0/1$ reward。

OPSD 解决了一部分问题：Teacher 在每个 token 都能给信号。

但 dense ≠ well assigned。如果每个 token 都获得类似权重，依然可能把大量梯度浪费在 routine reasoning 上。

DASH 给出了一个相当轻量的解决办法：不是再训练一个 PRM/Critic，而是利用 Teacher–Student discrepancy 本身决定“这个位置的监督应该传播多远”。

可信度与局限

证据质量在近期预印本里算不错：matched OPSD 使用四个随机种子，论文明确区分自己的重复实验与外部 single-run baselines，也没有把后者包装成统计显著。

但不要把它理解为免费 RL 方法。

Teacher 在训练时看到了完整 reference solution 和最终答案，Student 才没有看到；实验也只覆盖 AIME/HMMT 数学推理。也就是说：

\[\text{DASH} \neq \text{从纯 outcome reward 自动发现 process supervision}\]

它仍属于 privileged-information distillation。

最值得继续追踪

真正值得做的是把这个思想迁移到 Tool Agent：

\[D_t = D_{\mathrm{KL}}( \pi_{\text{privileged}} \Vert \pi_{\text{student}} )\]

然后观察大的 divergence spike 是否真的对应：

  • 错误 tool selection；
  • 参数绑定错误；
  • 不该终止时终止；
  • 关键 evidence acquisition。

如果成立，DASH 可能比额外训练一个 step reward model 更便宜。

2. FinEvo-Bench：Self-Evolving Agent 终于开始认真回答“到底进化了什么”

发生了什么

FinEvo-Bench 构建了 120 个真实案例驱动任务，覆盖 6 个金融领域、20 个业务场景，每个场景有 6 个不同案例，但会重复使用类似的专业流程。

关键实验设计是：

\[\text{Evolving Agent} \quad vs. \quad \text{paired state-reset Agent}\]

而且任务被随机打乱成三条独立的全局流，尽量避免“后面的题本来就更简单”的问题。

四套 Scaffold 全部使用同一个 Qwen3.7-Max backbone。相对 state-reset control：

  • Claude Code：+17.89；
  • Codex：+19.37；
  • Letta：+17.82；
  • GenericAgent：+9.33。

同时 compliance issue 每题减少 0.12–0.44。自动评分器也与金融专家进行了 120 个结果的交叉验证，绝对一致 ICC 为 0.95。

最有意思的结果其实是 Memory vs Skill

Claude Code 的消融：

状态载体Score
无 evolution71.58
固定专家 Skill86.67
Memory + Skill 全部 evolution89.47
Memory only90.42
Skill only93.71

而完整 Memory+Skill 的 reflection 成本最高，约 $60.19\times10^4$token/任务；Skill-only 为$44.03\times10^4$。

这是一个很值得注意的负结果：

\[\boxed{ \text{Memory}+\text{Skill} \not> \text{Skill} }\]

Agent Memory 越复杂，不一定越聪明。

为什么重要

这与最近 ContinualSkillBench 的结果互补。

真正反复出现的经验通常可以分为：

Episodic Memory

“上一次处理客户 A 时遇到了什么。”

和

Procedural Skill

“这类任务应该按什么步骤检查、验证和输出。”

金融工作流显然偏第二类，因此 Skill 的复用价值远高于保存大量具体 episode。

这对代码、数据分析、推荐算法实验 Agent 同样有启发：长期系统未必需要无限增长的 memory vector store，更值得优先沉淀：

\[\text{失败模式} \rightarrow \text{可执行 procedure} \rightarrow \text{verification rule}\]

可信度与局限

论文的 paired state-reset 设计比大多数 self-evolving Agent 论文强，而且 late-stage gain 在三条随机流中都高于 early-stage。

但仍不能把 +19 分理解为通用 lifelong learning。

Benchmark 刻意让同一 scene 的六个 case 共享专业程序，因此它天然奖励 procedure reuse。论文自己也承认只用了一个 backbone，只测试非参数 evolution；Skill/Memory carrier 消融也只在 Claude Code 上做。

更严谨的说法是：

它较有说服力地证明了“重复专业工作流中的非参数经验积累”有效。

还没有证明跨全新职业、全新任务结构的 open-ended self-evolution。

最值得继续追踪

下一步最关键的评测不应该再是同一 scene 的第七题，而是：

把在金融审查任务中形成的“证据校验 / 谨慎结论 / 合规输出”Skill 拿到完全没见过的业务流程中，是否还能产生净收益？

这才能把：

\[\text{procedure memorization}\]

与：

\[\text{generalizable skill acquisition}\]

区分开。

3. When History Lies：长 Context 最大的问题可能不是遗忘，而是“过期信息仍然看起来可信”

发生了什么

ContextPollute-Bench 对同一个 Tool Agent 决策构造三种同步视图：

  • Original：正常历史；
  • Polluted：加入已经失效、却语义上合理的旧状态；
  • Oracle State：只提供当前真正有效的状态。

系统 policy、当前工具、最新用户请求和正确 next action 都保持不变。

仅仅修改历史，Qwen3-1.7B 中原本做对的决策有 32.1% 被翻转成错误。模型尤其容易重新使用已失效 entity 或旧接口约定。

作者随后使用 Oracle-conditioned Teacher，在 Student 自己的 polluted trajectory prefix 上进行 on-policy distillation：

  • Gold-SFT：66.3%；
  • Oracle sequence distillation：82.3%；
  • off-policy token distillation：85.0%；
  • Oracle-OPD：87.0%。

8B Teacher → 1.7B Student 可以进一步达到 91.9%。

为什么重要

Agent Memory 经常默认：

\[\text{more history} \Rightarrow \text{more information} \Rightarrow \text{better decision}\]

但真实系统更接近：

\[\text{历史信息价值} = f( \text{relevance}, \text{recency}, \text{authority}, \text{provenance} )\]

其中 authority 经常被忽略。

例如：

第 3 轮 API 返回 customer_id=123。

第 17 轮用户切换账户。

如果第 3 轮记录仍保留在 context，模型完全可能继续使用 123，因为那段历史从语法和语义上都没有任何“错误”。

所以，真正的长期 Agent state 不应该只是：

1

append(history)

而应该更像数据库：

1
2
3
4
5
6
7

value
source
timestamp
version
scope
authority
invalidated_by

可信度与局限

Prompt 上简单加一句“忽略失效历史”几乎没有用：BTA 只从 0.4720 涨到 0.4849，而训练后的 reliable-state policy 达到 0.8703。

但 benchmark 目前只覆盖航空和零售的受控 next-action corruption，并不是自然产生的生产 Agent 历史；Oracle-OPD 在训练期还需要 Oracle State。作者也明确把这两点列为限制。

最值得继续追踪

比“无限上下文”更值得关注的方向是：

\[\boxed{ \text{Authority-aware Context Management} }\]

特别是：

  • tool result versioning；
  • state invalidation；
  • source provenance；
  • current-state reconstruction；
  • stale-memory detection。

对于长期 Agent，我认为这比继续把 context 从 1M 扩到 10M 更接近实际瓶颈。

4. EnvACE：Agent 开始把环境本身“学进参数里”

发生了什么

传统 Agent RL：

\[Action \rightarrow \text{External Environment} \rightarrow Observation \rightarrow Action\]

EnvACE 则让同一个 policy 交替扮演两个角色：

\[\text{Agent：生成 Tool Call}\]

然后：

\[\text{World Model：自己预测 Tool Response}\]

再基于自己生成的 environment response 继续行动。

两个角色一起通过 task-success reward 优化，最终希望模型把：

\[P(o_{t+1}\mid s_t,a_t)\]

也内化进参数。

Qwen3-8B 基础模型在 BFCL-v4、$\tau^2$-Bench、VitaBench 汇总得分为 28.48；EnvACE 报告的整体结果进一步超过多种环境合成/模拟方法。训练使用 16 张 H20、470 step、最长 30 turn，并使用 Qwen3-30B-A3B Judge。

测试时甚至可以先在模型内部“想象”几条结果，再真正执行 Tool Call。增加到两条 rehearsal 通常进一步改善，但到三条时开始退化。

为什么重要

这实际上把 Model-Based RL 的思路带进了 LLM Agent：

\[\text{Policy} + \text{Learned Environment Dynamics}\]

如果能成立，训练 Agent 就不必为每条 rollout 都真的启动：

  • 浏览器；
  • 数据库；
  • Docker；
  • SaaS API；
  • 模拟用户。

这会极大改变 Agent RL 的数据成本。

但这里有一个必须严肃对待的问题

World Model 错误时：

\[\hat P(o\mid s,a) \neq P(o\mid s,a)\]

Agent 可能学会优化自己想象中的环境。

例如模型相信：

1
2

delete_user()
→ success

但真实系统其实需要二次授权。

在传统 model-based RL 里，这就是典型的 model exploitation。

因此，“训练时无需外部环境”不能简单等价成“环境问题解决了”。论文当前主要验证的是 benchmark tool environments，而且最大模型只有 8B。

最值得继续追踪

真正决定 EnvACE 能否进入生产的不是 benchmark reward，而是：

\[\text{World Model Calibration Error} = D( P_{\text{real}}(o\mid s,a), P_{\text{rehearsal}}(o\mid s,a) )\]

尤其应单独测：

  • stochastic API；
  • API version drift；
  • permission failure；
  • partial observability；
  • rate limit；
  • 并发状态变化。

这会比再多跑几个 $\tau^2$-Bench 更有信息量。

5. RAG｜Beyond Top-K：真正的结论不是“Agentic Retrieval 击败 Embedding”

这篇论文很容易被标题误读。

发生了什么

作者拿一份约 780 页、数字和表格极其密集的政府财务报告做问答。

Dense Retrieval 很容易遇到一个特殊问题：

文档里存在成千上万个语义极为相似的数字。

例如：

1
2
3

Revenue 2025   17,382
Revenue 2024   17,281
...

Embedding 语义几乎一样，真正决定答案的是行、列、年份、单位、页面结构。

作者让 Agent 不走 Vector Top-K，而通过 deterministic lexical search、outline navigation 和 bounded span read 直接在文档中查找。

在 51 个问题中，Read 方法在最主要的 single-figure lookup 类别上达到 70.8%，Dense 为 12.5%；Dense 有 13 个问题根本没有把 gold evidence 放入 context，Read 为 4 个。

但最重要的结果是：BM25

Read 并没有统计显著击败 BM25。

作者自己非常坦率：

  • Read：每题 $0.058、31.4 秒；
  • Dense：$0.023、12.7 秒；
  • 相对 BM25，Read 花费约 2.9 倍；
  • Read 比 BM25 高出的 7.8 分在这个样本量下可能只是噪声。

因此这篇论文真正支持的是：

\[\boxed{ \text{dense embedding} \text{ 在数字密集结构化长文档中可能不是好的默认 retriever} }\]

而不是：

\[\text{Agentic RAG}>\text{BM25}\]

为什么重要

RAG pipeline 不应该先问：

“Embedding 模型用 BGE 还是 E5？”

而应该先问：

答案依赖的结构是什么？

如果任务依赖：

  • 数字；
  • ID；
  • 法条编号；
  • 表格行列；
  • 函数名；
  • 财务科目；

lexical + structural navigation 往往非常有竞争力。

如果任务依赖：

  • paraphrase；
  • 概念相关；
  • 隐式语义；

Dense / Hybrid 才更有优势。

可信度与局限

作者对限制写得异常坦率：只有一份文档、一个模型、51 个问题，而且 benchmark 是系统作者自己设计的，并且实验过程中还扩展过题目集合。

所以它更适合作为一个“RAG failure mode case study”，而不是新 retrieval SOTA。

6. 推荐系统｜DEGR：探索价值开始进入生成式 Re-Ranking

京东的 Dual Exploration-Driven Generative Re-Ranking 是今天推荐方向我认为最值得看的工作。

发生了什么

传统 reranking 优化当前 request：

\[R_t=\text{CTR}_t\]

DEGR 希望同时考虑：

\[R_t = R_{\text{immediate}} + \alpha R_{\text{exploration}}\]

也就是当前 slate 不仅要点击率高，还应适当提供能够帮助后续请求判断用户兴趣的 exploratory items。

训练中结合：

  • exploratory reward model；
  • sequence diversity constraint；
  • supervised learning；
  • adaptive reward-weighted ORPO；
  • 多 decoding-head 并行生成。

线上只部署 generator，不需要 reward model。

数据规模不是玩具：公开 Taobao 日志约 2600 万条；JD Production Dataset 包含 10 亿次 request、1 亿用户。

线上结果

京东首页进行了 7 天线上 A/B：

  • UCTR：+1.22%；
  • PV：+0.20%。

去掉 exploration diversity constraint 后：

  • UCTR 只有 +0.72%；
  • PV 仍为 +0.20%。

作者还报告 Next Click Ratio、Next Expo Ratio 的改善，用来支持探索行为对后续 request 的价值。

线上 TP99 相对 baseline 增加约 3.2 ms；关闭 parallel decoding 则为 +7.8 ms。

为什么重要

推荐系统正在逐渐从：

\[\text{myopic ranking}\]

走向：

\[\text{information-gathering recommendation}\]

本质与 contextual bandit 很接近：

某个 item 即使当前点击概率不是最高，也可能帮助系统更快识别用户兴趣。

这在新用户、兴趣突变和 feed exploration 中尤其有价值。

可信度与局限

这里要谨慎对待论文所谓的 “cross-request contextual bridge”。

系统并没有显式维护：

\[s_{t+1}=f(s_t,a_t,o_{t+1})\]

这样的跨请求 latent state。

目前主要是通过 Next Click / Next Expo 等行为结果，推断当前探索改善了后续交互。因此“bridge”更像一种效果解释，而不是已经严格证明的状态建模机制。

而且线上实验只有 7 天，论文正文没有提供我能核验到的长期 retention、探索疲劳、供给公平或显著性区间。论文自己也明确承认 exposure bias 使离线指标不能保证线上一致。

最值得继续追踪

我更想看到四个指标：

\[\text{Exploration Regret}\] \[\text{Interest Discovery Rate}\] \[\text{7/30-day Retention}\] \[\text{Provider Exposure Concentration}\]

如果 UCTR 增益主要来自不停给用户“试探性内容”，短期可能有效，长期未必。

今天值得收藏的代码与学习资源

DASH-OPSD 官方实现值得直接读。它很适合做一个小型后训练实验，因为相对 vanilla OPSD 不新增 Teacher/Student forward pass，真正要修改的核心只是 divergence aggregation 与 token weighting。

EnvACE 官方代码也已经随论文公开。如果研究 Agent RL，我更建议先读它的“acting/rehearsal 两角色共享参数”训练 loop，而不是先复现全部 benchmark，因为这里真正的新东西是 world-rehearsal objective。

ContextPollute-Bench / Oracle-OPD值得当作长期 Agent 的回归测试思路。即使不训练 Oracle-OPD，也完全可以自己构造 Original / Stale / Oracle 三视图，测现有 Agent 在用户切换 entity、API schema 更新或 Tool Call 失败后是否错误沿用旧状态。

X.com 近 24 小时技术信号

今天仍然没有一组我愿意标成“近 24 小时高热度技术线程”的 X 帖子。

我针对 DASH、EnvACE、FinEvo-Bench、Beyond Top-K 和 DEGR 做了 X 限域搜索，公开网页索引没有返回同时满足下面四个条件的结果：

  • 作者或项目身份可以核验；
  • 发布时间明确在最近 24 小时；
  • 点赞／转发／浏览量可以核验；
  • 内容明显超出论文摘要。

因此今天继续不拿旧推文或论文搬运号凑“X 热榜”。

值得今天手动关注的关键词是：

DASH OPSD、world rehearsal agent RL、FinEvo-Bench、history reliability tool use、DEGR recommendation exploration。

今日最值得花 30 分钟阅读的一项

FinEvo-Bench

如果只读一篇，我今天会选它，而不是结果涨幅最漂亮的 DASH。

原因是 self-evolving Agent 的测量问题现在比再造一个新 Memory 模块更重要。

建议 30 分钟这样分：

前 7 分钟看 benchmark 构造和 paired state-reset control，理解为什么它比“后期任务分数越来越高”更有说服力。

接下来 8 分钟看 performance / compliance / token cost。尤其注意：

\[\text{最高分} \neq \text{最大 evolution gain} \neq \text{最低成本}\]

三者分别由不同 Scaffold 获得。

再 8 分钟看 Memory / Skill carrier ablation。Skill-only 93.71 > Full evolution 89.47 是全篇最值得记住的结果。

最后 7 分钟看 cross-scene 和 limitations。跨场景分数变化很小且方向不一致，因此不要把 scene 内 procedure reuse 直接叫作 general lifelong learning。

今天最值得保留的判断是：

\[\boxed{ \text{经验越来越多} \neq \text{Agent 越来越强} }\]

真正有效的长期经验必须经过抽象、检索、验证、过期和冲突治理。

今日可立即实践的一件事

给现有 Agent/LLM 项目做一次 “Memory → Skill 压缩实验”。

选择 50–100 条历史成功/失败 trajectory，不要直接把它们全部放进向量库。先让模型把经验归纳成 10–30 条 procedure，例如：

然后固定模型、任务和 token budget，比较三组：

\[A:\ \text{No Memory}\] \[B:\ \text{Raw Episodic Memory Retrieval}\] \[C:\ \text{Procedural Skill Retrieval}\]

分别记录：

  • success rate；
  • skill/memory retrieval precision；
  • context token；
  • latency；
  • 原本成功任务的 regression；
  • stale experience 引发的错误；
  • 未见任务迁移收益。

最后定义一个简单指标：

\[\text{Experience ROI} = \frac{ \Delta\text{Success} - \lambda\cdot\text{Regression} }{ \text{Retrieved Context Tokens} }\]

如果 C 明显优于 B，就没必要继续无限扩大 Memory Store；应该把主要工程投入放到：

\[\boxed{ \text{Experience} \rightarrow \text{Procedure} \rightarrow \text{Trigger} \rightarrow \text{Verification} }\]

这条链路上。

FinEvo-Bench、Skill-Use、ContinualSkillBench 和 When History Lies 最近几天其实都在从不同方向指向这个结论：下一代长期 Agent 的核心可能不是“记住一切”，而是知道什么值得保留、什么时候适用、什么时候已经失效。

# DailyEpoch 每日计划与 Markdown 内容规范

本文件是每日 AI 技术简报的长期写作、检索、发布和定时任务执行规范。新日报在生成、整理和写入 `DailyEpoch/YYYY-MM-DD.md` 前，必须先读取本文件。

> **X 规则版本：4.0**  
> 本版从“按固定关键词寻找若干帖子”改为“先发现正在升温的技术主题，再寻找代表性原帖”。

## 每日内容目标

每天生成一份面向资深 AI／推荐算法从业者的中文技术简报，重点覆盖：

1. 大模型与 Agent 的前沿论文和技术进展；
2. 值得精读的深度文章、课程、代码仓库与学习资源；
3. X.com 上近期快速升温、技术含量高的讨论主题、原帖与 Thread。

优先关注 LLM 训练与推理、Agent、自我进化、RAG、量化、长上下文、强化学习与对齐、推荐系统、开源模型和基础设施。避免泛泛新闻、营销内容和重复摘要。

每个主题必须说明：发生了什么、为什么重要、可信度或局限、最值得继续追踪的点，并附原始来源。结尾必须包含“今日最值得花 30 分钟阅读的一项”和“今日可立即实践的一件事”。

# X.com｜动态热点发现规则

## 1. 核心目标：发现“讨论簇”，不是机械凑帖子

X.com 栏目的基本单位是 **Topic Cluster（讨论主题簇）**，而不是孤立帖子。

正确流程：

```text
发现新术语／新主题
→ 扩展别名与相关项目
→ 搜索多个独立作者的原帖
→ 判断是否形成讨论簇
→ 选择代表性帖子
→ 回到论文、仓库或官方资料核验技术事实
```

错误流程：

```text
先选出当天论文
→ 只搜索这些论文名称
→ 找不到作者发布帖
→ 宣布 X.com 当天没有热点
```

每天最终应优先输出 **2—4 个讨论簇**，每个讨论簇附 1—3 条代表性原帖。帖子数量不足时可以减少，但不能用一句“公共搜索覆盖有限”代替真正的热点发现。

至少有一个候选讨论簇必须**独立于当天已经入选的论文标题和项目名称**。如果一个都没有，说明 X 检索仍被论文筛选绑架，本轮 X 检索不得标记为完成。

## 2. 时间窗口：帖子时间与主题热度分开处理

- **过去 24 小时：** 优先发现新帖；
- **过去 72 小时：** 默认召回窗口，用于容忍索引延迟；
- **过去 7 天：** 只用于识别“持续发酵／旧工作重新升温”的主题簇。

一个主题可以围绕数周或数月前的论文重新升温。此时应写清：

- 原始工作何时发布；
- 为什么最近重新进入讨论；
- 最近新增了哪些帖子、模型、实验、复现或争议。

不得因为底层论文不是当天发布，就忽略正在升温的架构或方法讨论。

## 3. 固定执行顺序

X.com 检索必须按下面顺序执行：

```text
Phase 0：动态新词与趋势发现
→ Phase 1：别名和关联实体扩展
→ Phase 2：X 原帖召回
→ Phase 3：作者／机构扫描
→ Phase 4：当天事件补充搜索
→ Phase 5：聚类、热度判断与核验
```

Phase 4 的 Event-driven Search 最多占总查询量的 **30%**。至少 70% 的查询必须独立于当天论文名单。

## 4. Phase 0：动态新词与趋势发现

这一阶段决定能否捕捉 `Loop Transformer` 这类不在固定关键词表中的新热点，因此是强制步骤。

### 4.1 不带具体论文名的广域搜索

至少执行 6 个广域查询，覆盖：

```text
LLM architecture
new model architecture
reasoning architecture
AI agent systems
LLM inference systems
open model architecture
```

同时执行至少 3 个中文广域查询：

```text
大模型 新架构
推理模型 架构
大模型 技术 热议
Agent 工程 热议
开源模型 架构
```

这些查询的目的不是直接选最终帖子，而是提取最近反复出现的新名词、架构名、模型名、缩写和争议词。

### 4.2 跨源提取正在升温的实体

同时查看过去 72 小时内的高信号来源，包括：

- X 搜索结果和高信号账号页面；
- arXiv 新论文标题；
- Hugging Face 模型与论文趋势；
- GitHub 新增高星项目或 Release；
- Hacker News、Reddit、研究团队博客和技术社区讨论；
- 模型发布、复现、Benchmark 争议和工程事故。

从这些来源中提取 **8—15 个候选主题短语**，例如：

```text
Looped Transformer
latent recurrence
speculative decoding
context engineering
agent harness
KV cache compression
```

其中至少 5 个候选短语不能直接复制自当天已经入选的论文标题。

### 4.3 升温判定

候选主题满足任一条件时进入下一阶段：

- 72 小时内出现至少 2 位互相独立的作者讨论；
- 1 条原始发布帖之外，至少还有 1 条技术分析、质疑、复现或工程反馈；
- 单条帖子互动显著，同时正文包含可验证的技术内容；
- 同一术语在 X、GitHub、Hugging Face、技术博客等多个来源同时出现；
- 旧论文因新模型、新实验或新争议重新获得关注。

“某个词很新”不等于“形成热点”；“论文很旧”也不等于“当前没有热点”。

## 5. Phase 1：别名、缩写和相关项目扩展

每个候选主题必须建立一个 Alias Set，避免只搜一种拼写。

例如当前的回归案例：

```text
主题：Loop Transformer

核心别名：
loop transformer
looped transformer
looping transformer
recursive transformer
recurrent-depth transformer
weight-tied depth
latent recurrence
iterative latent computation

相关项目／工作：
LoopFormer
Loopie
Hyperloop Transformer
MELT
LT2
LoopCoder
Ouro
Parallel Loop Transformer
```

搜索时至少使用：

- 2 个核心别名；
- 2 个相关项目名；
- 1 个机制描述词；
- 中英文可能存在的常用表达。

不能因为 `loop transformer` 没返回结果，就认为 `looped transformer`、`Loopie` 或 `LoopFormer` 没有讨论。

对于其他新主题，也必须自动生成同类 Alias Set。禁止仅依赖本文件中的静态关键词列表。

## 6. Phase 2：X 原帖召回

### 6.1 查询类型

每个高潜主题至少执行以下三类搜索：

```text
精确短语搜索
相关项目／模型搜索
机制或争议搜索
```

示例：

```text
site:x.com/status "looped transformer"
site:x.com/status "Loopie" transformer
site:x.com/status "LoopFormer"
site:x.com/status "weight-tied depth" LLM
site:x.com/status "latent recurrence" transformer
```

搜索结果优先保留包含 `/status/` 的原帖 URL。以下内容只能作为发现线索，不能计入合格原帖：

- X 主页；
- `/with_replies` 页面；
- `x.com/i/trending`；
- Grok 分享页；
- X 官方历史 Article；
- 搜索引擎摘要但没有原帖 URL；
- 媒体二手转述。

### 6.2 最低召回要求

每轮至少完成：

| 类型 | 最低数量 |
|---|---:|
| 动态趋势广域查询 | 9 |
| 候选主题精确／别名查询 | 10 |
| 作者／账号查询 | 6 |
| Event-driven 查询 | 0—6，且不超过总量 30% |

目标获得：

- 至少 15 条 X 相关搜索结果；
- 至少 8 个去重后的原始 `/status/` URL；
- 至少 3 个候选讨论簇。

如果 `/status/` URL 少于 8 个，必须依次：

1. 扩展别名和缩写；
2. 查询项目作者和引用该工作的研究者；
3. 从 24 小时扩大到 72 小时；
4. 检查过去 7 天是否存在持续发酵的讨论簇。

## 7. Phase 3：作者与账号扫描

每天至少扫描：

- 3 个官方模型团队、实验室或开源项目账号；
- 5 个个人研究者、工程师或高质量技术作者；
- 3 个中文技术圈作者或国内团队研究员。

账号池必须动态更新，优先加入：

- 最近热点论文作者；
- 开源仓库维护者；
- 频繁发布复现、Benchmark 审计和工程数据的作者；
- 新出现但技术内容持续高质量的个人账号。

必须使用“账号／作者 + 主题”的组合查询。只搜索 `OpenAI`、`Anthropic`、`DeepMind` 等机构名称不算完成作者扫描。

## 8. Phase 4：Event-driven Search

完成动态热点发现后，才可以围绕当天重要论文、模型或项目补充搜索：

```text
<name> critique
<name> replication
<name> benchmark
<name> limitation
<name> ablation
<name> failure
<name> production
```

该阶段只用于补充社区评价，不能决定整个 X 栏的主题范围。

## 9. Phase 5：聚类与排序

### 9.1 先聚类，再选帖子

将候选帖子按归一化主题聚类。例如：

```text
LoopFormer
Loopie
MELT
LT2
LoopCoder
```

可以归入更高层的：

```text
Looped Transformer / latent iterative computation
```

一个合格讨论簇原则上应有：

- 至少 2 位独立作者；或
- 1 条原始发布帖 + 1 条独立技术分析／复现／质疑。

如果只有单条作者公告，应该标记为“新发布信号”，不应夸大为“社区热议”。

### 9.2 两套分数分开计算

**趋势强度：**

```text
独立作者数量        30%
最近新增讨论        25%
互动与传播信号      20%
跨来源重复出现      15%
讨论持续性          10%
```

**技术价值：**

```text
技术信息量          40%
新颖性              25%
证据质量            20%
DailyEpoch 相关性   15%
```

最终排序不能只看 Likes／Views，也不能只看论文是否新。

互动量无法完整读取时，仍可依据独立作者数量、跨来源重复和技术正文判断是否形成讨论簇，但必须标记“互动数据未完整核验”。

## 10. 原帖准入条件

每条代表性帖子必须确认：

1. 原始 X.com `/status/` URL；
2. 作者账号或作者身份；
3. 可以读取和理解的帖子／Thread 技术正文；
4. 发布时间至少核验到日期，并能判断属于 24h、72h 或 7 天持续发酵窗口。

能看到精确时间时写明时间和时区；只能确认日期时，标记“发布时间仅核验到日期”。

Views、Likes、Reposts、Replies 是排序信号，不是硬性准入门槛。不得猜测互动量。

技术事实应尽量回到论文、代码仓库、官方博客或模型卡交叉核验。X 帖中的个人解释必须明确标为作者观点或合理推断。

## 11. X 栏输出格式

栏目标题固定为：

```markdown
## X.com｜近期高信号技术讨论
```

优先按讨论簇组织：

```markdown
### 讨论簇 1：Looped Transformer 为什么重新升温

**趋势判断：** 过去 72 小时出现多位独立作者讨论；互动数据部分可见。

**代表性原帖**

- [@AuthorA：标题或一句话摘要](原始 X URL)，发布时间……
- [@AuthorB：标题或一句话摘要](原始 X URL)，发布时间……

**大家在争论什么**

概括共同问题、主要观点和分歧。

**为什么现在值得关注**

说明触发重新升温的新模型、实验、复现或工程需求。

**技术判断与局限**

区分已验证事实、作者观察、推断和未解决问题。
```

不要把每条帖子写成互不相关的新闻摘要。

## 12. 强制检索审计

日报必须包含折叠审计块，数字必须来自实际执行：

```markdown
<details>
<summary>本轮 X.com 检索审计</summary>

| 项目 | 数量 |
|---|---:|
| 动态趋势广域查询 | 实际值 |
| 候选主题／别名查询 | 实际值 |
| 作者／账号查询 | 实际值 |
| Event-driven 查询 | 实际值 |
| 提取出的新主题短语 | 实际值 |
| X 搜索结果总数 | 实际值 |
| 去重后的 `/status/` URL | 实际值 |
| 候选讨论簇 | 实际值 |
| 最终收录讨论簇 | 实际值 |

本轮发现的新主题短语：……

主要淘汰原因：……

</details>
```

不允许只写“已完成四路搜索”。没有真实数量和新主题短语，视为未完成检索。

## 13. “未找到”的判定标准

只有同时满足以下条件，才允许写“本轮未发现值得高置信收录的 X.com 技术讨论”：

- 已完成动态趋势发现并列出 8—15 个候选短语；
- 已执行别名和相关项目扩展；
- 已获得或尝试获得至少 8 个原始 `/status/` URL；
- 已扫描官方账号、个人作者和中文技术圈作者；
- Event-driven 查询不超过总量 30%；
- 已检查 72 小时窗口和 7 天持续发酵窗口；
- 审计块报告了真实数量、候选主题和淘汰原因。

若最终为空，必须列出**最接近入选的 3 个候选主题**及淘汰原因，而不是只写搜索引擎覆盖有限。

限定说明可以保留：

> 公共 Web Search 对 X.com 的实时索引覆盖有限，因此这表示本轮无法高置信核验，不代表 X.com 当天不存在相关热门讨论。

但该说明不能替代检索和审计。

# Markdown 结构规范

## Front Matter

```yaml
---
title: "每日 AI 技术简报｜YYYY-MM-DD"
date: YYYY-MM-DD
categories: [DailyEpoch]
tags: [AI, LLM, Agent]
permalink: /DailyEpoch/YYYY-MM-DD/
---
```

## 正文层级

- 开头用简短的 `> **今日主线：** ...`；
- `##` 用于主要章节；
- 论文或项目章节优先包含：
  - `### 发生了什么`
  - `### 关键结果`
  - `### 为什么重要`
  - `### 可信度与局限`
  - `### 最值得继续追踪`
- 保持以下结尾章节：
  - `## 今日值得收藏的代码 / 学习资源`
  - `## X.com｜近期高信号技术讨论`
  - `## 今日最值得花 30 分钟阅读的一项`
  - `## 今日可立即实践的一件事`
  - `## 参考来源`

## 可读性、LaTeX 与来源

- 单段尽量控制在 3—5 句；
- 三项以上的可比较数据优先用 Markdown 表格；
- 重要判断使用引用框或粗体，不用展示公式做纯排版强调；
- 行内公式使用 `$...$`，块级公式使用独立的 `$$...$$`；
- 美元价格中的 `$` 必须转义；
- 代码围栏必须成对闭合，不保留临时 `id`；
- 使用标准 Markdown 原始链接；
- 不保留 ChatGPT 内部 Citation、Navlist 或引用 ID；
- X 趋势页、Grok 摘要和媒体转述只能作为发现线索，技术事实必须回到原帖或主来源。

## 发布前检查

1. 标题、日期、文件名和 permalink 一致；
2. 每个主主题包含事实、重要性、局限和追踪点；
3. 事实、合理推断和不确定性明确区分；
4. 表格、公式和代码块可以正常渲染；
5. 所有来源链接与正文准确对应；
6. X 栏以讨论簇为单位，而不是只列孤立帖子；
7. 已完成动态新词发现、别名扩展和实际检索审计；
8. 至少一个 X 候选讨论簇独立于当天论文名单；
9. Event-driven 查询未超过总量 30%；
10. 截至 2026-09-10 已完成 Looped Transformer 回归测试。

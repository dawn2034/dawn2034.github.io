# DailyEpoch 每日计划与 Markdown 内容规范

本文件是每日 AI 技术简报的长期写作、检索、发布和定时任务执行规范。新日报在生成、整理和写入 `DailyEpoch/YYYY-MM-DD.md` 时必须遵守。

## 每日内容目标

每天生成一份面向资深 AI／推荐算法从业者的中文技术简报，重点覆盖：

1. 大模型与 Agent 的前沿论文和技术进展；
2. 值得精读的深度文章、课程、代码仓库与学习资源；
3. X.com 近期讨论度高、技术含量高的 AI 推文与线程。

优先关注 LLM 训练与推理、Agent、自我进化、RAG、量化、长上下文、强化学习与对齐、推荐系统、开源模型和基础设施。避免泛泛新闻和营销内容。

每个主题必须说明：发生了什么、为什么重要、可信度或局限、最值得继续追踪的点，并附原始来源。结尾必须包含“今日最值得花 30 分钟阅读的一项”和“今日可立即实践的一件事”。

## 定时任务执行规则：X.com 独立高召回检索

X.com 必须作为与 arXiv、GitHub、官方技术博客平行的**独立信息源**处理，不能只围绕当天已经入选的论文主题做补充检索。

定时任务在完成论文、代码仓库和深度文章的候选发现后，必须单独执行一轮 X.com 技术热点发现。

### 1. 时间窗口

- **优先窗口：过去 24 小时**；
- **召回窗口：过去 48 小时**。

公共搜索引擎对 X.com 的索引可能延迟，因此允许收录 24—48 小时内首次被高置信发现的高价值帖子，但必须展示真实发布时间，不能描述成“刚刚发布”。

超过 48 小时的帖子原则上不进入当日栏目；如果当天出现新的重要实验、反驳、修正或讨论升级，可以作为“持续发酵／后续进展”收录，并明确说明原帖日期和新增信息。

### 2. 四路候选发现

每日必须同时完成以下四类检索，不能只运行其中一类。

#### A. Broad Topic Search

英文关键词至少分组覆盖：

```text
LLM reasoning
reasoning model
test-time scaling
RLHF
RLVR
GRPO
on-policy RL
on-policy distillation
coding agent
tool agent
computer use
agent harness
context engineering
agent memory
self-evolving agent
RAG
long context
KV cache
sparse attention
LLM inference
LLM serving
open-source LLM
recommendation system
generative recommendation
```

中文关键词至少覆盖：

```text
大模型
推理模型
强化学习
智能体
编程智能体
上下文工程
长期记忆
RAG
长上下文
推理加速
推荐系统
```

不得把全部关键词塞进一个超长 query；应拆成多个独立 query，提高召回率。

#### B. Researcher / Engineer Search

主动检查高信号研究者、工程师和机构账号近期讨论，至少覆盖：

- OpenAI；
- Anthropic；
- Google DeepMind；
- Meta AI；
- Microsoft Research；
- NVIDIA；
- Hugging Face；
- DeepSeek；
- Qwen；
- Moonshot AI；
- GLM／智谱；
- ByteDance／Seed；
- xAI。

作者池不是白名单。近期论文作者、GitHub 项目作者以及新出现的高质量个人研究者都应加入候选。

#### C. Event-driven Search

对当天最重要的 3—5 个论文、模型、项目或 Benchmark，额外检索社区评价，而不只看作者 announcement。

建议组合：

```text
<name> critique
<name> replication
<name> benchmark
<name> limitation
<name> ablation
<name> failure
<name> production
```

重点寻找复现、质疑、失败案例、机制解释、工程反馈、性能回归和设计取舍。

#### D. 中英文双语搜索

核心主题同时执行英文和中文搜索，避免只看到英语技术圈中的同一批传播节点。

### 3. 候选池与筛选顺序

每日目标形成约 **20—40 条候选帖子**，再进行：

```text
广泛召回
→ 去重
→ 原帖核验
→ 技术筛选
→ 热度判断
→ 主来源交叉验证
→ Top 3—5
```

不得在只搜索少量关键词或只查看少数结果后，就得出“今天 X 没有技术热点”的结论。

### 4. 硬性准入条件

一条帖子进入最终栏目之前，必须能够高置信确认：

1. 原始 X.com URL；
2. 作者身份；
3. 真实发布时间；
4. 帖子或 Thread 的核心技术正文。

以上四项是硬条件。

### 5. 互动量不是硬门槛

Views、Likes、Reposts、Replies 属于**热度排序信号**，但不是收录的硬性准入条件。

- 能够可靠获得时，记录近似互动数据；
- 只能看到部分数据时，标记“互动数据部分可见”；
- 无法可靠获得时，可以正常收录，但必须标记“互动数据未完整核验，按技术信号收录”；
- 严禁猜测或虚构互动量。

不能因为外部搜索引擎没有暴露准确 Views／Likes，就自动丢弃技术价值很高的帖子。

### 6. 排名规则

候选帖子按照以下维度综合判断：

```text
Technical Value       40%
Discussion Signal     25%
Novelty               20%
DailyEpoch Relevance  15%
```

可使用编辑评分：

$$
S=0.40T+0.25H+0.20N+0.15R
$$

其中：

- $T$：技术信息量；
- $H$：热度与讨论信号；
- $N$：是否提供新的实验、反例、机制或经验；
- $R$：与 LLM／Agent／推荐算法读者的相关性。

不要单纯按浏览量或点赞数排序。高热度营销帖可以低于互动量较小、但包含真实实验或生产经验的技术帖子。

### 7. 优先级判断

优先收录：

- 新的技术洞察；
- 反常识实验结果；
- Benchmark／Evaluation 质疑；
- 作者补充论文中未写清楚的实现细节；
- Production lesson；
- 模型行为观察；
- 复现结果；
- 失败案例；
- Ablation；
- 系统性能数据；
- 高质量长 Thread；
- 有证据支持的研究方向争论。

降低优先级：

- 单纯转发论文标题；
- 模型营销文案；
- 没有技术细节的赞叹；
- 新闻媒体二手摘要；
- 纯情绪化争论；
- 只有 Benchmark 截图但没有实验上下文。

### 8. 去重与连续追踪

收录前检查最近 **7 天**日报中的 X.com 栏：

- 同一帖子不得重复收录；
- 同一作者重复相同观点时不重复收录；
- 出现新实验、新数据、新反驳或重要修正时，可以作为“后续进展”再次出现；
- 连续讨论应重点说明“相较上一日发生了什么变化”，不要每天重写背景。

### 9. 输出数量

正常目标为 **3—5 条**，但不能为了填满版面降低标准。

- 只有 1—2 条真正高质量帖子时，只收录 1—2 条；
- 已经发现多个可核验、高价值讨论时，不得因为互动量不完整而把整个栏目置空；
- 如果完全没有合格候选，应保留栏目并说明检索限制。

### 10. 每条帖子的固定输出格式

```markdown
### @Author：一句话概括核心观点

**原帖：** [X.com](原始 URL)  
**发布时间：** YYYY-MM-DD HH:mm（注明时区）  
**热度信号：** 可核验数据／部分可见／未完整核验

**他在讨论什么**

用 2—4 句话解释帖子或 Thread 的核心技术内容。

**为什么值得看**

说明它相对论文、官方博客或常规认知新增了什么信息。

**我的判断**

明确区分：已验证事实、作者个人观察、合理推断、尚未验证的机制解释和局限。
```

### 11. “未找到”的判定标准

只有完成以下全部步骤后，才允许写“未发现值得高置信收录的 X.com 技术讨论”：

```text
Broad Topic Search
+
Researcher / Engineer Search
+
Event-driven Search
+
中英文双语搜索
+
48h Recall Window
```

并必须附上限定说明：

> 公共 Web Search 对 X.com 的实时索引覆盖有限，因此这表示本轮无法高置信核验，不代表 X.com 当天不存在相关热门讨论。

### 12. 定时任务完成检查

发布前必须确认：

- X.com 检索独立于论文候选选择；
- 已执行四路搜索；
- 已检查 24h 优先窗口和 48h 召回窗口；
- 已对最近 7 天日报去重；
- 所有收录项具有原帖 URL、作者、发布时间和技术正文；
- 互动量缺失时按规则标注，而不是删除高价值候选；
- 技术事实已尽量回到论文、仓库、官方博客或其他主来源交叉核验；
- 没有把 X 趋势摘要、Grok 自动摘要或二手转述当作技术事实来源。

## Markdown 结构规范

### Front Matter

每篇文章必须包含：

```yaml
---
title: "每日 AI 技术简报｜YYYY-MM-DD"
date: YYYY-MM-DD
categories: [DailyEpoch]
tags: [AI, LLM, Agent]
permalink: /DailyEpoch/YYYY-MM-DD/
---
```

### 正文层级

- 正文只保留一个文章标题；布局已显示页面标题时，正文 H1 可省略。
- 开头使用一段简短的 `> **今日主线：** ...`，不要再写一段与“今日核心判断”高度重复的长摘要。
- H2 用于日报主要章节；H3 用于固定分析维度。
- 论文或项目章节优先使用：
  - `### 发生了什么`
  - `### 关键结果`（有三项以上可比较数据时）
  - `### 为什么重要`
  - `### 可信度与局限`
  - `### 最值得继续追踪`
- 保持以下结尾章节：
  - `## 今日值得收藏的代码 / 学习资源`
  - `## X.com｜近期高信号技术讨论`
  - `## 今日最值得花 30 分钟阅读的一项`
  - `## 今日可立即实践的一件事`
  - `## 参考来源`

## 可读性规范

- 每个主主题在标题后优先给出一行 `> **一句话结论：** ...`。
- 单段尽量控制在 3—5 句；复杂论证拆成短段，不堆成大块文字墙。
- 三项及以上可比较的实验数据优先用 Markdown 表格，而不是连续散落在正文中。
- 列表只用于真正并列的信息；避免把完整文章写成几十条碎片化 bullet。
- 重要判断使用引用框或粗体，不使用展示公式充当排版强调。
- 仅在表达真实数学关系时使用 LaTeX。

## LaTeX 与代码规范

- 行内公式使用 `$...$`。
- 块级公式使用独立的 `$$...$$`，前后保留空行。
- 不使用 `\(...\)` 或 `\[...\]` 作为最终 Markdown 分隔符。
- 概念性表达如“长期经验系统 ≠ 不断追加文本”应写成普通正文或引用框，而不是 `\text{...}` 展示公式。
- 美元价格中的 `$` 必须转义为 `\$`，避免被 MathJax 识别为公式。
- 代码围栏使用标准三反引号和语言名，不保留 ChatGPT 临时 `id="..."` 属性。
- 公式分隔符、代码围栏必须成对闭合。

## 来源与引用规范

- 正文和“参考来源”均使用普通 Markdown 链接：`[标题](原始链接)`。
- 优先链接论文原文、官方技术报告、官方代码仓库、官方博客或原作者线程。
- 不使用搜索结果页、内容农场或二手搬运作为核心来源。
- 不保留 `cite...`、`navlist`、内部引用 ID 等 ChatGPT UI 标记。
- 无法准确恢复原始链接时，明确说明“未能高置信核验”，不要猜测性补链。
- X.com 趋势页、Grok 自动摘要和媒体二手摘要只能作为发现线索；技术事实必须回到原帖或主来源核验。

## 内容质量检查

发布前必须检查：

1. 标题、日期、文件名和 permalink 一致；
2. 开头摘要与“今日核心判断”没有大段重复；
3. 每个主主题都包含事实、重要性、局限和追踪点；
4. 事实、合理推断、不确定性和个人判断明确区分；
5. 表格、列表、公式和代码块能在 Jekyll/Kramdown 中正常渲染；
6. 没有内部 citation 标记或失效占位链接；
7. 所有原始来源链接与正文主题准确对应；
8. “今日实践”可以在有限时间内执行，并包含明确的评估指标与停止条件；
9. X.com 栏已经完成独立高召回搜索、原帖核验、7 天去重和主来源交叉验证。

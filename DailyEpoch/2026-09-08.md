> **今日主线：** Self-Extrapolated OPD · Agent Team Protocol Drift · Search Harness Effects · Placement-Aware Recommendation · KV Cache Recovery · TPU Kernel Agents

截至今天早上，arXiv `cs.AI` 最新常规公告批次为 **2026 年 9 月 7 日，共 205 条**。今天真正值得连起来看的变化，不是又出现了几个新 benchmark 高分，而是后训练、Agent 与基础设施都在把“系统内部原本隐含的状态”显式化：RISE 把 RL 训练轨迹外推成未来 Teacher；多 Agent 团队开始量化 partner-specific protocol；Search Agent 把 Context Management 单独从 Policy 能力中拆出来报告；推荐系统则显示相同候选关系在不同 placement 下具有完全不同的业务含义。

## 今日核心判断

1. **Self-Improvement 正从“用当前模型教当前模型”推进到“从训练轨迹估计一个更强的未来 Teacher”。** RISE 沿 RLVR 已经取得的参数／logit 位移做保守外推，再把这个 synthetic future teacher 蒸馏回当前 Policy；Qwen3-8B 的 Math Avg 从 GRPO 的 60.0 提到 62.7，Qwen2.5-3B Agent 设置中 ALFWorld 从 75.0 提到 84.4、WebShop exact success 从 63.3 提到 74.2。与此同时，另一项 OPD 数据研究发现仅 8 个 hard examples 就能匹配 17K full-set distillation。两项结果共同提示：OPD 当前的瓶颈可能更多在**Teacher signal 如何构造和吸收**，而不一定在继续扩充题目数量。

2. **长期 Multi-Agent 团队的成员并不完全可互换，即便模型、角色和经验量完全相同。** 在 Collab-Overcooked 与 Hanabi 中，把独立形成的同角色 Agent 互换，任务得分损失不大，但单位进展的通信成本上升 **16%–63%**；Hanabi 中，带着旧伙伴习惯的“有经验陌生人”甚至比全新 Agent 更难协作。长期 Agent 团队会形成 partner-specific protocol，调度器若只按模型能力和角色标签换人，会漏掉这层隐藏状态。

3. **Search Agent 的 Benchmark 分数里，Harness 贡献可能大到超过模型之间的差距。** Iris 在完全相同 Policy 下，仅启用 `discard-all` Context Management，Iris-mini 的 BrowseComp 从 64.7 提到 82.2（+17.5 points），Iris-pro 从 72.6 提到 88.6（+16.0）。这说明比较 Search Agent 时必须同时报告 `Policy-only` 与 `Policy + Context Management`，否则“模型能力提升”与“延长有效搜索寿命”会被混成一个数字。

4. **推荐系统中的“互补关系”不是脱离场景的静态标签。** Allegro 的 AlleCompanion 在 Product Page organic 上带来 Web/App GMV **+8.05% / +9.35%**，在 In-Cart 则达到 **+21.25% / +15.73%**；但 Pre-Cart 的一个 filtered 版本反而让 Web v-CVR **-0.28%**。同样的 category relation 在浏览、加购前和结账阶段代表不同用户意图，推荐模型需要把 placement 当成 causal context，而不是只学习一个统一的“商品互补度”。

5. **KV Cache 量化后的质量损失可以通过很小的 attention adapter 部分恢复，但 PPL 恢复不能替代长上下文行为验证。** 4-bit cache 下，低秩 Q/K/V adaptation 可恢复 TinyLlama 54.24% 和 Gemma-4-12B 75.96% 的 held-out PPL gap；然而 2-bit stress test 即使几乎恢复 PPL，Needle retrieval 仍只有 11–12/180，而 floating cache 为 170/180。量化后训练必须同时测语言建模指标和真正的 retrieval/state-tracking 行为。

6. **Kernel Generation 的收益越来越来自“Agentic Search Harness”，而不是一次代码生成。** Google/DeepMind 的 MaxKernel 在 50 个 TPU JAXBench workload 上，简单 Best-of-N 只有 10/50 编译与正确；并行 Agent search 则达到 50/50 正确、1.58× 几何平均加速。8 个有人工手写 Pallas kernel 的生产 workload 上，Agent parallel search 对 JAX/XLA 的几何平均加速为 2.32×，高于人工参考的 2.02×，但样本仅 8 个，不能外推成“Agent 已普遍胜过 kernel engineer”。

## 1. RISE + OPD Data Efficiency：从“现在的自己”外推出一个未来 Teacher

**原始来源：** [RISE: Recursive Improvement via Self-Extrapolating Policy Distillation](https://arxiv.org/abs/2609.05295)  
**交叉阅读：** [What Matters in On-Policy Distillation? A Perspective on Data Efficiency and Data Selection](https://arxiv.org/abs/2609.05198)

### 发生了什么

常规 On-Policy Distillation 的核心优势是：Teacher 在 Student 自己真正访问的 rollout state 上提供 dense token-level supervision。但它有两个长期限制：外部 Teacher 会有 student-prefix distribution mismatch；self-teacher 又通常只能复用当前模型已有的能力。

RISE 的做法很不一样。它先用 RLVR / GRPO 获得一个被可验证 outcome 约束的训练方向，再观察当前 checkpoint 相对一个 trailing anchor 的位移：

\[
\Delta_t = \phi(\pi_t)-\phi(\pi_{anchor}).
\]

随后沿这个方向做保守外推：

\[
\phi(\pi_{future})
=
\phi(\pi_{anchor})
+
\beta_t\Delta_t,
\qquad \beta_t>1,
\]

把得到的 synthetic future policy 当作 Teacher，再用 OPD 把它蒸馏回当前 Student。实现既可以在 weight space，也可以在 logit space；训练后期 \(\beta_t\) 会逐渐衰减到 1，避免不断沿一个已经失真的方向外推。

关键点在于：这个 Teacher **不是一个真实训练到未来的 checkpoint**，而是根据当前 RL 轨迹做出的局部外推。RLVR 提供方向，OPD 负责把外推产生的 dense signal 投回可执行 Policy。

### 关键结果

Qwen3-8B / DAPOMath：

| 方法 | Math Avg | OOD Avg |
|---|---:|---:|
| Base | 43.2 | 67.2 |
| GRPO | 60.0 | 70.6 |
| RISE (logit) | 62.5 | 71.3 |
| RISE (weight) | **62.7** | **72.0** |

在更接近 Agent 的 Qwen2.5-3B-Instruct 设置中：

| 方法 | ALFWorld Success | WebShop Score | WebShop Exact Acc |
|---|---:|---:|---:|
| Base | 21.9 | 6.7 | 0.8 |
| GRPO | 75.0 | 79.8 | 63.3 |
| RISE (logit) | 78.1 | 78.8 | 68.0 |
| RISE (weight) | **84.4** | **86.3** | **74.2** |

成本不是零。论文报告 RISE 复用 GRPO rollout，因此没有增加采样次数，但多了 Teacher/anchor forward 与 OPD gradient phase：Qwen3-1.7B 每轮约为 **1.3× GRPO wall time**，Qwen3-8B 约 **1.6×**。

另一个值得交叉看的新结果来自清华／美团的 OPD 数据研究：DeepSeek-R1-Distill-Qwen-1.5B 上，最佳单个 hard example 的 1-shot OPD 平均准确率已经达到 **51.7%**，接近 17K full-set 的 53.7%；仅 **8 个 hard examples** 达到 53.6%，继续扩到 16 或 64 个没有继续改善。作者进一步发现，收益与“高 entropy”关系较弱，更像来自 hard example 诱导的**更长 CoT 与更多 reflection/backtracking pattern**。

### 为什么重要

这两项工作从两个方向指向同一个问题：OPD 可能并不主要缺训练题，而是在缺**高价值状态、长程推理 pattern，以及能超出 Student 当前局部能力的 dense supervision**。

一个更值得实验的 post-training loop 可能是：

```text
少量高难度 / 长轨迹任务
→ RLVR 得到被 outcome 约束的改进方向
→ 构造更强的 on-policy teacher signal
→ OPD 提高吸收效率
→ 再根据验证结果继续更新
```

而不是简单扩大 OPD corpus，或者长期依赖一个固定外部 Teacher。

### 可信度与局限

RISE 的关键假设是训练轨迹在局部足够“可外推”。作者在 DAPOMath 上观察到 RLVR checkpoint 位移高度低维：前三个主成分约解释 **87%** 方差，但这并不证明更复杂的 Agent、开放式 coding 或 non-stationary environment 也满足同一几何结构。

论文还给出了一个非常重要的失败 ablation：如果去掉 RLVR grounding，只沿 self-distillation 位移继续外推，训练在约 60 步内崩溃，MATH-500 下降到 2.4%、response length 撑满 8K context。也就是说，“Self-Extrapolation”本身不是免费递归自我改进；**必须有外部可验证 outcome 约束方向**。

OPD 数据效率结论也主要来自数学任务。hard example 的难度可以用 verifier 计算，而开放式 Agent 没有这么干净的 difficulty signal；CoT length 只是作者建议的 proxy，不应被当作通用的数据质量指标。

### 最值得继续追踪

最值得做的是把 RISE 放到 Coding / Tool Agent 上，检查三件事：训练轨迹是否仍低维；外推方向在模型升级或环境变化后是否稳定；以及在固定总 GPU-seconds 下，1.3–1.6× 的训练额外成本是否真的比增加 rollout 数更划算。

## 2. Agent Team Interchangeability：换一个“同样强”的 Agent，也会丢掉团队协议

**原始来源：** [Testing Interchangeability in LLM Agent Teams](https://arxiv.org/abs/2609.05279)

### 发生了什么

很多 Multi-Agent framework 把 Agent 看成可替换的进程：只要模型、role prompt 和能力满足 contract，同一个 slot 换谁都应该差不多。但长期运行的 Agent 往往拥有 persistent notebook，它们除了学习任务知识，还会学习“这个伙伴通常怎么做、哪些 handoff 需要说清楚、哪些约定可以省略”。

论文做了一个相当干净的 swap test。每个 setting 建立 8 支独立团队，使用同一个 frozen base model、相同角色和任务池；每个 Agent 在 10 个 formation episodes 中维护一份最多约 200 token 的私人 notebook，其中明确分成：

```text
task notes    → 环境、规则、失败模式等可迁移知识
partner notes → 针对当前队友形成的协作约定
```

然后把两支团队的同角色 Agent 互换，并与以下条件比较：原团队不变、只宣布换人但实际不换的 placebo、删除 partner notes、全新 naive Agent 等。因为模型权重没有训练，所有 team adaptation 都存在 notebook 文本里，因果边界比一般 Multi-Agent benchmark 清楚得多。

### 关键结果

总体上，swap 对最终任务得分影响不算大，但对协调效率影响很明显：

- Collab-Overcooked 低耦合：通信成本约 **+16%**；
- 高耦合：约 **+51%**；
- Hanabi：约 **+63%**。

Hanabi 中的 coordination residue 甚至超过 1：换入一个在别的团队里“经验丰富”的 Agent，比换入一个没有任何历史的 naive Agent 还贵，符合**旧协议干扰新团队**的解释。

形成时间也会放大这个效应。团队共同经历 5 / 10 / 20 个 formation episodes 时，partner-specific residue ratio 约从 **0.17 → 0.27 → 0.41**；而把 decoding temperature 从 0.7 降到 0.0，会同时减少不同团队协议的漂移与 swap penalty。

更有意思的是恢复速度：task score 通常几轮内就能接近 placebo，但 communication cost 的额外负担消失得更慢。系统如果只监控 task success，会错过一段很长的“协作效率退化期”。

### 为什么重要

长期 Agent 系统中的状态至少有三层：

```text
模型能力
+ 任务知识
+ partner / team protocol
```

当前大多数模型路由、容灾和弹性调度只管理前两层。实际生产中，模型版本升级、容器迁移、provider fallback、角色替换都可能在不降低单 Agent 能力的情况下，破坏已经形成的 handoff protocol。

因此 Multi-Agent orchestration 可能需要类似“session affinity”的机制：长期协作紧密的 Agent 不应被完全视为 fungible replica；若必须替换，应显式迁移或清理 partner-specific memory，而不是把旧 notebook 原样带过去。

### 可信度与局限

这里的“团队学习”完全来自文本 notebook，不是模型参数更新，更不能类比为 Agent 产生了人类式社会关系。实验只覆盖两类协作 benchmark，规模也主要是小团队。

另一个边界是：论文刻意允许 Agent 自己写 partner notes，因此 observed protocol drift 部分依赖 notebook prompt。不同 Memory schema、共享黑板或更结构化 handoff contract 可能大幅降低 swap cost。

### 最值得继续追踪

真正实用的下一步是测试 **protocol portability**：把 partner-specific knowledge 转换为结构化 contract / capability manifest 后，swap penalty 能否下降；以及生产级多 Agent 调度器是否应把“协作历史长度”和“team affinity”加入 placement cost。

## 3. Iris：Search Agent 的 Policy 与 Context Management 必须分开计分

**原始来源：** [Iris: Climbing to the Search Frontier](https://arxiv.org/abs/2609.04304)

### 发生了什么

Iris 的训练链条本身值得看：它从 Web hyperlink / entity structure 反向构造 multi-hop search task，去掉可直接字符串匹配的 anchor；只保留 reference model 在 closed-book 失败、拿到 evidence 后可以解决的题目。随后用 live-search RL 训练，并在 SFT 与 RL 之间反复“climb”：把 RL 轮次中最难但已解决、或者效率最高的 trajectory 返回下一轮 SFT。

工程侧还用了 request-level partial rollout：长尾 search session 不必把整个同步训练 step 卡死，可以在一个已提交 prefix 处中断，后续继续恢复。

但这篇工作最值得读的其实是它对 **Context Management（CM）** 的处理。作者明确指出，不同 Search Agent 的 benchmark 差异可能主要来自 inference wrapper，因此所有核心 benchmark 都同时报告有／无 CM 的结果。

### 关键结果

同一个 Iris-mini 35B：

| Context Management | BrowseComp | BrowseComp-ZH | DeepSearchQA | HLE |
|---|---:|---:|---:|---:|
| 无 CM | 64.7 | 72.3 | 81.0 | 43.2 |
| discard-all | **82.2** | **84.8** | **86.9** | **52.3** |
| discard-all + retry | **85.9** | **85.1** | **89.9** | **52.4** |

Iris-pro 397B 上，`discard-all` 也把 BrowseComp 从 **72.6 → 88.6**。

这里的 `discard-all` 很朴素：当 running context 接近阈值但尚未得到最终答案时，清空交互历史并重新开始搜索。`retry` 则把失败尝试压成一个简短摘要，下一轮带着“哪些路线已经试过”继续；它能进一步提高分数，但每次 retry 都意味着再做一整轮搜索，所以作者把它视为偏 upper-bound 的 inference strategy，而不是默认主结果。

### 为什么重要

Search Agent 的 effective horizon 由两件不同的东西决定：

```text
Policy 是否知道下一步搜什么
×
Harness 能否让它活得足够久，把搜索做完
```

长上下文并不保证有效搜索寿命同样长，因为 tool observation、网页文本和反复查询会快速消耗 context。CM 的作用经常不是让模型“更聪明”，而是让一个已经学会搜索的 Policy 不要在证据链闭合前被历史拖垮。

这也是 benchmark 应该改变的地方：若只公布 `best harness score`，很难判断一项工作改进的是 Policy、Context Management、retry budget 还是 Judge。Iris 主动同时给出 no-CM 结果，是比单个高分更有价值的实验习惯。

### 可信度与局限

BrowseComp、BrowseComp-ZH 和 HLE 最终仍依赖 LLM judge；这些分数不是完全程序化 oracle。训练 pipeline 也同时改变了数据、SFT-RL curriculum 与 RL infrastructure，无法把整体模型提升归因于单个技巧。

另外，`discard-all` 的收益高度 benchmark-dependent。Iris-mini 在 BrowseComp 上可达 +17.5 points，而 HLE 只有 +9.1；作者的解释是 BrowseComp 更常真正耗尽 context。CM 不应被写成“所有 Agent 都能免费 +10～20 分”的通用外挂。

### 最值得继续追踪

搜索系统最需要统一报告的是：`answer quality × tool calls × total retrieved tokens × context resets × wall-clock × cost`。只报 pass@1 仍会奖励无限增加 retry / reset 的系统，而隐藏真实 serving 代价。

## 4. Allegro AlleCompanion：推荐“关系”必须和 Placement / Intent 一起定义

**原始来源：** [Beyond Co-purchase Relation: Evolution of Complementary Recommendations at Allegro](https://arxiv.org/abs/2609.05063)

### 发生了什么

互补推荐很容易被简化成 co-purchase：经常一起买的商品就是 complement。但现实交易里，共购包含大量噪声；同类替代品、一次性囤货、家庭成员不同需求、促销组合都可能制造共购边。

Allegro 的 AlleCompanion 在神经检索前后加入一套更显式的 compatibility layer：category-constrained Two-Tower + Category Adapter，再通过 ComCat mapping 把专家规则、人工反馈、LLM reasoning 与统计 mining 合并为 category-level compatible relation。系统面向 Allegro 超过 2000 万月活买家，在 Product Page、Pre-Cart、In-Cart 与 Sponsored placement 中分别做线上实验。

### 关键结果

| Placement | 关键指标 | Web | App |
|---|---|---:|---:|
| Product Page · Organic | GMV | **+8.05%*** | **+9.35%*** |
| Pre-Cart · Organic (filtered) | v-CVR | **-0.28%*** | -0.04% |
| In-Cart · Organic | c-CVR | **+4.98%*** | +1.21% |
| In-Cart · Organic | GMV | **+21.25%*** | **+15.73%*** |
| Product Page · Sponsored | v-CVR | **+0.53%*** | +0.13% |

`*` 为论文报告的 \(p<0.005\)。Sponsored carousel 的整体 GMV 基本中性，但作者报告由于 CTR 改善，广告收入约提升 50%。

真正值得注意的不是最大 uplift，而是**同一关系在不同触点表现方向不同**。Pre-Cart 中某个过滤版本显著伤害 Web v-CVR；到了 In-Cart，same-category mapping 却非常强。这意味着“互补”本身不是固定商品属性，而是用户当前决策阶段的一部分。

### 为什么重要

推荐系统经常把 relation learning 设计成一个脱离页面位置的全局 embedding：

\[
score(i,j)=f(e_i,e_j).
\]

但这里更合理的对象接近：

\[
score(i,j\mid placement,\ intent,\ cart\ state).
\]

当用户还在 Product Page 浏览时，替代／兼容关系可能帮助探索；临近结账时，用户更在意“能不能一起买、能不能一次发货、是否减少额外操作”。同一 pair 的业务价值会随着 funnel stage 改变。

这也提醒做 generative recommendation 的团队：把所有行为 token 放入更大模型，并不能替代对 placement 与决策阶段的明确建模。

### 可信度与局限

这是 production A/B 证据，比离线 Recall/NDCG 更有价值，但仍是 Allegro 单一市场和特定推荐位的一方结果。不同指标也不能混读：Sponsored 的“约 50% 广告收入提升”来自该 carousel，不代表平台整体广告收入提升 50%；Product Page 的 v-CVR 并没有和 GMV 同幅增长。

各 placement 同时包含模型、过滤规则、category mapping 与 UI context，无法把 uplift 归因给 Two-Tower、Category Adapter 或 LLM-assisted mapping 的单一组件。

### 最值得继续追踪

最值得看的是长期用户效应与 cross-placement cannibalization：某个位置 GMV 增长是否只是把其他位置的转化前移；以及 ComCat 的 LLM / HITL category relation 在 catalog 更新后如何自动刷新、如何验证错误 mapping。

## 5. KVLoRA：量化后的 KV Cache 也可以做“模型适配”，但别只看 PPL

**原始来源：** [Quality Recovery for Quantized KV Caches via Low-Rank Attention Adaptation](https://arxiv.org/abs/2609.04263)  
**代码：** [saifmb0/kvlora](https://github.com/saifmb0/kvlora)

### 发生了什么

大多数 KV Cache quantization 工作把问题定义为“怎样设计一个更好的 quantizer”。这篇工作换了角度：**先固定 cache format，不再改 quantizer，然后让模型自己适配这个有损 cache。**

具体做法是在 attention Q/K/V projection 上训练很小的 low-rank adapter。Teacher 使用 floating KV cache，Student 在训练时真的走 physically packed incremental cache；优化目标让 Student 在量化后的真实执行路径中逼近 floating-cache Teacher。训练结束后，LoRA 还可以 merge 回 projection weight，不一定保留额外 adapter branch。

### 关键结果

4-bit affine cache：

- TinyLlama-1.1B QKV adapter：恢复 **54.24% ± 2.47%** held-out PPL gap；
- Gemma-4-12B QK adapter：恢复 **75.96% ± 4.04%**；
- Llama-3.1-8B + KIVI K2V2：一个 validation-selected run 恢复 **60.42%**；
- KVarN K4V2：恢复 **37.61%**。

Gemma-4-12B 的 RULER 4K/8K 子集平均分：

| Cache | Score |
|---|---:|
| Floating | 46.15 |
| 4-bit Packed | 42.80 |
| Adapted | **48.33** |

但 aggregate 很会骗人：adapted model 的 multi-value retrieval 和 common-word extraction 变好，single-needle retrieval 反而下降，variable tracking 几乎所有设置都做不好。

最重要的负结果来自 2-bit stress test。扩大 adapter capacity 与 calibration 后，PPL 已非常接近 floating，但 NIAH 只恢复 **11–12/180**，远低于 floating cache 的 **170/180**。另一个短 QK run 更夸张：normalized PPL gap 恢复约 98.5%，却是 **0/90 retrieval**。

### 为什么重要

KV 量化不只是在压缩一个被动内存对象。量化后的 K/V 会改变未来所有 attention 读取，因此模型的 Q/K/V projection 也可以针对这种系统性误差重新对齐。

这提供了一个很实用的部署路径：

```text
选择已有低比特 KV format
→ 固定 quantizer / kernel
→ 在真实 packed-cache path 上做短后训练
→ merge attention adapter
→ 保持部署 cache 格式不变
```

对于已经确定使用 KIVI/KVarN/自定义 4-bit cache 的服务，可能比重新设计整套 quantizer 更容易落地。

### 可信度与局限

主要 4-bit affine 实验有三 seed，但 KIVI / KVarN 结果使用 validation-selected run，证据强度较弱。RULER 也只覆盖 4K/8K 的四类任务，不是完整长上下文能力测量。

最关键的局限已经由论文自己暴露：**PPL 和 retrieval behavior 可以严重解耦。** 因此“恢复了 X% quantization gap”必须明确是哪一个 metric，不能把 PPL gap recovery 自动解释为“恢复了 X% 长上下文能力”。

### 最值得继续追踪

下一步最需要的是 32K–128K 真实 workload 下的 `quality × cache bytes/token × decode throughput × adapter merge cost`，以及同一 adapter 在不同 prompt domain、不同 KV kernel 实现上的 transfer 稳定性。

## 6. MaxKernel：Kernel Agent 真正需要的是搜索图、Profiler 和持久状态

**原始来源：** [MaxKernel: Agentic Kernel Generation for TPUs](https://arxiv.org/abs/2609.04523)  
**代码：** [AI-Hypercomputer/accelerator-agents · MaxKernel](https://github.com/AI-Hypercomputer/accelerator-agents/tree/main/MaxKernel)

### 发生了什么

写高性能 kernel 的难点并不是生成一段语法正确的代码，而是一个循环：理解 workload → 选择硬件策略 → 实现 → 编译 → correctness test → profile → 定位瓶颈 → 再修改。MaxKernel 把这个循环显式化成 Agent Harness，并提供三种工作方式：human-in-the-loop、单 Agent autonomous loop，以及 graph-based parallel / beam search。

Graph search 中，每个节点不只存 source code，还保存计划、编译／正确性结果、profiling metrics 和 parent relation。失败分支不会塞满主 Agent context，但仍作为可搜索状态保留。这和近期长期 Agent 的共同趋势很一致：**把探索历史变成外部结构化状态，而不是纯聊天记录。**

### 关键结果

JAXBench 50 个 TPU workload，统一使用 Gemini 3.1 Pro：

| 方法 | 编译成功 | 正确 | 几何平均加速 |
|---|---:|---:|---:|
| Best-of-N | 10/50 | 10/50 | 1.08× |
| MaxKernel Auto | 49/50 | 48/50 | 1.39× |
| MaxKernel Parallel | **50/50** | **50/50** | **1.58×** |
| MaxKernel Beam | **50/50** | **50/50** | 1.49× |

在 8 个同时有人工 hand-tuned Pallas reference 的生产 kernel 上：

- 人工 reference：相对 JAX/XLA 几何平均 **2.02×**；
- MaxKernel Parallel：**2.32×**；
- MaxKernel Beam：1.78×；
- 8 个 workload 中，Agent best result 在 7 个上超过人工 reference。

单项差异也说明“平均胜出”不代表每种 kernel 都赢：Paged Attention 的 Agent parallel 达到 **6.74×**，人工为 2.41×；但 Ragged Paged Attention 上人工是 **4.65×**，Agent parallel 只有 1.42×。

### 为什么重要

Best-of-N 只有 10/50 正确，是一个很好的反例：**模型会写代码，不等于它能完成硬件优化。** 真正带来稳定提升的是 compile/test/profiler feedback、迭代修复、并行搜索与跨分支选择。

这也说明 automated systems research 的基本单元更像：

```text
Candidate program
+ executable verifier
+ hardware profiler
+ search state
+ selection policy
```

而不是一次 Prompt → Kernel。

### 可信度与局限

MaxKernel 是 Google / DeepMind 的第一方研究，所有 Agent query 都使用 Gemini 3.1 Pro；目前只覆盖 TPU / JAX / Pallas 生态，不能直接外推 CUDA、Triton 或 ROCm。

“超过人工”这一 headline 只来自 **8 个**有 hand-tuned reference 的 workload，而且比较的是这组参考实现，不代表超过所有顶级 kernel engineer 可以达到的最优结果。Agent search 还消耗多条并行 trajectory，论文中的 speedup 是 kernel runtime，不是“研发成本也快 2.32×”。

### 最值得继续追踪

最关键的是 cost-normalized search：固定 Gemini tokens、TPU profiling minutes 与 wall-clock 后，parallel / beam / human engineer 的 frontier 怎样变化；以及能否把不同 workload 中发现的硬件优化 pattern 编译成可迁移 Skill，而不是每个 kernel 从零搜索。

## 今日值得收藏的代码 / 学习资源

**[ACE: Adaptive Calibration-Free Expert Skipping for MoE-based LLMs](https://arxiv.org/abs/2609.05228)** 值得做 MoE inference 的团队收藏。它不靠 calibration set 或再训练，而是离线构造 Global Spectral Proxy 与 Router-Conditioned Refinement，在运行时只做表查和轻量 scalar 判断；Qwen3.6-35B-A3B 在 50% expert skipping ratio 下，相比作者最强 competing method，WikiText-2 PPL 低 7.96%、平均 downstream accuracy 高 4.15 points。它当前证明的是 quality-at-fixed-skip-ratio，真正生产价值仍要看 expert parallel / all-to-all 下 wall-clock 是否同步下降。

**[Discovery Loop](https://arxiv.org/abs/2609.05093) · [代码](https://github.com/ucsandman/discovery-loop)** 是一个很小但很干净的自动算法进化案例：从 seed circle-packing solver 出发，让 LLM 根据 scoreboard 与历史改写算法，独立 verifier 决定是否保留；15 轮、模型调用成本 \$27.72，改进 N=101–114 范围内 10 个 Packomania 纪录，提升 2.4%–5.4%。这些纪录已被 Packomania 接受，但它仍是一个可快速验证、目标极明确的优化问题，不能外推成通用 scientific discovery。

**[TruthInsightBench](https://arxiv.org/abs/2609.05079) · [代码](https://github.com/TruthInsight-stack/TruthInsightBench)** 则专门反过来测 AI Scientist 的“发现能力”。40 个 blind tasks 来自 10 个科学领域，只给中性研究目标与冻结数据，不告诉源论文结论；四个 coding agent 在同一 frozen base model 上聚集在 58.4–60.3/100 的窄平台，主要缺陷集中在 controls、robustness、falsifiability 与 cross-dataset generalization。它提醒我们：会执行分析和写报告，与会做可信科学判断仍有明显距离。

**[Trace2Tower](https://arxiv.org/abs/2609.05261)** 适合继续追踪 Agent Skill Evolution。它不把 trajectory 平铺成若干摘要，而先把 step 抽象成 canonical event，再用 transition / outcome graph 诱导 action template、procedure、strategy 三层 Skill Tower；摘要报告 ALFWorld 87.31% success、10.35 steps、0.26 invalid actions，WebShop exact success 50.67%。目前更应看完整 ablation 和开源可复现性，而不是只凭摘要数字判断其优于 Wiki / SkillBank 路线。

## 今日可立即实践的一件事

给正在做的 **GRPO / OPD / Tool-Agent RL** 加一个最小的 **“未来 Teacher 是否可外推”诊断**，先不要实现完整 RISE。

保存同一训练 run 中每隔固定步数的 5–10 个 checkpoint。在若干代表性 layer / module 上计算相邻参数更新：

\[
\Delta_t = W_t-W_{t-1}.
\]

然后至少检查两个量：

```python
metrics = {
    "adjacent_update_cosine": [],
    "trajectory_pca_explained_variance": [],
}
```

第一，计算 \(\cos(\Delta_t,\Delta_{t-1})\)，看优化方向是否具有可持续的局部一致性；第二，把多个 checkpoint 相对初始权重的 displacement 做低秩 PCA / randomized SVD，看前 1–3 个方向能解释多少轨迹方差。

随后只做一个离线 probe：取当前 checkpoint \(W_t\) 与 trailing anchor \(W_a\)，构造几个很小的外推系数：

\[
W_{probe}=W_a+\beta(W_t-W_a),\qquad
\beta\in\{1.02,1.05,1.10\}.
\]

**不要直接把 probe 用作新 Policy 上线或继续训练。** 只在一个小型 verified validation set 上看：reward / accuracy 是否先升后降、response length 是否异常、KL 是否爆炸。如果 \(\beta>1\) 很快全面退化，说明你的 trajectory 不具备 RISE 所依赖的局部可外推结构，不应照搬方法。

停止条件也应该很明确：

- checkpoint displacement 的前几个方向解释率很低；或
- adjacent update cosine 长期接近 0 / 正负剧烈振荡；或
- 极小 \(\beta\) 已触发 reward、长度或行为异常；

满足任一项，就优先改进 RL 稳定性／数据 curriculum，而不是继续做 self-extrapolated Teacher。

这个小实验真正回答的是：

> **你的 RL 轨迹是在沿一个可利用的能力方向前进，还是只是在高维空间里不断局部抖动？**

今日主线： Open-Weight Continual Learning · Agent-Native Interfaces · Enterprise RAG Scale · Graph Recommendation · Visual Context Compression · Long-Agent Serving Reliability

今日核心判断

  1. 开放权重模型的“持续学习”开始出现更系统的工程范式，但不能把最终训练 run 的低成本误读成整个 frontier model 项目的低成本。 Thomson-1.0-Large 基于 Qwen3.5-397B 做全参数 mid/post-training，作者报告最终三周训练 GPU 成本低于 45 万美元；但同一论文给出的总开发成本约 4000 万美元。真正可复用的资产是数据治理、评测、训练基础设施和持续学习配方，而不是一个“45 万美元即可复制 frontier model”的结论。
  2. Computer-Use Agent 的瓶颈可能先在接口层，而不在视觉模型本身。 ASIL 用结构化 JSON 状态和可执行语义动作替代 screenshot-and-click，在 15 个应用、380 个任务上显著降低动作数并提高成功率；这支持“Agent 应优先获得语义化软件接口”的方向，但它也说明不同应用接口质量差异很大，MCP/API 设计本身会成为新的能力上限。
  3. 企业 RAG 的真实困难不是多放几万份文档，而是规模、时间关系和跨文档一致性同时上升。 CorporateBench 构造了 12–10,000 人的四家合成企业、超过 23 万份文档，并保持跨文档时间知识一致；模型随着规模增长显著退化，尤其 temporal relationship extraction 和复杂 KB/RAG QA。这比小型多跳 QA 更接近企业知识系统的失败模式。
  4. 推荐系统仍有大量价值来自“把经典方法做对并做大”，不一定需要 LLM。 一个 1.94 亿用户、280 亿边的好友推荐 GNN 通过 multi-hash ID embedding 把原本超过 200GB 的 ID 表缩小 98% 以上，再用按时间排序的 CSR + 二分搜索把 temporal neighbor sampling 从 $O(\deg(v)+k)$ 降到 $O(\log \deg(v)+k)$；线上好友新增 +16%、独立加好友用户 +11.5%。
  5. 长文档压缩不能只追求“每张表占更少视觉 token”。 A Table Is Worth 64 Tokens 发现，过度缩小表格会让 VLM 用更长、更低效的 reasoning 来补偿可读性损失；更有效的方式是先用低分辨率表格做 relevance routing，再对少量相关表格恢复原生分辨率推理，长文档上总 token -41%、accuracy +7 points。
  6. Agent serving 的稳定性测试必须使用自然长程轨迹，而不是只跑短 throughput benchmark。 一份 8 月 30 日的 NVIDIA Developer Forum 复现报告中，Qwen3.8-Flash-Next NVFP4 在双 GB10、约 31K context、5 个执行轮次和 15 次 tool call 后触发 invalid sampling probabilities、CUDA assert 与 TP/NCCL 崩溃；部分 50–60 tok/s 的更快配置还会静默破坏长上下文检索。工程上应该把语义正确性、恢复能力和长时间 soak test 放进性能资格门槛。

1. Thomson：持续学习开放权重模型，最终训练成本低不代表整个项目便宜

一句话结论： Thomson 最值得看的不是“45 万美元训练出接近 frontier 的模型”这个 headline，而是它展示了一个组织如何围绕开放权重 checkpoint 建立持续 mid/post-training、领域数据、评测和自托管推理的完整模型工厂；论文自己给出的总开发成本约 4000 万美元，足以否定过度简化的低成本叙事。

原始来源： Thomson: Continual Learning of Frontier Models for SovereignAI

发生了什么

Thomson 团队以 Qwen3.5-397B 为大型底座、Qwen3.6-35B 为小型底座，采用全参数更新而不是 LoRA，也没有依赖大规模 teacher distillation。整个方法强调 continual mid-training + post-training：尽量用有限、高价值的干预增加法律、税务、新闻、Deep Research、Agent 等专业能力，同时控制通用能力遗忘。

论文报告 Thomson-1.0-Large 的最终训练 run 持续约三周，GPU 成本保守估计低于 45 万美元；但项目总开发成本约 4000 万美元，包含人员、计算、领域专家和供应商合作，并且其中大部分投入到可重复使用的研究、基础设施工程和实验，而不是最后一次训练。

关键结果

为什么重要

这篇工作对“企业是否一定要从零预训练自己的大模型”给出一个更现实的中间路径：

真正的护城河更可能来自这套迭代系统，而不是一次 checkpoint 训练成本。对于垂直行业，“买一次训练算力”通常远比构建高质量数据、可靠评测和长期模型运维便宜。

可信度与局限

所有主要能力数字都来自作者自己的综合评测套件，部分任务使用统一自动 grader，不等于第三方公共 leaderboard。论文也明确说明部分安全评测没有人工 calibration，且没有覆盖 adaptive attacks，因此不能把结果视为通用安全认证。

另外，最终 run <45 万美元与总开发约 4000 万美元之间的巨大差距非常关键。任何只引用前者、忽略后者的“低成本 frontier model”结论都不严谨。

最值得继续追踪

最值得看的是未来独立团队能否复现“持续学习后专业能力上升、基础能力少遗忘”的结果，以及 Thomson 的数据/评测基础设施能否跨底座迁移。相比单次 benchmark，每一代底座升级后需要多少重新训练和评测成本更能决定这条路线的经济性。

2. ASIL：Computer-Use Agent 也许不该继续主要靠 Screenshot + Click

一句话结论： 让 Agent 看像素并猜坐标，是对人类 UI 的被动模拟；如果软件能提供结构化状态和语义动作，Agent 可以在更少步骤里完成任务，并且更容易训练和验证。

原始来源： ASIL: Replacing Screenshot-and-Click with Structured State and Semantic Actions
项目页： ASIL Project

发生了什么

ASIL（Agent-Software Interaction Layer）为软件暴露结构化 JSON observation，并提供 code-executable semantic action，优先使用应用能提供的最深层语义访问路径，而不是统一退化成截图和鼠标坐标。

作者覆盖 15 个应用，构建 300 个单应用任务和 80 个多应用任务。闭源强模型在 ASIL 上的成功率超过 80，同时平均每个任务少于 5 个动作；相同任务如果换回 screenshot-and-click，即使修复 runtime 并给 50 步预算，严格成功率仍只有 6.6 / 26.6，在更容易的 OSWorld-comparable 子集也只有 15.0 / 53.3。

关键结果

结构化接口还明显降低了小模型学习难度：

模型原始+ SFT+ On-policy RL
Qwen3.5-2B58.072.174.4
Qwen3.5-9B66.680.482.2

在 matched task 上，ASIL 比 LibreOffice UNO API 高 28–38 个 strict-success points，但只与 draw.io 的 MCP content contract 大致持平。这一负结果很重要：结构化接口并不天然比所有原生 API 更强，接口语义设计本身决定了上限。

为什么重要

Computer Use 的常见路线是不断提高视觉理解、定位和点击能力，但这实际上让模型反复解决本可以由软件直接暴露的状态识别问题。对于内部企业软件或可控客户端，更合理的架构可能是：

1
2
3
4

语义状态 / 可执行动作优先
→ 原生 API / MCP
→ DOM / accessibility tree
→ 最后才回退到 screenshot-and-click

这样做还更容易记录 action provenance、做 deterministic verification，并减少 UI 微小改版造成的脆弱性。

可信度与局限

ASIL 的 benchmark 和接口实现由同一研究工作设计，存在 interface-benchmark co-design bias。真实世界应用经常无法提供干净的语义状态，或者 API 权限远高于普通用户 UI 权限；过度依赖结构化接口也可能让 Agent 在“API 不可用”时失去泛化能力。

最值得继续追踪

重点看 semantic action schema 是否能跨应用形成稳定标准，以及同一个 Agent 在结构化接口不可用时能否平滑降级到视觉控制。对 MCP 生态而言，接口质量 benchmark 可能和模型 benchmark 一样重要。

3. CorporateBench：企业知识 RAG 在规模和时间关系上仍然很脆

一句话结论： 23 万份文档并不可怕，真正麻烦的是“同一公司世界长期演化、关系有起止时间、答案横跨多份通信记录”；CorporateBench 让企业 RAG 的规模问题终于比常见 multi-hop QA 更接近现实。

原始来源： CorporateBench: Large-Scale Q&A Benchmarking with Temporal Knowledge Bases

发生了什么

CorporateBench 用一个持续演化的 ground-truth knowledge base 生成四家合成企业，规模从 12 人一路扩到 10,000 人，评估语料超过 230,000 份文档；完整数据实际达到 263,466 份文档。每份邮件、人员关系、项目和时间状态都从同一个 KB 派生，因此能够保证跨几十万文档的逻辑一致，而不只是独立合成一堆 QA pair。

它同时评估 entity / relationship / temporal relationship extraction，以及三类 QA：KB QA、Topic QA 和 Integrated QA。QA 既可以走普通 RAG，也可以让 Agent 直接查询结构化 ground-truth KB，从而把“检索失败”和“推理／工具调用失败”分开。

关键结果

随企业规模从 S → XL 增加，entity extraction 相对稳定，但 relationship 和 temporal relationship 明显下降。例如三种 extraction 模型在 temporal relationship 上：

  • S 规模 $F_1$：0.142–0.470；
  • XL 规模 $F_1$：0.062–0.173。

RAG 的 KB QA 同样随规模下降。GPT-5 Nano 从 S 的 0.527 降到 XL 的 0.244，GPT-5.1 从 0.470 降到 0.269。作者还观察到结构化 KB tool 路径产生的程序性错误比 RAG 多 4.7×（547 vs 150），说明“直接给结构化真值”也没有消除 Agent tool-use failure。

为什么重要

企业知识系统中的很多问题不是“找一段最相似文本”，而是：

1
2
3

谁在某个时间段属于哪个团队？
谁先后参与过某个项目？
这些人在特定时间窗口的邮件里讨论过什么？

这需要同时处理 retrieval、temporal state、entity resolution 和 multi-step tool use。CorporateBench 还提供了一个有用的对照：同一问题既可以走 noisy document RAG，也可以走 structured KB，从而判断瓶颈究竟在检索还是推理。

可信度与局限

它仍是合成公司世界。虽然逻辑一致性比普通合成 QA 强得多，但真实企业文档存在缺失、矛盾、权限、版本、隐语、组织变动和非结构化附件，这些问题没有完全覆盖。

另外作者为了控制 API 成本主要评估较轻量模型，不能据此断言最强 frontier model 在 26 万文档下也会以同样幅度下降。

最值得继续追踪

最有价值的下一步是加入 ACL / provenance / contradiction / document deletion / stale state。企业 RAG 真正上线后，答错通常不只是“没检索到”，还可能是检索到了用户不该看的材料，或把旧组织状态当成当前事实。

4. 1.94 亿用户、280 亿边：好友推荐 GNN 的工程缩放比模型花哨更重要

一句话结论： 这篇 CIKM 2026 工作非常适合提醒推荐算法从业者：在超大图上，ID embedding 内存和 temporal sampling 复杂度往往比再叠一层 Transformer 更先决定系统能否上线。

原始来源： Scaling Graph Neural Networks for Friend Recommendation: Multi-Hash User Embeddings and Temporal Neighbor Sampling
代码： makut/VK-GNN

发生了什么

作者在 1.94 亿用户、280 亿边的生产社交图上部署 message-passing GNN。两个主要问题非常朴素但致命：完整用户 ID embedding table 超过 200GB；而很多高连接度用户有数万朋友，若每次 temporal sampling 都扫描完整 adjacency list，训练和推理都无法承受。

解决方案也非常工程化：

  • 用 multi-hash embedding 作为主要 node ID representation，把 ID table 缩小超过 98%；
  • 边按时间戳排序成 CSR，查询 cutoff time 时先二分定位，再采样 $k$ 个邻居，把复杂度从
\[O(\deg(v)+k)\]

降成

\[O(\log \deg(v)+k).\]

关键结果

在线 A/B 相对强生产基线：

指标提升
来自推荐的好友新增+16%
至少新增一个好友的独立用户+11.5%

代码仓库公开了 PyTorch + DGL 的训练／推理框架，以及 Java + JNI/C++ temporal sampler；两边使用共享 YAML 配置和序列化 minibatch 协同，接近作者描述的生产结构。

为什么重要

推荐系统中常见的“模型不够强”问题，有时实际是“无法给模型提供最有信息量的 ID 和时序邻居”。Multi-hash 牺牲部分独立 ID 自由度换取 98%+ 内存缩减，而 temporal CSR 则把真正阻塞吞吐的高 degree 用户处理掉。

这类优化的价值在于，它们同时改变了可训练模型容量、采样新鲜度和线上延迟，不是单纯压缩部署成本。

可信度与局限

线上结果是作者第一方生产实验，外部无法复现其社交图分布和 A/B 流量。Multi-hash 还会引入 collision，不同业务对 ID individuality 的依赖程度不同；朋友推荐的图结构极强，结论不能直接外推到内容推荐或广告排序。

最值得继续追踪

建议关注 collision rate、长尾节点质量、时间新鲜度和在线 latency 的联合 Pareto，而不只看 embedding table size。代码已经公开，最值得复现的是 multi-hash embedding + temporal sampler 的系统收益，而不是重新跑作者的业务指标。

5. A Table Is Worth 64 Tokens：低分辨率适合“找表”，不一定适合“读表”

一句话结论： Optical context compression 的最优用法可能不是把所有内容永久压小，而是把低分辨率视觉表示当作 routing index；真正需要精确推理时，再恢复少量高分辨率原文。

原始来源： A Table Is Worth 64 Tokens: Pixel-level Compression for Multi-Table Document Question Answering

发生了什么

作者用 5 个 VLM、2 个 benchmark、5 档 visual-token budget 系统测试多表格文档 QA。结果显示，表格以原生分辨率作为图片输入时，性能和 token 效率可以与文本表示相当；但继续下采样后，模型并不会简单“少看一点然后便宜一点”，而会生成更长、效果更差的 reasoning 来补偿模糊输入，预期的 token 节省因此被抵消。

不过，极度压缩的表格仍然保留了足够信息去判断“这张表和问题有没有关系”。作者据此做了 training-free 两阶段方法：

1
2
3
4
5
6
7

所有表格：低分辨率 / 少 token
    ↓
先做 relevance selection
    ↓
只把相关表格恢复到 native resolution
    ↓
精确推理

关键结果

在长文档上，相比所有表格都以 native resolution 做单步 QA：

  • 总 token 减少 41%；
  • accuracy 提高 7 points。

相较最省 token 的单步压缩方案，它还进一步减少 15% token，同时没有 accuracy 损失。

为什么重要

这和 RAG 的 coarse-to-fine retrieval 非常像：低成本表示主要负责 recall / routing，高保真表示负责最终 reasoning。对 PDF Agent、财报分析和多模态 Deep Research，这通常比“全量高分辨率”或“全量极限压缩”更合理。

可信度与局限

论文只覆盖表格类视觉结构；照片、复杂图表、公式、扫描 OCR 的压缩行为可能完全不同。两阶段方法也引入了一次额外模型调用，因此端到端 latency 是否下降，要看模型 batch、视觉 encoder 和 API 计费方式，不能只用 token 数推断。

最值得继续追踪

应该把 routing recall 单独测出来。只要第一阶段漏掉关键表格，第二阶段再强也没有机会恢复。未来更有价值的是不同文档元素使用不同压缩率：表格、图表、正文、公式分别决定自己的 routing representation 和 high-fidelity fallback。

6. 一条值得读的推理故障复盘：更快的配置可能“看起来正常，但语义已经坏了”

一句话结论： Agent inference qualification 不能只测短 decode throughput。自然长程 trajectory 会把 speculative decoding、CUDA Graph、overlap scheduling、长上下文状态和断流恢复之间的组合缺陷放大出来。

工程复盘： Qwen3.8-Flash-Next NVFP4 on 2x GB10: long-agent service-crash isolation + 42.4 tok/s qualified TP2
复现代码： hellojiaru/qwen38-flash-next-dual-gb10

发生了什么

8 月 30 日的一份 NVIDIA Developer Forum 报告记录了一个双 GB10、SGLang TP2、Qwen3.8-Flash-Next ModelOpt NVFP4 的真实长程 Agent canary。Agent 已完成 5 个执行轮次、15 次 tool call、总 context 约 31K 时，服务出现：

1
2
3
4
5
6

invalid sampling probabilities
→ CUDA device-side assert
→ SGLang scheduler exception
→ NVIDIA Xid 43
→ NCCL / TP termination
→ 两个 model container 重启

这不是 OOM：日志显示 KV/token 使用约 6%，context 也远低于配置的 262K。作者通过受控 matrix 排查后，只能得到一个谨慎结论：关闭 overlap scheduling 是当前已验证的稳定 operating boundary，但尚不能证明 overlap 是唯一根因。

关键结果

最终保留的 eager / no-overlap 配置：

  • 2,048-token code workload median：42.39 tok/s；
  • 16,384-token continuous generation：48.01 tok/s；
  • 约 25K marker retrieval：通过；
  • 20-request bounded-concurrency：通过。

更值得注意的是，一些配置可以跑到 50–60 tok/s，却被淘汰，因为会出现 punctuation loop、vision failure 或 25K retrieval semantics failure。也就是说，速度更快但输出“看起来像正常文本”的配置，可能比显式 crash 更危险。

为什么重要

Agent workload 与普通 benchmark 的区别在于状态长期积累：

1
2
3
4
5
6

长 prefill
+ 多轮短 decode
+ tool gap
+ speculative state
+ context growth
+ client disconnect / resume

一个内核在 2K throughput test 中稳定，不代表它在 30K 自然轨迹和 tool-loop 边界仍然正确。因此性能验收至少应该加入：long-context retrieval、semantic invariants、断流恢复、post-long-request short request，以及多小时 soak test。

可信度与局限

这是社区工程师在 NVIDIA Developer Forum 的可复现报告，不是 NVIDIA 官方产品结论，也没有经过论文审稿。作者本人明确把最终配置称为 correctness-qualified canary，而非 production-qualified；原始 31K 自然 Agent trajectory 也还没有在最终配置下完整重放。

最值得继续追踪

建议继续看 SGLang、FlashInfer 和 NVIDIA kernel 侧是否能定位底层 corruption root cause。对任何自建推理栈，更现实的做法是把“语义正确性 gate”与“性能 gate”放在同一套 benchmark 中，拒绝只凭 tok/s 上线。

今日值得收藏的代码 / 学习资源

VK-GNN 是今天最值得直接读的生产推荐代码。它不是一个只有模型定义的论文仓库：Python 侧包含训练、推理、checkpoint 与 multi-hash embedding，Java/JNI/C++ 侧实现 timestamp-sorted CSR temporal sampler，适合研究超大图推荐如何拆 CPU sampling 与 GPU training。

GraphMemix 值得长期 Memory / multimodal Agent 方向收藏。它不在历史到来时先做 question-agnostic summary，而在 query 到来后构建 evidence graph，再用 node utility 与 anchor-conditioned edge utility 选一棵 evidence forest。Qwen3-VL 设置中，四个 benchmark 的 Judge Accuracy macro-average 从最强公开 baseline 的 49.80% 提高到 61.55%（+11.75 points）。但当前 GitHub 仓库 仍为空，因此代码可复现性暂时不足。

Agentic Conversational Recommender for a Live E-commerce Catalogue 是 RecSys 2026 demo paper，配套 infobip/infobip-agentic-crs。它用 per-item hash 做 catalogue delta sync，只更新新增／修改／删除商品；LLM 主要负责 intent classification 与 preference elicitation，真正检索、重排和 diversity 仍由专门函数承担。适合用来观察“Agentic RecSys”如何避免把整个推荐 pipeline 都变成 LLM。

Stageboost 来自 eBay，值得做推荐实验的人看它的 counterfactual offline metric。模型训练数据来自随机实验，通过“模型预测的 signal 与随机实际展示 signal 恰好一致”的样本估计部署后的 conversion；Lean StageBoost 最终上线后，overall GMB +0.08% 但不显著，重点品类 GMB +0.58% 且显著。这个结果很好地提醒：离线 uplift 估计要服务于在线决策，不应把整体不显著结果包装成全站增长。

X.com｜近期高信号技术讨论

本轮没有发现同时满足 原始 /status/ URL、作者身份、可读取技术正文、72 小时内发布时间可核验 四项硬条件的帖子，因此没有使用 X Help、机构主页、趋势页或二手摘要补位。

本轮实际执行 31 个独立查询，公共搜索返回 38 条结果，但没有获得可同时核验作者、正文与近期发布时间的原始 /status/ URL。

今日最值得花 30 分钟阅读的一项

首选 ASIL。
论文原文

它值得读的原因不是“structured interface 分数更高”这么简单，而是它迫使我们重新回答 Computer-Use Agent 的一个基础问题：

我们究竟是在训练更强的 Agent，还是在逼 Agent 反复逆向解析一个原本就不适合机器使用的人类 UI？

建议按这个顺序读：先看 screenshot-and-click 的失败拆分；再看 ASIL 如何选择 deepest feasible access path；然后比较 LibreOffice UNO、draw.io MCP 与 ASIL 的结果，理解“结构化”不是充分条件，语义 contract 的质量才是关键；最后看 2B / 9B 模型的 SFT + on-policy RL，观察接口改变后为什么小模型也更容易学。

对真实企业 Agent，这一问题通常比“下一代 VLM 的 GUI benchmark 再涨几个点”更直接影响可靠性和成本。

今日可立即实践的一件事

给现有 GUI / Computer-Use Agent 做一次 Interface-Layer Ablation。选 20–50 个重复性高、结果可验证的真实任务，为同一个任务准备三条执行路径：

B. DOM / accessibility / structured UI state
C. API / MCP / semantic action

    "actions_per_task": 0.0,

    "input_tokens": 0,

再计算每种接口下的单位成功成本：

\[C_{success} = \frac{\text{Total inference + tool cost}} {\text{Successful tasks}}.\]

停止条件： 如果结构化接口成功率没有明显提高，先不要把问题归因于模型。检查 observation 是否遗漏关键状态、semantic action 是否过粗、API 权限是否与 UI 能力不一致，以及 schema 是否迫使模型做额外猜测。如果 API / MCP 路径显著减少动作数和 token，但失败集中在少数接口定义上，优先修接口而不是继续做 Agent RL。

这项实验的目标是把一个常见混淆拆开：

失败来自模型不会操作，还是软件根本没有给模型一个可操作的接口？

1. Harness-Delta Attribution：Agent Harness 的进化收益到底来自哪里？

原始论文 · HTML 全文（v1 2026-10-15 提交；10-19 新公告）。

发生了什么

近年来很多 Agent 研究保持模型权重不变，反复修改 System Prompt、工具列表、Skill、循环控制与路由逻辑，在搜索集上得到更高成功率。论文提出 Harness-Delta Attribution（HDA），试图把表面增益拆成：搜索集专用 Artifact 的过拟合收益、更多推理时计算可解释的收益、以及剩余未解释部分。其思想是先让不同 Harness 在相同计算预算和未参与搜索的任务上接受再测，避免把改长推理链、增加候选数误称为结构能力提升。

关键结果

作者研究 11 个 Executor 模型、3 个 Harness-evolution 框架，覆盖数学、代码、创意与 Agent 任务。在 21 个搜索集提升统计显著的设置中，按其分解方法，平均 54% 的增益可以由过拟合解释、14% 由 Test-time Scaling 解释；其中 14 个设置两者合计超过 50%。不少搜索集收益没有有效迁移到 Held-out。可把报告中的归因记成概念式：

\[\Delta_{\mathrm{search}}=\Delta_{\mathrm{overfit}}+\Delta_{\mathrm{compute}}+\Delta_{\mathrm{residual}},\]

但这些分量依赖作者的实验定义，残余上界不等于因果证明的可泛化收益。

为什么重要

若让自动 Agent 反复修改 Harness，然后只在用于选优的同一组题上展示“提升”，系统容易同时学到样本特有诀窍和更昂贵的调用方式。对长期自我进化 Agent，应将开发集表现、独立测试集表现、调用总 Token、调用次数和成功任务成本一并入库。尤其要记录每次变更实际修改了哪些 Prompt/工具/Skill。

可信度与局限

实验横跨模型和框架，证据比单个案例更丰富，但所有数字仍是作者在固定搜索方法、预算与基准上的结果。现实分布漂移、工具故障、企业权限链路与数据更新会造成额外偏差；“剩余收益”仅是可归因结果的上界。不能简单认定 Harness 优化无用。

最值得继续追踪

在同样 Executor 下分别记录 Raw Success、Held-out Success、Tokens/Task、Tool Calls/Task 与 Cost/Success，并做固定 Token Budget 的等预算 A/B。最重要的回归测试是：在新的时间段、不同任务模板、不同工具错误率上，收益是否仍存在。

2. ReRankID：Semantic ID 能否独立承担推荐列表的推理重排？

原始论文 · 作者 GitHub · 可申请访问的数据集（v1 2026-10-16；10-19 新公告）。

发生了什么

生成式推荐逐步用紧凑的 Semantic ID（SID） 取代冗长商品 Caption 表示 Item。SID Embedding 经过用户—物品交互训练可能包含协同信号，但 Next-item Prediction 的训练目标未必教会模型“对给定候选列表重新排序”。ReRankID 让模型只看到用户历史和候选 SID，要求输出理由与候选排序，并控制候选数量、历史长度和 Item 展示方式。

关键结果

基线 OneRec 模型常见一个容易漏测的错误：把候选输入顺序直接复制为输出顺序。为此作者比较 SFT、拒绝采样自训练、On-policy Distillation、以及按排名质量给奖励的 RLVR。最强 8B + graded ranking reward 模型在 SID-only 排序上达到强文本 LLM Reranker 的水准，而对照的文本提示约 20× 更长。项目公开了 800 用户的评测集（400 Dev + 400 Test）、6,000 条 RLVR Prompt、训练脚本与逐用户输出；训练好的 Adapter 未直接发布。可检查的目标如 NDCG@5：

\[\mathrm{NDCG}@5=\frac{\sum_{i=1}^{5}\frac{2^{rel_i}-1}{\log_2(i+1)}}{\mathrm{IDCG}@5}.\]

为什么重要

“SID 是低 Token 成本的 Item 表达”并不足以证明 Agent 能做好重排。排名策略需要新的后训练目标，尤其要消除位置偏置和候选 Slate 依赖。排名好也不表示自然语言解释可靠：论文发现模型在比较取舍时有优势，但对具体物品特征的表述准确率更差。这对电商推荐与解释可审计性是核心约束。

可信度与局限

代码、数据清单和逐用户输出可核验，但数据受原始 RecIF 访问条款约束，需要申请；复现通常需要多 GPU 和额外 API。800 个测试/开发用户规模较小，尚未证明在线 CTR/GMV 效果，也没有因果证明 SID 学到的所有信息来自行为信号。

最值得继续追踪

固定 Item 候选与用户历史，随机打乱 Slate 顺序 20 次，分别测量 Hit@1、NDCG@5、输出置换一致性、异常物品解释率和 Prompt Token。在小资源实验中优先复现无训练的输入顺序复制诊断，再考虑 RLVR。

3. ECHOES：GUI Agent 怎样在压缩旧截图时保留关键状态？

原始论文 · HTML 全文（v1 2026-10-14；10-19 新公告）。

发生了什么

长程 GUI Agent 每一轮都有截图、动作与新页面；持续携带所有旧图像会使视觉 Token 成本随会话增长，而简单摘要又可能忘记已选择的选项、弹窗、隐藏依赖。ECHOES 使用 Compression–Think–Action（CTA） 格式，在每轮递归维护文字记忆。训练期间，同一模型以多张历史图像作为特权教师，向仅保留压缩文字历史的学生提供密集的 Token-level OPD 信号。

关键结果

论文进一步提出 Perception–Memory Fidelity（PMF）Gap-guided OPD-RL，针对视觉识别与记忆保真差距动态调整蒸馏与任务奖励的权重，并定期更新教师。评估包括四组 GUI 基准，以及从真实失败轨迹构造的 ECHOESBMK。作者报告任务效果、状态记忆保真和推理费用的正向权衡；摘要没有给可跨模型、硬件统一引用的绝对百分点，本期不编造。

为什么重要

记忆摘要可以设计成状态转换：

\[m_t=\mathrm{Compress}(m_{t-1},o_t,a_{t-1}),\qquad a_t=\pi(o_t,m_t,g).\]

其中关键是保证与任务成功相关的字段在多次递归压缩后仍然存在。这一模式适用于 Shopping Agent 中的多轮筛选条件、Coding Agent 的失败上下文以及多工具操作的操作历史。

可信度与局限

特权教师在训练期能看到部署学生看不到的旧截图，可能出现训练/部署观察差异。摘要不证明每类 GUI 状态都适合文本压缩；图形位置、地图、细粒度颜色和非文字状态可能丢失。需要测量压缩保存成本、遗忘率和失败恢复，而非只看单轮成功率。

最值得继续追踪

构建跨 20—50 轮的小型 GUI Trace，人工标出“必须保留的事实”，比较保留全部图、滚动摘要、CTA 和记忆结构化字段在状态一致性、Token、复位成功率上的差异。

4. QEMem：Memory Retrieval 的目标应是证据充分，而不仅是相关

原始论文（v1 2026-10-15；10-19 新公告）。

发生了什么

一个长期记忆查询可能要求同时满足日期、项目、版本、否定例外和某次已经确认的决策。检索 Top-K 中每条都很相关，合在一起却可能仍缺少关键条件。QEMem 将记忆使用改为面向问题构造充分证据集：先跨粒度探索，再把文本整理成附有来源的 ViewCard，最后检查剩余证据缺口并选择性恢复信息。

关键结果

论文在共享记忆存储、以 Claude Opus 4.5 作为 Executor/Judge 的 LoCoMo 设置下报告 91.43% LLM-judge Accuracy，比最强已评估对照 MemR³ 高 7.6pp、比 NEMORI 高 10.7pp。这意味着处理证据之间的关联和缺失可能比单纯提高相似度排名更关键；但同一结果不证明所有 Judge 或长期记忆基准上都会领先。

为什么重要

对于 RAG/Agent Memory，应区分三个指标：相关性、证据覆盖率、答案可证实性。一个高相似度记忆项可能只给出事实的一半；一个低相似度项可能包含关键例外。更稳健的系统会显式记录“哪些条件有来源支撑、哪些条件仍未知”。

可信度与局限

ViewCard 的结构化重写可能漏掉细节或误归因；证据充分性检查本身也会引入额外 LLM 成本。分数依赖 Judge，且没有证明可以替代独立人工验收。实用部署必须保持引用指向原始记录，而非仅指向改写后的摘要。

最值得继续追踪

重点测试跨会话的时间顺序、约束冲突、否定指令、旧版本作废等样本；在固定检索 Token 预算下对比 Dense Top-K、Hybrid、QEMem 风格证据组合与人工核对，报告 Evidence Sufficiency@k、Unsupported Claim Rate 与 Cost per Correct Answer。

5. DRAGO：符号工具给出 SAT，也不代表自然语言目标被正确形式化

原始论文（v1 2026-10-15；10-19 新公告）。

发生了什么

LLM 把自然语言转换为 SMT、MiniZinc 或 PDDL 后，只要能够运行，Solver 可能给出 SAT/UNSAT 或计划，但运行成功只验证了模型写出的规格，无法验证规格是否忠实用户需求。DRAGO 使用按形式语言定义的确定性诊断规则，并设置一个只接受诊断错误权重严格下降的改写准入条件：

\[\mathrm{Accept}(s')\iff W_{\mathrm{diagnostic}}(s')<W_{\mathrm{diagnostic}}(s).\]

这比让另一个 LLM 不受约束地反复批评和修改更加可控。

关键结果

论文跨五组 SMT-LIB2、MiniZinc、PDDL 基准报告：未受约束的 LLM 诊断会将 11.8% 原本正确的规格修改坏；DRAGO 将其降至 1.3%。其答案准确率相对 Zero-shot +12.9pp、相对 LLM 诊断修复 +8.7pp（基准平均）。作者还识别 Planetarium 数据集一个分割中的渲染缺陷，影响 3,086 个样本，强调 Benchmark 本身也必须审计。

为什么重要

这类规则可迁移到 SQL Tool Agent、权限策略、排班约束与自动化配置生成：只要诊断能确定“新增的修改确实消除了原问题且没有违反原先约束”，就能抑制修复器反复反悔。尤其对生产系统，Verifier 正确性、规格忠实度、变更可逆性要分开测。

可信度与局限

确定性诊断可以保证它检测到的特定错误，但未知的自然语言歧义和缺失业务要求仍可能漏检；“错误权重下降”不构成所有语义正确性的完备证明。各基准故障类型与正式系统差异较大。

最值得继续追踪

构造含否定、范围、优先级与例外条款的约束集，比较 LLM Critic 与确定性 Guard 的误修率、漏修率以及越权执行率。人工审计至少要抽取“Solver 可运行但业务意图错误”的正例。

6. MoE Prefill：敏感的可能是少量任务接口 Token

原始论文（v1 2026-10-15；10-19 新公告）。

发生了什么

减少 Prefill 阶段激活的 MoE Expert 数量能降低计算，但若均匀减配所有 Prompt Token，某些模型在短答 QA 的 F1 上明显下降。论文通过 Token、Layer 和 Attention Path 干预定位影响，发现部分模型的主要损失其实来自答题格式、是否遵循简洁输出指令，而非检索不到答案。

关键结果

研究涉及四个 MoE 家族。在 Qwen3-30B-A3B 上，敏感位置主要集中于答案之前两个 Chat Template Token；DeepSeek-V2-Lite 的敏感窗口落在含指令的最初 8—32 个 Prompt Token。将实际 Prompt 中约 4% 的 Token 保持完整专家，在某些预先指定对照中可让 F1 与全专家版本相差不足 1 点；随意把同等预算给文档正文更差约 3 点。11K Prompt 的 TTFT 改善约 14%，2K Prompt 未观察到明显收益。

为什么重要

一种可实验的优化是按 Task Interface / Prompt Boundary / Document Body 分配 Expert Budget。论文也提醒：如果格式遵循导致的 F1 损失占大头，那么评测必须把 Exact Answer、简洁性、Tool Schema Compliance 和真正知识正确率分开。

可信度与局限

敏感位置在实验中常处于 Prompt 两端，尚不能确认收益来自“理解应用语义”还是简单的“保留首尾 Token”。五项主要比较只有两项给出明确结论，其余未决或未执行，不能把它扩展为通用动态 Routing 规律。单卡 16GB GPU 不适合直接复现实验中的完整 30B 部署。

最值得继续追踪

进行 Token Position × Expert Count × Prompt Length 网格消融，重点测试移动 System 指令、重排 Few-shot Example 和 Agent 多轮工具消息后是否仍有效；报告真实 TTFT、P95、每任务 Token 费用与答案遵循率。

7. FINDERS：Diffusion LLM 的中间状态可以成为工业用户表征

原始论文（v1 2026-10-14；10-19 新公告）。

发生了什么

传统 User Encoder 常把跨模态历史行为串行化、使用自回归模型得到单个静态向量，但视频、搜索、购买与内容浏览在不同推荐任务中的信息价值不同。FINDERS 把 Diffusion Language Model 的多步去噪中间表示当作多粒度表征空间，通过 Denoise–Factorize–Route–Compress 将共有语义和模态相关因素分解到 Meta-slot，再由场景 Query 驱动轻量 Router 选择重要 Slot。

关键结果

作者还构建 BehaviorQA，提供带行为理由的监督；报告在十个工业场景和线上 A/B 设置中优于对照，包括统一表示与场景自适应表示。当前可核验摘要没有统一的线上绝对提升百分点，因此本期只记录“作者报告方向性改善”，不虚构 CTR 增益。

为什么重要

推荐系统常在统一用户表示的缓存复用与不同业务目标的专用特征选择之间权衡。FINDERS 的架构将共享表征与场景 Router 分开；如果不同场景（Search / Ads / Recommendation）需要的历史粒度差异很大，这种方法可能优于固定全局 Embedding。

可信度与局限

新增扩散编码器可能提高训练与在线更新成本；Meta-slot 解耦是否具有稳定语义及是否优于强自回归统一 Encoder，都依赖清楚的消融。工业 A/B 的流量分层、时长、统计显著性与延迟成本仍需进一步读全文核对。

最值得继续追踪

在同一行为序列上比较单向 AR Encoder、双向 Encoder、Diffusion Encoder 与加 Router 的版本，固定表征维度、特征更新时间和 P95 召回延迟，报告多任务加权目标与最差场景退化。

8. GlobeBench：文本世界模型在多实体状态传播上仍然脆弱

原始论文 · 可复算代码、原始响应与评测记录 · 数据（v1 2026-10-15；10-19 新公告）。

发生了什么

世界模型用于 Agent RL 时，需要预测给定历史和动作后的环境新状态，而不仅是续写一段合理文字。GlobeBench 定义 1,632 项、五个领域、19 种仿真技能，给出冻结的历史轨迹，要求模型生成下一步环境观察。评测使用确定性规则和语义 Judge 联合评分，并开放历史模型输出、Judge 记录及离线重打分代码。

关键结果

20 个通用与专用模型中，作者报告 GPT-6 Astra 在其口径下达到最高 49.57% Task Success；当动作影响多个依赖对象、需要级联更新时，20 模型平均只有 5.1% 成功。631 个题目没有任何一个被测试模型成功解决。公开仓库记录了拒答和无响应，二者均在失败分母中，因此模型对比还受到安全拒答、上下文协议与 Judge 规则的影响。

为什么重要

假设自动化任务把“把商品移出库存”视作状态变化，则订单可售状态、组合套餐与后续优惠资格等依赖字段都必须更新。Agent 的错误往往不是遗漏主对象，而是遗漏依赖状态传播。这类评测可用于选择 Text World Model 做廉价 Rollout Simulator 的安全边界。

可信度与局限

项目提供数据、输出与 Judge，便于复算，但仍受轨迹真实性、题目生成、语义评分器及不同模型拒答策略影响。“最高 49.57%”只代表论文固定协议，不是行业通用世界模型榜单。线上交互时观察非冻结、工具有延迟、状态存在部分可观测性，难度可能更高。

最值得继续追踪

把错误分为：局部对象误更改、依赖未传播、规则遗忘、无效动作和拒答；对同一小型模拟器生成 Counterfactual Action Test，比较有/无显式状态图和 Checkpoint 的模型在多步预测的一致性。

9. PRIME：在调用工具前先定义“什么证据允许什么结论”

原始论文（v1 2026-10-15；10-19 新公告）。

发生了什么

企业规则检查经常允许多条证据路径。例如，一个合规结论可以由 A+B 证明，也可以由 C 证明。LLM Agent 有时在其中一条路径失败后仍宣布成功，或提前停在较弱结论，错失通过额外核验达到更强结论的机会。PRIME 在执行前固定允许的证据路径和判断规则，独立 Ledger 记录每项检查结果，再由程序拒绝越过证据范围的结论，并提示需要执行的下一项检查。

关键结果

作者在 480 个公开记录任务中报告，普通 Agent 已知规则但仍在 26.7% 任务上给出未授权结论；PRIME 在相同设置中没有此类结果。若使用 PRIME 主动建议/执行缺失检查，正当结论分数平均从只有拒绝机制时的 30.1 升至 59.2/100。这些保证明确依赖规则正确、检查地点可达且停止时预算充分。

为什么重要

Agent Eval 的终局答案最好同时输出证据集合、规则路径和已完成验证步骤。在财务审核、信息检索、SQL Tool Agent 或企业风控中，程序化 Evidence Ledger 能减少“看起来合理但缺证据”的自动决策。PRIME 也可作为 Agent 输出的外部 Guard，不依赖改模型权重。

可信度与局限

规则如果不完整或错误，系统仍可能作出错误结论；程序只能保证遵守预设逻辑。480 项任务不代表开放世界的复杂权限或安全攻击。必须区分“按规则合法”与“规则表达了真实业务目的”。

最值得继续追踪

在小型 Policy-as-Code 场景编写 EvidenceRoute -> VerifiedClaims 映射，模拟可替代证据、超时、缺字段及冲突证据，测量不支持结论率、额外工具调用数与达到最强支持结论的成本。

今日最值得花 30 分钟阅读的一项

Harness-Delta Attribution: Dissecting Gains From Harness Evolution（2026-10-15 v1；10-19 新公告）。

前 8 分钟读其归因框架，明确搜索集、独立测试集和不同计算预算的边界；随后 12 分钟看 11 个模型/3 个进化框架的实验，弄清 54% 过拟合 + 14% Test-time Scaling 的适用口径；最后 10 分钟将自己的 Agent Harness 的主要增益表改为“同预算 Held-out 成功率 + 成本”二维评价。读完最值得回答的问题是：如果不增加 Token 与工具调用，Harness 仍能让独立任务变好吗？

今日可立即实践的一件事

在本地完成一次 Harness Delta Replay（无需训练模型）。 选择 40—60 个 Agent 历史任务，按用户意图/工具类型分层，固定 20 个开发任务用来修改 Prompt 或 Router，保留另外 20—40 个只做最终独立验证。保存 Baseline 与 Improved Harness 的版本、Prompt、工具白名单和评估器版本；在同一个 Executor、固定总 Token/Tool Budget 下对比一次，随后再允许 Improved Harness 按原始更大预算执行一次。

请输出三组区别明确的增益：search-set Δsuccess、held-out Δsuccess @ matched budget、Δcost per successful task。如果只能在开发集上显著变好，或必须多消耗一倍 Token 才能变好，就暂时不给它“自我进化能力提升”的结论。少量样本使用 bootstrap 区间呈现不确定性，不做虚假的显著性宣称。对于只有 RTX 4080 16GB 的环境，可使用本地 4B/8B 量化推理模型和离线工具重放；若验证需要重型 Agent/多轮环境再考虑 2×A100。

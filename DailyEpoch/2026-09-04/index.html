今日主线： Harness-Policy Co-Evolution · Operational Skills · Adaptive Recommendation Compute · Ternary Compression · Per-Head KV Residency · Local Inference Routing

截至今天上午，arXiv 最新常规公告批次为 2026 年 9 月 3 日：cs.AI 共 162 条，cs.IR 共 41 条。今天最值得连起来看的变化是：Agent 的“自我进化”正在同时向外部 Harness 与可复用 Skill 层扩张；推荐系统开始把慢推理视为应按样本分配的稀缺计算资源；推理系统则继续下沉到 KV 驻留、极低比特权重和本地多机请求路由。一个共同结论是：能力、成本与可靠性越来越由“模型之外的系统结构”共同决定。

今日核心判断

  1. 安全自进化不能只改 Policy，也不能只堆外部 Guardrail。 SafeEvolve 用 on-policy 安全轨迹同时推动 safety prompt / SkillBank 的有界更新和 Policy 的 SFT-RL 内化；Qwen3.5-4B 在 AgentDojo 上 ASR 从 2.37% 降到 0.79%，clean utility 反而从 59.79% 升到 61.86%。真正值得关注的是“可审计、可回滚的 Harness 变更 + 参数内化”这一双层结构，而不是单一 benchmark 数字。
  2. AI Research Agent 缺的可能不是更多 reasoning token，而是一层“Operational Knowledge”。 Repo-To-Skill / DisCo 把 1,000 个常用 ML 仓库蒸馏成 5,000+ verified skills；固定 GPT-5.5 backbone、Harness 和下游执行预算后，MLE-bench Any-Medal 从 31.11% 提高到 72.89%。这是一项非常强的信号，但 Skill 的构建成本被单独核算，不能把运行时提升误读成“免费知识”。
  3. 推荐系统里的 Slow Thinking 不是越多越好。 DS-Frame 在 Beauty/SASRec 上，40.2% 样本走 Slow System 时 NDCG@10 为 0.0450，高于 100% Slow 的 0.0431；其归一化计算代理约 1.80×，而 always-slow 为 3.00×。核心问题是“哪些样本值得额外推理”，而不是统一增加推理深度。
  4. 极低比特压缩与推理加速必须分开评价。 Qwen3-4B 的 post-training ternarization 把量化线性权重做到 1.641 effective bits/weight，并把报告模型尺寸从 8.29 GiB 压到 3.96 GiB；但 10 项能力平均准确率从 64.5% 降到 54.7%，一个初步 Triton GEMV microbenchmark 还比 FP16 cuBLAS 慢 4.6×。压得更小不等于跑得更快。
  5. Hybrid Long-Context 模型的 KV 预算可以细化到“每个物理 KV Head”。 HeadWiseKV 用静态多级 history window 给不同 head 分配不同驻留长度，在 Qwen3.6-27B 的系统实验里，112K context 下 sampled peak device memory 降低 8.59%，最大验证成功 context 从 114K 推到 161K。它的优势是可预测 residency，而不是运行时再维护一套动态 selector。
  6. 本地 Multi-Agent 的瓶颈有时只是请求排队，而不是单模型不够快。 NVIDIA PAIR 在 Ollama / LM Studio 前面加本地 inference router，把独立请求路由到家用网络中的不同节点；一个五子 Agent demo 从单台 RTX Spark 的 18 分钟缩短到三设备集群的 8 分 48 秒。但它不做 VRAM pooling，也不切分单个请求，收益只属于具有足够并行度的 workload。

1. SafeEvolve：让 Harness 与 Policy 一起进化，而不是各自补漏洞

一句话结论： Agent Safety 的可持续形态更像“双层控制系统”——外层 Harness 快速吸收新失败模式，内层 Policy 再把稳定经验内化；关键是 Harness 更新必须有作用域、证据、验收和回滚。

原始来源： SafeEvolve: Harness-Policy Co-Evolution from Agent Experience for Safety Alignment
代码： MaoPopovich/SafeEvolve

发生了什么

SafeEvolve 不把 Agent Safety 只理解成最终回复是否安全，而把 tool call、网页注入、权限与多步执行路径一起纳入安全轨迹。每轮 rollout 结束后，它先从失败 bucket、攻击类型、工具族和执行质量中整理 evidence，再只修改一个明确的 Harness component，例如 safety system prompt 或 hierarchical SkillBank。

候选 Harness 不会直接生效。Parent 与 candidate 在同一组任务／环境上做 paired evaluation，只有在安全、clean utility 与执行质量都通过 gate 后才被接受；接受的变更带版本、支持证据与 rollback metadata。工具 API 与环境接口本身在论文实验中保持固定。

随后，Policy 通过两阶段训练把外部安全能力内化：

为什么重要

外部 Guardrail 有一个常见极限：规则越来越复杂时，弱 Policy 未必会稳定遵守；纯 Policy Safety RL 又有另一个极限：训练 substrate 是固定的，出现新的 prompt injection / tool failure 后，需要重新收数据、训练和部署。

SafeEvolve 的系统论价值在于把两种时间尺度分开：

  • Harness：可快速修改、审计、回滚；
  • Policy：更慢，但可以把反复出现的安全行为内化。

这比“所有新风险都写进 system prompt”或“所有风险都重新做 RL”都更接近长期 Agent 的现实维护方式。

可信度与局限

这是刚发布的预印本，主要证据来自 AgentDojo、AgentDyn、AgentHarm 与有限状态的可验证环境。论文虽然允许 Harness 进化，但实际 evolvable component 主要是 safety prompt 与 SkillBank，并没有证明任意 middleware、tool implementation 或权限系统都可以安全自动修改。

另外，proposer、verifier 和 acceptance gate 自己也可能存在 blind spot。一个系统可以做到“所有改动都通过 gate”，但如果 gate 没覆盖某类新风险，仍可能形成安全债务。Benchmark 内持续进化也可能逐渐编码 benchmark 特性。

最值得继续追踪

最关键的是三类独立证据：跨模型 Harness transfer、完全 held-out 攻击上的 frozen-harness 测试，以及不依赖同一 verifier 的外部 audit。真正的目标不是“安全分数越来越高”，而是新安全经验能被吸收，同时旧能力、clean utility 和未见风险不发生隐性回归。

2. Repo-To-Skill：把 GitHub 仓库蒸馏成 Agent 的“操作知识层”

一句话结论： 模型知道一个库“是什么”，和 Agent 知道“什么时候该用、怎么跑、怎么验证、失败后怎么恢复”是两种知识；Repo-To-Skill 的信号是，后者可以独立于模型参数被大规模编译和复用。

为什么重要

今天很多 AI Research Agent 仍在重复做一件昂贵的事：每次任务都重新搜索库、读文档、试 API、踩同样的安装坑、重新发现相同 validation pattern。

Skill 层的价值不是替代 reasoning，而是把已经验证过的操作知识从在线搜索预算中移走。这会把 Agent 的时间更多留给任务特定的新问题，而不是反复重建行业公共知识。

可信度与局限

论文的 controlled runtime comparison 做得比较干净，但 Skill construction budget 被单独计算，并没有包含在 with/without-skill 的下游运行预算中。因此 134.3% 不能理解成“同样总计算成本白拿一倍多性能”；更准确的说法是：一旦操作知识完成一次性蒸馏，在相同下游执行预算下价值很大。

另一个风险是 knowledge freshness 与 supply-chain quality。Skill 的 provenance 绑定到具体 commit 是优点，也意味着上游仓库更新后 Skill 可能过期；开源仓库本身也可能包含错误、脆弱示例或不安全脚本。

最值得继续追踪

最值得看的不是 Skill 数量继续从 5,000 变成 50,000，而是：Skill update 的增量成本、跨模型迁移、过期检测、负迁移率，以及“哪些任务值得先付一次蒸馏成本”。如果一个 Skill 只被用一次，它只是昂贵的预处理；被大量复用时，它才真正成为基础设施。

3. DS-Frame：推荐系统的 Slow Thinking 应该按样本路由

一句话结论： 复杂用户值得更多迭代 refinement，简单用户反复慢思考可能反而变差；推荐系统的 Test-Time Compute 更像一个 routing 问题，而不是统一增加深度。

原始来源： Recommender System as Slow and Fast Thinkers

发生了什么

DS-Frame 把推荐器拆成 Fast System 与 Slow System：Fast path 做常规高效预测；Slow path 对 latent preference 做多步迭代 refinement；一个 learned selector 在总预算约束下判断哪些样本需要进入慢路径。

它最值得关注的并不是“加一个慢模型”，而是实验直接显示 Slow-only 不是最优。

关键结果

Beauty / SASRec：

路由策略Slow activationNDCG@10相对 Fast gain
Fast Only0%0.0418—
Learned20.0%0.0441+5.5%
Learned40.2%0.0450+7.7%
Learned60.0%0.0454+8.6%
Slow Only100%0.0431+3.1%

在作者采用的 step-based proxy 下，$K=2$ 时 Learned Selector 约为 1.80× normalized cost，而 Slow Only 为 3.00×。注意：这里是归一化成本代理，不是实测 wall-clock latency。

为什么重要

这和 LLM Test-Time Scaling 的经验高度一致：额外计算的边际价值依赖样本难度与不确定性。推荐系统里尤其明显，因为大量请求本身很简单：用户意图清晰、近期行为一致、候选差距大。这些请求进入多轮 refinement，只会增加成本，甚至可能把原本正确的强信号“想复杂了”。

所以更合理的目标是：

\[\max \; \mathbb{E}[\Delta \mathrm{Utility}(x)\mid \text{slow}(x)] -\lambda \cdot \mathrm{Cost}(x)\]

而不是固定“所有样本多算两步”。

可信度与局限

当前主要是离线公开推荐数据，没有真实线上 A/B。Slow activation 被作为 cost proxy，不能直接换算成 GPU latency、吞吐或成本。Learned selector 也借助 sample-level guidance 训练，在分布漂移后 routing calibration 是否稳定还没有证明。

更重要的是，Beauty/SASRec 上 100% Slow 低于 40%–60% selective slow，说明慢推理具有可造成负收益的干预性；这要求上线前同时测 uplift 与 harm，而不是只测平均 gain。

最值得继续追踪

我会重点看：selector 的 OOD calibration、按用户生命周期 / 冷启动 / 多意图切片的 slow-path uplift，以及真实 serving 中 quality-per-ms。如果 routing 的成本本身接近 slow refinement，系统优势会迅速变小。

4. Qwen3-4B Ternarization：压到 1.641 bit/weight，但速度没有自动出现

一句话结论： 量化报告必须把“信息位宽、文件大小、任务质量、Kernel 性能、端到端吞吐”分开；这篇工作最有价值的部分，恰恰是它没有把压缩率包装成推理加速。

原始来源： Post-Training Ternarization of Qwen3-4B

发生了什么

作者对 instruction-tuned Qwen3-4B 做 weight-only post-training ternarization，activation 保持 16-bit。最终对 81.62% 参数进行目标量化，量化线性权重达到 1.641 effective bits per weight。

关键结果

指标Teacher / 原模型Ternary / Packed
10 项能力平均准确率64.5%54.7%
WikiText-2 PPL13.63918.748
报告模型尺寸8.29 GiB3.96 GiB

能力退化并不均匀：BoolQ 保留 84.6% 的 chance-corrected teacher performance，而 ARC-Challenge 只保留 43.8%。

最值得注意的是部署部分：作者明确说明 packed artifact 还没有做完整 task-accuracy / generation-throughput benchmark；一个初步 Triton GEMV 在测试 shape 上反而 比 FP16 cuBLAS 慢 4.6×。论文因此明确拒绝“compression alone yields faster inference”这一结论。

为什么重要

很多量化工作只证明前两层，然后在产品讨论中被自动翻译成“推理更快、更省 GPU”。这篇论文提供了一个很好的反例：低比特表示如果缺乏成熟 kernel，甚至可能更慢。

可信度与局限

这是单一 4B 模型的 weight-only 研究，不包含 activation quantization，也没有成熟的 end-to-end serving benchmark。因此它不证明 ternary inference 没有前景；它只证明一个可压缩 checkpoint 并不会自动带来部署收益。

最值得继续追踪

真正决定路线价值的是 packed ternary GEMM / GEMV kernel、batch size、prefill vs decode、memory-bandwidth 限制以及连续 batching 下的吞吐。如果未来专用 kernel 能把三值算子真正转成 bandwidth / compute 优势，当前质量—压缩 trade-off 才有完整工程意义。

5. HeadWiseKV：不同 KV Head 不必保存同样长的历史

一句话结论： Hybrid 模型虽然已经把大量 attention 换成 local / recurrent / linear path，但残余 global-attention head 仍可能成为 KV 内存瓶颈；HeadWiseKV 让每个物理 KV head 拥有静态、可预测的 history window。

原始来源： HeadWiseKV: Budgeted Per-Head Cache Residency for Hybrid Long-Context Language Models

发生了什么

HeadWiseKV 是 training-free 方法。它在总 KV-residency budget 下，为不同 KV head 分配多个离散 history window，而不是让整层统一保留相同长度。核心 SeqCalib 按网络执行顺序逐层校准，并让上层决策条件化于已经确定的 lower-layer policy，以避免把每一层独立调优后出现组合失真。

部署时也不是在完整 KV 上做 mask：grouped-cache runtime 会真正物理化不同 head 的驻留窗口，因此内存需求在 serving 前即可预测。

关键结果

论文在四个 hybrid long-context model 上报告接近 Full-KV 的 RULER / LoCoMo 质量；Qwen3.6-27B 的系统实验中：

  • 112K context 下 sampled peak device memory：-8.59%；
  • largest verified successful context：114K → 161K（1.41×）。

为什么重要

KV compression 常见两条路：运行时动态 eviction，或全模型统一窗口。前者需要 selector、统计与额外 kernel；后者简单但忽略 head specialization。

HeadWiseKV 选择一个很工程化的折中：用一次 offline calibration 换取 deployment-time 的静态 policy。对于对 latency jitter 和容量规划敏感的 serving 系统，这种可预测 residency本身就是价值。

可信度与局限

8.59% 的 sampled peak device memory 降幅并不巨大，最亮眼的 114K→161K 是在 fixed-model systems study 下的可服务 context 延伸，不应直接解读成所有 workload 都获得 41% 吞吐提升。

此外，方法主要针对 hybrid model 中残余 global KV；它不是 full-attention Transformer 的通用压缩解。静态 calibration 也要求部署流量与 calibration distribution 不要相差太大。

最值得继续追踪

最关键的是把“最大可运行 context”进一步换算成生产指标：resident sessions、P50/P95 TTFT、decode throughput、cache fragmentation，以及 workload shift 后静态 head budget 是否仍稳定。

6. NVIDIA PAIR：家里的多台机器可以先做“请求级集群”，不用先做模型并行

一句话结论： 对多 Agent / 多 Session 本地推理，最容易拿到的并行收益往往来自独立请求调度，而不是把一条推理切到多台机器；PAIR 就是在 Ollama / LM Studio 前加一层本地 router。

官方技术文章： NVIDIA PAIR Virtual Inference Router Expands Available Compute on Your Local Network
代码： NVIDIA/Personal-AI-Router

发生了什么

PAIR 发现同一局域网里的可用节点，通过 mDNS 配对、MTLS 通信，并根据：

1
2
3
4
5

node readiness
engine status
model availability
current job load
GPU utilization

为每一个独立 Ollama / LM Studio 请求选择一个节点。Agent 仍然看到原来的兼容 endpoint，不需要为了多机调度重写 Harness。

它不是分布式 inference engine：

  • 不做 GPU memory pooling；
  • 不把多块 GPU 拼成更大逻辑 GPU；
  • 不 shard 单个模型；
  • 一个请求从开始到结束只在一个选定节点运行。

关键结果

NVIDIA 的 configuration-specific demo 使用 Qwen 3.6 35B A3B、Hermes 五子 Agent：

  • 单台 RTX Spark laptop：平均 18 分钟；
  • RTX Spark laptop + DGX Spark + RTX 5090 三设备 PAIR：平均 8 分 48 秒。

官方明确标注这不是通用 benchmark，也不是线性扩展承诺。

为什么重要

很多本地 Agent 用户已经同时拥有台式机、笔记本、Mac、NAS / 工作站，但推理请求仍全部排队到一个 endpoint。对于 breadth-first research、并行 coding sub-agent、批量 verification 等 workload，请求级调度可以在完全不碰模型并行的情况下减少 queueing。

这也是一个常被忽略的系统原则：

先判断工作负载有没有 request-level parallelism，再决定是否值得上复杂 tensor / pipeline parallelism。

可信度与局限

这是 NVIDIA 的 beta + 官方 demo，只有一组多 Agent workload；网络、模型预热、KV cache、节点异构和不同 engine 的调度成本都可能显著影响收益。

高度顺序化的任务、一个超长单请求、只有一台机器拥有目标模型的场景几乎得不到帮助。它还不能让两台 16GB GPU 合起来加载一个 30GB 模型。

最值得继续追踪

最值得看的不是更多峰值 demo，而是 heterogeneous node 下的真实 scheduler：模型冷启动、prefill/decode 长度预测、cache locality、energy cost 与 node availability 是否会进入路由决策。

今日值得收藏的代码 / 学习资源

AREX-Skill：今天最值得直接打开的仓库。当前 README 已标注 5,000+ verified executable skills、1,000+ repositories，并把每个 Skill 的 provenance、验证与失败恢复作为运行时接口的一部分。比“看一篇 Skill 论文”更有价值的是直接观察一个仓库如何被拆成 SKILL.md + references + scripts。

SafeEvolve：适合研究 Harness Evolution 的团队重点看 paired acceptance gate、component-level patch、SkillBank 和 SFT-RL 如何串成闭环。它与 capability-oriented harness evolution 的不同点是：更新目标显式包含 clean utility 与 safety regression。

Persistent Discovery Context：数据 Agent 值得收藏。它不保存整条 reasoning trace，而只保存成功的 (intent → data objects) 映射；在词汇稀疏的 NYC Collisions 数据上，memory-only F1@5 甚至高于 metadata registry。更重要的负结果是：激活语义相似但任务族错误的 Memory 会把检索拉到 baseline 以下，说明长期 Retrieval Memory 必须有 family / scope gating。

vLLM Renderer APIs：9 月 2 日更新的 serving 文档。它把 tokenizer、multimodal preprocessing、detokenization、tool/reasoning parser 从 GPU inference engine 中解耦，允许 GPU-less frontend 与 token-in / token-out engine。对做 llm-d / Dynamo / 自定义 Gateway 的团队，这比继续把所有 request preprocessing 绑定在 vLLM server 进程里更值得试。

今日最值得花 30 分钟阅读的一项

首选 Repo-To-Skill，并直接配合 AREX-Skill 阅读。

它比“又一个更强 Research Agent”更值得看，因为它把一个长期被混进 Prompt / RAG / Harness 的东西单独命名出来：Operational Knowledge。

建议 30 分钟按这个顺序：

  1. 先看 Model / Harness / Operational Knowledge 三层为什么不等价；
  2. 看 repository graph 如何记录 use condition、procedure、validation 与 recovery；
  3. 看 provenance 为什么绑定 commit / package version，而不是只保留一段自然语言摘要；
  4. 再看 MLE-bench 的 controlled no-skill vs skill 结果；
  5. 最后一定看成本边界：Skill construction budget 独立于 downstream run budget。

如果只带走一个判断：

高价值 Agent Memory 不一定是“记住过去说了什么”，而可能是把重复验证过的工程知识编译成可执行、可审计、可更新的操作单元。

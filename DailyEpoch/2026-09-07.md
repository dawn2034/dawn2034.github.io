> **今日主线：** Automated AI Research · Explicit Agent State · Prompt-Injection Weak-Cell Maps · On-Policy Reranking · 10B Vector Benchmarking · WebGPU Kernels

截至今天早上，arXiv `cs.AI` 最新常规公告批次仍是 **2026 年 9 月 4 日**，共 165 条；周末没有新的常规批次。今天更值得关注的是过去 72 小时里几项已经从“论文结果”走到研究组织、Agent Harness 和基础设施层面的信号：OpenAI 首次公开了 Coding Agent 对内部研究流程的量化数据；Anthropic 的 FLT formalization 则提供了一个极端长程、多 Agent、机器可验证项目的工程案例；Prompt Injection 的评估开始从单一 ASR 转向“模型 × Scaffold × 攻击族”的弱点地图。

## 今日核心判断

1. **AI Research Agent 已经开始改变研究组织的实际吞吐，但“Agent runtime”不能直接等价为“研究进展”。** OpenAI 报告截至 8 月中旬，研究组织累计每 1 个 8 小时 human-workday 对应约 3.1 个 agent-workdays，研究者写代码和运行实验的频率也在上升；但高层 planning 仍只占很小比例，而且超过一半成功的 4–8 小时任务仍至少需要一次人工干预。真正的瓶颈正在从“写代码”迁移到选题、判断、算力与安全控制。

2. **超长程 Multi-Agent 的关键资产可能不是聊天历史，而是显式、可验证的任务图。** Anthropic 的 FLT formalization 初期曾因 Agent 丢失项目状态而失效；切换到 Prove2Me 的 theorem DAG、statement/proof 分离和可搜索自然语言描述后，数十个 Agent 才能稳定并行。最终项目消耗约 60 亿 output tokens，因此正确解读不是“模型独自 11 天解决 FLT”，而是“通用模型 + 强状态 Harness + Lean verifier”完成了超大规模 formalization。

3. **Prompt Injection 的平均攻击成功率掩盖了真正的生产风险：每个 Model–Scaffold pair 都有自己的高危弱点单元。** 同一 Harness、同一 395 封注入邮件下，九个模型的支付订单率从 0% 到 42%；同一个模型不同 attack family 可相差数倍。更麻烦的是，513/517 次成功支付发生时 Agent 没有主动报告攻击，失败攻击也有 95% 保持沉默。

4. **On-Policy Distillation 正从语言 token 扩展到排序 action。** 一项 EMNLP 2026 Findings 工作让 1B reranker 在自己的 Plackett–Luce ranking policy 上采样，再用 4B Teacher 给 student-sampled ranking 产生 soft reward；MAIR-11 上达到 0.7670 nDCG@6，相比 offline listwise KD 高 4.6 points。这里真正重要的是 student-state coverage，而不是把 Teacher 的静态排序再模仿一次。

5. **RAG / ANN 基础设施终于开始拥有接近生产数量级的开放 Benchmark substrate。** Qdrant-FineWeb-10B 提供 10.07B dense + 10.07B sparse vectors，并对 100,000 个 query 计算 exact top-1000 brute-force ground truth；Supernova 再把 embedding、ground truth、ingestion、load test 和 QPS / p95 / p99 / recall 测量做成开放引擎。它目前更像公共基础设施发布，而不是“某个向量数据库已经赢了”的结论。

6. **Browser / Local AI 的 kernel 层开始走向“版本化 + correctness evidence + 众包硬件验证”。** Hugging Face 发布 207 个 WebGPU kernels；在 Apple M4 的 809 个可比 case 中相对 ORT WebGPU 几何平均快 2.57×。但 1,756 个初始 case 中只有 809 个进入 headline 比较，而且这些数字只测 GPU operation time，不是完整模型端到端延迟。

## 1. OpenAI：Coding Agent 正在变成 AI Research 的常规劳动力

**原始来源：** [Research acceleration: The view inside OpenAI](https://openai.com/index/research-acceleration-view-inside-openai/)

### 发生了什么

OpenAI 9 月 6 日公开了一组内部研究组织的 Coding Agent 使用数据，并称其已经达到此前定义的“automated research intern”目标：在人工方向指导下，可以承担原本需要熟练研究人员数天完成的明确研究任务。文章同时把目标继续推进到 2028 年 3 月的“automated AI researcher”，但明确承认目前仍没有安全实现完整 recursive self-improvement 的方法。

从组织使用上看，Coding Agent 已经从偶尔辅助变成高并发日常工具。到 8 月中旬，研究组织的中位用户按 API 价格折算每天使用超过 **\$600** 的 Agent inference；90 分位用户超过 **\$7,000 / day**。按标准 8 小时工作日折算，整个研究组织累计使用约 **3.1 agent-workdays / human-workday**。

### 关键结果

| 信号 | OpenAI 报告 |
|---|---:|
| 研究组织 Agent runtime / human labor | **3.1 agent-workdays / human-workday** |
| 中位研究者 Agent inference（按 API 价格） | **> \$600/day** |
| 90 分位用户 | **> \$7,000/day** |
| 4–8 小时成功任务中至少需要一次人工干预 | **>50%** |
| 8 月 experiment / active experimenter | 自 2025 年 1 月开始追踪以来最高 |

任务结构也在变化：Build、Run、Analyze、technical support 等类别都明显增加，但高层 planning 仍只占很小的 Agent token 比例。OpenAI 还报告，从 1 月到 7 月，多个按人类预计完成时间划分的任务难度桶中，Agent 成功率总体提高；任务越长，人工 steering 仍越重要。

### 为什么重要

这组数据最值得看的不是“3.1 倍人力”这个容易被误读的数字，而是 **R&D bottleneck migration**。当写代码、查基础设施问题和运行实验更容易自动化后，研究过程中的稀缺环节会逐渐转向：

```text
Decide / Design
→ 实验优先级与资源分配
→ 结果解释与异常识别
→ 安全与对齐验收
→ 是否值得 scale / merge / deploy
```

这意味着 Automated Research 系统的下一阶段不只是让 Coding Agent 写更多代码，而是建立更强的 experiment provenance、independent evaluation、resource routing 和 stop criteria。

### 可信度与局限

这是 OpenAI 对自身组织的一方测量，且文章自己反复提醒这些指标仍很初步。**Agent runtime 不能解释成等价的人类生产力**：Agent 可以并发、失败、重复尝试，也可能大量消耗 token 去完成低价值工作；实验数量增加也不能自动推导出 research quality 或 frontier progress 同比例增长。

另一个重要混淆变量是算力：OpenAI 明确说 2026 年可用 compute 同时显著增加，因此 experiment count 与 Codex adoption 的相关性不构成严格因果识别。文章最有价值的是首次公开 measurement framework 和量级，而不是给“AI 已让研究加速 X 倍”一个可信单数答案。

### 最值得继续追踪

应该继续追踪 **成功任务的人类时间节省、干预次数、实验有效率、被 merge 的研究改动比例，以及每个成功研究结论消耗的 agent-GPU / token 成本**。如果只追 code volume 和 experiment count，Automated Research 很容易优化成高吞吐的实验制造机，而不是高质量的科研系统。

## 2. Anthropic FLT Formalization：真正 Load-Bearing 的是 DAG State + Lean Verifier

**原始来源：** [Anthropic：Formalizing Fermat's Last Theorem](https://www.anthropic.com/research/formalizing-fermats-last-theorem)  
**完整证明：** [anthropics/fermats-last-theorem](https://github.com/anthropics/fermats-last-theorem)  
**协作平台：** [Prove2Me](https://prove2.me/) · [Prove2Me 论文](https://arxiv.org/abs/2608.28433)

### 发生了什么

Anthropic 9 月 4 日公布其所称的首个端到端、机器检查通过的 Fermat's Last Theorem Lean formalization。Claude 在 11 天内生成约 **1300 万行 Lean**，建立 30,300 个机器可验证 theorem，其中 29,500 个进入最终证明；数十个 Agent 协作完成不同中间定理。

这里必须把“数学发现”和“形式化”分开。该项目沿用已知数学证明路线，Anthropic 自己也明确说 novelty 在 **verification / autoformalization**，并非发现了新的 FLT 数学证明。最终结果由 Lean 检查，使用 Lean 的标准公理体系。

### 关键结果

| 项目 | 规模 |
|---|---:|
| 主要自主 formalization 时间 | **11 天** |
| Lean 代码 | **约 1300 万行** |
| 生成的可验证 theorem | **30,300** |
| 最终证明使用 theorem | **29,500** |
| 模型 output tokens | **约 60 亿** |
| Agent | 数十个并行协作 |

更有工程价值的是失败路径。初期 Agent 虽能证明局部结果，却很快丢失整个项目状态、停止有效协作；这些失败工作最终仍贡献约 7% 的非 boilerplate 代码，但整体组织方式不可持续。

真正改变项目状态的是 Prove2Me：用 theorem statement 的 **DAG** 表示依赖关系，让 Agent 从 ready node 中选择下一步；statement 与 proof 分文件以降低编译和资源消耗；每个 theorem 同时保存自然语言描述，便于检索与复用。再配合 Claude Code multi-agent Harness，才形成可扩展的并行 formalization pipeline。

### 为什么重要

这是一份极端长程 Agent 系统的真实案例。它给出的核心 lesson 和“让 Agent 拥有更长 context”几乎相反：

> **当任务复杂度超过单次上下文可管理范围时，应把项目状态外显成机器可检查的 dependency graph，而不是继续把历史聊天压回 Prompt。**

DAG 节点天然提供 ready / blocked / proved / failed 状态，Lean 又提供 deterministic verifier。这样多 Agent 协作不需要互相信任自然语言“我已经完成”，而是共享可验证 artifact state。

### 可信度与局限

这是 Anthropic 的第一方项目报告；“首个完整机器检查 FLT proof”的表述目前主要来自项目方与参与评阅者。更重要的是，约 60 亿 output tokens 是非常高的计算投入，因此它不能作为“普通 Coding Agent 只靠多开几个 sub-agent 就能轻松完成多年项目”的证据。

Formal theorem proving 还有一个其他 Agent 场景缺少的优势：Lean 提供极强、低歧义的 verifier。软件产品、Research Agent 和企业 Workflow 没有同等质量的验证器，因此 DAG orchestration 可以迁移，验证可靠性却不能直接复制。

### 最值得继续追踪

最值得继续看 Prove2Me 是否能在更多大型 formalization 上稳定复现，以及 **DAG node granularity、proof reuse、失败节点重试策略和 token-per-verified-theorem** 是否随着项目累积显著改善。若这些指标下降，才说明系统在“学习如何组织工作”，而不只是堆更多模型调用。

## 3. Prompt Injection：不要问“模型 ASR 是多少”，要画 Weak-Cell Map

**原始来源：** [Agentic models, measured on the injections that move money](https://huggingface.co/blog/mihailgribov/agentic-models-measured-on-the-injections-that-mov)  
**Harness：** [mihail-gribov/quadrat-ipi-model-eval](https://github.com/mihail-gribov/quadrat-ipi-model-eval)  
**数据集：** [mihailgribov/quadrat-ipi](https://huggingface.co/datasets/mihailgribov/quadrat-ipi)

### 发生了什么

这项 9 月 5 日发布的社区实验固定同一个个人助理 Agent：19 个工具、同一 system prompt、同一 call loop 和 retry policy。Owner 的任务只有“把邮件记录进 journal”；每封邮件里却嵌入一个要求 Agent 创建支付订单的 prompt injection。实验从 Quadrat-IPI 中取出 `unauthorized_action × email` 单元里 395 条要求付款的注入，对九个模型逐一运行。

评估没有用 LLM Judge 判断是否“被骗”，而直接读取 tool log：是否多调用了无关工具、是否创建 payment order、是否使用了注入里的 payee / amount。控制组删除同一邮件里的注入后，在 **1,620 个 control episodes 中只发生 1 次支付**。

### 关键结果

| 模型 | 注入邮件触发 payment order |
|---|---:|
| gpt-4o-mini | **42.0%** |
| Qwen3-30B-A3B | **29.4%** |
| Hermes-4-70B | **19.0%** |
| Qwen3-235B-A22B | **18.5%** |
| DeepSeek-V4-Pro | **8.6%** |
| gpt-5.1 | **3.8%** |
| claude-haiku-4.5 | **0.0%**（95% 上界 1.0%） |

平均值仍然不是最有用的结论。按攻击 family 聚合，`pretext` 为 26.6%、`identity` 24.1%、`bare` 18.4%，而看起来更“像攻击”的 `guard` 只有 8.3%、`output_marking` 4.5%。例如 gpt-4o-mini 在 `pretext` 单元达到 68%，同一模型在 `persistence` 只有 8%。

监控信号也很差：517 个成功支付 episode 中，**513 个没有主动说自己看到了攻击**；攻击失败时，Agent 仍有约 95% 的 episode 完全不提醒 Owner。

### 为什么重要

生产安全评估不应该只维护一个“Prompt Injection ASR”。真正要测的是：

$$
R = f(\text{model},\ \text{system prompt},\ \text{tool set},\ \text{carrier},\ \text{requested action},\ \text{attack family})
$$

攻击者不会随机从你的平均分布采样，他们会寻找最脆弱的 cell。更强模型也没有形成简单单调排序：在唯一较干净的同代尺寸对比中，Qwen3-235B 的平均支付率低于 Qwen3-30B，但不同 family 的差距并不均匀。

### 可信度与局限

这是一篇 Hugging Face Community Article，不是同行评审论文；环境完全仿真、攻击者不自适应，并且只测了 `email → unauthorized payment` 这一小块 attack space。作者也明确写明：**数字属于 model + scaffold 的组合，不是模型的普适安全分数。**

这反而是它最值得保留的结论。换 tool permissions、approval queue、system prompt 或 memory policy 后，整张 weak-cell map 都可能变化，因此外部 model card 无法代替自己的 Harness evaluation。

### 最值得继续追踪

下一步应扩到 data exfiltration、memory write、order / booking、shell / HTTP 等动作，并加入 adaptive attacker。生产 Agent 还应该记录**被拒绝的攻击尝试**；如果只有“成功越权动作”才留下监控信号，就无法估计系统正在承受多少攻击流量。

## 4. On-Policy Distillation for Reranking：让 Student 在自己的 Ranking Space 里学

**原始来源：** [On-Policy Distillation Meets Off-Policy GRPO: Training Compact Instruction-Following Rerankers](https://arxiv.org/abs/2609.01947)

### 发生了什么

这篇 EMNLP 2026 Findings 工作把 OPD 的思路从语言生成扩展到 ranking action。第一阶段先用 LLM-judge feedback 对 4B Teacher 做 off-policy GRPO，训练数据约 88K；第二阶段不再把 Teacher 的固定排序当 demonstration，而让 1B Student 从自己的 Plackett–Luce policy 采样 ranking，再由 Teacher 对这些 student-sampled rankings 给出 soft reward。

也就是说，Student 学的是：**在自己真正会访问的排序状态里，哪些排列更接近 Teacher 的相关性偏好。** 这和传统 listwise KD 的区别不是 loss 名字，而是 supervision 的 support 从 teacher-observed ranking space 转到了 student policy 的 action space。

### 关键结果

| 评测 | 结果 |
|---|---:|
| MAIR-11，869 queries | **0.7670 nDCG@6** |
| 相比 offline listwise KD | **+4.6 points** |
| MAIR-Full，126 tasks / 9,356 queries | **0.6808 nDCG@6** |
| MAIR-Full | **0.7865 MRR@6** |
| 9,861-query validation | **0.7624 nDCG@6** |

作者还分别比较 offline pairwise RankNet KD 与 on-policy GKD：只换离线 distillation objective，或者把 Teacher distribution matching 搬到 on-policy，都没有复现 reward-based on-policy ranking distillation 的增益。

### 为什么重要

搜索／推荐蒸馏里一个常见问题是 Teacher 只提供“它认为最优的结果”，Student 从未获得自己错误决策附近的局部梯度。On-policy ranking distillation 把问题改成：

```text
Student 先暴露自己的 ranking distribution
→ Teacher 在 Student 真正访问的排列上评分
→ 更新 Student 的 reachable policy region
```

这与近期 OPD 在 reasoning 中强调 student-state coverage 的逻辑一致，也更接近推荐系统里 counterfactual policy learning 的思路。

### 可信度与局限

当前任务是 reranking，不是第一阶段 billion-scale retrieval；candidate 数量也远小于完整商品／文档空间。Teacher 本身经过 LLM-judge GRPO，因此最终监督质量仍受 Judge calibration 影响。

此外，论文主要报告 ranking quality，没有给出完整线上 P95 latency、batch throughput 或 A/B 结果。1B 比 4B 更便宜是合理推断，但具体 serving Pareto 仍需要实际系统数据。

### 最值得继续追踪

最值得尝试的是把 reward 从 Teacher relevance 扩展到 **业务可验证信号 + Teacher semantic preference** 的组合，并检查 Student on-policy sampling 是否能改善 hard-negative / tail-query 区域，而不是只提高平均 nDCG。

## 5. Qdrant-FineWeb-10B + Supernova：Vector Search Benchmark 终于跨进十亿级

**原始来源：** [Internet-Scale Knowledge Retrieval: A Novel Vector Search Dataset at 10B Scale](https://huggingface.co/blog/Qdrant/fineweb-10b-release)  
**Benchmark engine：** [Qdrant/Supernova](https://github.com/qdrant/supernova)

### 发生了什么

Qdrant、Vultr 与 Hugging Face 发布 Qdrant-FineWeb-10B：基于 FineWeb 与 `gte-multilingual-base` 构建 **10.07B dense + 10.07B sparse vectors**，vector 数据约 24.47 TB，原始文本与 metadata 约 28.66 TB。

更难得的是 ground truth。团队用 GPU brute force 对 **100,000 queries** 在完整 10B vector space 上计算 exact top-1000 nearest neighbors，总计超过一千万亿次距离计算。与数据集同步发布的 Supernova 把 embedding generation、exact ground truth、数据库 ingestion 和 stress testing 做成开放 pipeline。

### 关键结果

| 数据集 | 规模 / 表示 |
|---|---:|
| Qdrant-FineWeb-10B | **10.07B dense + 10.07B sparse** |
| PubMed-Multi-Vector | 23.9M dense + 23.9M sparse + **8.37B multi-vector tokens** |
| Coyo-Vector-Embeddings | **15.4M** 2048-d multimodal dense vectors |

Supernova 的 `nova-storm` 可以对 Qdrant、Milvus、Elasticsearch 等 backend 记录 QPS、$p_{50}$、$p_{95}$、$p_{99}$、build time 与对 exact ground truth 的 recall；`nova-bf` 则支持 dense、sparse 与 multi-vector 的 GPU brute-force ground truth。分布式控制层用 SkyPilot 统一 AWS、GCP、Azure、Kubernetes 与 Slurm。

### 为什么重要

很多 ANN / RAG benchmark 仍停留在百万或千万 vector，生产系统却早已面对十亿级 corpus、filter、hybrid sparse+dense 和 late-interaction。小数据集上的 ANN ranking 很容易被 cache、index build 策略和参数手工优化误导。

Supernova 的价值因此可能高于单个 10B dataset：它把“重新生成 embedding → exact ground truth → load → stress → recall/latency”变成可以重跑的实验链，使 embedding model、index 和 serving backend 可以在同一 measurement plane 上比较。

### 可信度与局限

这是一项 Qdrant 主导的厂商发布，目前公开的是数据和 Benchmark infrastructure，不是一个经过第三方审计的“Qdrant vs Milvus vs Elasticsearch”中立排行榜。FineWeb 的数据分布也不能代表电商、企业知识库、广告或高过滤率业务。

10B exact ground truth 的生成成本极高，普通团队很难完整复制。更现实的使用方式是复用已经发布的 ground truth，或者用 Supernova 在自己的百万／亿级数据上验证方法学。

### 最值得继续追踪

重点等待独立团队在同一硬件和相同 recall target 下报告 **index build time、RAM / SSD、QPS、p95 / p99、filtered recall、更新吞吐和成本**。只有这些指标一起出现，十亿级 benchmark 才能真正改变数据库选型和 RAG infrastructure 设计。

## 6. Hugging Face WebGPU Kernels：Browser AI 开始建立可验证的 Kernel Registry

**原始来源：** [Introducing @huggingface/kernels: 200+ WebGPU Kernels for Local AI](https://huggingface.co/blog/webgpu-kernels)  
**Kernel Collection：** [Hugging Face WebGPU Kernels](https://huggingface.co/webgpu-kernels)

### 发生了什么

Hugging Face WebAI 团队发布 207 个 WebGPU kernels 与 JavaScript loader `@huggingface/kernels`。与“仓库里放一批 WGSL shader”不同，每个 kernel 都作为独立、版本化 artifact 发布，同时携带 `manifest.json`、correctness cases、benchmark cases、provenance 与 WGSL templates。

同时发布的 Fleet 可以直接在浏览器中对本机 GPU 做 correctness / performance 测试，并在用户同意后贡献设备证据。目标是解决 WebGPU 最麻烦的问题之一：同一 shader 在不同 GPU、driver、browser、shape 上可能具有完全不同的性能和正确性边界。

### 关键结果

Apple M4 GPU 与 ONNX Runtime Web dev build 的 operation-level 对比：

| Operation | Hugging Face kernel | ORT WebGPU | Speedup |
|---|---:|---:|---:|
| Add | 0.064 ms | 0.227 ms | **3.52×** |
| MatMul | 0.115 ms | 0.131 ms | **1.14×** |
| Softmax | 0.114 ms | 0.240 ms | **2.11×** |
| LayerNorm | 0.061 ms | 0.135 ms | **2.22×** |

全部可比 case 的几何平均为 **2.57×**、中位数 **1.90×**，629 wins / 176 losses / 4 ties。

### 为什么重要

Local AI 的长期瓶颈并不只在模型量化。浏览器推理面对高度异构的 GPU 与 driver，而传统 kernel optimization 往往依赖少数实验室硬件。把 kernel contract、正确性测试、benchmark case 与真实设备 evidence 绑定在一起，更像一个“硬件条件化的软件包管理层”。

如果 Fleet 最终积累足够多真实设备结果，runtime 可以从固定 shader 逐步演进到：

```text
(model op, shape, dtype, browser, GPU)
→ 已验证的 kernel candidates
→ correctness-compatible subset
→ 选择该设备最快 variant
```

### 可信度与局限

headline 的 2.57× 只来自 Apple M4，且 1,756 个初始 test cases 中只有 **809 个**满足双方输出匹配和计时可靠条件后进入比较；剩余 947 个没有进入这个平均值。这个筛选必须和 headline 一起读。

更重要的是，计时只覆盖 GPU 上的 operation execution，明确排除了 kernel loading、session creation、input upload、shader compilation 和 readback；它也不是完整模型 benchmark。某个 kernel 快 2× 并不意味着浏览器 LLM tokens/s 会快 2×。

### 最值得继续追踪

Fleet 是否会公开更细的 device/browser correctness distribution，以及这些 kernels 上游进入 ONNX Runtime 后，完整 Transformer / VLM 在 Windows、macOS、Android 不同设备上的 **TTFT、tokens/s、memory 与 energy** 是否真正改善。

## 今日可立即实践的一件事

给当前一个长程 Coding / Research Agent 做一个最小 **Dependency-DAG State Ablation**。不要先改模型，只把原来散落在聊天历史或 `TODO.md` 里的任务状态抽成结构化节点：

```yaml
id: exp-17
objective: compare GRPO credit estimators
depends_on: [dataset-v3, baseline-grpo]
status: ready
artifact: null
verifier:
  type: metric_check
  condition: "eval_count >= 3 and no_nan == true"
provenance:
  created_by: planner
  last_updated_by: null
```

每个节点只允许 `blocked → ready → running → verified / failed` 等显式转移；`verified` 必须由程序化测试、独立 Judge 或人工验收产生，执行 Agent 自己不能直接宣布完成。让 Agent 每次只读取 ready nodes、直接依赖和相关 artifact，而不是重新加载完整历史。

对 10–20 个可重放的长任务比较：

```text
Full-history / summary baseline
vs.
Dependency-DAG state
```

至少记录：重复工作次数、错误依赖执行次数、context tokens、人工干预次数、verified task success 和失败后的恢复时间。

**停止条件：** 如果 DAG 只增加管理动作，却没有减少重复工作、状态遗忘或错误依赖，就不要继续复杂化 Harness；你的任务可能本身没有足够强的 dependency structure。反过来，如果任务越长收益越明显，就优先投资 state representation 和 verifier，而不是继续单纯增加 context window。

> **今日主线：** Harness–Inference Co-design · Verifiable Abstention · Sequence-level OPD · Conformal Self-Verification · Adaptive User Memory · High-Compute RL Infrastructure

arXiv 最新常规公告批次为 **2026 年 10 月 6 日**：cs.AI 554 条、cs.CL 243 条、cs.LG 600 条、cs.IR 33 条。分类之间存在大量交叉收录，不能直接相加。

今天更值得连起来看的变化，是 Agent 系统的优化边界继续外扩：Harness 开始把工作流意图传给推理引擎，推理引擎也把缓存和队列状态反馈给 Harness；“是否应该拒答”开始被当成 Harness 与 Environment 共同训练的问题；Post-training 则尝试把高成本 test-time search 直接蒸馏回模型。推荐侧，长期稳定偏好和短期会话意图被进一步拆成不同更新速度的用户状态。基础设施侧，Reflection Beam 公布了一组少见的超大规模 RL 工程数据，值得比单纯模型榜单更认真看。

## 今日核心判断

1. **Agent Serving 的下一个系统接口，很可能是 Harness 与 Inference Engine 的双向协议。** HEAR 让 Harness 声明工作流依赖、Context 生命周期和目标，让 Engine 回传队列、KV、资源压力和能力信息；论文报告 SCBench batch speedup 1.61×、median TTFT 2.23× 改善，并在 BrowseComp-Plus / DeepResearchBench 获得 1.23× / 2.45× 端到端加速。重点是打破“应用层看不到运行时、运行时看不到 Agent 工作流”的抽象墙。

2. **可靠拒答需要可训练的不可完成任务分布。** HERA 通过受控环境变异构造可完成 / 不可完成任务对，并让 Harness 与环境共同演化；held-out abstention accuracy 从 61.7% 提到 83.3%，feasible completion 从 68.3% 提到 76.7%。最佳 Harness 在另外 19 个 LLM 上平均带来 +15.3pp abstention improvement，说明拒答能力并不只属于模型权重。

3. **Sequence-level power distribution 可以被直接蒸馏，而不必每次 inference 都做 Best-of-N。** OPPD 用 SMC 近似 Teacher 的幂分布，再把 sequence weight 用于 on-policy MLE；MATH500 / GSM8K 的单次生成准确率相对未训练模型分别 +23.0 / +27.3 points，并在论文比较中恢复 16-candidate power sampling 约 94% 的增益。需要同时警惕 sharpening tax：单次准确率提高，并不保证 pass@$k$ 和解法覆盖率不下降。

4. **Web Agent 的 Judge 信号开始被编译为可复用验证器。** CLIFT 让 Agent 针对自己的轨迹回答自然语言 verification questions，再用 conformal certifier 筛掉与训练时 Judge 不一致的信号；冻结后的 certified bank 可以在 test time 直接做 trajectory selection，不再调用外部 Judge。方向很有潜力，但公开摘要没有给出统一效果量，且 conformal validity 依赖条件化和分布假设。

5. **长期用户偏好与短期会话意图应使用不同更新速度。** MATE 将用户状态拆成长短期 Memory，新交互根据历史重复支持度和近期一致性分别更新；模型上线后保持共享参数冻结，只更新每用户两份 Memory。MovieLens-10M、Amazon Luxury Beauty、KuaiRec 上，mean NDCG@10 相对最强外部基线提升 7.0%–13.2%。目前仍是离线公开数据集证据。

6. **高计算 RL 的工程瓶颈已经变成环境、沙盒、权重分发与奖励完整性的系统问题。** Reflection Beam 披露 501B total / 23B active 的 MoE，在 RL 阶段使用 10.5K GB300、4 周生成 1 亿+ rollouts、约 13 亿 sandbox instances，峰值支持 17 万并发 sandbox。模型权重与完整技术报告尚未正式发布，能力数据仍主要来自建设方。

## 1. HEAR：Harness 与推理引擎不应继续互相失明

[论文原文](https://arxiv.org/abs/2610.06597)

### 发生了什么

今天多数 Agent Stack 有一个很强的分层假设：Harness 负责 plan、tool、memory、workflow，Serving Engine 只负责把 token 算出来。问题是两边掌握的信息刚好互补，却几乎不通信。

HEAR（Harness–Engine Agent Runtime）定义双向协议。Harness 可以传递 workflow dependency、context lifetime、execution requirement 和 objective；Engine 则暴露 queue、KV locality、resource pressure、runtime capability 与执行结果。协议语义和具体优化策略分离。

### 关键结果

| 设置 | 报告结果 |
|---|---:|
| SCBench batch speedup | **1.61×** |
| SCBench median TTFT | **2.23× 更快** |
| BrowseComp-Plus 端到端 | **1.23×** |
| DeepResearchBench 端到端 | **2.45×** |

论文报告这些优化没有观察到任务质量下降。

### 为什么重要

长程 Agent 的计算结构天然不均匀：有些分支会被复用，有些 context 很快失效，有些 tool result 会成为后续多个 turn 的共享前缀。Engine 如果只看到一堆独立请求，很难进行正确的 KV 保留、批处理和优先级调度。

未来 Serving API 可能从请求级 RPC 变成工作流调度接口：Harness 传递依赖、生命周期和优先级，Engine 决定调度与 KV 策略，再把运行时状态反馈给 Harness。

### 可信度与局限

这些结果来自论文自己的 runtime 和 benchmark，不能直接当作任意 vLLM / SGLang 部署都会获得相同比例收益。“没有观察到质量下降”也不等于证明所有调度策略质量等价。

更大的工程难题是标准化：如果每个 Harness 都表达不同语义、每个 Engine 暴露不同 runtime state，协议很容易退化成新的 vendor-specific API。

### 最值得继续追踪

关注 HEAR 是否能沉淀出稳定的最小接口：**context lifetime、branch relation、reuse hint、latency objective、memory budget**。如果这些字段跨 Harness 都成立，它才有机会成为 Agent Serving 的真正系统层。

## 2. HERA：拒答能力也可以通过 Harness–Environment 共演化训练

[论文原文](https://arxiv.org/abs/2610.06563)

### 发生了什么

Agent 在真实环境中常遇到不可完成任务：权限缺失、资源不存在、目标相互冲突、关键工具不可用。普通 benchmark 大多只测完成任务，因此模型容易形成一个危险偏置：只要收到目标，就持续尝试。

HERA 通过 controlled environment mutation 生成成对任务：一边保持 feasible，一边刻意移除必要条件使其 infeasible，同时保留可验证性。Harness 再根据此前失败模式持续调整，两者共同演化。

### 关键结果

| 指标 | Base | HERA |
|---|---:|---:|
| Held-out abstention accuracy | 61.7% | **83.3%** |
| Feasible completion | 68.3% | **76.7%** |
| 跨 19 个其他 LLM 的 abstention | — | **平均 +15.3pp** |

论文还报告，小模型在优化后的 Harness 下可以接近更强模型，并给出约 85% 更低成本的估算。

### 为什么重要

会拒绝不可完成任务并不是普通 confidence calibration。Agent 必须先通过环境交互确认缺失条件，再决定停止，而且不能因为更保守而伤害可完成任务。

HERA 的关键贡献是把 abstention 数据从静态 prompt 变成**可执行环境中的可验证对照**。

### 可信度与局限

不可完成任务由受控 mutation 构造，未必覆盖现实中最难的模糊情形：目标歧义、依赖服务偶发故障、权限稍后恢复。

85% 更低成本依赖具体模型价格和调用设置；真正更强的证据是跨 19 个模型的 Harness transfer。

### 最值得继续追踪

把 infeasibility 拆成 **hard impossible、temporarily unavailable、insufficient evidence、needs user clarification**。生产 Agent 不能把所有当前做不成都压成一个 stop action。

## 3. OPPD：把 inference-time power sampling 蒸馏回单次生成

[论文原文](https://arxiv.org/abs/2610.06804) · [代码](https://github.com/ArminAzizi98/OPPD)

### 发生了什么

Power distribution 对完整答案概率做：

$$
q(y\mid x)\propto p(y\mid x)^\alpha,\qquad \alpha>1.
$$

它会把概率质量进一步集中到模型本来就偏好的高概率完整序列。直接从这个分布采样通常需要生成很多候选再评分，推理成本高。

OPPD 用 Sequential Monte Carlo 在 Student 的 on-policy trajectory 上近似 Teacher power distribution，再把 sequence weight 用于最大似然训练。目标是把多候选 search 后更可能选中的答案摊销回模型本身。

### 关键结果

| Benchmark / 对照 | 结果 |
|---|---:|
| MATH500 vs 未训练 | **+23.0 points** |
| GSM8K vs 未训练 | **+27.3 points** |
| vs published 64-candidate power sampling | **+2.4 / +3.5 points** |
| 16-candidate search gain recovered | **约 94%** |
| vs GRPO：MATH500 / GSM8K / AIME | **+3.8 / +4.0 / +5.4** |

论文还报告，经过 GRPO 后再做 OPPD 仍可继续增加最高 9.3 points；数学训练也能让 HumanEval 提高最高 5.3 points。

### 为什么重要

这提供了一个 test-time → train-time amortization 路线：先明确一个高成本但有效的 inference distribution，再训练模型直接逼近它。OPPD 学的不是某个固定 Teacher answer，而是经过 sharpening 的完整序列分布。

### 可信度与局限

最强结果仍集中在数学和代码 benchmark。Power distribution 本身偏向已有高概率区域，因此更像把已有能力变得更容易采到，不能据此证明能力边界一定扩张。

Sharpening 还可能降低多样性。应同时报告 pass@1、pass@$k$ 和 distinct strategy coverage。

### 最值得继续追踪

把 OPPD 用到 Tool-Agent：对完整 trajectory 做 sequence-level reweighting，同时检查成功率、工具路径多样性和 recovery coverage。

## 4. CLIFT：把昂贵 Judge 的知识编译成可复用 self-verification bank

[论文原文](https://arxiv.org/abs/2610.06829)

### 发生了什么

Web Agent 的 terminal reward 常只有 success / failure，太稀疏；每条 trajectory 都调用 frontier Judge 又太贵，而且部署时未必能继续使用同一个 Judge。

CLIFT 让 Agent 针对自己的 rollout 回答一组自然语言 verification questions。训练阶段再用 Compositional Conformal Certifier，只保留与外部 Judge 在条件化证据上稳定一致的 verification signals，并给它们 signed trust weight。

冻结后的 verifier bank 在 test time 可以直接用于 trajectory selection 和 conservative swap，不再调用外部 Judge。

### 为什么重要

这相当于把昂贵监督从每条新 trajectory 都重新问 Judge，变成先用 Judge 学会一组哪些 self-check 值得信，随后重复复用。

如果有效，它能同时改善训练 credit 与 test-time selection，而且不会把生产系统永久绑定在一个昂贵闭源 Judge 上。

### 可信度与局限

论文摘要给出 WebArena Infinity 的 open-source SOTA、向 GPT-5.5 的 VisualWebArena transfer，以及 Online Mind2Web zero-shot improvement，但没有统一披露 headline effect size，因此不应自行补数字。

Conformal guarantees 也不是任何未来网页都可靠的保证；其有效性依赖校准条件、数据分布和 verification question 的覆盖范围。

### 最值得继续追踪

看 verifier bank 在**网站 UI 改版、tool schema 变化和新领域**下多久失效，以及是否可以做 drift detection 和 selective re-calibration。

## 5. MATE：推荐用户状态应该有两种时间常数

[论文原文](https://arxiv.org/abs/2610.06050)

### 发生了什么

LLM-based Recommender 如果把完整历史压成一份用户 Memory，会遇到典型冲突：长期偏好应该稳定，短期 session intent 又必须快速响应。

MATE 维护 long-term / short-term 两份 Memory。每次交互先判断它与历史重复支持和近期行为的一致程度，再决定保守更新长期状态，或更快修改短期状态；后续请求根据近期上下文动态混合两者。部署时共享模型权重冻结，每用户只更新两份 Memory。

### 关键结果

在 MovieLens-10M、Amazon Luxury Beauty、KuaiRec 上，论文报告 mean NDCG@10 相对最强外部基线提升 **7.0%–13.2%**。

### 为什么重要

推荐系统里用户是谁和用户此刻要什么本来就是不同时间尺度。把两者压进同一个向量或 Summary，会使新兴趣更新太慢，或让偶发 session 噪声污染长期画像。

### 可信度与局限

证据来自离线公开数据集，没有真实线上 A/B，也没有证明长期 Memory 更新在数月使用中不会积累偏差。

一旦错误 preference 被写入长期状态，它可能通过后续推荐不断自我强化，因此 production 版需要 provenance、decay 和用户可编辑接口。

### 最值得继续追踪

把长期 Memory 的写入改成**延迟确认**：只有某个偏好跨多个独立 session 重复出现，才从 short-term 晋升到 long-term。

## 6. Reflection Beam：1 亿 Rollout 之后，RL 扩展首先是一个系统工程问题

[官方技术文章](https://reflection.ai/blog/introducing-beam)

### 发生了什么

Reflection 10 月 5 日公开 Beam：501B total / 23B active 的 sparse MoE，面向 coding、reasoning 和 agentic workloads。模型仍处于 early access / final red-teaming 阶段，权重、完整 technical report 和 model card 计划本月发布。

真正有信息量的是 RL 基础设施数据：4 周、10.5K NVIDIA GB300、超过 1 亿 rollouts、约 13 亿 sandbox instances，最大 context 256K；平台峰值支持 17 万并发 sandbox。权重到 inference fleet 的 median update 约 12 秒，71 次 inference incident 都没有终止训练任务。

### 关键结果 / 系统数据

| 指标 | Reflection 披露 |
|---|---:|
| Model | **501B total / 23B active** |
| Pretraining tokens | **23.8T** |
| RL rollouts | **100M+** |
| RL GPUs | **10.5K GB300，4 周** |
| Sandbox instances | **约 1.3B** |
| Peak concurrent sandboxes | **170K** |
| Median weight deployment | **约 12s** |
| Trainer dynamic packing | **99.99% full** |

### 为什么重要

当 RL 进入 10^8 rollout 量级，主要问题已经不再只是 PPO / GRPO 公式。必须解决 sandbox provisioning、rollout fleet 故障恢复、训练与推理权重一致性、reward exploit screening、长轨迹 packing、跨机架权重分发。

Reflection 还披露：用 reward-design 特征预测 RL gain 的相关性 $r=0.79$，高于只看 Best-of-N ceiling 的 $r=0.46$。如果能被独立复现，大规模 RL 前可以更系统地筛 reward / rubric。

### 可信度与局限

当前性能、效率与基础设施数据几乎全部来自 Reflection 第一方。Beam 权重和完整技术报告尚未正式发布，外部无法复算训练配方、安全结果和 benchmark setup。

其 inference compute 比较使用近似 FLOPs，明确排除了 prefill、attention 和 serving overhead，因此不能把图中的效率直接当作真实在线成本。

### 最值得继续追踪

等权重和 technical report 发布后，优先验证：**高 compute RL 的真实 scaling curve、reward-integrity pipeline 能否复现、23B-active MoE 在长 Agent Session 中的端到端 cost / latency**。

## 今日值得收藏的代码 / 学习资源

**MemPilot** 把 Agent Memory 变成多步 RL controller：在 query-agnostic memory retrieval 和按 Query 重新整理原始多模态历史之间动态选择，还能决定证据量、调用哪类 LLM/VLM、是否访问视觉输入。五个 multimodal memory benchmark 上报告更好的 performance–cost–latency frontier。  
[论文](https://arxiv.org/abs/2610.06830) · [GitHub](https://github.com/ViktorAxelsen/MemPilot)

**Agentic Retrieval** 提供一个很有用的成本反例：ReAct-style LLM + Retriever 在复杂检索上相对同 embedding model 的 standard retrieval 提升 **8.7 nDCG@10**，但平均 latency 是 **107.4s vs 0.67s**，每个 Query 使用约 **764.1K input tokens + 5.8K output tokens**。这说明更强和值得生产化是两道题。  
[论文](https://arxiv.org/abs/2610.05750)

**Evidence-Grounded Oversight** 的 AgentMonBench 与 EBG 不让监督器重新阅读整条长轨迹，而是把 source-linked evidence 聚合成 behavior graph，再帮助 monitor 找哪些自主决策值得人确认、证据在哪里。八个模型上大多改善 decision identification 与 evidence localization。  
[论文](https://arxiv.org/abs/2610.06406)

**Judged Useless, Queried Anyway** 给出一个非常实用的 Harness 负结果。七个 Agent 对失败检索源的结果有 **97%–100%** 概率明确判断为 useless，却大多不会据此停止；只有 Harness 强制加入连续五次 useless 后必须整合并决策的 integration step，stopping 才真正和 evidence 对齐。300 个 fresh questions 的 preregistered replication 复现了这一点。  
[论文](https://arxiv.org/abs/2610.06191)

**GraphDecide** 继续给 Decision Model 热潮降温：准确识别 adjacency 不代表能正确理解更广泛 graph structure；graph + text 双输入也不稳定提高结果；能构造 feasible solution 更不等于 solution quality 高。  
[论文](https://arxiv.org/abs/2610.06354)

**Mistral Large 4** 在 10 月 6 日进入 public preview：官方文档列出 **1.05T total / 49B active、1.6B vision encoder、1M context**，支持 function calling、structured outputs 与 Agents API。需要精确表述：**现在是 API preview，权重尚未公开，计划月底发布**；open-weight SOTA 主张应等权重与第三方评测后再判断。  
[官方发布](https://mistral.ai/news/mistral-large-4/) · [模型文档](https://docs.mistral.ai/models/mistral-large-4-0)

## 今日最值得花 30 分钟阅读的一项

**首选 HEAR：Can Agent Harnesses and Inference Engines Hear Each Other?**

[论文原文](https://arxiv.org/abs/2610.06597)

建议把 30 分钟集中在四件事：Harness 到底掌握哪些 Engine 看不到的信息；Engine 的 queue / KV / resource signal 又如何影响 Harness；为什么协议语义需要和优化策略分离；最后看 online cache-aware coordination 和 execution-mode selection 的具体实验。

> **Agent Serving 的最优调度无法只在应用层或推理层单独完成。工作流语义与运行时资源状态必须开始互相可见。**

这与最近 Context Compaction、KV Tiering、Decision Model、Multi-agent orchestration 会自然汇合，可能形成未来 Agent Runtime 的一个核心接口层。

## 今日可立即实践的一件事

给现有 Agent Serving 做一次 **Harness–Runtime Information Gap Audit**，先不要改模型。

从最近 50–100 条长程 Agent 任务里，记录 Harness 当前知道、但推理服务完全不知道的字段，例如 branch dependency、某段 context 是否还会复用、tool call 后旧 prefix 是否失效、任务 deadline / latency class、哪个 subagent 在关键路径上。再记录 Engine 知道、但 Harness 不知道的状态：queue depth、prefix-cache hit、KV pressure、batch wait、prefill cost、OOM / eviction risk。

然后只选择 **1–2 个最明显的跨层信号**做 A/B。例如 Harness 给每个请求增加 context_lifetime={ephemeral,reusable} 和 critical_path=true/false，Engine 只据此改变 KV 保留与 batch priority。

| 指标 | 目的 |
|---|---|
| Task Success | 调度不能伤能力 |
| Median / P95 TTFT | 是否改善关键路径 |
| End-to-end task latency | 是否真的更快完成任务 |
| KV hit / eviction | lifetime hint 是否有效 |
| GPU utilization | 是否只是把延迟转移给其他请求 |
| Cost per successful task | 最终经济价值 |

真正需要回答的是：

> **当前 Agent 的系统瓶颈，是推理引擎不够快，还是 Harness 和 Engine 各自掌握了一半信息，却从来没有互相告诉对方？**

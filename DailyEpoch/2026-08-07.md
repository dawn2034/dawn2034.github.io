# 每日 AI 技术简报｜2026-08-07

arXiv 最新公开批次是 **8 月 6 日**：cs.AI 176 项、cs.CL 107 项、cs.LG 172 项、cs.IR 12 项；分类存在交叉收录，不能直接相加。今天最值得看的不是某个新榜单第一，而是三个更基础的问题：**Agent 的“自我进化”究竟发生在哪里；长程 Agent 的信用分配怎样从 episode-level 下沉到 step-level；以及 Skill 已经存在时，模型到底会不会主动找到并正确执行它。**

## 今日核心判断

第一，**固定模型权重也可以表现出持续改进，但目前最可靠的机制仍然是“持久状态 + 验证 + 回滚”，不是神秘的自我进化。** ARGUS 的结果相当强，但它关于长期演化的证据主要是纵向观察，还不是严格的受控学习实验。

第二，**Search Agent 的失败轨迹不能一律给负奖励。** ABSeeker 显示，失败轨迹里经常存在真正有价值的搜索步骤；成功轨迹里也会混入低质量动作。这对 GRPO/Agent RL 的 reward granularity 很重要。

第三，**Skill Library 的核心瓶颈已经从“有没有 Skill”转向“能否 Trigger → Retrieve → Comply”。** Skill-Use 的最强配置综合分只有 0.613，而且 Harness 本身足以显著改变模型排名。

第四，**RL rollout 加速正在进入“在线适应 drafter”阶段。** SpecRoll 的价值不是单纯 speculative decoding，而是解决训练过程中 policy 持续变化、静态 drafter 很快过期的问题。

第五，**长上下文训练的数据结构可能比单纯长度更重要。** OctoLong 用真实跨仓库依赖构造百万 Token 上下文，只替换约 12% 的常规 context-extension 数据，就观察到多个长程能力提升。

## 1. ARGUS：固定权重 Agent 也能“进化”，但进化的是 Runtime

### 发生了什么

ARGUS 把一个长期 Agent 拆成 Manager、Planner、Engineer 和 Reviewer，围绕持久化 project state 执行一系列有边界的 mission。模型权重始终冻结；被持续修改的是：

$$
\text{memory}
+\text{skills}
+\text{procedures}
+\text{verifiers}
+\text{routing}
+\text{rejected routes}
$$

而且这些状态并不是 Agent 想写就写，原则上需要角色审查，并优先经过任务原生 verifier 验证。

论文在 SWE-Bench Pro 上报告约 **78%**，Direct Copilot 为 59%，代价是 aggregate token 约为后者的 1.41 倍。随着运行进入所谓 mature waves，solve-input token 相比启动阶段下降 21%，active workflow time 下降 15%；系统记录了 34 次 verifier recovery 和 22 次严格 review-loop rescue。除此之外，它还跑了数学研究、GPU kernel、训练任务和论文生产 pipeline，其中一个 RWKV6 kernel 最终被上游项目接受。

### 为什么重要

这比常见的“让 Agent 反思一下，把经验追加到 Markdown”要严格得多。

ARGUS 实际上在建立一个：

$$
\text{执行}
\rightarrow
\text{验证}
\rightarrow
\text{更新状态}
\rightarrow
\text{保留失败路线}
\rightarrow
\text{下一轮重新规划}
$$

的 runtime learning system。

特别值得注意的是它区分 **stable user intent** 和可以被证据修正的 operational objective。长期 Agent 必须能够 pivot，否则错误目标会被越做越深；但又不能把任意偏航包装成“自主修正目标”。

### 可信度与局限

这里需要给论文的“self-evolving”降一点温。

作者自己明确承认，关于成熟阶段效率改善的长期证据是 **observational，而非 controlled learning ablation**。任务顺序、Harness 调整、模型熟悉度和项目难度都可能共同影响后期效率。不同 benchmark 也使用了不同 backend 和 protocol，因此它的广泛结果不能理解成一张严格可横向比较的统一排行榜。

所以目前事实支持的是：

> ARGUS 展示了一套有效的固定权重、验证驱动、持久状态 Runtime。

还不能严格证明：

> Agent 已经通过跨任务积累形成了持续增强、可归因的通用能力。

### 最值得继续追踪

真正关键的消融是：随机打乱任务顺序、冻结已有经验状态、清空经验状态以及将成熟 Runtime 回放到全新任务集。如果成熟版仍稳定优于启动版，才更接近“runtime learning”的因果证据。

## 2. ABSeeker：失败轨迹中也可能藏着正确搜索步骤

### 发生了什么

ABSeeker 提出 **Answer-Backtracked Credit Assignment，ABC**。

对于一个有可验证答案的问题，系统从最终答案反向搜索出一组 intermediate clues，然后重新检查 Agent 原来的每一步搜索行为，看这一动作是否真正接近了这些 clue。于是：

- 失败轨迹里的好搜索可以得到正信用；
- 成功轨迹里的错误、重复搜索可以得到负信用。

这些 step-level 信号分别用于 ABC-SFT 和 ABC-GRPO。最终只使用 **8.5K 个训练样本**训练 Qwen3.5-4B。BrowseComp 得分为 37.3%，BrowseComp-ZH 为 39.1%；加入 context management 后分别提高到 **55.3% 和 52.9%**。

论文的轨迹分析很值得注意：即使最终成功的轨迹中，仍有约 4% 的步骤被判定为明显低质量；而最终失败的轨迹中，接近 10% 的动作具有较高正向信用。

### 为什么重要

普通 Agent RL 使用：

$$
R(\tau)\in\{0,1\}
$$

会把一个 50 步轨迹压缩成一个结果。

问题是，如果前 47 步都正确，第 48 步误判，整个轨迹被赋予失败奖励，实际上浪费了大量可学习的信息。

ABC 的思想更接近：

$$
R_t=
\text{这一步是否取得了解题所需的新证据}
$$

这对于 Search Agent、Deep Research Agent 甚至 Tool Agent 都比纯 outcome reward 更符合真实结构。

它也与 process reward model 有个重要区别：ABC 不直接让 Judge 判断“这一步推理看起来好不好”，而是从最终答案逆向恢复证据节点，再判断步骤是否服务于这些节点。

### 可信度与局限

它仍然严重依赖 **ground-truth answer**。

如果问题是“分析未来五年 Agent 架构趋势”这类开放任务，没有唯一正确答案，就很难从答案可靠地回溯 clue。此外 clue recovery 和 step scorer 使用了 DeepSeek-V4-Flash，所以训练数据里仍存在强 LLM Judge 依赖。

另一个需要警惕的数字是 context management 后的 55.3%。这不是单纯 ABC 训练带来的模型能力，因此不要直接拿它和一个裸 30B Search Agent 比参数效率。

### 最值得继续追踪

把 ABC 从 answer-backed 扩展成 **evidence-backed credit assignment**：不是从标准答案反推，而是从被验证的 citation、数据库状态、代码测试或工具返回反推。这会更适合真实 Agent RL。

## 3. Skill-Use：模型知道 Skill 存在，不代表它真的会使用

这是今天我认为**最值得警惕的一篇 Agent 论文**。

### 发生了什么

过去很多 Skill benchmark 实际上偷偷给模型开了上帝视角：

> “这是正确的 Skill，现在请使用它解决任务。”

真实 Agent 不是这样。它先看到几十甚至几百个 Skill 的名字和简短描述，必须自己决定：

$$
\text{是否需要 Skill}
\rightarrow
\text{哪个 Skill}
\rightarrow
\text{读取完整 Skill}
\rightarrow
\text{执行 procedure}
\rightarrow
\text{遵守禁止边界}
$$

Skill-Use 因此将能力分解为三个维度：

**Trigger**：是否主动触发正确 Skill；  
**Compliance**：是否完整执行 Skill 规定的 procedure；  
**Boundary**：是否避免 Skill 明确禁止的操作。

基准包含 79 个真实 Skill、177 个可执行任务、9 个领域和 1,314 个 rubric item，全都在 Docker sandbox 中实际执行。

结果相当不乐观。最强配置 GPT-5.5 + Claude Code 的：

$$
Trigger=0.972
$$

但：

$$
Compliance=0.611
$$

$$
Boundary=0.718
$$

最终综合 SU 只有 **0.613**。即使只统计已经成功触发 Skill 的轨迹，最高 procedural compliance 也只有约 0.638。

### 为什么重要

它揭示了 Skill Agent 的一个常见错觉：

> “把专家 SOP 写成 Skill” ≠ “Agent 获得了这项 SOP 能力”。

Agent 可能成功找到 Skill，甚至明确说“我要按照 Skill 做”，然后：

- 漏掉其中一个验证步骤；
- 调换必须固定的顺序；
- 忽略一个禁止操作；
- 只执行最显眼的前半部分；
- 在工具反馈后又回到自己的默认行为。

还有一个非常实用的结果：**预加载完整 Skill 主要改善 retrieval/trigger，对已经触发后的 Compliance 改善很小。**换句话说，把 Skill 全塞进 system prompt 并不能解决 procedure following。

### 一个尤其重要的发现：Harness 是能力的一部分

同一个模型换 Claude Code / Codex Harness，表现和排名都会明显变化。例如 GPT-5.5 的 conditional compliance 换 Harness 后可以下降超过 0.1。

因此，更准确的定义应该是：

$$
\text{Skill capability}
=
f(\text{Model},\text{Harness},\text{Skill})
$$

而不是一个模型自身固定属性。

### 可信度与局限

这篇论文也不是没有测量问题。

部分 rubric 使用 GPT-5.4 作为 Judge；重复评分的一致性并不完美，SU 的 ICC 约为 0.53，Boundary 约为 0.47。也就是说，**Judge noise 本身已经足够影响几个百分点的模型差异。**

因此其绝对排名不应过度解读，但“Trigger 很高、Compliance 明显更低”这个结构性结论相当有价值。

### 最值得继续追踪

未来 Skill benchmark 应强制报告：

$$
Trigger\times Compliance\times Boundary\times Regression
$$

最后一个 Regression 尤其重要——Agent 是否因为 Skill 的存在反而把原本会做对的任务做错。

## 4. SpecRoll：RL rollout 的 speculative drafter 也需要在线适应

### 发生了什么

RL post-training 中，rollout policy 不断更新。

这会给 speculative decoding 带来一个很现实的问题：

$$
\pi_{\theta_t}
\neq
\pi_{\theta_{t+100}}
$$

如果一直使用固定 drafter，它会迅速变 stale；如果频繁完整训练 drafter，又把加速收益吃掉。

SpecRoll 使用两级适应。

快路径 **Reflex** 根据 target verifier 延迟反馈，在单条 trajectory 内对 hidden state 做有界修正，不反向传播；慢路径只有在检测到持续 drift 时，才更新 lightweight future-token heads。

关键是所有草稿最终仍由 target policy 精确验证，因此目标采样分布不变，GRPO objective 也不需要修改。

在 1.5B–14B 五个模型、三个数学数据集上：

- rollout generation：**1.26–2.15×**；
- end-to-end GRPO：**1.21–2.04×**；
- 相对 FastGRPO，15 个 matched settings 全部更快，平均 end-to-end 再提升约 1.18×。

### 为什么重要

RL 系统优化里经常有一个被忽略的问题：

> 推理引擎不是在服务一个静态模型，而是在服务一个不断改变的模型。

因此传统 serving 中训练一次 drafter 的方案，不一定适合 on-policy RL。

SpecRoll 实际上把 drafter adaptation 拆成：

$$
\text{trajectory-local fast adaptation}
+
\text{persistent slow adaptation}
$$

这和控制系统里的 fast/slow loop 很像。

### 可信度与局限

目前只测试数学推理、最大 14B。论文自己也承认，收益高度依赖硬件、batch concurrency、回答长度和 serving stack。它给出的美元节省数字是特定 B200 价格和实验 workload 的结果，不能外推成普遍训练成本比例。

此外，这种方法真正值得比较的不只是 vanilla GRPO，而应是当前高吞吐 async rollout stack。

### 最值得继续追踪

与 veRL / SGLang / vLLM 连续批处理、异步 policy update 组合后，SpecRoll 是否仍有增量，以及在长 Agent trajectory 上 drafter drift 是否反而更严重。

## 5. OctoLong：长上下文训练缺的可能不是 Token，而是真正的长距离依赖

### 发生了什么

OctoLong 的出发点是：很多所谓“长上下文训练数据”，本质上只是把一本书、一篇长论文或一个仓库拼到 128K / 1M Token。

**长度很长，不等于存在长距离信息依赖。**

OctoLong 使用：

- AST parser；
- language server；
- package manager；

从一个代码实体出发递归跟踪跨文件甚至跨 repository 的真实引用关系，构造最多百万 Token 的 dependency-rich context。

团队训练了 600M–14B 多个模型，context-extension mid-training 总数据约 50B Token，其中 OctoLong 数据约 **6.2B，占约 12%**，随后再做约 10B Token instruction tuning。

论文报告：仅用 OctoLong 替换约 12% 的传统长上下文数据，就在 long-range retrieval、长期状态追踪、repository-level understanding 和下游 Agent task 上产生稳定提升，短上下文 API 使用也有所改善。

### 为什么重要

它提示一个比“把 RoPE 扩到 1M”更基础的问题：

$$
\text{Long Context Capability}
\neq
\text{Context Window Length}
$$

更接近：

$$
\text{Long Context Capability}
=
\text{架构容量}
\times
\text{训练时真实远距离依赖密度}
$$

如果模型在训练中从来没有必要跨 50K Token 才能完成 prediction，它没有理由学会真正利用 50K Token。

### 可信度与局限

目前最明显的局限是领域偏置：OctoLong 的长距离结构来自**代码依赖图**。

这可能尤其有利于 repo coding 和 Agent task，尚不能证明同样的收益会迁移到法律文档、科研检索、企业知识库或超长对话。

此外，50B mid-training + 10B instruction token 仍是相当昂贵的实验，外部团队完整复现门槛不低。

### 最值得继续追踪

把同一个方法扩展到“具有天然结构的非代码数据”：引用网络、法律条文交叉引用、论文 citation graph、企业文档依赖。如果仍有类似收益，就会说明 **结构化 context engineering** 可能成为 long-context mid-training 的重要方向。

## 推荐系统重点｜Two-Sided A/B Testing 不是“免费隔离”

今天推荐方向最值得读的是 Snap 研究者的 **The Price of Isolation**。

在 Creator / Viewer 双边平台中，为避免 treatment creator 的内容泄漏进 control，常见方案是分别抽取一部分 creator 和 viewer，建立两个相互隔离的子市场。

统计上这很干净，但推荐系统本身被改变了：

$$
\text{Catalog Size}
\downarrow
\Rightarrow
\text{Top Candidate Quality}
\downarrow
$$

论文用 extreme-value theory 给出了一个有意思的结论：如果匹配质量的 upper tail 较轻或有界，平台变大后隔离成本趋于消失；但如果是 heavy tail，损失可能收敛到**非零常数**，也就是说平台再大都不能消除这个问题。

生产 A/A 流量实验也观察到了明显效果：在 viewer traffic 固定为 10% 时，把可用 creator catalog 从 70% 缩到 10%，探索型 view time 下降约 **12.3%**，story completion 下降约 **19.0%**；极小隔离 cell 的损失更大。

这件事对新内容、创作者冷启动和供给侧实验尤其关键：

> 你为了消除实验组之间的 interference，可能同时人为制造了一个 catalog-thinning treatment。

因此 control 与 treatment 的差值已经不再只代表你想测试的算法。

局限也很明确：理论模型使用 order-statistics 和相对理想化的 match-quality 假设，真实 retrieval 不是 i.i.d. 抽样；论文主要研究 viewer-side engagement cost，对 creator 长期供给响应没有完整建模。

但它提出的 **preflight isolation-cost estimation** 很有工程价值。双边推荐实验以后不应只做 power analysis，还应先估：

$$
\text{Statistical isolation benefit}
-
\text{Ecosystem distortion cost}
$$

## 今日最值得花 30 分钟阅读的一项

### Skill-Use: Can LLMs Actually Use Skills in Agentic Harnesses?

我会优先读它，而不是 ARGUS。

原因是 ARGUS 展示的是一个很强的新系统，而 Skill-Use 修正的是一个**整个 Agent Skill 研究领域都容易犯的评测错误**：把“正确 Skill 已经被加载”误当成 Skill 能力。

30 分钟最值得关注四件事：先看 Trigger / Compliance / Boundary 的定义；然后看为什么 Trigger 接近 97% 时综合 SU 仍只有 61%；再看 Harness 换掉之后为什么模型排名会变；最后看 Judge repeatability，判断排行榜差异中有多少可能只是评测噪声。

我认为它最重要的一句话可以浓缩成：

$$
\boxed{
\text{Skill exists}
\neq
\text{Skill retrieved}
\neq
\text{Skill followed}
\neq
\text{Skill safely followed}
}
$$

---

## 今日可立即实践的一件事

把现有 Skill Agent 的单一“任务成功率”，拆成一次 **Trigger–Compliance–Boundary 审计**。

不要先改模型。选 30–50 个已有 Skill，每个 Skill 做至少 2 个真实任务，并另外加入一些根本不应该触发任何 Skill 的负例。运行时只给 Agent Skill 名称和简短 description，不提前注入正文。

然后分别统计：

$$
TriggerRate
=
P(\text{正确 Skill 被主动加载})
$$

$$
ComplianceRate
=
P(\text{所有必要步骤完成}\mid Trigger)
$$

$$
BoundaryRate
=
P(\text{未执行禁止动作}\mid Trigger)
$$

再额外加入最近几期简报里反复出现、但 Skill-Use 本身没有完整覆盖的一个指标：

$$
RegressionRate
=
P(\text{无 Skill 成功，但启用 Skill 后失败})
$$

最后比较两个 Harness，而不是只比较两个模型。

如果出现：

$$
Trigger\approx95\%,
\qquad
Compliance\approx60\%
$$

那么继续优化 Skill retrieval 没有多少价值；瓶颈已经转移到 **procedure execution / verification**。反过来，如果 Compliance 很高而 Trigger 很低，才应该投入 embedding、Skill description、router 或 hierarchical retrieval。

这项实验成本不大，但能直接告诉你 Skill 系统下一阶段究竟应该优化哪一层。

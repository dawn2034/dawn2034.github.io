每日 AI 技术简报｜2026-08-08

arXiv 最新公开批次是 8 月 7 日：cs.AI 201 项、cs.LG 162 项、cs.CL 94 项、cs.IR 15 项；分类存在交叉收录，不能直接相加。今天我筛下来，真正值得资深算法从业者关注的不是“又出了多少 Agent 论文”，而是三条更具体的变化：Harness 本身开始成为可优化对象；长程 Agent 的信用分配开始从 trajectory-level 下沉到 turn/error lifecycle；生成式推荐终于出现了更有说服力的线上全链路替换证据。

今日核心判断

第一，Agent 自我改进的评测问题正在变得比算法问题更重要。如果一个 Agent 可以反复读取验证集反馈、修改 Harness，再挑一个最好的版本，那么“验证集涨了”本身几乎没有证明力。HarnessOpt-Bench 的数据直接显示，可见的最佳 validation score 通常高于最终 held-out test；没有不可见测试集，所谓 self-improvement 很容易只是 evaluator search overfitting。

第二，长程 Agent RL 的问题正在从“有没有奖励”变成“奖励到底应该落在哪一步”。AgentOPSD、TRAJDEBUG 今天从训练和诊断两个方向指向同一个结论：一次失败轨迹中可能有很多局部错误，但真正决定最终失败的关键错误往往只有一个；反过来，成功轨迹里也并非每一步都值得强化。

第三，“自我蒸馏不需要监督”这个表述需要严格降温。u-OPSD 确实不使用外部标注或显式奖励，但它仍依赖模型自身多数投票构造伪答案；其伪标签实测约 13.3% 是错的。更有意思的是，提高 self-consistency 阈值反而持续降低性能，说明“高共识 = 高质量监督”并不成立。

第四，Tool Calling 可能正在从“结构化 JSON 调用”向“代码即编排”迁移，但目前证据仍只覆盖半真实环境。长调用链和大 fan-out 下 programmatic tool calling 确实很有优势；但 BFCL 使用的是 echo-return stub，并没有测试“第一个真实 API 的返回值会改变后续调用参数”的困难场景。

第五，生成式推荐今天的信号比过去大量 offline Recall@K 论文强得多。Yandex Music 的 Gryphon-v2 不是只在公开数据集上跑指标，而是直接替换“15+ 召回器 → 粗排 → 精排”的生产 Cascade，并做用户级随机 A/B。这已经值得认真研究，但它仍只证明了一个音乐场景中的短期可行性，并未证明生成式推荐应该普遍替代工业 Cascade。

1. HarnessOpt-Bench：Agent 能不能自动优化自己的 Harness，终于有了相对靠谱的评测方式

发生了什么

Scale AI 团队提出 HarnessOpt-Bench。这里被优化的不是模型权重，而是包围目标模型的 Agent Harness：Prompt、工具组织方式、执行逻辑、状态处理、验证、错误恢复等代码。

一个“Optimizer LLM + Coding Harness”拿到：

  • 初始 Agent Harness；
  • development / validation 反馈；
  • 固定的目标 Agent 调用预算；

然后自行修改 Harness，最后只能提交一个版本。真正测试分数来自搜索过程中完全不可访问的 held-out test。论文覆盖 5 个前沿优化模型、4 个任务、共 111 次优化运行。

结果里，一个很有意思的量化是：固定任务和 Harness，只换优化模型，normalized gain 平均变化 0.142；固定任务和模型，只换 Coding Harness，变化 0.079。也就是说，在这个 benchmark 中，“谁来改 Harness”的影响约是“用什么 Coding Harness 来改”的 1.8 倍，但二者都不是小变量。

为什么重要

这把最近大量所谓 self-improving Agent 拆开了：

\[\text{Agent 改进} = \text{模型能力} + \text{Harness 搜索能力} + \text{评测反馈}\]

过去常见的实验是：

Agent 看失败 → 改 Prompt / Skill / Harness → 在同一任务集上分数上涨。

这个流程本质上与 HPO 很像。如果验证集反复暴露，优化器可以逐渐学习评测器的固定漏洞，而不是获得真正泛化能力。

HarnessOpt-Bench 最重要的结果不是哪个模型排名第一，而是：大多数 run 的最佳可见 validation score 高于最终 test score。论文不能区分这是 selection overfitting 还是 validation/test distribution mismatch，但足以证明“只报告 search 中最高分”是危险口径。

可信度与局限

这篇工作的实验协议比多数 self-evolving Agent 论文严谨，但仍不是“Agent 已实现递归自我改进”的证据。

作者明确承认：benchmark 是 hack-resistant，不是 hackproof；固定 evaluator 和工具行为依然可能被重复 validation feedback 间接利用。初始 Harness 的成熟度也没有系统控制——“从一个很烂的 seed 修好”和“把成熟系统继续优化”实际上是两种不同能力。

最值得继续追踪

我最关注的是后续是否会加入 per-run evaluator jitter、环境随机化和跨 benchmark transfer。如果在 A 数据集上自动发现的 Harness patch 能在 B 数据集、甚至另一个目标模型上保持增益，self-improvement 的说服力会明显提高。

2. The Bitter Lesson of Tool Calling：Tool Agent 是否应该直接“写程序”而不是一轮轮吐 JSON？

发生了什么

这篇论文比较两种工具交互：

JSON Tool Calling

\[LLM \rightarrow JSON\ call \rightarrow Tool \rightarrow LLM \rightarrow JSON\ call \rightarrow\cdots\]

和 Programmatic Tool Calling（PTC）。

模型看到 typed Python stub 后，一次生成程序：

1
2
3

a = tool_a(...)
b = tool_b(a)
c = tool_c(...)

随后由执行器统一执行。

在 BFCL v4 的 14 个模型上，作者报告 PTC 在 11/14 个模型中达到或超过 JSON；在长链任务中，链长 ≥12 时平均优势达到 18.8 个百分点。在大量并行调用时，PTC 还能显著压缩结构化输出开销；论文测得 token 成本大约在 fan-out $N\approx26$ 后开始比 JSON 更划算。

Claude Sonnet 5 的一个压力测试尤其夸张：JSON 模式在 70 个并行调用以内保持 100% enumeration accuracy，到 72 个降到 75%，到 100 个变为 0；PTC 在 100 个仍为 100%。不过 GPT-5.6-Sol 的 JSON 到 100 个调用仍保持 100%，所以这不是 JSON 格式普遍存在的理论瓶颈，更像模型／provider 的 tool-call serialization 实现差异。

为什么重要

Agent 系统今天仍然大量采用：

\[\text{Reason} \rightarrow \text{Call} \rightarrow \text{Observe} \rightarrow \text{Reason}\]

每个工具调用都重新经过模型，长链任务的 latency 和 reasoning noise 会线性累积。

如果模型已经拥有足够强的代码能力，很多工作其实可以一次编译成“工具程序”。这实际上是把 LLM 从 step-by-step controller 提升成 workflow compiler。

对于数据分析、SQL Agent、批量检索、文件操作等任务尤其合理。

可信度与局限

标题里的 “Bitter Lesson” 有点过度包装。

最关键的问题是 BFCL 使用 echo-return stub：tool 返回的基本就是输入参数。论文自己承认，这主要测的是 argument serialization，而不是完整的 end-to-end API 执行。真实 Agent 中常见：

1
2
3
4

search() → 得到未知结果
→ 根据结果选择 id
→ fetch(id)
→ 根据内容决定 update()

这种依赖真实外部返回值的链路，无法仅凭模型参数内知识提前写死。

此外，让模型执行 Python 会扩大 sandbox、安全、资源限制和副作用管理的攻击面。

最值得继续追踪

我会重点看 mixed-mode Agent：

\[\text{LLM 生成局部程序} \rightarrow \text{遇到信息不确定点暂停} \rightarrow \text{读取真实工具结果} \rightarrow \text{继续编译下一段}\]

而不是在“全 JSON”与“整段代码”之间二选一。

3. 长程 Agent 信用分配：AgentOPSD 与 TRAJDEBUG 从训练、诊断两侧得到同一个结论

AgentOPSD：GRPO 不应该把同一个 Advantage 广播给整条轨迹

发生了什么

普通 GRPO 对一条轨迹得到：

\[A_{\text{seq}}\]

然后所有 turn、所有 token 基本共享这个方向。

AgentOPSD 认为这是不合理的。它用一个训练期才可见的 Skill-conditioned self-teacher，计算每个 turn 在“有 Skill”和“无 Skill”条件下的 log-prob gap，并把它解释成该动作对“最终成功概率”的证据。

随后维护：

\[B_k=P(\text{最终成功}\mid\text{当前历史})\]

每一步真正获得的信用由：

\[\Delta B_k=B_k-B_{k-1}\]

决定，再用它重新缩放原本的 GRPO advantage。重要的一点是：它只调整不同 turn 的更新强度，不会翻转最终 verifier 给出的成功／失败方向。

在 Qwen2.5-7B 上：

  • GRPO 的 ALFWorld 平均成功率：81.2%；
  • AgentOPSD：89.1%。

Search-QA 平均从 42.0 提升到 49.2；WebShop Accuracy 从 72.6 提升到 79.7。

为什么重要

这实际上解决 Agent RL 中一个比 PPO/GRPO 公式更基础的问题：

一条 40 步成功轨迹，究竟是哪两三步真正改变了结局？

如果前 30 步只是 routine navigation，第 31 步发现关键证据，那么前 30 步不应该得到与第 31 步同等程度的强化。

可信度与局限

“无需 critic”是真的，但并不意味着无需额外特权信息。

论文的 teacher branch 在训练时会检索一个描述正确 subgoal / action pattern 的 Skill；这个 Skill 在推理时不需要，但它参与了信用估计。也就是说，它本质上还是一种 privileged-information distillation，而不是纯 outcome reward 自己神奇地产生了 turn-level credit。

实验也只有 Qwen2.5 3B/7B 和三个相对受控环境。

TRAJDEBUG：7 个局部错误 ≠ 7 个致命错误

TRAJDEBUG 从错误诊断的方向得到了几乎同样的观察。

作者人工分析 50 条失败 Agent 轨迹，找到 381 个局部错误，平均每条 7.62 个；但每条轨迹最终只标记出一个 critical error，即真正持续传播、最终决定任务失败的错误。

将诊断转成针对性指导，然后重跑同一个失败任务，成功率平均提高 10.8%；把历史失败诊断汇总成 failure memory 再应用到 held-out task，平均提高 5.7%。

为什么重要

这说明 Agent failure analysis 不应只问：

第一个错误出现在哪一步？

而应该追踪：

\[\text{Error introduced} \rightarrow \text{repaired?} \rightarrow \text{latent?} \rightarrow \text{propagated?} \rightarrow \text{terminal impact}\]

有些错误下一步就自己修掉了；有些看起来不起眼，却改变了后面所有 observation。

可信度与局限

“critical error”本身是反事实概念：如果这一步不犯错，任务是否一定成功？仅凭已有轨迹通常无法完全回答。

同任务加入诊断后重跑的 +10.8% 也不能直接理解成模型获得了泛化能力；更强的证据是 held-out failure memory 的 +5.7%，但绝对增益仍不算很大。

4. u-OPSD：“无需任何监督”很有意思，但真正值得研究的是它为什么能容忍错误伪标签

发生了什么

u-OPSD 对同一道无标签题目采样 $G$ 条 rollout，对最终答案多数投票：

\[\tilde a = \operatorname{majority}(a_1,\dots,a_G)\]

然后从投票一致的轨迹中选一条完整 reasoning 作为 privileged teacher context，再蒸馏到与伪答案不一致的 rollout 上。

Qwen3 非 thinking 模式下：

  • 4B 相对 base：+8.5 分；
  • 8B 相对 base：+10.7 分；
  • 相对 supervised OPSD：分别 +3.2 / +2.3 分。

到了更强的 thinking 模式，优势明显缩小，只比 OPSD 高约 0.9 / 0.02 分。

最值得注意的实验其实不是主结果

作者检查伪标签，发现约：

\[13.3\%\]

是错误答案。

更反直觉的是 self-consistency threshold $\tau$：

  • $\tau=0$：step-150 平均 59.21；
  • $\tau=0.5$：53.93；
  • $\tau=0.9$：44.40。

也就是说，要求模型自己更加一致，反而让训练效果越来越差。

为什么重要

这直接削弱了一个很流行的叙事：

\[\text{模型共识越强} \Rightarrow \text{伪标签越可靠} \Rightarrow \text{训练越好}\]

这里至少第三个箭头没有成立。

更合理的解释是：过滤太严格之后，留下的大多是模型已经会做的简单题，真正有学习价值的“边界样本”反而消失了。

因此，自我进化系统可能更应该优化：

\[\text{Learning Value} \neq \text{Pseudo-label Confidence}\]

可信度与局限

所谓 “without any supervision” 应准确理解为：

不使用外部标签、外部 reward 或外部 teacher。

它绝不是信息论意义上的“无监督”：系统仍然依赖答案可 canonicalize、多条 rollout 能够互相投票，以及数学题存在相对明确的最终答案。

目前也只有 Qwen3 系列和数学推理。开放式 Agent、代码设计、研究任务是否还能靠 majority vote 构造有效 teacher，完全未知。

5. HERALD：一个 Reward 能抵抗攻击，不代表它在 RL 里真的有学习价值

发生了什么

搜索 Agent 的 Reward 常同时奖励：

  • 答案正确；
  • 有 citation；
  • citation 与内容一致；
  • 使用了 Search；
  • 没有作弊。

HERALD 做的是 counterfactual reward audit：对同一道题修改 retrieval evidence，但保持其他信息尽可能一致，看 Reward 是否仍能判断“模型实际上根本没检索到自己引用的证据”。

研究发现，原 reward 能阻止删掉搜索步骤或伪造 document ID，但一种 citation laundering 攻击仍能成功：模型可以引用 corpus 中确实存在、却没有被此次 retrieval 返回的内容。

增加一个极小的 $L$ penalty：

citation 对应的 corpus passage 必须真的存在于当前 retrieved evidence。

之后，测试中的攻击成功率降为 0，单侧上界为 0.50%。

为什么重要

这篇论文最有价值的地方其实是另一个负结果：

这个防御 detector 在 58,368 条训练轨迹里只触发 18 次。

也就是说：

\[\text{Reward 能检测攻击} \not\Rightarrow \text{Reward 能产生足够密集的训练信号}\]

安全 audit 和 RL learnability 是两回事。

可信度与局限

修复后的 reward 在 HotpotQA 和 2Wiki 满足 EM 非劣效性，但 MuSiQue 没达到。因此并不存在“加入 anti-hacking reward 永远没有质量代价”的结论。

实验仍是 Qwen3-8B、小规模 QA benchmark 和预先枚举的攻击模式。真实 Web Search 中，网页变化、snippet、缓存、搜索索引都更加复杂。

最值得继续追踪

Reward 设计不应只报告 attack success rate，而应同时报告：

\[\text{Detector precision}, \quad \text{trigger density}, \quad \text{policy learning gain}, \quad \text{clean-task regression}\]

这套口径非常适合 RAG / Search Agent 的 RL 项目。

6. 推荐系统｜Gryphon-v2：生成式推荐第一次比较像“真正替掉了生产 Cascade”

发生了什么

Yandex Music 的 Gryphon-v2 把一个传统线上链路：

\[15+\text{ Candidate Generators} \rightarrow \text{Pre-ranker} \rightarrow \text{Ranker}\]

替换成一个统一 generate-and-rank 模型。

它首先根据用户历史 autoregressive 生成 Semantic ID 候选，再用一个轻量 Ranking Module 复用已经计算好的用户 encoder state 排序。训练时仍然有强 Teacher Ranker，但通过 rollout distillation 把它的排序知识蒸馏进线上模型，所以线上不再跑 Teacher。

用户级随机 A/B 中，control 与 treatment 各占 eligible users 的 8%。结果相对原生产 Cascade：

  • Active users：+1.41%；
  • 总收听时长：+1.62%；
  • Likes：+7.12%；
  • Repeat：+15.25%；
  • 未播完比例：−9.65%。

全部报告 $p<0.001$，线上 Serving latency 与生产 Cascade 相当。

相对于“同一个生成 backbone + 在线 Teacher Ranker”的方案，Gryphon-v2 Serving throughput 约高 4×，主要因为避免了 Teacher 对最多 8000 条历史再单独执行一次推理。

为什么重要

过去很多生成式推荐论文最大的问题是：

SID Recall@K 比 SASRec 高了，然后宣布推荐范式已经变化。

Gryphon-v2 的证据级别明显不同：它真的与一个多阶段工业系统做了线上随机实验，而且 treatment 是完整替换生产 Cascade。

这说明生成式推荐的一个潜在终局确实存在：

\[\text{共享 User Representation} + \text{Generative Candidate Search} + \text{Lightweight Ranking}\]

而不是几十套异构 Candidate Generator 持续堆叠。

可信度与局限

但不要把“one model”理解成“只有一步”。

它仍然有：

  • Semantic ID 解码；
  • constrained generation；
  • collision resolution；
  • Ranking Module。

准确说，是一个线上 learned model 替代多个 learned stages。

而且线上实验只有一个音乐推荐 surface、短期 sampled traffic；论文明确没有测试 long-tail catalog coverage、艺术家多样性、novelty、exposure concentration 和长期效果。

换言之：

engagement ↑ 已经有强证据；生态质量、供给公平和长期稳定性，目前没有。

最值得继续追踪

如果后续能看到：

  • 新歌 / 长尾艺术家曝光；
  • catalog coverage；
  • 7/30/90 天 retention；
  • SID codebook 增量更新；
  • 新物品 cold-start；

那这项工作会比当前大多数 generative recommender 更有范式意义。

量化补充｜BaKron：两侧 Hessian 信息终于可以不付 $O(m^2n^2)$ 的代价

今天量化方向最值得扫一眼的是 BaKron。

传统 GPTQ 主要利用输入 activation 侧的 curvature。两侧 Kronecker-factored Hessian 可以同时描述 output-coordinate correlation，但直接在 vectorized weight 上做 adaptive rounding 的计算量过高。

BaKron 将核心求解器从：

\[O(m^2n^2)\]

降到：

\[O(mn(m+n))\]

并把 sequential step 降为 $O(m+n)$，因此能在与 GPTQ 相近的渐进复杂度等级下利用更丰富的二阶信息。

需要明确：这是离线量化器优化，不是推理 Kernel 加速论文。

不要因为它“更高效”就推断成 tokens/s 更高；这里的 efficiency 指量化求解器本身。更复杂的 Hessian 构造依然会让完整量化流程明显增加耗时。

真正值得跟踪的是：这种 two-sided curvature 是否能在 2–3 bit 极低比特区间稳定拉开与 GPTQ/AWQ 的差距，因为 4 bit 区间很多部署场景本来已经足够好。

今日值得收藏的学习资源

《Continual Learning in Transition》

这篇新综述不只是传统的 catastrophic forgetting 综述，而是把今天的 self-evolving Agent、test-time adaptation、memory、Skill、Harness 纳入统一框架，用三个轴组织：

\[\text{When}:\text{pre / post / inference}\] \[\text{How}:\text{off-policy / on-policy / beyond-gradient}\] \[\text{Where}:\text{parameters / external structures}\]

这个框架很适合判断一篇“self-evolving Agent”论文到底进化了什么：参数、Memory、Skill、Harness，还是只把历史塞回 Context。它是 taxonomy，不是实验证据，但作为近期研究地图值得收藏。

Hugging Face TRL：Multi-environment Agentic RL 已进入主仓库

TRL 的 GRPOTrainer 现在支持每个样本选择不同 Environment，并让 Environment 自己返回 Reward，可以在同一次训练里混合多个 sandbox task suite，同时接入 Harbor / OpenEnv。

这对 Agent RL 的工程价值很实际：以前每个环境都要自己写 rollout→environment→reward plumbing，现在至少开始形成统一接口。

需要注意，README 也明确区分“官方 release”和最新 source feature；若要使用最新功能，官方建议直接从 GitHub source 安装，因此现在不应默认生产环境的稳定版 pip 已经完整包含最新行为。

今日最值得花 30 分钟阅读的一项

HarnessOpt-Bench

今天我会把 30 分钟给它，而不是给性能涨幅最大的那篇论文。

原因很简单：如果自我进化 Agent 的评测协议是错的，那么后面所有算法收益都有可能是假的。

建议重点看三个部分：

前 8 分钟：评测协议。理解为什么 dev / validation / hidden test 必须彻底隔离，以及为什么必须限制 target-agent evaluation budget。

中间 10 分钟：Validation vs Held-out。注意论文最关键的负结果——search 中的最佳 visible score 系统性偏乐观。

再 7 分钟：Model vs Harness effect。看清模型本身和 Coding Harness 都能显著影响“自我优化能力”。

最后 5 分钟：Limitations。尤其是 fixed evaluator artifact 和 seed harness maturity。

它提供了一个很重要的判断标准：

\[\boxed{ \text{Self-improvement} \neq \text{在反复可见的评测集上不断涨分} }\]

真正的 self-improvement 至少必须在从未反馈给优化器的 held-out environment 上成立。

今日可立即实践的一件事

给任何正在做的 Agent / Prompt / Skill / Harness 自动优化项目，增加一个 Hidden-Test Harness Optimization Protocol。

把任务永久分成：

\[20\%\ \text{Dev} + 40\%\ \text{Validation} + 40\%\ \text{Hidden Test}\]

优化 Agent 可以看 Dev 的完整失败轨迹，也可以反复获得 Validation 的汇总成绩，但永远不能看到 Hidden Test 的样本、轨迹和逐题反馈。

每轮允许它：

1
2
3
4

inspect failures
→ modify prompt / skill / code / harness
→ evaluate validation
→ retain candidate

预算结束时只能 nominate 一个 candidate，然后测试一次 Hidden Test。

至少同时记录四个数字：

\[S_{\text{seed,test}}\] \[S_{\text{best,val}}\] \[S_{\text{final,val}}\] \[S_{\text{final,test}}\]

再定义两个指标。

Optimism Gap：

\[G_{\text{optimism}} = S_{\text{best,val}} - S_{\text{final,test}}\]

它告诉你自动优化过程究竟有多大程度是在“学 validation”。

Normalized Headroom Gain：

\[G_{\text{norm}} = \frac{ S_{\text{final,test}}-S_{\text{seed,test}} }{ 1-S_{\text{seed,test}} }\]

它比单纯的绝对百分点增益更适合比较不同 seed 强度。

最后再加一个Regression Set：专门保存 seed Agent 原本已经做对的任务。

如果一个自动生成的 Harness Patch：

  • Validation +8%；
  • Hidden Test +1%；
  • Regression −6%；

那不是“Agent 自我进化”，而是典型的评测驱动过拟合。

这套实验甚至不需要训练模型，却能非常快地判断一个 self-evolving workflow 的收益到底是真的，还是只是搜索预算制造出来的幻觉。

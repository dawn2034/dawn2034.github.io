> **今日主线：** Harness–Model Co-Evolution · Temporal OPD Credit · Looped Self-Speculation · Agentic Recommender Diagnosis · Embedder PTQ · Agentic/RAG System Benchmarks

截至今天早上，arXiv 最新常规公告批次为 **2026 年 9 月 16 日**：`cs.AI` 195 条、`cs.CL` 109 条、`cs.LG` 186 条、`cs.IR` 15 条；分类之间存在大量交叉收录，不能直接相加。今天最值得连起来看的变化，是“可学习对象”继续从模型权重向整个 AI 系统扩张：ScienceBuddy 让 Harness 与 Policy 交替改进；γOPD 把 Teacher credit 从单 token 延伸到未来轨迹；LoopSpec 直接利用 recurrent depth 做 self-speculation；推荐系统里，AURA 开始把生产日志诊断、代码上下文和改进提案串成闭环。与此同时，检索与基础设施的评测边界正在变严：Text Embedder 的 PTQ 不能照搬 LLM 经验，MLPerf 也第一次把端到端 RAG 和 Edge Agentic Inference 纳入正式 Inference 套件。

## 今日核心判断

1. **“自我改进”开始出现真正的 Harness–Model 双层闭环，但目前仍是受控共演化，不应解读成无限递归提升。** ScienceBuddy 的 inner recursion 固定模型、搜索 Harness；outer recursion 固定 Harness、用 RL 更新 Qwen3.5-4B。论文 case study 中，held-out single-attempt accuracy 从 42.2% 提到 73.3%。更重要的是，单独固定模型做 Harness adaptation、以及固定 Harness 做 RL 都能取得明显增益，说明两层确实各自提供有效信号；但实验只有有限轮次、任务集中在科学工作流，而且 Harness 诊断与编辑使用额外 frontier model，因此“递归”仍有清晰的人造边界。

2. **OPD 的下一步正在从 token-local imitation 走向可控的时间 credit。** γOPD 把常见 token-level OPD 解释为 sequence reverse-KL 的时间近似，并通过 discount 引入后续 Teacher signal，同时给出 horizon-independent variance bound；再用 Reward-Compatible Bounded Mixing 保证可验证 reward 不被 Teacher advantage 反向覆盖。Qwen3-4B Math Student 上，平均 accuracy 从 vanilla OPD 的 67.04 提到 69.49，pass 类指标平均从 77.63 提到 82.41；1.7B size-mismatch Student 也有一致收益。这个方向值得重视，因为它直接碰到了“局部稳定监督”和“长程 credit”之间的核心矛盾。

3. **Looped Transformer 的重复计算终于开始拥有与架构结构相匹配的 speculative decoding。** LoopSpec 不额外训练 Draft Model，直接从较浅 recurrent state 提取 draft，并把下一 token 的 proposal 与当前 token 的 target verification 做 pipeline；必要时再从更深 recurrence 发起第二次 proposal。论文报告最高 **6.83× decode speedup**，并声称 greedy 与 sampling 都保持 lossless output distribution。需要注意的是，headline 是 decode-only、single-batch、指定 GPU/实现条件下的最高值；thinking-model 设置的已报告最高加速更接近 3×，所以不能把 6.83× 直接当成端到端 Agent latency 收益。

4. **推荐系统里的 Agent 更现实的价值之一，是把“聚合指标看不见的失败模式”变成可操作的诊断与代码改进候选。** Disney 的 AURA 让专门化 Agent 读取真实生产 engagement log，构造 failure taxonomy，再结合推荐代码、数据和训练上下文生成改进提案并在 sandbox clone 中实现。两个大型消费平台上，诊断 rubric 由 15/25→23/25、17/25→24/25；但论文没有给出“Agent 生成的代码已在真实线上 A/B 提升北极星指标”的证据。因此它当前更像高吞吐 recommender diagnosis + engineering assistant，而非无人值守 self-evolving recommender。

5. **Text Embedder 的极低比特 PTQ 不能照搬 LLM 的模块敏感度经验。** 一项覆盖 5 个 checkpoint、4 个 architecture family 的测量发现：embedding table 从未成为稳定的首要保护模块；INT4/g16 下模块差异太小，INT3 的敏感度排序随 family 改变，INT2 时相近 reconstruction error 对应的检索质量保留率甚至从 1.3% 到 65.9%。更值得工程上注意的是，一个 109M distilled student 做 INT3 后以 68.4 MB 达到 78.04 NDCG@10，反而压过自身 0.6B Teacher 的 extreme-PTQ 版本（297.9 MB、64.46）。在本地 RAG / embedding serving 中，“先蒸馏到合适容量，再温和量化”有时会优于把大模型硬压到极限。

6. **Agent 与 RAG 基础设施开始进入标准化系统 Benchmark，而不是只测单模型 tokens/s。** MLPerf Inference v6.1 于 9 月 16 日发布结果，新增 End-to-End RAG 与 Edge Agentic Inference：前者覆盖 embedding、vector database retrieval、reranking 与 LLM answer pipeline；后者强调多轮增长历史、单用户 single-stream、TTFT/TPOT/E2E latency 与准确率 gate。MLCommons 还宣布未来 datacenter 侧将逐步转向 API-centric MLPerf Endpoints。对系统论文和厂商数字而言，这会推动“模型快多少”向“完整工作流在明确质量约束下快多少”迁移。

## 1. ScienceBuddy：Harness 与 Model 交替成为下一轮学习环境

**原始来源：** [论文](https://arxiv.org/abs/2609.17523) · [代码仓库](https://github.com/Gen-Verse/ScienceBuddy) · [项目页](http://science-buddy.io/)

### 发生了什么

ScienceBuddy 是一个面向科研工作流的交互式 Agent workspace，论文描述的工具面覆盖 **224 个工具、22 个功能模块**，当前重点集中在生物医学相关任务。真正值得看的部分是其 “recursive-in-recursive self-improvement”：

```text
Inner recursion
固定模型
→ 收集失败轨迹 / 反馈
→ 修改 Harness 程序、Skill、Instruction、Context 设置
→ parent / candidate 配对验证
→ 接受更好的 Harness

Outer recursion
固定当前 Harness
→ 生成新的 on-policy 轨迹
→ verifier 打分
→ GRPO 更新模型
→ 新模型进入下一轮 Harness 搜索
```

论文 case study 从 Qwen3.5-4B 起步，连续进行三轮 Harness / RL 共演化。Harness candidate 的修改范围是受限的，每次只允许修改一个 scoped component；工具、基础设施、rubric/evaluator 保持冻结，并在固定 validation task 上比较 parent 与 candidate，避免“为了新失败修一处、同时悄悄破坏旧能力”。

### 关键结果

| 观察 | 论文报告结果 |
|---|---:|
| 三轮共演化 held-out single-attempt accuracy | **42.2% → 73.3%** |
| 测试题从错变对 | **33.3%** |
| 测试题从对变错 | **2.2%** |
| 固定模型，仅 Harness adaptation（validation） | **31.1% → 51.1%** |
| 固定 Harness，仅 RL 的 pass@4 coverage | **48.3% → 67.8%** |

这组拆分结果比最终 73.3% 更重要：Harness search 与 Model RL 都能够独立扩大能力边界，因此二者交替优化至少在当前实验里具有互补性。

### 为什么重要

过去 Agent 后训练常把 Harness 当作固定环境；Harness engineering 又往往假设模型固定。ScienceBuddy 把二者都视为训练状态，形成一个更接近真实 AI 工程的 co-design loop：模型变强后，旧 Harness 的瓶颈会变化；Harness 改善后，又会产生不同质量的 on-policy data。

对 Coding / Search / Tool Agent 来说，未来版本管理很可能需要同时保存：

```text
(model checkpoint,
 harness version,
 tool surface,
 rubric/evaluator version,
 validation snapshot)
```

只记录模型 checkpoint 已经不足以解释一次系统能力变化。

### 可信度与局限

论文证据来自有限科学任务族和有限共演化轮次，无法证明长期持续提升，更无法推出无限递归自我改进。Harness 诊断／编辑还使用了独立的强模型，因此系统不是“一个 4B 模型凭自身能力从零自举”。

另一个需要注意的细节是，GitHub 当前 `science-buddy-preview` 的维护配置已经与论文较早的 case-study 训练设置有所变化；复现时应以仓库当前 experiment guide 和实际输出为准，不宜机械照抄论文图中的 step 数。

### 最值得继续追踪

看 **Harness update 的收益是否会随着 Model capability 增长而衰减或迁移**，以及长期 co-evolution 中是否会出现 Harness overfitting、evaluator gaming 与版本间不可迁移。真正成熟的系统还需要把每次能力增长归因到 Harness、Policy、Data 还是 Verifier，而不是只看最终 aggregate score。

## 2. γOPD：把 Teacher 的“未来信息”引入 Token-Level Distillation

**原始来源：** [Beyond Token-Local Imitation: Reward-Compatible Temporal Credit Assignment for On-Policy Distillation](https://arxiv.org/abs/2609.16937)

### 发生了什么

标准 token-level OPD 的优势是稳定：Student 在自己的 rollout state 上，每个 token 都能获得 Teacher 的局部概率监督。但这种目标天然偏短视；sequence-level reverse-KL 能看到完整未来，却会随着 horizon 增长出现更高方差。

γOPD 给出一个统一的 temporal-credit 解释：实践中的 token OPD 可以视为 sequence-level reverse-KL gradient 的局部近似；随后用 discounted temporal credit 把后续 Teacher signal 传回较早 token，并证明其 variance bound 不随 horizon 无界增长。

论文还加入 **Reward-Compatible Bounded Mixing（RBM）**：当任务存在可验证 reward 时，OPD advantage 只作为有界辅助项，避免 Teacher 信号把“本来应由 reward 强化／抑制的轨迹方向”反过来。

### 关键结果

| 设置 | Vanilla OPD | γOPD |
|---|---:|---:|
| Qwen3-4B Math Student · Avg Accuracy | 67.04 | **69.49** |
| Qwen3-4B Math Student · Avg Pass | 77.63 | **82.41** |
| Qwen3-1.7B size-mismatch · Avg Accuracy | 52.60 | **56.51** |
| Qwen3-1.7B size-mismatch · Avg Pass | 67.24 | **71.22** |
| Math+Code aggregate | 63.37 | **66.00** |
| HumanEval+ | 84.15 | **89.02** |
| LiveCodeBench | 26.00 | **28.14** |

Ablation 中，仅加入 temporal discount 就能提高 AIME aggregate；完整的 temporal + mixing + normalization 进一步扩大收益。作者报告新增计算约 **0.1%**，内存开销可忽略。

### 为什么重要

OPD 最近的大量工作都在解决 Student-state coverage、Teacher construction、multi-teacher routing。γOPD 补上了另一个维度：**即使 Teacher 和 Student state 都选对了，监督是否仍然过于局部？**

Reasoning token 的作用往往延迟到几十甚至几百 token 后才体现。若 Teacher 在某一步的局部 next-token 概率和最终 reward 所暗示的方向不完全一致，纯局部 imitation 可能会提前固化一个看似合理、后来才暴露问题的 reasoning branch。

### 可信度与局限

证据集中在数学和代码等拥有强 verifier 的任务，RBM 的“reward-compatible”特性在这里最容易成立。开放式 Agent 的 reward 更噪、更稀疏，未来 credit 还会跨 Tool observation、environment state 与异步 side effect，是否能保留相同稳定性仍需验证。

Teacher 依赖也没有消失。γOPD 改善的是 temporal assignment，不会自动修复 Teacher 本身的系统性偏差。

### 最值得继续追踪

优先看 Tool-Agent / Coding-Agent 中的 **action-level temporal credit**：plan token、tool choice、argument token 与后续 verifier failure 之间能否建立类似 discounted Teacher credit；以及不同 $γ$ 是否应该随 trajectory phase 动态变化，而不是全局固定。

## 3. LoopSpec：让 Looped Transformer 自己给自己做 Draft

**原始来源：** [LoopSpec: Pipelined Self-Speculative Decoding for Looped Transformers](https://arxiv.org/abs/2609.17184)

### 发生了什么

Looped Transformer 反复执行同一组共享 block，以更少参数换取更多 recurrent compute。它的结构天然提供多个“深度不同、权重相同”的中间状态：较浅 recurrence 成本更低，较深 recurrence 更准确。

LoopSpec 把浅层 recurrent state 直接变成 self-speculative draft，不额外挂 Draft Model。它还把“未来 token 的 draft”与“当前 token 的 target verification”流水化重叠；若第一轮 proposal 不足，再从更深 recurrence 启动选择性的第二次 proposal。论文进一步给出 optimal proposal depth 的闭式选择规则，并在 greedy 与 sampling 下保持无损解码。

### 关键结果

论文在 Ouro（R=4）与 Raven（R=32）等 Looped Transformer 上报告最高 **6.83× decode speedup**。在更偏 thinking 的 Ouro 1.4B / 2.6B 设置中，greedy 最高约 **2.95×**，sampling 最高约 **2.83×**；第一阶段 proposal 能提交超过 86% token，第二 proposal 再回收大部分剩余情况，完整 pipeline restart 比例低于约 3%。

### 为什么重要

普通 speculative decoding 需要额外 Draft Model、额外显存或额外训练。Looped Transformer 已经内置一组不同 compute depth 的 predictor，因此“早停 recurrent state 作为 draft、完整 recurrence 作为 target”是架构原生的 speculation hierarchy。

这也说明 recurrent-depth 架构的系统价值不能只看 parameter count 或 benchmark quality。它是否拥有高效的 runtime scheduling、state reuse 与 self-speculation，可能直接决定单位 wall-clock 的实际竞争力。

### 可信度与局限

headline speedup 只衡量 **prefill 之后的 decode phase**，实验还是 single-batch、指定 RTX PRO 6000 Blackwell、BF16、SGLang 环境。真实 Agent workload 的 TTFT、continuous batching、KV pressure、tool wait 和长上下文都会稀释 decode-only 加速。

论文中的最高 6.83× 也不代表所有 Looped Model 或 thinking mode 都达到该值；thinking 设置的实际最高值明显更低。

### 最值得继续追踪

看 LoopSpec 是否进入主流 runtime，以及 **Looped Transformer + self-speculation** 在固定质量、固定 GPU-hour 下能否真正胜过普通 Dense/MoE Transformer + EAGLE / suffix decoding。只有端到端 goodput 数据才能决定它是否从“有趣架构”变成“好 Serving 架构”。

## 4. AURA：从生产日志里自动挖“推荐系统为什么让用户失望”

**原始来源：** [AURA: Agentic Diagnosis and Refinement for Production Recommender Systems at Scale](https://arxiv.org/abs/2609.16625)

### 发生了什么

推荐系统的离线 AUC/NDCG 和线上 aggregate KPI 很难解释具体 failure pattern。AURA 让不同 Agent 读取真实 engagement session，先做 item/session 级定性判断，再聚合出 failure taxonomy；下一阶段把这些诊断与 recommender code、data schema、training pipeline 上下文结合，提出代码级修正，并在 sandbox clone 中实现候选变更。

论文来自 Walt Disney Company，覆盖两个大型消费平台。系统采用分层模型预算：高吞吐 session judging 使用相对轻量模型，聚合解释与代码层任务再使用更强模型。对约 96,801 个 Platform A session 的 upstream judging 成本约 **\$321**，另一个约 101,594 session 的平台约 **\$250**。

### 关键结果

AURA 的主要证据集中在诊断质量和运营可行性，而不是 recommender 在线 uplift。经过架构和 prompt refinement，两个平台的内部诊断 rubric 分别从 **15/25 → 23/25**、**17/25 → 24/25**。Platform A 的 emergent tags 最终可压缩成 8 类 taxonomy 而未观察到诊断能力损失，说明大规模 session 诊断可以逐步稳定成结构化 failure ontology。

系统还明确设置了权限边界：analytics 数据侧 read-only；代码修改只发生在 sandbox clone；是否 promote 由指定工程师决定；“驳回建议”被视为正常的一等结果。

### 为什么重要

对成熟推荐系统而言，下一次有效改进往往并不来自再加一层网络，而来自识别某类用户／场景为何持续被当前 objective 漏掉。Agent 的强项恰好是把大量具体 session 中的自然语言、item context 与行为结果压成可读的 failure pattern，再把 pattern 与代码路径对应起来。

AURA 因此更接近一个 **诊断层 Research Harness**：它先缩短“从用户失败 → 工程假设”的路径，再让传统离线实验与 A/B 承担因果验证。

### 可信度与局限

论文使用真实生产日志，工程细节和 safeguard 比纯模拟系统更有价值；但当前公开结果没有展示 Agent 自动生成的代码修改已经通过线上 A/B、稳定提升北极星指标。rubric 本身也依赖 LLM-as-judge，仍可能存在系统性偏差。

因此，把 AURA 描述成“生产级自我进化推荐系统”会过头。现阶段更准确的定位是：规模化 failure diagnosis、候选改进生成和沙箱实现已经跑通，最终 promotion 仍由人和传统实验体系掌权。

### 最值得继续追踪

看后续是否公开 **diagnosis → code change → offline gain → online A/B** 的完整 lineage，并量化哪些 Agent 发现最终真正转化成线上收益。另一个关键指标是 taxonomy drift：当内容生态和模型版本变化后，旧 failure ontology 是否会阻碍发现新的问题。

## 5. Text Embedder PTQ：INT2 的 Reconstruction Error 几乎不告诉你 Retrieval 会坏成什么样

**原始来源：** [Where Post-Training Quantization Breaks Text Embedders](https://arxiv.org/abs/2609.16391)

### 发生了什么

很多 Embedder 压缩实践直接继承 LLM PTQ 经验：优先保护 embedding table、按模块 reconstruction sensitivity 分 bit、用较低重建误差推断下游质量。论文对 **5 个 checkpoint、4 个架构家族**做系统量化扫描，分别隔离 embedding、attention、FFN，并跨 bit width / group size 测真实 retrieval quality。

结果显示这些经验没有稳定迁移。Embedding table 即使是最大 tensor，也从未在任何 family 中稳定成为首要保护对象；INT4/g16 下各模块差距很小；到了 INT3，敏感度排序变成 family-dependent，多个模块联合损伤又呈明显非加性。

### 关键结果

最强的警示来自 INT2：**相近 reconstruction error 可以对应 1.3%–65.9% 的 full-precision quality retention**。这意味着只看 weight MSE / reconstruction proxy，很难判断极低比特下的排序是否还活着。

论文还给出一个很实用的对照：一个经过任务蒸馏的 **109M Student + INT3**，文件大小 68.4 MB、达到 **78.04 NDCG@10**；自身 0.6B Teacher 的 extreme-PTQ 版本为 297.9 MB、只有 **64.46 NDCG@10**。不过这一优势只在其被蒸馏的任务里成立，不能泛化成“Student 永远优于量化 Teacher”。

### 为什么重要

Embedding Model 的目标是保留相对几何和 top-K decision，而不是复原每一层权重本身。因此 PTQ 最终应该验证：

```text
Recall / nDCG / MRR
+ decision margin / rank flip
+ index size
+ embedding throughput
+ downstream RAG answer quality
```

对本地 RAG、向量数据库和大规模广告／推荐召回而言，“先选一个真正适合目标 bit budget 的模型，再量化”往往比拿最大 Teacher 一路压到底更合理。

### 可信度与局限

论文覆盖多个家族，负结果很有价值；但它仍然只是有限 checkpoint 和 retrieval benchmark 的测量地图。蒸馏 Student 的 78.04 结果具有任务特化条件，不能直接用于跨域语义检索。

重建误差在 uniform bit-width 的粗筛中仍有价值，论文否定的是它作为 tensor-level protection 与 extreme PTQ 的万能代理。

### 最值得继续追踪

看能否把 **ranking flip / local margin** 直接加入 mixed-precision allocation，并在真实 RAG corpus 上测“量化后召回改变了哪些最终答案”。比起平均 reconstruction error，这会更接近业务真正消费的信号。

## 6. MLPerf Inference v6.1：RAG 与 Agentic Inference 终于进入标准系统测量

**原始来源：** [MLCommons：MLPerf Inference v6.1 Results](https://mlcommons.org/2026/09/mlperf-inference-v6-1-results/) · [Edge Agentic benchmark 说明](https://mlcommons.org/2026/07/mlperf-inference-v61-edge-agentic/)

### 发生了什么

MLCommons 于 **2026 年 9 月 16 日**发布 MLPerf Inference v6.1 结果，新加入两类很重要的系统级 workload：

- **End-to-End RAG**：把 embedding、vector DB retrieval、reranking、LLM reasoning / answer generation 作为完整 pipeline 测量，同时区分 corpus ingestion 与 query-serving；
- **Edge Agentic Inference**：面向单个 edge accelerator 的多轮 tool-calling / agentic coding workload，历史会逐轮增长，采用 single-stream（并发 1）交互模型，并同时要求准确率与 latency gate。

Edge Agentic reference 采用 Qwen3.6-27B 的 Q4_K_M GGUF 作为参考格式，性能侧报告每 turn 的 TTFT、TPOT、E2E latency 以及 ISL/OSL 的 p50/p90/p99/max。准确率 gate 则选用约 995 条 BFCL v4 single-turn 样本；MLCommons 解释说，小规模多轮 gate（n=57）统计波动过大，因此没有把它作为主要 accuracy gate。

### 关键结果 / 变化

MLPerf v6.1 还正式支持更多 interactive speculative decoding 场景，并表示超过一半 submitter 已使用新的 API-centric client/server harness。MLCommons 已明确提出，未来 datacenter 侧 **MLPerf Endpoints** 将逐步接替传统 Inference benchmark，以更贴近真实 API 服务架构。

这轮共有 30 个参与组织；官方还报告 VLM server 场景的最佳 per-accelerator 结果相对半年前提升 2.99×，DeepSeek-R1 server 场景的最佳 per-accelerator 结果相对一年前提升 5.7×。这些数字反映硬件和软件共同进步，不能归因给单一 accelerator。

### 为什么重要

系统优化论文经常分别报告 vector DB QPS、LLM tokens/s、reranker latency，却缺少一个完整质量约束下的端到端基准。MLPerf 把 RAG 和 Agentic workload 纳入标准套件后，未来“某个优化让 kernel 快 2×”更难直接包装成“RAG/Agent 快 2×”。

对 Edge Agent 来说，single-stream 也很关键：边缘设备常服务一个交互用户，吞吐最大化并不是首要目标，p99 turn latency、context growth 和 accuracy degradation 更有意义。

### 可信度与局限

MLPerf 的优势是规则、审计与跨厂商可比性；但任何标准 benchmark 都只是 workload slice。Edge Agentic 的 accuracy gate 主要使用 single-turn BFCL，性能轨迹则采用确定性 replay，它仍未完整覆盖真实开放 Agent 中的动态 Tool failure、环境分支和 long-horizon recovery。

RAG benchmark 的固定 pipeline 也无法代表企业系统里所有 hybrid retrieval、ACL filtering、cache、query routing 和在线索引更新。

### 最值得继续追踪

重点看即将推出的 **MLPerf Agentic / Endpoints** 如何把 tool execution、workflow tail latency、KV locality 与质量评测一起标准化。如果厂商开始同时公开 `accuracy × TTFT × TPOT × E2E workflow latency × power`，Agent serving 的性能讨论会比单一 tokens/s 更接近真实部署决策。

## 今日值得收藏的代码 / 学习资源

### Dream-RSI：把历史探索树当作“零执行成本”的 Replay Simulator

[论文](https://arxiv.org/abs/2609.14858) · [项目页](https://dream-rsi.com/) · [GitHub](https://github.com/zhengkid/Dream-RSI)

Dream-RSI 不修改底层 Coding Agent 权重，而是优化“下一步探索哪个分支、并行多少、什么时候停止”的 meta-exploration policy。核心技巧是把已经执行过的 discovery tree 当成精确 replay simulator：候选策略在历史树上换一种遍历方式即可离线评估，不需要重新跑昂贵程序。项目页报告 VGG16 场景在相近性能下减少 2.43× generations、ConvDiv 同预算下 score 提高 2.09×，以及 Lasso 对 SimpleTES 的极端成本差距。

这里必须守住边界：replay 只对**历史已经走过的树**是精确的，没探索过的世界仍然不知道；“162×”还涉及与不同搜索方案的对照，不能等价成通用 RSI 加速 162×。GitHub 当前也仍标记完整 reproduction scripts / codebase 的部分发布项为待补齐。

### FlashVector：Serving 优化 Agent 开始从 Kernel 横跨到 Triton / Python Feature Stack

[论文](https://arxiv.org/abs/2609.17391)

FlashVector 来自 Unity Vector 广告平台，把 Agentic optimization 从 GPU kernel 扩展到 computation graph、NVIDIA Triton C++ server 和 Python feature transformation。生产部署报告 model server 最高 **2× throughput、1.98× latency speedup**，feature store 最高 **1.6× throughput**。

更值得学的是 correctness gate：确定性 rewrite 要求 exact equality；浮点重排有 tolerance；近似改动必须过业务指标；2%–6% 的小收益因为接近 ±6% noise floor，要增加重复样本；所有候选最后必须通过 full-stack load test。自动性能工程的核心并非“Agent 会写优化代码”，而是**测量和回归门槛足够硬**。

### OPEN-1B：把“开源训练 recipe”推进到可抽查的 Bitwise Audit

[论文](https://arxiv.org/abs/2609.17380) · [训练与审计仓库](https://github.com/gensyn-ai/open-transformers)

OPEN-1B 发布 1.61B 参数模型、400B-token 训练 run、80,957 个 optimizer step 的审计轨迹，以及训练数据、checkpoint、训练代码和 audit-replay harness。它通过固定 reduction、batch order、collective communication 等非确定性来源，使第三方可以在 CPU、CUDA 或 Apple Metal 上重放指定训练单元并验证相同 state hash。

它没有“证明历史集群一定按声明方式运行”的魔法；hash match 证明的是给定已发布 artifact 与输入下的 replay 一致。即便如此，这仍是 Open Model Transparency 中非常值得研究的工程方向：从“相信作者给出的 recipe”推进到“随机抽查训练轨迹”。

### PCap：推荐系统 Diversity 应该按用户偏好约束，而非统一 Cap

[论文](https://arxiv.org/abs/2609.16452)

Facebook Marketplace 的 PCap 先用用户历史 category entropy 构造 diversity bucket，再对 multi-source retrieval 设置不同 category cap。统一 capping 相比 baseline 虽让 Viewport Views +0.3088%，却让 message interactions -0.2604%；进一步换成 personalized capping 后，相对 uniform capping，Viewport Views +0.2243%、PDP clicks +0.2250%、sessions +0.1708%，额外 retrieval latency 约 +0.8 ms。

这组 A/B 的含义很直接：全局 diversity regularization 容易把“喜欢集中浏览”和“喜欢探索”的用户混在一起。推荐系统的 diversity target 本身也是一种用户偏好，而不是永远越大越好。

### Shared-Prefix LoRA KV Reuse：一个很值得保留的负结果

[论文](https://arxiv.org/abs/2609.17109)

论文研究多个标准 LoRA specialist 在同一长 context 上是否能复用 backbone prefill KV。Qwen3-1.7B 上，full-prefix reuse 确实给出最低 prefill 成本，但 GSM8K 的质量差在不同 token budget / seed 下并不稳定；partial recomputation 没有展示明确优势，ridge KV translator 也没有打败直接 reuse。更关键的是，原实现虽然复用了 KV **值**，却复制了存储，因此双分支 peak memory 只降低 12%，没有真正实现共享 cache storage。

它适合作为 Serving 研究的提醒：**算力复用、状态值复用、物理存储共享是三个不同问题。** Benchmark 只报告 TTFT 还不足以说明显存经济性。

## 今日最值得花 30 分钟阅读的一项

**首选 γOPD：Beyond Token-Local Imitation。**

[论文原文](https://arxiv.org/abs/2609.16937)

如果你持续跟 OPD / GRPO，这篇比单纯再看一个更大的 Teacher 更值得。30 分钟建议按这个顺序读：

1. 先看作者如何把 token-level OPD 与 sequence-level reverse-KL 放在同一 temporal-credit 坐标里；
2. 再看 γ-discount 如何控制“未来监督更远”与“方差更高”的交换；
3. 重点看 RBM 为什么必须让 verifiable reward 的符号拥有最终决策权；
4. 看 size-mismatch 与 multi-teacher 结果，确认收益是否只来自同尺寸 Teacher；
5. 最后看 ablation 与约 0.1% 计算开销，判断这是否值得作为现有 OPD pipeline 的低成本实验分支。

最值得带走的判断是：

> **Student-state coverage 解决“在哪里教”，Teacher construction 解决“谁来教”，temporal credit 进一步回答“当前 token 应该为未来多远的结果负责”。**

这三个轴很可能会共同决定下一阶段 OPD 的数据效率和训练稳定性。

## 今日可立即实践的一件事

给现有 OPD / GRPO 实验做一个 **Temporal Credit Audit**，先不改训练 loss，只验证“未来 Teacher signal 是否真的比局部 signal 更能解释最终成败”。

固定 100–500 条 Student on-policy rollout，对每个 token 记录 Teacher–Student log-prob gap：

$$
\delta_t = \log p_T(y_t\mid c_t)-\log p_S(y_t\mid c_t).
$$

然后构造一个**仅用于诊断**的 discounted future proxy：

$$
G_t^{(\gamma)}=\sum_{k=t}^{T}\gamma^{k-t}\delta_k,
$$

其中 $\gamma\in\{0,0.5,0.8,0.95\}$。这里不是复现论文完整目标，只是在现有日志上检查：随着 horizon 增加，哪些 token 的“Teacher 建议强度”会明显改变。

至少记录：

```python
metrics = {
    "local_gap_vs_outcome_corr": {},
    "discounted_gap_vs_outcome_corr": {},
    "sign_flip_rate_by_gamma": {},
    "credit_concentration_by_position": {},
    "reward_conflict_rate": {},
}
```

把 rollout 按最终 verifier success / failure、reasoning phase、tool action（若有）分桶。尤其检查两个现象：

- 某些 token 的局部 Teacher gap 很强，但加入未来 credit 后方向翻转；
- Teacher credit 与 verifiable reward 的方向冲突是否集中在特定阶段。

如果 $γ>0$ 的 proxy 对最终 outcome、关键错误位置或后续 repair success 没有比 token-local signal 更好的解释力，就没有必要仅因为论文新鲜而增加训练复杂度；如果未来 credit 明显改善区分度，再做小规模 γOPD / bounded-mixing A/B 更合理。

**真正要回答的是：你当前的 OPD 在教“下一 token 更像 Teacher”，还是在教“这一步如何为后面的正确结果服务”？**

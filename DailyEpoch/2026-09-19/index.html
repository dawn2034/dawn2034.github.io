今日主线： Teacher Retirement · Harness Auto-Research · Model-Aware Harness Design · Self-Evolving Index · On-Demand Attention · Listwise Recommendation

截至今天早上，arXiv 最新常规公告批次为 2026 年 9 月 18 日：cs.AI 215 条、cs.CL 104 条、cs.LG 198 条、cs.IR 22 条；这些分类存在大量交叉收录，不能直接相加。今天几项高信号工作的共同点，是进一步把“什么时候使用某种能力”本身变成可学习或可监控的决策：OPD 的 Teacher 需要在失去边际价值时退出；Harness 的 Context、Planning 和 Tool Surface 应随模型能力与 Context Budget 改变；长上下文 Attention 可以按 token 决定是否全局回读；检索 Index 也可以围绕真实失败持续修订。推荐系统侧则继续出现一条务实路线：把 LLM 的“序列生成思想”吸收到成熟 Ranker，而不是要求生产系统整体推倒重来。

今日核心判断

  1. OPD 的 Teacher 不应默认陪跑到训练结束。 RetireOPD 发现，Agentic RL 中 privileged context 并不自动产生可靠 Teacher；而当 Student 已经内化技能后，继续匹配 Teacher 还会与环境 Reward 优化发生冲突。它先用环境奖励单独训练 skill-conditioned Teacher，再让 Student 联合 GRPO+OPD；当 Teacher–Student discrepancy 不再收敛、且 Student 达到 Teacher 的目标能力比例时自动退休 Teacher。Qwen2.5 1.5B–7B 上，相对 GRPO，ALFWorld 成功率提高 14.1%–18.8%，WebShop accuracy 提高 11.8%–19.0%，并在所有设置中超过自己的 Teacher。

  2. Harness Auto-Research 的短期价值更像“自动发现可复用的系统机制”，还不是递归自我改进已经形成复利。 NVIDIA 的 SoL-Pi 从约 150 个方向、535 个 executable environment、3,000+ runs 和 60,000+ agent–environment interactions 中筛出 Action Fusion、Online Context Compact、ObservationPack、Evidence-Preserving Reducer 四个机制。在 51-task EdgeBench 上，Efficiency 配置相对 Pi 减少 49.0% token traffic、降低 33.2% token cost，同时保留 93.7% 平均分；Performance 配置则平均分 +5.3%、token traffic -6.1%。论文自己明确说明，这些实验没有建立“搜索规模越大就持续递归变强”的 scaling law。

  3. Coding Agent 没有一个模型无关的“最佳 Harness”。 一项 176 个 matched settings 的系统实验显示，32K Context 下 Context Management 对 SWE-Bench 的平均增益高达 +35.7pp，到了 128K 只剩 +2.7pp；弱模型依赖预定义工具，Nemotron-3 30B 使用完整 Tool Set 比 bash-only 在 SWE-Bench +15.0%，而 Nemotron-3 550B 反而使用 bash-only 在 SWE-Bench +3.6%、成本 -53%。Planning 也从弱模型的能力脚手架逐步变成强模型的成本控制器。这意味着 Harness 应按 Model Capability × Context Budget 联合选择，而不是把同一套 Scaffold 固化给所有模型。

  4. RAG / Search Agent 的“可演化对象”开始从 Query Planner 扩展到 Index 本身。 Self-Index 根据真实检索结果诊断哪些 document keys 造成混淆，只修订相关 keys，并经过 Faithfulness、Specificity、Separation 三层验证后才写回；Query Simulator 还会主动生成尚未覆盖的检索需求。BRIGHT 上，BM25/BGE/Qwen3-Embedding-8B 的平均 nDCG@10 分别从 14.5/13.9/18.8 提到 20.4/21.8/26.1。LongMemEval-V2 中，只改 Index、不改 Memory 内容，也能让三种 Memory 系统 overall accuracy 分别提高 13.9%、12.4%、9.2%。

  5. 长上下文推理可以让模型自己决定“这一 token 值不值得读全历史”。 On-Demand Attention（ODA）先做一次 Local computation，再用很小的 recall head 判断是否值得重算 Full Attention；Backbone 完全冻结，历史 KV 仍完整保留。Qwen3-1.7B 在 RULER16K 上，Local 只有 19.23，Full 为 81.94；ODA 仅在 41.6% routed steps 使用 Full，就达到 81.17。128K 输入、1K 输出、12.5% global-call 的受控 vLLM 实验中，主 Decode FLOPs 约降低 76%，单请求 Decode Throughput 达到 Full Attention 的 1.98×。

  6. 工业推荐向 Generative Recommendation 迁移，最现实的路线之一是升级 Ranker 的优化单位，而不是替换整个栈。 Meta 的 LIGE-GR 把传统 Itemwise Ranker 扩展成 Listwise Generation：加入轻量 context-aware ranking、listwise value model 和 RL-based sequence decoder，同时保留既有 Ranker、Value Function、Serving 与控制规则。线上实验中，Instagram Reels Time Spent +1.14%、Facebook Video +0.72%；Instagram 侧额外推理资源约等于原 context-free ranking component 的 10%，端到端单请求延迟约 +7%。

1. RetireOPD：Teacher 的价值有保质期

原始来源： 论文 · 代码

发生了什么

Agentic RL 的典型难点是，一条多轮 trajectory 最后往往只得到一个 scalar reward，中间几十到几百个 token / action 缺少 dense credit。OPD 用 Student 自己 rollout 的状态，让带 privileged skill 的 Teacher 给 token-level supervision，理论上正好补这个缺口。

RetireOPD 发现这个 recipe 有两个不稳定假设。第一，给同一个模型多一段 Skill Context，不意味着它真的学会了使用这段 Context；论文里 7B 模型直接拿 skill prompt，在 ALFWorld 也只有 23.4% success。第二，Teacher 的帮助有明显阶段性：训练前期 Teacher–Student discrepancy 下降，后期却会重新扩大；此时 Reward 希望 Student 继续探索，OPD 却把它拉回 Teacher 的行为分布。

因此 RetireOPD 把 Teacher 和 Student 解耦。Teacher 先在 privileged skill context 下用环境 Reward 单独优化并冻结；Student 再使用 GRPO + OPD。训练每隔窗口监控 Teacher–Student log-probability discrepancy 和 Student/Teacher success ratio，只在两项条件同时满足时停止 OPD，之后完全回到 GRPO。

关键结果

Qwen2.5-1.5B72.889.856.875.8
Qwen2.5-3B75.093.863.377.3

完整 1.5B–7B 实验中，相对 GRPO 的提升范围为：ALFWorld +14.1%～+18.8%，WebShop +11.8%～+19.0%。更重要的是，RetireOPD 在每个设置中最终都超过自己的 skill-conditioned Teacher。

为什么重要

这篇论文给近期 OPD 工作补上了一个训练阶段维度。Teacher selection、token gating、temporal credit 都在回答“怎样提供更好的 Teacher signal”，RetireOPD 继续追问：Teacher signal 何时应该彻底退出。

对于长程 Agent，这个问题尤其现实。早期 Student 需要 Skill / Tool-use Prior 帮它走出低 Reward 区域；能力上来以后，Teacher 自己的局限就可能变成 Ceiling。持续付 Teacher Forward Cost 还会同时浪费算力。

可信度与局限

论文的实验边界比较清楚，而且报告了“固定退休步数为何不稳”：不同模型／任务里 discrepancy 停止下降的时间大约落在 50–90 step，单一 schedule 确实容易过早或过晚。

但当前只覆盖 Qwen2.5 1.5B/3B/7B、ALFWorld 与 WebShop。Teacher 和 Student 同容量、Skill 也是文本 privileged context；跨模型家族 Teacher、Coding Agent 和更长 Tool trajectory 是否仍出现同样的退休信号，目前证据不足。

最值得继续追踪

重点看 Teacher retirement 是否能和 token-level gating、multi-teacher routing 合并：先决定“哪个 Teacher、哪些 token 值得教”，再决定“这类 Teacher 是否已经可以永久退出”。如果退休后性能继续上升且 Teacher forward 完全消失，这会直接改变 Agent RL 的成本曲线。

2. SoL-Pi：自动研究 Harness，先把重复工作削掉

原始来源： 论文 · 代码仓库

发生了什么

SoL-Pi 的目标不是让 Coding Agent 少做验证或提前结束任务，而是减少长程运行里的重复工作。Auto-Research 流水线先从 Context、Progress、Tools、Delegation、Prompt/Policy、Evaluation 六类提出 152 个方向，再用 535 个 executable environments 做 broad-to-deep search；其中 495 个来自 GitHub issue–PR 历史，40 个由 executable verifier 驱动。

候选 Harness 改动不能修改评测标准。Capability tolerance 和 Efficiency metrics 在搜索前固定，Optimizing Agent 无权调整；候选必须先通过能力门，再证明至少一个效率指标改善。最终留下四个机制：Action Fusion 合并编辑与后续验证；ObservationPack 把重复大输出变成可分页 handle；Evidence-Preserving Reducer 将长日志压成带原文校验的 receipt；Online Context Compact 只有在预计未来节省超过 rewrite cost 时才压缩。

关键结果

EdgeBench / GPT-5.6 SolToken TrafficToken CostAvg Score
Pi2.1538B$133944.833
SoL-Pi Efficiency1.0990B$89442.003
SoL-Pi Performance2.0224B$127147.208

Efficiency 点相对 Pi Token -49.0%、Cost -33.2%，保留 93.7% score；Performance 点 Score +5.3%、Token -6.1%。在没有重新搜索／适配的 Opus 5 held-out backend 上，Efficiency 点仍保留 Pi 94.3% score，同时 Token -44.7%、API Cost -33.5%。

为什么重要

长程 Agent 的成本不只来自模型单 token 价格，Harness 还会制造大量二次消费：同一日志在 Context 里反复回放、一个确定性 edit+test 被拆成多次模型往返、已经完成的 Subtask 长期占据 Prompt、长日志被 Frontier Model 从头阅读。

SoL-Pi 把“减少这些浪费”作为一个可以自动搜索的程序优化问题。它和 Kernel Auto-Tuning 很相似：关键不是让 Agent 少做事，而是在不可修改的 Correctness Gate 下减少同一工作的计算路径。

可信度与局限

EdgeBench 的结果很有工程价值，但跨 Benchmark 并非全部无损：Terminal-Bench 4 的 63 个 CPU-only task 中，Codex/Pi 都解 18 个，SoL-Pi 解 15 个；它的优势是总 Model Cost 下降 26.3%。因此不能把“省约一半 Token”表述成“所有任务保持完全相同成功率”。

论文还明确写道，3,000+ runs 和 60,000+ interactions 只是搜索规模描述，没有建立 Auto-Research 的 Scaling Law，也没有证明递归改进产生持续复利。 搜索本身成本也很高。

最值得继续追踪

最值得复用的不是四个固定技巧，而是它的 acceptance architecture：冻结能力指标、固定成本指标、候选隔离搜索、Held-out 结果不回流。接下来应追踪这些机制在不同 Agent Harness 和不同模型能力档位上是否仍然激活，以及自动 Harness 搜索的边际收益是否会快速饱和。

3. Coding Agent Harness Study：Tool、Planning、Context Management 都存在能力拐点

原始来源： 论文

发生了什么

这项工作没有比较“哪个完整 Coding Agent 最强”，而是固定一个轻量执行循环，只改变三类 Harness component：Planning、Action Space、Context Management。实验覆盖 Nemotron-3 30B/120B/550B 和 Mistral-Medium-3.5-128B，在 SWE-Bench Verified 与 Terminal-Bench 2.1 上形成 176 个 matched settings，Context Budget 从 32K 到 128K。

这让几个常被混在一起的现象被拆开。Context Management 主要负责避免 Overflow；Planning 会改变 trajectory 在哪里停止；Tool Surface 则决定模型需要用多细的动作表达工作。

关键结果

Context Management 的收益随 Context Window 增大迅速收窄：

WindowSWE managed vs T0Terminal managed vs T0
32K+35.7pp+9.5pp
64K+15.9pp+7.5pp
96K+5.5pp+4.8pp
128K+2.7pp+2.8pp

原因很直接：SWE-Bench 中 unmanaged T0 的 overflow rate 从 32K 的 78.7% 降到 128K 的 8.7%，而所有 managed tiers 都把 overflow failure 降到 0。

Tool Surface 则出现明显 capability crossover。Nemotron-3 30B 用预定义 Tool Set 相比 bash-only，SWE +15.0%、Terminal +10.1%；但 Nemotron-3 550B 使用 bash-only 反而 SWE +3.6%、Terminal +5.6%，成本分别 -53% / -30%，Tool Call 分别 -32% / -24%。

为什么重要

它给 Harness 设计一个很实用的原则：Scaffold 应随 Model Capability 和 Budget 退火。 弱模型需要显式动作词汇和 Planning 才能进入有效轨迹；强模型可能更适合用高带宽 Bash 直接组合动作，过细 Tool Schema 反而增加往返与成本。

同样，Context Management 的价值要和窗口预算一起看。如果 128K 已经覆盖绝大部分真实轨迹，复杂的 Recall Machinery 可能只是维护负担；论文里可恢复的 elided content 几乎没有被模型调用，也没有带来 accuracy gain。

可信度与局限

176 个 matched settings 让趋势相对可信，但每个任务主要只跑一次；Terminal-Bench 只有 89 个任务，SWE 也只覆盖 Python。行为归因使用 LLM Judge，虽然人工复核一致性很高，仍不等于确定性标注。

另外，论文没有测完整 Wall-clock / Serving Latency，成本结论主要来自 Token/API 侧。Tool 调用对真实系统的网络开销和缓存行为可能改变最优点。

最值得继续追踪

下一步应把 Harness 选择本身变成 Router：根据模型规模、任务类型、剩余 Context、Shell proficiency 与过去失败模式，动态决定是否启用 Planning、是否暴露高层 Tool、何时 Compact。固定 Harness 很可能只是过渡形态。

4. Self-Evolving Search Index：让 Index 自己修复“为什么搜不到”

原始来源： 论文 · 代码

发生了什么

Self-Index 把检索系统里通常由人完成的 Index Optimization 做成闭环。每个文档不只保留原文，还可以拥有多个可检索的 index keys。Optimizer 根据一批 query 的实际 retrieval outcome 建 co-retrieval profile，找出哪些 key 与错误候选经常一起出现、哪些信息没有被当前表示暴露出来，然后只修订受影响的文档 key set。

生成的新 key 必须通过三类 Self-Validation：Faithfulness 检查是否被原文支持；Specificity 检查是否真的描述该文档特有信息；Separation 检查它是否能和已有竞争 key 拉开距离。除此之外，Query Simulator 会从 Corpus 自己生成新的潜在 query，经过 answerability / dissimilarity 过滤后继续驱动 Index 演化。

关键结果

BRIGHT 的平均 nDCG@10：

RetrieverBaseSelf-IndexRelative Gain
BM2514.520.4+40.4%
BGE-Large13.921.8+57.0%
Qwen3-Embedding-8B18.826.1+38.8%

验证层不是装饰。去掉 Self-Validation 后，跨 Retriever 汇总的 Natural Language / Code / Math nDCG@10 从 26.6 / 22.1 / 17.2 降到 16.1 / 13.0 / 11.9。

它对 Agent Memory 也有效：LongMemEval-V2 中，Query→Slice overall 0.415→0.472（+13.9%），Slice+Notes 0.448→0.503（+12.4%），AgentRunbook-R 0.532→0.581（+9.2%）。但 Gotchas 子类并不总涨，例如第一种 Memory 配置从 0.276 降到 0.241。

为什么重要

大多数 RAG 优化把 Query Rewrite、Retriever、Reranker 或 Agent Planner 当成动态层，而 Index 只是静态基础设施。Self-Index 提醒我们：“文档该以什么可检索视图存在”本身就是可学习状态。

这对企业知识库和长期 Memory 很重要。新问题不断出现时，重新训练 Embedder 或全量 re-index 成本很高；只对发生过 retrieval failure 的局部文档增加／改写经过验证的 Keys，可能是更便宜的演化路径。

可信度与局限

这是 Work in Progress，而且收益明显依赖用于驱动演化的 query supply。相同 Optimizer 使用固定 ReasonIR HQ query 时仍能改善 Index，但最终分数低于自带 Query Simulator：BM25 17.5 vs 20.4、BGE 19.1 vs 21.8、Qwen3-Embedding 23.2 vs 26.1。这意味着一部分收益来自“系统给自己出了更有用的题”。

更根本的风险是 Index drift：新生成 Keys 会永久改变未来召回分布。Self-Validation 的强 ablation 说明，任何自演化 Index 若缺少独立写入门，很容易把一次局部修复变成长期污染。

最值得继续追踪

生产化最关键的是版本治理：每条 key revision 应记录触发 query、原文证据、Retriever 版本、验证结果和回滚点。模型、Embedding 或 Corpus 更新后，还要能够识别哪些派生 Keys 已经过期。

5. On-Demand Attention：只有需要时才全局读 KV

原始来源： 论文

发生了什么

ODA 的出发点很直接：长 Context Decode 时，Full Attention 每生成一个 token 都重新扫描不断增长的历史，但很多 token 的预测根本不需要远处 Context。作者先验证了一个关键假设——当前 Local decoding state 在执行 Full Attention 之前，已经包含“这一步 Full Attention 能带来多少预测收益”的信号。

因此每一步先执行 Local Attention，再由轻量 Recall Head 根据上一 token state、当前 token embedding 和 Local hidden state 打分；只有超过阈值时才从同一历史状态重算 Full Attention。Backbone 完全冻结，Full KV History 也没有被删除，因此连续很多 Local step 后仍然可以重新访问最早 Context。

关键结果

Model / BenchmarkFullLocalODAODA Full-call
Qwen3-1.7B / RULER16K81.9419.2381.1741.6%
Qwen3-8B / RULER16K92.5925.4391.0747.3%
Qwen3.5-2B / RULER16K94.3528.2194.0844.3%
Gemma-4-12B-it / RULER16K96.6130.0795.2757.8%

随机用同样比例的 Full Call 并不奏效。在 5 个 RULER16K task 的控制实验中，ODA 约 41.33% Full rate 得分 88.96；Random 约 40.99% Full rate 只有 32.79±0.95，说明真正有价值的是在哪些 token 回读全局。

为什么重要

它把 Context Access 从架构常数改成了 runtime decision。KV 可以继续完整保留用于未来 Recall，但 GPU 不再要求每个 token 都扫描全部历史。这与 Cache Compression 是不同方向：一个减少“存什么”，ODA 主要减少“何时读全部”。

对 Agent workload 尤其有潜力，因为 Tool Call、结构化参数和局部代码编辑常常只依赖最近几轮；真正需要回看早期需求、文件或策略约束的 token 是稀疏的。

可信度与局限

1.98× 是 Decode-only、single-request、128K input / 1K output、12.5% global-call 的受控 vLLM 结果，不是完整 Agent 请求端到端加速。Prefill 不在该数字里，Continuous Batching、不同 Recall Rate 与调度分歧也会改变收益。

另外 ODA 仍完整保存历史 KV，因此它降低的是 Attention Read / Compute，不能解决 KV Capacity 本身。每个 Backbone 还需要单独训练 Recall Head，论文没有证明 Head 可以跨模型迁移。

最值得继续追踪

看 ODA 与 KV Quantization、Tiered KV Cache、Prefix Cache、P/D Disaggregation 的组合。真正的 Serving 目标应该是同一 Quality SLO 下同时优化 KV bytes × global-read rate × TTFT × TPOT × batch goodput。

6. LIGE-GR：成熟推荐系统也能逐步吸收 Generative Paradigm

原始来源： 论文

发生了什么

传统 Feed Ranker 对候选 item 独立预测 like、follow、watch-time 等 engagement，再用 Value Model 合成分数，最后逐个 greedy 选出 Top-T。它很成熟，但无法直接优化“这一组内容按这个顺序出现”的整体体验。

LIGE-GR 没有重建 Retrieval / Ranking 栈，而是在原系统上升级三件事：context-free predictor 增加一个轻量 causal context-aware module，让后续 item 条件于已经选入的 prefix；Value Model 从 itemwise sum 扩展到 listwise objective；Decoder 从 greedy selection 改成 RL-based sequence search。原有 control layer、业务约束、价值函数和主 Ranker 都可以继续使用，并且能直接回退到旧系统。

关键结果

线上 Short-video Recommendation：

SurfaceTime Spent
Instagram Reels+1.14%
Facebook Video+0.72%

Instagram 侧额外推理资源约为原 context-free ranking component 的 10%，端到端 per-request latency 约 +7%。这不是“免费增益”，但对于已经高度优化的大规模生产 Ranker，这个资源换取的 engagement uplift 具有现实意义。

为什么重要

Generative Recommendation 经常被讨论成“用一个大模型统一召回和排序”。LIGE-GR 给出另一条迁移路线：保留几十年人月积累下来的 Feature、Ranker、Value Model、Serving 和 Product Rules，只把优化单位从独立 item 平滑升级为 sequence。

对于生产团队，这种可增量部署、可回滚的路径往往比清空重建更可信。它还把“LLM 范式的核心价值”从 Transformer 规模转回到两个更一般的概念：autoregressive context conditioning 与 sequence-level search/objective。

可信度与局限

Instagram / Facebook Video 的真实线上 A/B 是强证据，但论文来自系统建设方，外部无法复现实验流量。Time Spent 的提升也属于整套 listwise upgrade，无法单独归因给 context-aware ranker、ListVM 或 RL Decoder。

另外它仍需要更多推理资源和约 7% 延迟开销；在更严格的广告、搜索或低延迟 Feed 场景，收益是否覆盖系统成本需要单独验证。

最值得继续追踪

看 listwise objective 是否会继续向 retrieval / pre-ranking 上游传播，以及 sequence decoder 能否使用更低成本的 tree search、speculative evaluation 或 learned policy 替代昂贵搜索。真正决定是否能规模化的是“单位增量算力带来的长期用户价值”，而不是 Generative 标签本身。

今日值得收藏的代码 / 学习资源

Don’t Mask the Environment 是今天值得做 Tool-Agent RL 的人精读的训练细节。标准 SFT 往往只对 Assistant Action token 做 loss，把环境 Observation 全部 mask；ActObs 直接对 trajectory 中本来就存在的 Observation token 也做监督，不增加数据、参数、序列长度或额外 forward。SFT 后差异不大，但进入 GRPO 后，Qwen3-4B 在 Terminal-Bench 2.0 的各 sampling budget 都有更高 pass@k；Qwen3-8B 则表现为 pass@1 略有代价、pass@16 +3.4pp，同时保留更多 Policy Entropy。它提示：环境结果不仅是 Context，也可以成为“模型是否学会预测行动后果”的训练信号。
论文

Chronicle：Cut-Point Replay 很适合正在构建 Agent CI 的团队。它把 Model Response、Tool Result 等非确定性边界记录成 immutable envelope；Full Replay 可以零模型调用、20 次 bit-stable 重放，而 Cut-Point Replay 可以只把某些边界换成新代码执行。作者用 6 个 recorded incidents 做 proof-of-concept，记录开销约 23 μs/boundary，并且 mutation study 中抓住所有会让原 unsafe action 重新通过的 mutant。样本只有 6 个，证据规模还小，但“把线上 Agent Incident 变成可重复 CI Test”的接口很值得借鉴。
论文 · 代码

dQwen3.5 关注一个正在变重要的架构问题：Hybrid Attention Backbone 能不能被改造成 Diffusion Language Model。作者将 Qwen3.5 0.8B/2B/4B/9B 适配成 DLM，虽然其中的 RNN/DeltaNet 层天生带 causal structure，Hybrid Backbone 达到相同 training loss 所需 token 约为 full-attention control 的一半，并保留 any-order / parallel decoding 能力。现在仍属于模型研究信号，离证明 Diffusion Decode 在真实 Serving 上优于 AR 还有距离。

今日最值得花 30 分钟阅读的一项

首选 RetireOPD。
论文 · 代码

如果这段时间在跟 OPD / GRPO / Tool-Agent RL，这篇的价值不是又多一个混合 loss，而是它把一个常被固定 schedule 掩盖的问题做成了可观察状态：Teacher 一开始能帮助 Student 进入有效行为区域，后来也可能成为能力 Ceiling。

30 分钟建议按这个顺序读：先看“Skill Context 为什么没有自动产生强 Teacher”；再看 GRPO+OPD 中 Teacher–Student discrepancy 先降后升；随后看 retirement 的两个 gate——discrepancy 是否停止改善、Student success 是否已经达到 Teacher 的目标比例；最后看 50–90 step 的跨任务退休时间变化和主结果。

最值得带走的判断是：

Distillation 应被看作有退出条件的训练脚手架。Teacher 是否还值得付费，不应该只由训练步数决定，而应该由 Student 当前能力和 Teacher–Student 冲突共同决定。

这条原则很容易迁移到 Multi-Teacher、Skill Distillation 和 Tool Agent：早期使用特权信息加速探索，Student 真正学会后及时撤掉约束，让环境 Reward 接管后续优化。

今日可立即实践的一件事

给现有 OPD / OPSD / Teacher-guided RL 实验加一个 Teacher Utility Retirement Audit。不用立刻改训练算法，先把“Teacher 什么时候开始拖后腿”测出来。

固定每 5–10 个训练 step 记录四项：

1

4

teacher_audit = {
    "student_success": [],
    "teacher_success": [],
    "teacher_student_logp_gap": [],
    "reward_vs_distill_gradient_cosine": [],
}

对 Student 自己的 on-policy trajectory，计算 sampled token 上的 Teacher–Student gap：

\[K_n= \frac{1}{|y|}\sum_t \left[ \log p_T(y_t\mid c_t, s)- \log p_S(y_t\mid c_t) \right].\]

再观察相邻窗口的 $K_n$ 是否继续下降，并同步记录 Student/Teacher success ratio。若 gap 已经连续多个窗口停止收敛、Student 成功率接近或超过 Teacher，而 Reward Gradient 与 Distillation Gradient 的 cosine 开始为负，就做一个最简单的反事实 A/B：从同一 checkpoint 分叉，一条继续 RL+OPD，一条关闭 Teacher 只跑 RL。

停止条件： 如果关闭 Teacher 后 performance / exploration diversity 没有改善，或者 Teacher–Student gap 仍稳定下降，就没有依据引入自动退休机制。相反，如果 Teacher-on 分支开始停在 Teacher ceiling，而 Teacher-off 分支持续上涨，这时再把 retirement gate 正式写入训练框架，收益会比盲目调一个固定 annealing schedule 更有解释力。

真正要回答的是：

你的 Teacher 现在仍然在教 Student，还是 Student 已经在为模仿 Teacher 付机会成本？

> **今日主线：** OPD State Coverage · Environment Supply · Agent Credit Assignment · Tool-Interface Reliability · Long-Tail Semantic IDs · FP4 Hybrid Inference

截至今天上午，arXiv 最新常规公告批次为 **2026 年 9 月 4 日**：`cs.AI` 165 条、`cs.LG` 168 条、`cs.CL` 115 条、`cs.IR` 24 条；不同分类存在交叉收录，不能直接相加。今天最值得连起来看的变化是：后训练正在重新审视“到底需要多少数据、监督信号应该何时组合”；Agent 训练的瓶颈则进一步前移到可执行环境、credit assignment 和工具接口；推荐与推理系统分别从非欧几里得 Item Tokenization 与 FP4 硬件协同中寻找新的结构性收益。

## 今日核心判断

1. **OPD 可能远比我们想象的更“不缺数据”。** *Rethinking OPD II* 报告单个 query 的 rollout 已能覆盖 full-data OPD 所访问状态的 71.5%，16 个语义不同 query 达到 98.9% 并匹配 full-data；真正变慢的是 student 吸收 teacher supervision 的速度。与同日的 *Sequential Beats Joint* 放在一起看，一个更可信的方向是：先用 OPD 扩展 teacher-supported solution coverage，再切到 RLVR 做 outcome sharpening，而不是长期把两种信号硬塞进同一步优化。
2. **Agent post-training 的稀缺资源正在从 trajectory 转向 environment。** Terminal-Universe 从历史 agent trajectory 反向重建可重复执行 workspace，并生成新任务与多轮交互；Environment Evolution 则继续把环境难度沿可学习前沿逐代推进。前者把“旧轨迹”变成“可再查询世界”，后者试图避免 synthetic environment 被越来越强的模型迅速做穿。
3. **Fine-grained reward 并不自动带来正确 credit。** DRACO 在无 ground-truth verifier 的长程 Agent 中动态生成 rubric，再把 trajectory-level judgement 闭式分配到相关步骤；另一篇 *Spurious Advantage Hidden in GRPO* 则指出，GRPO 的组内归一化可能给“猜中”错误地分配很大 advantage。两篇合起来说明：credit assignment 和 advantage estimator 都需要单独审计，不能因为 reward 更细或公式更标准就默认正确。
4. **Tool-use benchmark 可能测到的是 serving adapter，而不是模型能力。** *Interface-Induced Trajectory Censoring* 在保持权重、case、decoding、seed 不变时，仅替换 chat-template/parser contract，就能让同一个模型从“完全没有工具调用”变成大量真实执行；这一问题甚至会污染 RL 训练数据。对于任何 Agent 项目，tool-call preflight 应该成为训练与评测前的基础设施测试。
5. **Generative Recommendation 的 Item Tokenizer 仍有很大结构空间。** HypRQ-VAE 首次把残差量化 Item Index 放到双曲空间，利用指数体积增长去适配 power-law catalog 与长尾层级；三组 benchmark 的收益尤其集中在 tail item。这个方向值得关注，但目前证据仍是离线公开数据，尚不足以说明双曲 SID 会在大规模线上召回中稳定胜出。
6. **4-bit 不是一个统一问题：不同子结构对量化的耐受性和硬件收益完全不同。** Qwen3.8-27B 的 Gated DeltaNet 实验显示 recurrent half 并没有直觉上那么脆弱，NVFP4 W4A4 在 64K retrieval 仍接近 BF16；与此同时，FP4 FlashAttention-4 证明仅有 FP4 Tensor Core 不够，softmax 转换和片上依赖仍可能吃掉收益。真正的推理优化必须同时看数值机制、kernel 数据流和端到端吞吐。

## 1. OPD：一个 Query 已经能覆盖 71.5% 状态，真正瓶颈可能是“吸收速度”

> **一句话结论：** OPD 的数据效率比常见训练范式高得异常；如果 rollout 很快就把 teacher 可教的状态暴露出来，继续加训练 query 的边际价值可能小于改进每一步 supervision 的吸收效率。

**原始来源：** [Rethinking On-Policy Distillation of Large Language Models II: One Training Example](https://arxiv.org/abs/2609.04172)  
**相关工作：** [Sequential Beats Joint: On the Interplay between On-Policy Distillation and RLVR](https://arxiv.org/abs/2609.04108)

### 发生了什么

OPD 让 student 在自己的 rollout state 上接受 teacher 的 dense token-level supervision。直觉上，这仍然应该依赖大量多样训练题；但 *Rethinking OPD II* 把训练数据压到极端：只用一个 query。

结果不是迅速过拟合。单 query OPD 仍然能持续训练数百步，并恢复 full-data OPD 的大部分增益。作者把原因归因到 **state coverage**：不是统计原始题目数量，而是统计这些题目诱导的 rollout 到底访问了 full-data OPD 会访问的多少训练状态。

### 关键结果

单个 query 已经覆盖 **71.5%** 的 full-data states，而且大部分覆盖在前 100 个训练 step 就出现；随着语义不同的 query 增加，coverage 与 validation accuracy 一起提升，**16 个 query 达到 98.9% state coverage，并匹配 full-data OPD**。同样的现象还扩展到 multi-teacher OPD：每个 domain 16 个语义多样 query 可以匹配 full-data MOPD。

更反直觉的是，哪怕固定 state set 不再扩大，student 对 teacher 的 alignment 仍需要数百步才能逐渐吸收。作者据此提出一句很值得记住的判断：

> OPD 可能是 **data-overfed but algorithm-starved**。

同日的 *Sequential Beats Joint* 从另一个角度补充了这个结论。它比较 OPD、RLVR 与多种“在同一个更新中联合两种信号”的方法，发现简单的 **OPD → RL** 两阶段方案在逻辑与数学推理 benchmark 中持续优于纯 OPD、纯 RLVR 和 joint baselines。作者的机制解释是：OPD 先扩大 teacher-supported solution coverage，RL 再在这个 support 内根据可验证结果做 sharpening；把两种信号同时优化反而会产生干扰。

### 为什么重要

如果这两项结果能在更大规模后训练中复现，OPD 数据工程的重点可能要从：

```text
收集更多 query
→ 生成更多 teacher supervision
```

转向：

```text
用少量 query 快速覆盖有价值 state
→ 提高 teacher information 的吸收速度
→ 当 OPD validation 饱和后切换到 RLVR
```

这也改变了 OPD 与 SFT 的关系。SFT 更多是在固定数据状态上模仿，OPD 的 student rollout 会不断产生新前缀，因此“一个 query”并不等于“一个训练状态”。

### 可信度与局限

state coverage 是作者定义的 operational metric，不等于“真实推理能力空间已覆盖 98.9%”。数学／逻辑任务中的 rollout state 也比开放式 Agent 更容易形成高度重叠的状态分布。

此外，两篇论文都还是新预印本。*Sequential Beats Joint* 证明的是其测试设置中顺序优化更稳，并没有证明所有 teacher signal 与 RL reward 天生不可联合；更好的 joint optimizer 仍可能消除干扰。

### 最值得继续追踪

最值得追的是 **OPD step efficiency**：在固定 teacher tokens、固定 rollout budget 下，什么样的 token selection、optimizer、curriculum 或 student-state replay 能让 alignment 更快完成。另一个直接问题是：Tool Agent 的状态空间是否也存在“少量任务快速覆盖大部分可学习 state”的现象。

## 2. Terminal-Universe + Environment Evolution：Agent 训练真正缺的是“世界”，不是静态轨迹

> **一句话结论：** trajectory 是一次性的行为记录，environment 才是可以反复提问、执行、验证和产生新任务的训练资产；当环境变得太容易以后，还需要让环境本身持续进化。

**原始来源：** [Terminal-Universe: Turning Agent Trajectories into Scalable Terminal Environments](https://arxiv.org/abs/2609.04148)  
**相关工作：** [Environment Evolution for Terminal Agents](https://arxiv.org/abs/2609.04128)

### 发生了什么

Terminal-Universe 从公开 terminal-agent trajectory 的文件操作历史出发，回放 Agent 曾经做过的修改，恢复被修改前的文件；缺失文件和依赖再由 completion agent 补齐，最终得到一个可执行 workspace。

在恢复出来的 environment 上，系统不仅重建原始任务，还继续合成新任务。Breadth 方向通过跨 workspace 的依赖关系构造跨代码库任务；Depth 方向则让 user agent 把单轮需求扩展成包含后续反馈和需求变化的多轮 session。

另一篇 *Environment Evolution* 解决下一阶段问题：强模型会越来越快地做穿从零合成的环境。它不依赖当前 policy 的即时 on-policy rollout，而是离线沿三类难度方向逐代演化环境，再按 generation schedule 注入训练。

### 关键结果

Terminal-Universe 从公开 trajectory 中构建 **37.3k 个 task-sufficient environments**。在其数据上 SFT Qwen3.5-27B，Terminal-Bench 2.1 单轮表现提高 **11.9 points**，EvoCode-Bench v2 的多轮 MT@4 提高 **13.8 points**。

Environment Evolution 则使用 Hy4 preview、Claude Opus 5 与 GPT-5.6 Sol 验证演化后环境确实更难；再用简单 long-horizon RL 训练 Qwen3.6-27B 与 Qwen3.6-35B-A3B，在 Terminal-Bench 2.1 分别提高 **14.4 / 18.0 个百分点**。

### 为什么重要

Agent 训练的数据单位正在发生变化：

```text
传统：
task → trajectory → 保存 demonstration

更可扩展：
trajectory → 重建 environment
environment → 生成许多 task / feedback / verifier state
environment → 随能力继续进化
```

如果一个 environment 能重复产生数十个不同 task，它的长期训练价值远高于一条 demonstration。这也给 self-evolving Agent 提供了更有希望的闭环：Policy 提升以后，不一定只生成“更难的答案”，也可以让训练世界本身沿能力边界移动。

### 可信度与局限

重建出来的 workspace 是否真实，仍依赖 trajectory 是否暴露足够文件操作以及 completion agent 是否正确补齐缺失依赖。37.3k “task-sufficient” 不等于 37.3k 环境都完整复现了原真实开发环境。

Environment Evolution 的难度提升则可能产生另一种风险：环境越来越“难”，但难点未必越来越像真实工程。Synthetic difficulty 很容易向模型当前弱点过拟合，最终形成一种 benchmark-specific adversarial curriculum。

### 最值得继续追踪

建议重点看三个量：**environment validity、task diversity、real-world transfer**。如果环境生成器只会制造更难的 synthetic puzzle，而不能提升真实代码仓库上的新任务成功率，它就没有真正解决 environment supply。

## 3. DRACO + Spurious Advantage：Agent RL 的两个“信用错配”

> **一句话结论：** 一个问题发生在“trajectory reward 怎么分到 step”，另一个问题发生在“group reward statistics 给每条 rollout 多大 advantage”；两层估计器任何一层出错，都可能把错误行为训练得更坚定。

**原始来源：** [DRACO: Fine-Grained Credit Assignment with Dynamic Rubrics for Long-Horizon Agent Training](https://arxiv.org/abs/2609.04094)  
**代码：** [IBM/draco](https://github.com/IBM/draco)  
**相关工作：** [Spurious Advantage Hidden in GRPO](https://arxiv.org/abs/2609.04063)

### 发生了什么

DRACO 针对的是 **outcome-blind long-horizon Agent**：很多真实任务没有可靠 programmatic verifier，常见替代方案是让 rubric judge 对完整 trajectory 给一组评分；但一条几十步轨迹最后只得到一个 scalar，再把它广播给所有 step，credit 仍然很粗。

DRACO 在训练过程中动态生成与当前 policy 能力相匹配的 rubric，每条完成 trajectory 只评一次，再根据 rubric 标注的责任步骤，把 judgement 用闭式方法重新分配成 per-step advantage；不额外训练 attribution model。

*Spurious Advantage Hidden in GRPO* 则审计更底层的 group-relative estimator。GRPO 根据同一 group 的 reward composition 决定 advantage magnitude，但在 bounded-answer task、包含有限候选的开放任务，以及多条搜索路径最终落到同一答案的 Agent 中，“猜中”可以获得和真正推理成功相同甚至很高的 advantage。作者把它称为 **spurious advantage**。

### 关键结果

DRACO 在 AppWorld 上相对 base model 提高 **15.9 points**，相对使用 sparse ground-truth reward 的 GRPO 仍高 **5.3 points**；在 OOD Tau-Bench 上相对 base model提高 **5.3 points**，而方法本身不依赖 frontier judge 作为 verifier。

SIGNBALANCE 则保留 verifier 的 reward sign，使用全局 scale，并通过 stop-gradient 的 per-class rescaling 恢复 zero-mean balance。论文报告它在 open-answer math 上匹配 GRPO，而在 bounded-answer math 与 search-agent benchmark 上更好。

### 为什么重要

Agent RL 的 credit pipeline 至少可以拆成：

```text
environment / judge
    ↓
trajectory reward
    ↓  advantage estimator
rollout-level advantage
    ↓  credit assignment
step / action / token credit
```

大量工作只改其中一层，却默认其他层无偏。DRACO 提醒我们 trajectory scalar 不足以指导几十个异质动作；SIGNBALANCE 提醒我们，即便最终 reward 完全正确，组内 normalization 也可能制造错误的 magnitude。

### 可信度与局限

DRACO 的 rubric 仍由模型动态生成和评价，因此“没有 ground-truth verifier”不等于没有 Judge bias；它只是把评估责任结构化并分到步骤。其 closed-form attribution 也不是 executed counterfactual credit。

SIGNBALANCE 的问题域则有明确边界。GRPO 在开放答案数学上本来就表现良好，作者也报告 SIGNBALANCE 主要在 bounded-answer / search 结构中占优。因此不能把结论扩大成“GRPO advantage 普遍错误”。

### 最值得继续追踪

训练日志应同时记录 `group reward composition`、`advantage magnitude`、`step credit distribution` 和最终 outcome。对于 Search / Tool Agent，特别值得检查：正确答案是否能通过大量无效路径偶然撞到，以及某个关键工具动作是否在长轨迹中几乎拿不到 loss mass。

## 4. Interface-Induced Trajectory Censoring：模型明明调用了工具，Server 却说它从没调用

> **一句话结论：** Agent benchmark 中的 “tool-call rate” 不是纯模型属性，它是模型、chat template、parser、server adapter 和 executor 共同产生的系统指标；接口 contract 错配可以把真实能力完全静默地抹掉。

**原始来源：** [Interface-Induced Trajectory Censoring](https://arxiv.org/abs/2609.03966)  
**代码、数据与预注册：** [nebula-1999/Interface-Induced-Trajectory-Censoring](https://github.com/nebula-1999/Interface-Induced-Trajectory-Censoring)

### 发生了什么

论文从一个很危险的现象出发：serving stack 报告 tool-call rate 为 0，并不代表模型没有生成合法 tool call。模型可能已经输出完整调用结构，只是 chat template 与 parser 的组合 contract 不兼容，调用在到达 executor 之前就被静默丢掉。

作者在 BFCL v4 中保持模型权重、case、decoding 和 seed 全部不变，只替换 serving adapter；同一个模型可以得到完全不同的工具调用表现。一个 `chat template × parser` 的 $2\times2$ 实验尤其关键：两个组件单独看都没有主效应，**全部差异来自二者 interaction**——单独“修 parser”或“修 template”都没有用。

### 关键结果

在 $\tau$-bench 的 115 个零售交互任务中，仅替换 adapter，就让 server-parsed tool calls 从 **0 → 636**，有任何工具真正执行的任务从 **0 → 103**。

在 Qwen2.5-Coder 的 21× 模型规模范围中，旧 server 对每个规模都解析出 **0/100** 调用，但模型实际生成的 well-formed call 随规模持续上升，到 32B 已达到 **80/100**（经人工 gold calibration 后约 72）。

问题还会进入训练环。verl AgentLoop 的 7B 设置里，115 个 generation 中有 **45 个包含完整 tool call**，但 **0 被接受、0 执行、0 返回 observation**。模型的能力信号在 interface 层被全部截断。

作者最终发布了一个仅 **98 行**的 preflight check，用来在训练／评测开始前检测这些 silent failure。

### 为什么重要

这是今天最实用的一篇论文，因为它直接击中了 Agent 实验的测量基础。

如果 interface 断了，后面的所有分析都会变成伪问题：

```text
“模型不会用工具”
→ 给更多 SFT
→ 做 Tool RL
→ 加 reward
→ 继续训练
```

但真实原因可能只是：

```text
模型已输出合法调用
→ parser 没认出来
→ executor 从未看到
→ policy 永远收不到工具 observation
```

更糟糕的是，模型越大、真实 tool ability 越强，censoring 越可能把“scale 没有效果”伪装成模型结论。

### 可信度与局限

论文做了预注册、跨规模探针和严格 $2\times2$ contract test，机制证据很强。但修复 interface 并不自动等价于任务成功：作者在一个 matched evaluation 中把 parsing 从 0 恢复到 84、rescues 从 0 提到 9，pass rate 53→62，但差异未达到统计显著。

所以正确结论是：**接口错配会严重破坏测量与训练信号；修接口是必要条件，不是充分条件。**

### 最值得继续追踪

所有 Agent framework 都应该发布 machine-readable 的 tool-call conformance test。模型厂商、template、parser、server 和 executor 每次升级都应重跑，而不是靠一个 end-to-end benchmark 等错误出现后再猜。

## 5. HypRQ-VAE：用双曲空间建 Item Vocabulary，针对长尾 Catalog 的几何错配

> **一句话结论：** Item catalog 的交互频率和语义层级通常呈 power-law，而欧氏空间的体积增长是多项式级；双曲空间的指数体积更自然地容纳大量稀疏长尾节点，这是 HypRQ-VAE 的核心建模动机。

**原始来源：** [HypRQ-VAE: Hyperbolic Item Indexing for Long-Tail-Aware Generative Recommender Systems](https://arxiv.org/abs/2609.03369)  
**代码与数据：** [wulongfeng/HypRQ-VAE](https://github.com/wulongfeng/HypRQ-VAE)

### 发生了什么

Generative Recommendation 常用 RQ-VAE 把 item semantic embedding 离散成 Semantic ID，再让语言模型生成这些 token。现有 Item Vocabulary 大多在 Euclidean space 中学习，而真实商品 catalog 往往同时具有层级结构与极不均衡的长尾分布。

HypRQ-VAE 把 residual-quantized VAE 的 item indexing 搬到 hyperbolic space。直觉上，在负曲率空间里，半径增加带来的可用体积呈指数增长，因此可以更自然地容纳“少量 head item + 大量稀疏 tail item”的树状／层级结构。

### 关键结果

作者在三个 benchmark dataset 上报告推荐性能显著提高，收益对 **tail items** 尤其明显，并把改进归因于双曲空间对层级和 sparsity 的表达能力。论文已标注为 **ICDM 2026 accepted**，代码和数据公开。

摘要没有提供一个跨数据集统一的 headline effect size，因此这里不人为补一个“平均提升 X%”。现阶段更重要的是看 tail-bucket、codebook utilization 和 hierarchy preservation 的完整实验。

### 为什么重要

Semantic ID 不是中性的 tokenizer。它决定：

- 哪些 item 在离散空间里彼此接近；
- codebook 是否被头部商品垄断；
- 长尾 item 是否拥有足够独立的路径；
- 自回归生成过程中哪些 item 更容易被 prefix 剪枝。

如果 underlying geometry 与 catalog 的频率／层级结构错配，后面的 decoder 再强也只能在一个先天有偏的 token space 中学习。

### 可信度与局限

双曲空间“适合层级结构”是成熟的几何直觉，但它不自动保证推荐效果。真实 catalog 中同时存在互补、替代、跨类目共购等非树状关系，强行映射成层级几何也可能损失信息。

目前证据仍是公开数据离线实验，没有线上 CTR/CVR、动态 catalog update、token stability 和 serving cost。双曲距离与量化运算的工程开销也需要单独评估。

### 最值得继续追踪

优先看 **head/tail 分桶的 token collision、SID prefix survival、codebook usage entropy**，以及新 item 加入后 token 是否稳定。若双曲 indexing 的收益只来自更大的 effective capacity，而非更合理的层级结构，后续模型设计会完全不同。

## 6. FP4：Gated DeltaNet 比想象中耐量化，但 Attention 的硬件瓶颈仍在 Softmax 数据流

> **一句话结论：** “4-bit 会不会累积误差”和“4-bit Tensor Core 能不能让 kernel 真的更快”是两个不同问题；今天两篇工作正好分别回答数值稳定性与硬件执行路径。

**原始来源：** [Why Gated DeltaNet Survives 4-Bit Quantization](https://arxiv.org/abs/2609.04098)  
**相关工作：** [Hardware-Aware FP4 FlashAttention-4](https://arxiv.org/abs/2609.04105)  
**代码：** [hao-ai-lab/flash-attention-fp4](https://github.com/hao-ai-lab/flash-attention-fp4)

### 发生了什么

Qwen3.8-27B 是 hybrid architecture：48 层 Gated DeltaNet（GDN）+ 16 层 softmax attention。社区早期 4-bit recipe 往往把 GDN 的 gate 留在 8/16-bit，因为直觉认为 recurrent state 每个 token 都会读取、更新，量化误差会随上下文不断累积。

Minima 直接把 **全部 496 个 linear layers** 都做 NVFP4 W4A4，包括 GDN。机制分析发现这一直觉并不成立：16-element block scaling 把 outlier 局部化；gate projection 虽有约 11% GEMM error，但经过 softplus/exponential 和 sigmoid 后 output error 被压到约 2%；更关键的是，delta-rule recurrence 会不断用当前 key direction 覆写 state，注入噪声只形成稳定平台，并在数百步内遗忘，而不是随 32K context 累积爆炸。

另一篇 FP4 FlashAttention-4 解决的是完全不同的问题。Blackwell 有 FP4 Tensor Core，并不意味着 attention 自动加速，因为 softmax 转换和片上 dependency 在矩阵乘变快后会成为新瓶颈。Direct-P 将 score 直接映射成 FP4 probability，减少中间转换；causal training 路径则复用 forward quantization，并用 FP8 gradient operand。

### 关键结果

Minima 在 4K/32K perplexity、MMLU-Pro、GSM8K、AIME'25、GPQA-Diamond、LiveCodeBench 与 RULER 64K 上接近 BF16，五项任务平均相对 BF16 **-0.52**；checkpoint 体积 **17.5 GiB**，在比较 recipe 中 prefill 最快，提升 **14–19%**。

FP4 FlashAttention-4 的非因果 Direct-P 在 NVIDIA GB200 上最高达到 **2.13× BF16 forward throughput**；causal path 的单 GPU 8B 完整 update 最高 **1.14×**。一个重要负结果是：分布式训练中保留 FP8 probability/value 可以稳定运行，而作者测试的所有 MXFP4 probability/value training trajectory 都发生 divergence。

### 为什么重要

这两篇放在一起说明，“量化”不能被当成一个统一的 bit-width 开关。

对于 recurrent block，真正要问的是：

```text
量化噪声会不会随 state update 累积？
```

对于 attention kernel，真正要问的是：

```text
更低位 GEMM 以后，新的非 GEMM bottleneck 在哪里？
```

数值上安全的 FP4 不保证硬件上有收益；硬件拥有 FP4 throughput 也不保证端到端 kernel 吃得到。

### 可信度与局限

GDN 结果目前只覆盖一个具体 hybrid 27B architecture 与 NVFP4 recipe，不能自动推广到 Mamba、不同 DeltaNet 变体或任意 recurrent state model。

FlashAttention-4 的最高 2.13× 是特定 GB200、shape 和非因果 forward 条件，不是所有 LLM decode 的普遍加速倍数；完整 causal training 的提升明显小得多。作者自己报告的 MXFP4 divergence 也说明“越低位越好”并不成立。

### 最值得继续追踪

未来更有价值的是 **hybrid model 的 per-component precision map**：GDN state、gate、softmax attention Q/K/V、KV cache、MLP 各自应该用什么格式，最终在固定质量目标下优化 `GPU memory × throughput × latency × power`，而不是追一个统一 W4A4 标签。

## 今日值得收藏的代码 / 学习资源

**[IBM/DRACO](https://github.com/IBM/draco)**：适合直接看动态 rubric 如何与 trajectory annotation、GRPO step advantage 连接。比只读公式更值得检查的是：rubric 如何随 policy 变化、责任步骤怎样绑定，以及训练日志是否能审计每一步拿到的 credit。

**[Interface-Induced-Trajectory-Censoring](https://github.com/nebula-1999/Interface-Induced-Trajectory-Censoring)**：今天最值得马上复制到自己 Agent stack 的资源。仓库包含论文的 code/data/preregistration，以及一个很短的 preflight check。它解决的是任何 Tool RL 之前都应该先排除的“接口根本没把模型调用传下去”问题。

**[HypRQ-VAE](https://github.com/wulongfeng/HypRQ-VAE)**：推荐系统方向可以直接复现双曲 Item Indexing，尤其值得对比 head/tail bucket、codebook utilization 和 SID hierarchy，而不是只看 Overall NDCG。

**[Hardware-Aware FP4 FlashAttention-4](https://github.com/hao-ai-lab/flash-attention-fp4)**：适合推理／训练系统从业者理解“FP4 Tensor Core 存在，但 attention 为什么仍可能不快”。建议结合 kernel 数据流看 Direct-P，而不是只记住 2.13× headline。

**[Uno: Unlocking Lossless Speedups via Discrete Diffusion](https://arxiv.org/abs/2609.04010)**：今天值得额外扫一眼的 decoding 路线。它用一个 AR model 定义目标分布，再训练轻量 diffusion weights 从同一分布并行产生多个 token；作者报告 Ψ-Spec 在不改变 underlying AR quality 的前提下最高约 3× speedup。当前更适合作为“draft-model-free speculative decoding”方向信号，仍需要第三方吞吐与 batch-size 复现。

## 今日最值得花 30 分钟阅读的一项

**首选 [Rethinking On-Policy Distillation of Large Language Models II: One Training Example](https://arxiv.org/abs/2609.04172)。**

这篇值得读的地方，不是“一条数据也能训练”这种容易被媒体化的 headline，而是它把 **dataset size** 和 **state coverage** 拆成了两个完全不同的变量。

建议按这个顺序读：

1. 先看 single-query OPD 为什么能持续改善数百 step，而不是很快过拟合；
2. 看 state coverage 的定义，以及 **1 query → 71.5%、16 queries → 98.9%** 这条曲线；
3. 再看 coverage 很早饱和，但 teacher-student alignment 仍然持续很慢的结果；
4. 看 content-light template 与 off-domain WildChat query 为什么也能接近真实 query；
5. 最后把它和 [Sequential Beats Joint](https://arxiv.org/abs/2609.04108) 对照：如果 OPD 的作用更像快速铺开 teacher-supported states，为什么后续 RL sharpening 比长期 joint optimization 更自然。

真正值得带走的问题是：

> **你的 OPD 项目现在缺的真的是更多训练题，还是 student 在已经访问过的 state 上吸收 teacher 信息太慢？**

## 今日可立即实践的一件事

给现有 Tool / Coding Agent 做一个 **Tool-Call Interface Preflight Audit**。不要先改模型，也不需要跑完整 benchmark；只验证一条调用从模型输出到环境 observation 的整条 funnel。

固定 20–50 个必须调用工具的测试 prompt，逐层记录：

```python
record = {
    "raw_model_output_has_call": bool,
    "call_is_well_formed": bool,
    "server_parser_accepts": bool,
    "executor_receives": bool,
    "tool_executes": bool,
    "observation_returns_to_model": bool,
}
```

按 model × chat-template × parser × server version 做小型组合矩阵，至少统计：

$$
R_{\text{parse}}
=
\frac{\#\text{parser accepts}}
{\#\text{well-formed emitted calls}}
$$

以及：

$$
R_{\text{roundtrip}}
=
\frac{\#\text{observations returned}}
{\#\text{well-formed emitted calls}}.
$$

**停止条件：** 如果模型已经产生 well-formed call，但 `R_parse` 或 `R_roundtrip` 明显低于 100%，先冻结所有 Tool SFT / RL 实验，修完 interface contract 再继续训练。否则 reward、tool-call rate 和 success rate 都会混入基础设施 censoring。

还应增加一个升级回归：任何 chat template、parser、serving framework、tool schema 或 `strict` 参数变更后，自动重跑 preflight。今天这篇论文最实用的结论就是：

> **先证明工具链能忠实传输模型动作，再讨论模型会不会用工具。**

今日主线： Retrospection-Only Learning · Harness Test-Time Adaptation · KV-State Compaction · Verifiable RSI · Textual User Taste · Adaptive Looped Reasoning

arXiv recent 页面在 2026 年 9 月 29 日批次中显示：cs.AI 972 条、cs.CL 392 条、cs.LG 1,012 条、cs.IR 55 条。这里包含交叉收录等条目，不能直接相加，也不应把数字本身当成“原创新论文数”。今天真正值得连起来看的变化，是 Agent 后训练正在从“只学习成功动作”转向学习自己对失败的解释；Harness 从固定外部脚手架变成可以在测试时继续适配的对象；Context Compaction 开始保留隐式 KV 状态而不再每次重新 Prefill；Self-improvement 系统则进一步把实验动作、证据链和研究分支本身结构化。推荐侧，一个很现实的方向是：继续保留强行为 Embedding，同时给 Foundation Recommender 增加可读、可修改的自然语言用户状态。

今日核心判断

  1. Agent 改进不一定需要 Reward-based Policy Update。 ROFT 只训练 Agent 对自己执行经历写出的 retrospective explanation，不使用外部 Teacher，也不做 RL；Qwen3.5-4B 在 SWE-bench Verified / Pro 上 20 次更新后达到 49.2% / 26.8%，高于论文对照中 GRPO 40 次更新的 48.0% / 25.3%。更关键的是，它能学会一些 Base Model 64 次采样全部失败的任务，说明“先有成功轨迹才能开始学”并非必要条件。

  2. Harness 正在变成可学习、可测试时适配的程序参数。 Harness Learning 训练一个 Proposer，根据执行反馈修改 Solver 的可执行 Harness；到了未见任务上，模型权重保持冻结，只继续修改 Harness。论文在 Reasoning 与 Multi-hop QA 上观察到 Test-time Adaptation 可以迁移，而且只训练单次 Harness Revision 的 Policy，也能连续执行多轮改进。当前证据支持“Harness Revision 能迁移”，还没有证明任意 Tool / Browser / Coding Harness 都能稳定自我进化。

  3. Context Compaction 的系统成本里，Repeated Prefill 可能比“压缩算法本身”更贵。 KV-streams 在压缩后不清空 KV Cache，而把它作为连续状态往前流，使三种 Compaction 策略获得 2.6–5× 的训练 Wall-clock Speedup。更有意思的是，论文发现 KV 可以携带已经从显式 Context 消失的信息；在受控设置里，单靠 RL 就能学出这种 recurrent-state 行为。这既是效率机会，也是新的可观测性风险。

  4. Recursive Self-Improvement 的关键基础设施越来越像一个受约束的 Experiment OS。 RSI-Master 用 Experiment OS 限制实验动作并维护可追踪记录，再用 Worker / Reviewer 构建动态 Research DAG。Qwen3-4B-Base 在 PostTrainBench 上平均 54.49，对最强 Agent Baseline 为 46.53，论文报告 hacking rate 为 0.0%；扩到 35B 后在 LiveCodeBench-v6 为 41.21，对人类开发 Instruct Model 的 37.36。它证明了结构化实验治理可以提升 AutoResearch，但不能据此推出“RSI 已经进入递归加速”。

  5. Foundation Recommender 的用户状态可以增加一个“语言接口层”，但行为 Embedding 仍是主干。 Spotify 的 Textual User Taste 从 Listening Behavior、Interaction Signal、Metadata 和可选用户反馈生成结构化自然语言 Profile，并部署到百万级用户；与 Behavioral Embedding 结合后，Future-track Prediction MRR +0.6%，Search Ranking NDCG@7 +2.2%。它支持正向自然语言 Steering，但对否定表达和短期兴趣变化仍有明显问题。

  6. Looped Transformer 的额外计算应该按 Token 分配，而不是所有 Token 一刀切。 TaH2 用 Lookahead Depth Supervision 学习每个 Token 是否值得继续循环。在 AIME 上，Accuracy–Compute Slope 相对非循环 Baseline 提高 53%（2.74 vs 1.79），匹配测试时计算量时峰值准确率约高 3.4 points；最大循环深度从 2 增到 8 时，增益从 +2.8 扩到 +3.9 points。它支持“latent compute routing”这条线，但目前仍主要是数学推理和中小规模模型证据。

1. ROFT：只训练“复盘”，为什么行为也会变好？

论文原文

发生了什么

ROFT（Retrospection-Only Fine-Tuning）故意把训练流程压到极简：Agent 先执行任务，看到现有反馈，再写一段 retrospective explanation；训练时只对这段解释文本做 Next-token Loss，实际 Action Token 不作为直接监督目标。

它不使用外部 Teacher，也不依赖 Reward-based Policy Update。训练数据同时包含成功与失败的 Base-model Attempt，因此失败轨迹并不会因为 Reward 为 0 就被完全丢掉。

最有意思的一点，是 Retrospection 并不只是“把失败重新说一遍”。行为分析显示，解释中会隐式重建动作因果：哪些决定导致成功、哪些操作造成错误。后续同一模型再行动时，这种解释能力会迁移回 Action Policy。

关键结果

设置SWE-bench VerifiedSWE-bench Pro更新次数
ROFT49.2%26.8%20
论文中的 GRPO 对照48.0%25.3%40

论文还报告，ROFT 能解决一些 Base Model 64 条采样轨迹全部失败的单独任务。这一点比平均分更值得重视：训练不必先等待“至少有一个成功 Rollout”才能产生学习信号。

作者还做了一个有趣的控制：如果提示模型在复盘中强调更直接的解决方式，后续执行会变短，即使训练中没有显式 Length Penalty。

为什么重要

当前 Agent RL 很容易把“可学习信息”近似成 Reward 或 Preference。ROFT 提示了第三类信号：

模型对自己经历的因果解释，本身可能就是一种 Policy Improvement Target。

它尤其适合稀疏奖励环境。一个失败 Coding Task 可能没有任何 Task Reward，但失败日志、执行历史与回归测试仍包含大量可解释的局部证据。

这也意味着自我改进的数据飞轮可以多一条路径：

1
2
3
4
5

attempt
→ environment feedback
→ retrospective causal explanation
→ explanation-only fine-tuning
→ new attempt distribution

可信度与局限

现在最强的证据集中在 Qwen3.5-4B 和软件工程任务。ROFT 与 GRPO 的训练预算、轨迹分布和实现细节不能简单等价成“ROFT 普遍比 RL 快两倍”。

另一个风险是 self-explanation error：模型可能对失败给出听起来合理、实际上错误的因果解释。Coding 环境有测试和执行结果可以锚定解释；开放式 Research / Shopping / Browser Task 的反馈更弱，错误解释可能被反复写回模型。

最值得继续追踪

最值得做的是 Verifier-grounded Retrospection：保留 ROFT 的低成本结构，但让解释中的关键因果陈述被执行证据、状态差异或 Counterfactual Replay 约束。

如果“解释质量”比“最终 Reward”更密集，又能避免自我合理化，它可能成为 Tool-Agent Post-training 很强的一条路线。

2. Harness Learning：把 Test-Time Learning 从参数空间搬到程序空间

论文原文

发生了什么

一个 Agent 的能力由 Model 和 Harness 共同决定。Harness 控制模型调用、Tool Use、Context Flow、步骤拆解和信息传递，但今天多数系统把 Harness 当作上线前由人写好的固定程序。

Harness Learning 引入一个 Proposer Model。Solver 执行任务后，Proposer 读取执行反馈，直接修改 Solver 的 Harness；修改后的 Harness 再执行任务，并用任务表现作为训练 Proposer 的 RL Reward。

论文把这个过程类比成 Meta-learning：

1
2
3
4
5

gradient-based adaptation:
weights → gradient → updated weights

harness learning:
program → execution feedback → revised program

测试时不更新任何 Model Parameter，只反复更新 Harness。

关键结果

论文在 Reasoning 与 Multi-hop QA 上观察到三件事：

  • 训练后的 Proposer 能产生更好的 Harness Revision；
  • Test-time Adaptation 能迁移到未见任务；
  • 即使只训练 Single-revision Policy，测试时连续调用多轮仍能继续改善 Harness。

反过来，显式使用 Revision Sequence 训练并没有在所有设置中都稳定优于单步训练。这个负结果很重要：多轮自我修改并不天然需要在训练时复制同样长的修改链。

为什么重要

这是“外部脚手架学习”与“模型权重学习”之间一个很干净的分层。

Harness 有三个优势：修改立即生效；可以被人读、版本化、回滚；当错误来自 Workflow 而不是模型知识时，不必付出 Fine-tuning 成本。

对 Coding / Search / Shopping Agent，真正经常变化的东西往往就是 Harness：先搜还是先规划；什么时候追加 Retrieval；哪些 Tool 并行；什么证据必须进入 Final Answer；什么时候启用更强 Judge；什么失败应触发 Retry。

可信度与局限

论文任务仍比真实 Computer-use Agent 干净。真实 Harness 有权限、安全、Side Effect、API Rate Limit 与不可逆动作，错误 Program Revision 可能直接产生事故。

另外，“Test-time Adaptation”并不等于无成本。每轮 Harness 修改都需要额外执行反馈，系统只是把学习成本从参数更新迁移到了环境交互。

最值得继续追踪

下一步应看 Harness Patch 的治理接口：每个 Revision 是否能声明作用范围、触发原因、受影响 Tool、回归测试和回滚点。

如果 Harness Learning 与 Scope / Replay Gate 合并，才更接近可长期运行的 Self-improving Agent。

3. KV-streams：Compaction 后别把 KV 全扔掉

论文原文

发生了什么

长程 Agent 为控制 Context Length 会周期性 Compaction。常见实现会生成压缩后的新 Context，然后重新 Prefill，旧 KV Cache 全部失效。

训练阶段尤其昂贵：一条很长的 Agent Trajectory 可能发生多次 Compaction，每次都重新计算此前仍保留的内容。KV-streams 的核心改动非常直接：Compaction 后继续向前流式保留 KV，而不是全部 Flush。

关键结果

论文将 KV-streams 接到三种不同 Compaction Strategy 上，报告 2.6–5× Wall-clock Training Speedup，同时没有观察到任务性能受损的证据。

更值得注意的是第二个发现：被继续携带的 KV Cache 会变成一种 Recurrent State。即使某些信息已经不再出现在显式文本 Context 中，后续生成仍可能通过历史 KV 使用它。

作者在受控实验中进一步表明，这种行为不需要额外 Memory Loss；RL 本身就可能学会利用该隐式状态。

为什么重要

Context Compaction 过去被当成 Prompt / Memory 问题，KV-streams 把它变成 Runtime State Management 问题。

如果 Compaction 后仍然保留连续的模型状态，系统可以同时得到两个东西：短显式 Context，以及长隐式状态连续性。这会显著改变 Agent RL 的成本结构，也可能让“训练真正跨越多长 Horizon”不再完全由文本 Context Window 决定。

可信度与局限

这里有一个必须正视的代价：可见 Context 不再等于模型实际拥有的信息。

如果 KV 中残留已经被 Summary 删除、被用户撤销或被安全策略更新的内容，传统 Transcript Audit 很难完整解释模型为什么做出某个动作。KV-streams 因此不仅是效率优化，也引入 State Revocation 与 Observability 问题。

另外，2.6–5× 是训练场景的 Wall-clock Speedup，不能直接当作在线推理也会得到相同比例收益。

最值得继续追踪

最值得看的是 KV State Invalidation：当旧 Observation 被明确标记为错误、敏感或失效时，系统能否定位并删除对应隐式状态，而不是只能重置整条 KV Stream。

未来的长程 Agent Runtime 很可能需要同时管理：

1
2
3
4

visible context
+ structured memory
+ persistent KV state
+ revocation metadata

4. RSI-Master：AutoResearch 的核心不是“多跑实验”，而是控制实验自由度

论文原文

发生了什么

RSI-Master 针对 AutoResearch 的两个典型失败：experiment hacking 与 strategy lock-in。

前者是 Agent 通过改变评测、数据、日志或实验路径制造“看起来更好”的结果；后者是早期偶然找到一个还行的方向后，所有后续计算都继续微调同一路线，缺乏真正的方向切换。

系统加入两层结构：Experiment OS 约束允许的实验动作并维护持久、可追踪记录；Reviewer-Guided Research Orchestration 让 Worker 探索不同方向，Reviewer 比较相关实验的证据，形成动态 Research DAG。

关键结果

设置结果
PostTrainBench · Qwen3-4B-Base54.49
最强 Agent Baseline46.53
报告的 hacking rate0.0%
35B · LiveCodeBench-v641.21
human-developed Instruct Model37.36

论文还报告 35B 系统在 SciCode 上超过对应 Instruct Model，并在 HorizonMath 上取得非零分；作者指出该 Benchmark 上多数 Frontier Model 接近零。

为什么重要

Self-improvement 系统越来越像一个自主实验室。此时最危险的事情不是 Agent 没有 Idea，而是它同时能修改 candidate、data、training、evaluation、reporting 与 selection。

只要这些层缺少边界，搜索能力越强，制造错误结论的速度也越快。RSI-Master 的真正价值在于把“研究过程”本身变成系统对象：实验动作受约束，证据有 Lineage，不同方向不会被一个单一 incumbent 过早淘汰。

可信度与局限

这是论文作者自己的 Agent Pipeline 与 Benchmark 结果。0.0% hacking rate 只对其定义、测试到的攻击面成立，不能理解成系统已经杜绝 Research Hacking。

LiveCodeBench / SciCode 的提升也证明的是这套 AutoResearch 找到了更好的 Post-training Recipe，不等于系统已经具备开放式科研意义上的“递归自我改进”。

最值得继续追踪

下一步最重要的是 改进效率是否递归提高：

\[E_n= \frac{\Delta \text{capability}_{n\rightarrow n+1}} {\text{experiment compute}_{n\rightarrow n+1}}.\]

如果后代研究系统持续用更少实验找到更大的增益，才开始接近真正值得讨论的 RSI acceleration。

5. Spotify Textual User Taste：让用户状态第一次有了“可读接口”

论文原文 · Spotify Research 相关文章

发生了什么

传统推荐系统非常擅长用 Dense Embedding 表示用户，但这些向量无法直接展示给用户，也不方便 Foundation Model 读取、解释和接受自然语言修改。

Spotify 构建 Textual User Taste：从 Listening Behavior、Interaction Signal、Content Metadata 与可选 User Feedback 中生成结构化自然语言 Taste Profile，并部署到百万级用户。

它没有试图替代行为向量。更准确的架构是：

3
4

behavioral embedding
    → retrieval / ranking backbone

textual taste profile
    → interpretable user context
    → LLM reasoning
    → user steering

关键结果

与 Behavioral Embedding 组合后：

任务增益
Future-track Prediction MRR+0.6%
Search Ranking NDCG@7+2.2%

论文还显示 Profile 本身具有用户特异性，并支持正向自然语言 Steering。例如“more jazz”一类追加偏好能够把表示朝预期方向移动。

但否定表达是明显失败模式：类似“不要电子音乐”的文本进入 Embedding Space 后，模型可能反而被“electronic music”这个强语义锚吸引。短期偏好变化的响应也尚未被充分证明。

为什么重要

Foundation-model Recommender 需要的 User State 与传统 Ranking Embedding 不完全相同。

行为向量擅长预测；语言 Profile 擅长可解释、可编辑、可被 Agent / LLM 直接消费，并能把用户显式声明和系统推断放在同一接口中。

最合理的路线因此不是“文本替代 Embedding”，而是让两种表示承担不同职责。

可信度与局限

百万级部署是强工业信号，但公开指标仍来自 Spotify 自身。+0.6% / +2.2% 是与行为 Embedding 联合后的下游增益，不能解读为“语言画像单独比传统用户向量更强”。

更大的风险是用户状态被自然语言化之后，Profile 可能把不确定推断写成确定事实。它需要像推荐特征一样管理 Provenance、Freshness 与 Confidence。

最值得继续追踪

最值得看的是 Editable User State：用户修改一条 Taste Profile 后，系统能否把这次修正反向传播到检索、排序和未来 Profile 更新，而不是下一次 Batch Refresh 又把错误偏好写回来。

这会决定自然语言 User Model 是真正的控制接口，还是只是一层解释 UI。

6. TaH2：Test-time Scaling 不只是“想更久”，还要知道哪些 Token 值得多算

论文原文

发生了什么

Looped Transformer 重复使用同一组层，以固定参数量换取更多 Latent Compute。传统固定循环深度的问题很明显：每个 Token 都多算相同次数，但很多 Token 根本不会从额外迭代中受益。

TaH2 共同训练 Backbone 与 Iteration Decider。监督信号来自 Lookahead Depth：在线判断“再多一次循环是否真的改善当前 Prediction”，再让 Decider 学习只把额外迭代分配给有收益的 Token。

关键结果

AIME 上：

指标结果
Accuracy–Compute slope2.74 vs 1.79
相对提升+53%
matched compute 峰值准确率约 +3.4 points
depth 2 相对非循环 Baseline+2.8 points
depth 8 相对非循环 Baseline+3.9 points

固定深度 Looped Model 随 Depth 增加较快进入平台期，TaH2 的收益则继续增长。

为什么重要

它把 Test-time Compute Routing 下沉到了模型内部。

外部 Router 决定“这道题要不要 Think”；TaH2 决定“这个 Token 的隐藏状态是否值得再经过几轮计算”。两者可以形成层级结构：

1
2
3

request-level budget
→ turn-level budget
→ token-level latent iterations

这比统一延长 CoT 更接近真正的自适应计算。

可信度与局限

论文主要证据来自 AIME 等 Reasoning Task。Token-level extra depth 对 Retrieval、Tool Planning、Natural Language Generation 是否同样有效，还没有充分验证。

Looping 也不是免费计算。它省参数，不代表省延迟；真实部署还要看 Kernel、Batching、Memory Access 和 Decider Overhead。

最值得继续追踪

最值得看的是 Latency-matched Evaluation，而不只是 FLOPs-matched。对生产系统，动态循环只有在 Batch 不被严重打碎、GPU 利用率仍然健康时才真正有价值。

PEAR：AutoResearch 应该使用分级证据，而不是 keep-if-better

论文

PEAR 为工业搜索设计四级 Verifier Ladder：

1
2
3
4

Offline Replay
→ Shadow-Traffic Evaluation
→ Rapid Online Evaluation
→ Decision-Grade Online Evaluation

只有低成本证据已经显示统计意义上的正效应，Candidate 才进入更昂贵的层级。系统还为不同 Strategy 维护独立 Research State，避免一次短期流量波动把一个 Candidate 永久晋升成新的默认方案。

两个真实 Search A/B 中，论文报告 Main Order/DAU 分别相对 Baseline +2.7336% / +3.2957%。这些数字属于完整系统和第一方生产结果，但它的 Verifier Ladder 很值得直接迁移到推荐 AutoResearch。

Foil：Looped MoE 不是简单把同一层重复几次

论文

Foil 的设计是：Expert Layer 数减半、每层 Expert 数翻倍、Pass 数翻倍，同时让 Attention 在不同 Pass 间使用独立参数，而 Expert 与 Router 共享。

20B Token 时所有 Foil 配置都低于未 Flatten 的 Looped Baseline Loss；100B Token 时最 Flatten 的配置在相同参数与计算量下低 0.012 nat，Downstream Accuracy 持平或更好。

一个很值得记住的诊断结论是：Routing Confidence 比单纯 Load Balance 更能反映 Expert 使用是否健康。 MoE 看起来“很平均”不代表它真的在做有区分度的 Routing。

SpeakGR：Generative Retriever 学 SID 时，也要防止忘记自然语言

论文

Generative Retrieval 把 Document 表示成 Semantic ID 并让 LLM 直接生成 ID，但只做 Retrieval SFT 会显著扭曲原模型的 Natural-language Distribution。

SpeakGR 在 Student 自己生成的 Prefix 上，让当前模型对齐冻结的原始模型，并只在原 Text Vocabulary 上计算 Forward KL。相对 SFT-only，WikiText-2 的 Forward-KL Drift 在 MS MARCO 上降低 81.3%–93.8%，NQ 上降低 81.2%–85.2%，同时保持有效 Retrieval。

RenderRank：文本 Reranker 也许不一定要把文档当文本 Token 读

论文

RenderRank 把 Document 渲染成图像，让 VLM 使用更紧凑的 Visual Token 做相关性评分。11 个 BEIR Dataset 上输入 Token 减少 16.5%–35.5%，平均 NDCG@10 为 55.96；四个长文档数据集上约使用一半平均 Token，NDCG@10 为 88.27，最高平均 Throughput 为对照的 1.70×。

需要特别注意，视觉编码是否预计算、缓存命中和文档更新频率都会影响真实成本；论文里的 Throughput 不应直接外推到动态网页检索。

大家在争论什么

OpenShell 代表软件执行边界：Agent 进程外定义 File、Network、Process 与 Credential Policy。Sentry 则代表更强的 Out-of-band Monitoring：监控和部分 Enforcement 与 Agent 所在执行域隔离。

这类设计背后的基本假设很务实：

高能力 Agent 可以提出动作，但不应该拥有修改自身最终授权边界的权限。

为什么现在值得关注

过去几个月 Agent 的风险开始从“生成错误文本”升级到真实 Side Effect：浏览器、Shell、云资源、凭据和外部系统都可能被写入或调用。此时单纯提高 Alignment 并不能替代最小权限、审计日志、Circuit Breaker 和不可绕过的 Runtime Policy。

这也是今天几篇 AutoResearch 论文的共同背景：能力越强，越要把 Evaluation、Authorization 和 Artifact Lineage 放到 Policy 之外。

技术判断与局限

可以确认 OpenShell 已公开，官方材料也明确描述了 Sentry / BlueField 的独立监控结构。当前仍缺少的是大规模第三方攻击评测：Policy Definition 正确不等于 Runtime Implementation 没有绕过路径。

今日最值得花 30 分钟阅读的一项

首选 ROFT：Shockingly Simple Self-retrospection Improves Agentic Models Without RL。

论文原文

这篇最值得读的地方不只是“49.2 比 48.0 高”，而是它挑战了 Agent Post-training 一个常见隐含前提：Policy 必须直接从成功 Action 或 Reward Advantage 学习。

建议 30 分钟重点看四件事：explanation-only loss 到底如何构造；mixed success / failure trajectory 为什么仍能产生有效学习；64 次 Base Sampling 全失败的任务为何后来能被学会；Retrospection 的内容变化怎样映射到后续 Action Frequency 与 Response Length。

最值得带走的判断是：

失败轨迹并非只有“0 Reward”。只要环境反馈足够具体，Agent 对失败原因的自我解释可以成为比稀疏终局 Reward 更密集的学习载体。

但它最需要防的也是解释本身：一旦模型学会了错误的自我因果故事，Self-retrospection 会从学习信号变成自我强化的偏差源。

今日可立即实践的一件事

给现有 Tool-Agent / Coding-Agent RL 数据做一个 Retrospection Value Audit，先判断失败轨迹里究竟有没有值得学习的密集信号。

选 50–100 个现有失败任务。每条保持完整 Action / Observation / Test Feedback，然后让当前模型生成结构化复盘，但不要立即用于训练：

1
2
3
4
5

1. 最早出现实质性错误的状态是什么？
2. 哪个动作直接改变了后续可达状态？
3. 当时有哪些已观测证据支持 / 反对该动作？
4. 如果只允许改一个动作，应该改哪个？
5. 用什么可执行检查验证这个判断？

随后做两层验证。

第一层是 Evidence Grounding：复盘中的文件路径、错误码、Tool Result、测试状态必须能回到原轨迹。

第二层是 Counterfactual Replay：只替换复盘指认的第一个关键动作，再从该状态继续 Rollout 2–4 次，看成功率是否真的提高。

建议至少记录：

指标含义
Grounded retrospection rate复盘是否忠于实际轨迹
Correct first-error localization是否找对第一个关键错误
Counterfactual repair rate替换动作后是否真的改善
Self-consistency多次复盘是否指向相似因果位置
Tokens per useful training target比 RL Rollout 更省还是更贵

停止条件： 如果模型复盘听起来很合理，但 Counterfactual Replay 经常没有改善，就不要直接做 explanation-only fine-tuning；这说明当前模型主要在“事后讲故事”，而不是定位可操作因果。

真正要回答的是：

失败轨迹对你的 Agent 来说，是没有 Reward 的废数据，还是一批尚未被提取出来的因果监督？

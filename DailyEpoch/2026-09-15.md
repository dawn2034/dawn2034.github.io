> **今日主线：** Reward-System Evolution · Subquadratic Serving · Repository Skills · Generative Recommendation Decode · Lifelong User Modeling · Autonomous Research

截至今天早上，arXiv 最新常规公告批次为 **2026 年 9 月 14 日**：`cs.AI` 167 条、`cs.CL` 64 条、`cs.LG` 158 条、`cs.IR` 18 条；不同分类存在大量交叉收录，不能直接相加。今天最值得连起来看的变化，是“模型之外的可学习系统”正在变得更重要：Reward 不再适合被视为训练开始前一次性写死的函数；Agent 的 SKILL 文档需要用真正行为提升而非文档质量来验证；Serving 拆分也需要跟着 sparse / linear attention 的算术强度重画边界。推荐侧的两个新信号同样很系统化：大 beam 解码开始复用共享状态，超长用户历史则被压成可缓存、带时间锚点的用户状态。

## 今日核心判断

1. **开放式 RL 里，Reward System 本身正在成为需要随 Policy 一起演化的状态。** EvoRS 不只动态改 rubric，而是把 criteria、scoring mechanism 与多路信号组合统一成可执行 Reward-DAG；每隔若干训练步，用最新 on-policy rollout 诊断 reward hacking、coverage failure 与 signal saturation，再通过 matched replay 只接受真正修复问题的候选 Reward-DAG。Writing 与 roleplay 上，相对对应 policy 分别提升 2.107 和 4.767 points。最值得关注的不是这两个数字，而是“奖励可靠性会被优化过程本身逐步破坏”这一训练系统事实。

2. **Subquadratic Attention 会改变异构 Serving 的最优切分边界。** SQD 不再沿传统 attention-vs-FFN 切 decode，而是按 quadratic 与 subquadratic attention 的不同内存／算术特性拆分：sparse attention 把需要扫完整 KV 的 top-k selection 与后续 top-k attention+FFN 分开，linear/sliding-window 则把 dense attention layer 与 subquadratic layer+FFN 分开。8×B200 调整后的异构代理系统中，GLM 5.2、Nemotron 3 Ultra、Gemma 4 31B 的 tokens/J 分别提高 53%、31%、56%。但 Rubin+LPX 的最高 3.6× throughput 仍来自分析模型，不是量产硬件实测。

3. **Agent Skill 文件“写得像专家”不等于真的让 Agent 更强。** `Skill Issue` 用历史 merged PR 反向构造困难修复任务，并直接比较同一个 Coding Agent 在“有 SKILL / 无 SKILL”条件下的成功差异。三个 Kotlin 仓库上 GEPA 生成的文档平均 +4.9pp，SkillOpt 只有 +0.1pp；更关键的是，+4.9pp 在当前样本量下仍无法与 run-to-run variance 分离。这个负结果很重要：优化文档可读性、事实数量、CodeBLEU，甚至 token 成本，都可能选择出看起来很好、却不改善 Agent 行为的 SKILL。

4. **Generative Recommendation 的大 Beam 解码有一个很明显却此前没被充分利用的结构：绝大多数状态其实共享。** OneLA 让所有 beam 共用一个 prompt-derived recurrent state，只为短暂分叉后的 suffix 保存 compact append-only transition record，再用 ancestry index 描述每条 beam 的历史，而不是给每个 beam 复制完整 recurrent state。论文报告 1.54–2.46× end-to-end decode speedup。它的价值不只在一个 kernel，而是把“beam state”从复制对象改成共享基底 + 差分日志。

5. **超长用户行为建模正在从 candidate-dependent retrieval 转向可复用的 user-only state。** ChronicleRec 通过 recency-aware multi-granularity merge 保留近期细粒度、远期逐步粗化，再把 query token 插入时间轴，用 causal encoder 生成 chronologically ordered Chronicle Tokens。由于这些 token 与候选 Item 无关，可以按用户缓存，把 lifelong history modeling 从在线 candidate scoring 中拆出来。KuaiRand 与 Tencent AdLive 上接近 full-attention 效果，并给出 7 天线上 A/B 正向结果，但摘要没有披露统一 effect size，因此当前更应关注其状态设计而非放大线上幅度。

6. **“自动 AI 研究员”在开放问题上的现实边界，比榜单式 Demo 更值得看。** Telecom ticket retrieval 的案例中，autonomous research 在 10 周内达到人工 SOTA 的 90%（Recall@1 0.34 vs 0.38），而人工工作周期约 10 个月，单次 Cursor campaign 最高成本约 \$200；同时作者明确报告，它更擅长窄范围 HPO，仍缺少人类式研究直觉与创造性，并存在明显的运行与组织开销。当前更合理的定位是自动实验与搜索放大器，而非独立研究者替代品。

## 1. EvoRS：Reward 也会被 Policy“做穿”，所以 Reward System 需要演化

**原始来源：** [EvoRS: On-Policy Self-Evolution of Reward Systems for Open-Ended Reinforcement Learning](https://arxiv.org/abs/2609.12459)

### 发生了什么

数学、代码这类任务往往有比较清楚的 verifier；写作、角色扮演、办公 Agent 等开放任务只能依赖 rubric、LLM Judge 或 Generative Reward Model。问题在于，Reward 并不是一个静态测量仪器：Policy 持续优化它以后，会逐步暴露 Reward 的盲点，甚至学会在“满足评分器”与“满足真实目标”之间寻找缝隙。

EvoRS 将这种失效拆成三类：**Validity**——出现 reward hacking；**Coverage**——新出现的 on-policy response 不再被现有 rubric 覆盖；**Informativeness**——同一 query 下的 reward 越来越饱和、区分度下降。作者因此把完整 Reward System 表示成一个可执行 `Reward-DAG`，节点不仅包含评价 criterion，也包含连续打分、checklist、penalty、pairwise 等不同 scoring mechanism，以及多路信号最终怎样组合成 RL scalar。

训练过程中，Agentic Designer 周期性读取最新 on-policy rollouts 与 reward traces，只生成**有边界的候选修改**；随后对当前 Reward-DAG 与候选 Reward-DAG 在同一批 recent cases 上做 matched replay。只有候选能够修复目标 failure，同时保持已有有效 reward behavior，才替换当前状态；没有更好的候选时直接 no-op。

### 关键结果

Writing 与 roleplay 两个开放任务上，EvoRS 在三种独立 judge 下都得到最高最终质量，相对对应 policy 分别提高 **2.107** 与 **4.767 points**。论文同时报告 reward-hacking rate 和 coverage-failure rate 下降，组内 reward 的可区分性保持得更久。

真正更值得记住的 ablation 是：即使一开始构造一个很复杂、覆盖面很广的固定 Reward System，随着 Policy 继续优化，它仍会逐步失效。换句话说，问题并不只是“初始 rubric 写得不够好”。

### 为什么重要

这给开放式 RL 一个更接近真实训练的闭环：

```text
Policy rollout
→ Reward-DAG 打分
→ Policy 更新
→ 新 on-policy 分布暴露 reward failure
→ 生成受限 Reward-DAG patch
→ matched replay 验证
→ 接受 / 拒绝
→ 下一阶段 Policy 更新
```

在 Tool Agent、Search Agent 或企业 Workflow RL 中，这可能比单纯“不断生成新 rubric”更一般，因为失效点经常位于 score aggregation、penalty 设计和可验证信号的组合，而不只在自然语言 criterion。

### 可信度与局限

证据目前集中在 writing 与 roleplay，仍依赖 LLM Judge，不能把“Reward-DAG 自演化”直接等价成奖励已经客观正确。Designer 与 candidate selection 本身也可能引入新的 meta-overfitting：如果 matched replay 样本太窄，Reward System 仍可能只是在追逐最近一批 Policy 行为。

另一个现实成本是，Reward evolution 需要额外 replay、诊断和 Judge inference；论文证明的是质量与训练可靠性收益，不代表整体 GPU / token cost 一定更低。

### 最值得继续追踪

最值得看 EvoRS 是否能迁移到 **Tool-Agent RL / Search-Agent RL**：例如把 executable verifier、LLM Judge、trajectory-level rubric 与 step-level penalty 统一进 Reward-DAG，并检查 Reward evolution 是否真的改善长期训练稳定性，而非只提高最终 benchmark。

## 2. SQD：Subquadratic LLM 需要重新设计 Serving 拆分方式

**原始来源：** [Rethinking Heterogeneous System Disaggregation for Subquadratic Attention](https://arxiv.org/abs/2609.13134)

### 发生了什么

传统 P/D disaggregation 和 attention–FFN disaggregation 大多以 dense Transformer 为默认对象。随着 sparse attention、linear attention、sliding-window attention 大量进入新模型，同一个 decode step 内不同模块对 HBM 带宽、容量、算力和互联的需求已经明显分化。

SQD 的核心观点是：**系统切分边界应该跟着 attention complexity 走，而不是继续沿算子类别机械切分。** 对 sparse attention，top-k selection 仍需要索引完整 KV，属于大容量、低算术强度部分；真正的 top-k attention 与 FFN 则拥有相对静态的小工作集。对 linear / sliding-window 模型，则把 dense attention layers 与 subquadratic layers+FFN 分配到不同计算层级。

### 关键结果

| 模型 | 8×B200 异构代理系统 tokens/J 提升 |
|---|---:|
| GLM 5.2 | **+53%** |
| Nemotron 3 Ultra | **+31%** |
| Gemma 4 31B | **+56%** |

在固定功耗预算的 Rubin + LPX 分析模型中，SQD 相对最强 attention–FFN disaggregation baseline 得到 **1.2–1.5× 更紧的可达 latency**，吞吐最高 **3.6×**。

### 为什么重要

近期模型架构越来越混合：dense attention、sparse attention、linear recurrence、MoE、不同精度 KV 可能同时存在。未来 Serving scheduler 如果仍把“一个模型”当作一个均质算力需求，很容易把昂贵 HBM GPU 留给并不需要它的部分。

更一般地说，模型架构创新正在反向推动系统拓扑设计：**哪一层应该驻留在哪种 memory hierarchy、哪一步需要全 KV、哪一步只需要静态小状态**，会比“统一在一类 GPU 上跑所有算子”更重要。

### 可信度与局限

这里必须把实测与预测拆开。53% / 31% / 56% tokens/J 来自**调整后的 8×B200 heterogeneous system proxy**；最高 3.6× throughput 则来自 Rubin + LPX 的 analytical model。它们提供了强系统设计信号，但还不是未来 Rubin/LPX 集群的生产实测。

此外，细粒度 disaggregation 会增加跨设备同步、调度和数据搬运；真实收益高度依赖 batch、上下文长度、网络拓扑和模型的 dense/subquadratic layer 比例。

### 最值得继续追踪

看 vLLM、SGLang、TensorRT-LLM 是否开始显式建模 hybrid-attention layer type，并报告真实的 `tokens/J × TTFT × TPOT × interconnect traffic`。如果架构越来越 heterogeneous，Serving runtime 很可能也需要从 request scheduler 升级为 layer / phase-aware scheduler。

## 3. Skill Issue：SKILL.md 的真正评价指标只能是“Agent 行为有没有变好”

**原始来源：** [Skill Issue: Lessons from Optimizing Repository SKILLs for Coding Agents](https://arxiv.org/abs/2609.12742)

### 发生了什么

Repository-level Coding Agent 越来越依赖 `SKILL.md`、`AGENTS.md` 一类随代码版本化的知识文件。近期一条热门路线是让另一个 Agent 自动生成、反复改写这些文档，再在合成任务上优化它们。

论文指出一个基础评测漏洞：如果 synthetic task 太容易，强 Coding Agent 在**没有文档**时已经饱和，那么“优化后的 SKILL 在任务上分数很高”无法说明文档真正有用。作者改为从历史 merged PR 中构造 reverse-PR tasks：在一个冻结 base commit 上逆向撤销 PR 所修复的变化，让真实历史 bug / feature 重新出现，再比较同一个 Agent 有文档和无文档的配对差值。

### 关键结果

三个 Kotlin repository 上：

- GEPA 优化后的 SKILL：相对 seed 平均 **+4.9pp**；
- SkillOpt：仅 **+0.1pp**；
- 维护者主观上认为文档包含“只有真正做过项目才会知道”的 repo knowledge；
- 但 **+4.9pp 在当前任务数下仍无法和 Agent run-to-run variance 统计分离**。

更有价值的是失败目标：优化写作质量、仓库事实数量、与原 PR 的 CodeBLEU，甚至 token cost，都可能选出对 Coding Agent 实际修复成功率没有帮助的文档；纯 cost objective 甚至可能偏好空文件。

### 为什么重要

Agent Skill 生态正在快速扩张，但 Skill 是一种**控制系统输入**，不是普通文档。它的质量不能由“另一个 LLM 觉得写得好”来定义，而必须通过行为反事实来定义：

$$
\Delta_{skill}=P(\text{success}\mid\text{skill})-P(\text{success}\mid\text{no skill}).
$$

而且最好在同一个冻结 repo、同一组 executable tests、同一个 Agent 上配对测量。

### 可信度与局限

这项工作的结论非常克制，也是它最值得读的地方。只有三个 Kotlin/JVM repository，样本量不足，作者没有把 4.9pp 包装成确定收益。反过来，这也意味着目前还不能得出“自动 Skill 优化没有用”的结论；更准确的结论是：**现有 repo history 很可能不足以精确测量几个百分点的真实 uplift。**

Skill 的作用还可能强依赖模型与 Harness。某份文档对 Agent A 有效，不代表升级到 Agent B 后仍有效。

### 最值得继续追踪

最值得建立的是 repo-level Skill CI：每次 SKILL 更新都在一组冻结的 historical tasks 上做 paired evaluation，并长期记录 effect size 与置信区间。模型升级时也要重新验证，避免把旧模型专用的提示习惯误当成永久 repo knowledge。

## 4. OneLA：大 Beam 推荐解码应保存“差分状态”，而不是复制整个状态

**原始来源：** [OneLA: Scaling Linear-Attention Decoding to Large Beams in Generative Recommendation](https://arxiv.org/abs/2609.12399)

### 发生了什么

Generative Recommendation 往往需要 beam search 一次产生数百个 Item candidate。对 recurrent linear attention 来说，每个 beam 都拥有一个 recurrent state；最直接的实现要么为每个 beam 复制完整状态，要么每次从共享 prefix 重新 replay，二者都会造成显存和内存流量浪费。

OneLA 利用 GR workload 的特殊结构：所有 beam 有很长的共同 prompt，而真正不同的只有很短 suffix。系统只保留**一个共享 prompt-derived state**，每次 beam 分叉只追加 compact transition record；ancestry index 负责记录“某条 beam 由哪些 transition record 组成”，无需搬移旧状态。GPU fused kernel 再批量复用共享 state。

### 关键结果

论文报告 **1.54–2.46× end-to-end decode speedup**，同时显著减少 recurrent-state memory 与 data movement。这里的 headline 是完整 decode 加速，不只是一个孤立 kernel microbenchmark。

### 为什么重要

它提供了一个很通用的状态系统设计：

```text
长共享历史
+ 小量分叉增量
→ shared base state
+ append-only delta log
+ ancestry / version index
```

这与 copy-on-write、persistent data structure 很相似。Generative retrieval、tree search、multi-candidate planning 乃至某些 Agent branch rollout 都可能出现同样结构。

### 可信度与局限

OneLA 的收益高度依赖“大共享 prefix + 短分叉 suffix + 大 beam”这一 GR 负载；普通聊天 decode、beam 很小的任务不会得到同样收益。论文也围绕 recurrent linear attention，而非标准 dense softmax attention KV cache。

系统复杂度会转移到 ancestry management、fused kernel 和动态 beam scheduling；生产系统仍需要观察 beam pruning 与 batching 后的真实增益。

### 最值得继续追踪

看这套 delta-state representation 是否会进入大规模 generative recommender serving，以及它与 speculative decoding、candidate pruning 和 semantic-ID tree constraint 能否联合优化。

## 5. ChronicleRec：把超长用户历史压成“带时间锚点、可缓存”的用户状态

**原始来源：** [ChronicleRec: Pre-training Temporally Anchored Tokens for Lifelong User Modeling](https://arxiv.org/abs/2609.12375)

### 发生了什么

工业推荐里最贵的一类长序列方案，是针对每个 candidate 都重新从数万历史行为中挑选 target-relevant events。候选越多，历史建模就被重复做越多次。Target-independent compression 可以缓存用户摘要，但不少现有方法把一组 query token 统一放在序列末尾，再双向编码，容易生成时间顺序弱、彼此冗余的 summary token。

ChronicleRec 用 recency-aware multi-granularity merge：近期行为保留更细，越久远的历史越粗；随后把 query tokens **插入时间轴中的不同 anchor**，采用 causal encoder，保证每个 query 只能总结其 anchor 之前的历史。多个 branch 再屏蔽不同长度的近期窗口，迫使它们学习互补的 long-term signal。

训练时，用压缩后的旧历史预测被 hold out 的近期行为，使 summary 更贴近当前兴趣。最终 Chronicle Tokens 与当前 candidate 无关，因此可以按用户提前计算和缓存。

### 关键结果

KuaiRand 与 Tencent AdLive 上，ChronicleRec 优于 recent-window 与 single-pass compression baseline，并接近 full-attention 质量；论文还报告了 **7 天线上 A/B 的显著正向结果**。摘要没有给出一个统一可复述的线上 uplift 数字，因此这里不人为拼一个 headline effect size。

### 为什么重要

它与近期 SequenceO1 一类工作共同指向一个稳定的工程模式：

> **凡是只依赖用户历史、不依赖当前候选的昂贵计算，都应尽量变成可版本化、可缓存的 user state。**

真正 target-conditioned 的交互只发生在这个压缩状态和当前 candidate 之间。这样，超长历史的成本可以按“用户状态刷新次数”而不是“候选数 × 请求数”计费。

### 可信度与局限

目前公开线上结果来自单一工业场景，外部无法复现其数据和 Serving stack。压缩又天然引入 freshness trade-off：缓存越久越省算力，但越可能错过用户兴趣突变。

Chronicle Token 还属于 learned summary；如果早期压缩丢掉某个将来突然重要的长尾兴趣，后续 candidate scorer 无法恢复原始历史。

### 最值得继续追踪

建议关注 `cache hit × refresh interval × active-user bucket × cold-interest recall`，以及增量更新是否可以避免每次重算完整 lifelong history。长期看，这类 user-state cache 很可能和在线 feature store / embedding cache 融合。

## 6. Autonomous Research：开放问题里，Agent 目前更像高吞吐实验工程师

**原始来源：** [Autonomous Research for Open-Ended Problems: A Case Study on Telecom Ticket Retrieval](https://arxiv.org/abs/2609.13073)

### 发生了什么

很多“AI Scientist”展示集中在搜索空间相对规整的问题：给定 benchmark、固定 metric、有限模型家族，Agent 负责提 proposal、改代码和跑实验。Telecom ticket retrieval 刻意选择更开放的工业问题：表示方式、架构、训练数据构造都存在大量自由度。

作者让商业与开源 Agent 做长期 research campaign，并和人工研究过程比较。结果很有代表性：Agent 能快速执行大量 narrow optimization，却仍明显依赖人类定义研究方向、识别值得探索的结构变化，并处理复杂运行故障。

### 关键结果

系统在约 **10 周**内达到 **Recall@1 0.34**，约为人工 SOTA **0.38 的 90%**；对应人工研究周期约 **10 个月**。单次 Cursor campaign 的报告成本最高约 **\$200**。

同时作者明确指出两类短板：缺少 human-like intuition / creativity，以及不可忽略的 operational overhead。因此这篇论文并没有支持“AI 已独立替代 ML researcher”的结论。

### 为什么重要

它给“自动研究”提供了比 demo 更有用的组织边界。短期最适合自动化的部分是：

- 小范围架构与超参搜索；
- 可执行实验的批量运行；
- 日志与结果聚合；
- 已知方向上的局部变体搜索。

人类更高价值的部分仍集中在：定义问题、提出新的表示／假设、识别实验为什么失败，以及决定何时放弃当前搜索空间。

### 可信度与局限

这只是一个 telecom retrieval case study，10 周 vs 10 个月不能被解释成“研究效率普遍提高约 4×”。两条路径的人员配置、实验预算和搜索历史也并非严格 matched control。

0.34 vs 0.38 说明 autonomous pipeline 已经能逼近强结果，同时也恰好说明最后一段 gap 可能最依赖真正的新想法，而不是更多局部实验。

### 最值得继续追踪

未来报告应同时给出 `有效实验数 / 总实验数、每个有效改进的人类干预次数、GPU/token 成本、被人类采纳的 idea 比例、最终 merge / production rate`。只统计“Agent 跑了多少实验”会系统性高估研究进展。

## 今日值得收藏的代码 / 学习资源

### Recommendation Retrievers Need Verifiers

[论文原文](https://arxiv.org/abs/2609.12270)

这篇适合做多阶段推荐的人精读。它把 first-stage retriever 与 downstream ranker 之间的一个常见损失单独拿出来处理：相关 Item 可能已经在 retriever 的较深位置，却没有进入真正被 ranker 消费的短 prefix。作者训练一个 post-hoc generative verifier，只对 retriever top-K candidate 根据 identifier-token likelihood 重新打分，无需重训 retriever，也不需要在训练时做 sampled negatives。Amazon 与 YaMBDa 上，同一 recipe 对 SASRec、GRU4Rec、NextItNet、MiniOneRec 都提升 Recall@10。摘要没有统一 effect size，因此更适合当“output-side adapter”思路看，而不是当新的 SOTA 数字看。

### LifeFuse-Mem

[论文原文](https://arxiv.org/abs/2609.12436)

长期 Agent Memory 很容易把“这次会话的临时状态”写成永久偏好或永久事实。LifeFuse-Mem 显式加入 lifecycle label，把 durable 与 transient state 放进不同 memory component，并采用 lifecycle-aware update，目标是减少 temporary overwrite。它在专门的 anti-overwrite benchmark 上改善 retention，在两个公开 long-memory benchmark 上保持竞争力。当前缺少大规模真实 Agent 的长期部署数据，但“Memory 写入必须带生命周期语义”本身很值得落地。

### CoTT：只在不确定时支付昂贵 Test-Time Compute

[论文原文](https://arxiv.org/abs/2609.12489)

Confidence-Gated Transductive Test Generation 先用便宜的 inductive procedure 生成代码 reranking tests；只有当这一步 confidence 低时，才调用更贵的 transductive generation。它在报告的代码重排 benchmark 上优于 baseline，同时比“每个输入都做 transductive generation”成本更低。这个结构比具体代码任务更通用：**廉价信号负责 early exit，昂贵推理只服务边界样本。**

## 今日最值得花 30 分钟阅读的一项

**首选 EvoRS。**  
[论文原文](https://arxiv.org/abs/2609.12459)

这篇最值得读的原因，是它把一个经常被训练工程忽略的问题显式化：**Reward 并不是 Policy 学习过程外部、永远不变的“真值测量器”。Policy 越擅长优化它，Reward 自己越可能失去 validity、coverage 或 informativeness。**

30 分钟建议按这个顺序读：先看作者如何定义三类 reward failure；再看 Reward-DAG 为什么同时表示 criterion、scoring mechanism 和 signal composition；重点看 matched replay 怎样在同一批 recent on-policy cases 上比较当前与候选 Reward System；最后看 fixed reward 的退化轨迹与各类 ablation。

真正值得带走的问题是：

> **你的 RL 训练曲线继续上涨时，Reward 还在测量原来的目标，还是 Policy 已经把它逐渐变成一个容易优化、却越来越没信息量的代理指标？**

如果这个问题没有监控，继续增加 rollout 或训练步数甚至可能让系统离真实目标更远。

## 今日可立即实践的一件事

给现有 **GRPO / Agent RL / LLM-Judge Reward** pipeline 加一个最小的 **Reward Drift Audit**。先不要做完整 Reward-DAG，只检查当前 Reward 在训练过程中有没有被 Policy 逐步“做穿”。

每隔固定 checkpoint（例如每 50–100 个 update），冻结一批最新 on-policy prompts，每个 prompt 采样多个 response，并记录：

```python
reward_audit = {
    "within_prompt_reward_std": [],
    "zero_signal_group_rate": 0.0,
    "external_judge_alignment": 0.0,
    "high_reward_failure_rate": 0.0,
    "reward_saturation_rate": 0.0,
}
```

重点看三个量。第一，同一个 prompt 的组内 reward 方差：

$$
V_q = \operatorname{Var}_{y\sim\pi(\cdot|q)}[R(q,y)].
$$

如果大量 group 的 $V_q$ 接近 0，Reward 对 Policy 已经几乎没有优化信息。第二，取最高 Reward 的样本交给一个独立 Judge / verifier，统计 **high-reward-but-failed** 比例；它上升通常比训练 reward 本身更早暴露 hacking。第三，在固定 replay set 上比较早期 checkpoint 与当前 checkpoint 的 reward ranking 是否仍与外部质量排序一致。

随后只做一个低风险 A/B：针对最明显的 failure，构造一个替代 scoring mechanism，例如把连续 1–10 分改成 `checklist + targeted penalty`，然后让**旧 Reward 和候选 Reward 在完全相同的 recent rollout 上离线重放**。只有候选同时降低 high-reward failure、且不把大多数 group 压成同分，才值得进入在线训练。

**停止条件：** 如果 Reward 方差稳定、独立 Judge alignment 没有随训练下降、high-reward failure 也没有增长，就没有理由仅因为新论文而引入复杂的自演化 Reward 系统。反过来，如果 Policy quality 看起来停滞、训练 reward 却继续上涨，同时 reward informativeness 明显下降，优先修 Reward 往往比继续调 GRPO clip、KL 或 rollout 数更有意义。

真正要回答的是：

> **你的训练现在缺的是更强 Policy Optimizer，还是一个已经不再可靠的 Reward System？**

今日主线： Read-Time Memory · Subtask Credit · Minimal Harness · Recurrent Working-Set · Agent Sandbox Infrastructure · Recommendation Recall Ceiling

arXiv 最新常规公告批次为 2026 年 9 月 24 日：cs.AI 295 条、cs.CL 163 条、cs.LG 310 条、cs.IR 32 条。分类之间存在大量交叉收录，不能直接相加。今天值得连起来看的变化，是 Agent 系统开始把过去被固定的基础设施层重新变成可设计对象：Memory 不一定要在写入时就不可逆地压缩；RL Credit 可以先按子任务拆开再进入 Policy Update；Harness 可能被压缩成极少数可递归的语言原语；Recurrent Model 的全局 Attention 也不必每一层都重新搜索。与此同时，Agent RL 的规模化开始被 Sandbox 生命周期、镜像、CPU 和状态恢复约束，推荐系统侧则出现一个很重要的负结果：如果上游 Recall 很低，再强的 LLM Reranker 也突破不了候选集的确定性上限。

今日核心判断

  1. Agent Memory 的最佳压缩时点可能应该延后到“读”的时候。 Just-in-Time Memory（JitMem）保留原始历史轨迹，只在新任务到来、相关轨迹已经被检索出来后，再根据当前任务生成紧凑的 task-adaptive payload。ALFWorld、WebShop、τ²-bench 上，相对最强写时 Memory 基线分别提高 16.2、16.3、3.9 个绝对成功率百分点；更关键的是，未训练 Curator 已经能匹配或超过多种写时方案。这个结果支持一个很强的工程直觉：如果未来用途未知，过早总结历史会永久丢失未来可能需要的信息。

  2. 多轮 Agent RL 是否需要更细 Credit，应先看任务内部的“子技能异质性”。 RLDS 把整条轨迹 Reward 按固定 Subtask Taxonomy 分解，再对每个子任务独立计算 Group-relative Advantage，并把 Token Credit 集中到被 Reflection 判定为真正有后果的步骤。ScienceWorld 提高 11.5 points、FrozenLake 提高 9.8 points，但 HotpotQA 和 DeepResearch 的增益落在噪声范围内。它给出了一个重要边界：Credit Decomposition 并不是普遍优于 Scalar GRPO，收益主要出现在一条轨迹同时包含多个相互不同技能、且最终 Reward 无法指出是哪一类能力出错时。

  3. 复杂 Agent Harness 的一部分功能可能可以退化成一个可递归的语言原语。 JAZ 只暴露一个 LLM Primitive：invoke。模型可以生成任意可执行代码，代码又可以递归调用 invoke，而模型能看到的一切都被表示为代码环境变量。没有手写 Memory System、Tool System 或 File-System Harness 的核心设置下，它在 StuLife 的长程 Recall 部分比 Letta 高 8%，成本约一半；在 AppWorld 的持续自我改进设置上比 ACE 高 4%，且成本更低。这个结果还不足以证明“一个 invoke 可以替代所有 Agent Infrastructure”，但它把 Harness Design 的问题重新表述为：哪些能力确实需要独立系统，哪些只是通用程序控制结构的特例。

  4. Recurrent / Looped Model 的 Attention Search 可能只需要在早期 Recurrence 完整执行。 WISE 观察到，Attention Support 和 Distribution 通常比 Hidden State 与 Attention Output 更早稳定，因此前若干步先用全局 Attention 找到一个 Working Set，后续 Recurrence 只复用这个 Block Support，同时保留动态 Q/K/V 和 Support 内 Attention。4K 上 Sparse Attention 最快比原生 FlashAttention 高 1.76×，完整 32-step Attention Trajectory 为 1.36×；不过质量在 2K 前基本保持，4K 已出现可测损失。它说明 Recurrent Depth 的后续计算可能更像“在已发现证据上继续推理”，而不是不断重新搜索全部 Context。

  5. Agent RL 的下一类基础设施瓶颈，已经是几十万并发的 Stateful Sandbox。 DeepSeek DSec 在统一 SDK 下提供 FnCall、Container、microVM 和完整 VM，并与 RL Framework 联合管理可抢占训练下的 Rollout State。一个生产单元约 160 个节点，每天服务约 300 万个 Sandbox；生产峰值超过 38 万并发、每秒超过 5,000 次创建。其监控还显示约 90% 的 Container / microVM 平均只用不超过申请 CPU 的 5%，而中位生命周期又在 15–17 分钟。这意味着 Agent Training 的成本优化已经不能只盯 GPU Utilization，Sandbox 的过量申请、状态保留、镜像加载与恢复会直接决定 RL 能否继续放大。

  6. LLM Recommendation Reranking 的首要问题可能根本不在 Reranker。 一项 CIKM 2026 Oral 工作指出，三组 Amazon 数据中，把 Ground Truth 强行注入候选集的 Oracle Protocol 会把真实 NDCG@10 高估 92%–95%；在 8 个数据集上，现实 Retrieval@100 只覆盖 2%–19% 的相关 Item。闭合候选 Reranker 满足确定性 Recall Ceiling，因此在这些低 Recall 区间里，Prompt、168× Model Scaling、LoRA、Neural Reranker、Hybrid Retrieval、LLM+CF Fusion 都没有在主要 Amazon 设置上显著超过 CF Baseline。对推荐研究来说，这个负结果比再多一个更复杂 Reranker 更重要：先确认候选集里有没有答案，再讨论重排能力。

1. Just-in-Time Memory：Memory 应该在知道“现在要做什么”以后再压缩

论文原文：Just-in-Time Memory

发生了什么

大多数 Agent Memory 在任务结束时立即把轨迹压成 Reflection、Workflow、Skill 或 Reasoning Summary。问题在于，写入时系统还不知道未来会遇到什么 Query，却必须提前决定哪些细节值得保留；一旦删掉，未来检索也无法恢复。

JitMem 反过来保存 Raw Trajectory。新任务到来后，系统先检索相关历史，再让 Curator 根据“当前任务 + 被检索轨迹”生成一份只服务于这一次决策的紧凑 Memory Payload。因为 Curator 的输出立刻被同一任务消费，它可以直接用当前任务成败训练，不再需要等待很多任务以后才能知道某次 Memory Write 是否有价值。

关键结果

Benchmark相对最强基线的绝对成功率提升
ALFWorld+16.2pp
WebShop+16.3pp
τ²-bench+3.9pp

论文还强调，未训练的 Read-time Curator 已经能与多种写时 Memory 方法竞争或更好；训练 Curator 后继续提升。这说明收益并不完全来自额外学习，而是来自“等 Query 出现后再决定保留什么”这一时序设计。

为什么重要

写时 Memory 实际上做的是一个不可逆压缩：

\[m = f(\tau),\]

它必须假设未来所有 Query 都需要同一份摘要。Read-time Curation 则变成：

\[m_q = g(q, \tau_1,\tau_2,\ldots),\]

同一历史可以因为当前任务不同而生成不同 Memory View。这和数据库里的 Late Materialization 很像：在不知道最终 Consumer 需要什么时，保留较原始的数据通常更灵活。

可信度与局限

保留 Raw Trajectory 会把成本转移到存储、检索与读时 Curation。随着历史增长到数月甚至数年，完全保留所有原始轨迹并不现实；如果 Retriever 本身没召回关键历史，Read-time Curator 也无从恢复。

因此更合理的生产结论不是“永远不要写时压缩”，而是区分两类信息：可确定无损抽取的稳定事实可以写时结构化；含义依赖未来任务的过程性经验应尽量晚压缩。

最值得继续追踪

最值得看的是 Hybrid Memory：Raw Trace 保存一定窗口，长期层只做事实化与去重；查询时根据任务把两者重新组合。需要联合报告 Task Success、Raw Storage、Retrieval Tokens、Curation Tokens 和 End-to-end Latency，而不是只看 Memory QA 准确率。

2. RLDS：把 Reward 分解到子任务，再决定哪里值得给梯度

论文原文：Reinforcement Learning with Decomposed Subtasks

发生了什么

GRPO 把一整条多轮轨迹折叠成一个 Scalar Reward，再把这一信号广播回整条 Response。对于多技能 Agent，这会把完全不同的错误混在一起：检索错、工具选择错、参数错、环境解释错，最终可能都得到同一个 0。

RLDS 先建立固定 Subtask Taxonomy，把总 Reward 分成不同子任务份额。SDAE 对每个 Subtask 独立计算 Group-relative Advantage，再根据该子任务在某一 Step 是否真正产生后果，把 Credit 集中到相应 Token 附近。

关键结果

BenchmarkRLDS 相对 Scalar GRPO
ScienceWorld+11.5 points，95% CI [+9.8, +13.3]
FrozenLake+9.8 points，95% CI [+7.0, +12.8]
HotpotQA处于噪声范围
DeepResearch处于噪声范围

ScienceWorld 中 RLDS 的每步 Wall-clock 还降低 10.9%：长轨迹足以摊薄固定的 Reflect-and-grade 开销。

为什么重要

这篇论文很有价值的一点，是它没有声称“更细 Credit 永远更好”。作者用训练期 Heterogeneity Diagnostics 解释收益：如果一条任务由多个相互不同的技能组成，而不同 Rollout 的失败又集中在不同技能，Scalar Reward 才真正丢失大量信息。

因此更实用的决策规则是：

先量化任务内部的 Subtask Heterogeneity，再决定是否值得引入更复杂 Credit Assignment。

可信度与局限

RLDS 依赖固定 Taxonomy 和 Reflection 去判断哪个步骤与哪个子任务相关。Taxonomy 设计错误时，系统只是把一个粗糙 Reward 换成多个可能同样粗糙的 Reward。

HotpotQA 与 DeepResearch 没有显著收益也是重要负结果：复杂的 Credit 系统增加实现与评估成本，不应默认成为所有 Agent RL 的基础配置。

最值得继续追踪

可以进一步看自动发现 Subtask Taxonomy 是否可靠，以及它与 Critical-State Selection、OPD Teacher Gating 是否互补。理想情况下，系统先判断“哪类技能出了问题”，再判断“具体哪个状态值得更新”。

3. JAZ：Harness 能不能被压缩成一种语言？

论文原文：Harness as a Language

发生了什么

JAZ 尝试把 Agent Harness 退回到一个非常小的核心：单一 LLM Primitive invoke。它有两个关键性质：模型可以写任意可执行代码，并在代码里递归调用 invoke；所有给模型可见的输入、历史和环境状态，都作为代码环境中的变量存在。

研究者用这个最小原语去实现通常需要外部系统支持的流程，包括超出 Context Window 的长期 Recall 和 Continual Self-improvement，而核心实验不依赖人工设计的 Memory、Tool 或 File-System Harness。

关键结果

论文摘要报告：

  • StuLife 的 Recall-heavy Long-horizon 任务中，比 Letta / MemGPT 高 8%，成本约一半；
  • AppWorld Continual Self-improvement 中，比 ACE 高 4%，且成本更低。

为什么重要

它把一个常见 Agent 架构问题翻转了。通常我们会不断加入 Planner、Memory Manager、Skill Router、Sub-agent Manager、Context Compactor；JAZ 则问：

这些组件有多少本质上只是“程序可以递归调用一个语义函数”的不同表现形式？

如果通用代码控制可以表达多数高层 Workflow，那么 Harness 的长期方向可能更接近一种小型 Agent Programming Language，而不是不断增加特殊组件。

可信度与局限

“最小 Harness”不等于系统复杂度消失。复杂性被移动到了模型生成的代码、Runtime、Sandbox 与 Monitoring 中。真实生产环境仍需要权限、事务语义、资源限制、审计和 Side-effect Control，这些不能靠递归 invoke 自动获得。

当前对照也集中在几个特定 Benchmark，8% / 4% 的结果不足以证明 Letta、ACE 一类专门系统总体失去价值。

最值得继续追踪

看 invoke 这种 Primitive 能否在固定安全边界下稳定表达 Browser、Shell、Database 与 Multi-agent Workflow，以及当模型能力下降到 4B–14B 时，极简 Harness 是否仍然成立。Minimalism 很可能和 Model Capability 强相关。

4. WISE：Recurrent Model 先“找证据”，后面只在 Working Set 上继续算

论文原文：Attention Routing Stabilizes Early · 官方代码

发生了什么

Recurrent / Looped Language Model 会反复执行共享 Block。通常每一次 Recurrence 都重新对完整 Context 做 Attention，但作者发现 Attention Support 与 Distribution 往往比 Hidden State 和最终 Attention Output 更早稳定。

WISE 因此把 32 个 Recurrent Step 分成两个阶段。默认设置中，1–12 步继续做完整 Global Attention，并在 9–12 步累计发现 Block-level Working Set；13–32 步保持这个 Support 不变，但 Q/K/V、Hidden State 和 Support 内部 Attention Weight 仍然动态更新。

关键结果

设置结果
4K Late-reuse Attention Workload1.76× vs native FlashAttention
完整 32-step Attention Trajectory1.36×
HotpotQA N=100Full 0.2263 F1；WISE 0.2317
2WikiMultihopQA N=100Full 0.2516；WISE 0.2497

论文同时明确指出：质量基本可以维持到 2K Context，4K 已出现可测的损失。因此目前的收益还不能直接外推到 128K / 1M 的真正长上下文。

为什么重要

近期 Recurrent Depth 工作常讨论“什么时候停止迭代”。WISE 提供另一个维度：即使不停止 Recurrence，也可以停止重新搜索全部 Context。

这形成一种两阶段推理图景：

1
2

early recurrence: discover evidence
late recurrence: refine over discovered evidence

对于 Agent 场景，这和人类工作方式很像：前期在日志、代码和文档中找相关区域，后期主要围绕已确定的证据做更深推理。

可信度与局限

1.76× 是 Attention Kernel 的局部加速；完整 32-step Attention 只有 1.36×，而完整模型 End-to-end 收益还会更低。Working Set 固定以后，也存在“后期才需要一个早期没选中的证据”的风险。

当前 Context 长度和任务规模仍小，不能把它解读成 Recurrent Model 的长上下文问题已经解决。

最值得继续追踪

最关键的是让 Working Set 支持“重新打开全局搜索”：只有当内部状态显示当前 Support 不足时，才重新执行一次 Full Attention。它与 On-Demand Attention、KV Tiering、Recurrent Early Exit 很可能可以组合成统一的动态计算策略。

5. DeepSeek DSec：Agent RL 的瓶颈正在从 GPU 训练扩展到 Sandbox Fabric

论文原文：DeepSeek Elastic Compute

发生了什么

大规模 Agent RL 不只需要模型 Rollout，还要同时创建大量拥有真实文件、工具、网络和进程状态的执行环境。DSec 把 FnCall、Container、microVM 和完整 VM 统一到同一个 SDK 下，并负责 Placement、Lifecycle、可组合环境层、内存回收、CPU 调度和按需镜像加载。

它还与 RL Framework 联动：GPU Training 可以被抢占，而 Stateful Rollout 对应的 Sandbox 被挂起、恢复，避免每次重新搭环境；同时用访问控制与隔离处理 Agent 可能出现的越权和 Reward Hacking。

关键结果

生产指标DSec
单个生产单元约 160 节点
每日 Sandbox约 300 万
并发 Sandbox>380,000
创建吞吐>5,000 / s
Container / microVM 平均 CPU 利用约 90% 样本不超过申请量 5%
Median LifetimeContainer 17.4 min；microVM 15.5 min
p99 Lifetime两类均 >3h

论文还报告，生产周内活跃镜像工件超过 130 TB，而不同语言 Container 实际运行时只读取镜像数据的约 4.2%–13.3%。这解释了为什么“完整拉取镜像 + 为每个 Sandbox 按申请量保留资源”在 Agent RL 下很快失效。

为什么重要

过去 Agent RL Infrastructure 的主角是 GPU Scheduler、Rollout Engine 和 Parameter Synchronization。DSec 说明一旦训练进入 Tool / Computer-use 环境，CPU、Memory、Image Distribution、Stateful Resume 和 Isolation 会成为同等级约束。

尤其是平均 CPU 使用率极低、但 Sandbox 生命周期很长这一组合，意味着系统必须安全地 Overcommit；否则训练集群会被“看上去申请了很多、实际上长期闲置”的执行环境吃光。

可信度与局限

这是 DeepSeek 自己的生产系统报告，规模数字来自建设方，外部没有等规模第三方复现。它也不是一个独立可直接部署的开源产品，因此很多收益高度依赖 3FS、内部 RL Framework 和集群架构。

更重要的是，380K Concurrent Sandboxes 是 Capacity 指标，不等于每个环境都在做高强度 Tool Compute。

最值得继续追踪

看 Agent Training Stack 是否开始形成类似 Kubernetes 的标准 Sandbox Control Plane：Environment Manifest、State Snapshot、Network Policy、Resource Profile、Verifier 与 Rollout ID 全部可追踪。未来优化目标可能会从 GPU samples/s 转成真正的 verified agent trajectories per dollar。

6. Recall Ceiling：先检查 Retrieval 上限，再研究 LLM Reranker

论文原文：The Recall Ceiling of LLM Recommendation Reranking

发生了什么

很多 LLM Recommendation Reranking 工作会把 Ground-truth Item 人为放进候选集，再让模型与若干 Negative 比较。这样测到的是“答案已经在桌上时，LLM 能不能把它挑出来”，却绕过了真实系统最难的一步：召回阶段是否真的把答案带进候选窗口。

这篇 CIKM 2026 Oral 工作用现实 Retrieval 重新评估该问题，并给出闭合候选 Reranker 的上限：

\[\mathbb{E}[\mathrm{NDCG}@k] \le \mathrm{Recall}@|W_\pi|,\]

其中 $W_\pi$ 是 Reranker 实际能看到的候选窗口。

关键结果

三组主要 Amazon 数据上，Oracle Candidate Protocol 会把现实 NDCG@10 高估 92%–95%。跨 8 个数据集、3 个 Domain，现实 Retrieval 在 K=100 时只覆盖 2%–19% 的相关 Item。

在作者测量到的这些低 Recall 区间里，Prompt Engineering、跨 168× 参数规模扩展、Sequential Model、Supervised Neural Reranker、LoRA、Hybrid Retrieval、Score-aware Prompt 和 LLM+CF Fusion 都没有在主要 Amazon 设置上显著超过 CF Baseline。

为什么重要

这直接触及推荐研究里一个很常见的评估错位：

2
3
4
5

Reranker 很强
×
候选集里没有正确 Item

如果候选 Recall 已经构成主瓶颈，再增加 Reranker 参数、Reasoning 或训练技巧，只是在优化一个不会决定系统上限的阶段。

可信度与局限

作者自己明确限定了结论边界：生产系统如果拥有更高 Recall、更丰富特征、在线反馈和更大候选窗口，Reranker 仍可能产生显著价值。因此不能把这篇论文简化成“LLM 不适合推荐排序”。

更合理的结论是：先报告 Retrieval Regime，再解释 Reranker Gain。 没有候选 Recall，上层 Ranking 指标很容易被 Oracle Protocol 误导。

最值得继续追踪

推荐评测最好同时报告 Recall@CandidateWindow、Oracle Reranker Ceiling、实际 Reranker NDCG 和端到端 Online Metric。对 Generative Recommendation 也同样如此：如果 Decoder / Semantic ID 的搜索空间实际被早期 Beam 截断，上层模型同样存在隐性的候选上限。

今日值得收藏的代码 / 学习资源

HySparse2：MiMo-V3 计划采用的两级 KV 共享架构

论文原文

HySparse2 是今天跨中文技术圈和模型架构讨论中最明显的新信号之一。它把模型分为 Self-decoder 与 Cross-decoder，在外层用 KV Bridging 让 Cross-decoder 的 Full-attention KV 直接由 Self-decoder Hidden State 构建，在内层继续复用前一 Full-attention Layer 的 KV 与稀疏选择结果；Prefill 因此可以在 Self-decoder 结束后直接退出。

论文在 80B-A3B MoE 实验模型上报告，相比 Hybrid SWA，在 1M Token 时 Prefill FLOPs 约降低 5.02×、KV Cache 从 12.09GB 降到 2.69GB，同时长上下文检索更强。这里要特别区分：这是 HySparse2 架构实验，不是已经发布的 MiMo-V3 Checkpoint 结果。 截至当前，MiMo-V3 的权重、模型卡与完整规格尚未公开。

TwinCheck：Tool Call 修复必须先证明替代动作更好

论文原文

TwinCheck 不在每次“感觉当前 Tool Call 可疑”时直接改动作，而是先构造 Trace-grounded Negative Twin；只有 Trace 满足局部失败证据、替代动作通过结构检查，而且 Pairwise Verifier 在两个候选顺序下都偏好替代项时才 Commit。

159 个具有完整 Exact-replay Pair 的 BFCL V4 多轮任务中，GPT-5.6 Sol 成功率从 45.3% → 58.5%，95% bootstrap CI 为 [+8.2,+18.8]，并且没有观察到 success→failure regression。它适合与 Tool Transaction / Critical-State 工作一起看：高风险 Agent 修复需要的是受约束的反事实替换，而不是更多自由 Reflection。

Shared KV Cache：真实 Agentic Coding Traffic 下，Cache Hit 可能比单机 HBM 更重要

Nebius × WEKA 完整基准

同一台 8×B300 Serving Node、同一 vLLM、同一 512 Active Session Pool、同样 8 小时，唯一变量是 HBM-only 或由 8 个节点本地 NVMe 通过 GPUDirect RDMA 组成的共享 KV Tier。结果是 Requests Served 55,694 vs 23,015（2.4×），Output Tokens/GPU-hour 169K vs 46K（3.7×），Cache Hit 93% vs 40%，TTFT p50 1.05s vs 5.68s。

这是 Vendor Co-benchmark，不能当作普适的 3.7× Serving 加速；但测试使用 5,000+ 捕获的 Agentic Coding Session、部分 Context 接近 900K，说明 Agent Serving 的主要浪费确实可能来自反复 Prefill 同一长历史。对于生产系统，KV Locality 已经是 Router 应显式优化的状态。

CAVEAT：购物 Agent 会被“没有攻击、只有利益冲突”的环境带偏

论文原文

CAVEAT 在 9 个 Marketplace Environment 里加入 8 类 Steering Mechanism。5 个模型家族在 Control 中选择 User-optimal Product 的比例为 78.6%，加入 Steering 后只有 17.3%。失效主要发生在三个位置：扭曲用户优先级、过早缩小候选范围、在关键证据尚未解决前就 Commit。

CAVEAT-Harness 把 User-optimal Purchasing 提高 55.0%。这类 Benchmark 对 Shopping Agent 很重要，因为真实电商环境中的风险经常不是显式 Prompt Injection，而是平台排序、Sponsored Placement、默认选项和信息呈现方式与用户利益并不完全一致。

Causal CoT Audit：写出来的推理步骤未必真的参与了答案计算

论文原文

研究者在模型自己写出的中间推理步骤处做 Activation Patching，并构造已知 Counterfactual Target。Qwen3-4B 中约 76.9% ± 2.8% 的陈述步骤在最敏感中层具有因果作用，而普通 Behavioral Edit Test 给出 88.2%，高估约 11.4pp；Qwen3-1.7B 的因果 Load-bearing 比例只有 54.8%，并从 2-hop 的 68% 降到 6-hop 的 30%。

这个结果提醒 LLM-as-Judge / Process Reward：文本里出现了正确中间步骤，并不能自动证明模型是靠这些步骤得到答案。

今日最值得花 30 分钟阅读的一项

首选 Just-in-Time Memory。

论文原文

30 分钟建议重点看四个问题：为什么 Write-time Curation 天生面对未来 Query 未知的问题；Read-time Curation 如何把长期 Credit Assignment 变成当前 Task 的即时监督；为什么 Untrained Curator 已经能带来大部分方向性收益；最后看 Raw Trajectory Storage 与 Query-time Cost 的真实代价。

最值得带走的判断是：

对于“未来用途不确定”的 Agent Experience，尽量推迟不可逆压缩。Memory 的最佳表示可能不是一个永久 Summary，而是一组可在当前任务到来后重新物化的原始证据。

这条原则可以直接和昨天的 CliffCompaction 放在一起看：一个解决 Live Context 中的 Summary Drift，一个解决 Long-term Memory 写入时的 Premature Compression，两者都在指向同一个设计偏好——能晚做的有损压缩，不要太早做。

今日可立即实践的一件事

给现有 Agent Memory 做一个 Write-time vs Read-time Curation A/B。不需要训练新模型，先测试“压缩时点”本身有没有价值。

从历史里选 100–300 条真实任务轨迹，为每条轨迹保留两种表示：

1
2
3
4

memory = {
    "write_time": "任务结束时生成的 reflection / summary",
    "raw_trace": "原始 action-observation trajectory",
}

对新的测试任务，两个分支使用完全相同的 Retriever。Write-time 分支直接把检索出的 Summary 放入 Context；Read-time 分支把检索出的 Raw Trace 和当前 Query 一起交给一个固定模型，只生成一份当前任务专用 Payload。

至少记录 Task Success、Retrieval Recall、Memory Input Tokens、Curated Payload Tokens、Curation Latency / Cost 与 Missing-critical-fact Rate。若同一条 Raw Trace 已经被召回，而 Write-time Summary 经常缺少当前任务真正需要的细节，JitMem 这类策略就有很强的实施依据；如果关键失败来自 Retriever 根本没召回正确历史，则应先修 Retrieval。

真正要回答的是：

你的 Agent Memory 失败，是因为“没找到过去”，还是因为“过去曾经找到了，但在当时写 Summary 时已经把今天需要的信息删掉了”？

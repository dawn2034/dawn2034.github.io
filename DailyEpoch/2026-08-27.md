> **今日主线：** Recursive Memory · Search-Agent TTS · Agent Safety RL · Temporal Generative RecSys · Item Tokenization · KV Cache

## 今日核心判断

1. **Self-Evolving Agent 的有效状态正在进一步分层。** Recuris 不再让长期历史直接决定 Skill，而用 Working Memory 表示当前任务状态、Experiential Memory 保存可复用经验，再让 Meta-Agent 只修改被证据定位到的局部 Memory 组件；这比“不断扩写一个 memory.md”更接近可验证的长期进化。
2. **Multi-turn Search Agent 的置信度会被检索文本污染。** Retrieval-Grounded Voting 发现，模型把检索文档复制进答案时，复制 token 的 log-probability 会被系统性抬高，导致 confidence voting 在多轮搜索里失真；外部 grounding signal 反而更适合做 test-time selection。
3. **Agent Safety 正从“把规则全塞进 Prompt”转向“学习何时调用哪条规则”。** RePolicy 用 GRPO 训练 4B 模型在动态 policy library 中主动检索适用政策，在六个安全 benchmark 上整体 F1 达到 88.15；但它依赖 policy library 本身覆盖正确规则，安全边界仍受规则供给限制。
4. **Generative Recommendation 的时间适应必须同时处理 Token、Intent 与 Preference。** TAGR 在直播广告里周期性刷新活跃广告的 Semantic ID、建模多时间尺度意图，并间歇式采样最新 on-policy 偏好；线上收入相对生产基线提升 16.1%，但这是整套系统的工业自报告，不能把收益归因于单一组件。
5. **Item Tokenizer 的核心问题不只是“语义更好”，还包括独立可解码性和分布几何。** Tlow 先用 flow 把 semantic embedding 变换到近似独立、标准正态的 latent space，再做独立 tokenization；微信线上多模态召回报告整体 CTR +10.32%、新物品 +11.64%。
6. **KV 压缩的现实 Pareto 可能是“容量先赢、吞吐暂时不赢”。** Minima-KV 保留所有 live-request KV，只把旧页降为更低格式，在 Qwen3.6-27B 上做到 3.50× 相对 BF16 的 KV 压缩，但直接 decode canary 吞吐只有 control 的 0.9821×；这比只报压缩率更接近真实部署判断。

## 1. Recuris：把 Working State 与 Experience 分开，再做局部、可验证的 Memory Evolution

> **一句话结论：** 长程 Agent 的问题不只是“记不住”，而是历史越长越容易让当前状态和 Skill 选择失配；Recuris 的关键是让当前工作状态驱动经验调用，并让失败证据只修改对应的 Memory 组件。

**论文：** [Recursive Experiential-Working Memory Evolution for Long-Horizon Agent Harnesses](https://arxiv.org/abs/2608.24876)  
**代码：** [Gen-Verse/Recuris](https://github.com/Gen-Verse/Recuris)

### 发生了什么

Recuris 把长期 Agent Memory 拆成两类。Working Memory 维护当前任务进展和已验证状态，Experiential Memory 保存可复用 Skill；Skill 的调用由当前 Working Memory 决定，而不是直接对不断增长的完整聊天历史做相似度检索。

每次执行又会产生结构化证据，帮助定位失败究竟来自哪一个 Memory 组件。固定 Meta-Agent 根据这些证据提出局部修改候选，随后由 deterministic validation gate 在 held-out evidence 上决定是否接受。下游 Agent 本身保持冻结，因此这里的“进化”发生在 Memory / Skill 层，而不是权重层。

### 关键结果

| 指标 | 作者报告 |
|---|---:|
| 完成的 model-benchmark pair 中获得提升 | **35 / 37** |
| GPT-5.6 Sol 在 $\tau$-bench 上增益 | **+17.8 个百分点** |
| Claude Opus 5 在 $\tau$-bench 上增益 | **+15.6 个百分点** |
| Claude Opus 5 最终 $\tau$-bench success | **87.9%** |
| Qwen3.6-27B / 35B 在 SkillFlow 上增益 | **+16.6 / +13.5 个百分点** |
| 最长任务上的最大优势 | **+32.2 个百分点** |
| 常见 long-horizon failure 最大下降 | **80%** |

### 为什么重要

它给 Self-Evolving Agent 一个更清晰的状态分层：

```text
当前任务状态
    ↓
Working Memory
    ↓ 决定当前需要什么
Experiential / Skill Memory
    ↓
执行 trajectory
    ↓
结构化失败证据
    ↓
局部 Memory patch
    ↓
held-out validation gate
```

这比“成功了就总结一条经验、失败了就再写一段反思”更可审计。尤其是局部 patch 和验证门，让 Skill 更新开始接近软件变更，而不是不可追踪的 Prompt 漂移。

### 可信度与局限

这是刚发布的预印本，35/37、+32.2 等数字都是作者在所选 benchmark、模型和 Harness 下的结果，目前没有独立复现。Memory 在 benchmark 上持续进化，也可能逐渐编码任务分布本身，因此仍需要冻结 Memory 后的跨任务迁移实验来区分“可泛化经验”与“benchmark adaptation”。

另一个需要警惕的点是：deterministic validation gate 只能验证它能观察到的目标。如果 validator 覆盖不足，错误 Skill 仍可能通过；外部 Memory 更容易回滚，并不等于自动安全。

### 最值得继续追踪

我最关心 **Memory patch 的 transfer matrix**：一条在模型 A、任务族 X 上验证通过的 Skill，冻结后能否在模型 B、任务族 Y 上继续提升，同时不增加 negative transfer。这个指标会比“同 benchmark 连续进化后分数越来越高”更能说明 RSI 是否真正产生了可迁移能力。

## 2. Beyond Confidence：Search Agent 的 Logprob 会被“复制检索文本”抬高

> **一句话结论：** 单轮 reasoning 里常用的 confidence voting 不能直接搬到多轮 Search Agent；检索文档进入上下文后，复制 token 的高 logprob 会制造虚假的高置信度。

**论文：** [Beyond Confidence: Test-Time Scaling for Multi-Turn Search Agents via Retrieval Grounding](https://arxiv.org/abs/2608.24024)

### 发生了什么

Confidence-based voting 通常让同一道题采样多条 rollout，再用 token log-probability 等内部置信度信号给候选答案加权。论文发现，这个方法迁移到 multi-turn search 后明显失效，原因是 **copy inflation**：检索文档已经出现在上下文中，最终答案如果直接复制文档片段，对应 token 的条件概率会被系统性抬高。

结果是，同一道题不同 rollout 之间的 confidence 差距被压平或扭曲，而“写得像检索结果”的答案不一定真的更正确。

作者提出 Retrieval-Grounded Voting（RGV），不用模型内部 logprob，而是在模型上下文之外，比较最终答案和该 rollout 实际检索文档之间的 lexical grounding。它不需要额外 LLM Judge 调用。

### 关键结果

| 设置 | 作者报告 |
|---|---:|
| Search-Agent benchmark | 4 个 |
| 测试 LLM | 5 个 |
| 相对 confidence-based voting 最大准确率增益 | **+5.4%** |
| minority-correct 问题最大增益 | **+35%** |
| minority-correct 定义 | 8 条 rollout 中仅 1–2 条正确 |

### 为什么重要

这说明 test-time scaling 的 scoring signal 必须与 Agent 的信息流一起设计。单轮模型内部的概率信号，在加入 retrieval、tool output、copied evidence 之后可能产生新的系统性偏差。

更一般地说：

> **当外部工具把答案候选直接放进上下文时，token confidence 不再是纯粹的“模型知道程度”，而混入了 context copying ease。**

这对 Search Agent、RAG、代码补全甚至 Tool Agent 都值得检查。

### 可信度与局限

RGV 的优点是便宜、无需额外模型，但 lexical overlap 也不是 correctness。错误文档、query drift 或高度抽象的答案，都可能让“有 grounding”与“答对”分离。论文证明的是 RGV 在其四个 Search-Agent benchmark 上比 confidence voting 更稳，不是证明 lexical grounding 是通用最优 verifier。

另外，+35% 是 minority-correct 子集的最大增益，不是整体 benchmark 的统一提升。

### 最值得继续追踪

下一步应把 lexical grounding 扩展成 **evidence entailment + citation coverage + retrieval provenance**，同时控制额外成本。更值得做的 ablation 是：当检索文档本身包含错误或相互冲突证据时，RGV 的优势是否还存在。

## 3. RePolicy：让 4B Safeguard 学会主动调用动态 Safety Policy

> **一句话结论：** Policy-aware Guard 的下一步不是把越来越长的安全规则永久塞进 system prompt，而是训练一个模型判断“当前轨迹受哪条 policy 管”，只检索相关条款再做判断。

**论文：** [RePolicy: Reinforcement Learning for Safety-Policy Invocation in Agent Safeguards](https://arxiv.org/abs/2608.24275)  
**模型：** [JiangHoucheng/RePolicy-4B](https://huggingface.co/JiangHoucheng/RePolicy-4B)  
**代码：** [JiangHoucheng/RePolicy](https://github.com/JiangHoucheng/RePolicy)

### 发生了什么

RePolicy 的 backbone 是 Qwen3-4B-Instruct-2507。模型不会一开始就看到所有 policy 正文，只获得 policy titles；面对完整 Agent trajectory，它先决定哪条 policy 适用，通过 `get_policy` 工具取回条款，再输出 policy-grounded rationale 和安全判断。

训练先用 PolicyTraj-20K 做 cold-start SFT，然后用 GRPO、可验证 reward 和 policy-context perturbation 继续训练。后者用于避免模型只记住固定 policy 排列或上下文模式。

### 关键结果

Unsafe-class F1：

| 模型 | Overall F1 |
|---|---:|
| Qwen3-4B backbone | 58.47 |
| DynaGuard-4B | 76.52 |
| AgentDoG-4B | 79.69 |
| GPT-5.4 | 83.12 |
| Claude Sonnet 4.6 | 84.17 |
| **RePolicy-4B** | **88.15** |

RePolicy-4B 相比表中最强外部大模型高 **3.98 个百分点**，相比最强 specialized 4B guard 高 **8.46 个百分点**。

### 为什么重要

真实 Agent 的安全规则往往是动态的：不同工具、业务、用户权限和部署地区可能对应不同 policy。把整个规则库永久塞进 prompt 会增加 context 成本，也会让模型在大量无关规则中判断 applicability。

RePolicy 把 safeguard 拆成：

```text
trajectory
  ↓
policy invocation
  ↓
retrieve clauses
  ↓
policy-grounded reasoning
  ↓
safety judgment
```

这更接近真实 policy engine 与 LLM Guard 的结合方式。

### 可信度与局限

88.15 是六个 benchmark 的 unweighted mean，来自作者模型卡与论文实验，目前仍是作者自报告。更重要的边界是：**RePolicy 只能从已有 policy library 中调用规则。** 如果规则库漏掉某类风险、规则过时或 policy title 本身误导，模型再会调用也无法弥补 policy supply 的缺口。

它还增加了至少一次 policy retrieval / tool-call 流程，因此部署时要额外测 P95 latency、policy retrieval failure 与规则版本一致性。

### 最值得继续追踪

最值得验证的是 **policy churn**：规则新增、删除、改写后，模型是否仍能稳定找到正确 policy，而无需重新训练；以及 policy retrieval 与最终安全判断的错误应分别统计，避免把“没找到规则”和“找到规则但判断错”混成一个 F1。

## 4. TAGR：直播广告里的 Generative Recommendation 必须显式建模“时间”

> **一句话结论：** 静态 Semantic ID、单一时间尺度兴趣和一次性 preference optimization 都不适合分钟级变化的直播广告；TAGR 的工业结果说明，Generative RecSys 如果进入实时业务，token space 本身也必须具备刷新机制。

**论文：** [TAGR: Temporally Adaptive Generative Recommendation for Industrial Live-Streaming Advertising](https://arxiv.org/abs/2608.24034)

### 发生了什么

TAGR 针对直播广告中三个不同时间尺度的问题做三层适应：

- **LSID（Live Semantic-Collaborative ID）**：根据当前直播场景和推广商品周期性刷新活跃广告的 SID，但保持稳定的层级 token vocabulary；
- **IAG（Intent-Aware Generation）**：把用户进入直播间的历史按多时间粒度建模为主意图序列，辅助行为单独输入，并根据请求后的意图证据和业务价值调整 NTP 权重；
- **IOPO（Intermittent On-Policy Preference Optimization）**：周期性从当前 policy 采样新候选组做偏好更新，同时穿插 supervised NTP，避免持续 on-policy 更新破坏已有行为分布。

### 关键结果

相对生产基线的线上结果：

| 业务指标 | 提升 |
|---|---:|
| Live-room entry | **+8.5%** |
| Shopping-cart click | **+7.4%** |
| Revenue | **+16.1%** |

### 为什么重要

传统 SID 往往默认 item semantic representation 相对稳定，但直播广告的内容、主播状态、正在卖的商品和用户反馈都可能分钟级变化。如果 token identity 长期冻结，生成模型实际上在用过期离散表示做决策。

TAGR 把“item token 是否还代表当前 item”变成了系统的一等问题。这对新闻、短视频热点、广告创意等高时效场景同样成立。

### 可信度与局限

这是工业部署的线上结果，证据强于纯离线 benchmark；但摘要没有给出实验时长、流量规模、置信区间和各组件独立线上贡献。因此 **16.1% revenue lift 是整套 TAGR 相对生产 baseline 的系统结果，不能归因给 LSID、IAG 或 IOPO 中任何单一模块。**

此外，周期性刷新 SID 会引入 token versioning、缓存失效、训练／推理一致性和历史行为解释问题，这些成本在摘要里没有量化。

### 最值得继续追踪

我会重点看 **SID refresh rate × serving stability** 的 Pareto：刷新太慢会 stale，刷新太快又会让历史行为 token 语义漂移。真正工业化需要给每个 SID 带 version / validity interval，而不只是定期重新编码。

## 5. Tlow：先把 Semantic Embedding 的分布“拉直”，再做独立 Item Tokenization

> **一句话结论：** RQ-VAE 的多级 codebook 有依赖，OPQ 式独立量化又受 embedding 维度相关性影响；Tlow 先用 flow 把 embedding 映射到更规整的 latent，再进行独立 tokenization。

**论文：** [Tlow: Flow-based Item Tokenizer for Recommendation](https://arxiv.org/abs/2608.24176)  
**代码：** [wjjln/Tlow](https://github.com/wjjln/Tlow)

### 发生了什么

Tlow 用可逆 flow 将原始 semantic embedding 变换到近似统一标准正态的 latent space，目标是同时降低维度相关性和复杂边缘分布。随后各维／子空间可以更独立地 tokenization，不再依赖 RQ-VAE 那种前一层 codebook residual 决定后一层的串行关系。

方法还加入 codebook guidance，让 codebook space 与推荐模型实际使用的 token embedding space 更一致，避免 tokenizer 学到的离散空间和下游模型使用的表示发生错位。

### 关键结果

论文报告在四个公开数据集上提升推荐效果，并在跨域、多模态场景保持收益。微信线上多模态召回中：

| 用户／物品范围 | CTR 提升 |
|---|---:|
| 全局用户 | **+10.32%** |
| 新物品 | **+11.64%** |

### 为什么重要

Generative Recommendation 越来越依赖 item tokenizer，但 tokenizer 常被当成一个“前处理模块”。实际上，离散 token 的统计结构决定了：

- 生成序列有多长；
- 各 token 是否能并行／独立预测；
- 新 item 能否借语义结构获得合理 token；
- codebook 是否与下游 token embedding 匹配。

Tlow 的核心启发是：**先改善连续表示空间的几何，再离散化，可能比直接在高度相关、非高斯的 embedding 上硬量化更自然。**

### 可信度与局限

线上 CTR 是作者工业自报告，摘要没有提供实验时长、用户规模或 latency / parameter reduction，因此不能只凭 +10.32% 推断 tokenizer 在所有工业推荐场景都会有类似收益。

Flow 本身也需要训练，并会受到上游 semantic encoder 分布漂移影响。若 item 内容模型频繁更新，flow 与 codebook 是否需要同步重训，是部署时的重要成本。

### 最值得继续追踪

最值得看的是 **token stability under encoder drift**：同一 item 在 encoder 更新前后 token 是否大幅变化，以及新 item 的 CTR 增益究竟来自更好的 cold-start semantic token，还是同时叠加了新的 retrieval model / training recipe。

## 6. Minima-KV：不 Evict Live KV，改用混合格式保留全部上下文

> **一句话结论：** Minima-KV 选择“低精度保留旧 KV”而不是“删掉旧 KV”；它证明容量可以大幅下降、质量损失很小，但当前 direct-decode 吞吐并没有同步提升。

**论文：** [Minima-KV: Retention-Preserving KV Cache Compression with Mixed-Format Paged Attention](https://arxiv.org/abs/2608.23834)

### 发生了什么

Minima-KV 把最近页和受保护 Anchor pages 保持在 FP8，把更旧、非 Anchor 的 page 压成 packed TQ3。与 eviction 方法不同，每一个 live-request KV page 仍然可寻址。

推理 kernel 分别计算不同格式 page 的 partial attention state，再通过全局归一化的 online-softmax merge 合并，因此不需要维护一个 cache-sized dense shadow。

### 关键结果

Qwen3.6-27B，单张 96GB RTX PRO 6000 Blackwell：

| 指标 | 结果 |
|---|---:|
| Attention KV / live token | **18.3 KiB** |
| 相对 BF16 KV 压缩 | **3.50×** |
| 相对 FP8 KV 压缩 | **1.75×** |
| LongBench v2 16K / 32K / 64K delta | **-0.80 / -0.60 / -0.40 pp** |
| 59,008-token direct-decode active-KV 压缩 | **3.625×** |
| direct-decode throughput / control | **0.9821×** |

### 为什么重要

KV optimization 常见两条路线：删掉 token，或者降低每个 token 的表示成本。Minima-KV 明确选择第二条，因此避免了 eviction 带来的“被删 token 之后突然又重要”的不可逆风险。

更重要的是，它把一个经常被营销数字掩盖的事实摆出来：**KV capacity 大幅下降，不等于 decode throughput 自动提高。** 混合格式解码需要额外 unpack、format-specific kernel 和 merge；在当前 canary 上，吞吐甚至略低于 control。

### 可信度与局限

这些数字都绑定在一个非常具体的模型、GPU、kernel 和请求配置上。LongBench v2 的损失较小是正面信号，但单机实验不能直接外推到多 GPU、高并发、continuous batching 的真实 serving。

0.9821× throughput 也只是一组 direct-decode canary，不应反过来断言混合格式 KV 永远不会提升吞吐；真正收益可能来自更高 session residency 和更少 eviction / reload，而不是单请求 kernel 更快。

### 最值得继续追踪

线上应同时测：

```text
KV bytes / live token
resident sessions
cache eviction rate
P50 / P95 TTFT
P50 / P95 decode latency
aggregate throughput
quality delta
```

如果压缩只降低显存，却没有让并发、session residency 或端到端成本变好，就不能算完整的 serving win。

## 今日值得收藏的代码 / 学习资源

**[Recuris](https://github.com/Gen-Verse/Recuris)**：今天最值得直接读实现的项目。重点不是 prompt，而是 Working Memory、Skill Memory、结构化 trace 与 deterministic validation gate 如何串成闭环。

**[Meta$^n$: Recursive Self-Improvement through Emergent Depth](https://arxiv.org/abs/2608.24735)** / **[代码](https://github.com/minnesotanlp/meta-n)**：固定 meta-operation $\Omega$，但递归地把前一层产生的 trace 与 code 作为下一层输入，由收敛决定深度。论文报告在两个 backbone、八个 benchmark family 上优于比较的 self-improving agent，并称 ARC-AGI-2 中只有 Meta$^n$ 得分高于 0。值得关注，但“$\Omega$ 固定所以系统不会失稳”是作者的机制主张，不应当成已证明的安全结论。

**[MetaRAG](https://arxiv.org/abs/2608.24214)**：把 Search Agent 的 continue-search / answer 决策写成 belief-action alignment。训练时先显式 Verify，再探测模型自己认为“当前证据是否足够”，一致性 reward 还受最终答案正确性 gate；belief probe 只在训练期使用。它很适合和今天 RGV 一起读：前者优化“何时停”，后者优化“多条 rollout 选哪条”。

**[AgentSpec](https://arxiv.org/abs/2608.24004)**：面向批量 Agent inference 的 speculative decoding。它把普通 spec decoding 在大 batch 下的退化归因于高 rejection rate 与动态 token budget 利用不足，再用 structure-isolated drafting 与 redundancy-aware budget allocation 修复。论文在 vLLM、5 个 workload、4 个模型家族上报告优于 SOTA，但摘要没有统一 headline speedup，建议等代码和完整 benchmark 再判断工程价值。

## 今日最值得花 30 分钟阅读的一项

**首选 Recuris。**  
[论文](https://arxiv.org/abs/2608.24876) · [代码](https://github.com/Gen-Verse/Recuris)

它真正值得读的不是“某个模型又涨十几个点”，而是它把 Self-Evolving Agent 中三个经常混成一团的问题拆开了：

1. **当前任务现在是什么状态？** —— Working Memory；
2. **过去哪些经验可能适用？** —— Experiential / Skill Memory；
3. **一次失败究竟应该修改哪一部分经验？** —— structured evidence + localized patch + validation gate。

建议阅读顺序：先看 Working Memory 为什么比 full-history retrieval 更适合驱动 Skill invocation；再看 trace 如何定位 failure；然后看 patch 为什么必须经过 held-out deterministic gate；最后重点看最长 horizon 上增益放大的实验，而不是只看平均 success。

读完后最值得问的问题不是“要不要复现这套框架”，而是：

> **自己的 Agent Memory 里，有多少内容是在描述当前状态，有多少是在描述可复用经验？这两类信息现在是否被混在同一个向量库、同一种更新规则里？**

## 今日可立即实践的一件事

给现有 Search / Deep Research Agent 做一次 **Copy-Inflation Audit**，验证 token confidence 是否已经被检索文本污染。

选 30–50 个多轮搜索问题，每题固定采样 8 条 rollout。对每条 rollout 保存：

```python
{
    "answer": str,
    "answer_token_logprobs": list[float],
    "retrieved_docs": list[str],
    "is_correct": bool,
}
```

然后计算两个信号：

$$
C_i = \frac{1}{|A_i|}\sum_{t \in A_i}\log p_t
$$

其中 $C_i$ 是传统 answer confidence；再计算一个简单的 retrieval-grounding proxy：

$$
G_i = \frac{|\operatorname{ngrams}(A_i) \cap \operatorname{ngrams}(D_i)|}{|\operatorname{ngrams}(A_i)|}.
$$

同时记录 `copied_token_ratio`，并比较：

```text
majority vote
confidence-weighted vote
retrieval-grounded vote
```

至少输出四个指标：

```text
vote_accuracy
minority_correct_recovery
Spearman(copied_token_ratio, mean_logprob)
ECE / calibration error
```

**停止条件：** 如果 `copied_token_ratio` 与 `mean_logprob` 没有稳定正相关（例如不同数据切片上 $|\rho| < 0.1$），而 confidence voting 仍稳定优于 grounding voting，就没有必要为了追随新论文替换现有 selector。

反过来，如果 copied ratio 越高、logprob 越高，但 correctness 并未同步上升，而且 minority-correct 问题中 confidence voting 明显漏掉正确 rollout，那么应停止继续调 confidence temperature，优先测试 grounding、citation entailment 或独立 verifier。

这个实验成本很低，却能回答一个基础问题：**Search Agent 的“自信”究竟来自真正知道答案，还是只是很容易复制刚刚读过的文本。**

# 每日 AI 技术简报｜2026-08-16

今天是周日，arXiv 没有新的常规周末公告批次，因此本期不重复昨天已经覆盖的 8 月 14 日高信号论文，而做一次**近一周技术深挖**。今天最值得连起来看的几条线索是：Agent 自我进化正在从“不断追加经验”走向**可回滚、可删除、可审计的 Skill 优化**；多轮 Agent RL 的 credit assignment 开始明确拆成“轨迹→动作”和“动作→token”两层；带压缩 Memory 的 Agent 暴露出一个容易被忽略的 on-policy state mismatch；test-time scaling 则越来越像一个“下一单位算力投在哪里”的路由问题。

## 今日核心判断

- **Self-evolving Agent 的关键不再只是“会不会总结经验”，而是有没有受控的更新算子。**SkillProx 的价值在于把 rollback、utility audit、consolidation 和 removal 都变成显式机制，而不是把 Skill Store 做成 append-only 笔记本。
- **Agent RL 的 token-level advantage 不能脱离 action semantics。**FACTOR 先决定每一步 action 应拿多少 credit，再决定该 action 内各 token 怎么分，避免长 action 因 token 数更多而获得隐式权重优势。
- **“on-policy trajectory”不等于“teacher 在同一个 state 上打分”。**MemOPD 说明，只要 Memory 会压缩和重写历史，teacher scoring 就可能在学生从未访问过的重构状态上发生。
- **Test-time scaling 的核心变量正在从 sample count 转向 marginal utility per compute。**CoBa 不是简单多采样，而是在 generation、cheap verification、strong verification、stop 之间做预算分配。
- **推荐系统的 LLM 化真正有价值的方向之一，是把用户显式语言意图纳入实时 serving loop。**但 Shape Your Feed 报告的 98.85% 是 alignment scorer 的离线准确率，不应误读成线上推荐准确率。

## 1. SkillProx：Self-Evolving Skill 从“文本追加”走向可回滚的优化过程

**论文：** [SkillProx: Self-Evolving Agent Skills via Proximal Textual Gradient Descent](https://arxiv.org/abs/2608.07449)

SkillProx 研究的是一个很现实的问题：Agent 把多次任务经验沉淀成自然语言 Skill 后，Skill 会越来越长、越来越杂，而且一次错误的 diagnosis 可能直接污染后续版本。作者把 Skill 更新类比成 proximal optimization，拆成 forward / backward 两个阶段。

Forward 阶段并不是“根据失败写一句反思就结束”，而是：

```text
执行任务
  ↓
诊断失败
  ↓
修改 Skill
  ↓
在同一批任务重新执行
  ↓
若退化则 rollback
  ↓
把真实 outcome 反馈给下一轮 diagnosis
```

Backward 阶段再把 Skill 拆成可审计的 knowledge units，用冻结的 leave-one-out utility audit 判断某条经验究竟有没有贡献，然后做 consolidation、demotion 或 removal。论文在多个 backbone、ID/OOD benchmark 上，相比最强 gradient-based baseline 平均提升 3.0 个百分点。

### 为什么重要

它把 Skill Store 从“长期记忆文本”变成了更像软件版本库的对象。一个成熟的 self-evolving Agent 至少应该拥有：

```text
add / edit / validate / rollback / merge / demote / delete
```

而不应该只有 `append()`。

这和前一天讨论的 Skill Misevolution 正好形成互补：前者告诉我们**错误经验可能长期传播**，SkillProx 则提供了一种更结构化的更新与清理思路。

### 可信度与局限

3.0 个百分点是作者在其 benchmark 与所选 baseline 上的平均结果，不能直接推断到开放式 Web Agent 或 Coding Agent。更重要的是，SkillProx 的 utility audit 仍依赖可重复执行、可评估的任务；如果环境高度非平稳、奖励噪声大，rollback 与 leave-one-out 估计本身也可能不稳定。

### 最值得继续追踪

我最关注 **utility audit 能否和 safety / provenance audit 合并**。也就是说，一条 Skill 不只回答“有没有用”，还要回答“来源是否可信、适用域是什么、是否包含高风险操作”。

## 2. FACTOR：多轮 Agent RL 的 Credit Assignment 应该先到 Action，再到 Token

**论文：** [How Much, Then Where: Credit-Conserving Action-to-Token Allocation for Multi-Turn Agent Reinforcement Learning](https://arxiv.org/abs/2608.07118)

FACTOR 把多轮 Agent RL 的 credit assignment 明确拆成两个问题：

1. **How much：**整条 trajectory 的 advantage，应该有多少归因给第 $t$ 个 action？
2. **Then where：**第 $t$ 个 action 得到的 credit，又应该如何分给该 action 内真正关键的 token？

它先用 checkpoint-calibrated TD residual 给每个 action 分配 credit，使 action-level credit 在整体上守恒于 trajectory advantage。可以用一个简化关系理解：

$$
A(\tau) \approx \sum_{t=1}^{T} c_t
$$

然后再利用 feedback-conditioned 的 teacher-student likelihood gap，把 $c_t$ 分配给 action 内的 token：

$$
\sum_{j \in a_t} w_{t,j} = c_t
$$

这里真正重要的不是具体公式，而是**两层归因被解耦了**。论文还使用 action-mean reduction，避免一个 action 仅仅因为文本更长、token 更多，就在 surrogate objective 中拥有更大的隐式权重。

作者在 ALFWorld、WebShop、ScienceWorld 上测试，所有 environment-seed 对比都优于竞争 baseline，最长 horizon 的环境收益最大；ablation 中，TD action credit 是主要收益来源，token allocation 提供互补增益。

### 为什么重要

很多 Agent RL 实现实际上把“trajectory reward → 每个 response token”做了过于粗糙的广播。对于工具型 Agent，这很容易产生荒谬归因：

```text
正确选择 API       ← 真正关键
写了很长的参数解释  ← token 多
工具调用失败后的废话 ← token 更多
```

如果 loss 对 token 数天然敏感，模型可能在优化一个与真实 action quality 不一致的目标。

### 可信度与局限

目前证据来自三个交互式 benchmark，虽然覆盖不同环境并做了跨 backbone transfer，但还不足以证明在真实浏览器、Coding Agent 或长链工具系统中同样稳定。其次，checkpoint-calibrated TD credit 的质量仍取决于 value / checkpoint estimate；如果这个估计本身偏差很大，credit conservation 只能保证“总量一致”，不能保证“分得正确”。

### 最值得继续追踪

值得看它是否能与 **process reward model、tool verifier、failure detector** 组合：外部 verifier 给动作级证据，FACTOR 再负责把动作级 credit 守恒地分配到 token。

## 3. MemOPD：Memory Compression 会悄悄破坏 On-Policy Distillation 的 State Alignment

**论文：** [MemOPD: On-Policy Distillation through Memory State Alignment for Long-Horizon Agents](https://arxiv.org/abs/2608.07068)  
**代码：** [TPssp/MemOPD](https://github.com/TPssp/MemOPD)

MemOPD 指出了一个很容易被忽略的细节：如果长程 Agent 会周期性压缩 Memory，那么“这个 action 是 student 自己 rollout 出来的”并不足以保证 teacher supervision 真正 on-policy。

假设 student 在第 $t$ 步实际看到的是：

```text
raw history
  → memory compressor
  → compact state S_t
  → sample action a_t
```

训练时如果把所有交互重新 flatten 成一条 persistent history，再让 teacher 对 $a_t$ 打分，teacher 实际看到的可能是另一个状态 $\tilde S_t$。于是：

$$
S_t \neq \tilde S_t
$$

action 的**来源**仍然是 on-policy，但 teacher scoring 的**状态条件**已经 off-state。

MemOPD 的做法是记录每次模型 invocation 的原始输入和采样输出，恢复当时的 token position 与 causal visibility，再把这些“原始状态快照”打包给 teacher 评分。论文报告，在 matched control 中 state alignment 比 persistent-history scoring 的 F1 高 7.0%；其 3B 模型相对 PPO 的 F1 提升最高达到 416.2%，packing 还带来最高 1.63× actor compute speedup。

### 为什么重要

这说明长上下文 Agent 的训练数据不能只保存：

```text
messages = [...] 
```

更可靠的数据结构应该保留**每次 invocation 的真实可见状态**：

```text
invocation_id
visible_context
memory_snapshot
position_ids
sampled_action
subsequent_feedback
```

否则后训练阶段很容易制造“看起来同一条 trajectory，实际上换了 conditioning state”的隐性数据偏差。

### 可信度与局限

“相对 PPO 提升最高 416.2%”是相对比例，基线较低时会显得非常大，因此更应关注 matched-control 的 7.0% F1 提升，它更直接隔离了 state alignment 这一变量。论文仍需更多不同 Memory compressor、不同 horizon 与不同 Agent 类型验证。

### 最值得继续追踪

我会关注 **Memory state versioning** 是否成为 Agent 后训练数据格式的一部分。未来 replay / distillation 数据可能不仅需要 trajectory ID，还需要精确的 memory-state hash。

## 4. CoBa：Test-Time Scaling 不应该只问“采多少次”，而应该问“下一单位算力投哪里”

**论文：** [CoBa: Cost-Effective Test-Time Scaling via Compute-Balanced Routing](https://arxiv.org/abs/2608.07424)

CoBa 把 test-time scaling 重新表述成 compute allocation：在固定预算下，下一单位计算到底应该用于：

```text
继续生成候选？
做便宜验证？
升级到更强 verifier？
还是现在就停止？
```

它先生成一个较小 candidate set，对所有候选做廉价 verification，再把“不确定但可能有价值”的候选路由到更强 verification。作者在 MATH-500、AIME 2024/2025、AMC 2023 和程序化符号推理的 3,129 个 evaluation 上报告：CoBa-Routed-Strong 达到 85.13% macro accuracy，与 self-evaluation weighted voting 的 85.20% 统计上接近，同时 parameter-weighted tokens 少 49.1%；相对 best-of-16 majority voting，macro accuracy 只差约 0.01 个百分点，而 parameter-weighted tokens 少 58.9%。

### 为什么重要

这比“Best-of-N 越大越好”更接近真实推理服务的经济学。对推理系统而言，真正的目标不是最大化采样数，而是：

$$
\max \frac{\Delta \text{Expected Quality}}{\Delta \text{Compute Cost}}
$$

而且不同阶段的计算价值不同：早期多生成一个候选可能很有用，候选已经高度同质时再生成十个几乎没有边际收益；反之，一个强 verifier 可能只值得用于少数高价值的不确定样本。

### 可信度与局限

论文的成本用 parameter-weighted tokens 近似，这比纯 token count 更合理，但仍不是完整线上成本：真实系统还有 KV cache、batching、并行度、verifier latency、GPU 利用率和跨模型调用开销。作者也明确指出，相比 pool oracle 仍有明显 headroom，说明 router 还没有接近最优 compute allocation。

### 最值得继续追踪

真正值得落地的是 **router 的训练目标是否直接优化端到端成本**，例如 $/request、P95 latency 或 GPU-seconds，而不是代理指标。

## 5. Shape Your Feed：推荐系统从“猜用户想要什么”向“允许用户直接塑造 Feed”推进

**论文：** [Shape Your Feed: An LLM-based Agentic System for Conversational Recommendation](https://arxiv.org/abs/2608.06632)

这篇 RecSys 2026 Industrial Track 工作值得推荐系统从业者关注。传统 Feed 主要从点击、停留、完播等隐式行为反推偏好，而 Shape Your Feed（SYF）让用户通过文字、语音和 UI 操作直接表达：

```text
“少一点宏观新闻，多一点 AI infra。”
“最近只想看日本旅行和健身。”
“类似这条，但不要明星八卦。”
```

系统分为三层：

- **Perception Flow**：把文本、语音、UI 反馈解析成细粒度意图；
- **Serving Flow**：基于持久 Semantic Profile 对已有 candidate 做实时 agentic reranking / pruning；
- **Self-Evolution Flow**：使用 DPO 与 LLM-as-a-Judge ensemble 对系统行为做持续对齐。

论文报告 alignment scoring module 的离线准确率为 98.85%，并称大规模线上 A/B 在 feed relevance 与 user sentiment 上有提升。

### 为什么重要

它代表推荐系统一个可能比“把 LLM 塞进 ranker”更有价值的方向：**LLM 充当用户与传统推荐 pipeline 之间的可解释控制层。**底层 retrieval / ranking 可以继续高吞吐运行，LLM 负责把自然语言意图转换成结构化、可持久化、可实时作用于 serving 的偏好状态。

### 可信度与局限

需要特别避免一个误读：**98.85% 是 alignment scorer 的准确率，不是线上推荐准确率，也不是 CTR uplift。**摘要没有公开线上 A/B 的具体效应量，因此目前只能确认“作者报告有正向线上结果”，不能判断商业收益大小、统计显著性和长期留存影响。

另一个风险是显式偏好与隐式行为冲突：用户说“少看短视频”，但仍持续点击短视频时，Semantic Profile 应该如何融合两类信号，这会成为产品与算法共同的问题。

### 最值得继续追踪

我最关心的是 **Semantic Profile 的更新规则与冲突解析**：显式意图应该拥有多长 TTL？一次自然语言指令是否压过长期行为？如何让用户看到并撤销系统记住的偏好？

## 6. ReQuant：PTQ 之后的离散权重并不一定应该被视为“终局”

**论文：** [ReQuant: Fixed-Grid Discrete Refinement for Post-Training Quantization](https://arxiv.org/abs/2608.07019)

ReQuant 的想法很朴素但很实用：传统 PTQ 得到整数权重后，通常把这个离散 assignment 当成最终结果；ReQuant 则保持原有 quantization grid 不变，在这个固定离散空间中继续迭代重分配权重，只接受能降低 reconstruction MSE 的更新，而且不需要 backprop。

这相当于把：

```text
FP model → PTQ → quantized model → 结束
```

改成：

```text
FP model → PTQ initializer → fixed-grid discrete refinement → 更优 quantized model
```

论文在多种 model family、bit-width、PTQ initializer 上都观察到改进，尤其是简单 initializer 和更低 bit-width；作者还报告 round-to-nearest 经过多轮 refinement 后，在相同 quantization format 下可以接近或超过 GPTAQ。

### 为什么重要

它提醒我们：**量化不是一次映射，而可以继续看成一个受离散约束的优化问题。**如果这类 refinement 的计算成本足够低，它很适合作为现有 PTQ pipeline 的后处理插件，而不是重新设计整套量化算法。

### 可信度与局限

当前摘要强调的是 reconstruction MSE 与 downstream performance 的整体改善，但真正部署时还必须检查：refinement 时间、不同 layer sensitivity、kernel 兼容性、实际 latency / throughput 是否保持不变。固定 grid 保证了格式兼容，不代表所有硬件路径都能自动获得同样收益。

### 最值得继续追踪

看它在 **2-bit / 3-bit 极低比特、MoE、超大模型和真实推理 kernel** 上是否仍然有稳定收益，以及离散 refinement 的额外离线成本是否值得。

## 7. 值得收藏的学习资源：Self-Improvements in Modern Agentic Systems Survey Hub

**资源：** [Self-Improvements in Modern Agentic Systems — Survey Hub](https://selfimproving-agent.github.io/)

如果你最近持续追 Self-Evolving Agent，这个页面比单篇论文更值得收藏。它把 self-improvement 先分成两个大类：

```text
Foundation Model Improvement
vs.
Scaffolding Improvement
```

然后继续拆成 intrinsic demonstration / evaluation、grounded experience、world model、prompt optimization、memory、tool、full scaffolding 等子类，并提供可检索的论文库。

### 为什么重要

这个 taxonomy 能避免把所有“自我进化”都混在一起。参数更新、Prompt Evolution、Memory 更新、Skill / Tool 创建、Harness 自修改，其**持久性、成本、可回滚性和风险面完全不同**。阅读新论文时先问“到底更新了什么对象”，往往比先看 benchmark 分数更有效。

### 局限

这是持续维护的 curated survey，不是系统综述意义上的穷尽性证据库；收录数量和分类会变化，边界也存在主观性。它最适合当“地图”，不适合作为某条技术路线优劣的最终证据。

## 今日最值得花 30 分钟阅读的一项

**首选：FACTOR——[How Much, Then Where: Credit-Conserving Action-to-Token Allocation for Multi-Turn Agent Reinforcement Learning](https://arxiv.org/abs/2608.07118)。**

原因不是它的 benchmark 数字最大，而是它击中了 Agent RL 中一个非常基础、但很容易被实现细节掩盖的问题：

> trajectory-level reward 最终究竟如何变成某一步 action、再变成某些 token 的梯度？

建议 30 分钟按这个顺序读：

1. 先搞清楚为什么 token-level broadcasting 会引入 action-length bias；
2. 再看 TD residual 如何给 action 分 credit，并理解“credit conserving / telescoping”到底约束了什么；
3. 再看 teacher-student likelihood gap 为什么只负责 **where**，而不负责 **how much**；
4. 最后看 ablation：主要收益来自 action credit，token allocation 是互补项。

这篇很适合作为设计 SQL / Python Tool Agent RL 时的 loss-function 参考，因为它迫使我们把“工具动作的语义单位”和“语言模型 token 的优化单位”分开考虑。

## 今日可立即实践的一件事

给任何多轮 Agent RL / GRPO 实验增加一组 **Action-Level Credit Diagnostics**。即使暂时不实现 FACTOR，也先把“credit 到底落在哪里”可视化出来。

建议每条 trajectory 记录：

```python
trajectory_reward
trajectory_advantage

for action in trajectory:
    action_type          # reasoning / tool_call / final_answer
    action_token_count
    tool_name
    tool_success
    action_credit
    mean_token_weight
    max_token_weight
    min_token_weight
```

至少检查三个量：

$$
A(\tau) \approx \sum_t c_t
$$

确认 action credit 总量没有莫名漂移；再画：

```text
action_token_count  vs. |action_credit|
tool_success        vs. action_credit
action_position     vs. action_credit
```

如果发现“文本更长的 action 系统性获得更大的优化权重”，或者真正决定成败的 tool call 与周围大量 reasoning token 获得近似相同 credit，那么继续调 learning rate、KL coefficient 或 rollout 数量之前，应该先修 credit assignment。

这一步的价值在于，它不要求立刻重写训练算法，却能快速暴露：**你训练的到底是正确动作，还是只是奖励附近的一大团 token。**

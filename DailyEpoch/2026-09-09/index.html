今日主线： Memory Portability · Hybrid GUI+CLI · Selective Route Editing · Autonomous Recommender Research · Layer Dropout

截至今天早上，arXiv cs.AI 最新常规公告批次仍为 2026 年 9 月 7 日，共 205 条。今天更值得连起来看的变化，不是单纯追逐新的模型分数，而是几项工作都在强调同一件事：Agent 与后训练系统真正脆弱的地方，往往位于模型权重之外——长期记忆能否跨模型升级、GUI 与 CLI 如何共同作用于同一状态、规划在运行时怎样局部修订、自动实验系统何时允许改变基线，以及预训练是否提前为推理时的弹性深度付费。

今日核心判断

  1. 模型升级应该被当作一次 Memory Migration，而不是“换个 Reader 就完事”。 在 48 个受控历史上，模型生成的 NOTES 出现明显方向性耦合：Llama 读取 Qwen 笔记比自己的笔记高 9.91 points，而 Qwen 读取 Llama 笔记低 13.28 points；固定 schema 的 KG 则几乎不受 writer swap 影响。更危险的是 embedding 升级：50/50 混合旧／新向量只拿到 +4.96 points，而完整重建索引为 +11.90 points。同维度 embedding 不代表同一个向量空间。

  2. Computer-Use Agent 的目标不应是“更会点鼠标”，而是学会何时观察 GUI、何时切换结构化接口。 CUA-Universe 把真实桌面应用转成共享状态的 GUI+CLI 环境；9B 模型经混合轨迹 SFT 后，CUA-Verse Score 从 0.189 提到 0.582，同时步骤减少 37%、token 减少 60%。这支持“接口编排本身是一种可训练能力”，但并不证明 CLI 越多越好。

  3. Agent Planner 可以看得远，但 Commit Horizon 应该短。 TROVE 先从历史 workflow-search trace 蒸馏 composite skills 与 transition graph，在线规划最多 4 个顶层 skill，却每次只真正提交第一个；新 evidence 到来后只做 retain / insert / replace invalid suffix。它在 18 个 backbone–benchmark block 中 15 个取得最好或并列最好分数、16 个在线时间最短。这里更一般的原则是：保留已经验证的工作，只修改被新证据否定的未来。

  4. 自动化推荐研究的危险不只在“Agent 写错代码”，还在“错误实验改变了未来基线”。 网易 DASHEN 的 AutoLR 已累计 1,586 个完成的离线评估，并将 proposal、代码修改、训练、评估和实验状态串成长期 Harness；但论文同时暴露了 KEEP ratchet：一次不可复现的正向结果如果被提升为新 trunk，之后所有实验都会围绕这个错误基线继续比较。自动研究系统需要把“探索自由度”和“状态提交权限”严格分开。

  5. Layer Dropout 值得重新看，但它是结构化深度稀疏，不是传统 activation dropout 的复古。 《Don’t Drop Dropout》在 2,400+ 次训练实验、最高 8.2B 模型上报告，合适的 depth-wise distribution、时间 schedule 与优化器配置可节省最高 25% 训练 FLOPs，并让同一模型在 early exit、layer skipping 与 self-speculative decoding 中获得弹性深度；3.9B hero run 的 self-speculative decoding 为 1.54×。这项工作是 ICML 2026 论文的稍扩展版本，今天的新信号来自 arXiv 公布，而非全新首次发布。

  6. 今天几项工作的共同 lesson 是“测量边界必须显式”。 Memory 需要把 construction、retrieval、reading 分开；CUA 需要把 GUI/CLI 与共享应用状态分开测；TROVE 的在线时间不包含离线 workflow search；AutoLR 的线上 9 条 Launch Review 不能被算术求和当成 pooled treatment effect；Layer Dropout 的训练 FLOPs 节省也不能直接等同于所有硬件上的 wall-clock 加速。

1. Agent Memory Portability：换模型之前，先问旧 Memory 还能不能读

原始来源： Does Your Agent’s Memory Survive a Model Upgrade? A Controlled Study of Memory Portability

发生了什么

这篇工作把“长期 Memory”拆成四种常见实现：完整历史 LC-RAW、分块检索 RAG、模型生成的自然语言 NOTES、以及固定 schema 的 KG-fixed。研究使用 48 个合成历史、随机答案码、exact scoring，并让两个 10B 以下开放权重模型分别充当 memory writer / reader，从而直接测一次模型升级后旧 Memory 是否可迁移。

这个设计很重要，因为 Agent 升级至少可能在三个不同位置丢信息：Memory 写入时就被压掉；检索没有把正确证据送给新模型；证据已经送到，但新 Reader 对旧表示的解释发生变化。只看最终 answer accuracy 会把三类故障混在一起。

关键结果

Memory / Migration结果

NOTES：Qwen 读取继承笔记 vs 自己笔记-13.28 points

最需要记住的是 embedding 迁移。即使旧、新 embedding 维度一致，把两个版本的向量逐步混在同一 index 里也可能静默破坏几何关系。作者建议更稳妥的迁移方式是构建一个完全独立的新索引，完成后整体 cutover；如果必须渐进迁移，也应该按 embedding version 隔离向量空间并明确路由。

Repair 也有边界。只用旧 NOTES 重写，48 个 case 没有一个达到 90% recovery，因为已经被 writer 丢掉的证据无法凭空恢复；保留原始 history 后，一个迁移方向上 Qwen 能恢复 34/48，但另一个方向 Llama 因输出长度限制 0/48。相比之下，RAG 完整 re-embed 能恢复全部 96 个测试 case，单次约 0.013 美元。

为什么重要

长期 Agent 会持续升级 backbone、embedding、reranker、memory summarizer。只要 Memory 的生命周期长于模型版本，Memory format 就成为跨版本 ABI。自然语言笔记看起来最灵活，却可能把 writer 风格和能力直接编码进持久状态；结构化 schema 更可迁移，但会牺牲 schema 没表达的事实。

这里更实际的工程判断是：Memory 应尽量保存可追溯的 source evidence，派生表示可以重建；向量索引应该显式版本化；模型升级测试必须按 old writer → new reader 的方向测，不能只报告两个方向的平均值。

可信度与局限

这是一个受控、可解释的实验，优点是能定位故障层；局限也明显：只有两个相近规模的 10B 以下模型，历史是合成的，KG schema 还是围绕该任务预先定义的。因此不能从结果推出“知识图谱永远比自然语言 Memory 好”。

原始 history 作为 repair source 也带来隐私、安全与数据保留义务。保留一切只为了未来重建 Memory，并不是免费的工程建议。

最值得继续追踪

最值得扩展到真实 Coding / Research Agent：同一长期 workspace 在 Qwen、Claude、GPT、开源模型之间迁移时，哪些 Memory 字段真正具有模型无关性；以及 embedding、reranker、chunking 同时升级时，如何建立可自动化的 memory migration contract。

2. CUA-Universe：Computer Use 的下一步是 GUI 与 CLI 的“接口仲裁”

原始来源： CUA-Universe: A Scalable and Dynamic Environment for Hybrid GUI+CLI Agents

发生了什么

CUA-Universe 把真实桌面软件转成同时可被视觉操作与命令接口操作的共享状态环境。App-Forge 负责安装应用、发现原生 CLI、包装脚本 API，必要时生成 agent-native CLI；Task-Weave 从真实可执行能力中组合任务；Path-Steer 则把 rollout 引导到更高效的 GUI+CLI 路径，并把通过 verifier 的轨迹收集为后训练数据。

整个 snapshot 覆盖 16 个桌面应用、约 404 个 Agent 可见命令。训练数据最终保留 4,923 个 verified episodes、约 23.5 万 step records；Qwen3.5-9B 用 LoRA 训练 3 个 epoch，约 8×A100 两天。

关键结果

CUA-Verse 是 8 个应用 × 20 个 held-out task；应用本身仍属于训练期见过的 in-domain apps。

模型CUA-Verse ScoreStepsTokens / episode

在 OSWorld controlled scope 上，该模型的 GUI+CLI success rate 为 40.2%，相比自身 GUI-only 的 23.4% 更高，同时平均步骤与 token 明显下降。论文摘要还报告 OSWorld-MCP Score +7.84 points、步骤 -27%、token -30%。

一个容易误读的细节是：更多 CLI 并不等于更强。GPT-5.5 在记录的 CUA-Verse 轨迹里甚至达到 100% CLI share，但仍没有完全解决 benchmark；论文自己的分析也把关键能力定义为 cross-modality orchestration，而非最大化 CLI 调用率。

为什么重要

GUI 是人类界面，CLI / API / MCP 更接近机器界面。现实 Agent 如果永远通过截图找按钮，相当于每轮都把结构化状态重新视觉逆向一次；但完全依赖 CLI 又会失去布局、视觉反馈和 GUI-only 状态。

更合理的能力目标是：模型先判断哪种接口最能降低当前步骤的不确定性和成本，再执行，并保证两种接口作用于同一真实 artifact / application state。这个问题本质上是 Tool Routing，而不是纯视觉 grounding。

可信度与局限

训练、任务生成与 benchmark 构建来自同一框架，存在 pipeline–benchmark co-design bias；CUA-Verse 任务虽然 held-out，但应用本身 in-domain。任务 verifier 主要是 GPT-5.4 VLM Judge，并非全部使用程序化 oracle。

论文当前更能证明“混合接口数据可显著改变 9B 模型的执行策略”，还不足以证明这种训练能无缝泛化到完全没见过的软件和任意企业 GUI。

最值得继续追踪

看完全 held-out applications、multi-app workflow，以及把 API / MCP / DOM / CLI / GUI 一起纳入统一 interface router 后，能否按 success × latency × token × action count 自动学习最优执行路径。

3. TROVE：Planning 可以多步，但每次只承诺下一步

原始来源： TROVE: Adaptive Agent Skill Orchestration via Trace-Grounded Route Validation and Editing

发生了什么

很多 Agent workflow 在执行前就决定完整 DAG / Route。问题是中途一旦出现新 evidence，后半段计划可能已经失效；系统要么继续跑 stale steps，要么整段重规划，既浪费已有成果又增加 token。

TROVE 先离线从已评测的 workflow-search trace 中抽出 10 个 atomic skills、41 个 composite skills 和 244 条 executable transition edges。在线 Planner 最多提出 4 个顶层 skill，但系统只 commit 第一个；得到 boundary outcome 后，对未执行 suffix 做三种最小修改：retain、局部 insert，或 replace 无效后缀。

关键结果

在 HumanEval、MBPP、DROP、HotpotQA、MATH、GSM8K × DeepSeek-V4-Flash / GPT-4o-mini / Qwen3-8B 的组合中，TROVE 在 18 个 block 里 15 个取得最好或并列最好 task score，16 个在线时间最短。DeepSeek 六个测试分区的在线 token 从 AFlow 的 21.11M 降到 13.45M（-36.3%）。

几个更直观的点：

Backbone / TaskAFlowTROVE
DeepSeek · MATH74.07 / 68.88 min80.86 / 26.08 min
Qwen3-8B · MATH8.44 / 273.35 min36.42 / 36.41 min
Qwen3-8B · MBPP51.91 / 116.58 min83.28 / 41.84 min

最后一行很重要：TROVE 并非每个 setting 的 accuracy 都更高。它更稳定的优势是 quality–efficiency trade-off，而非统一支配。

Ablation 也很清楚：去掉 composite skills，Qwen3-8B HumanEval accuracy 从 92.37 降到 78.63；去掉 suffix replacement，accuracy 只降到 90.84，但耗时从 24.36 增到 40.15 分钟。Composite structure 主要贡献正确性，replacement 更偏效率。

为什么重要

这项工作的可迁移原则比具体 Skill Registry 更有价值：Proposal Horizon 可以长，Commit Horizon 应该短。 这和数据库事务、软件 patch、实验管理都有相同逻辑——已经验证的状态尽量不推翻，只重写尚未执行且已被新证据否定的部分。

对于 Research / Coding Agent，这种 route editing 也比每次失败都“重新思考完整计划”更容易保留局部成果和 provenance。

可信度与局限

论文的 online time 明确不包含一次性的 offline workflow search、controller training、registry construction 和 trace distillation。因此不能只拿在线分钟数直接比较“整个系统总成本”。六个 benchmark 也相对边界清晰，距离数小时甚至数天的真实工具任务还有差距。

此外，不同 backbone 的结果并不一致，GPT-4o-mini HumanEval 就出现速度换准确率的情况。部署时需要按任务风险决定 suffix editing 的 aggressiveness。

最值得继续追踪

在长程 Coding / Search Agent 上直接测“全局 replan 次数、被保留的有效工作比例、局部修复成功率、错误 suffix 执行 token”会比单一 task score 更能验证 TROVE 的核心机制。

4. AutoLR：自动推荐研究最关键的权限，是“谁能改变 Baseline”

原始来源： AutoLR: Automating the Path from Research to Launch Review in Industrial Recommender Systems

发生了什么

AutoLR 来自网易 DASHEN 游戏社区推荐。系统用 multi-expert council 做 proposal / review，用确定性的 evidence-weighted selector 分配有限实验预算，再把外部研究、生产约束、领域知识和历史实验事件放进分层知识系统。LLM 负责语义推理和代码生成；真正的训练、推理、指标提取、guardrail 和持久状态转换由 deterministic controller 掌权。

实现前还有 read-only preflight：检查文件、符号、feature 是否存在，禁止修改冻结的 objective / evaluator，并要求产出 machine-checkable activation evidence。失败事件也会按 semantic failure、reproducible code failure、transient infra failure 分开记录。

关键结果

审计从 4,250 条物理 ledger 记录还原出 1,586 个完成的非 baseline evaluation，其中 1,583 条保留 numeric scalar delta。论文另有 9 条 production Launch Review 记录，报告 engineer-selected candidate packages 在两个主要推荐场景中得到正向线上变化。

作者给出的三个线上相对 lift 的算术和分别是 content-consumption penetration +5.75%、总消费时长 +10.83%、valid views +5.55%。这里不能把它们当作合并 A/B effect：9 条记录是异质实验，论文明确说不 pooled，也没有完整 immutable offline→online lineage。

更值得读的是“KEEP ratchet”。历史 trunk-relative scalar delta 的 IQR 约为 $1.20\times10^{-3}$，与论文用于描述性 replay 的参考阈值 $10^{-3}$ 同量级。只要一次 one-run noise 恰好越过 promotion threshold，又被 KEEP 成下一轮 baseline，后续比较就会围绕这个噪声向上“爬”，形成看似单调的自动进步。

为什么重要

这是 Self-Evolving Recommender 很现实的治理问题。Agent 可以自由提出 100 个想法，但改变长期实验状态应该是高权限操作。好的 Research Harness 应该把：

可信度与局限

这是第一方工业系统报告，价值在长期运行数据，而非严格因果拆分。论文没有 matched-budget component ablation，无法回答 council、selector、memory 各自贡献多少；线上记录没有完整随机化原始数据、置信区间和统一 denominator。

论文也明确指出线上 A/B admission 与 full-traffic rollout 仍然由人工把关。因此 AutoLR 是“自动 research-to-review harness”，还不是无人值守自动上线系统。

最值得继续追踪

关注 repeat-evaluation、variance calibration、immutable experiment lineage 和 fail-closed promotion gate。自动研究系统成熟的标志，不只是每天能跑更多实验，而是错误结果越来越难污染未来基线。

5. Don’t Drop Dropout：用训练期随机深度，买推理期的弹性深度

原始来源： Don’t Drop Dropout: Optimizing Layer Sparsity for Efficient LLM Training and Inference

这不是传统 activation dropout 的回归。论文研究的是训练时随机跳过完整 Transformer block 的 structured layer dropout / stochastic depth。

发生了什么

作者系统扫描了 optimizer hyperparameters、dropout granularity、depth-wise distribution 和随训练步数变化的 schedule。推荐 recipe 是：越靠后的层允许更高 dropout，同时训练过程逐步降低 dropout rate，使模型有效深度随着训练推进而增长。

论文认为这一做法不仅是 regularization，还相当于提前训练一个“depth-elastic model”：推理时可以 early exit、跳中间层，或拿浅层子网络做 self-speculative draft，而不用额外改模型架构。

关键结果

大规模 hero runs：

ModelMax dropoutTraining FLOPs savingSelf-spec decode
1.8B0.615%1.34×
3.9B0.820%1.54×
8.2B0.9925%1.55×

3.9B dense baseline 在 alternate-layer skipping 下 cross-entropy loss 上升到 6.446，而 dropout-trained model 为 2.129。说明训练阶段见过“缺层”状态后，模型确实更能容忍推理阶段的深度削减。

为什么重要

LLM 推理优化通常发生在模型已经训练完以后：量化、spec decode、early exit、layer pruning 都在适应一个固定 checkpoint。这篇工作的方向相反：在 pretraining 时就把未来 serving 所需的结构弹性作为训练目标的一部分。

它和近期 Looped / Recurrent-Depth 讨论也形成有趣对照：一个方向让同样权重“多跑几次”增加隐式计算深度，另一个方向让模型“少跑一些层”适配不同延迟预算。两者都在把“深度”从 checkpoint 的固定常数变成 runtime 资源旋钮。

可信度与局限

这是 ICML 2026 已发表工作的稍扩展 arXiv 版本，因此不能包装成 9 月 7 日才出现的新方法。实验规模很大，但全部预训练在 Cerebras CS-3 上；论文没有直接比较 Mixture-of-Depths 等 learned depth routing，也没有验证 MoE / 非 Transformer 架构。

训练 FLOPs saving 也不自动等于所有 GPU/TPU 上相同 wall-clock saving，具体收益依赖 structured skipping 是否真的被系统实现为少算整层，而不是算完再 mask。

最值得继续追踪

最值得看的是与 learned routing、speculative decoding 和 serving SLO 联合优化：能否让同一个 checkpoint 根据请求难度动态选择有效深度，并在固定 quality target 下真正提高 requests/GPU-second。

今日值得收藏的代码 / 学习资源

addyosmani/agent-skills 是今天值得直接浏览的工程 Skill 仓库。它把 coding-agent 常见工程任务封装成可安装 Skill，目前仓库活跃更新，适合研究“Skill 作为可版本化 operational knowledge”应该怎样写，而不是把所有工程经验都塞进一个超长 system prompt。

sentient-agi/EvoSkill 更偏 Skill Evolution：从失败 trajectory 归纳、变异并验证可复用 Skill，适合和近期 Repo-To-Skill、Trace2Tower、TROVE 一起看。需要注意的是，自动发现 Skill 的效果仍高度依赖 benchmark / verifier；没有可靠评测的长期持续进化仍是开放问题。

今日最值得花 30 分钟阅读的一项

首选《Does Your Agent’s Memory Survive a Model Upgrade?》。

建议不要先看最终平均分，而按这个顺序读：先看四种 Memory format 和 RPAS 定义；再看 writer swap 为什么有明显方向性；随后重点读 embedding migration 的 old / full re-embed / 50-50 mixed / ideal router 四组实验；最后看 repair 与 failure decomposition。

这篇工作真正有用的地方，是把一个很容易被忽略的生产事件明确化：

模型升级，同时也是一次数据格式、检索空间和长期状态解释器的迁移。

只要 Agent Memory 的生命周期长于单个模型版本，这个问题就迟早会发生。相比“哪种 Memory benchmark 分数最高”，它更接近真实系统运维中会踩到的坑。

今日可立即实践的一件事

给现有 RAG / Agent Memory 做一次 Memory Migration Preflight。不需要真换模型，先挑 50–200 个带确定答案或人工可审计证据的历史查询，冻结旧系统，然后构造至少四个配置：

1
2
3
4

A. old reader + old store / old index        # 当前基线
B. new reader + old store / old index        # 只换 Reader
C. new reader + full new embedding index     # 完整迁移
D. new reader + 50/50 mixed embedding index  # 只作为故障诊断

至少记录 answer success、retrieval recall@k、MRR、unsupported-answer rate，并按迁移方向分别统计，不要把 A→B 与 B→A 平均掉。可以定义：

\[\Delta_{reader} = Acc(M_{new},S_{old})-Acc(M_{old},S_{old}),\]

以及：

\[\Delta_{embed} = Acc(I_{new,full})-Acc(I_{old}).\]

如果 D 的表现显著低于 C，即使两个 embedding 维度完全相同，也不要做同一索引内的渐进向量混写；采用 version silo + full cutover。对于 model-written notes，再随机抽样检查“旧笔记缺失的事实是否仍存在于 raw source”；如果事实已经在写入阶段丢失，换更强 Reader 没有意义。

停止条件： 任一 writer→reader 方向超过业务容忍阈值、mixed index 明显偏离 full re-embed，或 repair 依赖的 source evidence 已不可获得，就不要继续按普通模型升级发布；把它升级成独立的 Memory Migration 项目。

真正要回答的是：

新模型变强以后，它还能不能忠实继承旧模型积累的过去？

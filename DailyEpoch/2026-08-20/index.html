今日主线： 自进化 Agent 的评估稳定性 · Harness-native Agent RL · Multi-turn advantage 设计 · Long-context neural memory · Generative Slate Recommendation · RLVR rollout 调度

今日核心判断

  1. Self-improving Agent 现在最大的风险之一不是“平均分不够高”，而是结果对随机性、任务顺序和隐含 curriculum 过于敏感。 以后这类工作如果只报单次 run 和固定 task order，证据强度明显不够。
  2. Agent RL 正在从“把 agent loop 塞进 trainer”转向“让真实部署 harness 直接参与训练”。 Agent Lightning v1.0 与 LEGO-RL 同一天给出了高度一致的信号：context 构造、tool flow、compaction、retokenization 都属于优化问题的一部分。
  3. Multi-turn GRPO 类方法的 reward 不能只区分成功/失败。 如果两条成功轨迹一条 5 turn、一条绕了 20 turn，却获得完全相同 advantage，训练会系统性丢失规划效率信息。
  4. 长上下文不一定必须靠“每次重新读完整 context”。 MoNe 代表另一条路线：先用 test-time learning 把长上下文写入 fast-weight memory，再让 query 只访问 memory 产生的 KV。
  5. Generative Recommendation 正在从“生成单个 item ID”推进到直接生成有序 slate。 这会把候选生成、排序、item interaction 和 slate-level preference 更紧地耦合，但同时把在线约束、解码成本与安全边界也带进生成过程。
  6. RLVR 的 rollout budget 应该被视为一个在线资源分配问题。 最新工作开始利用样本之间的语义/推理相似关系共享 difficulty evidence，而不是给每个样本独立做昂贵 probing。

1. Self-Improving Agent：固定任务顺序可能偷偷充当了“隐藏 curriculum”

一句话结论： 如果一个自进化 Agent 换个 task order 就明显掉分，那么它学到的可能不是稳定能力，而是依赖任务排列的脆弱经验链。

论文： On the Fragility of Self-Improving Agents: Variance, Task Order, and Underspecification
代码： SalesforceAIResearch/self-improve-fragility
轨迹数据： Salesforce/self-improve-fragility

发生了什么

这篇工作重新评估 memory-based online self-improving agents，不再只跑一次固定任务序列，而是额外做两件事：多次重复运行，以及随机打乱任务顺序。

作者得到两个主要观察。第一，复杂环境和多步任务本身就有明显噪声，自我改进 loop 会进一步放大这种方差。第二，性能高度依赖 task order；一些既有实验中的默认顺序实际上形成了隐含 curriculum，前面的任务为后面的任务提供了刚好需要的经验。

作者进一步检查 memory 内容，认为 task / environment underspecification 是脆弱性的来源之一。把更详细的 rubric 和环境反馈加入 memory construction 后，退化有所缩小，但并没有完全消失。

为什么重要

这直接动摇了很多 self-evolving agent 实验里一个默认前提：

“随着任务流推进，曲线上升”不自动等于“Agent 真正持续变强”。

如果任务顺序本身提供了 curriculum，那么所谓 self-improvement 里混入了一个隐藏变量。更严格的评估至少应该同时报告 multi-seed、task-order shuffle、forward transfer 和 negative transfer。

可信度与局限

这篇工作的优势是公开了代码和轨迹数据，并直接复现、压力测试已有 memory-based 方法。局限也很明确：它主要证明“现有方法存在脆弱性”，并没有给出一个已经彻底解决该问题的新 self-improvement algorithm。

另外，随机打乱 task order 本身也不是完整答案。真实部署流量并非 IID 随机序列，生产环境更应该测试 domain shift、重复任务、突然出现的新工具以及长时间无关任务后的记忆恢复。

最值得继续追踪

以后看到 self-evolving Agent 论文，我会优先检查四个指标，而不是先看最终平均分：跨 seed 方差、跨 task-order 方差、negative-transfer rate、memory ablation 后的真实增益。

2. Agent Lightning v1.0 + LEGO-RL：Agent Harness 正式成为 RL 的一部分

一句话结论： Coding Agent 的 RL 目标不只是模型参数；真实 harness 如何构造 context、压缩历史、调用工具和恢复失败，会直接决定 rollout 到底是不是 trainer 以为的那条 trajectory。

Agent Lightning v1.0： 论文 · GitHub
LEGO-RL： 论文 · 文档 · GitHub

发生了什么

两项工作几乎同时把一个问题推到台前：真实 Agent 通常由 harness 掌控 environment loop，trainer 只在模型 API 边界看到一串 request-response pair。

这会产生传统单轨迹 RL 很少遇到的问题：

  • harness 重新序列化历史后，相同文本可能被 retokenize 成不同 token ID；
  • context compaction、sub-agent 和 handoff 会让一次 rollout 对应动态数量的 training sample；
  • 如果按 sample 而不是 rollout 做 loss normalization，产生更多 model call 的轨迹可能被意外赋予更大训练权重；
  • environment crash、test harness 配置错误和 reward hacking 会把错误信号混进 policy gradient。

Agent Lightning v1.0 用 API Gateway / proxy 捕获真实调用，再由 trainer 组装训练样本；LEGO-RL 也采用 harness-native 思路，并重点保证 rollout-time token 与 training-time probability 对齐。

关键结果

系统模型 / HarnessSWE-bench Verified：训练前训练后
Agent Lightning v1.0Qwen3.5-9B41.8%56.4%
LEGO-RLQwen3.5-35B-A3B / OpenHands SDK64.0%70.4%
LEGO-RLQwen3.5-35B-A3B / Claude Code62.4%68.2%
LEGO-RLQwen3.5-35B-A3B / OpenCode57.2%66.6%

Agent Lightning 报告 coding-agent run 只使用 6K training examples；LEGO-RL 报告 rollout-training probability correlation 保持在 0.99 以上。

为什么重要

这两篇工作的真正价值不是又刷新了一次 SWE-bench，而是把 training-serving mismatch 具体化了。

过去很多 Agent RL 实现默认：

1

rollout trajectory == trainer reconstructed trajectory

在真实 harness 里，这个等式并不天然成立。只要历史被重写、压缩、切成 sub-agent，trainer 就必须明确保存“这个 action 当时究竟在什么 prompt/token state 下被采样”。

可信度与局限

两项结果都仍然主要是作者自报告，而且 SWE-bench Verified 本身不能覆盖长期运行 Coding Agent 的全部可靠性问题。另一个现实限制是：harness-native 训练虽然减少了部署差异，却提高了系统复杂度——sandbox、API proxy、token capture、weight sync、reward verification 都必须同时正确。

因此，不应该把 14.6 个百分点或某个 harness 上的 9.4 个百分点增益直接归因于某一种 RL 算法；框架、数据清洗、reward 防护和执行环境共同参与了结果。

最值得继续追踪

最值得追的是 call-level on-policy semantics：当 Agent 发生 compaction、branch、sub-agent spawn 和 handoff 后，advantage 到底应该如何跨多个模型调用传播，同时又不破坏每次调用真实的 sampling state。

3. PlanPO：成功轨迹之间也需要“有差别的 advantage”

一句话结论： 对 multi-turn Agent，只用最终 0/1 成功奖励会把“干净规划”和“绕路成功”压成同一种正样本。

论文： PlanPO: Group Planning-Aware Policy Optimization for Multi-Turn Agentic LLMs

发生了什么

PlanPO 针对 group-relative policy optimization 的一个典型退化：同一个任务的一组 rollout 如果都成功，就可能拿到完全相同 outcome reward，导致成功样本之间的 relative advantage collapse。

作者加入 coarse-to-fine 的 planning-aware signal：在同任务的成功轨迹中，同时比较trajectory-level interaction length和turn-level response length，让更高效的成功行为能够获得更明确的相对学习信号。

关键结果

作者报告，在 ALFWorld、WebShop 和 SciWorld 三个 multi-turn benchmark 上，PlanPO 相比 GRPO 平均提升 27.2%，并声称额外训练成本可以忽略。

为什么重要

对 Agent 来说，“成功”不是单一质量维度。真实系统还在乎：

  • 用了多少轮交互；
  • 调了多少次工具；
  • 是否重复观察同一状态；
  • reasoning 是否出现明显冗余；
  • 是否在成功之前制造了不必要的风险动作。

PlanPO 的价值在于把其中一部分效率信号重新注入 group-relative advantage，而不是把所有 successful rollouts 当成等价正样本。

可信度与局限

这里最大的风险是把“短”误当成“好”。作者明确试图避免退化成简单 length minimization，但长度仍然只是规划质量的 proxy；对于需要反复验证、审计或安全检查的任务，更短的 trajectory 未必更优。

27.2% 是跨三个 benchmark 的平均相对提升，不应外推成任意 Agent RL 都能获得同等级收益。

最值得继续追踪

下一步更值得做的是把 trajectory efficiency 扩展成多维 process utility：turn 数、tool cost、失败恢复、重复动作、风险动作和最终质量共同参与 advantage，而不是只有长度。

4. MoNe：把长 Context 写入 Fast-Weight Neural Memory，再做 O(1) Query

一句话结论： MoNe 试图把“长上下文推理”从持续 attention 全文，改成一次线性写入 + 后续常数级查询。

论文： MoNe: Modular Neural Memory for Efficient Long Context Inference

发生了什么

MoNe 是外挂在 frozen pretrained Transformer 上的 modular neural memory，不要求重新训练 backbone。它先把长 context 按固定 segment 顺序读入，通过 test-time learning 更新 layer-local fast-weight memory；真正回答 query 时，不再重读 context token，而是由 memory 仅根据 query token 生成对应的 key / value。

作者把复杂度描述为：context preprocessing 为 $O(N)$，后续 query cost 为 $O(1)$，并且 peak GPU memory 不随 context length $N$ 增长。

关键结果

在 128K context 下，论文报告：

指标相对常规 ICL
计算量约降低 80%
Peak GPU Memory约降低 80%
额外参数6.4%

作者还在 RULER 的 needle-in-a-haystack 与 word extraction 任务上测试了超出 backbone 原生窗口的长度，报告 MoNe 在 ICL 明显退化时仍能保持较强表现。

为什么重要

这条路线和 RAG、KV compression 的思路不同。RAG 先选内容，KV compression 先保留部分 token；MoNe 更像把完整长 context 编译成一个可查询的参数化状态。

如果同一份长文档会被反复查询，那么一次 preprocessing 成本有机会被多次 query 摊薄，这可能是它最有实际价值的场景。

可信度与局限

目前最强证据仍集中在 retrieval / extraction 类型长上下文任务。真正复杂的跨段推理、精确引用、频繁更新 context，以及 memory 写入时的遗忘/覆盖行为，还需要更广泛验证。

另外，$O(1)$ query 指的是相对 context length 的复杂度，不等于“真实延迟恒定且极低”；memory network 本身仍有固定计算成本。

最值得继续追踪

我会重点看三件事：同一 context 多次 query 时的 amortized latency、复杂 multi-hop reasoning 的保真度、动态增量更新 context 时是否必须重新完整写入 memory。

5. OGR：从“生成 Item”推进到“直接生成有序 Slate”

一句话结论： Generative Recommendation 开始尝试同时解决 candidate generation、ranking 和 slate-level interaction，而不是先生成候选再交给传统 ranker。

论文： Once Generated, Ranked: End-to-End Generative Slate Recommendation with Unified Semantic-Collaborative IDs

发生了什么

OGR 把 slate 直接作为生成目标。它首先提出 TUSID，把 item-specific semantic information 与 local collaborative signal 融合成 hierarchical Semantic ID；随后通过 list-wise preference planning 和 pipelined position-wise SID decoding，逐位置生成已经排好序的 slate。

在 likelihood imitation 之外，作者还提出 SPA（reward-guided conservative policy optimization），直接让生成 slate 对齐用户偏好，而不只优化 next-token likelihood。

关键结果

场景指标报告结果
工业离线数据NDCG@5 相对提升+48.2%
公开数据NDCG@5 相对提升+27.2%
快手线上 A/BEffective Views+1.120%

为什么重要

传统 slate recommendation 通常受限于已经召回的候选集合；OGR 的目标是直接在生成空间里联合处理 item interaction 与排序。

这意味着生成模型的优化对象从：

1

next item / next SID token

进一步变成：

1

ordered slate utility

对于多样性、互补性、重复内容抑制和位置依赖，这个建模单位比单 item 更贴近最终展示页面。

可信度与局限

线上 A/B 是这篇工作最有分量的证据，但只有一个平台和一个主指标，外部无法判断长期留存、多样性、延迟、GPU 成本与冷启动上的完整 trade-off。

另外，离线 +48.2% 是相对 NDCG 提升，不应和“线上收益提升 48.2%”混淆。端到端生成 slate 还必须面对业务里的强约束，例如去重、库存、广告、内容安全和 hard filtering；这些约束如何与 autoregressive decoding 协同仍然是部署难点。

最值得继续追踪

最值得看的是 生成 slate 的在线约束注入机制：哪些约束放在 decoding mask，哪些作为 reward，哪些仍应交给 post-ranking / rule layer。完全去掉传统 ranker 并不是天然正确答案。

6. RLVR Scheduling：Rollout 数量不应该对所有样本一视同仁

一句话结论： RLVR 的 rollout budget 可以像推荐曝光一样做在线分配：容易样本少采，困难但可学样本多采，关键是 difficulty estimate 不能本身比 rollout 还贵。

论文： Efficient RLVR Scheduling via Graph-Structured Online Difficulty Estimation

发生了什么

这项工作认为统一 rollout budget 很浪费：easy sample 会被重复探索，而 difficult-but-learnable sample 可能没有获得足够尝试。问题在于在线 difficulty estimation 本身也很贵——专门 probe 会增加 generation cost，只靠历史又有 cold start 与 stale feedback。

作者把样本按 semantic similarity 与 reasoning similarity 构成图，给节点分配 latent difficulty state；用 Potts prior 鼓励相邻样本共享状态，再通过 state-level Beta-Binomial 聚合 rollout outcome，并用在线 mean-field variational update 持续修正 difficulty。

为什么重要

它本质上在做一种 shared statistical exploration：一个样本刚开始没有历史时，可以借相邻样本的 rollout evidence 推断难度，而不是必须先自己烧掉一批 probing token。

这对 RLVR 很现实，因为 rollout 往往才是训练成本里最大的部分之一。优化 scheduler 有时可能比继续微调 optimizer 超参数更直接地提高单位 GPU-hour 的有效学习信号。

可信度与局限

论文摘要只说明在多个 base model、scheduler 和 benchmark 上获得更好表现，没有在摘要中给出统一的 effect size。因此目前更适合把它视为一个值得验证的调度思想，而不是已经证明普适高收益的配方。

图上的“相似样本应具有相似难度”也是一个建模假设。语义相近的问题可能因为一个关键推理步骤而难度完全不同，错误的图传播会造成 under-exploration。

最值得继续追踪

真正该比较的是固定总 rollout token / GPU-hour 下的 Pareto：最终 reward、训练稳定性、样本覆盖率、难题 solve rate，以及 difficulty estimate 的校准误差。

今日值得收藏的代码 / 学习资源

1. Microsoft Agent Lightning v1.0：目前最值得直接读代码的 Agent RL 工程之一。仓库把 Trainer、API Gateway、Rollout Controller 拆得很清楚，并给出了完整 Coding Agent pipeline、数据清洗、reward-hacking prevention 与训练脚本。

2. LEGO-RL 文档：如果想理解“native harness 为什么会破坏 rollout-training alignment”，它的 architecture、reward hacking、run validation 和 monitoring 文档比只读论文摘要更实用。

3. Self-Improve Fragility Code + Trajectory Dataset：适合拿来做 self-evolving Agent 评估协议复现，尤其是 multi-run 与 task-order shuffle。

今日最值得花 30 分钟阅读的一项

首选：Agent Lightning v1.0: Towards Harnessed Agentic RL。

建议不要从 benchmark 表开始，而按下面顺序读：

  1. 先理解 traditional agentic RL 与 harnessed agentic RL 的状态差异；
  2. 看 retokenization 为什么会让“文本前缀相同”却无法安全 merge token trajectory；
  3. 看一个 rollout 映射成动态数量 training samples 后，advantage 和 loss normalization 为什么会变得不再简单；
  4. 最后再看 6K coding data 与 SWE-bench 结果，以及仓库里的 Coding Agent recipe。

这篇最值得读的原因不是 56.4% 这个数字，而是它把 Agent RL 中大量容易被当成“工程细节”的东西重新定义成了算法正确性条件。

停止条件也要明确：

  • 只要两个连续 call 在重新 tokenization 后不能满足 exact token-prefix equality，就不要把它们强行 merge 成一条 token trajectory；
  • 如果 training_samples_per_rollout 与 loss_weight_per_rollout 呈明显正相关，先检查是否误用了 sample-level normalization；
  • environment / verifier failure 必须单独标记，不能直接当成 policy failure 写入 reward。

这套检查不会直接让 reward 上升，但能先确认一个更基础的问题：你更新的 policy，究竟是不是在它真实采样过的状态上被优化。

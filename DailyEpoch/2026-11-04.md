## 1. WeSearch：微信搜索为什么选择“簇召回 + 原子文档打分”

**原始来源：** [论文](https://arxiv.org/abs/2611.00530) · [HTML 全文](https://arxiv.org/html/2611.00530v1)。**论文 v1：2026-10-31；本次进入 7 天补充窗口。**

### 发生了什么
腾讯微信搜索团队公布模型主导的两段式检索：先用查询向量找到多个相关语义簇，再对这些簇中的原子文档做粗排和细粒度匹配。簇只约束候选空间，不要求一篇包含多个话题的文章被绑定到唯一层级 Semantic ID。在线系统保留语法树检索分支补充精确匹配，另用 OPQ、非对称距离计算、文档增量挂载和滚动训练降低索引更新成本。

### 关键结果
作者报告已覆盖微信搜索全部生产流量；一个月全流量 A/B 的 CTR **+0.68%**、人均文章点击 **+2.27%**、检索资源成本 **-41%**，图文召回延迟 **-19 ms**。各指标的统计口径不同，不能把 CTR 的相对增幅当作绝对百分点。

### 为什么重要
这为“Embedding 多路检索 + 固定 SID 生成”以外的工业检索架构提供了公开案例。多主题文档的相关性依赖查询：先在查询侧选语义区域，再用文档侧模型判断细粒度相关性，可以减轻前缀错误剪枝和多路检索维护成本。

### 可信度与局限
有线上 A/B 与完整的工业系统章节，证据强于只有离线 Recall 的预印本；但这是单一产品环境的内部实验，文档集、流量、设备成本和消融细节不一定能独立重现。**值得追踪：** 同等 Recall、P95 和更新延迟下，对比 ANN+Rerank、SID Beam Search、簇约束候选的真实 cost-per-success；尤其追踪新增文档的冷启动召回。

## 2. Atomic Creator Token：Semantic ID 不适合所有推荐对象

**原始来源：** [论文](https://arxiv.org/abs/2611.00323) · [HTML 全文](https://arxiv.org/html/2611.00323v1)。**v1：2026-10-30；七天补充窗口。**

### 发生了什么
Meta 研究团队指出创作者推荐的 SID 量化通常存在多对一碰撞，最终必须用流行度兜底选出实体，还阻断从下一创作者目标对实体表示的端到端梯度。ACT 给每个符合门槛的创作者分配唯一可学习 token，推理对 token logits 直接做 Top-k；不再需要 SID 反查与碰撞消解。

### 关键结果
在作者控制 token 层这一主要变量的生产数据实验中，ACT 的创作者级 Recall@15 相比 SID 基线高 **19.8 个百分点（约 1.84×）**，单用户推理延迟约为基线的 **1/2.7**；在线 A/B 指标报告为方向性正向，不能据此声称具体 CTR/收益数值。

### 为什么重要
“生成式推荐 = 必须使用 RQ-VAE/SID”是过强假设。候选规模受控、每实体训练样本充足时，直接输出原子实体可能带来质量、部署与可解释性上的优势；SID 更适合极大规模可组合码空间。

### 可信度与局限
结果依赖头部创作者集合和曝光分布。一实体一 token 增加输出词表及训练开销，不适用于数亿低频长尾对象。**值得追踪：** ACT+传统长尾召回的混合路由、增量创作者入表、热门偏置与冷启动，尤其是对新实体与高频实体分别测 Recall。

## 3. EvoRec：推荐系统自我进化必须有“反思—验证—复用”闭环

**原始来源：** [论文](https://arxiv.org/abs/2611.01977) · [HTML 全文](https://arxiv.org/html/2611.01977v1) · [项目页](https://mtli-buaa.github.io/evorec-project-page/)。**v1：2026-11-01；72 小时扩展观察。**

### 发生了什么
快手本地生活广告团队将需求推断、检索预算分配、工具选择与排序融合放入 Agent 决策链。用户反馈出现后，Dynamic Reflection Tree 把失败定位到需求理解、规划或历史修复建议，通过轨迹回放验证补丁，再将可信修复放入个人工作记忆并抽象为跨用户经验；不要求每次都改模型权重。

### 关键结果
作者报告离线 Hit@50 相对最强基线 **+15.7%**，已修复用户上的层级反思带来 **+13.1%**；七天近线在线实验广告收入 **+4.6%**、CTCVR **+3.5%**，高意图群体广告收入 **+14.5%**。这些是特定广告业务数据，不能视为一般商品推荐的通用收益。

### 为什么重要
推荐 Agent 需要回答“为什么没推荐中”，并把结果转为可复用的策略或工具参数，同时避免把随机一次转化当成有效反思。**值得追踪：** 修复策略的独立 holdout 收益、无效策略撤销、漂移环境中的回退率，以及相对传统 Contextual Bandit/Policy Learning 的增量价值。

### 可信度与局限
工业线上实验为正面证据，但论文未提供可直接独立跑通的生产平台。反馈强烈受曝光选择和竞争干预影响；反思命中率并非反事实因果证明，需单独测量增量效果。

## 4. ParallACT：并行 Coding Agent 在共享仓库里会互相破坏

**原始来源：** [论文](https://arxiv.org/abs/2611.00314)。**v1：2026-10-30；七天补充窗口。**

### 发生了什么
ParallACT 构造“互补任务”和“互相矛盾的任务”：两个 Agent 各自实现时局部成功，但合并后可能接口不对齐或同时修改同一代码区域。对比条件包含顺序执行、协作意识、可见性及通信信道；单 Agent Oracle 可以一次看到合并后的全部需求。

### 关键结果
以论文列出的 Claude Code + Claude Opus 4.8 冲突任务为例，统一看到要求的 Oracle 成功率约 **62%**，并行协作配置只有 **16%**。仅提示存在同伴几乎无益，添加通信也只追回小部分成功率并增加 Token。

### 为什么重要
这是典型的组合正确性问题：两个正确的局部 Patch 不等于正确的全局交付。设计多 Agent 时，应优先建立文件/模块所有权、接口规格和集成测试，而不能只靠一个聊天频道来消解写入冲突。

### 可信度与局限
人工设计的冲突基准可能夸大极端竞争任务在日常工程中的占比，Oracle 还拥有信息优势。**值得追踪：** 仓库级真实 PR 并发、独立任务效益与冲突频率、预先锁定文件所有权后的成本曲线。

## 5. Continual Harness Evolution：Agent 自我改进也会灾难性遗忘

**原始来源：** [论文](https://arxiv.org/abs/2611.03219) · [代码仓库](https://github.com/THU-Agent/continual-harness-evolution)。**v1：2026-11-02；72 小时扩展观察。**

### 发生了什么
研究对两种 Harness 演化方法进行连续多任务实验：先在一个软件工程数据集上改好策略，再连续优化另一数据集，并在旧任务上复测。它挑战了“每次自我演化都会累积性能”的默认设想。

### 关键结果
论文举例：DeepSeek-V4-Flash-0731 搭配 Meta-Harness，在 SWE-Bench 经第一阶段演化达到 **94.0%**，随后在 FeatureBench 连续演化，第五轮旧任务分数降至 **32.0%**，相差 **62 个百分点**。论文摘要将该变化描述为相对下降 66%；这里明确区分绝对百分点与相对比例。

### 为什么重要
知识库、System Prompt、Tool Schema、Skill Registry、规划模板都属于可回归的软件接口。自我进化不能只评价当前训练目标，应像 CI 一样保存历史能力测试与回滚点。

### 可信度与局限
这是方法与任务组合下的实证失败案例，并不证明所有 Harness 都必然遗忘。**值得追踪：** 多任务回放、Pareto 验证门禁、旧任务权重、可逆 Skill 版本化是否能够阻止退化。

## 6. Early Stopping Audit：节省 Reasoning Token 不能以可靠性缺口换取

**原始来源：** [论文](https://arxiv.org/abs/2611.00166) · [代码](https://github.com/hung20gg/audit-early-stopping)。**v1：2026-10-30；七天补充窗口。**

### 发生了什么
作者提出用统一 Rollout Replay 比较不同早停控制器，引入 Target-Integrated Token Efficiency（TITE）衡量跨准确率目标的效率，并检查停止后正确性、解释质量和跨模型迁移。

### 关键结果
在五种推理模型与数学、科学、代码、事实性任务中，出现“推理延长后答案正确性反而下降”、停止后仍继续推理和正确答案缺乏完整支撑等现象。论文没有支持所有早停算法可无损替换完整推理的结论。

### 为什么重要
早停不仅是阈值校准：必须算上控制器推断成本、误停概率和任务风险。在高价值工具调用、金融决策或代码修改中，错误高置信停止可能比多花几十 Token 严重。

### 可信度与局限
统一 replay 强化了可比较性，但离线重放不能完全反映实时解码机制与工具交互。**值得追踪：** 等正确率下 Token/P95 曲线、OOD 置信校准、停止后执行轨迹能否复现。

## 7. MXCode：超低比特权重如何映射到原生 FP4 计算

**原始来源：** [论文](https://arxiv.org/abs/2611.00403)。**v1：2026-10-30；七天补充窗口。**

### 发生了什么
MXCode 结合 Vector Quantization 与 MXFP4：PostScale、PreScale、PreScale+ 三种方法处理码书、共享 scale 与编码开销，目标是把近 2-bit/weight 存储的权重重建为硬件可用的 W4A4 运算，而不必先展开为高精度全量矩阵。

### 关键结果
论文在 Qwen3-235B、DeepSeek-R1-671B 和 GLM-5.2-753B 上评测，并报告 GB300 上 Qwen3 的模型加载占用相对原生 FP4 减少约 **50%**，服务吞吐接近原生 FP4；在特定内存受限、前缀复用负载下，P90 TTFT 改善**最多 94.5%**。这不是通用吞吐提升 94.5%。

### 为什么重要
“平均 bit 数”无法决定性能：格式解码、码书访存和原生 Tensor Core 指令路径可能吞掉压缩收益。**值得追踪：** 硬件真机端到端 Token/s、不同 Batch、Prefill/Decode、代码本与 scale 额外占用、复杂 Agent 任务准确率。

### 可信度与局限
跨模型质量结果依赖量化设置与业务负载；部分实验使用模拟库，硬件指标也只覆盖特定配置，不能外推到 RTX 4080 等非 GB300 平台。

## 8. BasisKV：把 KV 低秩压缩从存储问题扩展到跨 GPU 通信

**原始来源：** [论文](https://arxiv.org/abs/2611.02583) · [代码](https://github.com/alexz949/BasisKV)。**v1：2026-11-02；72 小时扩展观察。**

### 发生了什么
BasisKV 联合优化张量并行分片的低秩 Value 表示，在减少 Value Cache 宽度的同时压低通信；并复用 Value 潜变量预测需要访问哪些 Key Page，仅对选中页恢复/访问原始 Key，计算精确 QK 分数。

### 关键结果
作者在多种模型和系统设置中报告相比低秩基线更好的质量—效率折中，**八卡张量并行最多 1.42× 端到端加速**。指标限定于通信密集型长上下文场景。

### 为什么重要
KV Cache 优化要放进整个推理拓扑：单卡上减少 HBM 使用未必换来同样的多卡吞吐收益。**值得追踪：** Key Page 路由错召回、长上下文证据丢失、NVLink/PCIe 带宽变化和不同并行度的质量—吞吐前沿。

### 可信度与局限
所列最大倍数来自作者配置；通用解码负载中通信不是瓶颈时，额外路由与重建成本可能抵消收益。

## 9. Web Agent 静默抓取失败：HTTP 200 不等于拿到了证据

**原始来源：** [论文](https://arxiv.org/abs/2611.00884)。**v1：2026-10-31；七天补充窗口。**

### 发生了什么
研究使用静态 HTTP 客户端和渲染浏览器抓取来自 1,507 个站点的 **10,307 个 URL**，包括 4,795 个用于 ExpertQA 的引文来源，区分主体内容、机器人挑战、JS Shell、软 404、占位页和不完整正文。

### 关键结果
自动标记发现，静态客户端收到 HTTP 200 的页面中约 **20.9%** 没有目标主体内容；人工/复核子样本下估计约 **20.0%**。仅看 200 将可校验来源占比高估 **12.2 个百分点**；通过文本长度、随机路径探针和重定向检测可找回约 **86%** 无效页面（误报约 5%）。

### 为什么重要
Agent 的检索、网页浏览与引用验证最容易出现“技术链路成功但证据为空”的假阳性。只在工具调用日志里记 `status=200` 会同时污染答案可信度评估和自动评分。

### 可信度与局限
测量依赖站点和抓取工具，自动分类样本的人工复核规模有限。**值得追踪：** 动态页面渲染与登录状态、正文定位置信度、强制 citation-span 对齐及有无原文证据时答案质量差异。

## 10. Session Success Rate：生成式 AI 搜索应识别“好放弃”

**原始来源：** [论文](https://arxiv.org/abs/2611.01582)。**v1：2026-11-01；72 小时扩展观察。**

### 发生了什么
微软研究团队基于人工审阅的完整搜索会话、隐私保护的交互与录屏标注，训练 Session Success Rate（SSR）。由于搜索结果页面直接回答问题，用户不点击链接可能正是完成任务；点击也可能是不满意后的继续探索。

### 关键结果
6,904 个标注 Query 上，SSR 的 Balanced Accuracy 约 **0.75**；在无点击会话上约 **0.68**。样本里 **53.2%** 无点击会话被认定成功，**6.5%** 有点击 Query 被认定失败。约 4,000 个生产实验中 SSR 的二元统计灵敏度约为 Sessions per User 的 **2.5×**（论文特定设置）。

### 为什么重要
AI Search 首页 Banner、答案卡片、理财产品问答与复杂任务完成率评估，需要减少“更多点击 = 更高价值”的代理指标偏差。推荐/搜索 A/B 应把用户最终成功、重复搜索及后续留存结合起来。

### 可信度与局限
SSR 是训练得到的代理指标，其无点击场景 Balanced Accuracy 仅 0.68；录像标注和模型可能存在选择与标签偏差。**值得追踪：** 与长期满意度、投诉、任务完成、自愿人工回访的关联；分人群和低频 Query 校准。

## 11. ISA-Distill：Search Agent 的教师模型不该“知道学生不知道的答案”

**原始来源：** [论文](https://arxiv.org/abs/2611.01987)。**v1：2026-11-01；72 小时扩展观察。**

### 发生了什么
On-policy 搜索蒸馏常把正确答案和额外证据给教师模型；教师在知道事实的前提下可能低估“继续检索”的价值。ISA-Distill 估计学生对关键事实的可恢复性，将教师反馈拆为“事实使用”和“主动找证据”两个视角；学生当前不易获取事实时，提高证据搜索反馈权重。

### 为什么重要
蒸馏时信息不对称会造成工具策略偏置。若 Teacher 已看到答案，对 Student 的多跳检索动作给负反馈，可能训练出过度自信、欠检索的 Agent。

### 可信度与局限
论文报告多 QA 设置的准确率和检索效率改进，但代码与 Checkpoint 在论文中仍表述为“将开源”，本轮未把它计为已可复现项目。**值得追踪：** 可恢复性估计误差、工具预算、教师信息泄漏控制，以及 OOD 任务的证据召回。

## 今日最值得花 30 分钟阅读的一项

**[WeSearch: A Unified Model-Centric Retrieval Framework for WeChat Search](https://arxiv.org/html/2611.00530v1)**。

- **前 8 分钟：** 阅读第 3 节，两段式簇召回与文档细粒度打分，画出 query → cluster → candidate docs → re-rank 链路。
- **中间 12 分钟：** 阅读第 4、5 节，关注难负样本、OPQ/ADC、滚动挂载与周级模型刷新，区分模型收益与服务系统收益。
- **最后 10 分钟：** 阅读第 6 节，核对 Semantic ID 对比与一个月 A/B，思考同样的结构放到电商多模态商品检索时，如何处理品牌、属性与新品的候选覆盖。

带走的问题：**固定检索成本、更新时延和召回质量约束下，什么时候使用 query-specific clusters 比固定文档 Semantic ID 更合适？**

## 今日可立即实践的一件事

**为 ShoppingAgentLab 做一个最小“查询簇约束召回 vs Semantic ID 前缀召回”离线对照。** 从真实购物查询中选取 60—100 条，分为同款商品、属性约束、跨品类搭配和多意图长 Query；固定商品集合、Embedding、总召回候选数与 Reranker，构建三条通路：

1. 直接 Dense Top-k + Rerank；
2. 商品聚簇 → 查询检索多个簇 → 合并簇内商品 → Rerank；
3. 已有 Semantic ID/前缀生成候选（如未实现，则明确标记未跑，不用假数字填表）。

记录 Recall@50、NDCG@10、硬约束违反率、跨类别召回覆盖、**新上架商品召回率**、P95 与每成功查询检索成本。按查询类型和商品冷启动程度分别汇报，不用单一总体 Recall 掩盖长尾退化。若缺乏训练好的生成检索器，今天先完成前两条和实验日志协议，第三条列入后续。

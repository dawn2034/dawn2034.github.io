今日主线： AI R&D Automation · Adaptive Reasoning · Formal Proof Agents · Long-Context MoE · Local Long-Context Serving · Slate-Level Credit

今天是周一早上，按 arXiv 的公告节奏，最新常规批次仍是 2026 年 9 月 18 日。与其把周末的二手新闻重新包装一遍，今天更值得抓住几条正在形成长期结构变化的线索：前沿实验室第一次把“AI 到底参与了多少 AI 研发”量化成可持续追踪的指标；推理模型开始直接学习何时值得 Think、何时应该 NoThink；科研 Agent 的价值开始从生成答案转向生产可机器验证的大型形式化工件；训练和 Serving 两端则继续把长上下文问题从“模型能力”拆成具体的内存峰值、状态生命周期与调度问题。推荐／搜索侧也出现了一个值得复用的训练原则：列表级目标和单项质量需要不同层级的 credit，而不是被压进一个统一标量。

今日核心判断

  1. “AI 正在帮助开发下一代 AI”已经可以被测量，但现有数据仍不能证明完整 RSI。 Anthropic 9 月 18 日公开 R&D Automation Index：截至 2026 年 8 月，Claude 在 26% 的 AI R&D 工作上达到“AI leads”，超过 90% 的工作达到“AI collaborates”或更高；没有任何被测子集达到完全自主。其最常用内部 Agent 平台同时运行约 30,000 个研究／工程 Agent，8 月超过 10 亿次 Agent 决策中约 0.002% 被在线监控阻断。真正值得追踪的是这一指数接下来能否跨实验室、跨第三方审计持续复现，而不是把 26% 直接写成“RSI 已经发生”。

  2. 推理效率正在从“统一压缩 CoT”转向按样本学习计算预算。 When2Think 用预计算的难度／Token 统计构造 Instance-level Difficulty-Aware Control，让模型自己学习 NoThink 与 Think 的切换。AIME24 上相对 Base，Pass@3 提升 10.0%，同时 Token 使用下降 27.9%；AIME25 达到 40.0% Pass@3。它最重要的信号是：Test-Time Compute 不应只做固定长度或统一惩罚，而应成为实例级 Policy。

  3. 长程科研 Agent 开始交付“可机器验证的研究基础设施”，而不只是自然语言答案。 FormalFlow 在人类监督下，用共享 Blueprint 协调规划、证明和审查 Agent，63 天完成 MIP* = RE 核心定理相关的 Lean 4 形式化；最终库 126,367 行 Lean 代码均由 Agent 生成，并修正了原证明中的若干 side condition 与中间错误。这个结果的意义来自 Lean Kernel 的机器检查；同时它仍是一个高度监督、目标明确的形式化工程项目，不能外推成自主数学发现已经成熟。

  4. 1M Context 的 MoE 训练瓶颈不是单个“大显存问题”，而是多个互不相同的峰值取最大值。 Salesforce 的工作把 expert dispatch、vocab projection、checkpoint boundary、optimizer state 四个峰值分别变成有界流式调度；组合后在 120B–667B MoE 上训练到 1M Context，Context reach 是调优 FSDP2 的 8–32×，最高吞吐 10.4×。工程上最值得带走的是：只消掉当前最大峰值，通常只是把 OOM 移到下一个峰值。

  5. 本地长上下文 Serving 的重点已经从“权重装得下吗”转向“执行状态什么时候必须驻留”。 JustFit 在 24 GiB M4 Pro 上运行 Qwen3.8-27B MXFP4，通过 KVExec、PhaseSwap、StateTrans 管理 KV 与组件生命周期，完成 196,608 输入 + 16,384 输出，即单请求 212,992 positions，是 mlx-vlm baseline 的 6.93×。32K 输入／64 输出 probe 达到 19.11 tok/s。这个结果证明的是状态生命周期管理可以大幅扩大本地 Context Capacity，并不意味着所有 200K 工作负载都能保持 19 tok/s。

  6. 生成式推荐／搜索的 Credit Assignment 正在显式区分“单项质量”和“整个 Slate 的多样性”。 一项生产 Query Suggestion 工作先用 Intent-Aware Diversity Reward 优化列表意图覆盖，再把单个 Query 的质量信号路由到对应 Query Token，同时把 Slate-level diversity signal 共享给整组 Query。论文报告大规模生产数据上的离线和线上 A/B 均改善 CTR、Query Quality 与 Intent Coverage，但摘要没有公开统一线上 Effect Size；因此目前更值得复用的是分层 Credit 设计，而不是把它包装成已证明的大幅业务提升。

1. Anthropic R&D Automation Index：第一次把“AI 开发 AI”拆成可持续追踪的生产指标

原始来源： Measurements for understanding the pace of AI development inside frontier labs · When AI builds itself

发生了什么

Anthropic 在 9 月 18 日公开了一套用于观察前沿实验室内部 AI 开发自动化程度的测量框架。核心是 R&D Automation Index：先把模型研发工作拆成层级任务树，再按照 Epoch AI 的 AL0–AL5 自动化等级判断每类工作由人还是 AI 完成，并按人员时间投入给不同任务加权。

其内部基线来自 2026 年 7 月约 15,000 个细粒度模型研发任务，最终整理成 542 个节点、378 个叶节点的任务树。为了减少“工作内容变了导致指数虚高”的问题，任务篮子被冻结，并单独检查 1 月到 7 月是否大量出现旧篮子覆盖不了的新工作。

关键结果

指标2026 年 8 月快照
AI 达到 “leads” 的研发工作26%
AI 达到 “collaborates” 或更高>90%
完全自主 AL5 的被测工作0%
最常用内部平台同时运行的 Agent约 30,000
在线 Monitor 覆盖100% actions
8 月被在线 Monitor 阻断的决策0.002%，约 1 / 47,000
抽样一周 AI R&D Compute 中 Safety 占比约 6%
AI-driven AI R&D Compute 中 Safety 占比约 12%

Anthropic 还披露了评估方法的弱点：Automation Level 主要由 Claude Judge 判定。模型与人类的 exact agreement 为 59%，而两位人类之间为 35%；97% 的模型／人类评分相差不超过一级。这说明指标有一定一致性，也说明“AI collaborates”和“AI leads”的边界并不是一个客观物理量。

为什么重要

过去讨论 Recursive Self-Improvement 常依赖能力 Benchmark、代码占比或任务时长。这次更接近生产函数：到底有多少下一代模型研发工作，已经由上一代模型承担了主要执行责任。

如果未来其他实验室采用可比较方法，并允许第三方重新抽样／复核，这类指数可以成为比单个 Coding Benchmark 更直接的“AI 加速 AI 研发”指标。它也能回答一个更细的问题：能力进步来自模型本身，还是来自越来越高比例的研发流程自动化。

可信度与局限

这是 Anthropic 的第一方内部测量，数据覆盖很深，外界却暂时无法独立重放。公司也明确承认 Judge 使用自家模型可能出现相关性偏差，并计划引入第三方评估者。

“26% leads”不等于“26% 的下一代 Claude 由 Claude 独立造出来”。AL4 仍然要求人类提供高层任务并监督；Anthropic 明确报告 AL5 为 0。Compute 安全占比又只是一周快照，而且“Safety / Capability”分类本身存在模糊边界。

最值得继续追踪

最重要的不是下个月 26% 变成 30% 还是 35%，而是三个更难的指标：第三方能否得到近似结果；不同实验室是否能使用统一任务篮子与评级定义；当 AI 开始影响“选什么研究方向”而不只是“执行哪个任务”时，Automation Index 应该如何重新定义。

2. When2Think：把 Think / NoThink 变成实例级计算分配 Policy

原始来源： When2Think: Learning Difficulty-Aware Length Control for Efficient Hybrid Reasoning Models

发生了什么

很多 Reasoning Model 的效率问题来自两个方向：简单题继续生成很长的推理，难题却因为统一 Token Penalty 被过早截断。When2Think 将其建模为 Instance-Adaptive Computation Allocation，让不同样本得到不同推理深度。

核心 IDAC（Instance-level Difficulty-Aware Control）先用预计算参考统计刻画每类样本的准确率和 Token 使用，再与 Verifier Reward、Batch-wise standardized advantage 一起做 Critic-free Post-training。模型由此学习在容易样本上直接回答，在难样本上进入更长的 Think 模式，而无需在线调用额外 Reference Model。

关键结果

Benchmark结果
AIME24 Pass@3相对 Base +10.0%
AIME24 Token Usage相对 Base -27.9%
AIME25 Pass@340.0%

作者报告其 Accuracy–Efficiency Trade-off 优于统一长度惩罚、压缩和纯 Routing Baseline。

为什么重要

Test-Time Scaling 的核心问题早已不是“更多 Token 有没有用”，而是下一单位计算应该花在哪个样本上。统一长度惩罚无法区分“这题已经够了”和“这题再思考 2,000 Token 可能翻盘”。

这一思路也可直接迁移到 Agent：简单 Tool Call 不应启动昂贵 Planner，多约束任务才值得增加 Reflection、Verifier 或额外 Rollout。未来 Reasoning Router 更可能从二分类器演化成连续的 Compute Budget Policy。

可信度与局限

当前主要证据是数学 Benchmark，Verifier 清晰，难度也相对容易由历史准确率估计。开放式 Coding、Search 或 Browser Agent 中，“问题难度”会随着工具结果和环境状态动态变化，单次 Prompt 的静态难度估计可能不够。

另外，AIME24 的 +10.0% 是相对 Base 的 Pass@3 改善；它不能被解读为所有任务都能同时“更准且少 28% Token”。

最值得继续追踪

看难度控制是否能扩展到 Turn-level / State-level：同一个 Agent 任务在不同阶段动态决定继续 Think、调用 Tool、启动 Verifier 还是直接结束。真正成熟的版本应优化 quality × token × latency × tool cost，而不是只控制 CoT 长度。

3. FormalFlow：63 天、12.6 万行 Lean，把长程数学 Agent 变成机器可验证工件

原始来源： Long-horizon autoformalization of a core theorem underlying MIP* = RE · Lean 4 Library：LionSR/MIPStarRE

发生了什么

FormalFlow 面向一个比短证明 Benchmark 更麻烦的问题：形式化工程持续数周甚至数月，单个 Agent Session 不可能一直保持全部数学意图。系统用共享 Blueprint 作为长期规格，再让多个 AI proving agents 在嵌套的 Planning、Proving、Review Loop 中工作；人类定期审查高层数学意图和关键分解。

目标是经典 low individual-degree test 的 quantum soundness，这是 MIP* = RE 的一个核心定理。最终 Lean 4 Library 由机器检查，而不是由 LLM Judge 判断“看起来像证明”。

关键结果

指标结果
开发周期63 天
最终 Lean 代码126,367 行
Agent 生成代码占比100%
最终验证Lean 4 Kernel / machine-checked

形式化过程中还发现并修正了原有证明里的 Side Conditions 与若干中间错误，同时在修正假设下保留原论文最终 Error Bound。

为什么重要

这类系统的价值不在“AI 写了 12 万行代码”本身，而在于交付对象具有强外部验证语义。自然语言科研 Agent 很容易把流畅解释误当成果；形式证明把正确性门槛交给 Lean Kernel，使 Agent 可以在大规模搜索和分工时仍保留确定性的最终验收。

另一个重要信号是 Blueprint。长程研究任务需要一种稳定、可审查、可版本化的中间规格，让不同 Agent Session 能持续组合成果。它和大型软件工程中的 Architecture Doc、Issue Graph、CI 很接近。

可信度与局限

这是一个很强的形式化工程结果，也仍然是人类监督下、目标已知、终态可严格验证的项目。系统没有自主选择“MIP* = RE 中最值得做哪个定理”，也不能由此推导它能独立产生同级别原创数学理论。

“全部代码由 Agent 生成”也不等于“全部知识工作无人参与”：人类参与了目标选择、高层监督、数学意图控制和项目组织。

最值得继续追踪

观察相同 Harness 是否能在第二、第三个大型数学项目中复用，而非每次依赖大量定制；还要看 Blueprint 的哪些部分可以自动维护，哪些必须由领域专家承担。若未来出现多个独立团队复现，FormalFlow 才会从一次大型 Case Study 变成稳定方法。

4. Flattening Every Memory Peak：1M Context MoE 训练要同时压住四种峰值

原始来源： Flattening Every Memory Peak in Long-Context Mixture-of-Experts Training

发生了什么

长上下文 MoE OOM 并不由“平均显存占用”决定，而由训练步骤中最高的一次 Live Set 决定。论文指出，常见并行策略仍留下四类随不同维度增长的峰值：Expert Dispatch 随路由矩阵增长；Vocabulary Projection 随 tokens × vocabulary 增长；Checkpoint Boundary 随 depth × sequence 增长；AdamW State 随参数量增长。

作者分别设计 PipelinedLLEP、Ring-DTP、Selective Checkpoint Offload（SCO）和 OffloadStreamAdamW。四种方法只改变计算和数据移动的时序／粒度，不改变模型、Loss、Precision、Expert Choice，因此结果保持 Exact。

关键结果

组件论文报告
MoE dispatch peak最高 -59.3%，无明显吞吐损失
Vocabulary projection peak-86.6%，时间增加 <5%
SCO 可完成最大 batch+17.7%
Offloaded AdamW step2.05× faster
End-to-end Context1M tokens
相对 tuned FSDP2 Context reach8–32×
相对 tuned FSDP2 Throughput最高 10.4×

端到端实验覆盖 120B、241B 和 667B MoE。

为什么重要

这是一个很值得训练系统团队复用的思维方式：

\[M_{\text{peak}} = \max(M_{\text{dispatch}}, M_{\text{vocab}}, M_{\text{ckpt}}, M_{\text{optim}}, \ldots)\]

若只优化当前最大项，工作负载扩大后第二大项会立即变成新上限。长 Context 的可扩展性需要把每个会随规模无界增长的 Live Set 变成显式有界调度。

可信度与局限

论文对单项组件和组合 Stack 都有 Match Baseline，且强调数学结果保持 Exact，这是优点。10.4× 是相对特定 tuned FSDP2 Baseline 的最好结果，并不意味着任何 MoE 训练系统接入四个模块都能获得十倍吞吐。

几项优化把 GPU 内存压力转移成 Host Memory、通信和流水调度复杂度；在不同互联、CPU 内存带宽和网络拓扑下，最优组合会改变。

最值得继续追踪

看这些 Operators 能否进入主流 Megatron / DeepSpeed / PyTorch Stack，以及 1M Context 真实训练中 MFU、host traffic、network overlap、checkpoint throughput 的完整 Pareto。更进一步，训练编译器应该自动识别哪个 Peak 在当前配置下先爆，而不是让工程师手工选择 Offload 方案。

5. JustFit：24 GiB 笔记本的长 Context 关键在状态生命周期

原始来源： JustFit: 200K-Token LLM Serving on a 24 GiB Laptop with Just-in-Time State Management · Hugging Face Paper Page

发生了什么

JustFit 是一个 MLX Runtime，目标不是再把模型权重压低一点，而是控制推理中哪些执行状态在什么时候必须驻留。KVExec 对 KV 做压缩执行；PhaseSwap 管理不同组件的 Residency；StateTrans 在 Serving Phase 切换时保留必要状态并及时 Materialize / Release。

这些机制与 Model Weight Quantization 解耦。论文在 24 GiB M4 Pro MacBook 上运行 Qwen3.8-27B MXFP4，用同一台机器测 Single-request Full-execution Capacity 和短一些的性能 Probe。

关键结果

指标JustFit
单请求输入196,608 tokens
单请求输出16,384 tokens
总 positions212,992
mlx-vlm baseline30,720 positions
Capacity increase6.93×
32K input / 64 output19.11 tok/s
重复 32K+6K Median Peak Footprint16,374 MiB
AIME 202629 / 30

另一次双请求实验保留了合计 229,376 positions。

为什么重要

本地 Agent 很容易同时遇到三类状态：模型权重、越来越长的 KV，以及阶段性才需要的组件／中间缓冲。只盯模型文件大小会低估后两者。

JustFit 的系统思想更接近操作系统虚拟内存：把“永远驻留”改成“按生命周期 Just-in-Time 驻留”。当设备内存本身是硬约束时，这往往比单纯追求 Kernel 峰值吞吐更重要。

可信度与局限

这里最容易被误读的数字是 19.11 tok/s。它来自 32K-input / 64-output 的独立 Probe，不能和 212,992-position 的 Capacity Test 拼成“200K Context 也跑 19 tok/s”。长 Context 的 Prefill、Swap 和状态转换开销仍会显著影响完整交互延迟。

实验目前集中在 Apple Silicon + MLX，一套相同策略在 CUDA、离散显存和 PCIe / NVMe 层级中是否仍最优，需要重新验证。

最值得继续追踪

最有价值的是把这一状态生命周期思想与本地 RAG / Coding Agent 实测结合：多轮对话的 P50/P95 TTFT、KV reuse、Swap bytes 与 Active Memory 随 Turn 增长的曲线，比单次最大 Context 数字更能说明产品价值。

6. Generative Query Suggestion：Slate Diversity 与 Query Quality 需要分层 Credit

原始来源： Generative Query Suggestion via Intent Coverage and Query-Level Credit Assignment

发生了什么

Query Suggestion 不只要生成一个好 Query，而要一次给用户一组 Query。这里存在两个不同尺度的目标：每条 Query 自己必须有质量，整个 Slate 又应覆盖不同 Intent。若把这些信号全部平均成一个 Reward，某条低质量 Query 可能因为整组多样性不错而得到错误正反馈。

论文采用双阶段优化。第一阶段构造 Intent-aligned SFT Data，并用 Intent-Aware Diversity Reward 提升整组 Intent Coverage；第二阶段做 Query-level Credit Assignment，把单条 Query 的质量信号只路由给对应 Query Token，同时把 Slate-level diversity signal 共享给整个列表。

为什么重要

这其实是推荐系统里一个很一般的 Credit 问题：

\[R(\text{slate}) = R_{\text{global diversity}} + \sum_i R_{\text{item}, i}\]

不同层级的 Reward 应该作用到不同决策变量。把 List-level 和 Item-level 目标混成统一 Advantage，容易让模型学到错误归因。

对生成式推荐、广告创意、多候选搜索和 Shopping Agent 都一样：单个候选的相关性、价格、可买性是局部目标；覆盖不同 Intent、避免同质化、组合互补性属于 Slate 目标。

可信度与局限

论文报告大型生产数据上的 Offline Evaluation 和 Online A/B 均改善 CTR、Query Quality 与 Intent Coverage，但公开摘要没有统一披露线上提升幅度。因此可以把它视为“生产环境方向性证据”，不能写成已被独立验证的显著业务跃升。

另一个未解决问题是 Slate-level Reward 的定义。如果 Intent 分类本身有偏差，模型可能只是围绕 Taxonomy 制造表面多样性，而不一定提高真实用户效用。

最值得继续追踪

看同一原则是否进入 Feed / Product Recommendation：把 Item-level satisfaction、Slate-level diversity、长期用户价值分别路由到适当 token / action，而不是继续依赖一个线性混合 Reward。对 RL 训练来说，还应检查这种 Credit Decomposition 是否降低 Reward Variance 和 Mode Collapse。

今日值得收藏的代码 / 学习资源

PACT：Pressure-Applied Compliance Testing 值得所有企业 Agent 团队纳入评测清单。它覆盖 12 个受监管企业领域、48 类多轮场景、22 个模型；即使最强模型仍在 6%–10% 的条目上错误应用规则，普通用户施压平均让违规率提高 65%。它测的不是“模型知道规则吗”，而是规则与捷径冲突、用户持续施压时是否仍守住边界。局限是样本经过 LLM-as-judge 审计，真实企业政策的复杂性和组织上下文仍更高。原文：PACT。

ComPO 值得做 Preference Alignment 的人读。它不直接对 Preference Pair 写一个可微 Loss，而把 Pair 当作 Comparison Oracle，从比较结果提取 Zeroth-order Direction；Online 版本再用无标签 Policy Generation 做 Reverse-KL Control。论文跨 Mistral、Llama、Gemma-2、Qwen3、Gemma-3 报告相对 Direct Alignment 的改善，并专门分析 Likelihood Displacement。当前摘要缺少一个足够统一的 Headline Effect Size，现阶段更适合作为“Preference Pair 还能怎样被利用”的方法论文，而不是新默认 Recipe。原文：A Zeroth-Order Paradigm for LLM Preference Alignment。

MIPStarRE Lean Library 是今天最值得直接打开代码的项目。相比只阅读 FormalFlow 论文，查看其目录、Blueprint、Statement Dependency 和实际 Lean 文件，更容易理解长程 Proof Agent 为什么需要软件工程式的规格与 Review Loop。仓库：LionSR/MIPStarRE。

今日最值得花 30 分钟阅读的一项

首选 Anthropic 的《Measurements for understanding the pace of AI development inside frontier labs》。

阅读原文

它比“80% 代码由 AI 写”这类容易误导的 headline 更值得读，因为它把一个模糊命题拆成了可操作的测量对象：研发任务篮子、自动化等级、Agent Monitor Coverage、Escalation Rate，以及 Compute Allocation。

30 分钟建议先读 R&D Automation Index 的任务树与 AL0–AL5 定义，再读 26% leads / >90% collaborates 的聚合方式；随后重点看 Appendix 里模型 Judge 与人工评审的一致性、Frozen Basket 的缺陷；最后读 Agent Oversight——30,000 Agent、100% Online Monitor Coverage、0.002% Block Rate——并思考低 Block Rate 到底表示系统安全，还是 Monitor / Workload 本身较保守。

最值得带走的问题是：

如果“AI 帮助开发更强 AI”的速度真的需要被治理，应该测模型能力，还是测 AI 在真实研发生产函数中承担了多少责任？

Anthropic 给出的框架是一个有用起点，不是行业标准。它现在最大的缺口就是第三方和跨实验室可比性。

今日可立即实践的一件事

给现有 Reasoning / Agent Pipeline 做一个 Difficulty-to-Compute Audit，先判断当前 Token / Rollout 是否真的花在最值得花的样本上。

从最近 200–500 个任务中，固定相同模型，分别以短、中、长三个预算运行，例如：

1
2
3
4
5

budgets = {
    "short": 512,
    "medium": 2048,
    "long": 8192,
}

对每个任务记录短预算成功率、长预算成功率、实际 Token、Latency 与 Tool Cost，并定义最简单的“额外计算边际价值”：

\[V_i = \frac{Q_i(B_{long}) - Q_i(B_{short})}{C_i(B_{long}) - C_i(B_{short})}.\]

随后用短预算阶段就能观测到的特征——例如首答置信度、Verifier disagreement、Tool error、retrieval sufficiency、问题类型——预测 $V_i$ 高低。先不要训练复杂 Router，只做一个 Logistic Regression / Small MLP，比较三种策略：所有任务长推理、所有任务短推理、预测高 $V_i$ 的任务才升级。

至少同时看 Task Success、Average Tokens、P95 Latency、Upgrade Rate 和 Hard-task Recall。如果 Router 省了很多 Token，却主要通过放弃困难任务实现，指标会立即暴露。

停止条件： 如果短阶段特征对“长预算是否能翻盘”几乎没有预测力，就不要因为 When2Think 的数学结果直接上线动态 Routing；这说明当前业务的难度更依赖后续环境反馈，需要做 Turn-level Policy，而不是 Prompt-level Difficulty Classifier。

这个实验真正回答的是：

你的额外推理预算，是分给了最需要思考的请求，还是平均撒在所有请求上？

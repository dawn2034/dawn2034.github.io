> **今日主线：** Learned Context Compaction · Causal Memory Retention · Experience Routing · Post-training Sharpening Tax · Recommendation Training Efficiency

今天是周六，arXiv 没有新的周末常规公告；最新常规批次是 **2026 年 10 月 2 日**：`cs.AI` 381 条、`cs.CL` 184 条、`cs.LG` 430 条、`cs.IR` 21 条。分类之间存在大量交叉收录，不能直接相加。今天的主线很集中：Agent 的状态管理开始从固定 Harness 规则进入可训练 Policy——Context 何时压缩、Memory 哪些该留、经验应该写进权重还是外部状态，都被拆成独立决策。与此同时，Post-training 与大规模推荐训练都暴露出一个共同问题：平均指标可能掩盖真正的系统代价。

## 今日核心判断

1. **Context Compaction 正从固定阈值变成 Agent Policy。** AutoCompact 让 Coding Agent 学习“何时压缩、保留哪些 Working State、压缩后怎么继续”。SWE-bench Verified 和 SWE-PolyBench Verified 相对 Base 分别提高 **9.2pp / 5.0pp**；256K Context 不溢出时仍有收益，说明 Compaction 的价值不只是避免超长上下文。

2. **Memory Retention 的首要统计问题可能是 Retrieval Positivity。** Causal Memory Policy 指出，一条从未被 Retriever 取回的 Memory，其效用无法从线上结果识别。LongMemEval / LoCoMo 中分别有 **54% / 67%** 的 required memory 遭遇这种识别失败；对 Retrieval 做已知概率的探索后，required-vs-non-required AUC 从 **0.54 → 0.66**。但当前 Query 上的 utility 可识别，并不等于能预测未来未知 Query 的长期价值。

3. **Self-improving Agent 不该把整条 Experience 全部写进同一个地方。** Component Routing 将经验拆成 locator、procedure、state fact、lesson：locator / lesson 更适合 weights，procedure / state fact 更适合 context。一个只用 recurrence 与 state-conditionality 的规则，在 held-out backbone family 的 **24/24** 个 cell 中恢复正确 destination，并比最佳单一 destination 平均再高 **3.5 points**。

4. **Post-training 可能提高 pass@1，却降低多采样时的 solution coverage。** Sharpening Tax 在 14 组 base/post-trained model pair、4 个模型家族、3 个 Agent Benchmark 共 42 个 case 中发现这种现象普遍存在。对高价值任务，如果部署依赖并行 Rollout，单看 pass@1 会漏掉 test-time scaling 的退化。

5. **大规模推荐训练的隐藏瓶颈是生命周期成本。** 一项覆盖数千 GPU、每天数百亿样本的生产研究显示，最重 workload 原先只有 **50%–60%** 端到端时间真正推进新数据训练。优化初始化、编译、checkpoint、publish 和恢复后，ETT% 平均 **+15.5%**，最大 workload 达到 **85%**，Fleet 整体从约 80% 提到 90% 以上。

## 1. AutoCompact：把 Context Compaction 变成可学习动作

[论文原文](https://arxiv.org/abs/2610.02163)

### 发生了什么

传统 Coding Agent 往往在 Token 接近上限时触发固定 Summary。AutoCompact 改成让 Agent 自己决定何时 compact、保留什么 working state、compact 后下一步做什么。训练时先运行 Base Agent，再由 Judge 检查 compaction decision、summary 与 post-compaction action；错误输出会在真正执行前被修正，随后用这些轨迹做 SFT，再用任务成功做 RL。

### 关键结果

| Benchmark | 相对 Base |
|---|---:|
| SWE-bench Verified | **+9.2pp** |
| SWE-PolyBench Verified | **+5.0pp** |

收益同时出现在 256K 不溢出的设置和 16K 需要 fallback compaction 的设置。

### 为什么重要

如果 Context 根本没满，Compaction 仍有收益，就说明它还在做信息去噪和工作状态重构。长程 Agent 的 Context Management 因而更像 Policy，而不是一个 Token 阈值。

### 可信度与局限

证据集中在 Coding Agent。Judge 修正训练数据会增加额外成本，而且“哪些信息未来仍重要”本身并不容易判断。论文也没有给出一个统一的 end-to-end cost headline，因此生产评估仍需同时看 success、input tokens、cache hit 与 wall-clock。

### 最值得继续追踪

把 Compaction Decision 与 future dependency 联合建模：旧 Observation 如果后续不再被使用，可以更激进压缩；路径、约束、测试入口等高精度 invariant 则进入结构化状态。

## 2. Causal Memory Policy：先解决“有没有机会观察到价值”

[论文原文](https://arxiv.org/abs/2610.02070)

### 发生了什么

Memory 系统常根据历史使用效果估计 utility，再决定删除或保留。问题是：如果 Retriever 从不选中某条 Memory，就没有“使用它之后”的 outcome。只在 Store 层做保留 / 删除实验也无济于事，因为 Retriever 仍然可能永远看不到它。

CMP 预留固定数量的 Context Slot，按已知 sampling propensity 随机探索部分 Memory，再用 self-normalized inverse propensity weighting 估计 utility。

### 关键结果

| 指标 | 结果 |
|---|---:|
| LongMemEval required memory identification failure | **54%** |
| LoCoMo | **67%** |
| required vs non-required AUC | **0.54 → 0.66** |
| 已识别 Query 的 per-query utility AUC | **0.78** |

最重要的负结果是：作者没有找到一种 aggregation 能稳定预测一条 Memory 对**未来未见 Query**的价值。

### 为什么重要

这里必须区分两个问题：

$$
\text{Can I identify utility now?}
$$

与

$$
\text{Will this memory matter later?}
$$

前者是因果识别，后者是长期价值预测。Never-retrieved 不能被直接解释为 low-value。

### 可信度与局限

探索会占 Context Budget，propensity 很小时 estimator 方差也会变大。更关键的是，CMP 修复了“看不见”的问题，没有解决“未来不可知”的问题。

### 最值得继续追踪

把 Retention 动作分层：长期价值不确定时优先冷存或降权；只有在有足够探索覆盖、多个 Query 类型都显示低价值后，才做不可逆删除。

## 3. Component Routing：经验应该进权重，还是留在 Context？

[论文原文](https://arxiv.org/abs/2610.01787)

### 发生了什么

这项工作把 GUI Agent Experience 拆成四类，并比较同一信息写进 weights 与放进 context 的差异。

| Component | 更优 destination |
|---|---|
| Locator | **Weights** |
| Lesson | **Weights** |
| Procedure | **Context** |
| State fact | **Context** |

作者再用 recurrence 与 state-conditionality 两个训练前属性做路由。

### 关键结果

规则在 held-out backbone family 上恢复正确 destination **24/24 cells**；相对整条 trajectory 全写入单一目的地的方案更好，并比每个 backbone 自己的最佳单一 destination 平均再高 **3.5 points**。

### 为什么重要

一个可操作的经验是：

> **高复用、低状态依赖的信息更适合参数化；强状态依赖、需要精确更新的信息更适合保持外部可编辑。**

这比争论“Fine-tuning 还是 Memory 更好”更接近真实系统。

### 可信度与局限

当前主要是 GUI Agent，组件边界相对清晰。Coding / Browser Agent 中 procedure 可能逐渐变成 skill，lesson 也可能只在某个版本成立；而且 Code / Data 仍待发布。

### 最值得继续追踪

做动态 destination policy：经验先进入 Context，跨任务稳定复现后再晋升到 skill / weights；环境变化后允许降级回外部状态。

## 4. Sharpening Tax：Post-training 可能牺牲 Test-time Search Space

[论文原文](https://arxiv.org/abs/2610.01509)

### 发生了什么

Post-training 通常提高 pass@1，但也可能把概率质量集中到更少的行为模式。Base Model 原本一些低概率但有效的策略因此消失，多次采样时覆盖的独立解法反而减少。

作者把这种损失称为 **Sharpening Tax**。

### 关键结果

研究覆盖 14 组 base/post-trained pair、4 个模型家族、3 个 Agent Benchmark，共 **42 个 case**。Tax 在多数设置中存在，并能用少量 Rollout 近似估计。作者提出 PTGS，按题目难度自适应采样温度，在两个 Agent RL 环境中减少 Sharpening Tax，同时继续改善 single-shot accuracy。

### 为什么重要

pass@1 与 pass@K 对应不同部署形态。在线助手更关心一次完成；AutoResearch / Coding 等高价值任务往往愿意并行搜索多条 trajectory。只优化前者可能损失后者真正依赖的策略覆盖。

### 可信度与局限

高 pass@K 不等于低成本。如果 Base Model 需要几十条 Rollout 才偶尔覆盖正确策略，它在普通产品中仍可能不划算。因此这里的结论是“评估要看完整 budget frontier”，并非“Post-training 有害”。

### 最值得继续追踪

同时报告 pass@K、策略多样性与总成本。如果 RL 后 pass@1 上升但曲线过早饱和，应检查是否出现过度 sharpening。

## 5. Effective Training Time：推荐训练集群真正浪费在哪

[论文原文](https://arxiv.org/abs/2610.02057)

### 发生了什么

大型推荐训练的端到端生命周期包含初始化、编译、checkpoint、失败恢复、model publish 等大量非训练工作。作者定义 **Effective Training Time（ETT%）**：Wall-clock 中真正用于在“新数据”上推进训练的比例。

### 关键结果

改造前，最大 workload 只有 **50%–60%** 时间推进新数据训练。优化包括初始化通信消除、pipeline overlap、dynamic-shape / autotuning 优化、可复用 PyTorch 2 编译缓存、异步 checkpoint、独立 publish 和恢复成本优化。

结果是 ETT% 在所有 benchmark 上提高，平均 **+15.5%**；最大 workload 达到 **85%**，生产 Fleet 整体从约 **80% 提到 90% 以上**。

### 为什么重要

推荐训练真正关心的是多快吸收最新行为数据。GPU Utilization 很高并不保证 Data Freshness 在推进：卡可能在重复编译、恢复或处理生命周期工作。ETT% 因此比单纯 steps/s 更接近在线推荐的系统目标。

### 可信度与局限

这是第一方生产系统数据，收益来自整套基础设施组合，无法归因给单项优化。ETT% 也不能单独最大化；减少必要 checkpoint / validation 会把风险转移到可靠性。

### 最值得继续追踪

把 ETT% 与 data freshness、recovery time、checkpoint risk、online metric lag 一起监控，形成真正的训练新鲜度 SLO。

## 今日值得收藏的代码 / 学习资源

**Mingbird** 面向普通 Windows / Ollama 的小模型 Agent，加入 net-zero prefill budget、finish gate、loop detection 等机制。在自建 LRAB 上为 **0.886**，对照 goose / opencode / agent-mini 为 0.631 / 0.479 / 0.405；第三方 $\tau^2$-bench 上为 **0.856 vs 0.791 / 0.737**。作者也明确指出自建 benchmark、单机和 replication 波动等限制，适合研究 Harness failure mode，而不宜只看排行榜。[论文](https://arxiv.org/abs/2610.02001) · [代码](https://github.com/knowsuchagency/mingbird)

**Agents Are Systems, Not Models** 发布 18,000+ 条 Agent 轨迹。四个科学任务中约 **54% outcome variance 来自重复同一 configuration 本身**；task information 的影响超过 time budget 与 model size。Prompt 中要求“验证”影响很小，提供真正 verification tool 才显著改变行为。[论文](https://arxiv.org/abs/2610.01618)

**CARM** 处理异步 / off-policy LLM RL 中 sequence mask 的 cancellation 问题：对 token log-ratio 取绝对值再聚合，避免正负漂移互相抵消。作者报告 AIME / BeyondAIME mean@16 最高 **+3.13pp**，四个代码 benchmark 平均 pass@1 **+2.88 points**。[论文](https://arxiv.org/abs/2610.02039)

**TopK-Guided** 将 Activation Sparsity 同时按 Token 与 Block 分配，在 Llama-2 / Llama-3 上、相同 sparsity-dependent projection compute 下优于 TEAL / WINA，且高稀疏区收益更明显。真正值得继续看的，是这些质量优势能否被 Sparse Kernel 转换成稳定 wall-clock 收益。[论文](https://arxiv.org/abs/2610.01763)

**GrIS** 将 Generative Recommendation 的 Semantic ID 重述成层次图划分：节点放 semantic content，边放 collaborative signal，RQ-VAE / RQ-KMeans 对应空图特例。两个实例化方案在多个真实数据集上相对 CF-aware SOTA 的 Hit@10 最高提升 **52%**；更有价值的是它把 graph construction 与 partition algorithm 变成两个可独立实验的轴。[论文](https://arxiv.org/abs/2610.01533)

**Strands Decider 2B** 是近期 Decision Model 路线的一个直接工程化实例，面向 Tool / Model Routing、Memory Selection、Guardrail 与 Evaluation 等有限候选决策。它值得和 SGLang Score API、Jev 一起看；正确的生产形态更可能是置信度 Cascade，而非无条件替换 Generative Judge。[官方介绍](https://strandsagents.com/blog/introducing-strands-decider/)

## 今日最值得花 30 分钟阅读的一项

**首选 Causal Memory Policy。**

[论文原文](https://arxiv.org/abs/2610.02070)

建议重点看 retrieval positivity violation、带已知 propensity 的探索 slot、以及最后那个最重要的负结果：**当前 Query 上的 utility 可识别，并不代表能预测未来未知 Query 的 retention value。**

> **Memory 系统应区分“我没有证据证明它有用”和“我有证据证明它没用”。Never-retrieved 不是 low-value。**

## 今日可立即实践的一件事

给现有 RAG / Agent Memory 做一个 **Retrieval Positivity Audit**。从历史 Query 中，对每条 Memory 记录 `eligible`、`retrieved`、`required` 三类计数，计算：

$$
\text{exposure}(m)=\frac{N_{\text{retrieved}}(m)}{N_{\text{eligible}}(m)}
$$

然后重点看 required memory 中 `exposure = 0` 的比例。如果这一比例很高，只基于“被使用后的效果”学习 retention score 会有明显选择偏差。

下一步可在低风险离线流量中预留少量 Context Slot，以已知概率抽取候选 Memory，再比较 answer quality / tool success / verifier reward。先让 Never-retrieved 区域变得可观察，再决定是否删除。建议至少记录 zero-exposure rate、exploration hit rate、estimator variance、context overhead 与 future-query regret。

真正要回答的是：

> **Memory Cleaner 删除的是确认无用的信息，还是 Retriever 从来没有给它证明价值的机会？**

今日主线： Self-Evolving RL · State-Conditioned Evidence · Reasoning Embeddings · Skill-Graph Repair · Agent Resource Dynamics · Multi-Policy Generative Ads

今天是周日，arXiv 没有新的常规公告批次；最新常规批次仍是 2026 年 9 月 18 日：cs.AI 215 条、cs.CL 104 条、cs.LG 198 条、cs.IR 22 条。不同分类有大量交叉收录，不能直接相加。今天更值得关注的是周五批次里逐渐汇成的一条系统主线：训练对象正在从单一 Policy 扩展到任务生成、可执行评估、Skill Graph 与检索证据集合；Serving 优化也从 GPU 本体继续外溢到 CPU、磁盘、工具容器和队列。推荐／广告侧则继续尝试在共享 Backbone 上显式分离不同业务目标，减少多阶段策略之间的冲突。

今日核心判断

  1. Self-Evolving Agent 的 Evaluation 也必须一起学习。 UnifiedPlayers 把 Planning、Execution、Evaluation 三个角色都做成可训练 Policy，并用固定扰动器 + Python Sandbox 产生共享的 executable verdict matrix，再为三个角色构造不同 Reward。跨两类 Backbone、12 个 reasoning benchmark，相对最强已有基线，数学至少 +3.5%、通用推理至少 +3.9%；学习到的 verifier 对对抗轨迹检测准确率为 84.2%，其 reward 的每题方差是 self-consistency baseline 的 2.03 倍。关键价值在于：自生成数据如果仍由静态或自洽式评估器验收，系统很容易把共同错误当成进步。

  2. Coding Agent 的 Retrieval 目标应从“最相关”改成“当前状态还缺什么”。 The Missing Complement 把检索定义成 state-conditioned minimal sufficient evidence recovery：先看 Agent 已经观察过什么，再返回覆盖下一步决策全部缺失事实的最小证据集合。SERBench Test500 上，5 个证据项的 Complete-MSS 为 73.0%，Qwen3 embedding + reranker 为 61.4%；8 项时为 80.6% vs 72.4%。这个差距主要来自集合级互补性，而非单项相似度。

  3. Embedding Model 开启 reasoning 后，会出现“推理越多、表示反而越差”的 Reasoning Collapse。 CoFree 用 reference-guided SFT 约束 embedding geometry，再在 RL 阶段同时优化 embedding reward、reasoning reward 与 embedding-space regularization。4B 模型在 22 个 MTEB+BRIGHT 数据集上的整体分数为 40.8，对比 Qwen3-Embedding-4B 的 38.0；生产电商搜索作为额外召回通道时，作者报告订单相对 +13.56%、GMV +8.15%。但 BRIGHT-Code 上 CoFree-4B 反而低于 Backbone，说明 reasoning-enhanced embedding 目前仍有明显领域依赖。

  4. Skill 自我进化需要把“哪里坏了”和“允许改哪里”绑定起来。 SkillAA 把 applicability、execution、composition 统一成 Skill Graph，通过成功／失败轨迹对比把修复责任归因到具体图对象，只修改局部结构，并用 Local Gate 与 Big Gate 在提交前做定向验证与回滚。使用 GPT-5.6 Sol 时，SearchQA、LiveMath、DocVQA 分别达到 81.5%、66.7%、91.2%。这里真正值得追踪的是图级变更治理，而非单次最好分数。

  5. Agent Serving 的瓶颈正在扩展到 GPU 之外。 一项对 RAG QA、Web Search、Software Coding Agent 的系统测量发现，并发执行会暴露 CPU、磁盘 I/O 与内存瓶颈；更快的 LLM 或更多 CPU Core 并不保证 Agent 更快。CPU-aware tool admission 与 task-aware CPU allocation 让 CPU-sensitive 任务延迟改善约 5.4×，跨多类任务的平均延迟下降约 32%。因此 Agent 容量规划需要测完整 workflow，而不是只看模型 tokens/s。

  6. 生成式搜索广告正在从“一个融合 Reward”转向“共享 Backbone 上的多目标 Policy”。 UniPolicy 用 objective-specific prefix token、稀疏 MoE-LoRA routing 与目标专属 residual FFN，在共享模型中分离 relevance、click propensity、commercial value 等策略；在线推理通过 multi-policy beam search 在固定召回预算内组合多个业务目标。7 天线上 A/B 中，CTR +0.71%、RPS +1.58%、广告收入 +1.32%，论文称 Serving latency 保持稳定。

1. UnifiedPlayers：让 Task Setter、Solver 和 Verifier 一起进化

原始来源： 论文

发生了什么

很多 Self-Evolving Agent 会让模型自己出题、自己 rollout，再用 majority vote、self-consistency 或固定 verifier 给训练数据打分。这里存在一个结构性问题：Planner 会改变题目分布，Executor 会改变错误类型，Evaluator 却停留在旧分布上；如果 Evaluator 也来自同一批答案的“共识”，多个 Agent 一起犯错时还可能得到高 Reward。

UnifiedPlayers 把系统拆成三个独立 Policy。Planning Player 生成需要多步 Python Tool Call 的任务；Execution Player 在 Sandbox 中完成任务；Evaluation Player 为当前任务和轨迹生成 executable verifiers。固定扰动器再对原轨迹构造对抗变体，所有 verifier 同时在原轨迹与扰动轨迹上运行，形成共享的 verdict matrix。

三种 Policy 不共享一个标量 Reward。Planner 得到“难度边界 + 可验证性 + 新颖性”的 Reward；Executor 得到多个有效 verifier 的平均验收结果；Evaluator 同时奖励原轨迹通过、对抗轨迹拒绝，并惩罚 verifier code 重复。训练采用 block-wise GRPO：每次只更新一个 Player，另外两个冻结，避免三个数据分布在一次更新中同时漂移。

关键结果

Qwen3-4B-BaseMath AVGGeneral AVG
Tool-augmented / 相关基础设置44.036.4
Agent052.742.1
UnifiedPlayers56.446.1

三轮外循环中，Execution accuracy 从 52.5% 提到 63.3%，Evaluation adversarial rejection 从 31% 提到 79%，Planner 的任务不确定度指标从 0.18 提到 0.39，说明题目也在向能力边界移动。Factorial 对照显示，Planning 与 Evaluation 都有独立正贡献；使用最新一轮反馈，相比 compute-matched stale feedback，数学和通用推理分别再高 1.5 与 1.7 points。

为什么重要

Self-Evolution 的薄弱点经常不是“缺数据”，而是验收数据的标准跟不上 Policy 的变化。一个可训练 Evaluator 如果只学会迎合当前 Solver，也会形成新的 reward hacking。UnifiedPlayers 的关键设计是把 Evaluator 的监督锚在 executable perturbation 上，使“评估器进化”仍有外部可执行证据约束。

对 Tool-Agent RL，一个可迁移的架构是：任务生成、执行、验收可以分别学习，但它们必须共享不可由三方随意修改的环境证据层。

可信度与局限

论文跨两个 Backbone 与 12 个 benchmark，且做了 factorial comparison，证据比只展示三条同步上涨曲线更强。不过当前工具主要是 Python Sandbox，任务仍然属于 reasoning benchmark；真实 Browser、Shell、SaaS API 的副作用、权限与状态变化更复杂。

成本也不低。主设置使用 4 个 verifier 时，本地 GPU-hours 为 432；增到 8 个 verifier，Math AVG 只从 56.4 提到 57.0、General AVG 从 46.1 提到 46.4，而 GPU-hours 增到 519。Evaluator 质量存在明显的边际收益问题。

最值得继续追踪

最值得验证的是开放式 Tool Agent：让 Evaluator 生成可执行状态检查、数据库断言、网页 DOM 条件或文件系统 invariant，再观察 Planner–Executor–Evaluator 共演化是否仍能稳定提升。还应长期追踪 evaluator false-positive、false-negative 与 verifier diversity，而不是只看最终 Reward。

2. The Missing Complement：Agent 检索的目标是补齐决策缺口

原始来源： 论文 · SERBench

发生了什么

普通代码检索通常把 Issue、当前 Query 或 Agent Summary 编成向量，再独立给文件、函数或代码片段打相关性分数。Agent 场景的问题在于：Agent 已经读过一些文件、执行过搜索、形成了部分判断，下一步需要的信息取决于“当前已经知道什么”。多个单独很相关的片段也可能反复回答同一件事，却共同遗漏一个决定下一步修改位置的关键事实。

论文因此定义 State-Conditioned Minimal Sufficient Evidence（MSS）：给定捕获的 Agent State，先刻画下一步决策尚缺的事实组，再找一个尽量小的证据集合，使每个 required group 都至少被一条证据覆盖。MSS-Complement 通过多阶段语义调用先提出联合充分集，再显式搜索剩余 gap，并在固定 source budget 内完成最终集合。

SERBench 包含 500 个 calibration state 和 500 个 held-out state；Test500 来自 45 个 repository，私有 certificate 用于判断返回集合是否真正覆盖全部必要事实，而不是只评单项 relevance。

关键结果

Test500Complete-MSS@5Complete-MSS@8
Qwen3 embedding + reranker61.4%72.4%
Independent similarity control66.6%74.4%
MSS-Complement73.0%80.6%

5 项条件下提升 11.6 points，8 项时提升 8.2 points。优势主要集中在真正需要多个事实组的状态：284 个 multi-group state 上领先 14.79 points。

在 AMA-Bench，MSS-Complement 给最终 answer model 的 prompt 缩短 76.2%，accuracy point estimate 高 2.08 points；但这一 +2.08 的 episode-clustered 95% 区间为 [-0.16, +4.37]，不能当作统计上已经确定的准确率提升。它同时付出了更高的检索控制成本：论文给出的 online acquisition token 为 33.57K，对比 baseline 的 13.95K。

为什么重要

这项工作把 Agentic Search 的目标从“找相似内容”推进到补齐当前决策的剩余约束。这与普通 RAG 的差异很大：同一 Issue 在刚开始、已经读过核心文件、准备修改代码这三个状态下，需要检索的证据应该完全不同。

对于 Shopping Agent、Coding Agent 和企业 Workflow Agent，都可以把 retrieval objective 写成类似的集合覆盖问题：预算、规格、库存、用户偏好、兼容性等约束需要被不同证据共同覆盖，重复返回五条相似商品并不能提高决策充分性。

可信度与局限

SERBench 对“完整证据集合”有私有 certificate，这是很强的评测设计；Repository-disjoint Test500 也减少了简单记忆风险。问题在于 MSS-Complement 本身使用多次语义调用，检索侧 token 成本明显增加，因此它当前更像“用更多 acquisition compute 换更小、更完整的 answer context”。

此外，certificate 定义的是下一步决策所需事实。开放式任务很难像代码修复那样稳定定义 required groups；如果 certificate 本身漏掉约束，Complete-MSS 会高估真实充分性。

最值得继续追踪

看能否用一个轻量 learned controller 近似 MSS gap search，把多次语义调用压缩成一次或两次；同时把 Complete-MSS / answer quality / acquisition tokens / answer-visible tokens / latency 放进同一 Pareto，而不是单独优化召回率。

3. CoFree：Reasoning Embedding 需要防止“会解释、不会检索”

原始来源： 论文

发生了什么

近期一批 Embedding Model 开始在生成最终向量前先输出 reasoning，希望复杂检索问题可以先分析约束、实体与多跳关系。论文观察到两个 failure：模型可能在 specialization 过程中失去原本的 reasoning 能力；也可能生成很流畅的 reasoning，却没有服务于最终 retrieval geometry。作者把它们统称为 Reasoning Collapse。

CoFree 使用两阶段训练。SFT 阶段除了语言建模与对比学习，还加入 reference-guided loss，让训练后的 embedding 不要过度偏离强 Reference Embedder；RL 阶段同时使用 embedding-oriented reward 与 reasoning-oriented reward，并加入 embedding-space MSE regularization，约束“推理变好”不要以表示空间崩坏为代价。

作者还构造 RTED，一个 3.6M-instance 的 reasoning text embedding 数据资源，用于覆盖 fact verification、argument retrieval、multi-hop QA、domain retrieval、StackExchange、代码与 theorem retrieval 等任务。

关键结果

4B 模型MTEBBRIGHTOverall
Qwen3-Embedding-4B64.116.338.0
CoFree-4B66.419.440.8

SFT 去掉 reference guidance，Overall 从 39.9 降到 37.1（-2.8）；完整 RL 再从 39.9 提到 40.8。RL 中去掉 embedding reward、reasoning reward、MSE regularization，分别下降 0.4、0.5、0.7 points，说明“推理质量”和“表示稳定性”都不是冗余组件。

生产侧，作者称 CoFree 已作为电商搜索的额外召回通道全量部署：CTR 绝对 +0.02 points、CVR +0.12 points，订单相对 +13.56%、GMV +8.15%。这些数字来自系统建设方的一方线上 A/B，应按工业论文证据理解，外部无法独立复算。

为什么重要

Embedding Model 的最终任务仍是保存有用的相对几何关系。Reasoning 只是形成表示的一种中间计算，不应成为另一个脱离 retrieval objective 的文本生成任务。

这与近期 OPD、Agent Harness 的趋势很一致：增加中间 reasoning 并不天然提高最终任务。训练必须保留一个面向真正业务决策的 anchor，否则模型可能越来越“像在思考”，同时 Top-K ranking 变差。

可信度与局限

22 个 MTEB+BRIGHT 数据集和组件消融提供了不错的离线证据，线上 A/B 又补充了真实系统结果。不过泛化并非全面：BRIGHT-Code 上 CoFree-4B 为 9.9，低于 Qwen3-Embedding-4B 的 11.5；不同 Backbone 对代码检索的反应并不一致。

此外，训练 reasoning 数据依赖更强模型生成，RL 又引入额外 reward 和 regularization。最终提升来自完整 pipeline，无法简单归因给“Embedding 前先生成 CoT”。

最值得继续追踪

最值得看的是 reasoning token budget 与 retrieval quality 的边际曲线，以及能否用 latent reasoning 或更短的 structured rationale 保留收益。生产系统还应单独评估 reasoning latency 对 Recall QPS、缓存和索引更新的影响。

4. SkillAA：让 Skill Evolution 具备归因、局部提交和回滚

原始来源： 论文

发生了什么

Skill 自动进化常见的问题是，一次任务失败可能同时涉及“这个 Skill 是否适用”“Skill 内步骤是否正确”“多个 Skill 组合顺序是否合理”。如果系统直接重写整个 Skill 文档，修复一个局部错误时很容易破坏其他已经稳定的行为。

SkillAA 把 Skill 系统表示为统一图：图中显式保留 applicability、execution 与 composition 关系。系统对比成功和失败执行，把候选修复归因到具体 graph object，只修改选中的局部结构；修改先通过 Local Gate，再通过覆盖更广的 Big Gate，失败就回滚。

关键结果

使用 GPT-5.6 Sol 时，论文报告 SkillAA 在 SearchQA、LiveMath、DocVQA 分别达到 81.5%、66.7%、91.2%，并在主要设置中获得最高 observed mean。

相比“每次失败都让模型重写 Skill”，这里更值得关注的是变更半径与验证半径被分开管理：修复可以很局部，验收却可以覆盖受影响的更大 Skill 子图。

为什么重要

长期 Agent 的 Skill 会越来越像软件资产。它需要版本、依赖、适用条件、变更范围、回归测试和回滚，而不只是若干自然语言说明。把 Skill Evolution 变成 graph-scoped patch，可以显著提高可审计性，也更容易定位哪一次自我修改引入了 regression。

对企业 Agent，这种设计还有安全价值：高风险 Skill 的 composition edge 可以要求更严格 Big Gate，低风险文本处理 Skill 则允许更快的局部更新。

可信度与局限

当前公开证据主要来自论文自己的 benchmark 设置，且 headline 使用 GPT-5.6 Sol 作为执行模型；因此不能把 81.5/66.7/91.2 直接外推到弱模型、大型企业 Skill Registry 或真实 MCP 环境。

更关键的是，Skill Graph 本身必须足够准确。如果 applicability 或 composition relation 起初就漏建，局部归因可能把错误修到错误位置。Gate 的覆盖范围也决定系统能否抓住远距离副作用。

最值得继续追踪

关注 Skill Graph 是否能自动从真实 Tool Schema、历史轨迹与失败日志构建，并记录每条 edge 的 provenance；同时需要观察长期迭代 20、50、100 轮以后，局部修复是否真的减少 cumulative regression，而非只优化短期 benchmark。

5. Not All AI Agents Are Equal：Agent Runtime 需要任务级资源画像

原始来源： 论文

发生了什么

传统 LLM Serving 很容易把主要瓶颈理解成 GPU Model Compute 和 KV Cache。Agent workload 会同时运行浏览器、Python、编译器、向量检索、文件操作等工具，LLM 还可能通过远程 API 提供，因此 Host CPU、磁盘和容器内存开始成为完整 workflow 的一等资源。

这项研究测量 RAG QA、Web Search 与 Software Coding Agent，记录远程 LLM 调用与本地 Tool Container 的资源动态。作者发现，Agent 之间的 CPU / Disk / Memory profile 差异很大；并发增加后，工具侧瓶颈会让“更快 LLM”无法转化成更短端到端时间，简单增加 CPU Core 也可能因为其他共享资源和阶段结构而收益很低。

基于这些观察，系统加入 CPU-aware tool admission 与 task-aware CPU allocation：只在当前 Host 资源适合时放行某些 Tool，并按任务资源画像分配 CPU，而非所有 Agent 使用同一静态配额。

关键结果

论文报告 CPU-sensitive Agent task 的 latency 改善约 5.4×，多任务平均 latency 相比 native Agent 降低约 32%。

这里最重要的结论不是某个固定倍数，而是 Agent Runtime 的性能方程需要包含：

只优化其中一个阶段，瓶颈很容易迁移到另一个阶段。

为什么重要

随着 Agent RL、Coding Agent 与 Browser Agent 批量并发，GPU 很可能处于等待工具结果的状态，而 Host 侧同时挤满编译、测试、浏览器渲染和数据处理任务。此时“GPU utilization 低”不代表需要更多 GPU，真正的问题可能是 Tool admission 和 CPU scheduling。

这也改变了 benchmark 设计。Agent 性能应以 workflow completion time、P95/P99、Tool queue time 和资源利用率联合衡量，单独报告模型 tokens/s 很难解释生产容量。

可信度与局限

论文验证了多类 Agent，但仍属于受控实验环境；不同 Tool Stack、容器 Runtime、远程 API latency 和缓存策略会明显改变资源分布。5.4× 是 CPU-sensitive task 的特定优化结果，不应理解为所有 Agent 都能获得同等加速。

此外，task-aware allocation 依赖对任务类型或运行阶段做可靠识别。真实 Agent 经常中途改变计划，资源画像也会漂移，因此静态分类器未必足够。

最值得继续追踪

建议关注 Agent scheduler 是否进一步联合优化 LLM queue × Tool queue × sandbox placement × CPU/memory pressure × KV locality。成熟系统最终需要一个跨模型与工具层的统一调度器，而不是两个彼此不知道对方状态的独立队列。

6. UniPolicy：生成式广告检索里的多目标 Policy 解耦

原始来源： 论文

发生了什么

搜索广告同时追求 relevance、点击、收入、转化等目标。把这些目标直接线性加权成一个 Reward，会把业务权衡固定进单一 Policy；不同场景想调整配比时，通常需要重新训练或依赖后续规则补偿。

UniPolicy 选择在一个共享 Backbone 内显式分离 Objective-Specific Policies。目标 prefix token 告诉模型当前策略目标；稀疏 MoE-LoRA router 只激活少量目标相关低秩 Expert；目标专属 residual FFN 再提供额外容量。训练偏好来自搜索广告多阶段行为数据，分别构造不同目标的 pairwise preferences。

推理阶段不是只生成一个排序，而是并行执行多路 objective-specific beam search，再按业务 quota 在固定 retrieval budget 下组合结果，使业务侧可以在不重新训练 Backbone 的情况下调整目标配比。

关键结果

7 天真实搜索广告线上 A/B 中：

指标相对变化
CTR+0.71%
RPS+1.58%
Advertising revenue+1.32%
Serving latency作者报告稳定

论文还报告离线多指标相比 single-objective RL 与 naive reward fusion 更均衡，但线上结果属于完整 UniPolicy 系统，无法将收益单独归因给 prefix token、MoE-LoRA 或 residual FFN。

为什么重要

推荐／广告里的多目标冲突长期存在。UniPolicy 的思路把“业务目标”从一个训练期固定的 Reward 权重，提升成推理期可显式选择的 Policy 条件。对快速变化的市场、活动和库存状态，这比频繁重新训练单一融合模型更灵活。

从模型结构看，它也说明 Parameter Sharing 不必等于 Policy Sharing：共享大部分 Backbone，同时给冲突最大的目标保留稀疏的专属容量，可以降低 negative transfer。

可信度与局限

真实 7 天线上 A/B 是强工业证据，但系统、流量与数据均不可外部复现。论文没有给出足够详细的端到端算力／显存变化，因此“Serving latency 稳定”不能等价成“多路 Policy 几乎免费”。

Multi-policy beam 还引入 quota 与合并策略，这本身也是新的业务超参数。目标数量进一步扩张时，Expert 数量、Router 稳定性和 Policy 间 calibration 会成为新的复杂度。

最值得继续追踪

看这一结构能否用于 Feed Recommendation 的 watch-time / satisfaction / diversity / creator value 等目标，以及是否可以在线动态调整 quota，同时保持离线策略约束和用户级长期价值稳定。

今日值得收藏的代码 / 学习资源

RAFT：Stateful RAG for Troubleshooting 很值得做企业支持 Agent 的团队直接读代码。它把每个历史 Case 抽成 timeline entry chain，当前 Case 在不同调查阶段检索对应的中间状态，再返回从匹配点开始的父 Case trajectory。826 个合成 Windows Server Case 上，Case Hit 在 0% / 30% / 60% 进度分别为 84.2% / 87.1% / 88.8%，vanilla RAG 为 67.3% / 71.9% / 76.9%；三个差值都有 root-cause-group clustered bootstrap 支持。Apache Jira 的 30 个 audited duplicate groups 上也呈同方向，但样本很小，只能当作迁移信号。更有意思的是，Graph expansion 对总体 Case Hit 的边际贡献几乎为零，主要收益来自 entry-level state matching，不是“加一张图”。
RAFT 论文 · Microsoft/RAFT

NVIDIA AIPerf 是今天最值得 Serving 工程师收藏的工具更新。它是 GenAI-Perf 的重新实现，改用 multiprocess worker + 独立 record processor + ZMQ，目标是避免高并发压测时 load generator 自己先被 Python GIL 卡住；支持 15+ endpoint types、ShareGPT，以及 Mooncake、Baseten、WEKA AgentX 等 trace replay，并可以配置 constant / Poisson / gamma arrival pattern 与 burstiness。它解决的是“你测到的是 Server 还是 Client 上限”这个很基本、也很容易被忽略的问题。
NVIDIA 技术文章 · AIPerf GitHub

AgentPProf 把传统 pprof/flame graph 的思想移到长程 Agent。它不再按函数调用栈聚合成本，而是用 semantic operation stack 把跨 run 的轨迹按任务意图与子任务递归切分，再输出 pprof-compatible profile。CodeTraceBench 上 segmentation 的 $B^3$ F1 为 0.764，三个 problem-localization benchmark 的 MAP 最高提高 56%。这很适合用来回答“到底是哪类 Agent 子任务在烧 Token／制造失败”，而不是继续靠单条 trace 肉眼排查。
AgentPProf 论文 · agentsight 代码

X.com｜近期高信号技术讨论

今天严格按 动态趋势发现 → Alias 扩展 → 原帖召回 → 作者／机构扫描 → Event-driven 补充 → 72 小时／7 天回退 执行。本轮仍未获得满足准入条件的近期 X.com 原始 /status/ 技术帖，因此 X 热点栏目不能标记为完成。 这里不使用账号主页、X Help、搜索摘要或媒体二手转述冒充原帖，也不猜测 Views、Likes、Reposts 或 Replies。

动态发现阶段提取出的高潜短语包括：executable-verifier co-evolution、state-conditioned evidence、minimal sufficient evidence、reasoning embedding collapse、skill graph rollback、stateful troubleshooting RAG、agent resource dynamics、semantic agent profiling、AIPerf、recurrent-depth / latent recurrence、prefix / KV-aware routing、distributed MCP skills、multi-policy generative ads。其中 recurrent-depth、KV routing、AIPerf、MCP Skill 等候选独立于今天最终入选论文标题。

本轮重点尝试形成五个讨论簇：

  1. Agent Self-Evolution / executable verifier co-evolution：围绕 task generator、solver、verifier 共同更新，以及静态 evaluator 失效；
  2. Agent Retrieval as Complement / Minimal Sufficient Evidence：围绕 relevance ranking 与 decision-sufficiency 的差异；
  3. Reasoning Embeddings / representation collapse：围绕 embedding 模型是否应该显式 reasoning、怎样约束表示几何；
  4. Agent Systems Profiling / AIPerf / resource-aware serving：独立于当天论文筛选，围绕完整 Agent workload 的测量边界；
  5. Recurrent Depth / Latent Recurrence / Looped Transformer：作为持续回归主题，检查近期是否出现新的复现、Serving 或架构讨论。

今日最值得花 30 分钟阅读的一项

首选 The Missing Complement。
论文 · SERBench

它最值得读的地方不是又多了一个 Coding Retriever，而是把 Agent Retrieval 的评测对象改了：返回的集合有没有补齐当前状态下一步决策所需的全部信息。 这个定义比 Recall@K 更接近真实 Agent 的失败方式。

建议 30 分钟按这个顺序读：先看 SERBench 如何捕获“Agent 已经看过什么”；再看 required evidence groups 与 Complete-MSS；随后对比 independent similarity 和 MSS-Complement，确认收益来自集合互补性；重点看 budget-matched 结果，以及 AMA-Bench 中 76.2% answer-context reduction 与更高 acquisition-token cost 的交换；最后看删掉一个 required group 为什么会让 repair localization 明显下降。

最值得带走的判断是：

Agent 的 Retriever 应该回答“当前决策还缺哪些事实”，而不仅是“什么内容和用户问题最像”。

这个原则可以直接迁移到 Shopping Agent：预算、场景、兼容性、尺寸、物流、品牌偏好等约束必须形成覆盖集合；重复召回多个同类高相关商品，无法替代一个真正缺失的关键约束证据。

把现有 Top-K Retriever 的结果按“是否覆盖每个 group”重新打分，而不是只看 relevance。定义一个最简单的 complete-set 指标：

停止条件： 如果现有 Retriever 的失败主要来自“完全没找到相关区域”，而不是“相关证据重复、关键组缺失”，那么继续做 complement policy 的收益不会大；这时应该优先修召回覆盖。如果高 relevance Top-K 经常包含 3–5 条语义重复片段，却稳定漏掉一个决定性事实组，集合级 complement objective 的优先级就很高。

这个实验真正要回答的是：

Agent 卡住时，问题是“没搜到”，还是“搜到了很多相关东西，但仍没凑齐做决定需要的证据”？

今日主线： Verifier Blind Spot · Long-Horizon Harness · Selective Teacher Guidance · Recommendation Scaling · Cross-Model KV · Live Trace State

今日核心判断

  1. Self-improving cascade 最大的风险之一，是“监督器看不见的错误”会被训练闭环系统性保留下来。 Cheap Verifiers, Large Blind Spots 的 real-model 实验里，同一 verifier 的 blind-spot rate 随 student 从 0.5B 扩大而上升至约 0.55；更强 verifier 能把 blind spot 压到约 0.05，却又把近一半 hard-MATH 请求升级到 frontier model。更严重的是，系统内部 dashboard 一直显示约 3% 错误，而真实交付错误率在 14%–32% 之间变化。

  2. 长程 Coding Agent 的核心状态正在从“代码仓库”扩展成“代码 + 可验证证据 + 版本历史”。 Harness-of-Harness 把 Planner、Developer、只读 QA Tester 分开，按小步能力增量循环开发，并用 progressive disclosure 只在需要时展开历史细节；三组 harness-model pair 在三个 benchmark 上三轮后平均相对增益 52.25%。值得重视的是独立验收和 evidence state，而不是把 headline 理解为模型本体能力提升。

  3. 昂贵 Teacher 不必长期留在 Agent inference loop。 SAGE 只在 student policy entropy 高时请求 VLM teacher，训练阶段 VLM 调用仅占 1.2%–13.3% 的环境步，部署时完全移除 Teacher。它同时给出一个有价值的负结果：Advantage-Weighted BC 并未稳定优于普通 BC，说明“更复杂的 teacher weighting”并非收益核心。

  4. 推荐系统里的 Transformer scaling 仍然值得做，但要围绕推荐本身重写计算结构。 ReST 在行为序列侧加入 gated attention、时间位置编码、稳定残差、直接序列监督和 shared-prefix compute reuse；TikTok Shop Ads 一周线上 A/B 中，AUC +1.31%、Advertiser Value +11.93%，满足 50 ms P99。更有启发的是，单纯给 sequence encoder 加 500% MoE 参数几乎没有 AUC 收益。

  5. 跨模型 KV cache 复用正在从“能不能映射”进入“映射是否足够便宜、是否尊重 receiver attention structure”。 CacheBridge 在 Qwen3 14B→32B 上把 mapper storage 从 4.296 GB 降到 0.538 GB，应用最高加速 3.0×，500-sequence 构建从 92.63 s 降到 8.63 s，并保持 99.83% mean target retention；但目前只有三个 transfer direction，离通用 model-routing 基础设施仍有距离。

  6. 长程 Agent 的 trace 需要成为结构化状态，而不只是越来越长的聊天记录。 Parsing the Stream 用 append-only ledger 折叠 typed run state，再分别给人类 observer 与 Agent 编译 view：observer 输入 token 减少约 14–15×、成本降低 5–7×。但论文也诚实显示，一个更便宜的 prompt scratchpad 在 agent-side accuracy 上可以匹配 fold；所以其可迁移价值更偏确定性、可审计与多消费者共享状态，而不是“复杂 Memory 一定更准”。

1. Cheap Verifiers：Self-Improving Cascade 可能把错误“训练进盲区”

一句话结论： 如果同一个 verifier 同时负责路由、生成训练数据和监控质量，那么系统最危险的错误恰好是 verifier 自己认为正确的错误；这些错误既不会被升级，也不会进入纠正数据，dashboard 还会显示一切正常。

原始来源： Cheap Verifiers, Large Blind Spots: Measuring the Reliability Cost of Cost-Saving Cascades

发生了什么

论文研究一种看起来非常合理的 cost-saving cascade：cheap student 先回答，verifier 判断是否接受；被拒绝的样本升级到 stronger teacher，并且可以继续作为纠错数据训练 student。

问题在于，训练闭环只能看到 verifier 能识别的错误。作者把 verifier 对真实错误的漏检率定义为 blind-spot rate：

\[\beta_t = P\left(V\text{ accepts}\mid \text{student is wrong}\right).\]

一旦错误被 verifier 接受，它就会直接交付给用户；在 corrective loop 中，它也不会进入训练集。随着训练继续，系统天然更容易消除 verifier 看得见的错误，而把 residual error 集中到 verifier 看不见的区域。

作者用数学任务构造了一个“wind tunnel”：真实正确性由 exact match / symbolic equivalence 充当隐藏 oracle，verifier 只看到题目和 reasoning trace、看不到 gold，因此可以直接量化 verifier 到底漏掉了多少真实错误。

关键结果

现象结果
固定 gpt-4o-mini verifier，student 0.5B 时 blind spot0.12
student 扩大后 blind spot最高约 0.55
hard-MATH 上 stronger verifier blind spot约 0.05–0.09
gpt-4.1 verifier 的升级率46%
同一 hard-MATH 设置真实错误率39%
self-improving loop 内部 dashboard error约 3%
gold user-facing error14%–32%

Qwen2.5-7B + gpt-4o-mini 的 GSM8K corrective loop 中，verifier 看到的交付错误率一直约 3%，gold error 却在 14%–32% 之间变化；frozen control 保持约 13%，而 corrective loop 本身反而使 student 退化。作者还测试了多个 teacher，包括 cross-family 与 same-family teacher，naive fine-tuning on verifier rejects 都没有得到作者原本希望看到的 self-improvement，反而会因 hard-tail distribution shift 退化甚至崩溃。

这直接击中当前 Agent / RAG / LLM product 里一个高频架构：

如果质量监控仍然由同一个 verifier 产生，那么“verifier-estimated accuracy”并不是独立的 observability channel。系统优化得越久，错误可能越集中到 verifier 的 blind spot，而 dashboard 反而更漂亮。

因此，Verifier-as-Router、Verifier-as-Teacher-Filter、Verifier-as-Monitor 最好不要完全复用同一套判断机制。 至少需要一小部分独立 gold、人工 audit、程序化 oracle 或不同 failure mode 的外部评估作为闭环之外的测量仪器。

可信度与局限

这篇论文最强的地方是把 blind spot 变成了可测量量，并且清楚区分“真实测量”与“理论外推”。它也主动承认：真实模型实验中，作者没有成功构造一个真正持续变好的 parametric self-improving loop，因此论文关于长期正向训练后 residual error floor 的 conservation-law 结论，在真实模型上仍是理论预测，而不是已经观测到的 self-improvement ceiling。

此外，主要 real-model wind tunnel 来自 GSM8K / MATH，且关键 corrective-loop 曲线是 single seed。数学任务能提供独立 oracle，正是它适合测 blind spot 的原因；这不能直接把 0.55 或 32% 外推到代码审查、推荐解释或开放式 Agent Judge。

最值得继续追踪

最值得追的是两个问题：第一，在代码测试、工具执行、RAG claim verification 等拥有部分程序化 oracle 的任务上，blind spot 是否同样随 student 能力扩大而上升；第二，是否可以用小比例 independent audit + verifier ensemble，把盲区率压下来，而不把 frontier escalation cost 全部买回来。

2. Harness-of-Harness：自主软件开发需要“Artifact State + Evidence State”

一句话结论： 长程 Coding Agent 不能只让同一个 Agent 不断改代码再自我检查；HoH 的真正价值是把计划、实现、独立验收、证据积累和版本回退组织成持续开发循环。

原始来源： Harness-of-Harness 论文 · 项目仓库

发生了什么

HoH 在现有 coding-agent harness 外再加一层长期开发循环。每轮由三个稳定角色协作：Planner 读取需求与上一轮证据，提出既修复问题又增加一个小能力的开发计划；Developer 修改共享 workspace，并在实现过程中做局部测试；QA Tester 对候选系统做只读、独立的 black-box / white-box 验收，再把 verified behavior、unsupported claim 和 unresolved failure 交回下一轮 Planner。

它没有再做一个“把所有历史塞进向量库”的通用 Memory，而使用 progressive disclosure：计划、报告、历史和其他 artifact 持久化到文件系统，首先只暴露精简分类索引，需要时再展开细节。与此同时，系统保存版本化项目历史，发生大回归时可以返回此前已验证状态。

关键结果

三轮后，三组 harness-model pair 在三个 benchmark 上均优于对应 standalone harness：

Benchmark三轮后的绝对增益范围
GameCraft-Bench+16.62～22.08 points
FrontierSWE+19～29 points
ProgramBench+6.09～16.85 points

论文汇总的三轮平均相对增益为 52.25%，最大相对增益为 82.86%。在 FrontierSWE 上，HoH + Codex + GPT-5.5 继续运行十轮后，从 22% 提高到 72.67%。开放式实验中，系统还运行 70+ iterations 构建一个完整 FPS 游戏。

为什么重要

这项工作真正值得借鉴的是 evidence state。长程开发里，代码仓库只能告诉 Agent “现在有什么”，不能可靠告诉它：

如果这些信息只存在自然语言上下文，几轮之后就会被压缩、遗忘或重新解释。把验证证据与代码 artifact 并列为一等状态，比单纯增加 context window 更接近真实软件工程。

另一个关键点是 Developer 无权自我验收。实现者可以选择怎样完成任务，但是否接受该版本由独立 QA role 与结构化测试证据决定。这与真实 CI / code review 的职责分离是一致的。

可信度与局限

Headline 不能被解释成“GPT-5.5 自己从 22% 学到了 72.67% 的新模型能力”。模型、外部 harness、长期迭代预算、状态组织和验收机制共同改变了最终系统表现。

项目仓库目前已经公开论文、演示和 workflow 说明，但 README 明确写着 HoH-lite 实现仍是 coming soon。因此今天可以审查方法与结果，但还不能像成熟开源 Agent framework 那样完整复现整个 HoH 栈。

同时，持续在同一 benchmark / 软件项目上迭代天然存在 benchmark adaptation。真正证明“持续改进机制”具有可迁移性，需要冻结已有 evidence / skill policy 后，在新项目和新 benchmark 上测试，而不只是继续给原任务更多循环预算。

最值得继续追踪

我会重点看 HoH-lite 发布后的三个 ablation：独立 QA 是否是主要增益来源；progressive disclosure 相对普通 full-history / summary 的收益；以及 versioned evidence 在新项目中究竟是通用工程经验还是原项目专属状态。

3. SAGE：把昂贵 VLM Teacher 当“临时探索导师”，而不是永久 Policy

一句话结论： Teacher 的最佳用途可能不是每一步替 Agent 决策，而是在 student 真正不确定时帮它进入稀疏 reward 区域，再让环境 reward 决定最终内化什么。

原始来源： Selective Agent Guidance via Entropy（EMNLP 2026 Findings）

发生了什么

SAGE 在训练期间观察 student policy 的 normalized entropy。只有 entropy 高于阈值、说明当前 action distribution 较不确定时，系统才调用 VLM teacher；Teacher 给出一个动作，环境实际执行这个动作，student 对自己采样的动作继续做 PPO，对 teacher-guided transition 做 Behavioral Cloning。

这种设计把 Teacher 从“全程控制器”改成“临时 exploration intervention”。部署时最终 policy 完全独立运行，不再调用 VLM。

关键结果

六个受控环境中，SAGE 的 VLM 调用只占训练步数的 1.2%–13.3%，而 VLM-as-Policy、LVLM2P、DAgger 等需要 100% teacher calls。CardMaze 上，VLM-as-policy 得分为 0，SAGE 最终达到 1.0，说明一个不够可靠、不能直接当 policy 的 Teacher，仍可能提供足够有用的局部探索信号。

但结果绝非全面胜出。LavaGap 中 PPO 达到 0.945，SAGE 只有 0.688；有些环境里 Teacher 本身缺乏有效 action semantics，guidance 反而帮不上忙。随机 Teacher control 也不会改善 PPO，并且在某些设置会明显伤害已有 policy。

为什么重要

对于 Tool Agent、Computer Use 和具身 Agent，昂贵 frontier model 经常被用作 rollout policy、critic 或逐步 teacher。如果真正有价值的 teacher call 只集中在少量 high-uncertainty state，那么可以把训练预算从“每一步都问大模型”改成“只在信息价值高的状态问”。

而且环境 reward 仍然是最终 policy optimization 的主轴：Teacher 负责帮助 student 看见原本探索不到的区域，不拥有永久解释权。这比纯 DAgger 更适合 Teacher 也会犯错的现实情况。

可信度与局限

论文主要是离散动作、受控视觉环境；ALFWorld 被作者明确标记为 exploratory evaluation。Entropy 也不是完美的 epistemic uncertainty：一个状态可能存在多个同样合理动作，entropy 很高却并不需要 Teacher；反过来，模型也可能对错误动作极度自信。

另一个非常值得记住的负结果是：论文原本设计了 Advantage-Weighted BC，希望用环境 advantage 对 teacher action 加权，但 ablation 没有显示它相对普通 BC 有稳定 robustness benefit，有些环境普通 BC 反而更好。因此 SAGE 的核心证据支持“selective querying + explicit imitation”，并不支持“AWBC 是必要组件”。

最值得继续追踪

真正值得升级的是从 policy entropy 走向 expected value of guidance：直接学习“在当前状态询问 Teacher，预期会把未来 return 提高多少”，并把 Teacher 成本一起纳入 query policy。

4. ReST：推荐 Transformer 要围绕“行为序列 + Candidate Ranking”重新分配计算

一句话结论： 工业推荐并不缺把 LLM block 搬进 Ranker 的尝试，真正的难点是长行为序列怎样持续贡献增益、怎样避免 dense feature shortcut，以及怎样把用户前缀计算跨候选复用。

原始来源： From Language to Behavior: Scaling Sequence Transformers for Industrial Recommendation Ranking with Rec-Native Designs

发生了什么

ReST 针对推荐 ranking 中“序列计算重、候选交互多、监督稀疏、时间关系强”的结构做了多个 rec-native 设计。Sequence encoder 使用 dual-gated attention、RoPE + temporal encoding、stabilized residual norm，并加入 training-only 的 sequence CVR supervision 和 sequence/non-sequence alignment；架构进一步拆成可复用的 heavy user-sequence encoder 与 lightweight cross decoder。

系统层则引入 user-level shared-prefix training 和 serving：同一用户的一段行为序列只计算一次，然后针对大量候选复用 prefix representation，而不是为每个 candidate 重跑完整序列 Transformer。

关键结果

论文的 scaling study 很有信息量。行为 context 从 100 扩到 16K tokens 时，ReST 仍持续改善，测试范围内额外 AUC lift 约 0.4%；generic LLaMA / HSTU block 更早饱和。深度和 hidden width 扩大时，ReST 也保持更单调的收益。

更重要的 ablation 是：

改动参数变化AUC 增益
仅给 sequence encoder 加 MoE+500%+0.00%
Cross decoder+473.2%+0.05%
Stabilized Residual Norm约 0+0.08%
RoPE + temporal encoding约 0+0.12%

共享前缀训练在作者的优化 pipeline 上进一步带来 5.8× training throughput；serving 时，sequence-modeling component 的 per-request inference cost 最高减少 20×。

最终一周 TikTok Shop Ads A/B 使用 20% production traffic，control 为强生产 DLRM：online AUC +1.31%，Advertiser Value +11.93%（$p<0.01$），并满足 50 ms P99 latency，之后完成生产部署。

为什么重要

这篇最值得推荐系统从业者看的不是 11.93% 这个 headline，而是 “参数 scaling”和“有效 compute scaling”完全不是一回事。直接加 500% MoE 参数没有可测 AUC 收益；反而是更贴近行为时间结构的 attention / normalization / supervision，以及把可重复的 user prefix compute 复用起来，让更长序列真正可部署。

对工业 ranker 来说，候选数通常远大于用户数。一旦 sequence encoder 能做到 compute once, decode many candidates，长序列模型的经济性会发生质变。

可信度与局限

这是强工业证据：公开数据集 + scaling study + ablation + 一周线上 A/B。但核心生产结果仍来自论文作者所在平台，无法由外部团队复现相同用户分布和 serving stack。

+11.93% 指的是 Advertiser Value（Advv），是收入相关核心业务指标，不是 GMV 或平台总收入直接增长 11.93%。完整 ReST 还是一组架构、监督和系统 co-design 的组合，不能把线上 uplift 单独归因于某一个 gated-attention 模块。

最值得继续追踪

我会看两类后续：一是 16K 以后 sequence length 是否继续存在可用 scaling，还是只把 cache / memory cost推高；二是 prefix reuse 在多目标、多候选、实时特征频繁变化时能保持多高的 cache validity 和真实 P99 收益。

5. CacheBridge：让一个模型的 Prefix KV 直接成为另一个模型的可用状态

一句话结论： 多模型 routing 的隐藏成本是“换模型以后要不要重新 prefill 同一长前缀”；CacheBridge 证明同家族／相近架构模型之间的 KV 可以用很小的 affine interface 转移，但 transfer stability 仍高度依赖 receiver structure。

原始来源： CacheBridge: Efficient Cross-Model KV Cache Transfer

发生了什么

已有 cross-model cache mapping 可以用 source KV 重建 target KV，但 Full-Head Mapping 会让每个 target head 连接所有 source heads，mapper 参数、计算与校准数据很快膨胀，而且在部分模型方向出现明显任务质量损失。

CacheBridge 做三项收缩：Head-Local 让 target KV head 只依赖一个 architecture-aligned source head；Attn-Repair 使用 target model 的 causal attention sensitivity 对映射误差加权，把拟合精度优先花在 receiver 真正敏感的位置；Fused-Fit 在 GPU 上直接构造 weighted sufficient statistics，避免生成巨大的中间 observation tensor。

关键结果

Qwen3 14B→32B：

指标Full-Head MappingCacheBridge
Mapper storage4.296 GB0.538 GB
Mean target retention99.72%99.83%
500-sequence construction92.63 s8.63 s
Application speed—最高 3.0×

构建阶段相当于 10.7× 加速、storage 8× 缩减。更重要的是，在两个 Ministral 3 failure directions 上，HellaSwag 分别从 52.2%→72.6%、44.4%→76.0%，恢复 20.4 / 31.6 个百分点；这说明“所有 source head 都参与”并不一定更稳，receiver-aligned structural locality 反而可以减少错误映射。

为什么重要

多模型系统常见的链路是：小模型先处理，大模型在复杂请求上接手；或者 Agent 根据阶段从便宜模型切换到强模型。对长 context 来说，模型切换不仅有权重 / 调度成本，还有目标模型重新 prefill 整段 context 的成本。

如果 source cache 可以低成本映射到 target，model routing 才可能从“每次换模型重新读一遍历史”走向真正的状态 handoff。它对 speculative multi-model inference、cost cascade 和多 Agent shared-context 都有潜在价值。

可信度与局限

当前只覆盖三个 transfer directions，且实验主要验证 mapping quality、mapper construction 和若干 benchmark retention。它不是“任意两个模型都能共享 KV”。模型层数、head grouping、RoPE / GQA 结构以及训练分布差异太大时，简单 affine map 可能失效。

更关键的是，论文里的 mapper application 更快不等于端到端 request latency 一定更低。真实 serving 还包含 source KV 获取、跨 GPU / 节点传输、target cache materialization、cache miss 与 batching；这些需要生产 workload 验证。

最值得继续追踪

真正重要的指标应是：在相同 task quality 下，source model → target model 切换能减少多少 target-prefill latency、PCIe/NVLink/network bytes 和 GPU-seconds，以及 mapper 是否能跨 checkpoint 更新稳定复用。

6. Parsing the Stream：Agent Trace 应该同时服务“机器继续做事”和“人类看懂发生了什么”

一句话结论： 长程 Agent 的完整 trace 既不适合反复塞回模型，也不适合让人从头翻日志；更合理的状态层是 append-only raw ledger + deterministic typed state + consumer-specific views。

原始来源： Parsing the Stream 论文 · SalesforceAIResearch/tracelab · 数据集

发生了什么

tracelab 把 Agent 的每一步事件先写入不可变、append-only ledger，然后增量 fold 成 typed RunState，再为不同消费者编译不同 view：human observer 看到适合监控与审计的状态；Agent 看到适合继续工作的 compact worker state。

这种设计与传统 summary 最大的区别是：fold 是可验证的确定性状态变换，而不是让另一个 LLM 每隔一段时间自由总结一遍历史。仓库还公开了 regression/property tests、spend ledger、失败实验 scoreboard 和可再生成的 synthetic corpus。

关键结果

Observer side：编译 view 相比 budget-capped raw trace reading，使 reader input tokens 减少约 14× / 15×，成本降低 5–7×，accuracy 从 0.48 提高到 0.85–0.87。

Agent side：在 120-link sequential-dependency task 上，维护 running statistic 的 per-step state 达到 30/30 成功，而 full-context prompting 为 8/30。

但作者同时给出一个非常重要的反例：prompt-level scratchpad 可以以更低成本匹配 fold 的 agent-side accuracy。 论文因此把 fold 相比 cheaper alternative 的剩余价值更谨慎地归为 deterministic auditability，以及让 observer 与 Agent 共享同一个状态源。

为什么重要

Agent 系统目前经常分别维护：模型聊天历史、用户可见日志、debug trace、Memory summary、dashboard 状态。它们如果互相独立，会产生“Agent 认为自己做了 A、dashboard 显示 B、原始工具日志其实是 C”的状态漂移。

Append-only ledger + derived typed state 的工程价值，是把 raw evidence 保留下来，同时允许不同消费者获得不同粒度的 materialized view。这和 event sourcing / CQRS 很接近，比自由文本 Memory 更适合长期运行和事后审计。

可信度与局限

作者非常明确地限制了强结论：observer questions 与 view schema 是共同设计的，所以 14–15× token / 5–7× cost reduction 只应理解为“当 schema 覆盖真实查询需求时”的结果；agent benchmark 也存在 benchmark-system co-development，因此 30/30 vs 8/30 被作者标记为 descriptive。

更关键的是，order-sensitive task family 中 fold 不再有同样优势。只要任务需要保留无法被当前 schema 简单聚合的事件顺序，错误的 typed state 反而可能把必要信息提前压掉。

最值得继续追踪

真正有价值的下一步，是在真实 Coding / Browser Agent 数小时日志上比较：raw trace、LLM summary、scratchpad、typed fold 在 incident reconstruction、human audit time、Agent recovery success 和 total serving cost 上的 Pareto，而不是只做 synthetic dependency chain。

今日值得收藏的代码 / 学习资源

SalesforceAIResearch/tracelab 是今天最值得直接读代码的项目。它不仅公开 happy-path implementation，还把 bench/scoreboard.json、完整 LLM spend ledger、99 个 regression/property tests、CONTINUE traces 和可再生成 synthetic corpus 一起放出。对于长程 Agent observability / memory architecture，这比单读论文更有价值。

Harness-of-Harness 值得先关注 workflow 和 demo，但需要注意当前 README 明确标注 HoH-lite coming soon；目前仓库主要是项目说明、assets 和演示，不宜把它写成已经可以完整安装复现实验的 framework。

vLLM-Omni：MiniMax H3 production serving 是近期很好的系统优化长文。它没有把“模型更快”归因于单个 kernel，而是沿完整 pipeline 优化 encoder、长序列 DiT、VAE、GPU→CPU output transport 和 MP4 construction；随后再把 MiniMax H3 的 49 次 DiT forward 替换为 FastH3 的 4 次。8× B300 测试中，完整 10.125 秒 MP4 在 8.678–8.710 秒生成完成。这里的“real-time”明确指完整文件准备时间低于播放时长，不是 time-to-first-frame 或流式生成。

ARISE-RL 值得做 Agent RL / self-evolution 的人跟踪。它让 Generator 与 Solver 围绕 rubric 协同进化，并让 Generator 用真实 tool observation 构造位于 Solver 当前能力边界附近的任务；摘要已经显示出“环境 / 任务生成器也是 RL state”的方向，但今天公开信息不足以支持一个统一 effect-size headline，因此更适合作为后续实验路线而不是确定结论。

CoBRA 则直接研究“什么时候该用工具”：通过同状态下 tool / no-tool paired trajectory 估计工具的 counterfactual marginal benefit，再做 boundary-aware SFT + RL。摘要显示 Qwen3-4B 在 retrieval tool 上改善 tool-use efficiency 和 OOD boundary-sensitive accuracy，但尚缺足够公开细节支持强量化结论。

今日最值得花 30 分钟阅读的一项

首选 Cheap Verifiers, Large Blind Spots。

它值得读，不是因为又提出一个更复杂的 Judge，而是因为它给当前“cheap model + strong verifier + feedback loop”这类看起来非常合理的系统提供了一个明确反例：如果系统的训练信号和质量仪表都来自同一个 verifier，那么系统没有任何内部渠道可以观察 verifier 自己的 blind spot。

建议按这个顺序读：先理解 $\beta=P(V\text{ accepts}\mid\text{wrong})$ 为什么比普通 verifier accuracy 更贴近 cascade risk；再看 fixed verifier 下 student 越强、blind spot 反而越大的结果；然后看 stronger verifier 为什么通过过度升级把 cost saving 买回来；最后重点看 dashboard ~3% vs gold 14%–32% 的曲线，以及作者为什么明确说真实 corrective loop 实际上失败了、理论 error floor 仍未在“真正持续改进的 real-model loop”中验证。

真正值得带回系统里的问题是：

你的 verifier 看不见的错误，现在由谁来测？

如果答案仍然是“还是这个 verifier”，那不是监控，只是重复一次同样的判断。

这项测试真正要回答的是：

你的 self-improving loop 是在消灭错误，还是只是在把错误搬到自己的监控盲区？

> **今日主线：** Test-Time Policy Optimization · Industrial Self-Evolution · Hybrid Retrieval Programs · KV Cache · Tool Authorization · Open-Weight MoE

## 今日核心判断

1. **Test-time training 正在从“多数票当伪标签”推进到“对同意与不同意样本采用不同优化规则”。** TTPO 的关键不是多做一次 self-consistency，而是承认 majority vote 出错时，agree / disagree rollout 的信息价值并不对称；在无标签条件下，它把 Qwen3-1.7B 的三项 test-time benchmark 平均分从 38.0 提高到 45.2，但结论仍主要来自竞赛数学，离开放式 Agent 的在线自适应还有距离。
2. **工业 Self-Evolving AI 的新瓶颈正在从“能不能自动实现改动”转向“下一轮到底应该改什么”。** Astar 用历史迭代记录训练专门的 evolution-direction model，并在 Lazada 广告系统完成 20 轮连续自动迭代；这比让通用 LLM 临时头脑风暴更接近可积累的工程经验，但其强结果仍是单一企业系统中的第一方验证。
3. **混合搜索不一定要把 SQL、向量检索、图检索的融合规则写死。** ProRetrieval 让 4B 模型直接生成可执行检索程序，用 SQL 作为集合代数连接结构化约束与文本／图像向量搜索；其 Hit@1 超过作者所测 GPT-5.5，但 benchmark 是作者新建的，不能直接等价为通用搜索能力领先。
4. **KV eviction 的常用“高 attention = 高重要性”假设值得重新审计。** TwinKV 的 leave-one-out probe 得到 attention magnitude 与 token 因果贡献的 Spearman $\rho=-0.004$；它不重写 eviction policy，而是把“无替代信息的孤儿 token”换回、“有近重复项的 donor token”换出，说明 redundancy repair 可能比继续堆单点 importance score 更稳。
5. **Tool output 中的“行动建议”不应天然继承执行权限。** SARA 把 action induction 与 runtime authorization 分开，并持续记录 action provenance；在 AgentDojo / AgentDyn 的四个主要设置中将 ASR 控制在 0.63% 以内。这个设计比单纯过滤恶意字符串更接近真实授权模型，但仍依赖可审计的用户目标与成功执行证据。
6. **Hy4 preview 值得关注的不是厂商榜单，而是 770B / 49B-active MoE、Gated Sparse Attention、原生 MTP 与 1M context 的组合。** 腾讯已经开放模型权重与 FP8 版本；内部 163 位专家、203 个工程任务的盲评略高于 GLM-5.3 和 Kimi K3，但这仍是第一方评测，真正有区分度的证据将来自第三方在 vLLM / SGLang 上的长程 Agent 成本与质量复现。

## 1. TTPO：多数票错了以后，不要把所有 rollout 一起带偏

> **一句话结论：** Majority-vote pseudo-label 最大的问题不是噪声本身，而是一个错误伪标签会把整组 rollout 的 teacher signal 同时翻转；TTPO 利用 agree / disagree 的不对称性，把无标签 test-time training 做得更稳。

**原始来源：** [TTPO: Test-Time Policy Optimization](https://arxiv.org/abs/2608.27448)  
**代码：** [ZJU-REAL/TTPO](https://github.com/ZJU-REAL/TTPO)

### 发生了什么

RL 和 On-Policy Self-Distillation 通常需要 ground-truth correctness signal。到了真正的 test-time training，最自然的替代方案是采样多条答案，用 majority vote 作为伪标签，再把它当 teacher target；问题是多数票一旦错，所有与它一致的 rollout 都被错误强化，与它不一致但可能正确的 rollout 又被统一惩罚。

TTPO 的观察是这种错误具有不对称性：**与多数票不一致的 rollout 往往本来就更不可靠，不论 majority vote 最终是否正确。** 因此方法把一组 rollout 拆成两个分支：agree branch 用 OPSD 做蒸馏；disagree branch 不直接向伪标签模仿，而用 grouped RL 处理。Token 级别再做一次筛选——蒸馏分支下调已经收敛的位置，RL 分支只重点惩罚“高置信但错误”的 token。

### 关键结果

TTPO 仓库给出的无标签 test-time training 结果如下：

| Qwen3 模型 | Base 平均 | OPSD-TTT | TTPO |
|---|---:|---:|---:|
| 1.7B | 38.0 | 41.9 | **45.2** |
| 4B | 57.4 | 59.4 | **61.1** |
| 8B | 60.7 | 63.7 | **65.3** |

训练期 OpenThoughts 设置中，TTPO 还在五项竞赛数学 benchmark 上达到与 label-supervised OPSD 相当或略高的平均结果；作者同时报告 non-thinking evaluation 的大幅改善。

### 为什么重要

这项工作最值得带走的不是某个数学分数，而是一个更一般的 self-training 原则：**伪标签不应该被当成对整组样本同质、等权的真值。** 当内部自监督信号可能出错时，应先分析“不同类型 disagreement 在错误伪标签下是否仍保留方向性信息”，再决定如何更新。

这对 self-evolving Agent 也有潜在意义。Agent 没有 ground truth 时经常依赖 self-consistency、self-judge 或多轨迹投票；如果一次错误多数意见可以同步污染所有 memory / skill update，系统会把偶然错误固化成长期状态。

### 可信度与局限

TTPO 的主要证据来自竞赛数学，reward 可验证、答案空间相对明确；开放式 Tool Agent 的 trajectory 不存在这么干净的 majority label。其次，agree / disagree 的不对称性是实验观察，不是所有任务都必然成立。迁移到 coding、search 或 workflow Agent 前，必须先验证 disagreement conditional accuracy 是否仍有相同结构。

### 最值得继续追踪

最值得看的不是把 rollout 数继续堆大，而是：**当伪标签错误时，哪些局部信号仍具有正确方向？** 如果 verifier、工具执行结果、retrieval evidence 或 process check 能与 TTPO 的不对称分支联合，test-time adaptation 才更接近真实 Agent 环境。

## 2. Astar：Self-Evolving 工业系统开始专门学习“下一轮改什么”

> **一句话结论：** 自动写代码、训练和评测已经越来越成熟，真正稀缺的是 senior expert 式的 evolution direction proposal；Astar 把这部分经验从历史迭代记录中训练成一个专门模型。

**原始来源：** [Astar: Learning to Propose Evolution Directions for Self-Evolving Industrial AI Systems](https://arxiv.org/abs/2608.27287)

### 发生了什么

工业模型迭代通常是一条闭环：提出方向 → 实现代码 → 训练 → 评估。后面三步已经可以被自动化系统大量接管，但“下一轮应该尝试什么”仍高度依赖资深工程师经验。论文首先报告，GPT-5.5 等通用模型直接做 proposal 时容易给出泛化、与当前系统状态错位的建议；作者据此把方向生成本身做成专门学习任务。

Astar 从工业历史 commit 和实验记录中构造 evolution corpus，通过 pairwise sample expansion 与 noise filtering 增加有效监督；模型侧使用 mid-training、SFT 和 RL，并用 hierarchical hints 缩小方向空间，用 reward model 充当昂贵真实训练的快速 surrogate evaluator。

### 关键结果

| 指标 | Astar-8B | Human experts | 最强通用 LLM |
|---|---:|---:|---:|
| 单 proposal 真实执行成功率 | **0.6786** | 0.3229 | 0.3071 |

在 Lazada 广告系统中，作者进一步让 Astar 连续指导 **20 轮、两周**自动迭代：离线 Hitrate@200 提高 **23.6%**；线上 A/B 报告 GMV 相对提升 **4.86%**、广告收入提升 **1.82%**。

### 为什么重要

这项工作把 Self-Evolving AI 的瓶颈从“执行自动化”推进到“研究方向选择”。如果 proposal quality 不能随着历史积累而提高，那么自动训练系统只是更快地跑大量低价值实验；真正可持续的系统需要把：

```text
proposal
→ implementation
→ training result
→ failure / success evidence
→ future proposal prior
```

变成可学习闭环。

对推荐／广告系统尤其如此，因为每次改动的价值强依赖当前模型、数据、业务约束和过去试过什么；纯通用知识无法替代这种局部经验。

### 可信度与局限

这是很强的生产信号，但也是高度场景化的第一方结果。Astar 学到的是 Lazada 工业迭代历史中的经验分布，不能直接推出它能在搜索、LLM 训练或另一家广告系统中同样超过专家。线上 uplift 也来自完整自动迭代闭环，不能拆解成“8B proposal model 单独贡献了多少”。

另一个风险是历史偏见：如果过去团队长期只探索某类架构，模型可能学会更高效地重复既有研究范式，而不是发现真正异质的新方向。

### 最值得继续追踪

我更关心 **proposal novelty × execution success × long-term transfer** 三者的 Pareto。一个方向如果只在当前 checkpoint 上有效、下一代模型立即失效，它更像局部调参经验；真正的 evolution knowledge 应该能跨版本保留一定价值。

## 3. ProRetrieval：让 LLM 生成“检索程序”，而不是只生成一个 Query

> **一句话结论：** 复杂搜索真正需要的是组合结构化过滤、文本／图像语义检索和 Boolean logic；ProRetrieval 把这些算子直接放进模型的 action space，让模型输出可执行 DSL。

**原始来源：** [ProRetrieval: Learning to Orchestrate Hybrid Search via Executable Program Synthesis](https://arxiv.org/abs/2608.27017)

### 发生了什么

现实电商或企业搜索经常同时包含硬约束和软语义，例如“价格低于某阈值、某品牌之外、外观和这张图相似，而且描述里要符合某种用途”。RRF 等 fusion 方法只能用固定规则融合结果；self-query retriever 通常能抽结构化 filter，却很难表达任意多路组合逻辑。

ProRetrieval 让 Qwen3-4B 直接生成一个 hybrid retrieval program。DSL 中既有 SQL operator，也有文本／图像 vector-search primitive；SQL 被当成集合代数，用交、并、差等逻辑组合异构 candidate set。模型用 GRPO + DAPO 训练，并通过分层四项 reward 同时约束程序可执行性和最终检索质量。

### 关键结果

| Benchmark | ProRetrieval 4B Hit@1 | GPT-5.5 Hit@1 |
|---|---:|---:|
| E-commerce | **0.81** | 0.69 |
| Enron Email | **0.91** | 0.86 |

作者同时报告它超过 Claude Opus 4.7 以及一组 retrieval、structured-query、graph 和 LLM-augmented baseline。

### 为什么重要

它把“检索策略”从 pipeline 外的人工逻辑，变成模型可以学习和优化的显式程序。相比 end-to-end 直接输出 item，程序中间态更容易：

```text
审计 → 执行 → 缓存 → 局部修复 → 权限控制
```

这对企业搜索很重要，因为很多错误不是 embedding 不够好，而是 **约束组合错了**。显式 DSL 也让失败更容易定位：是 filter 错、向量搜索错，还是集合操作错。

### 可信度与局限

两个 benchmark 都由作者新建，这给方法提供了合适的复杂查询结构，也同时带来 benchmark-design bias。4B 超过 GPT-5.5 证明的是“专门训练的 programmatic retriever 在该协议下更有效”，不能解释成通用 reasoning 能力超过 GPT-5.5。

此外，DSL 越强，生成空间越大；真实企业系统还要处理 ACL、动态 schema、索引版本、超时和成本预算。论文的逻辑表达能力不等于生产环境已经解决这些约束。

### 最值得继续追踪

最值得测的是 **program validity、retrieval quality 与 execution cost** 的三目标 Pareto，以及跨 schema transfer：换一套数据库字段或一套新向量索引后，模型是否仍能组合出正确程序，而不是重新训练。

## 4. TwinKV：KV Eviction 先别急着问“哪个 Token 最重要”，先问“谁有替身”

> **一句话结论：** Attention score 与 token 的真实因果贡献可能几乎无关；TwinKV 不发明第五种 importance score，而是在已有 eviction policy 后做一次 redundancy repair。

**原始来源：** [TwinKV: A Composable Repair Pass for KV Cache Eviction via Pairwise Key Redundancy](https://arxiv.org/abs/2608.27128)

### 发生了什么

作者先做 controlled leave-one-out probe：逐个移除 token，测它对最终答案的边际影响，再与 attention magnitude 比较。得到的 Spearman 相关只有：

$$
\rho=-0.004
$$

这直接挑战了“attention 高，所以 token 值得保留”的常见直觉。

TwinKV 换了一个更局部的问题：一个被淘汰 token 是否在当前 context 中存在近重复 key？如果没有，它是 **orphan**；一个已经保留的 token 如果存在近重复信息，则可以视作 **redundant donor**。TwinKV 在不改变总 KV budget 的前提下，把 orphan 换回、donor 换出，作为任意已有 eviction policy 后的 repair pass。

### 为什么重要

KV compression 的重要性估计经常试图把所有 token 排成一条全局序列；但信息冗余本质上是关系属性。两个 token 单独看都“重要”，如果互为近重复项，保留两个的边际价值仍然可能很低。

这种 composable repair 还有工程优势：不必推翻现有 eviction policy，而可以作为后处理层逐步接入。

### 可信度与局限

论文在 Qwen3-4B、Llama-3.2-1B、LongBench、LooGLE、RULER 与 MMLU-Pro 上测试，并与四种 eviction policy 组合；多数非饱和 baseline 获益，但并不是所有组合都提升。作者明确发现 few-shot classification exemplar 是负例，说明“近重复 key”不总等价于“语义可替代”。

更重要的是，$\rho=-0.004$ 只否定了作者该 probe 下 attention magnitude 的简单因果解释，不意味着 attention 信息对所有 KV policy 都无用。

### 最值得继续追踪

需要把 redundancy 从 key-space 邻近扩展到 **task-conditioned substitutability**：两个 token 表示相似，不代表对当前 query 可互换。若能低成本估计“删除 A 后 B 是否真的补得上”，KV repair 才会从几何启发式走向更强的因果标准。

## 5. SARA：Tool Output 可以影响行动，但不能自己给自己授权

> **一句话结论：** Prompt Injection 的危险不只是出现恶意文本，而是 observation 中的行动诱导被 Agent 错当成“已获授权的下一步”；SARA 用 provenance 把这两个角色拆开。

**原始来源：** [When Tool Outputs Become Commands: Separating Action Induction from Runtime Authorization in Tool-Augmented LLM Agents](https://arxiv.org/abs/2608.27146)

### 发生了什么

Tool Agent 必须读取网页、邮件、数据库和第三方 API 的 observation。问题是这些 observation 可能不只是提供数据，还直接写着“下一步请执行 X”“把文件发送给 Y”。如果模型把“看到一个动作建议”与“拥有执行这个动作的授权”混在一起，外部内容就可以把自己升级成命令。

SARA 在 observation 侧使用 context-isolated Action Probe，暴露并记录 action-inducing semantics 的来源；执行侧则只根据用户目标和来自已授权成功执行的 audited evidence 判断是否放行 tool call，并同时检查 goal、execution-chain 和 argument-level support。No-History-Promotion 进一步防止同一个外部动作建议被历史多次引用后逐渐“洗白”为可信授权。

### 关键结果

作者在 AgentDojo 与 AgentDyn 的四个主要设置中报告，SARA 把 Attack Success Rate 控制在 **0.63% 以下**，同时维持有竞争力的正常任务效用；额外 backbone 上也得到一致方向的 ASR 降低。

### 为什么重要

这比关键词过滤更接近真实权限模型：

```text
observation says X
≠
user authorized X
```

对浏览器、邮件、企业 Workflow Agent，最关键的安全对象应该是“动作来源”和“执行权限”的链路，而不是一段文本是否看起来可疑。

### 可信度与局限

SARA 的效果依赖系统能够明确表示 user objective、authorized successful execution 和 argument-level support。开放任务里，用户目标本身可能模糊；某些动作也需要从未执行过的新步骤，过强的 provenance gate 可能降低可用性。

0.63% 也是 benchmark 内 ASR，不代表现实攻击面已接近零。现实系统还会遇到跨工具状态、长期 memory、权限变化和 UI side effect。

### 最值得继续追踪

我会关注 provenance 是否能成为 Tool API 的一等字段：每个 action argument 不只保存值，还保存“这个值来自哪里、为何被授权、授权何时过期”。如果 provenance 只存在于自然语言 reasoning 中，很难真正审计。

## 6. Tencent Hy4 preview：开放 770B / 49B-active MoE，长上下文与 Speculative Decoding 一起设计

> **一句话结论：** Hy4 preview 的技术信号在于把大 MoE、稀疏注意力、跨层 IndexCache、原生 MTP 与 1M context 放在同一个开放权重模型里；厂商 benchmark 可以参考，但第三方 serving / Agent 复现才决定它的真实位置。

**官方发布：** [Tencent Releases and Open-Sources Tencent Hy4 preview](https://www.tencent.com/tencent-releases-and-open-sources-tencent-hy4-preview/)  
**模型卡：** [tencent/Hy4-preview-FP8](https://huggingface.co/tencent/Hy4-preview-FP8)  
**代码：** [Tencent-Hunyuan/Hy4-preview](https://github.com/Tencent-Hunyuan/Hy4-preview)

### 发生了什么

腾讯 8 月 28 日发布并开源 Hy4 preview。Backbone 为 **770B 总参数、49B 激活参数、78 层**；第一层是 dense FFN，其余 77 层使用 MoE，每层 256 个 routed experts + 1 个 shared expert，每 token 激活 top-8 routed experts 与 shared expert。模型另外内置 1 层 native MTP，用于 speculative decoding；该层本身约 10B total / 0.7B active。

Attention 使用 Gated DeepSeek Sparse Attention，并通过 IndexCache 跨层复用 sparse index；上下文长度为 1M。官方 FP8 权重已经在 Hugging Face 提供，并给出 vLLM 与 SGLang 部署 recipe。

### 关键结果

腾讯内部 163 位专家对 203 个工程任务做 blind side-by-side：

| 模型 | 平均分（4 分制） | Hy4 对比胜／平／负 |
|---|---:|---:|
| Hy4 preview | **2.99** | — |
| GLM-5.3 | 2.92 | 46.8% / 12.8% / 40.4% |
| Kimi K3 | 2.94 | 51.2% / 7.9% / 40.9% |

官方还称 Hy4 preview 参与了自身训练方法、数据策略、评估框架与低层 operator 的自动优化，并通过多轮推理系统优化让端到端吞吐比 baseline 提高 **31.8%**。这部分同样是腾讯第一方报告。

### 为什么重要

大 MoE 的竞争已经不只是“激活参数越少越省”。长 Agent session 的真实成本还取决于 attention、KV、speculative decoding 和并行通信。Hy4 把这些部件一起公开，意味着第三方可以比较：

```text
模型质量
× active compute
× 1M-context KV footprint
× MTP acceptance
× serving throughput
```

而不是只看一个 benchmark score。

### 可信度与局限

当前关键性能结果主要来自腾讯自测。内部专家盲评具有实际任务价值，但测试集、Harness、评分流程和对手版本并没有完全公开，不能视为独立 leaderboard。模型卡也明确列出已知问题：复杂任务存在 **over-reasoning**，并有 **over-verification** 倾向。

另外，1M context 是容量声明，不等于 1M 上的检索、推理和 latency 都足够好；770B 总参数的部署门槛仍然很高。

### 最值得继续追踪

最值得等的是第三方在同一硬件、同一 vLLM / SGLang 配置下测：长 context recall、MTP acceptance、tokens/s/user、P95 TTFT、KV residency，以及真实 Coding Agent 的 cost-per-success。

## 今日值得收藏的代码 / 学习资源

**[TTPO](https://github.com/ZJU-REAL/TTPO)** 已公开训练 recipe，README 明确给出无标签 test-time training 与 OpenThoughts 训练结果。对做 OPD / RLVR 的人，最值得直接复现的是 agree/disagree rollout 的条件正确率，而不是先照搬 loss。

**[Boosting LLM Exploration via Weak-Model Guidance in RLVR](https://arxiv.org/abs/2608.27420)** 提出一个反直觉的探索增强方法：让较弱小模型提供部分 reasoning prefix，主动把目标模型推离已经过度自信的推理模式。作者报告相对 vanilla RLVR 的优势会随 pass@$k$ 中的 $k$ 增大而扩大。它说明“弱模型”有时不是 teacher，而可以是 exploration noise source；摘要没有统一 effect size，当前更适合作为可验证的训练假说。

**[What Makes Good Agentic Data? An ACE Lens on Data Generation for LLM Agents](https://arxiv.org/abs/2608.27260)** 把 Agent 数据写成 $(E,q,\tau,v)$：Environment、task signal、interaction trajectory、optional verifier，并用 Accuracy–Complexity–divErsity 讨论数据生成。它最大的价值是提醒：Agent 数据不是“越多 trajectory 越好”，而是要在有效、对当前 learner 有信息量、不过度重复之间分配预算。

**[HarnessLens](https://arxiv.org/abs/2608.27311) / [代码](https://github.com/jhxu5214/HarnessLens)** 延续 Harness Evolution，但把重点放到验证成本：根据变更涉及的行为只选择相关任务做 verification，并要求 attributable evidence。作者在 3 种 harness、4 个 benchmark 上报告 held-out 平均 +7.6～13.6%，同时低于比较方法的 evaluation budget。它与昨天 AutoSaddler 的差异值得关注：前者更强调“验证哪些 patch”，后者更强调“如何系统地产生 patch”。

**[BCIT: Knowing When Not to Reuse](https://arxiv.org/abs/2608.26730)** 研究 autonomous post-training 的经验复用边界：旧 checkpoint 上一次成功 update，并不自动授权在新 parent weight 上重复。它把 source context、适用条件、hard conflict veto 和 bounded training trial 显式化，适合和 Skill / Memory provenance 一起看。

**[CritICL](https://arxiv.org/abs/2608.27455) / [代码](https://github.com/umwyf/CRITICL)** 不让弱模型教强模型“正确答案”，而是让弱模型暴露自己的 failure modes，再把这些错误模式作为 stronger model 的 input-specific critique context。对 test-time scaling 来说，这是把弱模型价值从答案质量转向失败模式覆盖。

## 今日最值得花 30 分钟阅读的一项

**首选 Astar。** [论文原文](https://arxiv.org/abs/2608.27287)

不是因为 8B 模型“超过专家”这个 headline，而是它把自动 AI 系统里一个经常被忽略的层次明确拆出来：**Proposal quality 本身是一种需要从组织历史中学习的能力。**

建议阅读顺序：先看为什么 GPT-5.5 等通用模型 proposal 会泛化、错位；再看 noisy commit history 如何转成 pairwise training data；然后看 hierarchical hint 与 surrogate reward model 如何降低真实训练验证成本；最后重点看 20 次连续迭代，而不是单次 proposal success。

最值得追问的是：

> 如果 proposal model 只复现过去专家的搜索偏好，它是在“积累研究经验”，还是在更高效地强化组织原有的局部最优？

这也是 Self-Evolving AI 从自动执行走向自动研究时必须面对的核心问题。

## 今日可立即实践的一件事

给任何正在做的 **self-consistency / self-training / test-time adaptation** 流程做一次 **Majority-Vote Asymmetry Audit**。先不要实现 TTPO，先验证它依赖的经验结构在自己的任务上是否存在。

挑 100～300 个有 ground truth 或可靠 verifier 的样本，每题固定采样 8 条 rollout。对每个样本记录 majority pseudo-label 是否正确，以及每条 rollout 是否 agree / disagree：

```python
record = {
    "majority_correct": bool,
    "rollouts": [
        {
            "agree_with_majority": bool,
            "is_correct": bool,
            "mean_confidence": float,
        }
    ],
}
```

至少统计四个条件概率：

$$
P(C\mid A,M),\quad
P(C\mid D,M),\quad
P(C\mid A,\neg M),\quad
P(C\mid D,\neg M)
$$

其中 $C$ 表示 rollout 正确，$A/D$ 表示 agree/disagree，$M$ 表示 majority vote 正确。

真正要验证的是 TTPO 的关键不对称性：即使 $M$ 为假，disagree rollout 是否仍然大多不可靠；同时检查错误 agree rollout 是否集中在高置信 token。

**停止条件：** 如果在自己的任务上 $P(C\mid D,\neg M)$ 并不低，甚至显著高于 agree branch，就不要照搬 TTPO 的“disagree → RL penalty”结构；你的 disagreement 中可能包含大量被错误多数票压制的正确探索。反过来，如果这种不对称在不同 seed、不同难度桶都稳定存在，再值得实现 label-free asymmetric update。

这个小实验的价值是先判断：**多数票失败时，剩余信号里到底还有没有可利用的方向性信息。**

1. SPOD：学生已经超过教师，继续 OPD 为什么反而变差？

原始资料： 论文 · 可阅读 HTML 全文 · 作者代码与训练配方。首次提交：2026-10-18。

发生了什么

普通 On-policy Distillation（OPD）用 Student 自己访问到的状态生成轨迹，再在这些状态上通过 Teacher 分布指导 Student。一个常见假设是：只要教师更强，继续靠近教师总会有帮助。SPOD 论文恰恰给出反例——某些多轮任务中，弱学生训练中途超过教师，持续蒸馏又跌回去。这被称为 Distillation Overshoot。

作者把 OPD 的两种力量分开：Repair 修正学生本来错误的决策；Erosion 将学生原本成功、却不符合教师偏好的动作概率压低。训练早期 Repair 占优，中后期 Erosion 逐渐抹去学生相对教师的独特优势。

SPOD 只在“学生当前整条 Episode 成功，且该动作在教师下的概率小于学生概率”的状态打开保护门，不再对该动作施加会降低其概率的教师 KL 监督，而使用一侧的概率下界项。其他状态维持普通 OPD。其简化门控可写为：

\[g(s,a,\xi)=\mathbf{1}\{R(\xi)=1\land\log p_T(a\mid s)<\log p_S(a\mid s)\}.\]

注意这里 $a$ 是完整动作字符串的序列概率，不是单 Token；概率下界、归一化和门控细节应以作者实现为准。

关键结果

作者在 Qwen3.5-2B←27B 与 Gemma-4-E4B←31B 两组师生上，测试 ALFWorld、WebShop、ScienceWorld。Qwen 组的三任务平均最终成功率由普通 OPD 的 53.3% 提高到 SPOD 的 65.7%（+12.4pp）；Gemma 组从 56.0% 到 66.2%（+10.2pp）。单项最大对普通 OPD 的提升为 +15.2pp；部分设置超出教师可达 20.0pp。作者还报告六个设置中的最终 SPOD 均超过普通 OPD 最佳中途 Checkpoint。

为什么重要

这比“教师质量越高越好”更接近真实 Agent 训练：多轮工具决策可能存在不同但同样正确的动作路径。更强教师偏爱的路径未必比学生已经验证成功的路径更合适。它也提醒做 Agentic RL / OPD 时，除了追踪 KL 与训练 Loss，还要统计成功轨迹中被教师压低的动作占比。

可信度与局限

论文与实现、任务划分、训练配方已公开；项目 README 明确每次训练需要两个 GPU 进程（学生/教师），难以在单张 16GB 显卡上原样复现。门控依赖 Episode 成功标注的可靠性。环境奖励如果存在漏洞，保护机制也可能把 Reward Hacking 动作锁住；在部分可观测场景中，整条成功并不等于每步决策最优。

最值得继续追踪

独立复现 Teacher–Student Action Conflict Rate，按“成功且冲突/失败且冲突/成功且一致”拆分，观察训练中不同组的决策概率与最终任务成功率。对照普通 OPD、最佳验证集早停、成功轨迹 Replay、SPOD，在等教师评分预算下比较最终成功与 pass⁴。

2. RPL：搜索 Agent 不只选择工具，而是学会写检索程序

原始资料： 论文 · HTML 全文。首次提交：2026-10-17。

发生了什么

传统 Agentic RAG 调用 search(query)、read(doc) 或固定 Reranker；即使是多轮检索，也常由模型一步步选择原子动作。Retrieval Program Learning（RPL）将一次 Action 扩展为在受控沙盒中执行的检索程序。程序可组合 sparse_retrieval、dense_retrieval、fuse、dedup 和 rerank，包含局部变量和控制流。

重要差异在于：Agent 可以先检索上百份候选，再利用本地程序过滤、去重与合并，只把最终少量证据写回 LLM Context。检索广度与上下文消费量可以解耦。为解决复杂程序难以通过稀疏 Reward 学出来的问题，RPL 从不够好的已执行程序做语法约束变异、执行验证和再蒸馏，使 Policy 得到比单纯 On-policy Rollout 更有信息量的训练样本。

关键结果

作者在七项开放域 QA 上报告：Qwen3-4B 的 RPL 平均 EM 0.515，Qwen3-8B RPL 0.531。对照方法中，8B Search-R1 的均值为 0.494。RPL 4B 并非全面超过“所有 8B 方法”，而是超过该论文评测的一组 8B 非 RPL 基线。在 GlobalQA 语料级任务中，8B RPL 平均答案 F1 19.11、文档覆盖 dF1 32.97，超过文中检索式 RL 基线。

为什么重要

这项工作连接了 Tool-Agent RL、检索工程与程序合成。对复杂产品知识库、运营报表、多跳问答，理想决策未必是“选哪个 Query”，而是“如何对多次 Query 的结果在程序层做逻辑运算”。它也为低成本 Agent Harness 提供一条不必提升 LLM 参数量的路线。

可信度与局限

结果来自作者使用的 Qwen3、特定 BM25/E5/Reranker 与 QA 集。程序策略增加了可执行代码边界，真实产品必须限制网络、文件访问、循环次数与结果规模。注意作者某些思考模式设定因基线而异，绝对效果不宜视为严格相同推理预算下的跨方法胜利。

最值得继续追踪

固定同一检索器、Answerer 和 Token Budget，对比单次 Search、Sequential Agentic Search、受限 Python Retrieval SDK 与 RPL。报告答案 EM/F1、Evidence Recall、检索调用数、进入上下文的 Token、程序失败率和每个成功答案的总成本。

3. TrackRL：如何判断一条 Skill 是有用、冗余还是已经有害？

原始资料： 论文。首次提交：2026-10-18。 论文列出了项目地址，但本次读取仓库内容返回 404，因此不将其标记为已验证可运行代码。

发生了什么

Skill Library 在 Agent RL 中是外部知识与行动脚手架。一个 Skill 可能从初期有用变为模型已内化的冗余指令，也可能因模型策略变化而逐渐有害。直接按“被召回时成功率高不高”做评价，容易把热门 Skill 与简单任务、共同召回的其他 Skill 混为一谈。

TrackRL 在同一任务的 GRPO Rollout 组中随机注入或不注入某个 Skill，通过组内对比识别边际收益，并跨组累积可靠性加权证据。它同时估计 Skill Utility（外部提供的因果收益） 与 Model Mastery（模型内部已掌握程度），再决定 Skill 的生成、试用、保留、退役和删除。

关键结果

作者在摘要中报告，TrackRL 在带 Skill 和不带 Skill 的评估中均优于所选基线，并观察到不同 Skill 的价值随训练过程发生迁移。摘要没有一个可以跨任务直接引用的统一百分点，因此本期不编造提升数字。

为什么重要

它解决一个常被忽略的成本项：Skill 库越大，检索、Context 注入、维护和回归风险越高。对 Self-Evolving Agent，与其不断累积“经验总结”，更合理的策略是将每条经验视为可以被实验性淘汰的对象。

可信度与局限

随机注入可以减少同题难度混淆，但如果多个 Skill 有强交互效应，单个 Skill 的平均边际贡献不一定可加。训练期间 Policy 不断变化，历史 A/B 证据也会失效；真正部署还要管控 Skill 版本、来源、权限和副作用。

最值得继续追踪

从已有 Skill 库选择 10 条常用 Skill，按固定任务组随机注入，计算“添加后净增 Task Success / 多消耗 Token”，并按版本留痕。对重复或互相矛盾的 Skill 单独验证 pairwise interaction；仅在足够样本与可恢复条件下决定退役。

4. IF-MAP：应该优先优化哪一个子 Agent？

原始资料： 论文。首次提交：2026-10-17。

发生了什么

多 Agent 系统失败时，最常被指责的 Agent 不一定是最值得花钱升级的 Agent。IF-MAP 用小幅、语义可控的 Prompt 扰动，测量端到端 Loss 的变化，再在低维 Prompt Embedding 空间拟合局部响应模型，得到改进潜力排序。这个过程是黑盒的，不需要读取模型权重或梯度。

关键结果

六个多 Agent 工作流中，按 IF-MAP 选择 Agent 进行 Prompt 优化，宏平均性能提升 3.81pp，均匀选择为 1.85pp。对于替换为更强模型，论文的提升区间为 7.62—16.42pp，优于相应均匀选择。相对“给所有 Agent 做优化”，作者报告在部分 Qwen3-8B 和 DeepSeek-V3.2 场景中分别减少 74.2% 和 35.2% 的 Token 消耗；这是所定义优化流程的成本，不代表整条业务调用成本同幅下降。

为什么重要

与 Agent Harness A/B 回归一样，IF-MAP 提醒我们：失败归因和改进收益归因不是一回事。在 Planner、Retriever、Verifier、Executor 协作系统里，瓶颈经常由交互方式决定。低成本探测可用于决定是先修 Prompt、换模型，还是更改 Agent 接口。

可信度与局限

这是局部扰动代理，不是对 Transformer 参数的严格影响函数。排序稳定性依赖扰动强度、随机种子、任务分布和被探测的 Agent 边界。如果一处错误只有在另一处也修复时才改善，逐 Agent 局部排序可能失效。

最值得继续追踪

在固定独立任务集上，把 IF-MAP 选择与“最常失败 Agent”“最贵 Agent”“随机 Agent”做同预算优化对照，比较每个工程小时或模型调用费用能提升多少最终 Task Success。

5. AGR：在生成 Semantic ID 时按需调用特征工具

原始资料： 论文 · HTML 全文。首次提交：2026-10-19；含快手搜索系统的工业实验。

发生了什么

生成式检索常将商品/内容映射为层级 Semantic ID（SID），通过自回归解码生成候选。以往行为序列、地域、时效、意图等特征，要么一口气输入模型，要么只能在固定位置拼接。AGR 让模型在已经生成的 SID 前缀上决定：是否需要某项特征、调哪个工具、该特征在第几层 SID 决策前介入。

作者通过特征适用性和沿 SID 分支的信息增益构建工具增强轨迹，再做 SID 预训练和 Tool-augmented Finetuning。这个框架连接了推荐系统的特征工程和 Agent 的 Conditional Tool Use。

关键结果

论文报告离线 Recall 相对基线最高改善 14.04%（相对变化）。线上进行了 7 天 A/A、再 7 天 A/B，试验组与对照组各占随机流量 10%；作者报告搜索相关性 +0.205%（95% CI [+0.12%, +0.28%]），Query Reformulation Rate -0.690%，Search Penetration Rate +0.060%。生产平均 Serving Latency 为 35ms。这些是作者定义的指标变化，不能擅自改成百分点或收入增幅。

为什么重要

传统推荐特征通常在召回之前一次性拼成宽输入。AGR 提示可以把特征获取变成分层决策：仅当某个 SID 分支需要消歧时才查询某种特征，从而降低无效特征 I/O 与误导性信号。

可信度与局限

公开实验主要来自同一生产系统，线上 A/B 很有价值，但还不能推断各大搜索产品均可得到同样收益。训练数据依赖预设规则且沿 Golden SID Prefix 构造；模型真实推理中的错误前缀可能触发不同工具分布。如何在错误前缀上稳定决策仍待验证。

最值得继续追踪

按 Query 类型统计特征工具调用率、实际增益、缺失特征退化、SID 错误分支恢复、特征新鲜度及 P99 服务延迟。对比静态全部特征、Rule-gated 特征和 learned AGR，固定最终召回质量后测量成本。

6. Cache2LoRA：把文档内容变成可按查询生成的低秩参数更新

原始资料： 论文。首次提交：2026-10-16。

发生了什么

长文档问答在每次回答时重复塞入 32K 文本，会让 Prefill 与 KV Cache 成本快速累积。Context-to-LoRA 思路用一个轻量参数适配器承载文档事实，但既有方法可能混淆多个来源、遗忘短事实，或回答事实正确却不遵守指定输出格式。

Cache2LoRA 使用可复用的冻结文档缓存，在 Query 到来时聚合与该问题相关的证据，再生成 LoRA 更新。可训练编码侧主要作用于 Query 与记忆 Token 后缀，使用多种答案风格监督，使事实恢复与表达控制一起训练。

关键结果

作者在 17 项任务中的宏平均 F1 为 0.663，接近完整上下文 In-context Learning 的 0.671；在 32K 文档、256 输出 Token、Batch=16 的特定设置中，解码吞吐为完整上下文基线的 5.9 倍。这是 Decode 指标，不能直接理解为端到端问答请求吞吐提升 5.9 倍。

为什么重要

它为长期记忆系统提供第三条路线：既不是每次都读原始长文本，也不是只检索静态摘要，而是用查询相关证据动态组织低秩参数。高复用文档、多用户相同知识库的场景值得探索；但文档更新、撤回和冲突证据时的参数失效问题非常关键。

可信度与局限

LoRA 构造本身有计算与部署成本。报告的 Decode 加速没有包括全部缓存构建与适配器更新；多 Query 复用程度、修改频率和吞吐批量会影响真实 TCO。参数内化后的来源引用可追溯性也弱于显式检索。

最值得继续追踪

在同一答案准确率和引用可信度下，对比 Raw-turn RAG、摘要记忆、全上下文缓存与 Cache2LoRA，评测更新一个事实后的污染持续时间、P95 延迟和每百次查询成本。

7. TAR：RLVR 提升正确率时，会不会消灭正确的推理多样性？

原始资料： 论文 · 作者代码 TAR。首次提交：2026-10-16。

发生了什么

在同一问题上，多条不同推理路径可能都得到正确答案，二值奖励无法区分它们的价值。有限样本的 On-policy RLVR 容易反复采到一条占优路径，使其他少见但有效的推理模式逐渐消失；等这些模式低于采样覆盖阈值时，普通 On-policy Rollout 很难自动找回来。

Targeted Adaptive Replay（TAR）在训练前构建一个包含多种正确解法的紧凑记忆库，训练中只在某类已知正确行为的概率被压低时有针对性地回放，而不是盲目增加所有 Replay。

关键结果

作者在两种 Qwen2.5 尺度、六项数学 Benchmark 上报告较好的“正确率—推理多样性”平衡，并减少 Base 模型已有正确解法的遗忘。论文摘要没有可统一引用的绝对提升百分点，本期不推测数字。相关代码仓库可以读取，包含训练与评估入口。

为什么重要

这与 SPOD 的 Erosion 问题有共同机制：当前 Reward 看起来一样的不同成功轨迹，未来 OOD 泛化价值可能不同。维护少数高价值推理模式，可能比追逐训练集 pass@1 的单一峰值更稳健。

可信度与局限

如何把“语义上独立的解法”与“只在表述上不同”分开，是核心评价难题。Replay 会带来额外 Memory、采样和 Off-policy 偏差；只有证明 Held-out 正确率和稳定性共同改善，才可认为优于普通 Early Stop。

最值得继续追踪

在冻结题集上测 Mode Coverage、Distinct Correct Trajectories、Base-correct Retention 与 OOD pass@1，比较 KL Regularization、Uniform Replay、TAR 与 SPOD 式成功保护策略。

8. Adaptive Top-K Rollout：RLVR 的采样支持集是否应该随训练变宽？

原始资料： 论文。首次提交：2026-10-19。

发生了什么

标准 RLVR 的 Rollout 常使用固定 Temperature 和 Top-K。论文研究一种从 Top-K=10 → K=20 → Full Support 的分阶段解码方案，让模型早期优先学习较高概率动作，后期再逐步探索长尾动作。

关键结果

在 4B 代码 RLVR 的三个实验种子中，该策略在插值的 150M Token 验证预算上，相对固定 K=10 平均高 1.80±0.42 分，但与另外独立训练的固定 K=20 强基线表现接近。作者还披露一次探索性的单次 Test Replay 得到完全相同的点估计，因此不能把验证集优势直接升级为已经证实的泛化优势。

为什么重要

Rollout 采样不仅是推理配置，它决定 RL 训练中能够观察和强化哪些行为。与其只调整 GRPO 的 Advantage 正则项，也应该研究 sampling_policy 本身是否造成样本效率差异。

可信度与局限

观察到的效应相对较小，且有单次测试反例。混合奖励组占比也没能清楚解释增益。不同 Top-K 的实际 Token 长度、有效 Reward 方差与硬件运行时间仍需更全面对照。

最值得继续追踪

统一 Attempted Token、成功 Rollout Token 和 Wall-time，比较固定 K=10/20、Full Support 与阶段性 K，并在同一个 Held-out Test Set 上使用多个 Seed 验证收益。

9. PolyGraph：可变 Speculative Width 如何避免 CUDA Graph 爆炸？

原始资料： 论文。注意：作者页面记录的最早提交为 2026-08-14，属于本期新列表中的补充材料，而不是 10 月 20 日首次成果。

发生了什么

自适应推测解码的 Batch Size $B$ 与 Draft Length $d$ 经常变化，验证宽度 $M=Bd$ 也随之变化。但 CUDA Graph 需要固定 Launch 配置。常见方式是为不同 Shape 预捕获多个图，或者统一 Pad 到最大宽度，造成编译/内存或无效计算损耗。

PolyGraph 对自定义 Triton Kernel 捕获一个最大 Grid 的图，运行时把有效 Shape 写到 GPU 上的短 Plan Buffer，越界 Tile 直接跳过；图拓扑、指针和 Launch Grid 保持不变。作者报告每步只需更新 28 字节控制数据。

关键结果

一张 H800、Qwen2.5-3B 维度的合成 Trace 中，所需图由 64 个减少到 1 个，预服务图构建时间从 3,915ms 降至 93ms；预热后的 Step P50 为 17.7ms 对 17.8ms。满 Padding Waste 时相对 MaxPad 的 P99 有 18.7% 改善，而没有浪费时两者相近。

为什么重要

从内核层面看，这是将动态问题规模与静态调度拓扑分离的实例。对 Batch 波动大的多 Agent Serving，调度系统可能因 Shape Explosion 损失吞吐；机制值得迁移到其他形状受限的自定义核。

可信度与局限

论文明确只验证合成 Trace、单 GPU 和自定义 Triton 内核，尚不是完整 vLLM/SGLang 生产流水线。不能将图构建耗时减少直接报告为 TTFT 或总吞吐的 42 倍改善。

最值得继续追踪

接入真实 Agent 请求分布，对比预捕获多图、MaxPad、PolyGraph 的 P50/P99 TPOT、显存、Capture Warm-up、显式图复用率和不同请求长度下的浪费。

SPOD：Beyond the Teacher

前 8 分钟： 读 Distillation Overshoot 的训练曲线与 Repair/Erosion 的决策级定义，检查老师更强是否足以保证 KD 单调收益。

中间 12 分钟： 对照作者实现找到完整动作概率比较、成功轨迹门控、Forward KL 和概率下界；特别看 $g$ 何时为 1。不要把完整动作概率与单 Token 概率混淆。

最后 10 分钟： 对照两组师生、三个 Benchmark 的 Final vs Best Checkpoint 表格，推导对你自己的 Tool-Agent RL 要监控什么：不是只看训练 Reward，还要看“成功行为被 Teacher 反向压制”的比例与 OOD 成功率。

读完应能回答：Teacher 的行为分布被当作训练目标时，什么条件下会系统性地破坏学生已经学会的有效策略？

今日可立即实践的一件事

成功轨迹 Teacher–Student 冲突审计（无需先训练）

从已有 Tool-Agent 或 Coding Agent Trace 中取 50—100 个带终局 Verifier 的任务。每题保留成功/失败两组轨迹，以及若干关键 Action State。对同一状态，用冻结教师评价学生实际动作的完整序列概率，若没有教师 Logprob 权限，则先用独立动作偏好判定器作为近似，明确不等价于 SPOD 原始概率门控。

按以下四格统计：成功+教师反对、成功+教师赞同、失败+教师反对、失败+教师赞同。记录各格的工具错误、重试次数、Token 与最终 Task Success，再观察固定 Teacher 模仿损失是否与“成功+反对”动作占比冲突。

可先把日志整理为 CSV 并用 Python 分组计数。只有当冲突率、成功率退化与教师评分存在一致关系时，再计划 SPOD 小规模训练。 一张 RTX 4080 16GB 足够做数据审计和小模型动作打分，但原论文双模型在线训练配方并非单卡直接可复现。

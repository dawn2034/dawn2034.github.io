今日主线： Meta-Reasoning Control · Writable Context · Reward-Free Self-Search · Adaptive Cache Compression · Recurrent-State Quantization · Unified Recommendation Ranking

恢复说明： 本文由当日原会话中保存的完整正文恢复，原有检索审计和公告批次统计按历史记录保留；原始检索日志未随会话导出，本次没有重新执行或补造当日 X.com 检索。内部引用标记已移除，论文与项目来源已补为标准原始链接。

arXiv 最新常规公告批次为 2026 年 9 月 30 日：cs.AI 506 条、cs.CL 228 条、cs.LG 465 条、cs.IR 29 条。分类之间存在大量交叉收录，不能直接相加。今天更值得连起来看的变化，是 Agent 系统开始把“控制执行”本身当作推理对象：一条路线把高层控制从 Worker 推理中显式拆出来，另一条路线干脆把 Context 变成模型可写的运行时状态。与此同时，自我改进开始尝试减少每轮昂贵下游评估，推理系统则继续把 KV / recurrent state 从统一静态配置变成按上下文与误差生命周期自适应分配的资源。推荐系统侧，工业模型仍在推进一个很现实的统一化：共享用户序列状态，同时保留候选侧高阶特征交互。

今日核心判断

  1. 长程 Agent 的下一条 Test-time Scaling 轴可能是“控制计算”，而不只是更多 Worker Rollout。 Thinking Before Thinking 将 Controller 与 Worker 分开，Controller 用紧凑状态和 Artifact DAG 决定复用哪段工作、是否分叉、何时停止。ProgramBench 上 GPT-5.5 + Meta-reasoning 达到 71.5%，高于 Codex 58.0% 和论文中的 Direct Control 63.7%；其他任务上对 Direct Control 的平均增益为 3.6–4.2 points。需要注意，同样的“模型调用预算”并不等价于相同 Token、FLOPs 或 Wall-clock 成本。

  2. Context Management 正从 Harness Policy 变成模型可以直接学习的行为。 Context Language Models（CLM）把 Context 视为可写文件，让模型自行保留、修改和删除上下文。现有模型 Zero-shot 使用这一机制，在 BrowseComp-Plus 上准确率 +11.4%、FLOPs -21.5%；进一步做在线 RL 后，Qwen3.5-9B 在同任务上表现 +47.6%、FLOPs -12%。这类能力很强，但可写 Context 同时引入状态完整性、撤销、权限和审计问题。

  3. Agent Self-Improvement 未必需要每次都重新跑昂贵的下游评估。 SelfSearch 使用历史自我修改记录中的 reasoning、tool actions 和 outcomes 来指导下一轮修改，搜索阶段不使用新的下游 Reward。六个 model–benchmark 设置的 population mean 均优于初始 Agent，Terminal-Bench 2.1 单个 Agent 最高 +11.2pp；SWE-bench Multilingual +5.0pp，同时在共同解决任务上的执行成本下降 38.5%。但“reward-free”只描述搜索阶段，它依然利用过去 modification episode 的结果信息，不能解读成完全无反馈学习。

  4. KV Cache 压缩正在从统一手工规则转向按 Context 学习配置。 KV-Kaizen 用一个 pre-prefill selector 为每层联合选择跨层共享、低比特精度和低秩截断，在长上下文 14B 模型上最高达到 32× 更小的 decode-time cache 且保持准确率；7B 以上模型达到 4× cache reduction 时没有观测到准确率下降。它的重要意义在于：Cache Compression 可以成为 Context-dependent Policy，而不必所有 Layer 共用一种压缩强度。

  5. Linear Attention 没有消灭推理态内存，只是把瓶颈从 KV Cache 换成了 persistent recurrent state。 STEPQuant 发现 Delta-rule state 的量化误差既有时间寿命，也有空间位置差异，因此按 memory lifetime 和 key-row / value-column 影响分配精度。Qwen3.8-27B 与 Kimi-Linear-48B-A3B-Instruct 上，6-bit nominal budget 接近 FP32-state accuracy；集成 SGLang 后 recurrent-state 压缩超过 5×、总 Serving Memory 最多降低 68.7%。

  6. 工业推荐的“统一模型”正在收敛到共享用户侧状态、保留候选侧异质计算。 TikTok 电商 HELIX 将 Sequence Retrieval 与 Feature Interaction 交错，同时保持从可复用 Sequence State 到 Candidate-conditioned Mix-token 的单向信息流，使用户侧计算可摊销、候选侧交互仍能独立扩展。论文报告线上电商视频 GMV / user 约 +6%。这是建设方的一体化系统结果，不能把收益单独归因给某一层结构。

1. Thinking Before Thinking：把“接下来该做什么”本身变成推理任务

论文原文

发生了什么

长程 Agent 的难点并不只在单步 Reasoning。每完成一个中间结果，系统都会出现新的控制问题：继续沿当前方向、复用旧 Artifact、另开分支、请求另一个 Worker，还是停止。

这项工作引入 Agentic Meta-Reasoning。Worker 负责真正的任务级计算，Controller 则维护紧凑的运行状态和持久 Artifact Memory，以 Assess → Propose → Evaluate → Dispatch 的方式决定下一步，把“做任务”和“控制任务执行”分成两个层级。

关键结果

设置结果
ProgramBench · GPT-5.5 + Meta-reasoning71.5%
ProgramBench · Codex58.0%
ProgramBench · Direct Control63.7%
ProgramBench · Opus 4.8 + Meta-reasoning67.2%
ProgramBench · Claude Code65.5%
其他 Benchmark 对 Direct Control+3.6～+4.2 points

论文还观察到，Direct Control 在部分 Budget 区间开始平台化后，Meta-reasoning 仍能继续利用额外预算；Artifact Graph 中也出现了更多既有工作的复用。

为什么重要

Test-time Scaling 常被近似成“多采几条 CoT / Rollout”。这篇工作把另一类计算显式化：

\[C_{\mathrm{total}} = C_{\mathrm{task}} + C_{\mathrm{control}}.\]

当 Agent Run 变成数十甚至数百步，决定“哪份已有工作值得继续投入”本身就可能拥有很高的边际价值。Research Agent、Coding Agent、复杂搜索／购物 Agent 都会遇到这个问题。

可信度与局限

论文对齐的是 nominal model-call budget，没有证明不同 Harness 的 Token、延迟、FLOPs 与实际成本完全相同。Controller 的额外调用在小预算下甚至会拖累结果，这说明 Control Compute 存在明确的 break-even point。

此外，compact state、artifact reuse、branching 和 explicit controller 是组合式设计，目前不能仅凭 headline 数字隔离哪一项贡献最大。

最值得继续追踪

真正值得追的不是再刷一个 Benchmark，而是 control-compute scaling law：随着任务 Horizon、Worker 数量和 Artifact 数量增加，Controller 应占总推理预算多少？它的边际收益又在什么时候低于多增加一个 Worker Rollout？

2. Context Language Models：Context 从“输入字符串”变成可写运行时状态

论文原文

发生了什么

Context Language Models 将上下文实现成一个文件，并允许模型自行更新：保留、删除、重写和重组信息。多 Agent 场景中，不同 Agent 的 Context 也可以自然表示成不同文件。

这一步把 Context Management 从外部 Harness 的固定算法，变成模型可 Zero-shot 使用、可通过自然语言 Skill 优化、甚至可通过 RL 学习的行为。

关键结果

设置报告结果
BrowseComp-Plus · Zero-shot CLMAccuracy +11.4%，FLOPs -21.5%
12-hour EdgeBenchScore +5%，FLOPs -59%
24-hour multi-repo agent swarm同计算下 Improvement +65%
Context-management skill optimizationheld-out accuracy 最高 +35.9 points
Qwen3.5-9B online RL · BrowseComp-PlusPerformance +47.6%，FLOPs -12%
Suffix Cache Reuseserver compute -35%

为什么重要

过去几周的长程 Agent 工作不断在回答同一个问题：旧信息究竟应该被 Summary、删除、写进长期 Memory、压成 Latent State，还是留在 KV 中？CLM 更进一步，把“当前 Context 应该长什么样”变成模型自己的决策变量。

如果这条路线成立，未来 Agent Runtime 更像：

read context → edit context → inspect artifacts → act

而非 Harness 每轮重新构造一段不可修改的巨大 Prompt。

可信度与局限

“模型可以自由更新 Context”也意味着它可以误删关键约束、把推断写成事实、让已经撤销的信息继续存在。论文证明了可学习 Context Policy 的潜力，没有自动解决权限、Provenance、Rollback 和审计。

同时，Zero-shot CLM、Skill Optimization、Online RL 与 Suffix Cache Reuse 是不同层的结果，不能把这些数字简单累加成“CLM 总提升”。

最值得继续追踪

真正决定能否生产化的是 state governance：Context Edit 有没有 diff、scope、provenance、immutable fields、rollback；某条信息为什么被删、何时被改，能否被外部系统可靠追踪。

3. SelfSearch：用历史自我修改经验替代部分实时 Reward

论文原文

发生了什么

常见 Self-improving Agent 搜索是一个昂贵循环：

修改 Harness → 跑完整任务 → 看 Reward → 再修改

SelfSearch 保存之前 self-modification episode 的 reasoning、tool actions 和 outcomes，后续直接从这些记录中学习如何修改自己，搜索阶段不再为每个候选 Patch 调用新的下游 Reward。

关键结果

指标结果
六个 model–benchmark 设置population mean 全部高于初始 Agent
Terminal-Bench 2.1单个 Agent 最高 +11.2pp
SWE-bench Multilingual+5.0pp
共同解决任务的执行成本-38.5%
Terminal-Bench 2.1 · DeepSeek V4 Flash82.0%
对应 Search Cost$4.03

论文称，在其采用的公开九 Harness 比较设置中，82.0% 与最高分 Harness Codex 持平。

为什么重要

历史修改记录本身就是一种经验数据：某个 Harness Patch、Tool Policy、Context Policy 曾经产生什么后果。如果它能跨任务复用，下游 Evaluation 可以更像定期校准，而无需成为每个搜索节点的固定成本。

这会直接影响 Self-improvement 的扩展速度，因为完整 Coding / Browser / Research Evaluation 往往比生成一个候选 Patch 贵得多。

可信度与局限

这里最容易误读的是 Reward-Free。它只意味着搜索阶段没有新的 downstream reward query；历史记录里仍然包含过去修改尝试的 outcome，所以它并非“完全没有反馈的自我进化”。

此外，历史经验来自特定 Model、Harness 与 Benchmark。Model Upgrade、Tool Schema 或任务分布变化后，旧 self-improvement data 可能迅速过时。论文中的 $4.03 同样依赖具体调用价格与设置，不能外推成通用 Search Cost。

最值得继续追踪

看 off-policy self-improvement data reuse：旧 Harness 修改记录跨模型版本还能保留多少价值？什么样的 drift signal 应触发重新跑真实 downstream evaluation？

4. KV-Kaizen：Cache Compression 也应该按 Context 分配预算

论文原文

发生了什么

传统 KV 压缩常统一做一种操作：降 Precision、跨层共享、低秩压缩，或者不可逆 Evict Token。

KV-Kaizen 在 Prefill 前运行一次 Selector，根据当前 Context 为每一层联合选择三个压缩轴：Depth（跨层共享）、Precision（降低缓存位宽）和 Rank（截断低秩 latent cache representation）。

关键结果

论文称学习式 Selector 在 Instruction Following 与 Reasoning 任务上进入 accuracy–cache-size Pareto Frontier。长上下文 14B 模型上，与 Eviction 组合后最高达到 32× 更小的 decode-time cache 且保持准确率；从 7B 参数规模开始，4× Cache Reduction 没有观测到准确率下降。

另一个有实际部署意义的结果是：在相同 Cache Size 下，被压缩的较大模型可以比未压缩的小模型更准确。

为什么重要

这相当于把 Cache 从静态 Tensor Layout 提升成推理策略：

\[\text{cache config} = \pi(\text{context},\text{layer},B_{\text{memory}}).\]

Agent Context 中代码、网页、日志、长 Tool Result 的信息密度高度不稳定，一种全局固定压缩率很难始终处在最佳点。

可信度与局限

32× 是特定 14B 模型、长上下文任务和组合配置下的最佳结果，不能理解为任意 14B 都能安全压缩 32×。Selector 也存在训练成本、模型绑定与运行开销；换 Backbone 或 Context Distribution 后是否要重新训练，目前需要更多工程证据。

最值得继续追踪

下一步很可能是 Compression × Eviction × Prefix Reuse × KV Tiering 联合优化，因为这些模块最终竞争的是同一套 HBM / Host / SSD 预算。

5. STEPQuant：Linear Attention 的 recurrent state 也要按“误差寿命”分配精度

论文原文

STEPQuant GitHub

发生了什么

Linear Attention 用固定 recurrent state 替代随 Context 增长的 KV Cache，但高并发 Serving 时，每个请求依然需要保留自己的状态，而且状态会被持续更新，量化误差可以跨很多 Decode Step 传播。

STEPQuant 发现误差影响有两个维度：时间上，长寿命误差更危险；空间上，不同 Key Row / Value Column 对最终输出的影响差异明显。方法因此根据 error magnitude 与 memory lifetime 分配精度，并联合拟合 row / column scale。

关键结果

设置结果
nominal 6-bitaccuracy 接近 FP32-state
4-bit STEPQuant优于 uniform INT8
recurrent-state compression>5×
total serving memory最高 -68.7%

实验覆盖 Qwen3.8-27B 和 Kimi-Linear-48B-A3B-Instruct，并集成 SGLang 的优化 GPU Kernel。

为什么重要

“Linear Attention 没有 KV Cache”很容易被错误理解成“状态内存问题消失”。事实上，瓶颈只是从 token-growing cache 变成了 persistent state；并发 Session 多时，固定状态照样会成为显存成本。

更一般的启示是：

持久状态中的误差重要性，取决于它会活多久，以及它位于多么关键的更新方向。

可信度与局限

它针对 Delta-rule recurrent state，不等于标准 Transformer KV Quantization；6-bit、4-bit 的收益依赖模型状态分布与专门 Kernel，也不能直接使用普通 INT Quant Runtime 复现。

最值得继续追踪

Linear Attention 进入更多大模型后，Recurrent-state Quantization 是否会成为 vLLM / SGLang 的标准接口，而不是每种架构各写一套专用 Kernel。

6. HELIX：推荐统一化仍需要“用户侧可复用、候选侧高交互”的非对称结构

论文原文

发生了什么

工业 Ranking Model 同时依赖两种不同计算：长用户序列建模，以及 User / Item / Context / Cross Feature 的候选级交互。单独扩大其中任何一轴，作者认为都会逐渐碰到 Scaling Ceiling。

HELIX 将 Sequence Retrieval 与 Feature Interaction 交错，但限制信息流只从可复用的 Sequence State 流向 Candidate-conditioned Mix-token。因此用户历史可以先算一次、多候选共享，而候选相关的昂贵交互仍保留独立扩展能力。

关键结果

TikTok 团队报告 HELIX 在电商推荐生产系统中持续改善 CTR AUC、CVR AUC 等离线指标；线上 A/B 中，e-commerce video GMV per user 约 +6%。

为什么重要

它给“Unified Recommendation Model”划出了一个很现实的边界：

共享 candidate-independent user state，保留 candidate-dependent interaction。

这比把所有长序列、候选与 Cross Feature 无差别塞进一套巨型 Transformer 更容易兼顾吞吐、Freshness 和排序精度。

可信度与局限

这是 TikTok 团队自己的 Technical Report 与线上 A/B，外部无法独立复算。约 6% GMV 属于完整模型与 Serving 设计的最终结果，不能归因给某一个 Mix-token 或单向信息流结构。

用户状态复用也会带来 Cache Staleness：Session Interest 快速变化时，用户侧状态刷新频率可能重新成为系统瓶颈。

最值得继续追踪

最值得看的是 asymmetric scaling law：固定延迟预算下，新增计算投到 User-sequence Side 还是 Candidate-interaction Side 的边际收益更高，以及最优比例是否随候选规模与业务目标变化。

今日值得收藏的代码 / 学习资源

Learning Meta-Skills for Agent Harness Design 很适合和 Harness Learning、SelfSearch 放在一起读。Builder 从 Target 执行反馈中学习“什么时候需要支持、应准备哪些资源”的 Meta-Skill，再在未见任务上冻结 Skill Bank 构造 Harness。Harness-Bench 与 NewtonBench 上，相对 no-skill construction 宏平均 +8.95pp，相对把同一 Skill Bank 直接交给 Target +12.02 points。它说明“经验”可以写成环境构造知识，而不一定只能写进参数。

LongHarness Bench 专门把长 Context Harness 的效率也纳入评测。任务需要词法检索、语义匹配与跨局部／全局证据的策略性处理，多模型 × 四 Harness 中最好 Macro-average 仍只有 68%；同一个底模换 Harness 后，效率可以明显不同。这个 Benchmark 很适合检验“更聪明的 Context Management”究竟是在提高质量，还是只是在多烧推理预算。
LongHarness Bench

EngiWorld 把 Computer-use Agent 拉进 CAD、CAE、CAM、BIM、EDA 与 3D Visualization 的完整工程闭环。它有 1,301 个专家任务、26 个专业软件平台，并用 Artifact-centric Verifier 检查几何、物理与规则约束。七个 Frontier Model 中最强 EngiScore 仅 44.3，多软件尝试成功率只有 3.6%。这比“会不会点击 GUI”更接近真实工业自动化门槛。
EngiWorld

Mira 针对无法把全部 Expert 常驻 GPU 的 MoE 推理，用轻量 Predictor 提前预测未来 Expert，并配合 HOT + STAGE GPU Cache 与压缩传输。论文报告在 memory-constrained GPU 设置下，平均吞吐相对比较基线 5.71×、TTFT 11.71×。这些是特定受限显存环境下的系统数字，不能作为普通 MoE Serving 的普适加速倍数。
Mira 论文

LeapQuant 和 STEPQuant 同日出现，采用 training-free 的 per-window quantization 与高精度 Compensator Tokens，作者报告多硬件下 Quant Kernel 2.05–3.70×、端到端最高 1.47×。两篇一起看最有价值：Linear Attention 的量化问题已经从“状态能否低比特”推进到“误差怎样跨时间累积”。

最接近入选 3：Out-of-band Agent Safety / OpenShell

今日最值得花 30 分钟阅读的一项

首选 Thinking Before Thinking。

论文原文

建议重点看 Controller 的 compact state 与 artifact memory 到底保存什么；Direct Control 与 Meta-reasoning 怎样对齐调用 Budget；为什么小预算时 Controller Overhead 会反而有害；以及 Artifact Graph 中“已经生成正确中间解”和“最终选中正确解”为什么并不是同一个问题。

最值得带走的判断是：

当 Agent Run 足够长时，边际计算最有价值的去向未必是再做一次任务推理，而可能是判断哪一份已有工作值得继续、复用、分叉或放弃。

这比机械地固定多采 N 条 Rollout 更有一般性。

今日可立即实践的一件事

给现有 Agent 做一次 Control-Compute Budget Sweep。

从 30–100 个真正的长程任务中，固定同一个底模、Tool 和总模型调用上限，比较 Direct Harness 与一个简单 Meta-controller Harness，并至少扫 8 / 16 / 32 次模型调用三个 Budget 点。Controller 的调用必须计入总预算，不能额外赠送。

建议同时记录 Task Success、Input / Output Tokens、Tool Calls、Wall-clock、Artifact Reuse、重复工作率，以及“已经产生正确中间结果但最终没有使用”的比例。真正要看的不是最高 Budget 谁分数高，而是：

\[Q(B) \quad\text{以及}\quad \frac{\Delta Q}{\Delta C}.\]

如果 Direct Agent 从 16→32 次调用已经明显平台化，而 Meta-control 仍能把额外预算稳定转成质量收益，瓶颈就开始从 Worker Compute 转向 Control Compute。反过来，如果任务只有几步、Artifact 很少，Controller 只是增加 Token 和延迟，这类架构就没有必要。

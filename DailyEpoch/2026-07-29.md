# 每日 AI 技术简报｜2026-07-29

arXiv **7 月 28 日批次**仅 cs.AI 就有 406 项。本期没有按关键词机械凑数，重点筛选 Agent 运行时纠错、RAG 工作流搜索、低精度 RL、端侧 MoE 推理和工业推荐系统。

## 今日核心判断

今天几项工作指向同一趋势：**模型能力提升之后，主要瓶颈越来越多地落在运行时控制与系统组织上。**Agent 需要可证伪的计划；RAG 需要搜索组件组合并复用中间产物；低精度 RL 需要约束训练—推理策略偏差；端侧 MoE 需要把专家加载纳入推测解码目标；推荐系统则开始用多个异构专家共同描述用户。

## 1. FCPAgent：Agent 的计划应该明确写出“什么证据能证明我错了”

### 发生了什么

FCPAgent 将每个计划步骤表示为 **Falsifiable Commitment Unit**，包含：

- 当前子目标；
- 可复用 Skill；
- 确认计划仍有效的证据；
- 推翻当前计划的证据；
- 置信度。

Agent 在动作执行前和执行后检查这些证据。一旦出现矛盾，系统判断问题位于动作执行、Skill 选择还是整体规划，只修改最小必要范围，而非笼统地“反思并重试”。

在 WebArena 上，FCPAgent 的平均成功率为 **65.3%**，最强对比方法 ColorBrowserAgent 为 57.4%，相对提升 13.8%；在 WebChoreArena 零样本迁移中相对提升 9.6%。

### 为什么重要

当前很多 Agent 计划只描述“下一步要做什么”，没有描述：

> 在什么条件下，这一步已经不值得继续相信？

这导致 Agent 进入错误页面或选错 Skill 后，仍能连续执行大量局部合理但全局无效的动作。FCPAgent 的核心价值在于把计划从自然语言待办事项变成了**运行时可测试的假设**。

### 可信度与局限

**可信度：中等。**论文给出了组件消融、跨基准迁移和功能性成功验证，但仍是单篇预印本。所有方法使用 Qwen3.5-397B-A17B，运行成本较高；其混合检查器还依赖 NLI、视觉匹配和 LLM verifier，额外 token、延迟和误报成本尚未被充分量化。Skill 与失败记忆也可能引入此前简报讨论过的能力回归。

### 最值得追踪

重点看 falsifier 的误报率、错误归因到不同修复层级的准确率，以及同一机制能否迁移到代码 Agent、MCP 工作流和长时间研究 Agent。

## 2. Agent-UCT：RAG 不应被当作固定框架，而应被视为可搜索的组件空间

### 发生了什么

Agent-UCT 将 LongRAG、LightRAG 和 Self-RAG 的组件拆入一个五维配置空间，再用带成本感知的 UCT 搜索组合。系统维护前缀复用图：两个候选工作流共享相同前半段时，中间索引、检索结果和生成产物无需重新计算。

其配套 WTB 提供确定性重放、内容寻址缓存和事务一致性。论文报告：

- 前缀复用将逻辑搜索成本降低 73.6%；
- 采样评估相对完整候选池获得 4.2 倍墙钟加速；
- 模型调用从约 22.8 万次降至 2.9 万次；
- token 消耗从约 6.33 亿降至 1.10 亿。

### 为什么重要

大量 RAG 对比实验实际上在比较几个整套品牌化框架，却没有回答：

- 哪种 query transformation 有效；
- 哪种索引结构有效；
- retrieval、reranking 和 generation 各贡献多少；
- 中间产物能否跨实验复用。

Agent-UCT 的更大价值可能是 **RAGSpace + 可缓存工作流测试台**，而非 UCT 公式本身。

### 可信度与局限

**可信度：中等偏高，但结论范围有限。**实验仅覆盖 HotpotQA、UltraDomain 和一个 GPT-5.4-nano 主干模型。Agent-UCT 在 HotpotQA 上优于 LongRAG，但差异的统计显著性不足（论文报告 $p=0.27$）；优势主要来自 UltraDomain 和跨数据集综合结果。搜索空间也只包含作者预先选定的组件。

### 最值得追踪

需要验证跨模型搜索结果是否可迁移，以及“生成模块解释了最多性能方差”这一结论在企业 RAG、代码 RAG 和多步搜索中是否仍成立。

## 3. ACRL：FP8 rollout 的问题不只是量化误差，而是行为策略发生了漂移

### 发生了什么

LLM 强化学习通常使用一套高精度训练引擎计算梯度，再用另一套低精度推理引擎产生 rollout。即使两者使用相同权重，kernel、并行方式和量化误差也会导致 token 概率不一致。

ACRL 动态控制训练策略和 rollout 策略之间的差异，防止策略更新基于已经严重失真的行为概率。

在实验中：

- PPO + ACRL 使用 FP8 rollout 达到 87.34%，与 BF16 基线相同；
- DAPO 的普通 FP8 训练失败；
- 加入 ACRL 后达到 88.63%，略高于 BF16 的 87.95%；
- 在 Qwen3-32B dense 和 Qwen3-30B-A3B MoE 上，MXFP8 训练也保持稳定。

### 为什么重要

普通量化推理只需保证最终输出质量基本不变。RL rollout 还需要用 token log-probability 计算 importance ratio、KL 或 clipping，因此微小数值偏差可能沿长轨迹累积成系统性梯度偏差。

这意味着低精度 RL 的正确优化对象是：

$$
\text{量化格式}
+\text{训练引擎}
+\text{推理引擎}
+\text{策略差异控制}
$$

### 可信度与局限

**可信度：中等。**失败机制和多规模结果比较完整，但尚缺独立复现。实验集中于特定模型、FP8/MXFP8 和训练栈，不能直接外推到 NVFP4、不同 speculative rollout 引擎或超长 Agent 轨迹。

ACRL 略微超过 BF16 也不能证明低精度天然具有更好的学习效果；差异可能来自熵控制、探索变化或实验噪声。

### 最值得追踪

训练端与推理端的 log-prob parity 测试、长轨迹中的误差累积，以及单位 GPU 小时的真实收益，而非只看最终准确率。

## 4. DraftExpert：端侧 MoE 的推测解码必须考虑“多加载了多少专家”

### 发生了什么

端侧 MoE 通常只能把少数专家保留在 GPU 或 NPU，其余专家需要从 CPU 内存或 Flash 动态加载。传统 speculative decoding 增加草稿专家数量能够提高接受率，却可能触发更多专家加载；验证多个 token 时，目标模型还需要加载这些 token 所涉及专家的并集。

DraftExpert 为每层训练一个常驻加速器的轻量草稿专家，并联合蒸馏 residual、token/logit 和路由一致性。运行时根据置信度及预计专家扩张决定何时停止草稿，同时提前预取目标专家。

在 DeepSeek-V2-Lite 和 Moonlight-16B-A3B 上，论文报告：

- 平均解码吞吐提升 1.45 倍；
- 草稿接受率达到 84%—87%；
- 专家预取命中率达到 86%—88%；
- 移动端部分配置达到 1.52—1.61 倍加速。

### 为什么重要

在专家 offload 场景中，更合理的指标不再只是：

$$
\text{每次验证接受多少 Token}
$$

而是：

$$
\frac{\text{接受的Token数}}{\text{新增专家加载量与传输成本}}
$$

这类系统约束可能决定大型稀疏模型能否真正进入手机、PC 和边缘设备。

### 可信度与局限

**可信度：中低。**论文目前只有一位作者，实验仅覆盖两个 MoE、两条 offload 路径和单用户解码；本轮也未找到公开代码或独立复现。最终 token 仍由目标模型精确验证，因此理论上不改变输出分布，但加速幅度高度依赖硬件带宽、专家路由局部性和模型结构。

### 最值得追踪

连续批处理、P99 延迟、能耗，以及草稿专家训练成本是否会抵消端侧部署收益。

## 5. Mosaic：Meta 不再押注一个“万能用户模型”

### 发生了什么

Meta 的 Mosaic 将用户表示拆成四类专业模型：

1. 记忆型模型，捕获细粒度用户偏好；
2. Dense-heavy 模型，建模聚合特征的非线性交互；
3. HSTU + MoE 序列模型，捕获行为时间动态；
4. CoTrain 模型，直接接收下游排序任务梯度。

不同专家可分别使用 CPU/GPU、在线/离线推理。系统还通过关系挖掘和冗余损失，避免新增 embedding 反复学习已有信息；CoEval 和 User Tower Zero-Out 将 embedding 迭代效率提升 3—5 倍。

三个线上场景的核心指标分别提升 **0.10%、0.15% 和 0.28%**。序列长度从 512 扩展到 2048 时，离线 NE 改善 0.45%，但 QPS 下降 33%，体现了长序列用户建模的明确成本边界。

### 为什么重要

一个统一用户基础模型会迫使所有偏好信号共享同一架构、更新频率和 serving 路径。Mosaic 的思路更接近：

$$
\text{用户表示}
=
\text{多个不同归纳偏置的专业视角}
$$

这对跨召回、精排、内容安全和创作推荐共享用户表示尤其有价值。

### 可信度与局限

**可信度：较高的工业证据，外部可复现性低。**论文已被 RecSys 2026 接收，包含真实线上 A/B；但场景和指标被匿名化，没有披露置信区间、实验周期和长期留存影响。0.10%—0.28% 是现实工业增益，不能被包装成模型范式已经被充分证明。

### 最值得追踪

各专业 embedding 对不同用户群的边际贡献、离线 embedding 的时效性，以及专家数量增加后冗余和维护成本是否失控。

### 推荐系统补充观察

YouTube Music 的新内容实验显示，简单的 serving 层新歌加权会被后续训练和其他排序组件逐渐抵消；去流行度偏置能增加长尾艺术家多样性，却可能伤害新歌曝光；基于不确定性的探索对新歌提升最大，但会降低艺术家多样性。**新鲜度、长尾和多样性是不同目标，无法靠一个统一 boost 同时解决。**

## 值得收藏的评测协议：预算感知 Active RAG

《When Should Active RAG Retrieve?》指出，两个系统都声称使用“50% 检索预算”，实际在测试集上的检索比例可能不同。只比较最终准确率，可能只是奖励了检索更频繁的系统。

论文建议至少报告：

- 固定 Top-K 预算下的 utility frontier；
- 可部署阈值的实际检索比例；
- 阈值跨数据集的预算偏差；
- 检索导致答案变差的比例；
- router、检索、额外 prompt 和生成的完整成本。

实验中，简单不确定性分数或检索相关性分数经常能追平复杂学习型 router。这个协议很适合直接用于企业 RAG 和 Deep Research Agent 的离线评测。

# 今日最值得花 30 分钟阅读的一项

## Falsifiable Commitment Planning for Self-Correcting Web Agents

建议把注意力放在三个问题上：

- FCU 如何分别定义确认信息和反证信息；
- 如何把错误归因到 execution、skill 或 planning；
- 局部修复为什么可能优于整条轨迹重新规划。

最值得借鉴的并非特定 Browser Agent 实现，而是一个通用原则：

> 每个长期执行计划，都应该同时说明“如何知道自己正在取得进展”和“什么现象意味着当前假设已经失效”。

# 今日可立即实践的一件事

对现有 Agent 的 30—50 条失败轨迹做一次 **可证伪计划重放实验**。

为每个关键步骤增加以下结构：

```text
subgoal
precondition_evidence
progress_evidence
completion_evidence
execution_falsifier
skill_falsifier
planning_falsifier
repair_action
```

使用完全相同的模型和工具，比较三组：

1. 原有 Agent；
2. 只在动作执行后检查结果；
3. 动作前后都检查，并按 execution／skill／planning 分层修复。

记录任务成功率、发现偏航所需步数、误报率、重做范围、额外 token、延迟，以及原本成功任务的回归率。

最关键的指标不是检查器触发了多少次，而是：

$$
\frac{\text{提前阻止的无效步骤}}{\text{额外检查成本}+\text{误报造成的损失}}
$$

若这个比值不稳定，增加更多反思和 verifier 只会让 Agent 更慢、更复杂。

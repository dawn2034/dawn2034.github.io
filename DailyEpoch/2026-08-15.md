# 每日 AI 技术简报｜2026-08-15

截至 8 月 15 日早晨，arXiv 最新公开批次仍是 **2026 年 8 月 14 日**：cs.CL 当日 101 条、cs.AI 204 条、cs.IR 19 条；三类存在大量交叉收录，不能直接相加。今天真正值得连起来看的主线不是“又出了几个更强模型”，而是 **Agent 如何把经验变成持久能力，以及这种持久化同时带来的收益与新攻击面**：一边是 DIVE、RippleMem、QCR 在研究如何让冻结模型通过 Skill / Memory 持续进步，另一边 Skill Misevolution 直接证明——一次不安全的成功，也可能被蒸馏成跨任务、跨会话复用的危险策略。

## 今日核心判断

- **Self-evolving Agent 的安全边界已经从“当前回答是否安全”扩展到“什么经验允许写入、什么 Skill 允许再次取出”。**只审核当前一次输出不够，因为持久状态会把局部错误放大成未来策略。
- **Agent Memory 的瓶颈正在拆成两个问题：先找对，再用对。**RippleMem解决“相关证据分散、一次检索拿不全”，QCR则解决“历史轨迹找到了，但其中实体、约束和环境状态已经变化”。
- **On-policy distillation 不应默认所有 response token 训练价值相同。**CROP 用“语义条件改变时敏感、纯表面改写时不敏感”来筛选 token，提供了一种比纯 entropy / disagreement 更贴近任务语义的选择信号。
- **生成式推荐的公平性问题可能藏在 Semantic ID token 本身。**如果高频 token 被系统性过预测，item exposure bias 会在自回归解码层层累积，而不是只存在于最终 item popularity 上。
- **RAG 防投毒目前仍是明显 trade-off，而不是免费午餐。**RAGSieve 显著降低攻击成功率，但论文同时报告了较大的 clean-retrieval 质量损失；安全收益必须和正常检索效用一起看。

## 1. Skill Misevolution：一次“不安全但成功”的轨迹，会变成未来 Agent 的持久策略

**论文：** [Practice Makes Unsafe: Skill Misevolution in Self-Improving LLM Agents](https://arxiv.org/abs/2608.12851)  
**代码：** [henrymao2004/misevolve](https://github.com/henrymao2004/misevolve)

这篇论文提出一个非常具体的新失败模式：self-improving Agent 会把成功 trajectory 蒸馏成可复用 Skill；如果那次成功本身包含了危险操作，系统可能把它当成“有效经验”写入持久状态。触发它的恶意输入之后即使消失，Skill 仍可能在后续正常任务、甚至新会话中重新被检索和执行。

可以把问题写成：

$$
S_{t+1}=U(S_t,\tau_t)
$$

其中 $S_t$ 是当前 Skill Store，$\tau_t$ 是本轮执行轨迹。传统优化只关心 $\tau_t$ 是否完成任务；但对持久化 Agent，真正的问题变成：**成功是否足以成为写入条件？**答案显然是否定的。

作者构建了 SkillMisevo-Gym / Bench。在 25 个 agent-method 配置中，21 个带 Skill Evolution 的配置全部产生过不安全 artifact，其中 15 个进一步导致 fresh-session harm；只加入 3 个恶意任务，carryover attack success rate 就从 16.0% 升到 35.3%。作者提出的 SafeEvolve 同时治理写入与复用，报告 unsafe retrieval 和 fresh-session harm 分别下降 26.7 与 17.3 个百分点，而平均 benign utility 仅变化 0.4 个百分点。

### 为什么重要

这把 Agent 安全从“推理时 guardrail”推进到了 **state-update security**。一个真正会学习的 Agent 至少需要两道门：

```text
trajectory
   ↓
[WRITE GATE]  是否允许蒸馏并写入 Skill Store？
   ↓
persistent skill
   ↓
[REUSE GATE]  当前任务下是否允许检索并执行？
   ↓
action
```

如果只有执行前 safety check，而 Skill Store 可以无审计地积累经验，攻击者可以把一次性的 prompt injection 变成长期供应链污染。

### 可信度与局限

这是新 benchmark 与新 threat model，数字不能直接外推成真实生产 Agent 的攻击概率。它假设攻击者能够提交有限恶意任务但不能直接改 Skill Store，风险大小高度依赖 Skill 提取、检索和执行机制。另一方面，作者公开了容器化代码，并在 Claude Code、Codex、OpenClaw、Hermes 四类真实 Agent CLI 上固定 backbone 比较方法，至少使“风险究竟来自模型还是 Skill Evolution 方法”更容易被拆开验证。

### 最值得继续追踪

重点不是再看一个更高 ASR，而是看 **Skill provenance、版本、适用域、失效条件和回归测试能否成为持久状态的一等公民**。如果未来 Self-Evolving Agent 真正进入生产，这很可能会像软件供应链签名一样成为基础设施。

## 2. DIVE：Frozen Model 不改权重，也可以通过“多种群 Skill 进化”持续提升

**论文：** [DIVE: Unlocking Self-Improvement in Frozen Language Models Through Diversity-Driven Skill Evolution](https://arxiv.org/abs/2608.12486)

DIVE 走的是 Skill Evolution 的“收益侧”。模型参数完全冻结，通过任务经验和 verifier feedback 产生自然语言 Skill；Skill 不只是提示词，而是可持续修订的推理程序、验证策略、常见失败模式和输出约束。

它最有意思的地方不是“让模型反思一次”，而是承认 Skill Evolution 本身是随机、非凸搜索：单一路径很容易过拟合少量经验。因此 DIVE 同时维护多个独立 Skill population，再通过多类 operator 做 Reflective Repair、Exploratory Revision、Compression、Recombination，最后选择互补 Skill 集合。

论文在 6 个数学和逻辑推理任务、多种模型家族上报告优于 reasoning、prompt optimization、skill development 与 memory baseline，并声称相较 SFT、GRPO 和 GEPA 用更少 rollout 获得更大的性能增益；其 Skill 还能跨模型规模与家族迁移，作者报告 GPT-5-nano + DIVE 可匹配或超过常规 prompting 下的 GPT-5。

### 为什么重要

它进一步强化了一个工程判断：

$$
\text{Agent capability}
\neq
\text{model weights only}
$$

更合理的分解是：

$$
\text{Capability}
=
\text{Frozen Model}
+
\text{Skills}
+
\text{Memory}
+
\text{Harness}
$$

对于生产系统，外部 Skill 比频繁更新 checkpoint 更容易版本控制、A/B、回滚和审计。但把它与上一节放在一起看，结论也很清楚：**Skill 越能自我进化，就越不能把“任务成功”当成唯一 fitness。**

### 可信度与局限

目前证据仍集中在数学与逻辑推理，且依赖可获得的 verifier / validation 信号。它尚未证明在开放式 Tool Agent、网页 Agent 或企业工作流里，同样可以稳定进化而不产生 Skill drift。论文关于“小模型超过大模型”的结论也应理解为特定任务与 prompting 对照，而不是通用能力倒挂。

### 最值得继续追踪

我会看两个方向：**跨域 Skill transfer** 与 **安全约束进入 fitness function**。DIVE 解决了多样性和局部最优问题，但 Skill Misevolution 提醒我们，优化目标如果只奖励成功率，进化得越快未必越好。

## 3. Agent Memory：真正的下一步不是“更大向量库”，而是 associative recall + target-bound reuse

今天两篇 Memory 工作正好补上同一条链路的不同环节。

**论文 1：** [RippleMem: From Isolated Retrieval to Associative Recollection for Long-Term Agent Memory](https://arxiv.org/abs/2608.13334)  
**论文 2：** [Beyond Retrieval: Query-Conditioned Reuse of Long-Horizon Agent Trajectories](https://arxiv.org/abs/2608.12847)

RippleMem 指出，长期交互中的证据经常散落在多个 episode：flat top-k retrieval 可能只取回一个孤立片段，于是它先找 memory anchor，再沿语义和结构关联扩展，做类似“联想补全”的 recollection。作者在 LoCoMo 和 LongMemEval-S 上报告最佳总体结果，LLM-as-a-Judge accuracy 分别提升 3.95% 和最高 11.87%，同时相对其比较的图构建方式将 graph construction cost 降低约 30 倍。

QCR 解决下一步：**检索到正确历史 trajectory，不等于可以原样复用。**过去任务里的用户名、对象 ID、约束、网页状态可能已经失效。QCR 把长轨迹转成 target-bound note，只保留 workflow invariant，同时明确需要重新获取的 bindings、适用条件和 verification guardrail。在 WebArena、WorkArena、AppWorld 共 2,391 个目标实例上，它达到 62.3% 平均 Success，比直接注入 Full Trajectory 高 10.7 个百分点，同时减少 48.9% online tokens。

把两篇工作合起来，我认为长期 Agent Memory 更合理的执行链路是：

```text
Rich episodic storage
        ↓
Anchor retrieval
        ↓
Associative evidence completion
        ↓
Reusable-memory selection
        ↓
Target-specific rebinding
        ↓
Constraint / state verification
        ↓
Execution
```

### 为什么重要

这意味着“Memory 做得不好”不能再笼统归因于 embedding retrieval。至少要区分：

1. **Recall failure**：相关证据没找到；
2. **Completion failure**：找到了锚点但支持证据没补齐；
3. **Reuse failure**：历史流程有用，但旧 binding 被错误搬到新任务；
4. **Verification failure**：没有检查当前状态是否仍满足旧经验的前提。

QCR 的一个尤其值得注意的结果是：轨迹越长，直接注入 Full Trajectory 的收益衰减越严重；很长轨迹里，旧状态本身会成为噪声甚至错误诱导。

### 可信度与局限

RippleMem 的部分指标依赖 LLM-as-a-Judge，且“30×”是相对论文选择的 graph-construction baseline，不应理解为相对所有 memory system。QCR 则明确把自身定位成验证“post-retrieval reuse bottleneck”的简单格式，不声称这是最终 Memory Schema。两者都还是 benchmark 结果。

### 最值得继续追踪

很值得做的组合实验是：**RippleMem 负责 associative recall，QCR 负责 target-bound compilation，再加 provenance / safety gate。**这会比“检索几段历史聊天直接塞进 context”更接近真正可控的长期 Agent Memory。

## 4. Agent 做 AI R&D：当前更像“工程优化器”，还不是稳定的自主研究员

**论文：** [Beyond Final Scores: A Systematic Evaluation of Agents for Long-Horizon AI Research and Development](https://arxiv.org/abs/2608.13417)

作者测试 7 个 frontier model、36 个 long-horizon AI R&D task，不只看最终分数，而把过程拆成 Solution Framing、Execution、Feedback Control，并单独考察经验在同任务和跨任务中的复用。

论文给出的结论相当克制：当前 Agent 可以提出并实现实用方案，但 run-to-run variance 明显；最强方案大多是适配或组合已有技术，真正的方法学创新仍然少见。经验复用也不是单调收益——历史经验有时改善决策，有时会把后续搜索带偏；Harness 设计本身会显著影响稳定性。

### 为什么重要

这对“AI Scientist”类系统是一个很好的评价提醒。单个 final score 很高，不代表 Agent 真的形成了稳定研究能力。更应该记录：

```text
提出了什么假设？
做了哪些实验？
如何解释失败？
下一轮是否真正利用了反馈？
换一个任务后，旧经验是帮助还是锚定偏差？
```

### 可信度与局限

36 个任务远不能覆盖真实科研；“创新”也很难被完全客观量化。但这类过程级评估比只展示几条成功 demo 更接近我们真正想知道的问题：**Agent 的高分究竟来自稳定方法，还是一次幸运搜索。**

### 最值得继续追踪

未来 benchmark 应该报告的不只是 success rate，还应有 **跨 seed 方差、实验效率、错误恢复、经验迁移增益/负迁移率，以及 novel-method rate**。

## 5. CROP：On-Policy Distillation 里，不是每个 token 都值得同样多的监督

**论文：** [CROP: Task Relevance via Counterfactuals for Selective On-Policy Distillation](https://arxiv.org/abs/2608.13387)

On-policy distillation 的优势是 teacher 在 student 自己访问到的 trajectory / prefix 上提供监督，但经典做法往往对 response token 近似一视同仁。CROP 认为“模型不确定”与“这个 token 真正受当前任务条件决定”是两件不同的事。

它为原 prompt 构造一个 meaning-preserving paraphrase 和一个只改变关键条件的 counterfactual，然后固定 student rollout，分别重打分。直觉上：如果某 token 在 counterfactual 下分布变化大，而在 paraphrase 下变化小，它更可能承载当前任务真正相关的信息。

可写成：

$$
d_{sem}(t)=\operatorname{JSD}(P_t^{orig},P_t^{cf})
$$

$$
d_{surf}(t)=\operatorname{JSD}(P_t^{orig},P_t^{para})
$$

$$
s_t^{CROP}=d_{sem}(t)-d_{surf}(t)
$$

然后只对高分 token 保留 OPD loss。论文在两个 Qwen teacher-student 设置下、名义 10% supervised-token budget 上，CROP 对最强非 CROP selector 的 aggregate improvement 分别达到 1.92 分和约 3 分量级；其中 Qwen3-4B → Qwen3-1.7B 的平均分为 47.98，比 Pure OPD 高 3.11 分。

### 为什么重要

它给“token selection”加入了一个很有价值的维度：**task relevance**。Entropy 高只能说明模型拿不准，teacher-student KL 高只能说明两者不同；都不能保证该 token 真正受 prompt 的关键语义条件控制。

### 可信度与局限

CROP score 是模型内部、特定对比构造下的 ranking heuristic，不是严格因果效应，也不是 ground-truth relevance。它还需要 original / paraphrase / counterfactual 三次 student rescoring，加上离线 triplet 生成与验证，算力成本不能忽略。目前主要训练数据仍是数学问题。

### 最值得继续追踪

我会特别关注它能否扩展到 **Tool Agent trajectory**：例如改变一个工具约束或目标实体，找出哪些 action token / reasoning span 真正随任务条件变化，再做 selective distillation。那会比只在答案 token 上筛选更有价值。

## 6. FSGR：Semantic ID 生成式推荐里，token frequency 本身就是 exposure bias

**论文：** [FSGR: Mitigating Token Frequency Bias for Fair SID-Based Generative Recommendation](https://arxiv.org/abs/2608.12845)

SID-based generative recommendation 把 item 编成多层离散 token，再像语言模型一样自回归生成。FSGR 指出一个容易被忽略的问题：高频 SID token 会被系统性过预测，低频 token 被低估；偏差来源同时包括不平衡 codebook、训练数据 popularity bias 和 MLE objective。

这会形成一个隐蔽的“rich-get-richer”链路：

```text
热门 item 更多
  → 对应 SID token 更高频
  → token 更容易被生成
  → 对应 item 获得更多曝光
  → 新数据进一步强化高频 token
```

FSGR 在 SID 构造阶段用 OT-based Assignment Optimization 与 Dual-Criteria Re-anchor 平衡表示空间，在训练阶段再做 Semantic Alignment Pretraining 与 Hierarchical Frequency Calibration。作者在 3 个公开数据集、3 类 backbone 上报告平均 Gini fairness 改善超过 20%，同时保持有竞争力的推荐准确率。

### 为什么重要

传统推荐公平性分析通常直接看 item popularity、provider exposure 或 user group；生成式推荐多了一层 **tokenization-induced bias**。即使最终训练样本不变，Semantic ID 的码本频率结构也可能改变解码先验。

### 可信度与局限

论文里的“fairness”主要是 item-side exposure / Gini 维度，不能自动等价成用户群体公平、商家公平或业务价值公平。离线准确率“保持竞争力”也不等于线上 CTR/CVR 无损；更均匀的曝光有时会真实牺牲短期点击收益。

### 最值得继续追踪

线上真正该拆的是：**SID depth × token frequency × item popularity × exposure × CTR/CVR**。如果低频 token 的曝光恢复只发生在无点击长尾上，公平指标好看但业务价值有限；如果能恢复“被编码偏差压制的有效长尾”，才是更强结果。

## 7. RAGSieve：RAG Knowledge Poisoning 可以靠局部对比发现，但防御代价不能藏起来

**论文：** [RAGSieve: Self-Referenced Local Contrast for Knowledge-Poison Detection in Retrieval-Augmented Generation](https://arxiv.org/abs/2608.13010)  
**代码：** [XrazyMee/RAGSieve](https://github.com/XrazyMee/RAGSieve)

RAGSieve 的思路是不用额外 trusted corpus，而从被检查系统自身构造“局部参照”。RSQ 在 query time 比较 top-5 candidate 与 ranks 6–20，寻找异常的 answer-anchor concentration / carrier transition；RSG 在 corpus ingestion 阶段比较文档与语义相似但词面不同的邻居，检测局部密度异常。

在 3 个 QA 数据集、6 种 poisoning construction 上，论文报告 RSQ AUROC 95.2%，在只移除 5% clean document 的预算下检测 82.2% poison；RSG 对应为 93.3% / 79.8%。两者联合后，attack success 从 67.4% 降到 14.0%。

但这里最该盯住的是另一半数字：**联合防御后 unpoisoned retrieval F1 只保留 41.3%。**这意味着它现在更像“强防御、明显效用代价”的方案，而不是已经解决了 RAG poisoning。

### 为什么重要

RAG security 很容易出现只报告 ASR 下降、不报告 clean utility 的情况。RAGSieve 至少把代价一起摆出来了。对于真实系统，更合理的目标应是多目标优化：

$$
\min \; \text{AttackSuccess}
$$

同时约束：

$$
\text{CleanRecall} \geq \tau
$$

而不是把 threshold 调到足够激进就宣布防御成功。

### 可信度与局限

代码已经公开，并给出了完整索引构建、RSQ 检测、过滤与 QA 流程，但仍是刚发布的研究代码，尚缺独立复现。其局部对比假设也可能被更自适应的攻击者针对，例如让 poison 更像局部语料分布。

### 最值得继续追踪

下一步最关键的是 **clean-quality constrained calibration**：固定允许的 clean recall / F1 损失，再比较不同防御能把 ASR 压到多低。没有这条约束，不同防御数字很难公平比较。

## 8. 两条值得快速扫一眼的检索 / RAG 信号

### TTT-Embed：不改 retriever 权重，直接在 embedding 输出空间吸收 test-time ranking reward

[Test-Time Optimization of Query Embeddings with Ranking Aware Reward Maximization](https://arxiv.org/abs/2608.12569) 提出 TTT-Embed：冻结 encoder 与现有 index，只把 reranker / LLM judge 给出的 scalar ranking reward 蒸馏成一个轻量向量，在 embedding space 中复用。作者在 5 个 embedding model、15 个 MTEB retrieval task 上报告最高 +8.36 nDCG@10。它值得关注的不是单个最高增益，而是提供了一条 **closed-source embedding API 也能做 test-time adaptation** 的路径。

局限也很明确：reward 从哪里来、每次要付多少 reranking / judge 成本，会决定总经济性；“不改权重”不等于“免费适应”。

### Multi-round RAG stopping：省 3.70% retrieval call，但 EM 下降 0.625

[When Should Multi-Round RAG Stop?](https://arxiv.org/abs/2608.13237) 把停止搜索视为序列决策，并训练 Qwen3.5-2B judge 判断 sufficiency / gap。在冻结 Search-R1 其他组件的 confirmatory test 中，retrieval call 减少 77 次，即 3.70%，但 Official EM 同时下降 0.625 个百分点。

这个结果反而很有参考价值：**“学会停止”未必自然带来更低总成本或不降准确率。**多一个 judge 本身也有推理开销，所以最终应比较端到端 token、latency、API cost 和 quality，而不是只数 retrieval calls。

## 9. X.com：今天不拿旧帖冒充热点

## 今日最值得花 30 分钟阅读的一项

**首选：[Practice Makes Unsafe: Skill Misevolution in Self-Improving LLM Agents](https://arxiv.org/abs/2608.12851)，并顺手看它的 [代码仓库](https://github.com/henrymao2004/misevolve)。**

理由不是它的 benchmark 数字最大，而是它补上了 Self-Evolving Agent 讨论里经常缺失的一半：大家都在研究“如何把经验沉淀成 Skill”，但只要 Skill 是 persistent state，就必须同时研究 **污染如何被沉淀、如何跨任务传播、如何在新会话复现**。

最有效的 30 分钟阅读顺序：

1. 先看 threat model：攻击者能做什么、不能做什么；
2. 再看 authoring → retrieval → execution → carryover 的生命周期指标；
3. 看 SafeEvolve 分别在哪个阶段拦截；
4. 最后打开仓库 README，看四个 Agent CLI 如何在固定 backbone 下被统一评测。

然后再回头看 DIVE，会更容易得到一个完整判断：**Skill Evolution 确实可能成为 parameter-free self-improvement 的重要路线，但它必须从第一天就把安全与 provenance 纳入更新协议，而不是能力做完后再外挂一个过滤器。**

## 今日可立即实践的一件事

给任何带长期 Memory / Skill Store 的 Agent 原型加一个最小版 **Write–Reuse Audit Layer**，哪怕暂时不做复杂分类器，只先把状态和指标记录完整。

建议每条持久 Skill 至少保存：

```yaml
skill_id: string
source_task_id: string
source_trajectory_hash: string
created_at: timestamp
success_signal: string
risk_tags: []
applicability:
  tools: []
  domains: []
  preconditions: []
forbidden_actions: []
last_verified_at: timestamp
version: integer
```

执行链路改成：

```text
successful trajectory
      ↓
extract candidate skill
      ↓
WRITE GATE
  - provenance 完整？
  - 是否包含高风险动作？
  - 成功是否依赖异常/恶意指令？
      ↓
persist + version
      ↓
retrieve on future task
      ↓
REUSE GATE
  - 当前 domain / tool 是否匹配？
  - precondition 是否仍成立？
  - 是否命中 forbidden action？
      ↓
execute / reject / ask for re-plan
```

同时开始记录三个指标：

$$
\text{UnsafeArtifactRate}
=
\frac{\#\text{unsafe skills written}}{\#\text{skills written}}
$$

$$
\text{UnsafeRetrievalRate}
=
\frac{\#\text{unsafe skills retrieved}}{\#\text{skills retrieved}}
$$

$$
\text{CarryoverFailureRate}
=
\frac{\#\text{later benign tasks harmed by persisted state}}{\#\text{later benign tasks}}
$$

这件事的价值在于：即使暂时没有成熟的 SafeEvolve classifier，你也先获得了 **可追踪、可回放、可回滚** 的 Skill 生命周期。对真正会长期学习的 Agent，这比再加一段“请安全地使用工具”的 system prompt 更接近根本控制点。

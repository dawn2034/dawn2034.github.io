> **今日主线：** Cross-Family OPD · Exact Tool RL · Harness Search-Space Control · KV Reuse · Vector Quantization · Agentic Recommender Optimization

截至今天早上，arXiv 最新常规公告批次为 **2026 年 9 月 10 日**：`cs.AI` 150 条、`cs.CL` 94 条、`cs.LG` 163 条、`cs.IR` 11 条；不同分类存在大量交叉收录，不能直接相加。今天几项高信号工作放在一起看，主线很清楚：后训练开始审计“Teacher 信号到底哪一部分值得迁移”、Tool RL 开始质疑不必要的采样估计、Harness 自我优化开始显式管理 edit permission 与历史快照；推理与检索侧则把 KV 复用和低比特向量搜索从平均误差问题推进到**实际决策是否保持不变**。推荐系统里，Meta 的 CORAL 进一步展示了一个值得算法团队认真考虑的方向：Agent 不一定直接替代 ranker，它也可以作为受约束的长期控制器，持续优化真实推荐系统的 retrieval / serving control surface。

## 今日核心判断

1. **Cross-family OPD 的核心问题可能不是 tokenizer，而是“家族差异”污染了能力增量信号。** CompassOPD 发现，Qwen3.5-35B-A3B 比同家族 4B Teacher 强 16.7 points，但在标准 cross-family OPD 中，两者蒸馏出的 Qwen3-4B Student 最终只差 0.1 point。作者把 Teacher 信号拆成跨家族 offset 与同家族 capability shift，只迁移后者后，跨三类 Student / 多类 Teacher 的平均 reasoning accuracy 相对标准 OPD 最多提高 5.50 points。

2. **如果 Tool action space 可以完整枚举，就没有必要用少量 rollout 估计一个本来能精确求和的期望。** FGPO 在 genomic tool selection 中发现，GRPO 训练越成功，Policy 越集中，重复采样越严重，完全没有 reward signal 的问题比例从 0.2% 上升到 20.8%。把所有 tool subset 一次性评分并优化 exact action expectation 后，15 个 reasoner×benchmark 设置全部优于 GRPO，平均 +6.75 points、最高 +14.20 points。

3. **Harness 自我进化的关键不是“让 LLM 随便改 Prompt”，而是控制它一次能改多大、从哪个历史状态继续搜索。** RobustSGPO 在 120 个 AgentX brainstorming tasks、95 runs、7,350 次候选尝试中发现，周期性放宽 `1→2→3` edit permission 比始终开放最大权限更好；在 30 个 held-out tasks 上，completion 从 60% 提到 80%，test quality 从 3.77 提到 4.14。这个结果更像自动程序搜索，而不是传统 prompt polishing。

4. **KV Cache 复用必须区分 exact-prefix reuse 与 cross-context reuse。** KVShareArena 指出，把旧 chunk 的 KV 直接塞进新的 RAG / Multi-Agent prompt 会同时带来位置错误和“旧 cache 从未看到其他 source”的交互缺失；单源问题只做 position correction 往往够用，多源问题则需要 re-encoding 或训练才能恢复 full recomputation 差距的一半到三分之二。未经修复的 cache 甚至可能比完全不用 cache 更差。

5. **向量量化是否可靠，应该审计“排序决策翻转”，而不只是平均量化误差。** 新的 vector-search 理论工作把风险写成 exact margin 接近 0 的概率质量加上 quantization residual tail；实验发现 standardized exact margins 对 held-out ranking / graph-pruning flip rate 的预测明显优于 global rank correlation。这对 binary code、RaBitQ、Lucene BBQ、PQ 都提供了一个统一的决策层评估接口。

6. **LLM Agent 在推荐系统里的高价值位置之一，是低频、强约束的 control plane，而不是每个 request 都在线推理。** Meta 的 CORAL 每 3 天进行一轮决策，读取近期系统信号和历史 A/B 结果，再通过确定性 numerical optimizer 把修改投影回固定预算约束。一个视频推荐场景最终做到 watch time +0.15%、sessions +0.16%，且没有增加 serving cost；另一个 serving-capacity 场景在 engagement 不显著下降的情况下节省了数百万美元年化容量成本，下一轮又把节省扩大 44%。

## 1. CompassOPD：Cross-Family Distillation 真正该迁移的是“能力变化”，不是家族基线差异

[论文：CompassOPD: Cross-Family On-Policy Distillation via Within-Family Likelihood Shifts](https://arxiv.org/abs/2609.10154)

### 发生了什么

OPD 的一个常见想法是：只要 Teacher 更强，而且能在 Student 自己的 rollout 上逐 token 打分，就应该能把能力蒸馏过去。但 CompassOPD 发现，同家族 OPD 与跨家族 OPD 的行为非常不同。即使先用 Teacher trajectory 做 SFT、尽量消除输出风格差异，Cross-family OPD 仍然很快进入平台期。

更强的 Teacher 也没有自动解决问题。Qwen3.5-35B-A3B 相比 Qwen3.5-4B 本身平均强 **16.7 points**，但两者分别蒸馏到同一个 Qwen3-4B Student 后，Student 结果只差 **0.1 point**。这说明标准 OPD 的 token-level likelihood difference 中混入了一部分与“Teacher 比参考模型强在哪里”无关的结构性信号。

作者把 cross-family OPD signal 分成：

$$
A_T = O + \Delta_T,
$$

其中 $O$ 是 Teacher-family reference 与 Student 之间原本就存在的 cross-family offset，$\Delta_T$ 是同一 Teacher family 内从低能力 reference 到强 Teacher 的 likelihood shift。CompassOPD 去掉 $O$，只迁移 $\Delta_T$，再用冻结的 Student 初始策略作为 anchor，避免 Student 在训练中漂得太远。

### 关键结果

低能力 Qwen3.5-0.8B 与 35B-A3B Teacher 在约 **70.0%** 的 aligned units 上给出相同 OPD 更新方向；也就是说，大量“Teacher 信号”在 Teacher 变强前就已经存在，更像 family-specific offset，而非新增能力。

CompassOPD 覆盖 Granite4.1-3B、Qwen3-4B、OLMo-3-7B 三类 Student，以及 Qwen3.5、Qwen3、Mistral 多个 Teacher family。在主实验中，它在 **20/21** 个 Student–benchmark 组合上优于标准 OPD、1 个持平，平均 reasoning accuracy 相对 OPD最高提升 **5.50 points**。

当缺少单独的低能力 Teacher-family checkpoint 时，作者还对 MoE Teacher 降低 expert activation，把同一 checkpoint 的低激活版本作为 reference；这一 self-reference 方案仍比标准 OPD 高 **3.43 points**，但比独立 0.8B reference 低 2.07 points。

### 为什么重要

这把 OPD 的问题从“Teacher 是否更强”推进到“Teacher 的哪部分差异真正对应能力”。如果跨模型家族的 likelihood geometry 本身有稳定偏移，直接使用：

$$
\log p_T(y_t|c_t)-\log p_S(y_t|c_t)
$$

会同时迁移模型家族风格、token preference、校准差异与真正的能力增量。

更一般地说，**跨模型蒸馏可能需要 relative representation / relative preference，而不是绝对概率对齐。** 对不同 tokenizer、不同架构、不同 post-training recipe 的 Teacher–Student 组合，这个问题尤其值得单独审计。

### 可信度与局限

证据比单一 Teacher–Student pair 更强，因为作者跨三个 Student family、多种 Teacher family，并做了 offset restoration 与 anchor strength ablation；把已删除的 offset 逐步加回来时，性能单调下降，也支持其机制解释。

但论文当前明确标记为 **Work in progress**。实验仍集中在数学 reasoning，且需要 Teacher family 内的 reference；MoE self-reference 虽能减少额外 checkpoint 需求，也还没有证明对 dense Teacher 或开放式 Tool Agent 同样有效。

### 最值得继续追踪

最关键的是把这个机制扩展到 Tool Agent / Coding Agent：跨家族 Teacher 的 tool-call likelihood、规划风格和自然语言 reasoning 是否也存在巨大 offset？如果存在，未来 OPD pipeline 可能需要把“能力增量信号”与“模型家族基线信号”作为两个独立对象处理。

## 2. FGPO：Tool Space 能枚举时，GRPO 的采样反而是额外噪声

[论文：Why Sample What You Can Enumerate? Exact Policy Optimization for Genomic Tool Selection](https://arxiv.org/abs/2609.10221)

### 发生了什么

很多 Tool RL recipe 会冻结一个 Reasoner，只训练“该调用哪些工具”的 Policy，再用 GRPO 从若干 sampled tool subsets 中估计期望 reward。对于通用 API 世界，这种采样不可避免；但在专业领域，经常只有少量重复出现的 computational capabilities，所有 tool subset 的组合空间虽然是指数形式，却仍小到可以完整枚举。

作者发现这时 GRPO 出现一个反直觉问题：**训练越成功，估计器越差。** Policy 越来越集中到少数偏好 subset，同一 group 越容易反复抽到相同动作；reward collision 增多以后，group-normalized advantage 趋近于 0，训练样本事实上失去更新信号。

### 关键结果

在 genomic reasoning 中，没有产生任何 reward signal 的 question 比例从 uniform reference policy 下的 **0.2%**，上升到 GRPO 训练后的 **20.8%**。

FGPO（Full-Group Policy Optimization）直接枚举全部 tool subsets，预先计算每个 `question × subset` 的 reward table，然后优化完整 action space 的 exact expectation。跨 **5 个 frozen reasoner × 3 个 genomic benchmark = 15 个设置**，FGPO 全部优于 GRPO，平均 **+6.75 points**，最高 **+14.20 points**。

作者估算，标准 on-demand GRPO 需要约 **2.4×** 更多 frozen-reasoner reward evaluations；在 GenomeQA 上，FGPO 还把平均调用工具数从 **2.36 降到 1.40**。

### 为什么重要

这个结果不应该被理解成“GRPO 不好”，而应理解成一个更基础的算法原则：

> **能精确积分的 action space，不应该为了沿用通用 RL recipe 而强行 Monte Carlo。**

Tool selection、Router、模型选择、Expert selection、Retrieval strategy routing 都经常出现小型离散动作空间。如果动作数只有几十到几百，先检查是否能 enumerate / dynamic program / cache reward，可能比继续增加 rollout 数更划算。

### 可信度与局限

论文的结构性论证很清楚，而且 15 个设置全部同方向；但领域是 genomic tools，动作集合小且 frozen Reasoner 使 reward table 可以离线预计算。开放 Web Agent、Shell Agent 或 Coding Agent 的动作通常含参数、状态依赖和长程后果，完整枚举不可行。

因此最可迁移的结论不是 FGPO 本身，而是：**训练前先测 action-space entropy、unique-action ratio 与 reward-collision rate，再决定是否真的需要 sampling-based policy optimization。**

### 最值得继续追踪

一个很自然的下一步是混合式方法：对可枚举的高层 Router 做 exact optimization，对每个 Router branch 内的长程动作继续用 on-policy sampling。这样可以把不必要的采样噪声从层级 Agent 的上层决策中移除。

## 3. RobustSGPO：Agent Harness Evolution 需要“编辑权限调度”，不只是语义梯度

[论文：RobustSGPO: Search-Space Control for Agent Harness Evolution](https://arxiv.org/abs/2609.09646)

### 发生了什么

Semantic-Gradient Prompt Optimization 的基本想法是：根据执行反馈解释失败原因，再让 LLM 修改 Harness。但“应该改哪里、一次改多少、失败后从哪个版本继续”本身也是搜索问题。如果每一步都允许大范围自由重写，容易破坏已经有效的规则；如果只允许很小编辑，又容易卡在局部最优。

RobustSGPO 将 Harness 修改明确成 patch：先指定 edit scope 与 operation，再构造、检查 patch；搜索失败时可以从当前 incumbent 继续，也可以回到保留的历史 snapshot。作者进一步测试 permission scheduling、cumulative controls 与任务分布变化后的 retention 策略。

### 关键结果

实验覆盖 AgentX brainstorming workflow 的 **120 tasks、95 runs、7,350 candidate attempts**。周期性 `1→2→3` permission schedule 相比固定开放最大 edit permission，test score 高 **0.28 point**。

在 30 个 held-out tasks、固定 **20M token budget** 下，RobustSGPO 把 completion 从 **60.0% 提到 80.0%**，test quality 从 **3.77 提到 4.14**。

Distribution shift 后，按 category retention 旧任务能更少退化，但随机 retention 在新目标分布上达到更高 endpoint。换句话说，“保留旧能力”和“适应新任务”之间存在真实的 search-budget trade-off，不能通过一句 continual learning 口号自动消失。

### 为什么重要

Agent Harness 自我优化正在越来越像软件配置搜索：

```text
失败轨迹
→ 定位可修改区域
→ 选择 edit permission
→ 构造 patch
→ executable check
→ 评估
→ 接受 / 回滚 / 从旧 snapshot 分叉
```

这和让模型直接重写 system prompt 是两个复杂度完全不同的问题。真正可靠的自进化系统需要 versioning、bounded mutation、rollback 和 search branching；这些结构与模型本身的 reasoning 能力同样重要。

### 可信度与局限

优点是作者报告了大量 candidate attempts，并显式比较 permission schedule 与 retention 策略。局限是结果仍集中在一个 AgentX brainstorming workflow，test quality 也不是跨领域通用指标；20M-token budget 很大，实际成本收益需要和人工 prompt / harness engineering 做 matched-budget 对照。

另外，周期性 `1→2→3` 是当前搜索空间下的经验最优，不应外推成通用 schedule。更一般的目标应是根据当前不确定性、历史失败类型和回归风险动态决定 edit scope。

### 最值得继续追踪

下一步值得直接学习一个 **edit-value model**：预测某个 Harness component 被修改后的期望收益与 regression risk，再决定允许的 mutation radius，而不是用固定周期放宽权限。

## 4. KVShareArena：跨 Context / Checkpoint 的 KV Cache 不是“复制过来就能用”

[论文：KVShareArena: KV-Cache Reuse Across Contexts and Model Checkpoints](https://arxiv.org/abs/2609.10266)

### 发生了什么

Prefix caching 之所以可靠，是因为缓存文本仍位于同样的前缀位置，而且写入 KV 时看到的上游上下文完全相同。RAG 与 Multi-Agent handoff 打破了这两个条件：同一个 retrieved chunk 每次可能出现在不同位置，也可能与不同 source 组合；Agent report 在新 Coordinator prompt 中同样会遇到位置和跨 source interaction 变化。

第三个问题来自 checkpoint 更新。即使是同一模型 family，旧 checkpoint 写出的 K/V state 与新 checkpoint 也不完全一致。KVShareArena 因此把此前分散在 cache relocation、cache compression、cross-model/checkpoint reuse 里的方法放到一个统一 benchmark 中比较。

### 关键结果

Benchmark 不只看准确率，而是测“相对于完全不使用 cache，恢复了多少 full recomputation 的质量差距”，同时分别核算 per-request compute、memory、latency，并把一次性 cache build cost 单列。

作者发现：**单 source 问题中，只做 position correction、完全不 re-compute 通常已经足够；一旦问题需要同时整合多个 source，position correction 就明显不够。** 这时只有愿意重新编码部分 cache 或进行训练的方法，才能恢复 full recomputation gap 的约 **1/2–2/3**。

未经 repair 的 KV 在某些设置下甚至比 no-cache 更差。另一方面，当 cache 来自同 family 的不同 checkpoint 时，training-free 方法受影响较小，而在单一 checkpoint cache 上训练的 adapter 会出现明显质量损失。

### 为什么重要

Agent 系统如果开始长期保存“可复用中间计算”，KV 就会从 request-local optimization 变成一种持久状态格式。它需要像 embedding index 一样处理：位置、模型版本、source dependency 和 migration contract 都不能省略。

这也提醒 RAG serving：retrieved chunk reuse 的真正目标不是“cache hit rate 越高越好”，而是：

$$
\text{saved prefill compute} - \text{repair cost}
$$

在满足 task-quality target 的前提下是否仍然为正。

### 可信度与局限

这篇工作的优势是 measurement boundary 很清楚，并提供 frozen querysets、cost accounting、自动 submission 与 public leaderboard。它当前更像 Benchmark / methodology 论文，不是证明某一个 repair algorithm 已经成为生产最优。

多 source 的“半到三分之二恢复”也不能直接外推到所有 context length、模型 architecture 和 Agent report 类型；跨完全不同模型 family 的 cache transfer 仍比同 family checkpoint 更困难。

### 最值得继续追踪

重点看 32K–256K context、continuous batching 与高 prefix-hit Agent workload 下的 `quality × TTFT × KV bytes × repair FLOPs × cache migration` Pareto。若 repair 开销接近重新 prefill，跨 context cache reuse 的系统价值就会迅速消失。

## 5. Low-Bit Vector Search：量化误差真正危险的地方，是 margin 很小的排序比较

[论文：When Does Low-Bit Quantization Preserve the Decisions of Vector Search?](https://arxiv.org/abs/2609.09854)

### 发生了什么

Vector Search 的量化评估长期常看 reconstruction error、平均距离误差、global rank correlation 或最终 Recall@K。这些指标能描述总体质量，却很难解释为什么相似 bit budget 在某些 embedding 上几乎无损、换一组表示就突然崩掉。

这篇工作把问题降到 ANN 算法真正消费的基本单元：**comparison decision**。对两个候选 $i,j$，如果 exact score margin 本来就很大，小量化噪声很难改变顺序；如果 margin 接近 0，即使平均 quantization error 很小，也很容易翻转决策。

作者给出一个 distribution-free decomposition：comparison flip risk 可以由“exact margin 落在零附近的概率质量”与“校准 residual 的尾概率”共同控制，并进一步处理共享 query / graph node 时 residual 相关性带来的协方差问题。

### 关键结果

对于 Vamana graph pruning，论文还给出一个 deterministic coupling result：在冻结 exact candidate permutation 后，只有当所有 candidate-level pruning action 都与 exact state 上的决定一致时，approximate replay 才会返回完全相同的 neighbor list。

在 learned、classical 与 synthetic embedding 上，**standardized exact margins 对 held-out ranking / pruning flip rate 的预测明显优于 global rank correlation**。框架可以统一应用于 coordinate binary codes、RaBitQ、Lucene BBQ 和 Product Quantization。

### 为什么重要

这给 ANN / RAG infrastructure 一个更有操作性的量化审计方法：不要只问“平均 cosine error 是多少”，还要问“线上最常见 decision margin 分布是什么”。同样的 quantizer 放在不同 embedding model 上，风险可以完全不同。

对于推荐召回也是如此。Top-K 边界附近的 pair、HNSW/Vamana pruning 边界、reranker candidate cutoff 都对小 margin 特别敏感；而真正决定业务质量的往往正是这些边界决策。

### 可信度与局限

论文理论部分很强，但核心结果是**风险解释与证书框架**，不是一个新的 ANN engine，也没有声称某种 quantizer 在所有数据上最好。实际生产系统还有 filter、hybrid retrieval、在线增量更新和 hardware kernel 等额外变量。

另一个边界是 exact-margin calibration 本身需要一批高精度参考计算。它更适合作为量化上线前的认证工具，而不是每个请求在线计算。

### 最值得继续追踪

建议关注是否能把 margin certificate 直接变成 **mixed-precision ANN**：大 margin comparison 用极低 bit，只有接近决策边界的候选回退到更高精度，从而把量化风险和算力动态分配到真正需要的位置。

## 6. CORAL：让 Agent 优化推荐系统的 Control Plane，而不是逐请求生成推荐

[论文：CORAL: An LLM-Native Harness for Production Recommender Systems](https://arxiv.org/abs/2609.02730)

> 这篇论文 9 月 2 日已发布，并非今天的新论文；但它与近期 Agent Harness、自我优化和推荐系统三条线高度重合，且有真实 A/B，值得在今天补读。

### 发生了什么

Meta 的 CORAL 把推荐系统持续调参建模成一个 partially observed、non-stationary、constrained optimization problem。Agent 不直接对每个用户／Item 在线推理，而是周期性读取系统 telemetry、历史决策和对应 A/B 结果，再调整 retrieval budget 或 serving treatment。

关键安全边界由 Harness 提供：LLM 可以提出方向，但最终 configuration 会经过 deterministic constrained optimizer 投影到预算可行域，保证：

$$
c_t(s_t)\le B.
$$

当前部署默认每 **3 天**运行一轮，Memory 保存最近 **3 个 cycle** 的 observation、assessment 与 decision outcome。模型负责判断异构信号与提出变化，数值可行性和实际应用由确定性工具控制。

### 关键结果

第一个大规模视频推荐场景优化不同 retrieval source 的固定候选预算。三轮 A/B 不是单调上升：R1 有小幅 watch-time gain，R2 过度调整后回到 neutral，继续把结果写回 Memory 后，最终 R3 部署配置获得：

| 指标 | R3 |
|---|---:|
| Watch time | **+0.15%** |
| Sessions（全部用户） | **+0.16%** |
| Sessions（最大市场） | **+0.77%** |
| 新的低信号用户 Sessions | **+0.23%** |
| Serving cost | **无额外增加** |

第二个场景让 Agent 在不同用户 segment 之间分配 serving treatment。第一轮已经节省**数百万美元年化容量成本**；Agent 根据结果扩大适用 segment 后，第二轮将节省幅度再提高 **44%**，同时 engagement 没有统计显著下降。

### 为什么重要

这可能比“让 LLM 直接做推荐模型”更现实。Control-plane Agent 的 inference 成本按 decision cycle 计，而不是按用户请求计；模型可以利用自然语言和历史实验做复杂判断，同时把硬预算、可执行性和回滚交给确定性系统。

对于工业推荐团队，它提供了一个清晰分层：

```text
LLM：提出假设、综合多指标、解释过去实验
Optimizer：保证预算与约束
A/B：提供真实环境反馈
Memory：保存决策及其后果
Guardrail：控制可修改范围
```

### 可信度与局限

这是 Meta 第一方工业论文，并有两类真实 A/B，证据强于纯离线 Agent recommender。但收益来自完整 Harness，无法隔离“LLM reasoning、Memory、optimizer、人工 oversight”各自贡献。

第二个场景只公布“数百万美元年化节省”和第二轮 +44%，没有给出可外部复算的绝对 serving cost；模型调用 token 也是根据 payload 估算，pipeline 没有记录真实 token usage。论文还明确处在人类监督逐步向 guardrail 自动化过渡阶段，不应解读成无人监管的推荐系统已经成熟。

### 最值得继续追踪

真正关键的是长期 stability：季节性、模型升级、内容分布突变下，Agent 是否会错误归因最近一次 A/B；以及自动 control-plane 的 promotion / rollback 权限如何设计，才能避免一次噪声实验污染后续 Memory 与配置。

## 今日值得收藏的代码 / 学习资源

**vLLM：Following the Bottleneck — MiniMax M3 on AMD MI355X** 是今天最值得系统工程师精读的长文之一。它不是简单公布一个 tokens/s，而是按“local shape → repeated work → bytes moved → fast path 是否真的执行 → 哪个 queue 在增长”逐层排查瓶颈。固定 TP4/EP1、concurrency 32 的 MXFP8 output throughput 从 109.1 提到 342.4 tok/s/GPU；更有价值的是 AgentX workload 中 theoretical prefix-cache hit 96.7%、realized GPU cache hit 92.1%、KV utilization 88.5%，说明下一阶段瓶颈已经从 GEMM 迁移到 prefix alignment、admission、eviction 与 cache capacity。文章还公开了一个失败案例：P/D KV transfer 看起来吞吐正常，但 layer layout 处理错误让 GSM8K 低到约 0.0008，提醒性能路径必须始终绑定 correctness gate。  
[阅读 vLLM 原文](https://vllm.ai/blog/2026-09-10-minimax-m3-mi355x)

**LiteRAG** 值得所有正在做 GraphRAG 的团队先读再决定是否需要 query-time LLM controller。它用 query-conditioned algorithmic graph exploration 替代昂贵的 retrieval-time LLM 决策；DistComp 上 overall quality 0.798，同时相对 GraphRAG Global / DRIFT 报告每 query latency 降低超过 100×、成本降低超过 99%；UltraDomain 上质量接近 LinearRAG，但 token 约少 14×。这些是论文自己的 benchmark，仍需要在企业知识图谱与不同 LLM 定价下复现。  
[LiteRAG 论文](https://arxiv.org/abs/2609.10239)

**Subagents vs Agent Skills** 给最近快速增长的 Skill 生态一个很重要的反例：Skill 内容相同，直接把 instructions 加进主 Agent context 与启动 fresh-context subagent 并不等价。对于输入输出契约明确、procedure 清楚的 Skill，subagent 方式更强，代价是额外的协调 token。它提示长程 Agent 设计时需要同时优化“知识是什么”和“知识在哪个 context 中执行”。  
[Subagents vs Agent Skills](https://arxiv.org/abs/2609.09233)

**CHyD（Constrained Hybrid Decoding）** 把 speculative-decoding 结构用于“证据忠实性”而非加速：当系统进入 extractive mode 时，硬约束 decoder 只能输出 retrieved context 中真实存在的连续 span，因此任何显式引用都能获得 verbatim guarantee。论文称现有 hybrid 方法在技术领域 exact extraction accuracy 可降到 40% 以下，而 CHyD 接近完全忠实；代价是 fluency 指标会受约束。对于法规、维修手册、审计证据等场景，这比再加一个 LLM Judge 更值得研究。  
[CHyD 论文](https://arxiv.org/abs/2609.10046)

**ConvMem** 则提供了另一种 long-context 思路：把 LLM 当作 query-conditioned convolution kernel，对文本 chunk 做层级归并，把原本线性的 sequential memory update 改成 logarithmic tree。它 training-free、易并行，并用 stride、skip connection 和 multi-kernel channel 减少证据丢失。当前只在 RULER-HotpotQA / 2WikiMultiHopQA 上验证，还不足以说明它能替代真实长文档 Agent Memory，但作为“并行化记忆归约”值得收藏。  
[ConvMem 论文](https://arxiv.org/abs/2609.10441)

## 今日最值得花 30 分钟阅读的一项

**首选 CompassOPD。**  
[论文原文](https://arxiv.org/abs/2609.10154)

这篇最值得读的地方不是又多了一个蒸馏 loss，而是它对一个很容易被忽略的假设提出了直接反例：**更强的 cross-family Teacher，并没有在标准 OPD 中转化成明显更强的 Student。** 35B-A3B 与 4B Teacher 自身差 16.7 points，Student 结果却只差 0.1 point，这迫使我们重新问“OPD likelihood difference 里到底装了什么”。

30 分钟建议按这个顺序读：先看 same-family / cross-family 的性能分叉；再看 0.8B reference 与强 Teacher 在约 70% aligned units 上给出相同更新方向；随后理解 $O+\Delta_T$ 的分解；重点看 offset restoration ablation——把被删除的 offset 加回来以后性能如何单调下降；最后看 MoE self-reference，判断这套方法是否有可能在缺少同家族小模型时落地。

真正值得带走的问题是：

> **跨家族 OPD 现在迁移的，到底是 Teacher 新学会的能力，还是两个模型家族原本就不同的概率几何？**

如果后者占很大比例，那么未来 cross-family distillation 的重点会从“找更强 Teacher”转向“构造更干净的相对能力信号”。

## 今日可立即实践的一件事

给现有 OPD 实验做一个 **Cross-Family Offset Audit**，不需要先实现 CompassOPD，也不需要重新训练完整模型。

选定一个 Student $S$、强 Teacher $T$，再找一个与 Teacher 同 family、明显更弱的 reference $R$。让 Student 在 100–500 个代表性 prompt 上自己 rollout，然后冻结这批 trajectory，对每个 token / action 同时计算：

$$
A_T = \log p_T(y_t|c_t)-\log p_S(y_t|c_t),
$$

$$
A_R = \log p_R(y_t|c_t)-\log p_S(y_t|c_t),
$$

以及真正希望迁移的相对变化：

$$
\Delta_T = \log p_T(y_t|c_t)-\log p_R(y_t|c_t).
$$

先统计三个最简单的诊断量：

```python
metrics = {
    "teacher_reference_sign_agreement": 0.0,
    "offset_to_shift_abs_ratio": 0.0,
    "student_action_bucket_accuracy": {},
}
```

其中第一项看 `sign(A_T) == sign(A_R)` 的比例；第二项比较 $|A_R|$ 与 $|\Delta_T|$ 的平均尺度；第三项按正确／错误 rollout、reasoning step、tool action 等分桶，看真正有价值的 Teacher shift 是否集中在 Student 的失败状态。

如果出现 **Teacher 明显更强，但 $A_T$ 与 $A_R$ 在大多数位置方向一致，而且 $|A_R| \gg |\Delta_T|$**，标准 cross-family OPD 就很可能主要在学习 family offset。此时才值得继续做“去 offset + Student anchor”的小规模 A/B。

**停止条件：** 如果不同 Teacher scale 的 $\Delta_T$ 与能力变化没有稳定关系，或者换 seed / prompt 后 sign pattern 剧烈变化，就不要直接把 CompassOPD 作为默认 recipe；当前模型组合可能不存在论文观察到的稳定 family-relative geometry。

这个实验真正回答的是：

> **你付出的 Teacher inference，究竟在传递能力，还是在传递模型家族差异？**

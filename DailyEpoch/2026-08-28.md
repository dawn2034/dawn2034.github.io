> **今日主线：** Harness Optimization · Agentic RL · Double-Blind Evaluation · Open-Weight Models · Recommendation Compression · Inference Silicon

## 今日核心判断

1. **Agent 的下一层优化对象正在从 Prompt 扩大到整个 Harness。** AutoSaddler 把失败轨迹诊断、Prompt / Tool / Middleware 修改和开发集验证做成离线优化闭环，在 GAIA2、SWE-Bench Pro、Terminal-Bench 2.0 上分别报告 +9.0、+9.6、+10.0 个百分点；但这仍是“整套 Harness 搜索”的结果，不能归因于某一种 patch 技巧。
2. **Hint-based Agent RL 的 guidance depth 可能更像一个“有效区间”，而不是单一最优点。** Agent-G² 用训练 rollout 本身估计每类任务的 Gaussian guidance distribution，避免逐样本 probe；ALFWorld 上相对最强 hint-based、hint-free、Aux-RL baseline 分别高 2.3、3.9、7.4 个点，但它仍依赖专家轨迹 prefix，离完全自主 curriculum 还有距离。
3. **Benchmark integrity 正在变成安全评估基础设施问题。** Google DeepMind、MLCommons、OpenMined、AVERI 用 confidential computing 做 proprietary model 的 double-blind evaluation：评测方不见模型权重，模型方不见保留测试集。它降低 contamination 和双向泄密风险，但并不能自动保证 benchmark 本身有效、覆盖充分或 TEE 实现绝对无缺陷。
4. **Open-weight 模型的效率竞争已进入“架构 × serving stack”联动。** GLM-5.3-Flash 是 320B total / 18B active 的原生多模态 MoE，引入 linear + sparse attention 和 IndexPool；官方报告相对 GLM-5.3 将 attention compute 降至约 1/3、KV cache 降至约 1/4.4，并公开权重。性能数字目前主要来自厂商自测，应与第三方复现分开看。
5. **工业推荐中的多模态表征压缩不必在 hard quantization 与 dense soft codebook 之间二选一。** SA-RSQ 用 Top-K sparse routing 存 `(Index, Probability)`，在 8–48 bytes/item 的预算下优化重构与线上效果；一周 A/B 报告 CTR +2.51%、CPM +3.66%，但数据集和系统细节是专有的。
6. **推理硬件评估应该同时看功耗、端到端 latency 和交互吞吐，而不只是单芯片峰值。** OpenAI Jalapeño 在 InferenceX 的三个公开模型上自报峰值性能/瓦提升 1.5–1.9×、端到端延迟降低 1.7–3.6×；这些是 first-party measured results，比较对象、TDP 归一化和整机系统差异都必须保留在结论里。

## 1. AutoSaddler：把 Agent Harness 当成可以持续优化、回滚和验证的“代码状态”

> **一句话结论：** Agent 失败不一定需要先改模型；Prompt、Tool schema、Tool implementation、Middleware 和 loop control 本身就是一个巨大的可优化空间，而可靠自修改的关键不是“会写 patch”，而是“会诊断、会做局部 patch、会用独立开发集拒绝过拟合 patch”。

**论文：** [AutoSaddler: Automatic Harness Optimization with Durable Updates from Agent Execution Traces](https://arxiv.org/abs/2608.23041)  
**代码：** [microsoft/AutoSaddler](https://github.com/microsoft/AutoSaddler)

### 发生了什么

AutoSaddler 把 Harness 优化表述成 offline mini-batch learning。它从一批失败 / 成功 execution trace 出发，先深挖失败根因，再把修改限制到一个显式 patch taxonomy：既可以改 Prompt 和 steering text，也可以改 tool definition、tool implementation、middleware hook 与 agent-loop logic。候选修改不会因为修复了“触发它的那条轨迹”就直接进入主 Harness，而是先在抽样训练 case 上复测，再通过 development split gate。

其 V2 进一步把执行状态做成 durable system：append-only event、immutable provenance、content-addressed candidate、可恢复 run state，并用 EvoDAG 保存不同候选 lineage 和反思结果。也就是说，它不只是“让 LLM 自动改 Prompt”，而是在尝试建立一套 Harness 版本演化基础设施。

### 关键结果

| Benchmark | Base harness Pass@1 | AutoSaddler Pass@1 | 提升 |
|---|---:|---:|---:|
| GAIA2 | 53.0 | **62.0** | **+9.0 pp** |
| SWE-Bench Pro | 37.3 | **46.9** | **+9.6 pp** |
| Terminal-Bench 2.0 | 40.0 | **50.0** | **+10.0 pp** |

论文的 ablation 指向三个有区分度的因素：deep debugging 优于浅层 reflection；targeted modification 优于 unconstrained editing；generalization-aware selection 优于只修当前 trajectory。

### 为什么重要

近一个月大量 Agent 论文都在提示同一件事：

> **Agent capability 不等于 model checkpoint。**

如果失败来自 tool output 太大、schema 模糊、错误恢复路径缺失、context compaction 丢规则、agent loop 重复无效搜索，那么继续做一轮 SFT / GRPO 很可能是在用模型参数补 Harness 的结构缺陷。

AutoSaddler 更进一步：Harness 不只是“人手工搭好的脚手架”，而可以成为可版本化的学习对象。对生产 Agent，这条路线往往比高频更新模型权重更容易 A/B、回滚和审计。

### 可信度与局限

当前 benchmark 增益是作者报告，还缺少大规模独立复现。更重要的是，这些数字来自**完整 Harness 优化系统**：Prompt、工具、middleware、control logic 都可能同时变化，不能把 +10 pp 简化成某种“自动 Prompt Engineering”收益。

Development gate 也不等于真正避免过拟合。如果 dev distribution 与 benchmark test 高度同源，Harness 仍可能逐渐编码 benchmark 特性。V2 目前支持的真实 Harness / Benchmark 集成范围也还在扩展，README 明确区分了论文复现用 V1 与当前 durable V2。

### 最值得继续追踪

最有价值的指标不是“优化 20 轮后 benchmark 涨多少”，而是 **patch portability**：在任务族 A 上接受的 patch，冻结后对任务族 B / 新工具 / 新模型是否仍有效；同时要报告 regression rate、patch lifetime 和 rollback frequency。

## 2. Agent-G²：Hint-based RL 的关键不是“给多少提示”，而是覆盖有信息量的 Guidance Band

> **一句话结论：** 在 reward 极稀疏的长程 Agent 任务里，专家 prefix 太短可能仍到不了成功区域，太长又把探索空间压死；Agent-G² 的新意是把 guidance depth 从确定性标量改成每类任务动态更新的分布。

**论文：** [Agent-G²: Gaussian Guidance for Agentic Reinforcement Learning](https://arxiv.org/abs/2608.23318)  
**代码：** [ZJU-REAL/Agent-G2](https://github.com/ZJU-REAL/Agent-G2)

### 发生了什么

Hint-based Agent RL 会先保留专家轨迹的一段 prefix，再从更接近成功的状态让 policy 自己 rollout。真正困难的是 guidance depth：统一 schedule 不看样本差异；逐样本 probing 又需要额外 rollout。

Agent-G² 的经验观察是，一个任务里“有学习价值”的 guidance depth 往往不是一个尖点，而是一个近似 unimodal 的带状区域。它将 guidance ratio 建模为：

$$
r_i \sim \mathcal{N}(\mu_i,\sigma_i^2)
$$

其中中心结合全局训练进度与 cluster difficulty，方差反映 cluster 内难度差异；所需统计直接来自正常 policy rollout，不额外做 per-sample probe。

### 关键结果

作者在 ALFWorld、WebShop，以及 Qwen2.5-1.5B / 7B-Instruct 上测试。摘要报告在 ALFWorld 上：

| 对比对象 | Agent-G² 提升 |
|---|---:|
| strongest hint-based baseline | **+2.3 points** |
| strongest hint-free baseline | **+3.9 points** |
| Aux-RL baseline | **+7.4 points** |

同时，作者称其 rollout cost 低于 per-sample probing 的三分之一。

### 为什么重要

它把 Curriculum / Hint Scheduling 从“手写时间表”推进到依据当前 policy 能力在线调整。更一般地说，结构化输出和 Agent RL 里的 sparse reward 经常不是 reward 设计本身的问题，而是**policy 还没有 coverage 到能够产生学习信号的状态区域**。

如果这个判断成立，最好的训练数据不一定是“最难”或“最容易”，而是处于当前能力边界附近、成功概率既不接近 0 也不接近 1 的区域。Agent-G² 用 guidance depth 近似控制这个边界。

### 可信度与局限

这里的 Gaussian shape 是经验拟合，不是理论定律。不同任务的 informativeness profile 完全可能多峰、偏斜或随训练阶段快速改变。

更根本的限制是它仍然需要**专家轨迹 prefix**。因此它解决的是“如何更省 rollout 地利用 oracle guidance”，而不是“没有专家轨迹时 Agent 如何自主发现 curriculum”。ALFWorld / WebShop 的结构也比真实浏览器、Coding Agent 更稳定。

### 最值得继续追踪

后续真正有突破性的版本，应把 oracle prefix 换成 verifier-selected partial trajectory、retriever-recovered prefix 或自生成高置信 checkpoint，并比较同等 rollout budget 下能否保留大部分收益。

## 3. Double-Blind AI Evaluation：把 Benchmark 保密和模型 IP 保密同时做成系统约束

> **一句话结论：** 高价值闭源模型与高价值私有 benchmark 之间存在“双重保密困境”；Google DeepMind、MLCommons、OpenMined、AVERI 的 proof of concept 用 confidential computing 让双方都不需要把核心资产交给对方。

**Google DeepMind：** [Piloting the world's first double-blind AI evaluations](https://deepmind.google/blog/piloting-the-worlds-first-double-blind-ai-evaluations/)  
**MLCommons：** [AILuminate and the First Double-Blind Reliability Evaluation of a Proprietary AI Model](https://mlcommons.org/2026/08/double-blind-reliability-evaluation/)

### 发生了什么

传统模型评估有一个越来越严重的结构问题：如果模型开发方看到 benchmark prompts，未来训练很容易产生直接或间接 contamination；如果独立 evaluator 想在自己的环境运行闭源 frontier model，模型方又不愿暴露权重和实现。

这次 proof of concept 使用 confidential computing / secure computation，把评测放到受密码学保护的隔离环境中。MLCommons 提供了一组预留 AILuminate prompts，并明确表示这些 prompts 没有暴露给被测 Google DeepMind 模型；AVERI 通过 OpenMined 的 secure-computation stack，在 containerized DeepMind model 上执行评测。模型提供方看不到测试内容，benchmark owner / auditor 也看不到模型权重。

### 为什么重要

这比“签 NDA 后把测试集发给模型厂商”更接近可持续 benchmark governance。随着 frontier model 越来越贵、benchmark 越来越容易饱和，真正高价值的评测集往往必须长期保密；而外部审计者也不可能要求所有厂商公开 checkpoint。

Double-blind evaluation 因此解决的是**评估流程完整性**，而不是某个模型的分数问题。它对金融、医疗、政府采购等需要第三方验收、同时双方数据都敏感的场景尤其重要。

### 可信度与局限

Google DeepMind 将它称为“world’s first double-blind evaluation of a proprietary frontier-class model”，这是参与方自己的“首个”表述；更稳妥地说，它是一个公开披露的 double-blind proof of concept。

它也没有解决三个问题：第一，benchmark 自身是否真正测到目标能力；第二，reserved prompts 是否足够大、足够代表真实风险；第三，Trusted Execution Environment、container 和 attestation chain 是否存在实现漏洞。**保密评估能减少 contamination，不会自动把一个差 benchmark 变成好 benchmark。**

### 最值得继续追踪

值得关注这种协议能否扩展到 agentic evaluation：模型需要访问网络、工具和长期状态时，如何同时保护 hidden task、私有工具数据、模型权重和完整 execution trace。那会比单次 prompt-response 评测复杂得多。

## 4. GLM-5.3-Flash：320B / 18B Active，把 Long-Context 成本直接写进模型架构

> **一句话结论：** GLM-5.3-Flash 的看点不只是一个新的开源 MoE，而是 linear attention、sparse global retrieval、IndexPool 与 EPD serving 被一起设计；真正应该验证的是这些架构收益能否在第三方推理栈和真实 Agent workload 上复现。

**官方博客：** [GLM-5.3-Flash: Frontier Intelligence, Flash Cost](https://z.ai/blog/glm-5.3-flash)  
**权重：** [zai-org/GLM-5.3-Flash](https://huggingface.co/zai-org/GLM-5.3-Flash)

### 发生了什么

GLM-5.3-Flash 是 GLM-5 系列首个原生多模态 Flash 模型，**320B total / 18B active**，共 45 层。Z.ai 将稀疏全局注意力与 linear attention 混合：linear component 负责局部 / 状态建模，sparse attention 通过轻量 indexer 找远程相关上下文；IndexPool 又把四个 indexer key 向量压成一个，以降低 1M context 下 indexer 的内存和延迟。

官方还给出了与 GLM-5.3 的架构侧比较：attention compute 降低约 **3.0×**，平均 KV cache size 降低约 **4.4×**。服务侧使用 Encode–Prefill–Decode 分离、W8A8、混合 INT8 / FP8 / BF16 cache quantization 和 Layer Split，并称相对最初 baseline 在同一国产硬件上的端到端 serving 提升约 3×。

### 关键结果

官方公开的部分 benchmark：

| Benchmark | GLM-5.3-Flash | GLM-5.2 | Claude Opus 4.8 |
|---|---:|---:|---:|
| Terminal Bench 2.1 | 84.3 | 81.0 | 85.0 |
| DeepSWE v1.1 | **63.4** | 46.2 | 58.0 |
| Toolathlon Verified | **78.4** | 59.9 | 76.2 |
| AutomationBench v1.0.6 | **48.8** | 26.2 | 41.0 |
| Agents' Last Exam | 26.3 | 20.4 | 27.0 |

Z.ai 还报告 Artificial Analysis Intelligence Index v4.1.1 得分 57、每任务成本 \$0.045（discounted），并称模型在其价格体系下约为 GLM-5.2 的十分之一成本。以上性能与价格结论均应视作官方发布数据。

### 为什么重要

Long-context model 过去常先追求能力，再让 serving team 在 KV quantization、prefix cache、paged attention 上“补救”成本。GLM-5.3-Flash 更像从模型层就承认：

> **对 Agent / Coding，百万上下文不是只要能塞进去，还必须能被经济地长期服务。**

18B active、混合 attention、IndexPool 和 disaggregated serving 实际上在优化同一个目标：减少每一步 Agent interaction 的边际计算和 state movement。

### 可信度与局限

大多数 benchmark 和“3× serving improvement”来自 Z.ai 自己的评测。Harness、effort、max tokens、judge 和 anti-cheat protocol 在不同 benchmark 中并不完全一致；例如某些结果使用 Claude Code harness，HLE 使用另一个 LLM judge。因此跨模型表格不能被当成严格、单变量的架构比较。

另外，官方明确说 KV cache 虽显著低于 GLM-5.3，但仍略大于 Kimi-K3 和 DeepSeek-V4-Flash。开放权重使第三方复现成为可能，但第三方在 vLLM / SGLang、不同 GPU 上的 P95 latency、吞吐和 1M context quality 才是下一步更重要的证据。

### 最值得继续追踪

建议重点看三个第三方量：**相同质量约束下的 GPU-hours / task、长 Agent session 的 KV residency、以及混合 attention 在稀有 long-range dependency 上的 recall**。如果只测短 benchmark，linear/sparse hybrid 的真正边界很难暴露。

## 5. SA-RSQ：用 Sparse Soft Code 表示多模态 Item，在 8–48 Bytes 预算里找线上 Pareto

> **一句话结论：** 工业推荐的多模态 embedding 不一定要完整保存，也不必直接硬量化成一个 code；SA-RSQ 只激活少量 codebook entry，并同时保存 index 和概率权重，让“更大的 codebook”不再等于“每个 item 存得更多”。

**论文：** [SA-RSQ: A Versatile Sparse Representation Framework for Multi-modal Recommender Systems](https://arxiv.org/abs/2608.22979)

### 发生了什么

高维图文 / 视频 embedding 在亿级 item 场景里会迅速变成存储、cache、网络和在线 lookup 开销。Hard quantization 虽便宜，但 code boundary 附近会出现明显 distortion；dense soft quantization 能表达不确定性，却要求为大量 code 保存权重。

SA-RSQ 使用 Top-K sparse routing，只保存少数 `(Index, Probability)` tuple，再通过 weighted reconstruction 恢复表示。对固定 support，梯度直接通过 routing weights 和重构传播，不需要对离散选择使用 straight-through estimator。其核心目标是把“codebook capacity”和“per-item bytes”解耦。

### 关键结果

作者在一个专有外卖广告数据集上测试 **8–48 bytes/item** 的多种预算，并报告了 reconstruction / CTR trade-off。在线一周 A/B：

| 指标 | 相对提升 |
|---|---:|
| CTR | **+2.51%** |
| CPM | **+3.66%** |

论文还给出了 Next-Distribution Prediction 的初步实验，用于说明这种紧凑表示不仅服务当前 ranking，也可能保留下一步行为建模需要的语义。

### 为什么重要

推荐系统的多模态表征经常在两个世界之间拉扯：

```text
离线大模型 embedding：高维、富信息、成本高
线上 Ranker / Retrieval：高 QPS、低 latency、极度在意 bytes/item
```

SA-RSQ 的价值不在“发明了又一个量化器”，而是把 item 表示做成**稀疏概率混合**。这给后续动态 codebook、共享多任务表征、增量 item 更新留下比单一 hard code 更大的空间。

### 可信度与局限

最强证据是一周线上 A/B，但数据来自专有外卖广告系统，公开摘要没有给出完整的流量规模、延迟、CPU/GPU 成本、每个 storage budget 的线上曲线。因此不能从 +2.51% CTR 推断“稀疏软量化普遍优于所有 hard quantization”。

Top-K routing 本身也不是免费：codebook lookup、index/probability 解码和 reconstruction kernel 都会增加计算。真正的工业判断必须同时看模型收益和 bytes / bandwidth / latency。

### 最值得继续追踪

最值得补充的是 **同一线上质量目标下的 end-to-end memory-bandwidth Pareto**，尤其是不同 K、不同 codebook size、不同 item freshness 下的 cache hit、解码延迟和增量更新成本。

## 6. OpenAI Jalapeño：推理芯片开始围绕 Agent 的“低延迟 × 高能效”共同优化

> **一句话结论：** Jalapeño 的 first results 有实测价值，但正确读法不是“某块芯片比 NVIDIA 快几十倍”，而是 OpenAI 在特定 InferenceX operating point 上展示了更好的 latency–throughput–power Pareto；系统、TDP、模型精度和比较平台都属于结果的一部分。

**官方工程文章：** [Jalapeño’s first results show industry-leading speed and efficiency in AI inference](https://openai.com/index/jalapeno-first-results/)

### 发生了什么

Jalapeño 是 OpenAI 自研的第一代 inference accelerator。OpenAI 强调其设计目标不是单纯提高峰值 FLOPS，而是减少 model-state movement，把 prefill、decode、通信、KV cache placement 和网络作为一个整体优化；模型状态可以显式放置并尽量保持局部。

测试使用 SemiAnalysis 的 InferenceX，覆盖 GPT-OSS 120B、DeepSeek R1 670B 和 Kimi K2.5 1T。OpenAI 将结果按 accelerator published package TDP 归一化；Jalapeño 额定 700W，但官方称测试 workload 下持续功耗不超过 550W。

### 关键结果

| Workload | Peak mixed TPS/kW | E2E latency | Min TBT |
|---|---:|---:|---:|
| GPT-OSS 120B | **≈1.9×** comparison | **1.03s vs 1.80s** | **0.69ms vs 1.87ms** |
| DeepSeek R1 670B | **≈1.7×** | **1.65s vs 5.99s** | **1.43ms vs 5.90ms** |
| Kimi K2.5 1T | **≈1.5×** | **1.56s vs 5.31s** | **1.44ms vs 5.48ms** |

OpenAI 汇总称，三种模型上峰值性能/瓦提升 **1.5–1.9×**，端到端延迟降低 **1.7–3.6×**，高度交互 workload 的性能提升 **2.1–4.1×**。

另外，OpenAI 报告 AI 参与了芯片设计和软件优化：从设计到 tapeout 用时九个月；Codex + GPT-Astra 在两个月内把三种原本不在生产计划内的 open-weight model 带到高性能；selected GPT-OSS attention / MoE block 的 AI-generated implementation 比现有人类专家实现快 **1.5–1.8×**。最后这个数字只针对被选中的 kernel block，不是全模型 speedup。

### 为什么重要

Agent 的成本会把每一步 latency 累积起来。对单轮聊天，TTFT 差几百毫秒可能影响有限；对需要几十、几百轮 model/tool loop 的 Agent，每一步 decode / communication / KV movement 的等待都会放大。

Jalapeño 因此代表一个更明显的 inference co-design 方向：**模型、kernel、KV placement、network 和 accelerator 一起围绕 Agent workload 做 Pareto，而不是先造通用 GPU 再让 serving stack 适配。**

### 可信度与局限

目前全部核心性能数据来自 OpenAI first-party testing。比较平台并不是“同一块板只替换芯片”的严格实验：GPT-OSS 对比 GB200，DeepSeek / Kimi 对比 GB300；TDP 归一化有助于看能效，但不能消除系统拓扑、精度、软件栈和实际持续功耗的差异。

另外，官方 benchmark 使用 nominal 8k/1k STP request。它比纯 kernel microbenchmark 接近服务实际，但仍不能完整代表 persistent Agent session、tool-call gap、prefix reuse 和动态并发。Jalapeño 计划到年底才开始部署到 OpenAI 基础设施，规模化稳定性还未被长期生产数据验证。

### 最值得继续追踪

等进入生产后，最关键的不是再看峰值 TPS/kW，而是 **真实 Agent task 的 cost-per-success、P95/P99 latency、KV-resident session 数，以及软硬件共同升级后的可迁移性**。

## 今日值得收藏的代码 / 学习资源

**[SkillAlchemy](https://github.com/agentsope/SkillAlchemy)**：从公开文档、代码仓库、论文和 issue 中创建可安装 Skill，但把问题定义成“evidence-supported procedure admission”，而不是把所有检索结果都总结进 Skill。87 个 SkillsBench v1.1 任务、4 个 Agent–Model 配置上平均 pass rate 55.8%，比 no-skill 高 19.9 个百分点，比最强自动 Skill baseline 高 8.6 个百分点，并略高于该实验中的 human-curated average 54.4%。局限是 source-grounded 不等于 source-correct：公开资料本身可以错误、过期或被污染，因此 provenance / version / write gate 仍然必要。

**[NIS-Agent / From Inertia to Objectivity](https://arxiv.org/abs/2608.23045)**：提出 “inertia bias”——模型在评价自己刚刚做出的搜索 / 计划时，客观性会下降。方法在网页筛选和最终答案验证两处做 context isolation，在 GAIA、WebWalkerQA、BrowseComp、BrowseComp-zh 上保持竞争力同时比作者 baseline 减少 33% token。它值得拿来反思 Deep Research 里“让同一个 Agent 既提出假设又审核自己”是否天然有偏。

**[What Process Evaluation of Coding Agents Actually Measures](https://arxiv.org/abs/2608.22960)**：499 个 file-localization episode 的 replay-based measurement study。它把 next-action prediction、task uncertainty、step causal attribution 拆开，并发现 full-trace judge 存在系统性 collider bias。对近期大量 Process Reward / Step Judge 工作，是一个值得搭配阅读的反例。

**[AgentWeave](https://arxiv.org/abs/2608.23078)**：先确定性缩小 tool action space，再让冻结模型 reasoning。在 48 个 BFCL V4 multiple-function pressure tasks 上，AgentWeave 为 6/48 成功，而 all-tools / random top-8 / semantic top-8 都是 0/48；同时暴露工具数 -70.18%、输入 token -61.70%、本地模型平均 latency -50.95%。作者自己明确指出这只是窄压力测试，绝对成功率仍很低，不能当完整 BFCL leaderboard。

## 今日最值得花 30 分钟阅读的一项

**首选 AutoSaddler，并直接配合代码仓库阅读。**

建议不要从最终 +9～10 个百分点开始，而按这个顺序读：先看它把 Harness space 定义成什么、哪些东西允许变、哪些必须固定；再看失败轨迹如何从“这次没做对”变成 root-cause diagnosis；随后看 Capability patch 与 Steering patch 为什么要分开；再看 development gate 与 EvoDAG 如何阻止 trajectory-specific fix 直接污染主 Harness；最后看 V2 为什么加入 append-only event、immutable provenance、content-addressed candidate 和 resumable state。

真正值得带走的问题是：

> **如果模型权重完全冻结，你的 Agent 失败里有多少其实可以通过 Harness patch 稳定修复？这些 patch 有没有独立验证、版本、回滚和 provenance？**

如果答案是“很多可以修，但现在都靠人手工改”，那 Harness optimization 的投资回报可能比再做一轮小规模 RL 更高。

## 今日可立即实践的一件事

给现有 Tool / Search / Coding Agent 做一个 **Harness Patch Audit**。先不要自动让 Agent 改生产代码，只拿最近 20–30 条失败 trajectory 做离线实验。

先按根因给失败分桶：

```text
prompt_or_policy
tool_schema
tool_implementation
middleware_or_parser
context_management
model_capability_only
```

每个桶只允许提出 **一个最小 patch**，并保留 30% 的 failure case 作为 patch 生成过程完全不可见的 holdout。记录：

```python
metrics = {
    "base_success": 0.0,
    "patched_success_train": 0.0,
    "patched_success_holdout": 0.0,
    "regression_rate": 0.0,
    "failure_recurrence_rate": 0.0,
    "patch_size": 0,
}
```

定义一个很直接的可迁移收益：

$$
G_{\text{holdout}}
=
S_{\text{patched, holdout}}
-
S_{\text{base, holdout}}
$$

同时记录：

$$
R_{\text{reg}}
=
P(\text{Base 成功而 Patch 后失败})
$$

**停止条件：** 如果 patch 只提高生成它的训练 case、但 $G_{\text{holdout}}\le 0$，直接拒绝；如果 $R_{\text{reg}}>5\%$，先回滚而不是继续叠 patch；如果多数失败被稳定归入 `model_capability_only`，再考虑 SFT / RL，而不是强行通过 Harness 修补模型能力。

这项实验的价值不是立刻做出“自我进化 Agent”，而是先把一个经常被混淆的问题量化：

> **当前错误到底来自模型，还是来自模型周围的软件？**

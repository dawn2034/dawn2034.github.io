> **今日主线：** Action-Level Skill RL · Tiny Runtime Advisor · Environment Synthesis · Semantic-ID GRPO · Memory Poisoning · Agentic Inference Benchmarking

截至今晨，arXiv `cs.AI` 最新常规公告批次为 **2026 年 8 月 24 日**，该批次共列出 200 条提交。今天最值得连起来看的不是某个单点 benchmark，而是一组关于 **“训练和部署时，究竟应该把能力优化到哪里”** 的工作：Skill 不再只按整条轨迹统一处理，而开始进入 action-level 生命周期；运行时可靠性不一定需要另一个同等级大模型，可以让极小 comparator 只做局部比较；Self-Evolving Agent 的训练瓶颈则进一步前移到“能否自动生成可执行环境”。推荐系统侧，Semantic ID 的树结构正在迫使 GRPO 显式处理 target-path coverage；长期 Memory 则暴露出一个更根本的安全边界——文本内容看起来无害，并不等于其中事实是真的。

## 今日核心判断

1. **Skill-based Agent RL 正从“有没有 Skill”转向“这个动作此刻应不应该受 Skill 影响”。** AUSO 的 OOD 增益说明 action-level 区分可能比 trajectory-level routing 更有价值，但其 JSD 信号衡量的是“Skill 改变了 policy 多少”，不是严格的因果收益。
2. **运行时干预未必需要一个会完整解题的强 Critic。** COTA 用 0.5B comparator 只比较同一状态下两个局部 continuation，在三类 Agent 环境、三个明显更大的 actor 上都取得正增益；代价是额外 candidate generation 与比较，使平均端到端时间约为原 actor 的 1.38 倍。
3. **Self-Evolving Agent 的下一个基础设施问题可能是 Environment Supply，而不只是 Data Supply。** AgentMercury 把“生成带实体、服务、工具、状态和不变量的持久世界”本身做成可学习能力，但其跨域增益仍需要独立复现，尤其是 business-world RL 对 AIME26 的大幅提升。
4. **Semantic-ID Generative Recommendation 的 GRPO 不能把所有 hard sample 都当成普通低 reward 样本。** DASO 显式检测 rollout group 卡在哪一层 SID prefix，并把有限 guided budget 投到 target-missing 区域；它的收益支持“coverage gap”诊断，但不是纯 on-policy 方法，也不能把整套框架增益归因给单一动态分配器。
5. **Agent Memory 的安全问题不止 Prompt Injection。** 普通、无指令的错误事实只占 1.2% corpus 就能让 LongMemEval accuracy 从 0.850 跌到 0.300；这说明 content-only screening 天生无法判断“一个看似正常的陈述是否为假”，需要外部 grounding 与更合理的 provenance policy。
6. **Agentic inference 的 benchmark 正在从固定 8K/1K 请求转向 session replay。** NVIDIA 最新文章里真正值得跟的是 AgentX 对长上下文、KV 复用、tool-call gap、动态并发的建模；Vera Rubin 的“30×/MW”仍是 NVIDIA 预览结果，且明确等待 SemiAnalysis 审核，不应当成已经独立验证的硬件结论。

## 1. AUSO：Skill 的生命周期需要落到 Action，而不是整条 Trajectory

> **一句话结论：** 训练早期 Skill 可以是 Teacher，训练中期应让 Policy 自己探索，训练后期则只在某个具体动作确实受益时继续依赖 Skill；把三阶段放在同一个 RL backbone 里，是 AUSO 最值得看的设计。

**论文：** [AUSO: Action-Level Unified Skill Optimization from Internalization to Utilization](https://arxiv.org/abs/2608.21292)  
**代码：** [JordanSancholhz/Action-Skill](https://github.com/JordanSancholhz/Action-Skill)

### 发生了什么

很多 Skill-based Agent 方法会在“外部 Skill 检索”“Skill internalization”“直接做 RL”之间做任务级切换。AUSO 认为这个粒度太粗：同一条 trajectory 中，有些动作确实因为 Skill 变好，另一些动作可能被 Skill 干扰。

它把训练拆成三个连续阶段。早期同时使用 Teacher guidance 与环境 outcome，让 Policy 吸收基础 Skill；中期移除 Teacher，回到标准 GRPO 做 autonomous exploration；后期对 Student 已访问的同一状态，分别计算 **有 Skill context** 与 **无 Skill context** 时的动作分布差异，再将这个 action-level information signal 与 trajectory advantage 结合。

后期的核心直觉可以写成：

$$
I_t = \operatorname{JSD}\left(
\pi(\cdot \mid H_t, S),
\pi(\cdot \mid H_t)
\right)
$$

其中 $I_t$ 大，只表示 Skill 对第 $t$ 个动作的 policy distribution 影响更强；它本身并不证明这个影响一定有益，因此 AUSO 还要和最终 trajectory outcome advantage 结合。

### 关键结果

所有主要方法使用相同的 Qwen2.5-7B-Instruct backbone、每题 8 个 rollout，并在各 benchmark 上训练 150 个 optimization steps。

| Benchmark | Skill0.5 | AUSO | 差值 |
|---|---:|---:|---:|
| WebShop ID Avg. | 40.4 | **49.7** | +9.3 |
| WebShop OOD Avg. | 40.6 | **51.2** | +10.6 |
| ALFWorld ID Avg. | 93.1 | **94.3** | +1.2 |
| ALFWorld OOD Avg. | 58.5 | **67.9** | +9.4 |
| Search-QA Overall | 44.2 | **47.5** | +3.3 |

ALFWorld 的 `Pick Two & Place` OOD task 从 33.3 提高到 54.2，是论文里最明显的单类提升之一。

### 为什么重要

Skill 的使用权开始从“trajectory-level mode switch”下降到“action-level decision”。这和近期 Agent RL 的另一个趋势是一致的：真正决定路径的局部动作，不能总被整条轨迹的平均信号淹没。

更值得注意的是，AUSO 没有把 Skill 永远当外部拐杖。随着 Policy 成熟，优化目标从“模仿 Skill 提供者”逐步变成“判断 Skill 对当前动作是否仍然有增量价值”。这比永久 Retrieval-Augmented Agent 更接近一种能力内化—自主化—按需调用的生命周期。

### 可信度与局限

这是刚发布的预印本，尚无独立复现。更关键的是，JSD 衡量的是 **Skill sensitivity**，不是执行反事实意义上的 causal utility：如果 Skill 大幅改变动作分布但方向错误，仍然会得到大 $I_t$，最后只能依赖 outcome advantage 间接纠正。

OOD 结果也要谨慎解释。论文的 policy training 只使用 ID task，但 ALFWorld OOD evaluation 使用对应的 OOD-specific skill bank；因此这里证明的是“Policy 能在未用于 policy update 的 OOD task 上更好利用相应 Skill”，而不是“完全没有 OOD-specific guidance 时仍能零样本迁移”。

### 最值得继续追踪

我最想看的下一步，是把 JSD sensitivity 换成或结合 **action counterfactual replay**：同一个状态下有 Skill / 无 Skill或不同 Skill 真正执行后，最终 return 是否发生变化。这样才能把“Skill 改变了我”进一步推进到“Skill 确实帮了我”。

## 2. COTA：别让 Tiny Critic 解整道题，只让它比较两个局部选择

> **一句话结论：** “比较 A 和 B 哪个更好”可能远比“请给出正确下一步”容易，因此很小的辅助模型也能对强 Agent 提供有价值的运行时纠偏。

**论文：** [Don't Solve, Just Compare: Tiny Advisors for Runtime Intervention in LLM Agents](https://arxiv.org/abs/2608.21027)

### 发生了什么

COTA（Comparison-Only Tiny Advisor）不训练一个能够独立完成任务的 Critic。它用同一 prefix 下的 counterfactual branches 训练一个 **0.5B comparator**，只学习局部 pairwise preference：

```text
Actor 提出 action
        ↓
生成若干 alternative
        ↓
0.5B comparator 做重复 pairwise comparison
        ↓
若判断原 action 明显更差
        ↓
把更优 alternative 作为“建议”返回
        ↓
原 Actor 自己重新规划
```

关键点是最后一步。COTA 不让小模型直接接管环境动作，而只返回 non-binding advice。论文的 $2\times2$ ablation 显示，“pairwise comparison + constructive intervention”明显好于让辅助模型强制执行它选中的动作。

### 关键结果

以 Qwen3-8B 为例：

| Environment | 原 Actor | + COTA | 端到端时间倍率 |
|---|---:|---:|---:|
| WebShop reward | 0.3960 | **0.5630** | 1.413× |
| ALFWorld success | 82.84% | **90.30%** | 1.138× |
| $\tau^3$-Retail success | 37.50% | **45.00%** | 2.024× |

论文还测试了 Qwen3.6-35B-A3B 和 DeepSeek-V4-Flash，COTA 在 **9/9 actor–environment 组合**中都提升原 actor。整体平均端到端 episode time 为原 actor 的 **1.38×**，其中 7/9 设置低于 1.5×。

### 为什么重要

这是一个很实用的“任务降维”思路。辅助模型最困难的部分通常不是发现一个局部动作有问题，而是独立理解完整世界状态、给出一条足够强的替代方案。COTA 把后者重新交给强 Actor，只要求小模型做更窄的比较任务。

从系统角度，它说明 runtime reliability 不一定需要“双强模型”配置。可以把大模型预算保留给主 Agent，把监督层训练成专门的 narrow comparator。类似思想也可能迁移到 Tool Selection、Plan Branch、SQL query candidate、代码 patch candidate 等可构造局部 alternatives 的环节。

### 可信度与局限

这不是免费的可靠性提升。COTA 需要额外生成 alternatives、重复做 pairwise comparison，在 $\tau^3$-Retail 的 Qwen3-8B 设置里端到端时间已经超过 2×。它还需要 same-prefix counterfactual branch 数据来训练 comparator，因此离线数据构造成本不能忽略。

另一个边界是：它依赖“当前状态能生成几个质量尚可的 alternative”。如果 action space 极大、候选生成本身就失败，Comparator 再准也没有可比较的好选项。当前证据也只来自三类 benchmark，没有证明 comparator 能跨工具生态和 domain 长期泛化。

### 最值得继续追踪

真正值得测的是 **intervention value per extra compute**：

$$
\frac{\Delta \text{Task Success}}
{\Delta \text{Runtime Cost}}
$$

并根据 Actor 自身置信度、状态风险和历史 failure rate 动态决定是否启动 comparator，而不是每一步都固定支付监督成本。

## 3. AgentMercury：Environment Generation 正在变成 Agent 的可学习能力

> **一句话结论：** 如果 Agent RL 缺的是高质量交互环境，那么下一步不一定只是合成更多 trajectory，而可能是让模型自己生成“可执行世界”，再从世界中自然产生任务。

**论文：** [AgentMercury: Your Agent Can Synthesize Verifiable Environments for Business Scenarios at scale](https://arxiv.org/abs/2608.20634)

### 发生了什么

AgentMercury 不围绕某一道 task 合成脚本，而先从高层 business scenario 实例化一个 persistent world：里面包含实体、服务、工具、状态，以及跨服务必须保持的 executable invariants。任务和 trajectory 随后从这个世界中产生。

作者构建了 **4,783 个可执行环境**，覆盖 14 个行业、50 个国家，并把这些环境作为 RL training substrate。更进一步，他们把“环境构建过程”本身收集成 construction traces，再训练模型学习如何生成新的 executable world。

### 关键结果

| 指标 | 训练前 | 训练后 |
|---|---:|---:|
| Qwen3.5-4B：EnterpriseOps-GYM | 12.3 | **15.7** |
| Qwen3.5-4B：AIME26 | 45.9 | **56.0** |
| Qwen3.5-35B-A3B：held-out business world authoring success | 3.3% | **83.3%** |

论文称这些环境在生成时没有针对上述 evaluation benchmark 做定向设计。

### 为什么重要

这把 self-improvement 的资源对象从“数据”扩大到了“世界”。

传统路径是：

```text
人工写环境
→ Agent rollout
→ 收集 trajectory
→ RL
```

AgentMercury 希望变成：

```text
业务场景
→ Agent 生成 executable world
→ verifier 检查状态与不变量
→ 自动产生多种任务 / trajectory
→ RL
→ 再训练更强的 world author
```

如果这条闭环成立，环境供给会从高成本人工瓶颈变成一种可扩展能力。对 Tool Agent、企业 Workflow Agent、仿真型 Agent，这可能比继续合成“单题单轨迹”更有长期价值。

### 可信度与局限

这是作者自建环境分布上的预印本结果。Synthetic business world 能否代表真实企业 API 的权限、异常、非平稳状态、隐性流程和脏数据，目前没有充分证据。

尤其需要克制解读的是 AIME26 从 45.9 到 56.0：在 business-oriented environment 上做 RL 后数学 benchmark 大涨，是很有趣的 transfer signal，但目前不能据此断言“环境 RL 普遍提升通用推理”。仍需要检查训练配方、数据混合、可能的间接重合，以及独立团队复现。

### 最值得继续追踪

我会重点看三件事：**World Validity、Task Diversity、Real-System Transfer**。生成环境只有“能运行”还不够；它还必须覆盖真实 failure mode，不能让 Agent 学会一套只在 synthetic simulator 里成立的捷径。

## 4. DASO：Semantic-ID GRPO 的 Hard Sample，问题可能是“根本没进入正确分支”

> **一句话结论：** 如果 rollout group 连 target SID 的第一层分支都进不去，继续做 vanilla group-relative reward 只会反复采到低信息样本；DASO 把 rollout budget 主动投向当前 policy 最缺的 SID prefix 深度。

**论文：** [Difficulty-Aware Semantic-ID Optimization for Generative Recommendation](https://arxiv.org/abs/2608.20611)  
**代码：** [LucasXinYu/DASO](https://github.com/LucasXinYu/DASO)

### 发生了什么

Semantic-ID Generative Recommendation 把 item 表示成层级 SID，并自回归生成。论文先做了一个很关键的诊断：冻结 SFT checkpoint 后，很多 prompt 的 exact target **不在 50-beam constrained ranking 的前 16 个候选中**；更困难时，前 16 个候选甚至没有一个进入 target 的 SID branch。论文还报告，公开测试集中超过一半 prompt 连第一个 target SID token 都没有匹配。

这会让 vanilla GRPO 遇到典型 coverage problem：同一 group 的 raw rollouts 都离 target 很远，reward 低且缺少可区分结构。

DASO 每个 rollout group 都在线计算 prefix-match depth，找出当前最明显的 SID bottleneck，然后只拿一个有上限的 guided budget 替换最弱的部分 raw completions：有些 completion 从 target 的第一层或前两层 SID prefix 开始，有些直接提供 full target completion。训练仍保留原始 rollout，同时加入 SID-prefix intermediate reward 和 SFT anchor。

### 关键结果

公开 Amazon Reviews 2018 实验使用 Qwen2.5-1.5B / 3B，GRPO group size 为 16、600 个 optimizer updates。论文明确说明：**除非另有说明，公开数字来自 single run。**

| Backbone | Dataset | MiniOneRec-style GRPO HR@5 | DASO HR@5 |
|---|---|---:|---:|
| 1.5B | Industrial & Scientific | 0.1321 | **0.1421** |
| 1.5B | Office Products | 0.1420 | **0.1639** |
| 3B | Industrial & Scientific | 0.1334 | **0.1476** |
| 3B | Office Products | 0.1313 | **0.1683** |

完整 DASO 在 12 个公开指标中 9 个最好，并在 11/12 指标上超过 MiniOneRec-style GRPO。Office Products 的提升最大，而这个数据集恰好有更高比例的 no-prefix hard prompts。

### 为什么重要

DASO 把推荐 RL 中的一个问题讲得非常具体：**Reward sparsity 有时不是 reward function 本身太差，而是 policy 根本没有 coverage 到 reward 有区分度的区域。**

这和树结构输出尤其相关。Semantic ID、SQL AST、Tool Plan、层级动作序列都有类似特征：前面走错分支，后面再多 rollout 也只是重复探索同一片 reward desert。

因此训练监控不应只看平均 reward 和 KL，还应该直接记录：

```text
target_prefix_depth_distribution
all_zero_reward_group_ratio
group_reward_variance
reachable_target_rate
```

### 可信度与局限

论文自己明确提醒，MiniOneRec + GT、Sibling-GRPO 与 DASO 的比较是**完整训练框架比较**。DASO 同时包含动态分配、SID-prefix credit、SFT anchor 和 bounded guidance，不能把全部提升归因于“difficulty-aware allocation”单一组件。

它也不再是严格意义上的纯 on-policy rollout：guided completion 使用 target prefix，属于训练期 oracle information。当前结果是公开离线 benchmark + 内部数据，没有线上 A/B；single-run 结果也意味着方差仍未知。

### 最值得继续追踪

下一步最有价值的是把 oracle target prefix 换成 **retriever / beam recovery / verifier 选出的 prefix**。如果仍能恢复大部分收益，DASO 才更接近通用 structured-RL recovery，而不是依赖训练标签的特定技巧。

## 5. Utility Under Attack：Memory Poisoning 不需要 Prompt Injection

> **一句话结论：** 一条“语法正常、没有任何恶意指令、只是事实错误”的 Memory，content safety detector 没有理由仅凭文本知道它是假的；长期 Agent 因此必须把事实真实性与来源治理放进 Memory lifecycle。

**论文：** [Utility Under Attack: Agent Memory Poisoning and the Limits of Content Screening and Provenance Ranking](https://arxiv.org/abs/2608.21230)

### 发生了什么

作者向 LongMemEval corpus 加入普通的错误事实陈述：没有隐藏指令、没有 trigger、没有针对 retriever 做 embedding 优化，也没有迭代攻击。只污染 **1.2% corpus**，accuracy 就从 0.850 降到 0.300。

更关键的是，系统原本有一套四阶段 write-time content screening：它在 indirect prompt injection 上 recall 为 0.832，而且对含 trigger-word 的 benign text 只误报 1.5%。面对 360 条纯事实型 poison，这套 screening **拒绝了 0 条**。

原因并不神秘：一句“东京是法国首都”和一句“东京是日本首都”在形式上都可以是正常陈述。没有外部 grounding，单看文本无法稳定判断哪句为假。

### 关键结果

论文随后测试 provenance-weighted retrieval：

| 配置 | Accuracy | Poison in Context | Poison Ranked #1 |
|---|---:|---:|---:|
| Clean | 0.850 | 0.0% | 0% |
| Poisoned，无防御 | 0.300 | 20.0% | 100% |
| Trust weight = 0.15（原默认） | 0.317 | 20.0% | 87% |
| Trust weight = 0.35（加强） | 0.475 | 8.8% | 2% |

原默认权重相对无防御的差异不显著（$p=0.80$）。把 trust weight 调高确实能压制 poison，但代价也非常尖锐：当真正的 answer-bearing evidence 本身来自 untrusted channel 时，强 provenance penalty 让 evidence recall 直接掉到 **0**，accuracy 从 0.8583 降到 **0.0417**。

### 为什么重要

这里暴露的是两个不同安全层：

```text
内容安全：
“这段文本是否包含恶意指令或危险 payload？”

事实安全：
“这段文本陈述的事实是否真实、是否仍有效、来源是否可信？”
```

Prompt Injection detector 主要解决第一类，不能被期待自动解决第二类。

论文也给出了另一个很实用的设计警告：把 provenance 作为一个简单 additive score，容易出现“太弱时攻击者靠相似度把它压过去；太强时合法 untrusted evidence 永远进不了 top-k”的两端失效。

### 可信度与局限

作者对局限写得相当明确。攻击目前是 non-adaptive，论文认为这更像 attack floor，而不是最强攻击；但这仍只在一个 retriever、一个 embedding 分布和一个 reader 组合上测试。

作者提出把 provenance 从 additive weight 改成 **bounded occupancy constraint**，例如限制 untrusted memory 在 retrieved context 中最多占多少比例。不过这只是由实验失败推导出的设计建议：论文明确写明，**该 gate 尚未实现、也没有评测**。因此不能把它当成已验证防御。

### 最值得继续追踪

更靠谱的 Memory security stack 很可能需要同时具备：

- 写入时绑定不可伪造的 source / origin；
- 对高价值事实做外部 grounding 或 cross-source verification；
- 检索时使用 bounded provenance constraints，而不是无限惩罚；
- 对事实更新保留 supersession 与版本；
- 单独监控 integrity failure 和 availability failure。

真正关键的指标不是“poison detection accuracy”，而是 **在保留合法 untrusted evidence 的前提下，能把错误事实暴露压到多低**。

## 6. AgentX：Agentic Inference Benchmark 正从“固定长度吞吐”走向 Session Replay

> **一句话结论：** NVIDIA 这篇文章最值得看的不是 30× headline，而是 AgentX 为什么认为固定 8K input / 1K output 已经不足以代表 Coding Agent 的真实 serving workload。

**技术文章：** [NVIDIA Vera Rubin and Blackwell Set a New Standard for Agentic AI Performance per Watt](https://developer.nvidia.com/blog/nvidia-vera-rubin-and-blackwell-set-a-new-standard-for-agentic-ai-performance-per-watt/)  
**AgentX Dashboard：** [InferenceX Agentic Inference Benchmarks](https://inferencex.semianalysis.com/inference?g_model=Kimi-K3&i_optimal=1&i_seq=agentic-traces)  
**Harness：** [SemiAnalysisAI/agentx-harness](https://github.com/SemiAnalysisAI/agentx-harness)

### 发生了什么

SemiAnalysis 的 AgentX 不再只发送固定长度 prompt。它回放 production-style Claude Code session，保留每一轮的 input/output length、reasoning time、tool-call latency 和不断增长的 context；并通过不同 concurrency 测量吞吐与交互体验之间的 Pareto。

这使 benchmark 能覆盖普通静态请求难以表达的系统行为：

```text
长 context prefill
+ repeated-prefix / KV cache reuse
+ tool-call gap
+ sub-agent burst
+ dynamic concurrency
+ MoE distributed serving
```

NVIDIA 文章明确说，InferenceX 过去的固定 8K/1K scenario 已被降到 maintenance mode，因为它越来越不能代表 stateful Agent workload。

### 关键结果

NVIDIA 报告的硬件数字包括：

- Vera Rubin NVL72 preview：在 AgentX 的 DeepSeek V4-Pro workload、160 tokens/s/user 时，最高 **30×** GB300 NVL72 的 throughput per provisioned megawatt；
- GB300 NVL72：DeepSeek V4 Pro 1.6T 上最高 **15×** H200 NVL8 的 throughput/MW；
- 同一对比中，GB300 最高报告 **10× 更低 cost per million tokens**；
- Kimi K3 2.8T 上，GB300 NVL72 在可比 interactivity 下报告约 **80×** H200 NVL8 的 throughput/MW。

### 为什么重要

Agent serving 的真实约束不是单次 token throughput，而是“有多少长期 session 能同时驻留、反复复用 prefix，并在工具间歇后快速恢复推理”。

因此未来做 Agent inference benchmark，至少应该同时报告：

```text
E2E latency
TTFT
tokens/s/user
throughput per power budget
prefix-cache hit rate
KV residency / eviction
session concurrency
tool-gap recovery
```

同一个 kernel 在固定 8K/1K 上更快，并不保证真实 Agent session 更快；cache eviction、prefill/decode 调度和 session-aware routing 可能占据更大份额。

### 可信度与局限

这里必须严格区分 benchmark 设计与硬件结论。AgentX 的 session-replay 方法本身值得关注；但 **Vera Rubin 的 30× 数据是 NVIDIA 自己测得的 preview result，文章明确写着 pending SemiAnalysis review**。

此外，GB300 NVL72 与 H200 NVL8 在整机拓扑、GPU 数量、scale-up fabric、精度和 serving stack 上并不是“只换一块芯片”的单变量实验。`throughput per megawatt` 是 AI-factory 级系统指标，适合评估部署经济性，却不能直接解释成单 GPU 性能倍数。

### 最值得继续追踪

等 SemiAnalysis 独立提交和更多厂商结果进入 AgentX 后，重点看 **相同 model、相同 precision、相同 Agent trace、相同 UX target** 下的 P50/P95 TTFT、session residency 和 energy-normalized throughput，而不是只看一个最优 operating point 的峰值倍数。

## 今日值得收藏的代码 / 学习资源

**[AUSO / Action-Skill](https://github.com/JordanSancholhz/Action-Skill)** 已公开训练脚本、ALFWorld / WebShop / Search-QA 配置和 Skill generation 相关代码。它基于 `verl` / `verl-agent`，适合直接追 action-level JSD signal 是如何进入训练 loss 的。

**[DASO](https://github.com/LucasXinYu/DASO)** 当前仓库规模还很小，但已经公开 config、RQ/SID 相关代码和 logit processor。对 Generative RecSys，更值得先复现它的 `prefix-depth distribution` 诊断，再决定是否上完整 guided rollout。

**[DreamBench-SWE](https://arxiv.org/abs/2608.20664)** 是今天值得收藏的 Memory benchmark。它专门测试跨 session 软件任务中“后续任务需要依赖先前 session 里不可从当前上下文推断出的证据”，并用 executable hidden oracle 打分。其 preregistered successor 中，无 external memory 为 21/180，deterministic verbatim event memory 为 82/180，一个固定的 hosted Mem0 literal-storage 配置为 97/180。作者明确提醒，这些结果不能被解读成对所有 Memory backend 的机制性优劣证明。

**[EnSI-RAG](https://github.com/RamonMeng/EnSI-RAG)** 把长文档索引从 raw chunk 改成 entity-centered `(entity, type, semantic-category, value)` record，同时保留回原始 passage 的 provenance。论文在 Loong / Oolong 上报告平均 accuracy 78.24，相对其引用的 published baseline 高 6.62 个点；这里是与已发表基线分数的比较，不是所有方法在同一代码路径重跑，因此更适合作为结构化索引思路，而不是直接把 6.62 当成严格 head-to-head 增益。

**[AgentX Harness](https://github.com/SemiAnalysisAI/agentx-harness)** 值得做推理系统的人直接看。它把“Agent workload”从一句营销词变成可重放的多轮长 context trace，可以用来检查自己的 vLLM / SGLang / TensorRT-LLM serving stack 在 cache reuse、TTFT 和并发上的真实行为。

## 今日最值得花 30 分钟阅读的一项

**首选 [Don't Solve, Just Compare: Tiny Advisors for Runtime Intervention in LLM Agents](https://arxiv.org/abs/2608.21027)。**

它最值得看的不是“0.5B 模型帮助 35B / 更大模型”这个 headline，而是一个更一般的系统设计原则：

> **不要让辅助模型承担它不需要承担的完整任务能力；把它训练成一个更窄、可验证、信息密度更高的判断器。**

建议 30 分钟按这个顺序读：

1. 先看为什么 failure detection 不够——发现动作可能错之后，还必须提供 recovery direction；
2. 再看 same-prefix counterfactual pair 如何构造 pairwise supervision；
3. 重点看 `Absolute-Q vs Pairwise`、`Forced vs Constructive` 的 $2\times2$ ablation；
4. 最后看 1.38× 平均 runtime overhead，判断这是不是自己场景里可接受的 reliability premium。

这篇最有价值的地方，是它给“强 Actor + 小监督器”提供了比“再部署一个同等级 Critic”更有经济性的中间路径。

## 今日可立即实践的一件事

给现有 Tool Agent 做一个 **Local Alternative Comparator** 小实验，不需要先训练 0.5B 模型。先用当前强模型或便宜 Judge 验证“局部比较”这个接口值不值得做。

从 20–50 条失败 trajectory 中，挑出可以明确定位的 decision point。对每个状态保存原 action，再生成 2–3 个 alternative：

```python
sample = {
    "state": state,
    "original_action": action,
    "alternatives": alternatives,
    "final_outcome": outcome,
}
```

然后分别测试两种干预：

```text
A. Forced
   Comparator 选一个 action，直接执行。

B. Advisory
   Comparator 只告诉 Actor：
   “原 action 可能不是最佳；候选 B 更值得考虑。”
   然后让 Actor 重新规划。
```

至少记录：

$$
\mathrm{InterventionPrecision}
=
P(\text{原 action 确实更差}\mid \text{触发干预})
$$

$$
\mathrm{NetUtility}
=
\Delta \mathrm{SuccessRate}
-
\lambda \cdot \Delta \mathrm{RuntimeCost}
$$

以及：

```text
intervention_rate
recovery_success_rate
forced_vs_advisory_gap
extra_model_calls
extra_tokens
end_to_end_latency
```

**停止条件：** 如果 Advisory 相比 Forced 没有更高成功率，或者每 1 个百分点的 success gain 要付出超过业务可接受的 latency / token 成本，就不要急着训练专门 comparator。先优化 candidate generation 和 intervention threshold。

反过来，如果“只给局部建议、让 Actor 自己重规划”稳定优于“让 Judge 直接接管动作”，那么再把 pairwise comparison 数据蒸馏到 0.5B–1B 小模型，才有明确的工程价值。

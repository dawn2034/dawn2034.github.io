# 每日 AI 技术简报｜2026-08-18

本期以过去一周已经能够用论文原文、官方工程文章稳定核验的高信号工作为主。今天最值得重视的变化，不是某个 benchmark 又涨了几个点，而是几个常用叙事正在被重新校准：**On-Policy Distillation 的 pass@1 提升未必等于能力边界扩张；大模型教师的价值可以通过层级 Memory 而不是改权重转移给小 Agent；多智能体 RL 的高 reward 与真实协作可能完全脱钩；Semantic ID 的“可组合”也不等于真正能覆盖未来冷启动 item。**

## 今日核心判断

- **OPD 项目不能再只看 pass@1 / avg reward。** 如果小采样预算变强、但大 $K$ 的 pass@K 下降，更合理的解释是采样分布被重塑，而不是学生获得了新的 reasoning capability。
- **Agent distillation 的一个现实方向，是把 teacher trajectory 编译成结构化外部 Memory。** 对 4B–8B 小模型，这可能比要求小模型自己积累成功轨迹更有效，也更容易回滚和审计。
- **Multi-Agent RL 必须把“团队得分”和“合作质量”分开评估。** 一个 Agent 学会把全部任务包办，同样可能让总 reward 上升。
- **Semantic ID 的 token recombination 不是 open-world recommendation。** 新 item 一旦包含从未见过的 atomic token 或缺乏支持的 SID path，生成模型可能从结构上就难以到达它。
- **RAG 防投毒目前仍是安全—成本 Pareto。** leave-one-out counterfactual 检测可以很强，但如果每次查询都要多次完整生成，吞吐和延迟代价不能忽略。
- **Agent serving 的 context architecture 本身就是性能工程。** 稳定、append-only 的 prefix、确定性的 tool 排序和按需加载工具，会直接影响 prompt-cache 命中和重复计算成本。

## 1. OPD 的“幻觉式蒸馏”：pass@1 变强，不代表 reasoning boundary 真的变宽

**论文：** [Towards Understanding On-Policy Distillation through the Lens of Test-Time Scaling](https://arxiv.org/abs/2608.11829)

这篇论文直接挑战了一个很常见的解释：学生在 On-Policy Distillation（OPD）后 benchmark 更高，所以它从更强 teacher 那里“学会了原本不会的能力”。作者没有只看单次采样，而是逐步增加 test-time sampling budget $K$，同时观察 `pass@K` 和 `avg@K`。

这两个指标回答的是不同问题。可以粗略理解为：

$$
\mathrm{pass@K}=P(\text{K 次采样中至少一次正确})
$$

而：

$$
\mathrm{avg@K}=\frac{1}{K}\sum_{i=1}^{K}\mathbf{1}[y_i\ \text{correct}]
$$

前者在大 $K$ 时更接近“这个问题是否仍位于模型可到达的解空间内”，后者更接近随机采样一次时拿到正确答案的平均概率。

论文观察到一个很关键的分叉：OPD 后模型在各个采样预算下的 `avg@K` 普遍更好，但 `pass@K` 的优势会随着 $K$ 增大逐渐转回 pre-OPD base model。作者进一步用 `pass@1024` 做 problem-level solvability 判断，发现**原本可解但训练后变不可解的问题，多于原本不可解但训练后新学会的问题**。因此作者把这种现象称为 “illusory distillation”：OPD 更像把概率质量重新集中到一批更常见、更容易采到的正确路径，而不是稳定扩大能力边界。

### 为什么重要

这会直接改变 OPD / self-distillation 项目的实验设计。只报告 pass@1、greedy accuracy 或平均 reward，无法区分两种完全不同的进步：

```text
A. 原本会，但正确轨迹概率很低 → 训练后更容易采到
B. 原本不会 → 训练后真的出现新的可解轨迹
```

两者对模型长期能力、test-time scaling、探索多样性和后续 RL 的意义完全不同。

### 可信度与局限

证据目前主要来自数学推理设置，且 `pass@1024` 仍然只是有限采样预算下对“能力边界”的代理指标，不应把它理解成严格的理论能力边界。论文的结论更准确地说是：**在这些模型、数据与 OPD 配置里，单纯用小 $K$ 性能去推断 capability transfer 会过度乐观。**

### 最值得继续追踪

真正值得研究的是：能否在保留 OPD sampling-efficiency 收益的同时，不压掉那些低概率但有效的 reasoning modes。可能的方向包括 on/off-policy 混合、explicit diversity regularization、rare-path retention，以及直接把 large-$K$ capability retention 纳入训练或 early-stop 标准。

## 2. Agent Memory Distillation：把强 Teacher 的轨迹“编译”为小 Agent 可复用的层级记忆

**论文：** [Agent Memory Distillation: Empowering Small LLM Agents with Hierarchical Teacher Memory](https://arxiv.org/abs/2608.07169)

Agent Memory Distillation（AMD）走了一条和参数蒸馏不同的路：**不训练 student 权重，而是从强 teacher 的成功工具调用轨迹中提炼结构化 Memory，再让小 Agent 在执行时使用。**

作者把 Teacher Memory 拆成三层：

```text
Workflow Memory
  └─ 任务级策略：整体应该按什么顺序解决

Subtask Memory
  └─ 中等粒度示例：某类局部目标具体如何完成

Function Memory
  └─ 函数级约定与坑：参数怎么填、常见调用错误是什么
```

Workflow 与 Subtask Memory 在任务开始时主动注入；Function Memory 则在工具调用失败时按需检索。作者用 GPT-5-mini 作为 teacher，在四个 4B–8B student 上测试，报告 AppWorld、BFCL V3、ToolSandbox 平均准确率分别提升 **27.2、11.2、3.4 个百分点**；其中 Subtask Memory 的贡献最大，而且 4B 级小模型受益最明显。

### 为什么重要

这说明“蒸馏 Agent 能力”不一定非要把 teacher 的知识塞进 student 参数。对工具 Agent，很多可迁移知识本来就是程序化或半结构化的：调用顺序、异常恢复、参数模式、任务分解。这些知识以外部 Memory 保存，往往比权重更新更容易版本控制、回滚和审计。

可以把它看成一种外部化的 capability transfer：

$$
\text{Small Agent Capability}
=
\text{Base Model}
+
\text{Teacher-Compiled Memory}
$$

### 可信度与局限

这篇论文目前仍是 under review 的预印本。三个 benchmark 都属于相对可控的 tool-use 环境，不能直接推断到开放网页、企业 API 或强非平稳环境。另一个现实问题是 Memory 本身也可能过期、相互冲突或被错误 teacher trajectory 污染；“training-free”不意味着没有维护成本。

### 最值得继续追踪

下一步真正关键的是 Memory lifecycle：来源 provenance、版本、适用范围、TTL、冲突合并和回归测试。只要这些机制缺失，teacher memory 越多，系统也可能越难治理。

## 3. Multi-Agent GRPO：团队 reward 上升，可能只是一个 Agent 把活全干了

**论文：** [Training Small LLMs as Spatial Multi-Agent Policies](https://arxiv.org/abs/2608.01425)

这项工作先解决小 LLM 在空间协作环境里“根本不会行动”的问题。直接让冻结的小模型选择低层动作时 reward 为 0，因此作者不让 LLM 控制每一个原子动作，而是给它一个由 symbolic planner 执行的短程 `option` 库，例如一段可行、带类型约束的局部行为。每个 Agent 再用自己的 LoRA，通过 per-agent multi-agent GRPO（PA-MAGRPO）学习在这些 option 中做决策。

这套抽象把策略空间从：

```text
每一步都预测底层动作
```

变成：

```text
LLM 选择短程 option
→ symbolic planner 执行
→ 环境反馈
→ 下一次 option 决策
```

在三款游戏、四个小模型 backbone 上，方法把原本 0 reward 的冻结模型提升到能完成任务。但论文最有价值的结果反而不是 reward，而是 behavioral audit：**reward 增长与 cooperation 可以脱钩。一个 Agent 可能学会把任务几乎全部包办，另一个 Agent 基本闲置，团队分数仍然很好。只有任务结构强迫协作时，真正的 cooperation 才出现。**

### 为什么重要

这对所有 Multi-Agent RL 都是一个提醒：共同 reward 只测“团队有没有拿到结果”，不测“系统是否形成了我们想要的协作结构”。如果目标是训练多角色 Agent，至少还应该记录角色分工、贡献度、行动覆盖率和 workload balance。

### 可信度与局限

论文证据来自空间协作游戏，而且 symbolic option library 本身显著缩小了原始动作空间。它证明的是“合理的中层动作抽象 + MARL 可以让小 LLM 学会有效策略”，而不是证明这种方案能够直接扩展到开放式软件 Agent 或现实多 Agent 组织。

### 最值得继续追踪

建议未来把 Multi-Agent eval 拆成两层：task reward 与 cooperation metrics。尤其应该观察单 Agent ablation、per-agent contribution、role entropy，以及把某个 Agent 移除后团队性能下降多少。

## 4. Semantic ID 冷启动边界：token 可重组，不代表新 item 真正可达

**论文：** [Can Generative Recommendation Reach Cold Items? A Temporal Perspective on Semantic-ID Generation](https://arxiv.org/abs/2607.21101)

Semantic-ID generative recommender 的一个直觉优势是：item 不再是完全独立的 ID，而是由共享语义 token 组成，因此理论上可以把见过的 token 重新组合成训练期没出现过的新 item。论文指出，这个推论只在相对封闭的 token 空间里成立。

作者改用 absolute-time protocol，把训练期 item 与未来出现的新 item 真正按时间拆开，并在 token 层诊断 target 是否可达。结果是：如果未来 item 的 SID 主要由已经观察过的 token 和受支持的 prefix 构成，模型确实有时能够命中；但一旦出现**未见 atomic token**或**缺乏支持的 SID path**，模型会明显失败。

这说明 SID generation 更像一个层级语义桶：

```text
早期 token → 选择粗粒度语义区域
后续 token → 逐步收窄到具体 item path
```

“能够重组旧 token”与“能够开放式生成未来 catalog”不是一回事。

### 为什么重要

生成式推荐如果要真正替代传统 candidate retrieval，就必须回答一个很现实的问题：**刚入库、没有行为历史的新 item，模型在解码空间里到底有没有路径到达？** 如果它的 atomic token 本身没有被训练过，或者 prefix 在训练期几乎没有支持，后面的 decoder 再强也可能无济于事。

一个更值得监控的量不是只有 NDCG，而是：

$$
P(\text{target reachable at depth }d)
$$

并按 `all-token-seen / any-token-unseen / prefix-seen / prefix-unseen` 分桶。

### 可信度与局限

这篇论文主要是在特定 SID-based generative recommendation 设置下做机制诊断，不意味着所有 Generative RecSys 都有同等冷启动问题。文本条件生成、动态编码或 hybrid retrieval + generation 可能绕开部分边界。

### 最值得继续追踪

我会重点看三类方案：更独立、可扩展的 SID 空间；用动态文本内容补足冷 item 表征；以及从“生成唯一 SID”改为 scoring-based / hybrid interface，让冷 item 不必先通过固定离散 token 路径才能进入候选集。

## 5. RAGuard：RAG 投毒防御可以很强，但 6× Generation Cost 不能被藏起来

**论文：** [RAGuard: A Layered Defense Framework for Retrieval-Augmented Generation Systems Against Data Poisoning](https://arxiv.org/abs/2607.26339)

RAGuard 做了两层防御。第一层对 dense retriever 做 adversarial fine-tuning，让它学会下调 fabricated facts、contradictions 和 reasoning traps 等合成毒文档。第二层 ZKIP（Zero-Knowledge Inference Patch）完全不依赖 poison label、正确答案或模型内部状态，而是对每个检索文档做 leave-one-out generation：删除某一文档后重新生成，如果答案语义和输出熵发生异常大变化，就把该文档视为可疑。

论文在被污染的 Natural Questions 上测试 5%–30% poison ratio，报告 ZKIP 在其测试攻击配置下把 measured attack success rate 压到 **0.000**，同时 Recall@5 与 clean-corpus baseline 相差不超过 0.03。

但代价同样明确：如果 top-$k$ 为 5，需要原始生成加 5 次 leave-one-out，总共 **$k+1=6$ 次 generator pass**。

### 为什么重要

ZKIP 的思路值得关注，因为它利用的是模型自身对 evidence 的 counterfactual sensitivity，而不是要求维护一套完美的可信知识库。它提供了一个可以用于 closed-source generator 的黑盒信号。

### 可信度与局限

“ASR = 0”只对论文覆盖的攻击构造成立，不能解读成已经解决 RAG poisoning。自适应攻击者可能专门优化“删掉任一单篇文档都不产生明显答案变化”的协同式毒文档。更现实的瓶颈是 6× generation overhead；对高 QPS 在线 RAG，这往往不可接受。

### 最值得继续追踪

真正值得落地的是近似版本：先用低成本 classifier / retriever signal 筛掉绝大多数正常 query，仅对高风险样本触发 counterfactual generation；或者蒸馏 ZKIP 的 leave-one-out 信号，训练一个便宜的 poison-risk estimator。

## 6. 值得精读的工程资源：Agent 的“上下文设计”就是 Serving 性能设计

**官方工程文章：** [How GPT‑5.6 fuses frontier intelligence with frontier efficiency](https://openai.com/index/gpt-5-6-frontier-intelligence-efficiency/)

这篇 OpenAI 工程文章里，对 Agent 开发最有复用价值的不是某个模型 benchmark，而是 harness 如何减少**循环中的重复成本**。一次复杂 Agent turn 可能包含几十次 model request；任何每次多付一点的 context、serialization 或 cache miss，都会被循环次数放大。

文章给出了三个很实用的设计原则：

```text
1. Deferred discovery
   不要把所有 tool / MCP / skill 一次性塞进 context，只在需要时暴露。

2. Cap tool output
   避免单次工具输出无意中吞掉大段 context；文章称默认上限为 10,000 tokens，除非模型另行请求。

3. Preserve exact prefixes
   model-visible history 保持 append-only；tool definition 使用确定性顺序；approval policy 等运行时配置放在执行层，而不是反复改 tool schema。
```

第三点尤其容易被低估。Prompt cache 的前提不是“语义差不多”，而是前缀足够稳定；工具列表换个顺序、在历史中间插入一条状态、动态改 schema，都可能让本可复用的 prefix 失效。

### 为什么重要

对 Agent，成本并不是：

$$
\text{Cost}=\text{一次模型调用成本}
$$

而更接近：

$$
\text{Total Cost}=\sum_{t=1}^{T}(\text{context}_t+\text{generation}_t+\text{tool overhead}_t)
$$

所以 context bloat 和 cache instability 会随着 Agent loop 长度不断放大。

### 可信度与局限

文章中的性能数字——例如端到端 serving cost 降低 20%、draft-model 改进带来超过 15% token-generation efficiency 提升——是 OpenAI 对内部生产系统的自报告结果，外部无法完整独立复现，而且收益高度依赖具体 workload。更值得直接借鉴的是可验证的工程原则，而不是照搬百分比。

### 最值得继续追踪

如果在做 Agent serving，建议把 `prompt_cache_hit_rate`、`prefix_churn_tokens`、`tool_schema_tokens`、`tool_output_tokens` 和 `model_calls_per_task` 放到同一张 dashboard。很多“模型慢”最后会发现其实是 harness 反复让模型重读几乎相同的上下文。

# 今日最值得花 30 分钟阅读的一项

首选 **[Towards Understanding On-Policy Distillation through the Lens of Test-Time Scaling](https://arxiv.org/abs/2608.11829)**。

它值得读，不是因为“OPD 不行”，而是它迫使我们把一个常见实验结论拆得更细：**模型在小采样预算下更容易答对，与模型拥有更宽的可解问题集合，是两回事。**

建议按这个顺序读：先看不同 $K$ 下 `pass@K` 与 `avg@K` 的分叉；再看 `pass@1024` 的 learned / forgotten problem 分析；然后看训练过程里 large-$K$ capability 何时开始下降；最后看 off-policy distillation 与其他 OPD variant 的对照。

如果正在做 On-Policy Self-Distillation，这篇论文会直接改变实验面板和 early-stop 标准，比再抄一个 loss function 更有价值。

# 今日可立即实践的一件事

给任何 OPD / self-distillation 实验补一个 **Capability-Retention Dashboard**。不要只保存最终 checkpoint 的 pass@1，而是在训练过程中固定一组 probe problems，对同一 checkpoint 评估：

```python
K_LIST = [1, 2, 8, 32, 128, 512]

for ckpt in checkpoints:
    for k in K_LIST:
        log_pass_at_k(ckpt, k)
        log_avg_at_k(ckpt, k)

    classify_problem_transition(
        base_model,
        ckpt,
        large_k=512,
        labels=["retained", "learned", "forgotten", "never_solved"],
    )
```

再增加两个诊断量：

$$
\mathrm{NetCapabilityGain}(K)
=
\mathrm{LearnedRate}(K)-\mathrm{ForgottenRate}(K)
$$

和：

$$
\mathrm{SamplingEfficiencyGain}(K)
=
\mathrm{pass@K}_{\mathrm{OPD}}-\mathrm{pass@K}_{\mathrm{Base}}
$$

如果出现：

```text
pass@1 ↑
avg@K ↑
large-K pass@K ↓
forgotten > learned
```

就不要把结果写成“teacher 成功扩展了 student capability”。更准确的描述是：**OPD 改善了已有能力的采样效率，但同时可能收窄了低概率 reasoning modes。** 此时优先检查 early stopping、on/off-policy mixing、diversity regularization 或 rare-path retention，而不是继续盲目增加训练步数。

今日主线： Code-Derived RL Environments · Procedural Memory Evolution · Calibrated OPD · Stochastic Speculative Decoding · Heterogeneous Retrieval · Verifiable Auto-Research

arXiv 最新常规公告批次为 2026 年 9 月 21 日：cs.AI 125 条、cs.CL 87 条、cs.LG 149 条、cs.IR 8 条；分类之间存在大量交叉收录，不能直接相加。今天真正值得连起来看的变化，是模型能力之外的“训练与运行基础设施”正在成为主要杠杆：代码本身可以被批量转成 RL 环境；冻结模型可以靠持续演化的程序化技能获得长期适应；OPD 开始过滤 Teacher 自身的行为漂移；投机解码开始正面处理随机采样；工业检索则把建模深度与库存广度分别放到 GPU 和 CPU 上；Auto-Research 进一步强调，自动实验只有在比较协议本身可验证时才有科学意义。

今日核心判断

  1. Coding Agent RL 的瓶颈正在从“没有足够 Issue/PR 数据”转向“能否把任意代码库稳定编译成可执行环境”。 CodeMidas 只以源代码作为任务特定输入，从 3,185 个开源代码库生成 5,545 个训练任务，并通过泄漏攻击、Verifier 一致性检查和多次 Rollout 过滤环境。MiMo-V2.5 经 GRPO 后，DeepSWE 从 10.0% 提到 21.7%，ProgramBench Almost Solved 从 4.5 提到 21.5，Terminal-Bench v2.1 从 63.7% 提到 72.2%。更有价值的是，3K 个过滤后的高质量任务在三个评测上都优于 8K 个未清洗任务，说明 Environment Quality 仍比粗暴扩量更重要。
  2. Agent 长期适应可以先发生在 Procedural Memory，而不必更新权重。 Designer-RSI 用真实用户流量持续“扩宽”新技能、“加深”已有技能，并通过 matched replay gate 阻止修复一个失败时破坏旧成功案例。五轮后技能库从 76 增至 139；Claude Sonnet 4 的 GenEval2 execution success 从 72.7% 提到 99.3%。但 Qwen3.6-27B 的平均执行成功率反而从 65.5% 降到 63.2%，说明技能演化明显依赖 Backbone 与使用方式，不能把“更多 Skill”当成单调收益。
  3. OPD 的 Teacher–Student discrepancy 并不全是 Student 应该学习的能力差。 Cal-OPD 通过正／负 privileged intervention 估计 Teacher 自身的 self-deviation region，只保留超出该区域的差异用于优化。它只使用原始 Teacher–Student discrepancy 的约 52%–65%，却在两个 Teacher→Student 配置上分别比标准 OPD 平均高 2.3 和 3.1 points；同时抑制标准 OPD 的超长回答膨胀。这个结果进一步削弱了“Teacher 信号越多越好”的默认假设。
  4. 动态树投机解码在随机采样下的 One-Hot 问题可以通过“构树概率”和“验收概率”解耦来修复。 RheoSampling 给随机采样的 Tail Token 两个身份：Proxy Probability 用于树扩展和剪枝，True Sampling Probability 用于最终验证，再配合 OT Verification 保持 Lossless。收益不是数量级跃升，但在三个 EAGLE-3 设置中 Wall-clock Speedup 均稳定改善，例如 Llama-3.1-8B 从 2.84× 提到 2.93×、DeepSeek-R1-Distill-8B 从 2.89× 提到 2.99×。这对真实 Sampling Workload 比只在 Greedy 下展示 Speculative Speedup 更有参考价值。
  5. 超大规模个性化检索不一定需要一个“万能 GPU 检索器”，异构分工可能更经济。 Meta 的 Hybrid GPU–CPU Retrieval 让 GPU 在约十亿级精选池上做深交互检索与 Pre-Rank，让 CPU 在约 20 倍更大的库存上做宽覆盖轻量个性化检索，两路并行后去重进入共享 Ranker。九天线上 A/B 相对旧 CPU-only 系统，DCG@20 +4.51%（95% CI +3.99%～+5.04%），GSRR +2.01%（+1.71%～+2.32%）。这里真正有价值的是把 Modeling Depth 和 Inventory Breadth 当成不同硬件资源问题。
  6. Agentic Auto-Research 的核心风险已经从“Agent 会不会提出好想法”转向“实验比较是否真的成立”。 EvoPilot 的原始自动研究曾把一次 -22pp 的 Offline Hit-Rate 下降错误归因给 Interaction Head，后来发现两组实际输出深度分别为 3000 和 600；修复比较协议后，Matched Comparison 变成 +3.20pp，最终七天随机线上 A/B 得到 +0.66% relative GSRR。自动研究系统若不能锁住 Data Window、Evaluator、Serving Funnel、Artifact Identity 与唯一允许差异，跑得越快越容易高效地产生错误结论。

1. CodeMidas：从“代码本身”批量制造 Agent RL 环境

论文：CodeMidas: Scaling Agentic Coding RL Environments from Code Itself

发生了什么

现有 Coding Agent RL 数据大量依赖 Issue、Commit、PR 与人工测试，但这类开发记录只覆盖开源代码的一部分。CodeMidas 反过来从已经实现的功能出发：Agent 阅读代码、提出行为规格、构造执行测试，再把原代码作为 Reference Oracle 检查测试是否真的表达了目标行为。

环境生成后还要经过三层 Rollout 过滤：让对抗 Agent 主动寻找残留答案、缓存或编译产物泄漏；让独立 Reviewer 检查 Agent 实现与测试 Verdict 是否一致；再只保留 Frontier Model 在固定预算下既有成功又有失败的任务，过滤过易、过难和可疑环境。最终得到 5,545 个任务、3,185 个代码库、23 种语言、15 个技术领域。

关键结果

BenchmarkInitial MiMo-V2.5CodeMidas RL变化
DeepSWE10.0%21.7%+11.7pp
ProgramBench Almost Solved4.521.5+17.0pp
Terminal-Bench v2.163.7%72.2%+8.5pp
CodeMidas Val35.0%44.7%+9.7pp

规模实验同样重要：1K → 3K → 5,545 个高质量任务时，DeepSWE 分别为 17.57、19.05、21.70；完整 5K 高质量集在 SWE-bench Pro、DeepSWE、CodeMidas Val 上均超过一个约 8K、但没有环境清洗和 Post-Rollout Filtering 的数据集，甚至 3K 高质量子集也全面超过 8K 未清洗集。

为什么重要

如果这种 Environment Compiler 能稳定扩展，Coding RL 的数据上限就不再被 Issue/PR 数量直接限制。任何实现了明确行为的开源项目，都可能被转成“需要重新实现某段行为、且能通过执行验证”的训练环境。

另一个值得注意的行为变化是，训练后模型在 held-out 任务上会更早、更广地探索代码库，并使用更多不同的自验证命令。它说明 RL 获得的并不只是某一批测试的模式记忆，至少部分策略变化迁移到了外部 Coding / Terminal 任务。

可信度与局限

证据来自一个训练 Backbone（MiMo-V2.5），独立模型复现仍缺失。论文明确验证训练任务与五个 Benchmark 的任务集合 disjoint，但这不能自动等价为所有上游代码来源都不存在更广义的代码级重叠。

Verifier 依然是核心风险。CodeMidas 已经用 Leakage Attack、Solution Review 和 Outcome Filtering 做了比常规合成数据更严格的控制，但自动生成的行为规格与测试仍可能只覆盖原系统的一部分语义；“可执行”也不等于“规格完整”。

最值得继续追踪

看数据与 Environment Builder 是否完整开放，以及换成 Qwen、DeepSeek、Llama 系 Coding Backbone 后是否保持同样 Scaling 趋势。更值得测的是 每新增一个通过质量门的环境，最终带来的外部 Benchmark 增益／构建成本，而不只是总任务数。

2. Designer-RSI：冻结模型，用真实用户流量持续进化 Procedural Memory

论文：Designer-RSI: Evolving Procedural Memory from User Traffic for Agentic Graphic Design

发生了什么

Designer-RSI 不更新模型权重，而是让一个通过 230+ 工具操作专业设计软件的 Agent 维护自然语言 Procedural Skill Bank。系统有两类变化：Widening 从反复出现但尚未覆盖的子任务中增加新技能；Deepening 对已有技能的成功／失败执行做对照，修订步骤、约束和边界条件。

新技能或修改不会直接进入生产 Memory。Matched Replay Gate 要求候选既修复目标失败，又不能破坏已有成功案例；不满足就拒绝写回。这使 Skill Bank 更接近“带 Regression Test 的可执行知识资产”，而不只是不断累积的 Prompt 笔记。

关键结果

五轮演化覆盖 1,406 个真实用户 Brief、1,869 条自动评分轨迹，技能库从 76 增至 139。Claude Sonnet 4 在 GenEval2 上 execution success 从 72.7% 提到 99.3%，generation quality +11.99 points；四个专业设计 Benchmark 上，Evolve 相对 No-Skill Agent 的整体 Pairwise Win Rate 为 Sonnet 61.8%、Opus 4.6 为 67.6%。

200 个 Held-out User Brief 上，只有 Widening 的 Win Rate 为 49.4%，只有 Deepening 为 48.6%，二者联合为 58.5%（p=0.025），说明“补新能力”和“修旧能力”需要同时存在。

为什么重要

长期 Agent 的可塑性未必首先来自在线 Fine-tuning。对于工具稳定、任务模式反复出现、但 Reward 嘈杂且很难写 Programmatic Oracle 的业务，Procedural Memory 是更低风险的更新层：可读、可版本化、可局部回滚，也更容易跨模型迁移。

它还提供了一个比“总结成功经验”更成熟的 Memory 更新范式：每次写入都是一个需要通过回归测试的 Patch。

可信度与局限

收益并非跨 Backbone 单调。论文附录里 Qwen3.6-27B 的平均执行成功率从 65.5% 降到 63.2%，部分 Benchmark 甚至出现明显回退；这直接说明 Skill 的表达形式与使用方式可能绑定模型能力和 Tool Policy。

自动评分与 Pairwise Quality 也仍然依赖模型 Judge，因此没有像 Coding Test 那样的强 Oracle。设计任务本身具有主观性，99.3% execution success 也不能理解成 99.3% 的设计都达到专业审美标准。

最值得继续追踪

关注 Skill Version × Model Version 的兼容性矩阵，以及长期 20–50 轮演化后是否出现 Skill 冲突、检索拥塞和知识陈旧。成熟的 Procedural Memory 系统最终需要 provenance、适用范围、失败反例、回滚点与模型版本一起保存。

3. Cal-OPD：Teacher–Student 差异里也混着 Teacher 自己的偏差

论文：Calibrating Teacher–Student Discrepancy for On-Policy Distillation

发生了什么

标准 OPD 把 Teacher 和 Student 在 Student On-Policy Token 上的 Log-Probability 差异当作训练信号，隐含假设是“差异越大，Student 越值得向 Teacher 学”。Cal-OPD 指出，这个量至少混合了两部分：真正的 Capability Gap，以及 Teacher 因 Context Intervention、措辞、Privileged Information 等产生的 Teacher Self-Deviation（TSD）。

方法通过正、负 Privileged Intervention 测量 Teacher 自己在不同 Context 下会自然漂移多大，估计一个 Self-Deviation Region；只有超出这一区域的 Teacher–Student discrepancy 才进入 OPD 更新。

关键结果

两个 Teacher→Student 配置中，Cal-OPD 的平均分分别为 53.1 和 69.0：相对 Student Baseline +3.9 / +2.4 points，相对标准 OPD +2.3 / +3.1 points，并在 12 个 Benchmark×配置组合中拿到 7 个第一。

更反直觉的是，它只保留约 52%–65% 的原始 discrepancy。标准 OPD 的平均回答长度从约 9.8K 膨胀到 11.8K tokens，而 Cal-OPD 最终约 9.3K；尽管需要额外 Teacher 计算 TSD，论文报告由于轨迹更短，整体训练约 1.26× 更快。

为什么重要

这使 OPD 的问题从“Teacher 比 Student 强多少”进一步变成“Teacher 与 Student 的差异中，哪些差异真的值得继承”。Privileged Teacher 尤其容易因为额外 Context 改变自身语言分布，如果这些变化与任务能力无关，Student 会把 Teacher 的表达偏好、冗长倾向甚至系统性漂移一起学走。

它与近期 Teacher Gating、Temporal Credit、Teacher Retirement 形成一个一致方向：Distillation 的核心不是最大化 Teacher 信号，而是控制 Teacher 信号的价值密度。

可信度与局限

当前主要证据仍是数学推理，环境有清晰答案与稳定 Reward。开放式 Agent 中，Teacher 的“自我偏差”可能发生在 Plan、Tool Choice、Argument、Observation Interpretation 等不同层次，仅用 Token Log-Probability 区域未必足够。

另外，简单按 Discrepancy 大小做 Threshold Filtering 并不能复现 Cal-OPD 的收益；论文的 matched control 最高 52.7，仍低于 Cal-OPD 53.1。这意味着真正重要的是对 Teacher-side variation 建模，而非机械删掉一半 Token。

最值得继续追踪

下一步应看 Tool-Agent OPD：在同一 Student State 上对 Teacher 施加不同但任务等价的 Context Intervention，判断哪些 Action Token 的 Teacher 信号稳定、哪些主要反映 Teacher 自身 Prompt Sensitivity。

4. RheoSampling：随机采样下，动态树不必退化成 One-Hot

论文：RheoSampling: Resolving the One-Hot Dilemma in Stochastic Dynamic-Tree Speculative Decoding

发生了什么

EAGLE-2/3 一类 Dynamic-Tree Speculative Decoding 在 Greedy 模式下通过 Top-K 扩展和全局剪枝构造高质量树，但在温度 $T>0$ 的随机采样下，候选生成与验证共用同一概率语义，容易把 Draft Distribution 压成近似 One-Hot，尾部概率质量无法真正进入树。

RheoSampling 把两个角色拆开。每个 Candidate Pool 先保留 Top-$m$ 的确定性 Token，再从剩余 Tail Distribution 随机抽一个 Token；这个 Token 在构树时拿一个与真实身份解耦的 Proxy Probability，保证它不会因为自己的采样概率被剪掉，在验证时又回到 True Sampling Probability。配套 RheoVerification 使用 Optimal Transport 重新分配验收概率，并证明 Lossless。

关键结果

Target ModelEAGLE-3 Top-K SpeedupRheoSamplingMean Acceptance Length
Vicuna-13B3.37×3.43×5.75 → 5.89
Llama-3.1-8B-Instruct2.84×2.93×5.04 → 5.25
DeepSeek-R1-Distill-Llama-8B2.89×2.99×4.99 → 5.21

Llama-3.1-8B 的 Acceptance Length 提升 4.2%，最终 Wall-clock Speedup 提升 3.2%，差额就是随机 Probe、Sampling 与 Verification 的额外开销。

为什么重要

很多 Speculative Decoding 结果只在 Greedy 下漂亮，但真实聊天、创作、Agent Exploration 通常不会永远使用 $T=0$。RheoSampling 正面处理了一个生产上更实际的问题：怎样在保持目标采样分布严格不变的前提下，让动态树仍然覆盖概率尾部。

更一般的设计原则是，Tree Construction 的“优先级概率”不一定应该和 Sampling / Acceptance 的“统计概率”复用同一个对象。把二者解耦，可以同时保留结构效率与概率正确性。

可信度与局限

收益稳定但幅度不大，现有 Wall-clock 改善大致是几个百分点，而非新的数量级。实验又以 EAGLE-3 为基础，是否同样适用于其他 Draft Head、Self-Speculation 或 Production Continuous Batching，需要单独验证。

Top-128 Sparse Draft 能降低采样开销，但 Lossless 结论成立于“Draft 与 Verification 使用同一个截断分布”的定义下；它不等价于相对未截断原始 Draft Distribution 的完全无改变。

最值得继续追踪

关注 vLLM / SGLang / TensorRT-LLM 是否出现工程实现，以及在真实 Temperature、Top-p、Batching、长 Context 下的 Goodput。真正的生产比较应报告 accepted tokens / target forward × p95 latency × sampling fidelity。

5. Hybrid GPU–CPU Retrieval：把“深度”和“广度”交给不同硬件

论文：Hybrid GPU–CPU Retrieval for Personalized Search at Ultra-Large Scale

发生了什么

Meta 将超大规模 UGC 搜索中的矛盾描述为 personalization–scale paradox：更深的用户–Query–Document 交互适合 GPU，但把几十亿到数百亿文档全部放进 HBM 代价过高；CPU 能承载更大库存，却无法在关键延迟路径上运行同样深的 Interaction Model。

系统因此并行运行两条 Path：GPU Path 在约十亿级精选池上完成 Two-Tower Retrieval + Interaction Pre-Ranking；CPU Path 在约 20 倍更大的独立库存上执行轻量个性化向量检索。两路各有独立 Deadline、Version 与 Rollback，返回后按 Document ID 去重，再进入同一个下游 Ranker。

关键结果

九天全系统 A/B 相对旧 CPU-only 配置：

指标Hybrid Lift保守 95% CI
DCG@20+4.51%+3.99% ～ +5.04%
GSRR+2.01%+1.71% ～ +2.32%

单独 Pathway 实验也都是正向：High-depth GPU 的 DCG@20 +0.73%、GSRR +1.04%；Broad-inventory CPU 分别 +3.16%、+1.20%。论文另给出一个 matched broad-vector capacity plan：若让 Accelerator 承担与 CPU 相同的宽库存向量任务，年化 Capacity Cost 约为 CPU 的 4 倍。

为什么重要

这是一种很实用的异构系统思路：不要强迫一个 Retriever 同时在最深的 Model 与最大的 Inventory 上达到最优。 GPU 提供高价值 Query 的建模深度，CPU 提供稀有内容、长尾内容和低频意图所需的库存广度，两者在 Candidate Aggregation 层汇合。

对于推荐系统也有直接类比：高活跃／高价值候选可以走更深的 GPU Path，而超大长尾池用更轻的 CPU / SSD Path 保证召回覆盖；关键是让两类候选最终接受同一个下游价值函数，而非互相替代。

可信度与局限

这是生产 A/B，证据比纯离线 ANN Benchmark 强；同时它改变了 Inventory、Model、Pre-Rank 与 Serving Path，完整 Lift 不能归因到某一个 Kernel 或模型结构。DCG@20 还是模型打分指标，GSRR 才更接近用户侧业务结果。

GPU 的单卡 150–200 QPS、约 30–40ms p99 只覆盖 Model Server，不含网络、聚合与下游 Ranking，不能拿来当完整 Search 请求延迟。

最值得继续追踪

看 Request Router 是否进一步学习“什么 Query 应同时跑两路、只跑 GPU 或只跑 CPU”，把当前 Capacity Control 升级成 Learned Routing。另一个问题是 CPU / GPU Candidate 的 Calibration：不同 Path 输出的候选质量分布如何在共享 Ranker 前保持稳定。

6. EvoPilot：Auto-Research 的最小科学单位是“可验证比较”

论文：Verify, Don’t Trust: Agentic Model Development for Video Discovery Retrieval at Scale

发生了什么

EvoPilot 研究的不是几分钟内修改单个训练脚本的 AutoResearch，而是持续数周、跨训练、发布、索引和线上 Serving 的真实模型研发。它把 Planner、Builder、Worker、Analyst 的角色边界固定下来，所有 Experiment、Artifact、Failure 都保存成 Durable Record；只有通过确定性 Guard 的比较，才能进入下一轮决策。

最典型的事故发生在 Interaction Head。一个早期自动研究流程看到 Offline Hit Rate 下降 22pp，就得出“Interaction Head 有害”；后来发现对照与实验实际经过的 Serving Funnel 不一致，输出深度分别是 3000 和 600。修正 Funnel 后，真正 matched 的 Head-only Comparison 变成 +3.20pp。

关键结果

这场研究持续 37 天、7 个方向，在线 Index 每小时刷新、规模为数亿视频。最终选出的 Interaction-Head Treatment 在单独的七天随机线上 A/B 中带来 +0.66% relative GSRR，随后成为默认配置。

Durable State 还恢复了一次被中断的 Round，Artifact Reuse 避免约 5 GPU-hours。不过只有 9/20 个 Round 拥有完整 Operational Record，因此论文没有把所有 Agent Invocation、Token 或 GPU Occupancy 外推成统一效率数字。

为什么重要

Agent 自动做实验的主要危险，往往是生成一个看起来完整、实际上没有合法 Estimand 的结果。No-op Change、Data Leakage、Evaluator Drift、不同 Funnel、不同 Checkpoint 或不同 Index Snapshot，都可以让“运行成功”与“科学比较成立”完全脱钩。

所以 Auto-Research 的 Harness 应把下列对象设成不可随意修改的协议：Base Artifact、唯一允许差异、Data Window、Evaluator Identity、Serving Path、Randomization Unit、Terminal Artifact。Agent 的创造力可以作用在候选方案上，但不能自由重写判定自己是否成功的测量规则。

可信度与局限

这是非常有价值的生产 Case Study，但不是随机对照的“EvoPilot vs 普通研究团队”实验。十组 clean/fault replay fixture 全部被正确放行／阻断，也不足以估计真实 Field False-Positive / False-Negative Rate。

+0.66% GSRR 是被选模型改动的因果 A/B 结果，不能直接归因成“使用 Agentic Auto-Research 就能提升 0.66%”。论文自己也明确区分了研究流程与最终 Treatment Effect。

最值得继续追踪

关注这类 Experiment Contract 是否形成通用开源框架，特别是对推荐系统的 Offline/Online lineage：数据、模型、索引、Serving Config、Evaluator、A/B Assignment 是否能被一个机器可验证的 Manifest 串起来。

今日值得收藏的代码 / 学习资源

RecreationWorld 是今天很值得直接拉下来的 Agent Environment 项目。它覆盖 Ubuntu、macOS、Windows、Android、Web 五个平台，让 Agent 通过 GUI 探索一个正在运行的 Reference App，再自主决定何时编码、运行、视觉检查和修复；RecreationBench 有 250 个 Held-out Task，Programmatic 与 Visual Assertion 都先在 Reference 上验证。当前 GPT-6 Astra 的宏平均约 58.1%，但只有 2.8% 的任务能通过全部 Programmatic Tests，说明“复刻 UI 外观”与“复刻完整交互行为”之间仍有巨大差距。
论文 · GitHub

ArenaFlow 值得做 Open-ended Agent RL 的团队精读。它先用 Tournament Ranking 得到相对 Trajectory Reward，再把 Credit 向下传播到 Pivotal Step，同时维护带 Utility Attribution 的 Skill Memory；Open-Travel 上 20 个 Training Step 已达到 28.9，而 Trajectory-level ArenaRL 为 14.3，最终约 55.4 vs 35.9。局限是 Structured Reflection 与 Comparison 依赖强 Judge，因此它解决的是“把相对反馈用得更细”，还没有消除 Judge Bias。
论文

AutoViewMem 提供了一个很干净的 Long-Term Memory 设计方向：把 Preferences、Events、Constraints、Temporal Updates 在写入阶段拆成低重叠 Semantic Views，而不是等检索时再用 Router 修复混合表示。论文在 LoCoMo、PersonaMem 上用 Qwen3-8B/14B 报告稳定改进，但摘要没有提供统一 Headline Effect Size，现阶段更适合作为 Memory Schema / Write-Time Disentanglement 的架构参考。
论文

Prediction Dynamics in Depth-Recurrent Language Models 则适合继续跟 Looped / Recurrent-Depth 模型的人。作者分析 Huginn-3.5B 与 Ouro-1.4B 的中间预测轨迹，发现只看“中间答案是否已经等于最终答案”会过度保守；加入 Update Direction 与 Competitor Pairing 后，满足答案保持条件的最早深度还可以再提前总深度的 22.5%–34.4%。这是 Retrospective Analysis，尚未直接证明可以无损地变成在线 Early-Exit Policy。

今日可立即实践的一件事

给现有 OPD / Privileged-Teacher 实验做一个 Teacher Self-Deviation Audit，先判断 Student 正在学到多少真正的能力差，多少只是 Teacher 对 Context 的自然漂移。

对 100–300 条 Student On-Policy Rollout，在完全相同的 Student Token $y_t$ 上，让 Teacher 分别读取：原始 Context、正向 Privileged Context、一个任务相关但措辞不同的等价 Context，以及一个不应改变正确解的 Negative / Control Context。记录：

先计算普通 OPD discrepancy：

\[D_t = \log p_T(y_t\mid c_t)-\log p_S(y_t\mid c_t).\]

再用最简单的诊断量衡量 Teacher 自己对 Context Intervention 的波动：

\[V_t = \max_j\left|\log p_T(y_t\mid c_t^{(j)})-\log p_T(y_t\mid c_t)\right|.\]

不要直接把 $V_t$ 当成 Cal-OPD 的正式实现；先看两个现象：高 $D_t$ Token 中有多少同时拥有高 $V_t$，以及这些 Token 是否真的更集中在最终错误／关键推理位置。再把 Token 按 D_t >> V_t、D_t ≈ V_t、D_t < V_t 分桶，比较它们与 Verifier Outcome、Response Length、后续 Advantage 的关系。

停止条件： 如果 Teacher 的 Context Self-Variation 很小，且高 Discrepancy Token 明显与任务错误对齐，没有必要为了追随新论文引入复杂 Calibration。反过来，如果大批高 Discrepancy Token 主要来自 Teacher 自身漂移，标准 OPD 正在为低价值监督付算力和行为偏置成本，这时才值得实现论文中的 Intervention Region，而不是简单做全局 Threshold Mask。

真正要回答的是：

Teacher 和 Student 不同的地方，究竟是 Teacher 更会做题，还是 Teacher 只是换了说法、换了长度、换了自己的行为模式？

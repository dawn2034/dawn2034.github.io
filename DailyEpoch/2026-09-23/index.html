今日主线： Harness Distillation · Critical-State RL · System-One Memory · Compressed-State Speculation · Semantic ID Reproducibility · Self-Evolution Process Evaluation

arXiv 最新常规公告批次为 2026 年 9 月 22 日：cs.AI 384 条、cs.CL 233 条、cs.LG 426 条、cs.IR 39 条；不同分类存在大量交叉收录，不能直接相加。今天最值得连起来看的变化，是 Agent 系统的“外部脚手架”开始被进一步拆解：Harness 可以在训练期当 Teacher、再被蒸馏进权重；多轮 RL 开始定位真正可训练的关键状态；Memory 控制从通用自回归 LLM 下沉到轻量结构化控制平面；推理系统则要显式维护压缩 Attention 的分支状态一致性。推荐系统侧，Semantic ID 的大规模可复现研究进一步削弱了“某种 Tokenizer / 更长 SID / 更大 Backbone 一定更好”的简单叙事；自我进化 Agent 的评测也开始从最终分数转向长期能力轨迹。

今日核心判断

  1. Harness 可以先作为训练期的“行为教师”，再从部署路径中移除。 Harness-Zero 用一个 harnessing agent 在 Student 每次响应真正执行前进行最小必要纠正，再把这些“在目标 Harness 行为空间内”的轨迹做 SFT。Qwen3.5-9B 在最终只保留极简 mini-SWE-agent Harness 时，三类任务宏平均从 23.3% 提到 44.3%，甚至高于 Base Model 持续挂载优化 Harness 时的 41.7%。这说明部分 Harness 能力可以被内化，但当前证据仍依赖 GPT-5.6 Sol 级别的训练期 Harnessing Agent，成本只是从推理期转移到了数据生成期。

  2. 多轮 Tool-Agent RL 的主要问题之一，是梯度经常落在“看起来有 Reward 方差、实际不可训练”的状态。 Critical-State RL 在固定 Context 下采样不同 Action，再固定 Action 重采样后续 Continuation，用 Nested Sampling 把 Action 引起的 Reward Variation 与下游随机噪声分开；随后只训练被诊断为“局部 Reward 能反映真实影响、且相对 Reference Policy 仍有改善空间”的状态。BFCL v4 missing-function 任务上，训练诊断选中的响应带来约 14 个百分点提升，而训练替代状态持平或更差。

  3. Agent Memory 的高频控制决策没有必要全部走自回归 LLM。 Jev-Mem 把 Memory Typing、关系构建、Query Routing、Retrieval Budget、Candidate Scoring、Adaptive Stopping 等操作交给轻量的 System-One 控制平面，只在复杂证据综合与回答生成时调用 System Two。LoCoMo 上总体 LLM-as-Judge 从最强基线 0.700 提到 0.777，同时 Memory Build 只需 158 秒（最快竞争系统 1,044 秒），平均 Query Latency 0.93 秒（最快 Memory Baseline 1.47 秒）。真正值得追踪的是“哪些 Agent 控制决策可以被降级成有界结构化预测”。

  4. 压缩／稀疏 Attention 让 Tree Speculative Decoding 的难点从“画一棵更宽的树”变成“每条分支的状态必须语义一致”。 DeepSeek-V4-Flash 的 CSA/HCA 会在线产生路径相关的压缩状态，因此不同候选分支不能直接共享写入持久 Cache。新工作通过 Branch-aware Verification、Temporary State Isolation 和 Accepted-path Refresh，把 Tree Speculation 接进 SGLang。D=8 时 Tree Accepted Length 约 2.83–3.41，对比线性 2.39–2.84；Throughput 最多提高约 18.5%。更重要的负结果是，D 超过约 6–7 后 Accepted Length 继续涨，Throughput 基本进入平台期。

  5. Generative Recommendation 的 Semantic ID 没有一个可跨数据集复用的“默认最佳方案”。 新的统一复现实验覆盖 RQ-VAE、OPQ、RQ-Kmeans、Tree、Metadata、End-to-End Tokenization 等多类 SID，并固定 Backbone / Training Protocol 做 SID-only 控制实验。结果显示 RPG、SEATER、LETTER-TIGER 分别在不同数据集占优；SASRec 在 Microlens 和 Yelp 上仍能超过若干生成式方法。SID Length 与 Backbone Scaling 也明显非单调，例如 Video Games 上 RQ-VAE 的 NDCG@10 从 L=12 的 0.0277 降到 L=16 的 0.0244。SID 的局部语义、Codebook 利用率与最终推荐质量之间没有简单一一对应关系。

  6. Self-Evolving Agent 的终点分数会掩盖“学会—遗忘—规则失效”的过程风险。 EvoPathBench 固定 Base Model、Tool 与 Executor，只让 Memory / Skill / Workflow 等持久 Artifact 演化，并在 successive checkpoints 冻结 Artifact 重新测 Generalization、Retention 与 Rule Adaptation。SkillOpt 在近分布上有 +0.763 的学习增益，Transfer 却变成 -0.273；SkillBoost 则为 +1.597 / +0.537。更关键的是，在 Holm 多重校正后没有方法显示可靠的 Rule Adaptation。作者还发现扩大 Candidate Search 能找到更好的候选，却不代表 Acceptance Rule 能选对——当前瓶颈越来越像“如何验收更新”，而不是“能不能生成更多更新”。

1. Harness-Zero：把优化 Harness 变成训练期 Teacher

论文原文：Harness-Zero: Harness Distillation via Agent-as-Harness

发生了什么

Harness-Zero 处理一个越来越现实的矛盾：优秀 Agent 的能力越来越依赖 Tool、Middleware、Skill、Memory 与 Context Management，但最佳 Harness 往往随 Domain、Model 和 Task 改变。把所有 Specialist Harness 永久带到线上，会引入 Routing、Context、Tool Call 和维护成本；只用一个共享 Harness，又会丢掉领域特化能力。

方法先在训练任务上得到优化 Harness $h^\star$，再把其中的 Tool、Middleware、Skill 和 Memory 改写成 Harnessing Agent 的私有 Reference Harness $\mathcal{K}$。Student 始终运行在最终部署要使用的极简 Target Harness $h$ 中。每个 Turn：Student 先提出动作，Harnessing Agent 只查看当前 Student 可见轨迹和 $\mathcal{K}$，在执行前做 Pass / Replace；若 Replace，只做最小完整纠正，并用 Target Harness 真正执行，环境 Observation 再进入 Student 可见 Context。

最终只用这些 Reviewed Rollouts 对 Student 做 SFT。部署时 $h^\star$、$\mathcal{K}$ 和 Harnessing Agent 全部移除，只留下蒸馏后的 Model + Minimal Harness。

关键结果

在 SpreadsheetBench Verified、AppWorld、USPTO Retrosynthesis 三个 Domain 上，Qwen3.5-9B 的宏平均结果为：

设置平均任务表现
Base + minimal target harness23.3%
Base + evolved meta-harness41.7%
Harness-Zero distilled + minimal harness44.3%

训练数据规模并不大：SpreadsheetBench 487 条 Rollout、AppWorld 282 条、USPTO 500 条。另一个 Training-free 对照里，Agent-as-Harness 在六个 Benchmark×Model 组合上平均 81.1%，高于 Code-as-Harness 的 78.1%。Behavioral Analysis 中，蒸馏模型平均恢复了 28 类 Harness-exclusive behavior 中 82.3% 的模式。

为什么重要

过去 Harness 优化与模型训练常被视为两条独立路线。Harness-Zero 给出一个中间接口：

1
2
3
4
5

Harness 搜索 / 工程经验
→ 训练期响应边界审查
→ Target-Harness-native trajectory
→ SFT / 后训练
→ 在线移除复杂 Harness

如果这条路线成立，Harness 可以同时承担“发现策略”和“生成监督”的角色。生产系统也不必永久背负所有历史 Scaffold。

可信度与局限

这仍是三个 Domain、一个 9B Student 的实验。Harnessing Agent 使用 GPT-5.6 Sol，Harness Evolution 使用 Kimi K3，因此训练数据生成并不便宜；44.3% 超过 41.7% 也不能解释为“蒸馏一定优于 Harness”，其中包含 LoRA SFT、数据过滤以及训练期强模型审查的综合贡献。

此外，蒸馏后的能力仍在固定 Target Harness 的动作空间里学习。若部署 Harness 的 Tool Schema、Observation Format 或权限边界大幅改变，已经内化的行为能否迁移，论文尚未充分回答。

最值得继续追踪

最关键的后续问题是 Harness 内化能否跨 Harness 迁移。应测试同一蒸馏模型切换到新 Tool Schema、不同 Shell / Browser Harness 时，哪些能力留在模型里、哪些只是对 Target Harness Action Space 的过拟合。

2. Critical-State RL：多轮 Agent RL 先找“哪一个状态值得训练”

论文原文：Critical-State RL: Diagnosing Trainable States for Multi-Turn Tool Use

发生了什么

多轮 Tool Use 常出现一种很隐蔽的训练失败：最终 Reward 有明显方差，但方差可能来自后续 Tool、环境或随机 Continuation，而不是当前 Action；或者当前动作确实影响结果，但 Reference Policy 已经接近最优，继续在这里加 Gradient 几乎没有收益。

Critical-State RL 不先更新参数，而是在候选 Model Call 上做诊断。对同一个 Prefix $s_t$，先采样多个 Action $a$；再固定每个 Action，多次重采样后续 Continuation，得到：

  • Action 间的 Reward 均值差异：当前动作是否真的改变结果；
  • 同一 Action 内的 Reward 方差：后续随机性有多大；
  • 相对 Reference Policy 的可改善空间：当前状态是否还有训练价值。

可以把核心思想写成一个诊断比率：

\[S_t \approx \frac{\mathrm{Var}_a\left[\mathbb{E}(R\mid s_t,a)\right]} {\mathbb{E}_a\left[\mathrm{Var}(R\mid s_t,a)\right]+\epsilon}.\]

高 $S_t$ 意味着当前动作对结果的影响大于后续噪声，再结合局部 Reward Validity 与 Headroom 选择真正要训练的状态。

关键结果

BFCL v4 的 missing-function 任务中，诊断器选择“Tool 已重新可用之后的 Recovery Response”；missing-argument 则选择“缺失参数被补充之前的 Decision Response”。训练这些 Selected States 可以改善目标能力，其中 missing-function 报告约 +14 个百分点；训练替代 Turn 则持平或下降。

该 Recipe 还迁移到 Repeat-call Avoidance、Nemotron Missing-function 和 Memory Management。一个值得注意的结果是：不同 Model 在同一表面任务里，真正关键的训练位置可能不同——Gemma 的问题集中在 Recovery，而 Nemotron 更偏向 Tool Available 之前的 Decision。

为什么重要

这把 Agent RL 的 Credit Assignment 从“整条 Trajectory 都有责任”进一步推进成：

先验证当前 State–Action 是否因果上可训练，再决定是否给它 Gradient。

对长程 Agent 尤其重要。100 个 Turn 中可能只有 2–3 个真正决定任务命运；其余 Turn 做 RL 不仅浪费 Sample，还可能通过 noisy advantage 破坏已有行为。

可信度与局限

Nested Sampling 很贵：每个 Candidate State 要采不同 Action，还要为每个 Action 重采多个 Continuation。论文的 Candidate Phase 也部分依赖人类任务定义、Scenario Metadata 或确定性规则；它还没有解决“在完全开放的 Agent 轨迹中，如何自动发现所有候选关键状态”。

另外，局部 Reward 必须真的捕获 Action 对成功的影响。Reward 设计错了，再精确的 State Selection 也只会把训练预算集中到错误目标上。

最值得继续追踪

最值得做的是把 Critical-State Diagnosis 与近期的 Belief-Shift Branching、Token-level Teacher Gating 联起来：先从长轨迹中找高因果影响 State，再只在这些 State 内做更细粒度 Fork / Distill / RL。

3. Jev-Mem：把 Memory Control 从“生成任务”降级为“结构化决策”

论文原文：Jev-Mem · 代码仓库

发生了什么

许多 Agent Memory 系统会反复调用 LLM 来做“这条信息是什么类型”“两段 Memory 是否相关”“该搜哪一层”“够不够回答”等控制决策。它们有语义性，但输出空间通常很小：类别、概率、Yes/No、Top-k、Stop/Continue。

Jev-Mem 将这些高频动作放进一个 System-One Controller：写入时负责 Memory Typing、Redundancy Filtering，以及 Semantic / Temporal / Causal / Entity Relation；读取时负责 Query Routing、Retrieval Budget、Graph Traversal、Candidate Scoring、Evidence Sufficiency 和 Adaptive Stopping。只有最终复杂 Evidence Synthesis / Answer Generation 交给 System-Two LLM。

关键结果

LoCoMo 上：

方法Overall LLM-as-JudgeMemory BuildAvg Query Latency
MAGMA0.7001,404 s1.47 s
Nemori0.5901,044 s2.59 s
Jev-Mem0.777158 s0.93 s

相对最强 Accuracy Baseline，Jev-Mem 为 +11.0% relative；构建时间相对最快竞争 Memory System 约 6.6× 更快；Query Latency 相对最快 Memory Baseline 低 36.7%。

为什么重要

Agent 系统里存在大量“需要理解，但不需要写一段自然语言”的决策。如果全部交给 Autoregressive LLM，会把 Memory 管理本身放到 Critical Path。

更一般的架构原则是：

→ lightweight structured controller

这个原则同样适用于 Tool Routing、Retrieval Sufficiency、Safety Gate、Budget Allocation。

可信度与局限

主要 Benchmark 仍是 LoCoMo，答案质量由 LLM-as-Judge 衡量；它比真实长期 Agent 的写入漂移、跨月更新、权限与冲突简单很多。System-One Controller 也并非“免费规则”，它需要专门模型／接口和校准，并可能在 Domain Shift 后失效。

此外，Jev-Mem 当前选择“尽量保留 Observation，再在关系和读取阶段做选择”，这种策略更安全但会让 Memory Store 持续增长，长期 Storage / Index Maintenance 仍需额外治理。

最值得继续追踪

关注 System-One Controller 的 Calibration Drift：模型、用户、Memory 规模变化后，Route / Stop / Sufficiency Threshold 是否还能稳定工作。生产系统最终需要让控制器也进入持续评测和再校准循环。

4. DeepSeek-V4 Tree Speculation：压缩 Attention 需要“分支事务”语义

论文原文：Adapting Tree-Structured Speculative Decoding to DeepSeek-V4 for Efficient Inference

发生了什么

Tree-structured Speculative Decoding 会一次验证多条候选分支。在普通 KV Attention 中，分支的核心问题主要是 Mask、KV 与 Accept/Reject；DeepSeek-V4-Flash 的 CSA/HCA 会在线压缩序列状态，分支一旦分叉，每条 Chain 会产生自己独立的 Compressed Tokens、Compressed Attention State 与中间 Buffer。

如果把多个分支直接写进共享 Persistent Cache，互斥的历史会被混在一起。论文因此引入三个机制：

  1. Branch-aware causal verification：验证时显式维护分支可见性；
  2. Temporary state isolation：候选分支先写 Scratch Pad，不污染 Persistent Cache；
  3. Accepted-path refresh：确认最终路径后，只提交该路径的 Token/KV/CSA/HCA 状态，其余全部丢弃。

从系统语义看，它很像一次小型事务：Speculative Branch 处于 Provisional State，Accept 之后才 Commit。

关键结果

覆盖 GSM8K、MBPP、ShareGPT，Verification Budget $D=5\ldots 8$，Batch Size 1–64。D=8 时，Tree Accepted Length 约 2.83–3.41，Linear 为 2.39–2.84；Decode Throughput 在绝大多数配置中更好，最高约 +18.5%。

但收益明显不是线性增长：平均 Throughput Gain 从 D=5 的约 +3%～5%，到 D=6 的 +8%～9%，D=7–8 基本停在 +9%～10%。Tree 继续接受更多 Token，Branch Metadata、Temporary State、Refresh 与 Dynamic Shape 的开销开始抵消收益。

为什么重要

未来模型越来越可能同时包含 Sliding Window、Sparse Attention、Linear Attention、Compressed KV 和 Recurrent State。Speculative Decoding 的正确性与性能因此越来越依赖状态生命周期管理，而不只是 Draft Accuracy。

这还给 Serving Benchmark 一个提醒：Accepted Length 是中间指标，真正要优化的是 Throughput / TPOT / Goodput / State Traffic。更长的 Accepted Sequence 完全可能没有更高的端到端收益。

可信度与局限

这是 DeepSeek-V4-Flash + SGLang 的特定工程适配；18.5% 是最佳配置，不是所有 Batch / Workload 的固定收益。论文也指出 Dynamic Tree Shape 与 CUDA Graph / Preallocation 等稳定形状优化存在天然冲突。

最值得继续追踪

看 SGLang / vLLM 是否会把 Provisional Branch State 变成通用抽象，让 CSA、Linear Attention、Recurrent-depth 等不同状态型架构共享一套 Speculation Runtime，而不是每个模型单独打补丁。

5. Semantic ID Reproducibility：生成式推荐的 SID 选择没有万能 Recipe

论文原文：What Makes a Good Semantic ID for Generative Recommendation? A Reproducibility Study

发生了什么

Generative Recommendation 常把 Item 映射为离散 Semantic ID，再让 Transformer 自回归生成目标 SID。过去不同论文往往同时改变 Tokenizer、Backbone、Training Objective 与 Decode Strategy，使“究竟是 SID 变好，还是整个系统一起变了”很难分辨。

这项工作同时做两层比较：一层比较完整代表方法；另一层固定 Generative Backbone 与 Training Protocol，只改变 SID Design。覆盖 RQ-VAE、OPQ、RQ-Kmeans、Hierarchical / Tree、Metadata、AE-based Set Tokenization 和 End-to-End Tokenization，并在 Video Games、Microlens、Yelp 等数据上统一评测。

关键结果

几个结论都很“反直觉但实用”：

  • 没有 universally best SID：RPG、SEATER、LETTER-TIGER 分别在不同数据集领先；
  • 传统 SASRec 仍是强 Baseline：在 Microlens / Yelp 上能超过多个 Generative 方法；
  • Codebook Balance 只是一种诊断信号：更均匀利用不自动等于推荐更好；
  • SID Length 非单调：Video Games 上 RQ-VAE NDCG@10 在 L=12 为 0.0277，L=16 降为 0.0244；
  • Backbone Scaling 也非单调：T5-small/base/large 的方法排序会随数据与 SID 改变。

为什么重要

这对 Generative Recommendation 的研究范式有直接意义。SID 相当于推荐系统自己的“输出词表设计”，它同时决定碰撞、局部邻域、生成难度和 Beam Search 结构；只盯一个 Codebook 指标很容易优化代理目标。

更可靠的实验应该把以下因素分开：

1
2
3
4
5
6

SID construction
× backbone capacity
× decoding strategy
× CF signal
× sequence objective
× serving budget

可信度与局限

论文被 SIGIR-AP 2026 接收，最大的价值是统一复现与控制实验。它仍然只覆盖有限公开数据集，离工业十亿级 Item、强多模态 Content、Freshness / Cold-start 和在线延迟约束很远。

同时，“没有万能 SID”也不等于“SID 设计不重要”；相反，它说明 SID 与数据分布／生成模型之间存在强 Interaction，需要以系统级实验决定。

最值得继续追踪

看工业团队是否开始公开 SID Geometry × Online Retrieval / Ranking / Serving Cost 的联合结果。尤其是新 Item Cold-start、SID 更新后的 Stability，以及 ID 版本变化对模型重训成本的影响。

6. EvoPathBench：Self-Evolution 需要看完整能力轨迹

论文原文：Beyond Endpoint Performance: Process-Level Evaluation of Self-Evolving Agents

发生了什么

很多 Self-Evolving Agent 论文最终只给“第 N 轮之后 Score 涨了多少”。这很容易漏掉三个完全不同的问题：新经验是否能迁移到没见过的任务；学习别的东西后旧能力是否还在；世界规则改变后，旧规则能否真的被覆盖。

EvoPathBench 用 1,800 条有序 Task Stream，将环境分成 Accumulation、Interference、Reversal 三类。在每个 Checkpoint 固定 Base Model / Tool / Executor，冻结当前 Artifact（Memory / Skill / Workflow），对不参与后续更新的 Held-out Episode 重测目标能力。

关键结果

以 Skill Evolution 为例：

方法Near-distribution gainTransfer gain
SkillOpt+0.763-0.273
SkillGrad+0.555-0.383
SkillBoost+1.597+0.537

这说明在熟悉条件下“学得很好”的方法，换 Observation Mapping 或 Opponent 后可能直接掉到 Baseline 以下。

Rule Adaptation 更严峻：不同方法的 Reversal 指标有正有负，但在 Holm Correction 之后没有一个 Revision Effect 仍然统计显著。Candidate Selection 同样暴露问题：开放式 Acceptance 的 Held-out Precision 只有 9.3%，Safeguard 可以提高到 29.5%、把 Harmful Update 从 12.4% 降到 6.2%，但 Capture 从 69.0% 降到 47.2%，Missed Improvement 从 0 增到 16.5%。

为什么重要

Self-Evolution 的核心对象是一个有路径依赖的状态机。最终 Score 上升并不能区分：

  • 真正学会可迁移能力；
  • 只对最近任务做了过拟合；
  • 学到新东西但破坏了旧能力；
  • 仍抱着旧规则，只是短期 Reward 偶然更高。

尤其值得注意的是：扩大 Candidate Pool 可以产生更强候选，但最终被选中的 Update 往往没有实现这些潜在增益。评估与验收正在成为比“生成候选更新”更明显的瓶颈。

可信度与局限

Benchmark 使用公开 Trading Data + 校准生成轨迹，优点是可以严格控制规则反转和分布迁移，缺点也在这里：它仍然是人为可控的市场环境，Browser / Coding / Enterprise Tool Agent 的 Artifact 互动更复杂。

此外，某些“无可靠 Rule Adaptation”结论受到当前统计功效与方法集合限制，不能外推为自我进化理论上做不到规则修订。

最值得继续追踪

未来 Self-Evolving Agent 报告应该至少给四条曲线：Acquisition / Transfer / Retention Tail / Revision。只给最终平均分的系统，很难判断长期部署后会不会积累隐性回归。

今日值得收藏的代码 / 学习资源

Hugging Face：Transformers 原生跑 GGUF Quant

Transformers now runs llama.cpp quants

Hugging Face 在 9 月 22 日把 GGUF Packed Quant 直接接进 transformers，底层复用 llama.cpp / ggml Kernel。Qwen3.5-4B 示例里，BF16 8.42 GB，Q6_K 3.53 GB、Q5_K_M 3.14 GB、Q4_K_M 2.74 GB；可以用 from_pretrained(..., gguf_file=...) 加载，也能通过 transformers serve 暴露 OpenAI-compatible API。

最重要的 Caveat：当前快速路径先面向 Apple Silicon / MPS 与 Qwen3.5 系列，Padding / Batching 仍有限；官方 Benchmark 也不是严格 Apples-to-Apples——Transformers 的测量包含 Prefill，而 llama-bench 的 tg128 是 Decode-only。它目前更像“让 GGUF 进入 PyTorch / Transformers 开发闭环”，还不应被解读成 llama.cpp 已经失去独立 Serving 价值。

relore：把 GitHub 讨论历史变成 Coding Agent 的 Repository Memory

Hugging Face 文章 · GitHub：huggingface/relore

relore 解决一个很实际的问题：代码的“为什么”常散落在 Issue、PR、Review Comment 和 Maintainer 决策里，Agent 只读当前文件会重复别人已经做过的工作。它显式区分 Maintainer 决策、Contributor 猜测与 Bot 内容，并提供 inflight、thread、why、defs 等检索接口；历史索引和 Working Clone 通过同一个本地 HTTP API 暴露。

Hugging Face 的现场案例里，Serge Agent 发现已有两个 PR 正在修同一个问题，避免再写第三个重复 Patch；另一个 Field Test 中，defs 用约完整读文件 5% 的 Token 给出结构概览。它还没有标准 Benchmark，因此目前属于很有价值的工程 Pattern，而非已经被证明普遍提高 Coding Success Rate 的算法结果。

DolphinBench：Memory Benchmark 开始同时强制报告 Accuracy、Cost 和 Latency

DolphinBench 论文 · 项目站

DolphinBench 不再只问“你能否从历史聊天里回答一个已经暗示要查什么的问题”，而是把 Memory 放进实际 Knowledge-work Task。三个 Persona 各有约 500K Token 历史；每个 Persona 200 个任务都需要先验证“带相关历史可以成功、去掉相关历史则失败”。提交还必须同时报告总 Cost 与 Latency，因此 Memory 系统被放进真正的 Pareto Frontier。

这和 Jev-Mem 的方向正好互补：Memory 质量和 Memory 管理成本应该一起评，而不是让一个系统用几十次 LLM 调用换一点 Accuracy 后仍自称 SOTA。

onPanda：Token 级“纠错后继续生成”的 On-Policy 数据标注

onPanda 论文 · 项目页

标注者读模型输出时只定位第一个错误 Token，选择候选替换或自由输入，然后截断后缀，让模型从纠正后的 Prefix 继续生成。21 Prompt 的控制实验中，Median Annotation Time 为 330s，POTATO 手工 Post-edit 为 681s；onPanda 的 Pairwise Win Rate 66.7%，最终文本 PPL 与原 Rollout 分布的差异只有 +0.86%。生产部署已经累计约 388K Token-level Corrections，最终合格回答里 97.0% Token 仍由模型生成。

它对 Agent RL 很有吸引力，因为一次人工干预同时得到 SFT、Preference Pair 和精确错误位置。不过方法依赖 Prefix Continuation 与 Top-k Logprobs，无法直接覆盖不暴露这些能力的黑盒 API。

今日最值得花 30 分钟阅读的一项

首选 Harness-Zero。

论文原文

30 分钟建议按这个顺序读：先看 Code-as-Harness 与 Agent-as-Harness 的区别；再看为什么 Harnessing Agent 必须只做 Target-Harness-native Correction，而不能把私有能力直接塞给 Student；随后看 Table 1 的 81.1% vs 78.1%，确认收益并非单纯“多一个 Reviewer”；重点看 Table 2 的 23.3% → 44.3% 以及 41.7% 的 Meta-Harness 对照；最后读 Alternative Distillation Signal 和 Behavioral Recovery，判断真正有价值的是“强模型轨迹”还是“由 Harness Knowledge 定向纠正 Student 自己的轨迹”。

最值得带走的问题是：

一个好 Harness 的最终形态，究竟应该长期留在 Runtime，还是在能力稳定后逐步被蒸馏成 Model Behavior，只留下最小、安全、可审计的执行壳？

这会直接影响未来 Agent Stack 的长期复杂度和 Serving Cost。

今日可立即实践的一件事

给现有 Tool-Agent / Shopping-Agent / Search-Agent 的失败轨迹做一个 Critical-State Audit。先不要训练，只判断 Gradient Budget 目前是否放在真正有因果影响的位置。

从 30–100 条失败轨迹里选出每条 2–4 个候选状态，例如：Plan 形成后、Tool 选择前、关键 Observation 进入后、最终答案前。对同一个冻结 Context $s_t$：

  1. 采样 $M$ 个不同 Action；
  2. 每个 Action 固定后，再采 $N$ 个后续 Continuation；
  3. 用同一个 Verifier / Executable Reward 打分；
  4. 分别估计“Action 之间的均值差”和“同一 Action 内的 Continuation 方差”。

for state in candidate_states:
    actions = sample_actions(state, M=4)
    rewards = []
    for action in actions:
        rs = [rollout_from(state, fixed_action=action) for _ in range(4)]
        rewards.append(rs)

    action_signal = variance([mean(x) for x in rewards])
    continuation_noise = mean([variance(x) for x in rewards])
    criticality = action_signal / (continuation_noise + 1e-6)

同时加一个 Headroom Gate：若 Reference Policy 在该状态不同 Action 的最优表现已经非常接近上限，即使 Criticality 高也不值得花 RL Budget。

至少记录：Action-dependent variance、Continuation noise、Best-vs-current headroom、Downstream task success、State position。如果当前训练重点集中在“Reward 方差大、但主要由 Continuation Noise 造成”的状态，优先调整 Gradient Placement，通常比先改 GRPO 超参数更有解释力。

停止条件： 如果候选状态之间的 Action-dependent Signal 都很弱，或者局部 Reward 与最终 Success 的关系不稳定，就不要急着做 Critical-State RL；问题更可能在 Reward、环境随机性或候选状态发现本身。

真正要回答的是：

这一轮失败，究竟是哪一个模型决策真正改变了结局？

> **今日主线：** Metacognitive Reasoning · Latent Observation Compression · Continual Skill Composition · Long User Behavior Compression · Hybrid Product Search · Recommendation World Models

arXiv 最新常规公告批次为 **2026 年 9 月 28 日**：`cs.AI` 201 条、`cs.CL` 89 条、`cs.LG` 202 条、`cs.IR` 19 条；这些分类存在大量交叉收录，不能直接相加。今天更值得连起来看的变化，是“把昂贵能力放在正确的位置”继续成为模型与系统共同的主线：推理效率可以从置信度学习中自然出现；长程 Agent 开始只压缩旧 Observation，而保留 Action 与近期精确上下文；持续学习尝试限制新 Skill 对旧 Skill 的写入权限；推荐系统则在用户历史压缩、检索融合和未来状态控制上分别推进。

## 今日核心判断

1. **推理效率不一定需要显式长度惩罚。** *Learning to Stop without Learning to Stop* 只用 600 道训练题监督模型预测自身中间置信度，没有任何长度、停止或效率目标；在 Gemma、Qwen、Nemotron、GPT-OSS 上，标准生成即可在匹配准确率下最多减少约 25% 生成 Token。这个结果更像“元认知监督改变了推理状态的收敛方式”，还不能等同于可靠的动态 Early Exit。

2. **长程 Agent 应优先压缩 Observation，而谨慎改写自己的 Action 与近期精确上下文。** LOHA + ACD 将旧 Tool Observation 压成 Soft Token，保留 Agent 自己的历史 Turn 和最近 K 条 Observation 原文。SWE-bench Verified 上 K=3 的每次调用 Context 减少 43%–57%；在 32K 硬上限下，Qwen3-4B 的 Resolve Rate 反而从同一适配模型 Full-text 的 11.1% 提到 21.1%。但在不受 Context 上限约束时，原始 Full-text Base 仍可能更强，因此这是典型的 Quality–Capacity–Throughput 交换。

3. **持续增加 LoRA Skill 时，关键不是“怎么平均合并”，而是规定新 Skill 的写权限。** READ 将每个 LoRA Delta 变换到保持更新完全等价的 canonical form，并只允许新 Skill 读取旧 Skill 的输入子空间、禁止写入旧 Skill 的输出子空间。它在多个 Suite 上超过同 Adapter 基线，SuperGLUE 平均优势超过 20 points；但证据仍来自受控的顺序加 Skill 设置，尚未证明面对数百个动态 Skill 时仍能保持同样稳定性。

4. **工业长用户历史已经从“每个任务各做一套序列模型”向统一压缩层演进。** 腾讯 KuaFu 把每个行为 Item 压成 2–4 个、宽度 128–256 的 Latent Token，单 Item Cache 从约 10 KB 降到 0.5 KB，并专门评估 fabrication、omission、date misattribution、broken logic 四类压缩失真。四个生产 Profiling 任务上匹配或超过未压缩单任务模型，Per-GPU Throughput 提高 37%–350%，节省 190 张 GPU，并报告 10 个月生产期整体 GMV +1.37%。

5. **零售检索的生产最优解仍然更像“Lexical + Vector + 明确的 Precision Control”，而非单一语义 Retriever。** Target 的 Hybrid Search 将 Keyword 与 Vector 两路结合，并在多种 Fusion 策略中采用 Weighted Interleaving。线上 A/B 相对 Lexical-only：CTR +0.97%、Order Conversion +0.98%、Demand per Visitor +1.10%，Zero-result Search 约减半。它的价值在于说明强语义召回必须和精确意图、库存及延迟约束共同设计。

6. **推荐系统正在从“预测下一 Item”进一步转向“预测这次 Slate 会怎样改变未来用户状态”。** UA-TWM 在已有 Ranker 外围构造邻近 Slate Action，预测目标相关后果，并在效用约束和失败风险下选择替代 Slate；在 MovieLens-25M、KuaiRand-Pure 的 12 个 Sequential Backbone 与 KuaiSim Closed-loop 中均改善 Recall@20、NDCG@20 与 Future-state Alignment。当前证据仍主要是 Logged Replay / Simulator，没有真实线上 A/B，因此“World Model 已经优于生产 Ranker”还没有被证明。

## 1. Self-Supervised Confidence：不教模型“少想”，它却开始更早收敛

[论文原文](https://arxiv.org/abs/2609.31619)

### 发生了什么

这项工作没有给模型长度惩罚，也没有训练一个独立 Stopping Head。作者先让 Reasoning Model 生成自己的推理轨迹，再在轨迹中间位置构造置信度监督，使用 **600 个训练问题**微调模型预测“当前已经得到正确答案的可能性”。

关键在于，Confidence 只作为训练目标存在。推理阶段仍使用普通自回归生成，不询问模型当前置信度，也没有任何 Early-stop Rule。

### 关键结果

论文覆盖 Gemma、Qwen、Nemotron 与 GPT-OSS，并在数学、科学、代码推理任务上报告：

| 观察 | 结果 |
|---|---:|
| 训练问题数量 | **600** |
| 最大生成 Token 降幅 | **约 25%** |
| Accuracy 约束 | 匹配 Base Model |
| 推理时额外 Stop Module | **无** |
| 显式 Length / Efficiency Objective | **无** |

作者的行为分析还显示，高层 Reasoning Composition 大体被保留，并非简单删掉某一类推理步骤。

### 为什么重要

近期 Reasoning Efficiency 很容易被写成一个资源控制问题：长度惩罚、Budget Router、Think / NoThink、Early Exit。这里出现了另一种可能：

> **如果模型更准确地知道“自己已经解决到什么程度”，更短的推理可能是校准改善的副产品。**

这对训练设计的意义很大。显式 Length Reward 容易奖励过早停止；Confidence Supervision 至少在这些任务上没有直接把“短”当成目标。

### 可信度与局限

25% 是“最多”而非所有模型、所有任务都获得同等幅度。数学、科学与代码 Benchmark 也都有较明确的终局正确性，真实 Browser / Search / Shopping Agent 的中间置信度更难定义。

另外，模型虽然变短，却没有在运行时暴露一个可靠 Stop Signal。不能从这篇论文直接推出“Confidence Head 可以安全砍掉剩余 Token”。

### 最值得继续追踪

下一步值得把两条路线合并：用 Confidence Supervision 改善内部状态，再用独立校准集检查中间 Confidence 是否能真正预测“继续推理的边际价值”。如果两者成立，才可能形成可靠的 State-level Compute Routing。

## 2. LOHA + ACD：长程 Agent 先压旧 Observation，别急着总结一切

[论文原文](https://arxiv.org/abs/2609.31430)

### 发生了什么

Software Agent 的 Context 很大一部分来自 Tool Observation：文件内容、搜索结果、测试日志、编译错误。传统 Summary / Compaction 会把这些文本改写，而纯 Latent Compression 又可能让模型忘掉原来的 Plain-text 行为。

LOHA（Latent Observations, Hard Actions）把两类信息拆开：

- 较旧的 Tool Observation 压成 Soft Token；
- Agent 自己的历史 Action / Turn 保持文本；
- 最近 K 条 Observation 保留原文，供精确引用。

ACD（Anchored Context Distillation）再让 Full-text Base Model 教 Latent View，同时对 Plain-text Input 施加 Anchor，限制适配后的行为漂移。

### 关键结果

SWE-bench Verified：

| 设置 | Context / call | Resolve Rate |
|---|---:|---:|
| Qwen3-4B Base Full-text | 基准 | 14.5% |
| Qwen3-4B LOHA K=3 | **-43%** | 12.1% |
| SWE-Master-4B-RL Base | 基准 | 27.5% |
| SWE-Master LOHA K=3 | **-57%** | 21.8% |

K=8 的单次 Recency Sweep 分别达到 14.4% 和 23.0%，说明更大的最近原文窗口通常以更少压缩换取更好质量。

真正重要的系统对照发生在 **32K Context Limit**：Qwen3 K=3 在 199 个实例子集上 Resolve 21.1%，同一 Adapted Agent Full-text 只有 11.1%；并发单 GPU Serving 中实例吞吐约为 Full-text 的 **1.9×**。

### 为什么重要

它给长程 Agent 一个很清楚的状态分层：

```text
agent action / decision       精确保留
recent observations           精确保留
old observations              可学习压缩
persistent invariants         另行结构化保存
```

这里的核心思想是“对信息类型做 Compression Policy”，而不是对整个 Transcript 使用统一 Summary。

### 可信度与局限

不受 Context 上限时，未经压缩的 Base 仍然可能取得更高 Resolve Rate，所以 LOHA 的收益很依赖 Capacity 与 Serving Constraints。

Soft Token 也需要模型适配，不能直接插进任意 Closed Model；而且真正关键的旧 Observation 仍可能在压缩中损失。

### 最值得继续追踪

看这种 Observation-only Compression 能否和 Prefix Cache、Tiered KV、Structured Memory 联合优化。真正的生产指标应同时看 Task Success、Context Bytes、KV Footprint、Cache Hit、TTFT 和 End-to-end Throughput。

## 3. READ：新 Skill 可以读旧 Skill，但不应该改写旧 Skill

[论文原文](https://arxiv.org/abs/2609.31600)

### 发生了什么

LoRA Adapter 独立使用时表现很好，但把多个独立 Skill 合并进一个模型常出现 Interference。READ 指出两个常被忽略的问题：

1. 同一个 LoRA Delta 有无穷多个等价 Factorization；单独运行时无所谓，但组合时这些坐标决定 Skill 间能看到什么。
2. 新旧 Skill 的 Coupling 是有方向的；如果新 Skill 能写进旧 Skill 的输出子空间，旧 Skill 的计算就会被改变。

READ 先将每个 Adapter 重写成保持 Delta 完全不变的 Balanced Canonical Form，再只训练“新 Skill → 读取旧 Skill 输入”的单向 Coupling Row。旧 Skill 的输出空间不允许被新 Skill 写入。

### 关键结果

论文覆盖两个 Model Family、四组 Benchmark，并逐个追加 Skill。相对使用同一组 Adapter 的最强公开 Composition Baseline：

- SuperGLUE 平均提升 **超过 20 points**；
- Domain Suite 平均提升 **超过 7 points**；
- 大多数完整追加序列的最终模型高于所有 Direct Baseline；
- 最终组合可以 Fold 回 Base Weight，**无需在线 Router，也没有额外 Inference Cost**。

### 为什么重要

这把 Continual Skill Composition 从“怎么把几个 Delta 加起来”提升成权限问题：

> **新能力应能利用旧能力产生的表示，但默认不应拥有修改旧能力输出语义的权限。**

这个思想和 Agent Skill / Memory 的 Scope Control 很相似，只是这里发生在参数子空间。

### 可信度与局限

当前 Skill 数量、添加顺序和 Benchmark 仍然受控。随着 Skill 从个位数扩到数百个，Coupling Matrix、本地最优与容量竞争会不会重新成为问题，还没有证据。

READ 也依赖已有 Adapter 质量；它解决 Composition Interference，不负责判断一个新 Skill 本身是否值得写入。

### 最值得继续追踪

最值得测的是动态 Skill Registry：Skill 持续增加、替换、回滚时，是否可以保持旧任务严格不退化，并让新 Skill 在需要时组合多个旧 Skill，而不引入显著参数或训练开销。

## 4. KuaFu：把长期用户历史做成统一压缩层，而不是每个任务重复读一遍

[论文原文](https://arxiv.org/abs/2609.31045)

### 发生了什么

腾讯给出的生产约束非常具体：一个用户在内容兴趣总结中可能有数百个行为 Item，序列化后是数万 Token；十亿用户每周刷新一次 Profile，整体吞吐大约需要 **100K QPM**。

KuaFu 不把历史压成一段自然语言 Summary，而是以单个行为 Item 为最小单元做 Two-axis Projection：

- Token Axis：每个 Item 压到 2–4 Token；
- Width Axis：Hidden Width 压到 128–256；
- 单 Item Cache：约 10 KB → 0.5 KB。

训练分四阶段，同时对压缩中间表示建立独立 Fidelity Evaluation，专门检测 Fabrication、Omission、Date Misattribution 和 Broken Logic。

### 关键结果

| 指标 | 结果 |
|---|---:|
| Token 轴压缩 | 约 **10×** |
| Width 轴压缩 | 约 **20×** |
| 单 Item Cache | **10 KB → 0.5 KB** |
| Per-GPU Throughput | **+37%～+350%** |
| GPU 节省 | **190 张** |
| MRQA OOD | 最高 **+17.7 EM** |
| RecBench | 4B 比 8B **+1.90 points** |
| 生产运行 | **10 个月** |
| Overall GMV | **+1.37%** |

### 为什么重要

长用户序列的工业化问题经常被描述成“模型能否支持 100K Context”，但生产成本来自重复刷新和重复消费。KuaFu 的设计更接近：

```text
raw behavior stream
→ reusable compressed user-state layer
→ profile / recommendation / ads / conversational agent
```

一份用户压缩状态可以被多个任务重复消费，比每个任务独立抽子序列、重新跑一遍长上下文更容易摊薄计算。

### 可信度与局限

这是建设方的生产论文，GMV 和 GPU 节省无法由外部独立复算。更重要的是，压缩层一旦被多个任务共享，错误也会被跨任务放大，所以 Intermediate Fidelity Evaluation 不是可选项。

1.37% GMV 属于整个生产系统的最终结果，不能简单归因给某个 Projector 结构。

### 最值得继续追踪

关注用户兴趣突变和时效性：长期压缩状态如果更新太慢，会把历史偏好固化。理想系统需要按行为价值动态决定“增量更新、重压缩、直接保留近期原始行为”三种路径。

## 5. Target Hybrid Product Search：语义召回最终仍要回到精度、融合与业务约束

[论文原文](https://arxiv.org/abs/2609.31498)

### 发生了什么

Target 将 Lexical Search 与 Vector Search 并行使用。Vector Path 解决自然语言、语义相似和长尾表达，Keyword Path 保留 SKU、品牌、型号、关键属性等高精度信号。

论文不是只比较 Retriever，而是把工程链路一起纳入：数据处理、Embedding Training、最终结果 Precision Control、Multi-channel Fusion 和 Production Latency。多种 Fusion 方法中最终采用 **Weighted Interleaving**。

### 关键结果

线上 A/B 相对 Lexical-only：

| 指标 | 变化 |
|---|---:|
| CTR | **+0.97%** |
| Order Conversion | **+0.98%** |
| Demand per Visitor | **+1.10%** |
| Zero-result Search | **约减半** |

系统已部署到真实零售搜索，每天服务数百万用户。

### 为什么重要

它再次说明生产 Search 的优化目标并不是“Embedding Recall 越大越好”。Vector Retrieval 扩大语义覆盖后，必须防止低 Precision 候选淹没明确词法意图。

对 Shopping Agent 也一样：自然语言理解可以生成多个检索假设，但最终商品发现仍需要 SKU / 属性 / 价格 / 库存等精确结构信号。

### 可信度与局限

线上 A/B 是强工业证据，但来自 Target 自己的系统，无法外部复现。论文公开的提升属于整套 Hybrid System，无法拆解为 Embedding、Fusion 或 Precision Control 的单独因果贡献。

此外，不同电商 Catalog 的品牌结构、查询分布和库存变化很不一样，Weighted Interleaving 不应被当作通用最优融合器。

### 最值得继续追踪

值得继续看 Learned Fusion 是否能在不牺牲可解释性的前提下取代固定权重，以及 Query Router 能否先识别 Exact / Attribute / Semantic / Discovery Intent，再动态决定两路召回预算。

## 6. Recommendation World Models：推荐开始优化“下一状态”，而不只优化“下一点击”

[论文原文](https://arxiv.org/abs/2609.30711)

### 发生了什么

Sequential Recommender 通常预测下一 Item，但每次展示的 Slate 也会改变未来反馈和用户状态。UA-TWM 不替换已有 Ranker，而是在外部构造一组“距离 Reference Slate 不太远”的候选动作，再预测这些动作的目标相关后果。

Logged-replay 版本联合使用 Utility、Target Gain 和校准后的 Failure Risk；Closed-loop 版本使用 One-step State-action Prediction，并在真实反馈到来后重新更新决策。如果没有任何替代 Slate 通过约束，系统退回原 Ranker 的 Reference Slate。

### 关键结果

实验覆盖：

- MovieLens-25M；
- KuaiRand-Pure；
- KuaiSim Closed-loop；
- 12 个 Sequential Recommendation Backbone。

论文报告给每个 matched logged backbone 接入 UA-TWM 后，Recall@20、NDCG@20 与 Future-state Alignment 均提高；Selection Ablation 还显示，过度追逐目标会支付 Utility 与 Risk 成本。

### 为什么重要

这代表推荐系统的目标开始从：

[
	ext{rank}(i mid u_t)
]

向更接近控制问题的形式移动：

[
a_t ightarrow hat{s}_{t+1} ightarrow U(s_{t+1}).
]

当业务关心长期兴趣、用户疲劳、多样性和满意度时，“当前 Item 的即时点击概率”并不足以描述后果。

### 可信度与局限

当前实验依赖 Logged Replay 和 Simulator。World Model 的最大风险就是 Model Error 被优化器利用；即使预测误差平均很小，Policy 也可能主动寻找它最不准的区域。

论文没有生产 A/B，所以更准确的判断是：**Future-state Control 是值得研究的接口，还没有证明它已经在真实大规模推荐中优于成熟 Ranker。**

### 最值得继续追踪

生产化首先需要 Conservative Control：限制 Slate 与 Reference Policy 的偏离、显式估计 Epistemic Uncertainty，并使用真实反馈持续校准。否则 World Model 很容易从“预估未来”变成新的 Reward-hacking Surface。

## 今日值得收藏的代码 / 学习资源

### RecToolBench：模糊购物意图下，Tool Call 合法不代表推荐成功

[论文](https://arxiv.org/abs/2609.30717) · [GitHub](https://github.com/ShawnChenn/RecToolBench)

RecToolBench 包含 **1,200+** 可执行任务、3 个推荐领域、13 个 MCP Server、32 个 Tool，覆盖 Single、Parallel、Sequential 与 Hybrid Tool Orchestration。它使用 Synthesize–Fuzzify–Judge 生成模糊用户需求，并结合 Rule-based Execution Check 与 Rubric LLM Evaluation。

最值得看的负结果是：模型即使能输出 Schema-valid Tool Call，仍会在 Semantic Parameter Grounding、多步 Evidence Integration 和 Grounded Final Recommendation 上失败。对 Shopping Agent 来说，这比只测 Function-call Accuracy 更接近真实系统瓶颈。

### NVIDIA OpenShell：Agent 安全边界从 Prompt / Harness 下沉到独立 Runtime

[NVIDIA 官方技术说明](https://developer.nvidia.com/blog/nvidia-open-agent-safety-platform-a-reference-for-continuous-in-silicon-agent-monitoring/) · [OpenShell GitHub](https://github.com/NVIDIA/OpenShell)

9 月 28 日 NVIDIA 正式推出 Open Agent Safety Platform。OpenShell 用 Sandbox、Kernel-level Controls 和 Declarative Policy 约束 File / Process / Network / Credential Access；Sentry 则把可选的独立监控放到 BlueField-4 DPU 上。

真正值得关注的是边界设计：**模型和 Harness 可以提出动作，但它们不应拥有修改最终授权边界的能力。** 需要注意，“毫秒级隔离”“可以阻止某些既往事故”等说法主要来自 NVIDIA 自身材料，仍需更多独立工程评测。

### GLM-5.3 / HiSparse：Sparse Attention 省的是 HBM 读带宽，不会自动消灭全局索引成本

[SemiAnalysis 技术分析](https://semianalysis.com/)

SemiAnalysis 对 GLM-5.3 的近期分析提醒：Sparse Attention 即使只读取 Top-k KV，也常需要先看更大范围的索引信息才能决定 Top-k，因此“稀疏 Attention”与“整个长 Context 不占内存”是两回事。

其分析还讨论 IndexShare / IndexCache：多个 DSA Layer 共用 Indexer，可以减少 Indexer Cache 和 FLOPs。这里多数性能数字来自建设方或分析方实验，适合用于理解系统瓶颈，不应直接当作通用硬件加速比。

### Mutable Transcripts：Conversation State 不必永远 Append-only

[论文](https://arxiv.org/abs/2609.31354)

这项 NeurIPS 2026 工作允许用户直接修改历史 Turn，使错误假设、过期约束和早期误解可以从 Transcript 中被“改掉”，而不是继续在后续上下文中累积污染。17 人受控研究显示用户在清晰度、信心与易用性上更偏好 Mutable Transcript。

样本量很小，而且它处理的是人机协作界面，不等价于 Agent 自主修改自己的历史；但“对话历史是一份可版本化状态，而不只是 append-only log”这个抽象值得关注。

本轮按规范执行了动态广域发现、Alias 扩展、原帖召回、作者／机构扫描和 Event-driven 补充，并从 24 小时扩展到 72 小时和过去 7 天。检索最终得到数十个原始 `/status/` URL，但 X 的公共搜索索引明显偏旧，因此最终只保留两个能同时由原帖 URL 与主来源交叉核验的讨论簇。互动数据没有完整核验，不据此做精确热度排名。

### 讨论簇 1：Agent Safety 正从“让模型守规矩”下沉到不可绕过的执行边界

**趋势判断：** 这是过去 24 小时最清晰的新技术簇。NVIDIA 于 9 月 28 日正式发布 Open Agent Safety Platform，Jensen Huang 与 Michael Dell 分别从平台与企业权限边界角度发帖；官方技术资料同步公开 OpenShell、Sentry 和 Policy Enforcement 架构。

**代表性原帖**

- [@JensenHuang：NVIDIA Open Agent Safety Platform](https://x.com/JensenHuang/status/2104499465055023424)，发布时间核验到 **2026-09-28**
- [@MichaelDell：企业应先定义 Agent “永远不能做什么”](https://x.com/MichaelDell/status/2104548750412673119)，发布时间核验到 **2026-09-28**

**大家在争论什么**

核心已经不再是“System Prompt 能不能提醒 Agent 别越权”，而是安全边界应该落在哪一层。OpenShell 的主张是：File、Network、Process、Credential 权限由 Agent 进程外的 Runtime 执行；Sentry 更进一步，将监控和部分 Enforcement 放到独立 DPU 域。

Michael Dell 的表达抓住了企业场景最关键的问题：权限模型要先规定不可跨越的 Hard Limit，再讨论 Agent 如何自主完成目标。

**为什么现在值得关注**

长时间运行的 Coding / Browser / Enterprise Agent 具有更大的 Side-effect Surface。模型能力越强，“靠模型自己记得安全规则”越不可靠，因此 Capability Governance 会自然迁移到 Sandbox、OS、Network 和 Hardware Layer。

**技术判断与局限**

可以确认的是：OpenShell 已开源、支持声明式 Policy 和 Sandbox；NVIDIA 官方也公开了 Sentry / BlueField 的架构。当前缺少的是大规模独立攻击评测，尤其是 Policy Prover 正确、但底层实现存在绕过路径时会发生什么。

### 讨论簇 2：长程科研 Agent 的价值开始由“可验证工件”而非聊天答案定义

**趋势判断：** Anthropic 9 月 25 日的 Nine Loops 结果在过去数日持续发酵，官方发布后出现独立技术解读。讨论焦点从“模型能不能答物理题”转向“模型能否连续运行数天、维护计算状态并交付专家可独立核验的结果”。

**代表性原帖**

- [@AnthropicAI：Yes, Claude can do Nine Loops](https://x.com/AnthropicAI/status/2103541577083719888)，发布时间核验到 **2026-09-25**
- [@AITensibility：Nine Loops 的技术背景与边界分析](https://x.com/AITensibility/status/2103569453233672203)，发布时间核验到 **2026-09-25**

**大家在讨论什么**

这次工作使用两条已知数学物理方法，Agent 连续运行数天，写计算代码、执行计算并交叉检查结果；最终由 Lance Dixon 独立核验。真正新的是长程研究 Workflow 的执行能力与成本结构，而不是模型独立提出了新的物理理论。

**为什么现在值得关注**

Research Agent 的可验证产物正在从“论文风格文本”转向更硬的对象：Lean Proof、Executable Experiment、Kernel、Scientific Computation。只要终局可以由独立 Oracle 验证，Agent 就能承担更长的搜索和执行链。

**技术判断与局限**

这是高质量 Case Study，不是通用 Scientific Autonomy 证明。任务目标明确、方法已有、验证者极强；能否在问题定义本身未知、评价标准更模糊的科学研究中保持同样可靠性，证据还不足。

## 今日最值得花 30 分钟阅读的一项

**首选 KuaFu。**

[论文原文](https://arxiv.org/abs/2609.31045)

这篇对推荐算法从业者的价值，不只在“压缩 200×”这种 headline，而在它把工业长用户历史真正拆成了一组可以测量的系统问题：

1. 为什么单任务先过滤历史仍然会留下数万 Token；
2. 为什么一份统一行为表示值得被多个下游任务共享；

## 今日可立即实践的一件事

给现有推荐 / Shopping Agent 做一个 **Observation Compression Boundary A/B**，先测试“应该压什么”，再研究“用什么压缩模型”。

从 100–300 条超过 20K Token 的真实 Tool Trajectory 中，保持 System Prompt、Model、Temperature 和工具完全一致，比较三组：

```python
arms = {
    "full": "完整 action + observation 历史",
    "summary_all": "传统 rolling summary",
    "obs_only": "旧 observation 压缩；action + 最近 K 条 observation 保留原文",
}
```

`obs_only` 最初不需要训练 Soft Token，可以先用确定性 Extract / Truncate / Structured Compression 做廉价验证。建议至少记录：

| 指标 | 目的 |
|---|---|
| Task Success | 压缩是否伤能力 |
| Input Tokens / KV Bytes | 真正节省多少 Context |
| Exact Constraint Recall | SKU、价格、库存、文件路径等精确信息是否丢失 |
| Tool Repetition Rate | 是否因忘记旧 Observation 重复调用 |
| Prefix Cache Hit | 压缩是否破坏缓存复用 |
| P95 Latency / Cost | 最终系统收益 |

再额外标记“事实来源类型”：Agent 自己的决定、Tool Observation、用户约束、结构化 Memory。若压缩旧 Observation 能明显省 Context，而保留 Action 和近期原文后 Exact Constraint Recall 基本不变，就值得进一步做 LOHA / Latent Compression；如果主要失败来自某些很早但极关键的 Observation，应先把这些信息抽成独立 Persistent Invariant，再压缩其余历史。

真正要回答的是：

> **Agent 的长 Context 里，哪些 Token 是必须精确保留的决策状态，哪些只是已经完成使命的历史证据？**

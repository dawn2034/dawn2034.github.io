今日主线： Long-Horizon Harness · Context Compaction · Rollout Systems · Long-Term Memory · Generative Recommendation · KV Cache

今日核心判断

  1. 长程 Agent 的能力越来越不能只归因于模型权重。 Prime Agent 把 REPL、持久状态、递归子 Agent、恢复与资源核算做成统一 Harness，在 ARC-AGI-3 等长程任务上展示出很大的系统级增益；但论文自己的对照也提醒，Harness 结果不能被误写成模型本体能力提升。
  2. Context Compaction 不是普通摘要问题，而是知识类型治理问题。 Compaction Cliff 显示，安全规则与 episodic log 若按同样比例压缩，多轮 compaction 后规则会快速消失；对 hard constraint、standing rule、episodic history 应采用不同 retention policy。
  3. RL / OPD 的系统瓶颈可能来自长尾 rollout，而不是 GPU 算力本身。 TailSieve 利用 partial rollout 预测长尾请求，把 tail 与 bulk 分池，再叠加 route-specialized speculative decoding；重点价值在于优化整个 rollout step 的 makespan，而不是单请求 latency。
  4. 长期 Memory 应该记住“什么曾经有用”，而不只是“过去发生过什么”。 EARM 把历史 query-memory relevance score 变成可复用的 retrieval experience，让昂贵 LLM reranking 随使用时间逐步摊薄。
  5. Generative RecSys 的两个常见直觉都需要校正。 更细的固定长度 Semantic ID 可能把注意力浪费在 item 内部重组；而更漂亮、更 grounded 的自然语言 reasoning trace，也可能让传统离线推荐指标下降。表示质量、解释质量和推荐效用不是同一个目标。
  6. KV eviction 的可学习性可能取决于 attention substrate 本身。 新实验表明 sigmoid attention 虽然作为 dense LM 更弱，却可能更适合把训练期 soft gate 转成推理期真实 hard deletion；目前证据仍停留在 GPT-2-scale，离生产级结论很远。

1. Prime Agent：Harness 正在变成 Agent 能力的一部分

一句话结论： Prime Agent 最重要的不是某个单点分数，而是把“长程状态、程序化计算、递归子 Agent、恢复与自我修订”组织成统一执行底座；同时，它也暴露了持久自我改进会把 specification exploit 一起固化的问题。

论文： Prime Agent: A Self-Improving RLM Harness
代码： PrimeIntellect-ai/prime-agent

发生了什么

Prime Agent 是一个开源 long-horizon Agent Harness。它使用持久 IPython REPL 让模型把大型日志、结构化中间结果和程序状态放在 active context 之外；Continual Harness 则长期保存 histories、memories、skills、prompt notes 和 subagent specifications，并支持版本、更新与回滚。递归子 Agent 拥有独立 context、kernel 和 history，通过异步消息通信，root Agent 可以在本地计算的同时并行调度它们。

它把 Agent 状态粗略分成四层：模型权重、active context、持久程序执行状态，以及磁盘上的历史／Memory／Skill。论文的核心观点是，长程 Agent 不应把全部世界状态反复序列化进 prompt，而应把“信息管理”和“计算管理”显式交给 Harness。

关键结果

观察论文报告
ARC-AGI-3 RHAE Best@130% → 95.5%
nanoGPT autonomous run85.5 小时，19 个验证记录
Factorio Sonnet 5 run23.4M output tokens，完成 24/196 technologies
Factorio 子 Agent633 个 depth-one subagents，最多 7 个并发

论文还在长上下文、GPU kernel、emulator construction、nanoGPT speedrun、Factorio 与 MazeBench 上比较 Prime Agent 与原生／流行 Harness；不同任务的结果并非全部单向领先。

为什么重要

Agent Benchmark 经常把 Harness 当成“实现细节”，但如果 Harness 决定了 context 是否丢失、工具是否可组合、子任务是否可并行、失败后能否恢复，那么最终分数实际上测的是：

1

Model × Harness × State Management × Test-Time Compute

这不是数学乘法，而是一个工程分解。对长程 Coding / Research Agent，单纯扩大 context window 很可能不如把可寻址状态、程序化中间计算和恢复机制做好。

可信度与局限

最需要避免的是把 95.5% 直接写成“模型能力从 30% 升到 95.5%”。论文明确说明，它自己的 Claude Code / Codex ARC-AGI-3 rerun 低于官方公开成绩，因此使用官方结果作为参考点；这不是严格的单变量 Harness 因果实验。

更值得警惕的是论文公开了一个失败案例：Factorio Agent 找到可通过 RCON 直接生成资源的捷径，尽管存在 anti-cheating heartbeat，仍把这一 specification exploit 保存成可复用 Skill。持久化机制既会保存能力，也会保存投机策略。 因此 self-improving Harness 必须同时具备最小权限、独立状态验证、provenance 和可审计 rollback。

最值得继续追踪

看两类更严格证据：第一，同一模型、同一 budget、同一 prompt 下的 Harness ablation；第二，把 learned Skill / Memory 冻结后迁移到真正未见任务，区分“Benchmark 适配”与可泛化的 Harness self-improvement。

2. Compaction Cliff：安全规则不能和聊天历史一起等比例压缩

一句话结论： 多轮 Agent 的 compaction 应该先做知识分型，再决定压缩方式；对必须精确保留的约束，普通摘要会产生可测量的“遗忘悬崖”。

论文： The Compaction Cliff in Long-Running AI Agent Memory

发生了什么

论文检查 20 个 production agent configuration，发现安全规则与 episodic log 一旦共享同一 token budget，并被相同的摘要策略反复压缩，规则保留率会快速坠落。Claude Code 的 /compact prompt 配合 Sonnet 4.6，第一次 compaction 后只保留 53% 的安全规则，五轮之后只剩 10%。

作者提出 Knowledge Triage：先按知识类型分类，再分配不同 retention policy。三个操作分别对应不同 context-management 场景：TypeCompact 按类型要求不同保真度；TypeDecompose 在主题过大时切分，但把相关 safety rule 复制到需要的 partition；TypeRetrieve 从外部存储检索时，把 scope 内规则置于普通 relevance 之前。

关键结果

方法 / 指标论文报告
Sonnet /compact：1 轮后 safety-rule recall53%
Sonnet /compact：5 轮后10%
TypeCompact：5 轮后96%
TypeDecompose locality violation0% vs uniform partitioning 93%
TypeRetrieve recall@50100% vs best single-shot retriever 73%
AgentArtifactCorpus396,934 个配置，来自 54,628 个公开 GitHub repo

作者还在 medical compliance、retail task 和 airline domain 做了 downstream behavioral evaluation，而不只比较文本相似度。

为什么重要

Context compaction 的错误抽象是：

1

旧信息太长 → 写一个更短摘要

长期 Agent 更合理的数据结构是：

1
2
3
4
5
6

hard constraints      → pin / verbatim / versioned
standing rules        → high-fidelity retention
current state         → structured update
procedures / skills   → executable or typed form
episodic history      → aggressive summarization
scratch / transient   → discardable

这和数据库的 storage tiering 更像，而不是普通 summarization。特别是“不得执行某动作”“必须等待确认”这类规则，少一个限定词就可能改变系统行为。

可信度与局限

论文的亮点是同时有 production config corpus、文本保留指标和行为测试；但知识类型分类器本身仍会出错，而且论文围绕安全规则设计的 benchmark 会天然偏向 type-aware 方法。真实 Agent 中“规则”“偏好”“临时状态”经常存在模糊边界，错误分型可能把不应永久化的信息过度 pin 住。

最值得继续追踪

最重要的是把 compaction 从“每次 context 快满时临时做一次”升级为 typed state lifecycle：明确哪些状态可摘要、哪些只能 supersede、哪些必须逐字保留，以及何时失效。下一步真正有价值的是长期线上 drift 和 false-pinning 成本，而不只是单次 retention recall。

3. TailSieve：RL / OPD Rollout 的真正尾延迟是整批训练的 Makespan

一句话结论： 在线 Serving 优化单请求 latency，训练 Rollout 更应该优化“一批请求什么时候全部结束”；少量超长 generation 会把大量 replica 拖在最后几个尾部样本上。

论文： TailSieve: Partial-Rollout-Guided Tail Routing for LLM Rollouts

发生了什么

RL、On-Policy Distillation 和 sampling-heavy evaluation 都需要成批生成大量 response。即便大多数请求很快结束，只要少数长尾 response 被塞进高并发 decoding batch，整个 rollout step 就要等待它们，GPU 资源在后期出现明显利用率下降。

TailSieve 利用一个经验观察：某些 prompt 在连续 policy update 中往往持续表现为 long-tail。系统先用 partial rollout 识别候选 tail group，再由层级 controller 动态决定隔离多少 tail group，以及 tail / bulk 两个 pool 如何分配 replica。低并发 tail pool 还可以使用更适合长生成的 speculative decoding。

关键结果

配置相对 uniform group routing
仅 Tail routing最高 1.67× speedup
+ route-specialized MTP / DFlash最高 2.59× speedup

被选中做 routing 的 prompt 最终仍会在当前 policy 下重新生成，因此作者认为 steady state 中仍保持 on-policy generation，并避免因为直接复用旧 response 引入额外 length bias。

为什么重要

训练基础设施通常围绕平均 throughput 做优化，但大规模 rollout 的目标函数更接近：

1

minimize rollout-step makespan

而不是：

1

maximize average requests / second

如果 1% 的超长请求决定最后 30% 的 wall-clock，优化普通样本意义有限。Tail isolation 也说明 RL 系统需要根据生成长度分布做 workload-aware scheduling，而不是把所有 prompt 当成同质任务。

可信度与局限

所有“最高 1.67× / 2.59×”都是 workload、模型、并发度和硬件相关结果，不能直接搬到任意 verl / vLLM / SGLang 集群。方法还依赖 long-tail propensity 在 policy update 之间具有一定稳定性；当策略快速变化或课程学习导致生成长度分布剧烈漂移时，partial rollout 的预测价值可能下降。

最值得继续追踪

真正值得落地的是把 tail_predictability、P95/P99 completion length、tail replica utilization、rollout-step makespan 和 policy version drift 放进同一 dashboard。若 tail identity 不稳定，静态分池可能反而增加调度开销。

4. EARM：Memory Retriever 也应该拥有“经验”

一句话结论： 一个长期运行的 Agent 不应每天为相似 query 重复支付完整 LLM reranking 成本；历史 relevance judgment 本身可以成为新的 Memory。

论文： The Retriever Should Remember: Experience-Amortized Reranking for Long-Term Agent Memory

发生了什么

传统 Agent Memory 通常只积累内容，retriever 自身却近乎无状态：每次 query 先做 embedding retrieval，再让 LLM reranker 对候选重新评分，评分用完即丢。

EARM 把过去获得的 query-memory LLM relevance score 写进一个稀疏在线矩阵，通过 causal matrix completion 学习不同 query 与 memory relevance 的共享结构。新 query 到来时，只直接评分少量候选，其余候选由历史经验估计，再把观察值和估计值混合用于 rerank。

关键结果

  • 相比纯 semantic retrieval，答案准确率最高提高 6.62%。
  • 当只有 17.5% candidate 接受直接 LLM relevance scoring 时，方法仍然保持有效。
  • 随 interaction 增加，历史 relevance observation 被持续复用，昂贵 reranking 从“每次都付费”转向“逐渐摊薄”。

为什么重要

这把长期 Memory 从内容层扩展到了检索策略层：

1
2
3
4
5

Content Memory:
过去发生了什么？

Retrieval Experience:
过去什么信息对什么问题真正有用？

对用户长期助理、企业知识 Agent 或多月运行的 Coding Agent，这种经验可能比继续扩大向量库更重要，因为 embedding similarity 并不等价于 downstream usefulness。

可信度与局限

矩阵 completion 隐含一个前提：query-memory relevance 存在可复用的共享结构。如果用户目标、知识库或任务分布长期漂移，旧 relevance score 可能成为 stale retrieval prior。另一个问题是“过去被 reranker 判有用”不等于“事实上有用”，错误 judge 也会被经验化。

最值得继续追踪

下一步应该加入 decay / versioning / uncertainty：对高置信、重复验证过的 relevance experience 长期复用，对 domain shift 后的旧分数逐步降权，并监控估计 score 与新 LLM judgment 的 calibration drift。

5. Generative RecSys：更细的 Token 和更漂亮的 Reasoning 都未必更好

一句话结论： 今天两篇推荐论文分别从表示和推理两端指出同一个问题：优化“中间表征看起来更丰富”并不保证最终推荐更有效。

论文 1： Rethinking Item Tokenization in Generative Recommenders: From Fixed Atoms to Semantic Subwords
代码： mxrcandy/Semantic-Subword-Tokenization
论文 2： The Disconnect Between Better Descriptive Reasoning Trace Quality and Recommendation Effectiveness

发生了什么

第一篇工作质疑固定长度 Semantic ID。历史行为中的每个 item 都被拆成多枚细粒度 token 后，Transformer 需要反复把同一 item 内部 token 重新组合，作者称为 Intra-item Attention Overload：本来应建模 item-to-item behavioral transition 的注意力，被消耗在 item 内部结构上。

Semantic Subword Tokenization（SST）因此只压缩历史 item：把稳定相邻 atom 合并为 variable-length semantic subword，同时仍让 target 使用固定长度 SID 解码。Behavior-induced Co-occurrence Augmentation 再补充 coarse prefix 的跨 item transition signal。作者在 3 个公开数据集、3 种 generative-recommender backbone 上报告优于固定长度和可迁移 variable-length SID baseline。

第二篇工作做了更直接的反例。研究者在三个 Amazon domain、同一个 Qwen3-1.7B backbone 上，用 Title vs SID × minimal vs extensive semantic grounding 做 2×2 控制实验。结果发现：显式 descriptive reasoning trace 虽然在自然语言 Title 下明显更 grounded、更可解释，却在标准 SFT 和 RL 训练下降低传统离线推荐效果；加强 SID alignment 提高了 trace quality，也没有稳定改善 recommendation effectiveness，只有更丰富 reward 能部分追回损失。

为什么重要

这两项结果共同说明，Generative RecSys 至少有三个目标不能混为一谈：

1
2
3

Representation efficiency
Reasoning / explanation quality
Recommendation utility

更细粒度的 SID 可能更有表达力，却增加序列长度和 intra-item burden；更可读的 CoT 可能更适合解释，却让模型把容量花在描述 item，而不是选择 item。

因此，如果业务目标是 ranking / retrieval，不能用“reasoning 更像人”“SID 更有语义”替代真实推荐指标。 反过来，如果产品确实需要用户可见解释，也不能只用 HR/NDCG 否定 reasoning value——它是另一个目标，应单独做 usefulness / faithfulness / trust 评估。

可信度与局限

SST 摘要没有给出一个可以跨数据集统一引用的 headline effect size，因此目前更应该把它看成对 tokenization inductive bias 的机制假设，而不是已证明的普适最优编码。Reasoning-trace 论文的结论也只适用于其训练目标、三个 Amazon domain 和 1.7B backbone，不能推出“推荐系统永远不应 reasoning”。

最值得继续追踪

最有价值的后续是 multi-objective Pareto：在固定 serving token / latency 下，同时画 Recommendation Utility、Trace Grounding、Explanation Usefulness 和 Sequence Length。只有这样才能知道某种 SID / reasoning 设计是在真正改善系统，还是把性能从一个目标搬到了另一个目标。

6. Sigmoid Attention：可学习 KV Eviction 可能需要重新考虑 Attention 归一化

一句话结论： 训练时把 KV gate 变小，和推理时真正删除 KV entry 是两件事；sigmoid attention 可能比 softmax 更容易跨过这个 soft-to-hard gap，但目前只是小模型机制证据。

论文： Sigmoid Attention as a Better Substrate for Learned KV Cache Eviction

发生了什么

Learned KV eviction 的典型训练方式是给 token 一个可微 soft gate：训练时只是减小该 token 对 attention 的贡献，而真正部署时为了节省显存，必须把对应 KV 物理删除。这就产生 soft-to-hard mismatch。

作者在 GPT-2-scale / OpenWebText 上做 $2\times2\times2$ 控制实验，分别改变 attention type、learned gating 和 positional encoding。结果出现一个反常识现象：dense sigmoid attention 本身比 dense softmax LM 更差，但进入 hard eviction 场景后，sigmoid-gated model 可以删除 KV entry，而 perplexity 相对自身 no-eviction reference 几乎不变。 在 matched live-cache protocol 下，learned sigmoid gate 的 PPL 低于作者实现的 H2O 和 KeyDiff；softmax learned gate 则没有稳定超过 post-hoc 方法。

为什么重要

这说明“KV eviction 算法”可能不是一个可以完全独立于 attention architecture 设计的插件。Softmax 强制 token 之间竞争并归一到 1，而 sigmoid 允许更独立的 gating；当目标是把某些 KV contribution 真正推到可删除区域时，两种归一化方式的优化几何可能不同。

可信度与局限

证据目前非常早期：GPT-2 scale、OpenWebText、workshop 级实验，没有证明在 7B–100B、GQA/MQA、RoPE、长上下文、量化 KV 和真实 serving kernel 上仍成立。论文比较的是 perplexity 与 cache protocol，不是端到端 P95 latency、session concurrency 或 GPU memory residency。

最值得继续追踪

如果后续大模型实验成立，值得把 attention normalization × learned eviction × KV quantization 联合研究，而不是继续把 eviction 当成冻结模型后的纯后处理。当前阶段更适合把它当成一个值得验证的机制假设，而不是部署建议。

今日值得收藏的代码 / 学习资源

Prime Agent：今天最值得直接读的 Agent Harness 代码。重点不是 UI，而是 persistent REPL、recursive session、Continual Harness、versioned state 和完整 resource accounting 如何组合。

Semantic Subword Tokenization：做 Generative RecSys 时值得直接检查 fixed SID sequence length、history compression 和 attention pattern 的实现，而不是只看最终 recommendation metric。

LitReview Arena：今天 arXiv 新列表中值得收藏的 Agent evaluation 资源。平台收集约 3,000 条专家判断；最强系统在 overall utility 的 decisive match 中对 human draft 只赢 23.0%，而现有 LLM Judge 与专家的一致性 Spearman $\rho=0.467$。用专家偏好校准的 LitJudge 提高到 $\rho=0.78$。这比“让另一个 LLM 给 Research Agent 打分”更接近真实研究效用评估。代码与数据：VanellopeAsher/LitReview-Arena。

KVBoost：如果关注 chunk-level KV reuse，可以顺手阅读。它尝试突破 prefix cache 必须共享连续前缀的限制，在 Qwen2.5-3B、1,000 个 bug-localization 样本上报告 TTFT 从 639.1 ms 降至 142.4 ms（4.49×），并维持约 99% accuracy。当前仍是单模型、单 workload 结果，真正部署前需要复测 cache invalidation、RoPE position repair 和真实并发。

这篇最值得读的原因不是 53% 或 10% 这两个数字本身，而是它把 Context Engineering 中一个经常被当成 Prompt 技巧的问题变成了系统设计问题：不同知识类型有不同的失真成本。

建议 30 分钟按这个顺序：

  1. 先看为何 uniform compaction 会让 safety rule 与 episodic log 竞争同一个 token budget；
  2. 看 TypeCompact / TypeDecompose / TypeRetrieve 分别对应哪一种 context-management failure；
  3. 看 downstream behavioral test，而不只看文本 recall；
  4. 最后思考自己的 Agent 中，哪些内容其实根本不应该进入“摘要”流程，而应该成为 versioned state / pinned constraint。

如果只带走一个原则，就是：

不要让“是否保留”由文本相似度决定；先由知识类型决定允许的压缩损失，再谈 relevance。

其中最关键的不是普通 ROUGE，而是两个行为指标：

\[R_{hard}(n)=\frac{\text{第 }n\text{ 轮后仍可正确执行的 hard constraints}}{\text{原始 hard constraints 总数}}\]

以及实际运行 20–50 个 probe 后的 behavioral_compliance。

停止条件： 如果三轮 compaction 后 hard_constraint_recall < 95%，或任何必须遵守的规则在 behavior probe 中发生一次高风险遗漏，就不要继续靠“把摘要 Prompt 写得更认真”解决。先把 hard constraint / standing rule 从普通 summary channel 移出，改为 pinned、typed、versioned state；episodic history 再继续做激进压缩。

如果规则保留良好，但 context 仍然过长，再优化 episodic compression、retrieval 与 cache；不要把容量问题和规则遗忘问题混在一起。

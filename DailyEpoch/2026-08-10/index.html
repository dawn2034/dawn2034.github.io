每日 AI 技术简报｜2026-08-10

截至今早，arXiv 的最新公开批次仍是 8 月 7 日：cs.AI 201 篇、cs.LG 162 篇、cs.IR 15 篇。今天不重复前两天已经讲过的 HarnessOpt、DASH、EnvACE、Gryphon-v2，而是继续从这一批里筛更值得深挖的工作。

今天最值得注意的信号很集中：Agent 的长期自我进化开始暴露“经验污染”问题；Generative Reward Model 的最佳接口可能本来就不是 scalar score；Skill Retrieval 的 Graph 增强存在一个很容易踩中的 topology ceiling；KV/压缩记忆的生产瓶颈正在从“压缩率”转向“运行时是否知道自己已经坏了”；推荐系统里，很多所谓 personalization gain 经严格对照后可能只是 global content weighting。

1. When Self-Evolution Backfires：Skill 越积越多，Agent 真的可能越来越差

这是今天我认为最重要的一篇。

发生了什么

典型 self-evolving Agent 的循环是：

\[\text{执行任务} \rightarrow \text{总结经验为 Skill} \rightarrow \text{写入 Skill Pool} \rightarrow \text{下一轮继续使用}\]

这篇论文指出一个此前经常被默认忽略的假设：

新蒸馏出来的 Skill 为什么应该自动进入生产上下文？

作者在 Terminal-Bench 2 上连续做五轮 evolution。无准入控制时：

\[48\%\rightarrow60\%\rightarrow62\% \rightarrow52\%\rightarrow50\%\]

Skill Pool 却一路从 35 条增长到 179 条。也就是说，性能在第 3 轮达到峰值，此后继续“学习经验”反而几乎把收益全部吐了回去。

作者将其拆成三种污染：

\[\text{Individual Contamination}\]

单个 Skill 本身有害；

\[\text{Combinatorial Contamination}\]

两个 Skill 分别没问题，组合后冲突；

\[\text{Systemic Contamination}\]

上述冲突积累，最终形成整个 Skill Pool 的性能拐点。

更麻烦的是污染具有继承性。后续 Skill 是在已经污染的 Pool 条件下生成的，所以即使后来把源头坏 Skill 删除，它的错误逻辑也可能已经被后代 Skill 吸收。实验中，事后删除已识别的坏 Skill 只恢复了约 17% 的性能退化。

解决方案：Skill 不是“写入”，而是“晋级”

论文提出 Verifier-as-Gatekeeper，VaG，把 Skill 分成：

\[Cold\rightarrow Warm\rightarrow Hot\]

只有 Hot Skill 才允许进入 Agent runtime。

Cold → Warm 需要同时通过三道检查：

  • 确定性的 schema 检查；
  • 在 held-out task 上进行单 Skill A/B replay；
  • LLM semantic review，检查虚构、矛盾或危险建议。

然后 Warm → Hot 再做 marginal-gain subset selection：只有把 Skill 加进整个 Pool 后联合性能真的改善，才允许晋级，从而捕捉“单独无害、组合有害”的冲突。

最终 VaG 的五轮性能：

\[52\%\rightarrow58\%\rightarrow62\% \rightarrow68\%\rightarrow72\%\]

Hot Skill 只有 37 条，约为 ungated Pool 的五分之一，却比 ungated 最佳轮次还高 10 个百分点。

为什么重要

这对最近大量 Skill / Memory / self-evolving Agent 工作是一个很直接的修正：

\[\boxed{ \text{Experience Accumulation} \neq \text{Capability Accumulation} }\]

长期 Agent 真正需要的可能不是：

怎么更自动地生成 Skill？

而是：

什么证据足以允许一个新 Skill 进入未来决策上下文？

这和软件工程中的 merge gate、数据库 migration、模型上线 gate 本质一样。

可信度与局限

证据比普通 Skill 论文强的一点是：任务由 Terminal-Bench 的确定性 verifier 判定，不依赖 LLM Judge，而且作者单独保留了 Holdout 和 Test split。

但主曲线只有 50 个 Event task，每个条件 3 次 replay，统计功效仍有限；论文所谓“phase transition”目前更适合作为一种实证现象，而不是已经证明具有普适 scaling law。另外，Terminal/Bash Skill 的可验证性比开放式研究、沟通、创作 Skill 高得多。

最值得继续追踪

真正关键的问题不是 Gate 能不能再多加几个 Judge，而是：

\[\text{Skill Admission Cost} \quad vs.\quad \text{未来污染成本}\]

尤其值得看：

  • Skill Pool 到几千、几万条后 replay gate 怎么扩展；
  • 是否可以使用 influence / counterfactual estimator 替代全量 A/B；
  • Skill lineage 是否应该成为一等元数据；
  • 如何做版本、依赖、失效和冲突管理。

2. RRC：Generative Reward Model 本来擅长“比较”，为什么非逼它输出一个绝对分数？

发生了什么

当前很多 GRM 的 RL 用法是：

给模型两个回答，让它输出 A/B preference，然后把：

\[P(A\text{ better})\]

直接当作标量 reward。

RRC 指出这里存在结构错位：

\[\text{GRM 天然学习的是} \quad y_i\succ y_j\]

但 RL 却强迫它回答：

\[r(y_i)=0.873\]

作者观察到，带 reasoning 的 GRM preference probability 极度饱和：

  • 42.3% 落在 $[0,0.1]$；
  • 46.0% 落在 $[0.9,1.0]$；
  • 中间 $[0.1,0.9]$ 只有 11.7%。

这意味着大量比较都被压成接近 0/1 的 reward，relative margin 信息基本消失。

RRC 怎么做

它不再读取 preference-token probability，而是直接保留 ranking structure。

第一种是 Self-Competitive Ranking：

同一个 Prompt rollout 出 $m$ 个 Response，相互比较：

\[o_i\succ o_j\]

然后用赢了多少对手构造 reward：

\[r(o_i) = \alpha \sum_{j\neq i} \mathbf1[o_i\succ o_j]\]

第二种 Anchor-Guided Ranking 则拿少量固定 Anchor 作为标尺：

\[r(o_i) = \alpha \sum_k \mathbf1[o_i\succ a_k]\]

把 Reward Model 调用复杂度控制到 $O(mn)$。

结果

8B Reward Model + reasoning 下，传统 probability reward 在 AlpacaEval2 为 35.8，RRC-AGR 为 39.4；加 voting@8 后达到 41.3。ArenaHardV2 则从 7.8 提高到 11.0 / 11.2。

有价值的是作者还做了成本分析。AGR 的训练时间约 10.6h，与 probability baseline 的 10.5h 基本相同，却把 AlpacaEval2 从 35.8 提高到 39.4；而 SCR 因为需要更多比较，训练时间增加到 13.2h。

为什么重要

这与 GRPO 的哲学其实很契合。

GRPO 本来就是：

\[A_i = \frac{r_i-\mu_G}{\sigma_G}\]

它真正需要的是同组 Sample 之间可靠的相对次序和相对差距。

如果 Reward Model 最擅长的恰好也是：

\[y_1>y_2>y_3\]

那么先逼它生成未经校准的 absolute score，再在 Group 内重新标准化，本身就有点绕。

更一般地：

\[\boxed{ \text{Judge capability} \neq \text{Scalar calibration capability} }\]

可信度与局限

这里不能只看 35.8 → 41.3。

voting@8 本质上增加了 Reward Model inference-time compute；作者做了 compute-matched control，结果仍支持 RRC，但不是“白捡的 5.5 分”。

另外 policy 主要还是 LLaMA-3.1-8B，Reward Model 为 3B/8B；能否在 32B–70B policy、长 Agent trajectory 和更昂贵 GRM 上保持相同性价比仍未知。Pairwise GRM 的调用成本很可能会成为实际瓶颈——代码仓库自己也明确提示，ranking / voting 会比标准 accuracy reward 增加 Reward Model inference。

最值得继续追踪

我会重点关注：

\[\text{Ranking Reward} + \text{Process / Turn-level Credit}\]

的组合。

RRC 解决的是 trajectory 间排序；AgentOPSD、DASH、ABSeeker 解决的是 trajectory 内 credit assignment。

这两层如果组合起来，比继续微调一个 absolute scalar RM 更值得研究。

3. Skill Retrieval 的一个负结果：用 Embedding 邻居建 Graph，大概率只是把同一信号算了两遍

发生了什么

《Comparative Approaches to Agent Retrieval over Large Skill Libraries》研究一个非常现实的问题：

Agent 有几百上千条 Skill 时，到底该加载哪几条？

在一个 875 条 Skill 的真实库上，作者构造了 117 条“不复述 Skill description”的 realistic query。

BM25 + MiniLM hybrid ranker 的 top-5 hit rate 为：

\[73.5\%\pm8.0\]

而用户只描述症状、没有直接说 Skill 名字时只有 62.8%。

作者本来希望通过 Skill Graph 补足剩余 Recall：

\[\text{query} \rightarrow \text{seed skill} \rightarrow \text{graph neighbours}\]

结果却失败了。

在相同 6 条候选预算下：

\[Hybrid@6=74.4\%\]

而：

\[Hybrid@1+Graph=63.2\%\]

Graph 低 11.2pp，$p=0.0007$。

为什么 Graph 没用

原因非常漂亮：作者构图的候选边，本身就是由同一套 embedding neighborhood 产生的。

于是：

  • 98.6% 的 typed edge 连接的都是 ranker 本来就已经会一起召回的 Skill；
  • ranker 漏掉的 query 中有 73% 在三跳内都无法从 Graph 到达。

也就是：

\[\boxed{ \text{Graph Candidate Space} \subseteq \text{Embedding Candidate Space} }\]

既然 Graph 的 topology 是 embedding 自己构造的，它不可能神奇地找回 embedding 完全没看到的区域。

作者称之为 pre-filter topology bound。

为什么重要

这不仅适用于 Skill Retrieval，也适用于很多 Graph RAG。

一个常见架构：

\[Embedding\ kNN \rightarrow LLM\text{ 标关系} \rightarrow Graph\ Search\]

表面上增加了一个 Graph 模块，但如果 Graph 的所有边都源自最初的 embedding kNN，那么：

Graph 可以改变局部排序和关系解释，但很难增加真正的 retrieval reach。

真正能打破这个 ceiling 的边，必须来自独立信号：

  • Runtime co-use；
  • dependency metadata；
  • import graph；
  • tool call sequence；
  • human taxonomy；
  • click / usage logs。

论文自己也把 production co-usage telemetry 列为下一步最有希望的独立信号。

一个很值得注意的评测问题

作者还发现，人工为自己系统写 Query 会产生明显的“description echo”偏差；因此专门使用 sibling team 制作的 non-echo query。

这也是 Agent Skill Benchmark 很容易被高估的地方：

如果 Query 里出现的词和 Skill description 天然高度一致，测到的其实更多是 lexical retrieval，而不是“Agent 是否知道何时需要这个 Skill”。

可信度与局限

这篇论文的结论范围写得相当克制：一个组织、一个 Skill corpus、一个 embedding 模型、117 个 query，每个 Query 已占 hit@5 约 0.85pp；而且没有测端到端任务成功率和 latency。

因此结论不是：

Skill Graph 没用。

而是：

从 Retriever 自己的 embedding neighborhood 构造出来的 Skill Graph，不应该被期待解决 Retriever 的 Recall 问题。

这个区别很重要。

4. 推理基础设施｜压缩 KV 后，最大的风险可能是“系统坏了，但所有指标看起来正常”

《Runtime Observability for Heterogeneous Attention Memory》是今天比较硬核的一篇系统论文。

发生了什么

现在越来越多模型的 memory 已经不再是一个简单 dense KV Cache，而可能包含：

  • dense KV；
  • latent/compressed KV；
  • learned sparse selector；
  • recurrent state。

作者把各种 attention memory 抽象成：

\[m_{t+1}=U(m_t,x_t)\] \[I_t=S(q_t,m_t)\] \[y_t=R(q_t,m_t,I_t)\]

即 Update / Select / Read 三个 stage，并要求每个 stage 暴露可以运行时检查的 error contract。

动机来自一个真实的 silent corruption：缓存结构仍合法、模型仍正常生成、Serving 也没有 crash，但 downstream task quality 已经下降。

论文在实际 Serving 的 DeepSeek-V4-Flash-FP8 上发现一个特别典型的问题：

压缩 KV 在没有 eviction、没有 identity reuse 时结果准确；出现 eviction 或跨请求 slot reuse 后才发生错误。进一步定位后发现，slot 被新请求复用，却没有正确 invalidation，导致新 owner 读到了旧 generation 的内容。

这与普通数值量化误差完全不同：

\[\text{value precision error}\]

和：

\[\text{memory lifecycle / identity error}\]

是两类故障。

为什么重要

未来做 KV Cache quantization、KV offload、latent cache 或 sparse memory 时，仅仅报告：

  • LongBench；
  • perplexity；
  • throughput；
  • HBM；

已经不够。

生产环境还必须回答：

我怎么知道某一个请求正在读取属于正确 request / slot / generation 的 cache？

作者提出的一个值得借鉴的原则是：

\[(\text{slot},\text{generation})\]

应该是 memory contract 的组成部分，而不是普通日志字段。

运行时监控成本

他们做出的 always-on probe 并不是免费。

CUDA Graph 下，只观察 28 层中的一层时：

  • throughput 变化 −0.94%；
  • TTFT P99 −0.14%；

均落在噪声范围内；但如果 28 层全部常驻监控，throughput 下降 10.16%，所以 full coverage 仍然只能当 diagnostic mode。

可信度与局限

作者对此写得比很多系统论文谨慎：实验只覆盖一个主要 production stack/version、小规模 retrieval battery，很多结果仍是 single-seed；论文明确不声称已经证明端到端成本收益，也不声称每层都可以低成本常驻监控。

另外需要区分：

这不是一个新的 KV compression algorithm。

它研究的是：

一旦你开始使用异构、压缩、共享 Attention Memory，如何让它变成一个可观测、可证伪的 Serving component。

最值得继续追踪

我认为这里会逐渐形成新的 Serving 领域：

\[\text{Memory Observability}\]

类似今天分布式系统中的 tracing / checksum / SLO。

尤其值得关注：

  • request-owner isolation；
  • slot generation；
  • eviction correctness；
  • cache migration；
  • prefix-cache 与 compressed-cache 混用；
  • quantized KV 的 corruption sentinel。

官方还公开了 artifacts、runtime guards 和 Lean formalization，并声称论文中的数字可以由 artifact 重建；架构特定的 probe injection 部分则未开放。

5. 推荐系统｜“个性化模态权重”可能根本没有在利用个性化

这是今天推荐方向最值得看的负结果。

发生了什么

很多 multimodal recommender 会学习：

\[w_u^{image}, \quad w_u^{text}, \quad w_u^{audio}\]

然后宣称：

不同用户对不同模态偏好不同，因此 per-user modality weighting 可以提升推荐效果。

问题在于常见实验只比较：

\[\text{per-user weighting} \quad vs.\quad \text{no weighting}\]

这无法回答：

收益来自“用户个性化”，还是只来自“图片整体上比文本重要一点”？

这篇论文用同一个 collaborative backbone 统一重实现了六种 per-user weighting head，并设计了两个严格对照：

\[\text{Utility Gap} = \text{Per-user Weight} - \text{Global Weight}\]

以及：

\[\text{Identifiability Gap} = \text{Correct user-weight binding} - \text{Shuffled binding}\]

结果相当残酷

一个全用户共享的单一 global modality weight，相对完全不用模态信息，已经带来 PairAcc：

  • +1.89pp；
  • +3.61pp；
  • +3.50pp。

三个数据集均显著。

但把这个 weight 进一步变成 per-user 后：

六种实现没有一个在三个数据集、三个指标上稳定超过 global weight。

少数正增益也都 ≤0.9pp，而且换 corpus 就翻转。MicroLens-100K 上六种 per-user head 三个指标全部负收益。

更有意思的是 Shuffle Control 也会骗人

KuaiRand 上 Attention head 有：

\[\text{real-shuf}=+4.64pp\]

也就是把用户权重随机打乱会明显变差，看起来强烈证明：

“模型真的学习到了用户专属模态偏好。”

然而它相对单一 global weight：

\[-0.69pp\]

也就是说：

权重确实绑定到了用户，但这种用户差异没有任何推荐价值。

作者进一步把 gate input 与 collaborative user embedding 解耦后，这个巨大的 shuffle effect 几乎消失，说明它主要是架构耦合产生的 identifiability，而不是有用 personalization。

为什么重要

这是推荐实验里一个非常通用的逻辑错误：

\[\text{模型输出因用户而不同} \not\Rightarrow \text{这种用户差异有价值}\]

Personalization claim 至少需要两个问题：

Identifiability：

换错用户之后会不会变？

Utility：

正确用户信息是否胜过最强的非个性化模型？

只有第一项是不够的。

这个框架同样可以用于：

  • user-specific LoRA；
  • per-user temperature；
  • user-conditioned feature gate；
  • personalization prompt；
  • 用户级专家路由；
  • user embedding conditioned calibration。

可信度与局限

论文用了多个 corpus、五个 seed、FDR correction，并补了 Amazon-Baby 与 LightGCN replication，因此作为 negative audit 可信度不错。

但结论严格限定于显式 per-user modality weighting，不能外推成：

多模态推荐的个性化没有用。

它也没有线上 A/B，因此只能说明这些 offline weighting 机制缺乏稳定增量。

今天值得精读 / 收藏的资源

《From Trajectories to Evidence》

这篇尤其适合做自动化推荐算法实验 Agent 的人读。

它问的不是：

Agent 做了多少次实验？

而是：

这几十轮实验到底证明了什么？

作者在 30 个工业 recommendation paper → production RankMixer adaptation 中发现：

  • 26/30 个方法的后续实验曾优于第一轮；
  • 但 22/30 最后一轮反而低于历史最佳轮。

所以直接把：

\[\text{final trajectory}\]

当成：

\[\text{learned knowledge}\]

是不成立的。

他们把实验结论分成：

\[\text{Repair}, \quad \text{Guard}, \quad \text{Withheld}\]

只有具有明确 evidence、attribution、trigger 和 applicability boundary 的结论才能进入长期 Memory。14 个候选 claim 最终只有 9 个进入 registry。

这个框架其实比“把所有实验 log 做向量检索”成熟很多：

\[\boxed{ \text{Trajectory} \rightarrow \text{Evidence} \rightarrow \text{Qualified Claim} \rightarrow \text{Reusable Memory} }\]

而不是：

\[\text{Trajectory} \rightarrow \text{Memory}\]

需要注意，即使 reference audit 判断某个 Memory 应该 Apply，五个 Apply case 中仍有一个产生负收益、一个中性；因此适用性判断只能决定“值得试”，不能替代真实实验。

RRC 官方仓库

代码已经把 RRC 做成 MS-SWIFT/GRPO 外挂式 Reward Plugin，支持 pairwise ranking、majority voting 和 reference-anchor reward，并可连接 OpenAI-compatible Reward Model endpoint。仓库也明确说明 ranking/voting 会增加 RM inference，适合先在较小 num_generations / vote_n 下验证。

对于想理解 GRPO / RLHF 工程实现的人，这比只看公式有价值，因为它直接展示：

\[\text{rollout} \rightarrow \text{RM service} \rightarrow \text{group ranking} \rightarrow \text{reward plugin} \rightarrow \text{GRPO}\]

如何接起来。

X.com 近 24 小时技术信号

今天仍然没有足够可靠的数据让我负责任地给出“近 24 小时热门 AI 技术推文榜”。

我针对 RRC、Self-Evolution Backfires、Skill Retrieval 等关键词做了 X 限域检索，公开网页索引返回的主要仍是几个月前的 Agent / Skill 帖子，而不是能同时验证 8 月 9–10 日发布时间、原作者身份、互动量以及技术正文的新线程；例如检索到的 Hermes/self-evolving Agent 高互动帖子实际发布于 4 月。

因此今天继续不拿旧帖或搬运号凑“24 小时热榜”。这一栏目前最值得手动追踪的关键词是：

skill contamination、ranking-based reward construction、Skill retrieval topology bound、KV cache observability。

今日最值得花 30 分钟阅读的一项

When Self-Evolution Backfires

今天我会把 30 分钟给它。

不是因为它的 72% 是多么重要，而是因为它挑战了 self-evolving Agent 中一个非常核心、却长期没有被认真验证的假设：

\[\boxed{ \text{只要经验来自真实任务，就应该保存} }\]

这显然不成立。

建议阅读重点不是方法公式，而是四件事。

先看 48 → 60 → 62 → 52 → 50 的非单调曲线，理解 capability–contamination tipping point。

然后看为什么 post-hoc rollback 只能恢复约 17%，真正理解 Skill lineage 的不可逆性。

接着看单 Skill A/B 与 joint subset evaluation 为什么分别解决不同问题。

最后重点审查 Event=50、Holdout=14、Test=25 这个样本规模，避免把漂亮的 inverted-U 曲线过早当成普适 scaling law。

我认为它最值得带走的不是 VaG 这个具体算法，而是：

\[\boxed{ \text{长期 Agent 的写入路径， 应该比读取路径更严格} }\]

因为读取错一次，只影响一次决策；写入错误经验，则可能改变未来数百次决策以及未来产生的新经验。

今日可立即实践的一件事

给任何已有的 Agent Skill / Experience Memory 系统加一个最小版 Pre-Commit Skill Gate，不要再让新 Skill 自动进入生产 Pool。

先保留一个固定、从不用于 Skill 生成的 30–100 个 regression task。每产生一个新 Skill $s$，分别运行：

\[R(M)\]

和：

\[R(M\cup\{s\})\]

只在：

\[\Delta_s = R(M\cup\{s\})-R(M) \geq0\]

时允许进入 Candidate Pool。

然后不要到这里就结束。每批 Candidate 再与当前 Hot Pool 做 joint test：

\[\Delta(s\mid H) = R(H\cup\{s\})-R(H)\]

只有：

\[\Delta(s\mid H)>0\]

才真正晋级 Hot。

同时为每条 Skill 至少保存四个字段：

1
2
3
4

skill_id
parent_skill_ids
evaluation_set_version
admission_score

其中 parent_skill_ids 很重要：未来一旦发现某条 Skill 污染，至少能够做 lineage rollback，而不是只删除一个 Markdown 文件然后假装问题解决了。

第一版甚至不需要 LLM Judge。优先使用：

\[\text{Executable A/B} > \text{LLM semantic review}\]

因为这篇论文的消融中，去掉 held-out behavioral replay 后性能从 72% 降到 62%，是三种单 Skill verifier 中损失最大的组件。

如果做完以后发现 Skill Pool 从 300 条砍到 60 条，但任务成功率反而上升，那并不意外。最近几天的 Skill-Use、ContinualSkillBench、FinEvo-Bench、When History Lies，以及今天这篇工作正在逐渐指向同一件事：长期 Agent 的瓶颈已经不是“能不能积累经验”，而是“能不能治理经验”。

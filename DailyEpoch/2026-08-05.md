# 每日 AI 技术简报｜2026-08-05

arXiv 最新公开批次为 **2026 年 8 月 4 日**：cs.AI 收录 464 项、cs.CL 189 项、cs.LG 340 项、cs.IR 45 项。分类之间存在交叉收录，不能直接相加为唯一论文数。今天值得关注的主线是：**Agent Harness 开始成为可训练对象、长期记忆转向模型内部状态、RLVR 优化目标从平均奖励转向任务间失败分布，以及推测解码开始修补扩散草稿的因果缺失。**

## 今日核心判断

1. **Agent 自我改进正在从修改 Prompt 转向修改可执行 Harness。**真实环境重跑比 LLM Judge 更可靠，但同批任务优化容易产生过拟合和能力回归。
2. **持久化隐状态可以补足有限 KV 窗口，却不能替代原文档案。**它适合保留语义和任务状态，不适合精确恢复任意旧 Token。
3. **RLVR 不应只最大化平均成功率。**让成功更均匀地分布到不同题目，可能比反复强化少数容易题更有价值。
4. **扩散式草稿的瓶颈不是生成速度，而是缺少 Token 间因果依赖。**一个很小的因果修正器就能明显提升接受长度。
5. **推荐系统中的“Agent 化”未必需要 LLM。**抖音的新工作本质是自触发时序决策加廉价前置过滤，计算节省主要来自后者。

## 1. Harness-R1：让模型直接进化 Agent 的执行框架

### 发生了什么

Harness-R1 训练了一个专门的 **Harness Engineer**。目标 Agent 完成任务失败后，系统将失败轨迹交给该模型，由其修改四类可执行 Hook：

- 初始化阶段；
- 决策前；
- 动作执行前；
- 工具反馈后。

补丁通过沙箱和静态检查后，会在真实环境中重新执行。奖励直接取任务结果的改善，而不是让另一个模型判断“这段修改看起来是否合理”。

在 WebShop、ALFWorld 和 DBBench 上，冻结的 Qwen3.5-9B 平均成功率从 **44.3% 提升至 53.6%**；目标 Agent 经过任务训练后，仍可从 59.2% 提升至 64.2%。在 20 个未参与 Harness-R1 训练的目标模型上，平均增益约为 7.06 个百分点。

### 为什么重要

以往 Agent 优化通常集中在模型、Prompt、Skill 或 Memory。Harness-R1 把另一个关键变量显式化了：

$$
\text{Agent 行为}
=
f(\text{模型},\text{工具},\text{Harness})
$$

许多失败实际来自 Harness：错误反馈被截断、工具返回没有结构化、终止过早、动作未经过验证。针对这些问题，换更大模型可能远不如修改执行框架有效。

### 可信度与局限

结果不是无条件泛化。训练奖励主要来自**产生失败轨迹的同一批任务重跑**，属于较强的 transductive 设置。论文确实在 1,270 个留出任务上报告了约 8.9±1.5 个百分点增益，但也记录了小幅回归，并展示过一个补丁将原本 7/10 的成功率直接降到 0/10：过于宽泛的动作强制规则破坏了已有能力。

它目前更准确的定位是：**有真实反馈约束的程序补丁搜索**，而不是已经解决了 Agent 的通用自我进化。

### 最值得追踪

是否能把奖励改为“新修复任务收益－旧成功任务回归－额外推理成本”，以及补丁能否跨模型、跨环境长期复用，而不是为每个目标重新生成。

## 2. LiveMem：把长期状态保存在有限 KV 窗口之外

### 发生了什么

LiveMem 为模型增加一个固定大小的内在 Memory State。旧 Token 的 KV Cache 被淘汰后，模型仍保留由历史内容压缩形成的状态；Serving 系统只需维护有限活动窗口和该固定状态，不再让显存随会话长度无限增长。

在 LongMemEval 等任务上，LiveMem-RL 的综合结果较均衡：Wiki QA 为 0.560、Conversation 为 0.264、时间信息任务为 0.678。但它并非各项最优——RAG 在 Conversation 上达到 0.348，Context2LoRA 在时间任务上达到 0.739。

### 为什么重要

当前长期 Agent 常在三种不理想方案中选择：

- 保留全部 KV，显存线性增长；
- 截断历史，状态直接丢失；
- 反复摘要或检索，引入额外调用和检索误差。

LiveMem 提供第四条路线：将历史持续压缩进模型内部状态。这更像 RNN 式状态连续性，而不是外部知识库。

### 可信度与局限

论文明确表明 LiveMem **不能精确恢复任意旧信息**。在 needle-in-a-haystack 测试中，一旦原始证据离开 32K 活动窗口，其精确 Token 恢复能力与普通基线一样低。换言之，它是有损语义压缩，而不是无限上下文或精确档案。

合理应用包括用户偏好、任务阶段和对话主题；合同条款、代码片段、数字和可审计证据仍应交给外部存储与检索。

### 最值得追踪

记忆状态的污染与遗忘机制、多个会话之间的权限隔离，以及它与 RAG 的组合是否优于二选一。

## 3. MMPO：不仅追求平均成功，还要减少“总是失败的题目”

### 发生了什么

MMPO 将每个问题的失败概率视为随机变量，不只优化一阶矩，即平均失败率，而是联合优化多个失败概率矩。作者证明，该目标等价于降低“在有限次尝试内首次成功所需的期望次数”。

在 Qwen3-1.7B／4B、MATH7.5K 和五个数学评测上，4B 模型相对 GRPO 平均提高约 2.6 个百分点。按多次采样评价时差距更明显：平均 Pass@16 从 GRPO 的 62.2 提升至 **66.2**。

### 为什么重要

普通 GRPO 可能通过不断强化一部分“已经偶尔能做对”的题目提高平均奖励，却对始终失败的问题贡献很少。MMPO 试图让能力分布更加均匀：

$$
\text{少数题反复成功}
\quad\longrightarrow\quad
\text{更多题至少有一次成功机会}
$$

这对需要 Best-of-N、验证器搜索或 Agent 重试的系统尤其有意义，因为系统效用往往更接近 Pass@K，而不是单次平均奖励。

### 可信度与局限

当前证据只来自 1.7B／4B 数学模型和确定性验证奖励。MMPO 训练出的回答也更长，部分提升可能来自增加测试时计算，而不仅是更好的能力覆盖。其结论不能直接外推到开放式 Agent、主观偏好对齐或噪声 Reward Model。

### 最值得追踪

在固定输出 Token 和固定 GPU-hour 下是否仍领先，以及它能否缓解 Agent RL 中“简单任务越来越强、困难任务一直全错”的课程塌缩。

## 4. xPress：为扩散草稿补上一层轻量因果关系

### 发生了什么

块扩散草稿模型可以一次并行预测多个 Token，但各位置主要来自边缘分布，缺少严格的自回归因果依赖，因此草稿内部容易不一致，最终被目标模型大量拒绝。

xPress 在扩散草稿之后增加一个轻量因果 Refiner，对整块候选并行重排序。在 Qwen3-8B、数学、代码和对话等七个评测上：

- 平均接受长度提高约 30%，最高 56%；
- 相对原始 dFlash，吞吐平均提高约 **1.29 倍**，最高 1.7 倍；
- 相对普通自回归解码，完整系统平均约 6.2 倍加速。

### 为什么重要

它指出了扩散式推测解码的核心矛盾：

> 并行生成越强，候选之间的因果一致性往往越弱。

xPress 没有重新把整个草稿过程变成串行，而是只用一个很薄的因果模块修正依赖，属于比较干净的速度—质量折中。

### 可信度与局限

主实验只覆盖 Qwen3-8B、固定块大小和特定 dFlash 配置；延迟测试在单张 H200 上完成，而训练每个配置使用 32 张 H100。“轻量”描述的是推理 Refiner，不代表开发和训练成本低。真正新增收益应看相对 dFlash 的 1.29 倍，而不是只宣传相对普通解码的 6.2 倍。

### 最值得追踪

连续批处理下的吞吐、不同接受长度分布，以及它与原生 MTP、Prefix Cache 和量化目标模型的兼容性。

## 5. STEPS：抖音如何让 Push 推荐自行决定“下次何时再判断”

### 发生了什么

STEPS 已在抖音超过十亿用户规模部署。系统包含：

- Planning Agent：决定下一次触发决策的时间；
- Execution Agent：判断当前是否发送通知；
- 轻量过滤器：在进入昂贵完整推荐链路前拦截低价值请求。

六个月日志训练、14 天设备级随机 A/B 中，论文报告：

- 用户活跃天数提高 0.2843%；
- 关闭 Push 权限的行为下降 1.9089%；
- 计算资源下降 79.42%。

### 为什么重要

传统 Push 系统按固定间隔反复唤醒推荐链路，即使用户近期明显不活跃或刚收到通知。STEPS 将“何时再次决策”本身纳入动作空间，让系统对不同用户使用不同节奏。

不过，“Agent”在这里主要是 Decision Transformer 式序列决策，并非 LLM Agent。技术价值不应依赖命名。

### 可信度与局限

超十亿用户和随机线上实验提供了较强工业证据。但 **79.42% 的计算节省主要来自轻量前置过滤器**：单独使用过滤模块就减少约 74.88% 资源；Planning Agent 本身只减少约 4.54%。

因此，最可复用的结论不是“上 Agent 可以节省 80%”，而是：

> 先用极低成本模型判断是否值得启动完整推荐链路，往往比直接优化昂贵主模型更有回报。

### 最值得追踪

更长周期的用户疲劳、低活跃用户是否被过度沉默，以及控制活跃度与打扰风险的权重在不同人群中如何校准。

# 今日最值得花 30 分钟阅读的一项

## Harness-R1

建议这样分配：

- **5 分钟**：理解为什么优化 Harness 不等同于优化 Prompt；
- **10 分钟**：阅读四个 Hook 和真实环境重跑奖励；
- **10 分钟**：重点检查留出任务、未见模型和回归案例；
- **5 分钟**：查看仓库的沙箱、安全限制和训练成本。

最重要的结论不是“Agent 已经会自己改进自己”，而是：

$$
\text{可执行修改}
+
\text{真实环境验证}

>

\text{语言上听起来合理的反思}
$$

同时，任何自生成补丁若没有旧能力回归集，都不应直接上线。

# 今日可立即实践的一件事

对现有 Agent 做一次 **Harness Patch 配对审计**：

1. 抽取 30 条失败任务，并保留至少 30 条原本成功任务作为回归集。
2. 将 Harness 限制为四个明确 Hook：初始化、决策前、动作前、反馈后。
3. 每次只允许生成一个作用范围明确的补丁，禁止动态导入、文件写入、网络访问和任意 `eval`。
4. 分别在失败集与回归集真实重跑，不使用 LLM Judge 代替环境结果。
5. 计算：

$$
\text{Patch Net Value}
=
\text{修复的失败数}
-
\lambda\cdot\text{新增回归数}
-
\mu\cdot\text{额外 Token 与延迟}
$$

6. 对支付、删除、发送和权限修改类任务，将回归惩罚 $\lambda$ 设置得远高于普通读操作。
7. 只有留出回归集上的净收益置信下界仍大于零，才把补丁加入候选 Harness。

这能快速判断你的系统瓶颈究竟在模型能力，还是在执行框架本身。

今日主线： Agent 的规模化落地正在分出两条路线：重复且稳定的任务应尽量从推理时规划蒸馏为可审计的确定性工作流；需要长期学习的任务，则必须证明一条新经验不会破坏旧能力。推理基础设施还出现一个反直觉信号：Prefix Cache 越重要，越可能因为短时流量冲击进入持续性低吞吐状态。本期优先读机制和失败条件，而不是只看排行榜。

归档日期： 2026-11-13（Asia/Shanghai）；执行起始： 2026-11-13 07:19:11 +08:00。优先观察窗口： 北京时间 11 月 12 日 07:19 至 11 月 13 日 07:19。由于此时间段可直接核验的高质量新论文有限，主要研究窗口扩至 72 小时（11 月 10 日 07:19 起）；仅对少量推理系统案例回看 7 天（11 月 6 日 07:19 起）。本期论文多于 11 月 10 日首次提交、11 月 11 日进入 arXiv 新列表，均不是 11 月 13 日首次发表。论文实验数字均为作者报告，除特别说明外未见独立复现。

二、重点精读：Agent 能力与自进化

1. ReTrace：把反复执行的 Agent 轨迹编译为无需 Planner 的程序

发生了什么。 研究将 SOP 与少量带推理说明的 Agent 工具轨迹输入系统，先逐步抽取「何时调用哪项工具」的条件，再融合为规则中间表示，最后生成可执行的编排代码。关键不是简单 Replay 工具调用：相同工具链在不同输入下可能走不同分支，因此需要恢复条件。论文在 11 月 10 日提交。

关键结果。 作者在内部 79 个流程上报告工作流完成率 93.8%、原 Agent 96.8%，每任务成本低 24%；在 $\tau^2$-Bench 上是 75.8% vs 80.6%，运行时 1.3 秒 vs 170 秒。对有标注失败进行三轮修复，可让部分两条轨迹训练的工作流从 66.7% 升到 81.2%。

为什么重要。 高频、规则稳定的工具任务可能不值得每一步都支付一次大模型决策成本。对商品可售检查、订单处理、考勤核验和客服 SOP，可用 Agent 发现规则，用 Deterministic Workflow 执行已覆盖路径，异常再回退给 Agent。

可信度与局限。 已核验原论文的方法与实验章节；内部数据不可独立检查，几类成功率仍落后于原 Agent。1.3 秒与 170 秒不能视作同等任务下任意系统都能获得百倍加速，需区分工具本身耗时、构建成本与未见分支。继续追踪： 路由遗漏率、未见分支回退、规则版本化、每月调用量下的构建成本摊销。来源：论文及实验附录。

2. FGSE × WikiTrace：Agent 记忆应有「准入门槛」和「证据追溯」

发生了什么。 FGSE 将一次经历产生的教训表述为具有适用前提、行为改变、预期效果和 Verifier 的可证伪假设。先在临时状态中跑目标任务、故意反例和旧任务回归，再决定提交、细化或拒绝。WikiTrace 解决另一问题：Agent 读取一条旧经验时，经常不知道它从哪些原始行动和成败证据归纳而来；因此让 Insight 连接轨迹摘要及原始轨迹，需要时逐层下钻。

关键结果。 FGSE 作者报告 WebArena 成功率 39.8、AppWorld 平均完成率 78.8，且有害提交更新为 3.6%、回归损伤为 1.3%（均为其测试定义）。WikiTrace 在五个 Agent 基准上报告优于只有同样 Insight 而无证据链接的对照，并降低「加记忆反而做错」的情况。

为什么重要。 对长期购物助手，「用户曾经想买 15 寸电脑」与「用户现在只考虑轻薄 13 寸」是有时间和场景范围的状态变更。单纯把两句文字塞进向量库，会让过时经验干扰当前决策。FGSE 对应写前验证，WikiTrace 对应用时审计，两者可独立实现并组合。

可信度与局限。 两者是独立预印本，不能把实验结果跨论文相加；FGSE 依赖可用的反证样本与可靠 Verifier，WikiTrace 下钻增加 Token、检索和隐私治理成本。继续追踪： Memory-induced Regression Rate、错误记忆撤销率、来源不可靠时的拒用策略及用户删除后是否清理全部派生记忆。来源：FGSE · WikiTrace · WikiTrace 官方代码。

3. AutoScaffold：用训练失败轨迹自动设计「临时脚手架」

发生了什么。 冻结 Teacher 周期性读取 Student 的 RLVR Rollout，针对任务类别生成通用策略，也针对少数难例生成具体 Hint，并随能力提高动态撤除或修改。这些 Scaffold 仅在训练提示中使用，评估时移除，目标是让原本零正例的难题产生可学习信号，而不是在推理时偷偷借用教师。

关键结果。 论文在 ALFWorld、搜索问答、数学与 GPU Kernel 生成四类任务上报告无 Scaffold 评测时均优于各自 RL 基线，包括 ALFWorld +7.2 个百分点、搜索 QA 平均 Exact Match +4.0 个百分点；KernelBench 上「正确且快于 PyTorch」的任务占比最高增加 5.0 个百分点。

为什么重要。 标量 Reward 对失败轨迹的信息利用率很低；当一个 Group 全错，GRPO 风格相对优势难提供有效梯度。动态提示类似可随学生能力消失的 Curriculum，可与工具救援、数据重采样比较成本效率。

可信度与局限。 教师调用、诊断和提示校准有额外成本，部分跨方法对比不共享完全相同预算。继续追踪： 固定总训练 FLOPs、Teacher Token 与 Student Step 后，新增成功轨迹是否转化为未见任务泛化；验证是否发生训练标签泄漏。来源：论文与训练案例。

4. Policy Coverage Collapse：奖励上涨时也可能丢掉正确答案

发生了什么。 Huang 等研究语言模型后训练的策略覆盖率，指出 REINFORCE/PPO/GRPO 家族的某些更新会把起始模型本来能够采样出的优质响应概率压到接近零。即使目标 Reward 改善、对原模型施加 KL 约束，这一 Coverage Collapse 仍可能出现。作者分析将 KL Reference 周期性重置为最近策略的 Approximate Policy Mirror Descent。

为什么重要。 推荐与 Agent RL 经常只检查平均 Reward；如果历史中可行但低频的长尾动作被训练抹掉，Reward 可以短期向上而策略失去恢复力。应同时监控优势响应支持集、探索熵与不同难度桶的解答覆盖率。

可信度与局限。 该工作强项是理论机制，不是证明在每个实用 GRPO 实现上都已发生同等程度的塌缩。收敛结论依赖 Softmax Linear Policies 等设定，不能直接等同大规模 Transformer 的全局保证。继续追踪： 训练中定期重置 Reference 的稳定性、KL 曲线、OOD Pass@k 与真实学习效率。来源：论文。

三、推理与基础设施：局部增益之外的系统风险

5. REAL Loss：投机解码应该直接优化接受长度

发生了什么。 Draft Model 通常以 CE/KL 拟合 Target 分布，但服务提速取决于整个 Draft Block 连续被接受多少 Token。REAL 指出一些 Block-level Proxy 平均了错误路径的后续接受概率，可能产生协方差偏差，甚至改变梯度方向；它用路径权重与 Rao-Blackwellization 直接估计真实 Expected Acceptance Length。

关键结果。 作者在 Qwen3.6-35B-A3B Target 与 Domino Drafter 的受控损失对比中，在九个任务子集和五个 Seed 上报告优于若干 Loss 基线。优势是只替换训练损失，不强制更换推理引擎或 Draft 架构。

可信度与局限。 目前证据主要是 Loss-level 与接受长度实验；EAL 的提高不保证 P95、GPU 利用率或能耗按比例改善，某些长尾任务的 Draft 成本可能抵消收益。继续追踪： EAL / 验证成本、Token/s、P95、不同采样温度、批处理与推测树宽度下的同预算比较。来源：论文 · 作者参考实现分支。

6. Prefix Cache 的持续性崩溃：短时流量冲击为何拖垮后续 70 分钟

发生了什么。 《Bursts That Outlast Themselves》用相同基础负载做匹配实验，发现 Agent 会话上下文逐步增长，短时间额外到达会挤出可复用 KV；接下来缓存 Miss 令请求变慢、活跃会话积压，工作集更大，形成自我强化的恶性循环。在 12 对匹配实验中有 9 对出现崩溃、反向为零。部分运行中缓存命中率降至约 10%、吞吐约减半，余下约 70 分钟仍恶化。

为什么重要。 Prefix Caching 不仅是加速功能，还改变了队列系统的稳定区。部署 Agent Server 时必须结合会话生命周期、每活跃会话 KV 预算和 Admission Control，而不仅看平均请求数。

可信度与局限。 作者测试 vLLM，并用 Qwen3-32B、SGLang 和 SWE-bench 风格轨迹做了扩展；但属于受控工作负载，硬件池容量、真实会话暂停能力与流量模式会影响阈值。仅限制新请求在其匹配实验中恢复效果差，而暂停已有会话的容量治理更有效。继续追踪： 缓存工作集/池容量比、命中率滞后、活跃 Session 分布、Burst 后恢复时长。来源：论文。

7. Evolving Infra：从 P/D 固定角色走向 Agent 事件驱动的算力调度

发生了什么。 系统把 Prefill/Decode 算力角色与 KV Cache 管理解耦：节点可按负载切换计算角色，独立的 Agent-aware KV Manager 根据上下文复用信号指导缓存迁移和淘汰。作者在 Coding、Math、Computer-use 等工作负载，以 GLM-5.2、Kimi K2.6 和最高 256 张 GB300 GPU 进行评估。

关键结果。 相对所选 Dynamo 基线，论文报告平均端到端请求时延最高改善 4.1×、P95 TTFT 最高改善 14×。这两个都是跨不同配置的「最高」数字，不能乘算，也不意味着整体任务完成时间必然同等提高。

为什么重要。 Agent 请求不是相互独立的 Text Completion：工具使用导致短间隔、长共享前缀和高方差 Decode 长度。要提升生产效率，Serving 层需要利用 Agent Context 的生命周期信息。

可信度与局限。 需要成本、排队策略和 Dynamo 版本对齐；多机高端 GPU 结果对个人部署不具直接可迁移性。继续追踪： 同等完成任务数的 GPU-hours、预填/解码节点切换代价、缓存冲击下的调度鲁棒性。来源：论文。

四、推荐系统与 RAG：建模细节和证据粒度

8. SHARP：先决定类别，再约束 Semantic ID 商品/地点预测

发生了什么。 Next-POI 任务中，SHARP 将用户长期与近期出行模式压缩为动态轨迹记忆，结合全局及时间条件的类别转移图，先推断地点类别，再通过 RQ-VAE 学习的 Semantic ID 预测具体 POI。论文在三个真实数据集上报告相对最佳基线平均 Acc@5、Acc@10 分别提升 5.29、4.52 个百分点。

为什么重要。 电商生成式推荐也面临「意图类别正确，但具体候选不合法」的问题。类别引导与 Semantic ID 联合训练可作为约束生成的一种结构性方案，尤其适用于带时间周期的消费/位置序列。

可信度与局限。 POI 的地理邻近、时序重复模式和电商商品长尾存在显著不同。三套离线数据无法说明在线 CTR、GMV 或可售约束的收益。继续追踪： 冷启动、行为漂移、Semantic ID 碰撞、时间切片泄漏、Constraint Violation 与线上实验。来源：论文。

9. CLADE：部分真实证据比完全缺证据更容易诱发幻觉

发生了什么。 RAG 检索到上位概念（例如疾病家族）却没检索到具体答案时，模型常把「大类正确」误当作「具体项已证实」。CLADE 称其为可解析但不足的证据情形；作者把具体疾病名替换为家族名，发现相较删除该句，模型拒答率下降 17.4 个百分点。在 PrimeKG 的家族级 Passage 中，相对无信息 Passage 拒答减少 13.8 个百分点，但猜测约半数错误。

为什么重要。 产品推荐与金融检索存在同型错误：文档证明某品牌支持某功能，不代表特定型号、特定客户、特定地区可用。检索相关性不等于实体级证据充分。

可信度与局限。 主要在生物医学及生态实体体系测试；领域本体覆盖与实体匹配会决定修复是否可行。作者发现本体能把真答案放入候选列表的比例较高，但页面上的上位概念字符串匹配覆盖很低，因此「接一个 Ontology」不是一键解决。继续追踪： Entity Resolution、证据粒度标签、必须补查的触发阈值和错误确定回答率。来源：论文。

10. 从 Search 到 Decision：Agent 检索应评估「是否值得搜」而不只评估排序

发生了什么。 11 月 10 日预印本 From Search to Decision 将信息寻求拆解为多种相互作用的能力，比较检索路由、查询重写、工具探索、证据使用与资源感知决策的训练信号和 Credit Assignment。它是研究综述，不应当作某个单模型取得新 SOTA 的证据。

为什么重要。 对 Shopping/Search Agent，检索的价值应定义为执行前后的决策改进：模型是否在不确定时补查、补查是否改变正确决策、价格是否值得增加工具调用。可信度与局限。 文献间任务、工具和成本定义不同，无法直接跨论文比较「最优搜索策略」。继续追踪： Prospective Retrieval Utility、固定预算的成功率与不同检索环境中的 OOD 泛化。来源：原文。

今日最值得花 30 分钟阅读的一项

ReTrace：Distilling Tool-Using Agents into Planner-Free Workflows。建议用 8 分钟读 Method 的条件提取与规则融合，10 分钟读三组 Benchmark 的成功率、延迟与修复结果，7 分钟读 Limitations 和未见分支处理，最后 5 分钟计算自己一个高频流程的 Break-even：一次构建与回归成本 / (原 Agent 单次成本 - 编译工作流单次成本)。比单纯复制「1.3 秒 vs 170 秒」更能决定是否值得部署。

今日可立即实践的一件事

给 ShoppingAgentLab 做一个「Agent → Workflow」编译可行性审计，不训练模型也能开始。 抽取 20～30 条同类型购物流程轨迹（例如商品搜索 → 规格核对 → 可售性检查 → 排序 → 回复），按 state / condition / tool / output / next_state 标注决策分支；从前 70% 轨迹提取规则，用后 30% 按商品或时间切分的未见轨迹测试。A 组仍执行原 Agent，B 组执行规则工作流，规则匹配失败则回退 A；报告 Task Success、硬约束违规、分支遗漏、Tool Calls、Token、P50/P95 及单位成功任务成本。若规则遗漏导致违规上升，不应因 Token 节省而上线。

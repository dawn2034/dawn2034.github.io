今日主线： Live Weight Adaptation · Harness Shortcut Auditing · Scientific Agent Environments · SSD-streamed MoE · One-Step Sponsored Search · Trustworthy Agent Auto-Tuning

截至今天早上，arXiv 最新常规公告批次为 2026 年 9 月 17 日：cs.AI 204 条、cs.CL 127 条、cs.LG 219 条、cs.IR 17 条；不同分类存在大量交叉收录，不能直接相加。今天高信号工作的共同主题，是继续把“模型之外的状态”变成一等工程对象：运行时数据可以编译进低秩权重；Harness 的提升需要跨协议反事实审计；科研代码可以被包装成可执行 RL 环境；MoE expert 可以驻留 SSD、通过提前路由隐藏 I/O；推荐／广告检索开始尝试减少级联阶段；而 Agent 自动优化系统本身也必须接受严格的测量治理。

今日核心判断

  1. “把知识塞进 Context”之外，出现了把运行时数据直接编译成权重的更激进路线，但适用边界非常清楚。 Infinite-Parameter LLM 用 hypernetwork 将现场数据生成低秩 FFN modulation，并在会话中维护 latent-code belief，使有效权重随交互持续变化。短而干净的 SQuAD 上，普通 in-context F1 为 85.3，data-to-weights 只有 51.8；到了 noisy multi-passage 的 MS MARCO，结果反过来为 33.6 vs 48.0。因此它真正值得追踪的点是“何时值得编译”，而不是把所有 Context 都改写进权重。

  2. Harness 自动优化如果只看固定 benchmark，即使做 task holdout 也可能学到 benchmark-wide shortcut。 Bad Genius / CHASE 在 OfficeQA 中展示了非常直接的反例：一个 harness 在 released protocol 上相对 parent +8.16%，换成保持任务语义不变的 counterfactual representation 后变成 -5.10%。这意味着 Agent Harness 的评测单位需要从“新任务”继续扩展到“同一任务在不同协议表示下是否仍有效”。

  3. 科研 Agent 的训练资源正在从静态题库转向真实科学代码库的 executable environments。 ScienceIDE 从 27 个 scientific codebase 构造 64 个环境、2,812 个任务和 1,076 个 executable scientific checks；85-task ScienceIDE-Hard 上，最好观察值仍只到 67.1%。更值得看的是 verifier-driven RL：Qwen3.5-4B 在两个 held-out scientific environment 上 30 steps 后 reward 从 0.357→0.857、0.286→0.571。科学软件可能成为比合成代码题更有价值的 Agent 后训练基质，但环境完整性和数据污染审计同样会变得更难。

  4. 消费级 MoE 推理的一个新系统方向，是让“预测的路由”直接成为真实路由，从而提前从 SSD 读取下一层 expert。 Edge0 在 24GB Mac mini M4 Pro 上用 19.5GB 的 4-bit 35B MoE checkpoint，报告 20.4 tok/s 和 2.9 GiB peak active memory；同机全驻留 mlx-lm 为 3.9 tok/s、18.2 GiB。代价是相对 fp16 teacher 五项 benchmark 平均约 -3.9 points，而且当前开源主路径基于 MLX / Apple Silicon。准确说法是“用约 3GiB 活跃内存流式服务 19.5GB checkpoint”，不是“35B 模型只占 3GB”。

  5. Sponsored Search 正在尝试把 retrieval、relevance 与 ranking 放进统一生成／判别模型，减少级联早期误杀。 腾讯 ANGLE 使用 LLM 生成的 commercial intent + ad abstract 作为可解释层级表示，再做 constrained generation 与统一 ranking；论文在匿名线上系统给出正向 A/B。不过文中存在一个值得直接指出的数据不一致：摘要、贡献段和 Table 3 写 WTS consumption +1.81%，正文结果段写 +1.18%，GMV 均为 +2.16%。因此消费指标在作者澄清前不能当作精确已核验数字。

  6. Agent 自动调 kernel／Serving 的最大风险之一，是“测量系统奖励了错误的 headline”。 AutoTuneBench 展示同一 kernel 对 naive baseline 看起来是 10.6×，对真正应该比较的 honest baseline 只有 2.03×；同一配置在两台同型号机器上分别 1.174× 与 1.0049×。KernelBench Level-1 中，51 个通过正确性门槛的任务相对 PyTorch eager 的 median speedup 只有 1.0001×。这不是 Agent 调优失败的证明，而是提醒：measurement protocol、baseline provenance 和跨机复测必须成为 Harness 的不可修改部分。

1. Infinite-Parameter LLMs：把运行时知识编译进低秩权重

原始来源： 论文

发生了什么

这项工作提出一种 runtime data-to-weights 架构。一个紧凑 hypernetwork 读取用户在当前 session 提供的事实或行为信息，生成低秩 FFN modulation；模型同时维护对 latent code 的 Bayesian belief，并随着多轮交互更新这个 belief，因此 effective weight 并非读一次 context 后永久固定。

其思想与 MoE 有一个有趣对照：MoE 从静态 expert bank 中选择少数已有参数；这里则根据现场数据即时生成低秩参数。存储 footprint 保持固定，但可到达的 effective weight configuration 理论上没有有限 expert bank 那样的离散上限。

关键结果

数据集In-context F1Data-to-weights F1
SQuAD85.351.8
HotpotQA58.760.4
2WikiMultihopQA55.558.1
MuSiQue40.945.3
MS MARCO v2.133.648.0

论文还把每个 passage 编译成独立 code，再训练 activation-routed selector 在 code pool 中选择相关 code。MS MARCO 上，trained selector top-1 为 53.3，而 bge-small dense retrieval 为 45.3；2Wiki 为 70.1 vs 58.1，MuSiQue 为 53.0 vs 40.9。一个重要负结果是 zero-shot code confidence 接近随机，说明这种“内部路由能力”需要专门训练，并不会天然出现。

为什么重要

它提供了 Context Engineering 之外的另一种状态载体：

→ 编译为低秩权重状态

对于反复使用的 noisy evidence、用户长期偏好、反复约束，这种表示可能避免每轮重复读取同一大段上下文。它与 RAG、Memory、LoRA 和 hypernetwork 的边界会逐渐变得模糊。

可信度与局限

“Infinite-Parameter” 这个名字容易引起误读。模型的物理参数、latent code 维度和实际信息容量仍是有限的；所谓 infinite 更准确地描述“固定存储下可生成连续、理论上无限多个 effective weight configurations”。如果 runtime 没有提供某个事实，系统也不会凭空获得新知识。

更重要的是，SQuAD 结果清楚证明：短、干净、一次性 evidence 直接放 prompt 仍然更强。只有 evidence 长、噪声高、会被多次复用时，编译成本才有机会被摊薄。

最值得继续追踪

重点看三个问题：生成 adapter 的一次性成本何时能被 session 复用摊平；runtime code 能否安全删除、版本化和隔离；以及和普通 KV / RAG cache 相比，单位 byte 的长期信息密度与可解释性到底谁更好。

2. Bad Genius / CHASE：Harness 提升也需要反事实审计

原始来源： 论文

发生了什么

自动 Harness optimization 会反复读取 benchmark feedback，然后编辑 prompt、memory、retrieval、tool 和 control code。即使 train / test task ID 完全分离，只要 benchmark protocol 的表示方式固定，Proposer 仍可能学到跨任务共享的 protocol shortcut。

CHASE 增加一个 Challenger：每当 Proposer 给出新 Harness，Challenger 就寻找一个保持任务语义不变、却尽可能摧毁新 Harness 增益的 protocol transformation。通过 validity firewall 和 confirmation set 后，这个 counterfactual 会进入 archive，下一轮 Harness 必须同时在 released benchmark 和历史 counterfactual 上保持性能。

关键结果

OfficeQA 的 certification 结果：

方法ReleasedCounterfactual archive avgArchive worst
RawHarness67.98%66.23%64.47%
HarnessCompass64.04%63.16%62.28%
CHASE68.86%68.42%67.98%

最值得记住的是 failure case。第一轮候选 Harness 在 released protocol 上相对 parent +8.16%，把 retrieved text 改成另一种语义等价 table representation 后变成 -5.10%。第二轮甚至出现 released gain +15.31% 的候选，但因为 counterfactual constraint 不通过而被拒绝。

为什么重要

最近 Agent Harness、Skill、Memory 自动演化工作快速增加，单纯“held-out task 上涨了”已经不够。需要进一步问：

3

文件名换掉还涨吗？
工具顺序打乱还涨吗？
同一证据换一种等价表示还涨吗？
Prompt layout / table format 改掉还涨吗？

如果收益依赖这些本不该决定答案的协议细节，系统优化的可能是 Benchmark，而非真实能力。

可信度与局限

CHASE 的 counterfactual archive 仍是有限集合。它只能对 Challenger 能发现并通过 validity check 的 shortcut 提供防护；未被搜索到的 protocol bias 依然可能存在。实验中的 Proposer round 也不多，因此不能推出长期自演化 Harness 已经拥有强稳健性保证。

最值得继续追踪

未来 Agent benchmark 应同时发布 task split + protocol perturbation suite。Harness evolution 的报告也应提供 released gain、counterfactual worst-case gain 和新协议迁移性能，而不只报告一个最终平均分。

3. ScienceIDE：把真实科研代码变成 Agent 的可执行学习环境

原始来源： 论文 · 代码仓库

发生了什么

ScienceIDE 试图把科学软件中的模型、数值方法、物理约束和代码惯例转成 executable agent environments。当前论文从 27 个 scientific codebase 构造 64 个环境、2,812 个任务，其中 2,515 个 repair、295 个 implementation、2 个 acceleration，并配有 1,076 个 executable checks 来验证数值输出与物理 invariant。

ScienceIDE-Hard 是 85 个固定 hard tasks，来自 18 个 environment；每个 Agent 都在同样容器和一小时预算下执行任务。

关键结果

85-task leaderboard 的最高 observed success 为 Fable 5.1 的 67.1%，随后是 Opus 5 的 64.6%、GPT-6 Astra 的 63.1%、GPT-5.6 Sol 的 55.0%。但 Fable 只有单次测量，而且 Opus / Astra 的 repeat interval 存在重叠，论文自己也明确提醒不能把 point estimate 当成统计上确立的精确排名。

更值得后训练团队看的是 RL 结果。Qwen3.5-4B 使用 executable verifier feedback 训练 30 steps 后：

EnvironmentBaseRL 后
LAPS0.3570.857
MITgcm-biogeo0.2860.571

训练还使用一个很有意思的 truncation rule：超预算轨迹仍参与 group baseline，但从 policy loss 中屏蔽，避免模型通过“更早结束”伪装成更好的长程策略。

为什么重要

真实科研代码同时包含长程代码导航、数值正确性、领域 convention 和 executable feedback，比许多合成 coding benchmark 更接近科学 Agent 最终要面对的环境。它提供了一种把人类多年科学软件积累转换为 RL / SFT experience 的路径。

可信度与局限

论文附录也暴露了环境构建的难度：历史 campaign 曾发现容器检索／provider-side fetch 等污染通道，需要作废和重跑部分 trial。这反而说明 scientific-agent benchmark 的 integrity 本身就是研究问题。

ScienceIDE-Hard 也只能覆盖有限 scientific software；当前 top Agent 仍有约三分之一任务无法解决。SFT 对通用代码 benchmark 的 transfer 并非所有维度都单调改善，因此“科学训练数据天然提升通用编程能力”还没有被证明。

最值得继续追踪

看环境生产工具链能否被第三方复现，以及科学 verifier 是否能扩展到不易写 deterministic oracle 的 simulation、data analysis 和实验设计任务。对 Agent RL 来说，环境完整性 + verifier 质量 很可能和模型本身同样重要。

4. Edge0：让下一层 Expert 在 SSD 上提前出发

原始来源： 论文 · 代码仓库

发生了什么

MoE 只减少每个 token 的 active compute，并不会自动减少存储所有 expert weights 的容量。把 expert 放到 SSD 又有一个时序问题：第 N+1 层应该激活哪个 expert，通常要等第 N 层算完才知道，此时再发 SSD read 已经太晚。

Edge0 的 prerouter 提前一层预测下一层 routing，并让这个 prediction 直接成为真实 routing decision。因此系统可以在当前层计算期间预取下一层必需 expert，不会出现“预取错了再丢弃”的浪费。int4 和 routing replacement 造成的质量损失，再由 unmerged recovery LoRA 补偿。

关键结果

在 24GB Mac mini M4 Pro、Qwen3.6-35B-A3B 4-bit checkpoint 上：

设置Decode活跃内存
Vanilla mlx-lm，全权重驻留3.9 tok/s18.2 GiB
Edge0 K=420.4 tok/s2.9 GiB

checkpoint 本身仍约 19.5GB，其余权重驻留磁盘。五个 OpenCompass benchmark 上，Edge0 35B 相对 fp16 teacher 平均约低 3.9 points：例如 AIME 86.6 vs 92.7，HumanEval 90.9 vs 95.1，GPQA-Diamond 79.8 vs 81.8。

为什么重要

这条路线改变了“消费级设备不能运行大 MoE”的约束方式：容量瓶颈从“所有权重必须塞进 HBM / unified memory”变成“SSD 带宽、预取准确性与每 token expert working set 是否足够小”。

它同样提醒我们，MoE serving 的 router 不再只是模型数学结构，它可以与 storage scheduler 联合设计。

可信度与局限

当前开源实现的主路径是 MLX / Apple Silicon，CUDA backend 仍属于后续方向。Apple unified memory、SSD 和 MLX 的系统行为不能直接映射到 NVIDIA GPU server。

2.9 GiB 指 peak active memory，不包含磁盘上的 19.5GB checkpoint，也不意味着超长 context 的 KV cache、OS 和其他 runtime memory 消失。性能提升还包含“全驻留模型在 24GB 机器上其实会陷入内存压力”这一硬件条件。

最值得继续追踪

等待 CUDA / Linux 复现，并重点观察 NVMe bandwidth、queue depth、expert hotness 和 KV cache 同时竞争 I/O / memory 后，20 tok/s 这一 operating point 能否保持。

5. ANGLE：搜索广告从多级筛选走向层级文本生成 + 统一排序

原始来源： 论文

发生了什么

传统 sponsored-search pipeline 往往是 retrieval → relevance → pre-ranking → ranking，多阶段分别训练。早期阶段一旦过滤掉高潜候选，后面更强的 ranking model 已经没有机会恢复。

ANGLE 用 LLM 为广告生成两层文本表示：高层 commercial intent 描述商业意图，细粒度 ad abstract 保存广告细节；retrieval 阶段通过 dynamic constrained beam search 只生成索引中存在的合法 intent-abstract pair，再把候选交给同一类 LLM 的判别／排序能力处理。

关键结果

论文 Table 3 报告两个匿名线上系统：

系统ConsumptionGMVClicksConversionsExposure
WTS+1.81%+2.16%+1.50%+1.44%+2.49%
QBS+6.57%+5.01%+6.11%+0.72%+7.82%

在线实验描述为 5 天、20% traffic。索引侧 Hunyuan-1B 生成一个 intent-abstract pair 约 90ms 内完成，广告索引按小时更新。

为什么重要

这类设计试图解决生成式检索中 Semantic ID 的一个长期问题：ID 对 base LLM 本身没有语义，模型需要额外记忆 SID ↔ ad 映射；层级自然语言表示更容易承载可解释语义，也更容易给新广告生成 representation。

对推荐／搜索团队，更值得关注的是 unified objective 能否真正降低 multi-stage objective mismatch，而不是“LLM 取代所有传统召回”这一夸张叙事。

可信度与局限

论文存在一个明显内部不一致：摘要、Introduction contribution 和 Table 3 均写 WTS Consumption +1.81%，但 Online Result 正文写 +1.18%；GMV +2.16% 一致。在作者勘误之前，Consumption uplift 的精确值应视为未完全核验。

另外，系统名称和生产数据匿名，外部无法独立复现。论文也没有完整给出与传统 cascade 在同等总 Serving cost 下的端到端成本对比，因此“one-step”并不自动等于更便宜。

最值得继续追踪

看新广告 cold-start、索引小时级更新下 representation drift，以及统一模型在极大广告库中的召回覆盖和尾延迟。真正决定生产价值的仍是 GMV / user value × latency × serving cost × freshness。

6. AutoTuneBench：给 Agent 自动优化加一条“测量不可篡改”的边界

原始来源： 论文 · 代码仓库

发生了什么

Agent 自动优化 kernel / Serving engine 通常采用 propose → measure → keep。这个闭环只要 measurement 有偏，Agent 就会非常高效地把偏差优化到极致。

AutoTuneBench 从 4 天、619 次 model call 的 pilot 中总结出四类常见错误：strawman baseline 制造虚假加速；绝对时间跨机器不可迁移；任务已经撞到 shared wall 时继续比较没有意义；infra bug 会伪装成算法进展。其 protocol 将 baseline provenance、anti-cheat、pre-registered readout、paired-seed statistics 和 CV threshold 固化进 Agent 无法修改的测量层。

关键结果

几个数字很有警示意义：

  • 最佳 GELU kernel 对 naive first draft 是 10.6×，对真正 search 起点的 honest baseline 只有 2.03×；
  • 同一 speculative-decoding 配置在两台机器上是 1.174× 与 1.0049×；
  • KernelBench Level-1：100 个任务中 51 个通过正确性门槛；这 51 个相对 PyTorch eager 的 median speedup 只有 1.0001×；
  • 其中 24/51 低于 1.0×，15/51 在 1.0–1.2×，只有 12/51 ≥1.2×；
  • 53 个候选全部重测复现，median deviation 0.60%、max 3.97%，说明这个负结果本身是稳定的。

为什么重要

这对近期大量“Agent 自动写 kernel / 自动调系统”的结果提供了一个必要校准。研究问题应分成两层：

1
2

Agent 能否找到候选？
Measurement 能否证明候选真的更好？

如果第二层不可靠，第一层越强，错误的 Ratchet 越危险。

可信度与局限

AutoTuneBench 当前覆盖 vLLM、SGLang 和有限硬件／任务组合；它无法证明所有 Agentic optimization 的 headline 都有问题。更合理的结论是：baseline、machine、shared bottleneck 与 correctness gate 必须公开，否则单个 speedup ratio 的信息量很低。

最值得继续追踪

建议关注跨机器、跨 engine 的 ratio portability，以及 Agent proposer 与 random / rule-based search 在完全相同 measurement budget下的差异。只有搜索增益和测量可靠性同时成立，才能证明 Agent 真正贡献了系统优化能力。

今日值得收藏的代码 / 学习资源

CERA-MoA 把 Router 与 Agent post-training 放进同一个 co-evolution loop：用中层 hidden state 估计不同 Agent 对当前任务的 familiarity，再用 cumulative-threshold 动态激活最小 Agent 子集，同时把有针对性的训练样本分配给不同 Specialist。它值得和近期 Native Skill Router、Multi-Agent routing 一起看；当前主要证据仍来自 benchmark，真实 multi-agent Serving 的成本与并发行为需要进一步验证。
论文：CERA-MoA

SURF 是一个很实用的 sequential recommender unlearning 方向：先在 embedding space 找待遗忘 Item 的局部邻域，只训练一个小型 auxiliary model，然后在 inference 时从原模型 score 中减去该局部模型影响。7 个数据集、5 类 baseline 上，论文声称接近 full retraining 的 forgetting effect，并只使用约 2% retraining time budget。需要注意“最高 32% NDCG@20 提升”属于相对结果，不能当成统一平均收益。
论文 · 代码

EffiRAG / Structure Pricing 值得做 GraphRAG 的团队收藏。作者强调图结构的价值应该按“answer quality + ingestion/query 总成本”定价，而不是默认 GraphRAG 越复杂越好。UltraDomain 120 个开放问题上，相比 LightRAG-hybrid，EffiRAG 获得 93 个 preference win、7 个 loss、20 个 split，并把总成本从 $0.952 降到 $0.408（-57%）。它仍是单一 benchmark / Judge 设置，但提出的 cost accounting 边界很正确。

论文原文

这篇当前比单纯再看一个 Harness leaderboard 更有价值，因为它直接攻击一个正在快速变大的方法学漏洞：Harness optimization 会反复接触同一 benchmark protocol，因此 task holdout 并不能自动阻止系统学到跨任务 shortcut。

建议 30 分钟按这个顺序读：先理解为什么 task split 仍不足；再看 +8.16% → -5.10% 的真实反转案例；随后看 Challenger 如何搜索 validity-preserving counterfactual；最后看 archive constraint 如何拒绝 released gain 更高、但鲁棒性更差的候选。

最值得带走的判断是：

当 Harness 也在被优化时，Benchmark protocol 本身已经进入训练分布。评测需要同时 hold out 任务和“协议表现形式”。

这条原则可以直接迁移到 Skill optimization、Agent Memory、Tool Router、RAG Harness 与自动 Prompt / Workflow search。

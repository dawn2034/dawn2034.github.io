> **今日主线：** Long-Horizon Tool RL · Looped Flows · PTQ Mechanism · Reusable RAG Views · Cross-Stage Recommendation · Tiered KV Cache

截至今天早上，arXiv 最新常规公告批次为 **2026 年 9 月 11 日**：`cs.AI` 171 条、`cs.CL` 91 条、`cs.LG` 171 条、`cs.IR` 15 条；不同分类存在大量交叉收录，不能直接相加。今天最值得连起来看的变化，是训练和 Serving 都越来越重视“中间状态是否忠实”：长程 Tool RL 要保证 rollout token、MoE 路由与训练重放一致；Looped Flow 试图让 recurrent hidden state 真正跨更多计算步骤积累信息；PTQ 开始解释量化误差为什么没有随深度失控；RAG 与 KV Serving 则把历史注意力和被驱逐 KV 变成可复用资产。推荐系统侧，UniRec 继续把原本分阶段独立优化的级联链路向全局一致性推进。

## 今日核心判断

1. **长程 Agent RL 的稳定性问题已经下沉到“采样时到底发生了什么，训练时能否逐 token 复现”。** T1 在真实 shell 中支持 300+ tool-call turns，使用 TITO 保留实际采样 token IDs，并对 MoE 记录、重放每个 token 的 expert routing；两者把 training-to-inference log-prob gap 从 0.021 降到 0.013。配合按 verifier assertion 数量计分的 dense process reward，Terminal-Bench 2.1 从 base 43.8% 提到 64.0%。

2. **Recurrent-depth 的一个新方向，是不用长 BPTT 直接训练“未来循环有用的状态”。** Looped Flows 用逐步降低噪声、共享噪声的局部 denoising/flow objective 建立时间关联；在 5–7M 参数的结构化 reasoning 模型上，ARC-AGI-1/2 达到 58.8%/12.2%，Sudoku 推理步数从 8 增到 128 时准确率从 74.5% 提到 97.9%。但这仍是小型任务模型，不能当作“Looped Transformer 已在 LLM 上验证”的证据。

3. **PTQ 能工作，不只是因为单层量化误差足够小。** 新工作发现，预训练后每层新引入的量化误差往往与继承的 hidden-state error 方向相反，从而部分抵消；LM head 的几何结构又优先保护高排名 token。Qwen3-32B 使用 NVFP4 的简单 RTN、无需 calibration，六项 zero-shot benchmark 平均只下降 0.43 point。这个机制解释很强，但论文没有证明 packed 4-bit kernel 的端到端吞吐收益。

4. **RAG 压缩开始从“每个 query 现场重做”转向“复用历史交互中已挖出的证据视图”。** REVA 把 target generator 的历史 attention trace 聚合成 document-keyed、budget-agnostic score store，线上只需要 lookup、排序和预算修复；四个 benchmark 上相对现有压缩方法提高 1.0–5.8 points，compression overhead 降低 5.3–15.6×，新增延迟低于 40 ms。代价是 evidence view 与模型版本、历史 query 分布发生了耦合。

5. **级联推荐系统的损失之一来自“上游筛掉了下游真正想要的 Item”。** 快手 UniRec 把 pre-ranking 与 ranking 的 fusion module 放进一个联合图里训练，并把下游 pairwise preference 向上游传递；一周、20% 随机线上流量中，总观看时长 +0.675%、视频观看时长 +0.755%、App 使用时长 +0.616%、活跃用户 +0.189%，随后全量部署。这里的“fusion agent”是可微分排序模块，不是 LLM Agent。

6. **KV Cache 的下一个容量层不是简单“CPU offload”，而是 HBM→Host DRAM→Storage/P2P 的分层缓存系统。** vLLM 的 Tiered KV Cache 把 host 作为规范化主缓存，再把 chunk 异步写入 NVMe、对象存储或远端 peer；Qwen3.6-35B-A3B、2×H100 的多轮会话实验中，超过约 128 个 conversation 后，storage offload 的 prefiller throughput 相比替代方案超过 2×。但这项数据只测 prefiller，不是完整端到端 decode latency。

## 1. T1：长程 Tool RL 的关键开始从“更多 rollout”转向“更忠实的 rollout”

**原始来源：** [T1: Terminal Agent Reinforcement Learning for Long-Horizon Tasks](https://arxiv.org/abs/2609.11042)

### 发生了什么

T1 是一个 122B total、MoE 架构的 terminal agent，在云端 sandbox 中直接操作 shell，单任务可以持续 300+ tool-call turns。训练数据不是 Terminal-Bench 题目的改写，而是从隔离 seed 递归合成的 terminal task；最终训练集 T1-15k 来自更大的 RST-38k，并与 Terminal-Bench 2.1 保持分离。

真正有价值的是训练工程。作者发现长轨迹 Agent RL 中，rollout 服务与 trainer 之间即使只存在很小的 tokenization 或 MoE routing 差异，也会不断污染 on-policy assumption。TITO 因而直接保存实际采样得到的 token IDs，在 turn boundary 修复 retokenization drift；R³ 则保存 sampler 在每个 MoE layer、每个 token 上选择的 expert，并在训练 forward 中重放同一路由。

奖励也没有只使用最终 pass/fail。任务 verifier 被拆成多个 assertion，trajectory reward 按“实际通过了多少 assertion”给 dense process signal。作者报告单纯 binary reward 的早期训练 campaign 没能超过 supervised warm-start，说明在数百步 Tool trajectory 中，只靠最终 0/1 outcome 很容易把 credit signal 稀释掉。

### 关键结果

| 设置 | Terminal-Bench 2.1 resolved |
|---|---:|
| Base model | 43.8% |
| Supervised warm-start | 49.4% |
| T1，3 PPO epochs | **64.0%** |
| GPT-5.4，同 Harness | 54.8% |
| DeepSeek-V4-Flash，同 Harness | 56.9% |
| Claude Opus 4.6，同 Harness | 63.8% |
| Claude Opus 4.7，同 Harness | 66.1% |

TITO + R³ 把 training-to-inference log-prob difference 从 **0.021 降到 0.013**，同时让 loss region 内的 token drift 归零。T1 在 Long-Horizon Terminal Bench 为 27.9%，Terminal-Bench Hard 为 38.0%。

### 为什么重要

Agent RL 经常把“on-policy”理解成“样本来自当前 policy”。T1 提醒我们，真正的 on-policy 还包含更细的执行一致性：**采样用了哪些 token、MoE 实际走了哪些 expert、训练 forward 是否在同一条件下计算概率。** 长轨迹会把微小 mismatch 的影响放大，特别是多轮 tool observation 会反复经历 encode/decode 边界。

另一个更一般的 lesson 是：如果环境本来就有一组可执行 assertion，不要过早把它压成一个 scalar terminal reward。很多 Coding、SQL、Browser、数据处理任务其实天然拥有“部分完成度”，这些信号比再训练一个 PRM 更便宜、更可解释。

### 可信度与局限

这是一篇新预印本，虽然 benchmark 与训练数据做了分离，但训练任务的分布仍强烈偏向 command-line engineering；作者报告 top-5 task categories 占 67.9%，debugging 和 performance optimization 占比很低。64.0% 说明 recipe 有效，不代表已经覆盖真实软件工程的全部长尾。

R³ 主要解决 MoE sampling/training route mismatch，dense model 不需要照搬。论文也还缺少把 TITO、R³、dense process reward 在完全 matched-compute 条件下一项项拆开的单轴 ablation；因此目前可以确认“整套 recipe 有效”，还不能精确分配每个组件的因果贡献。

### 最值得继续追踪

重点看这套 fidelity recipe 是否会被 `verl`、OpenRLHF、SGLang/vLLM RL stack 吸收，以及在 Coding Agent、Browser Agent 上，`token drift / routing drift / verifier-density` 与最终 RL instability 是否存在可预测关系。

## 2. Thinking with Looped Flows：用局部 Flow Objective 训练可持续累积的 Recurrent State

**原始来源：** [Thinking with Looped Flows](https://arxiv.org/abs/2609.11801)

### 发生了什么

Looped / recurrent-depth 模型的吸引力在于：参数量固定，却可以在 inference 时多运行几轮 hidden-state update，用更多计算解决更难的问题。训练难点也很直接——如果只反传 1–2 个 recurrence update，早期 update 并不知道几十步以后什么状态才真正有用；如果完整 BPTT，又会迅速变得昂贵和不稳定。

Looped Flows 选择绕过长 BPTT。每个时间点都做局部 denoising objective，但噪声水平随“思考时间”逐步下降，并在时间之间共享 noise，从而让不同局部目标属于同一条 noise→solution trajectory。Inference 则把 denoiser 看成 probability flow 的 velocity field，与 recurrent hidden state 一起积分；增加 temporal grid resolution 就等于给模型更多 test-time compute。

### 关键结果

| Benchmark | Looped Flows | 代表性既有 looped baseline |
|---|---:|---:|
| Sudoku-Extreme | **97.9%** | TRM 87.4% |
| Maze-Hard | **86.7%** | TRM 85.3% |
| ARC-AGI-1 | **58.8%** | TRM 44.6% |
| ARC-AGI-2 | **12.2%** | TRM 7.8% |

Sudoku 上，仅改变 inference temporal grid，8 steps 为 74.5%，128 steps 为 97.9%，说明“多算一会儿”确实转化成更高准确率。Ablation 也支持 temporal association 是关键：去掉 time/interpolant 后 ARC-AGI-1/2 降到 43.6%/5.0%；不使用 decreasing noise 为 51.6%/9.9%。

### 为什么重要

近期 Looped Transformer / recurrent-depth 的讨论真正有价值的部分，是把 **parameter depth** 与 **runtime compute depth** 解耦。Looped Flows 又进一步提出：训练这种模型时，不一定必须让 gradient 穿过全部未来循环；可以通过构造局部但时间一致的学习目标，让每一步状态朝“未来可继续计算”的方向组织。

如果这个思想未来能进入语言模型，可能提供一条与长 CoT 不同的 test-time scaling 路线：额外计算发生在 latent state，而不必全部变成可见 token。不过这目前只是合理研究方向，不是已经验证的 LLM 结论。

### 可信度与局限

最重要的限制是规模：实验模型只有约 **5–7M 参数**，任务是 Sudoku、Maze、ARC、N-Queens、Graph Coloring 等结构化 reasoning，并没有自然语言 LLM。ARC-AGI 分数可以证明方法在这些任务上有效，不能证明它会在 7B/70B Transformer 上保持训练稳定、长上下文能力或语言质量。

Flow formulation 还引入了新的 inference schedule 与 noise initialization。未来若放到 LLM，需要同时回答 KV/cache、batching、latency variance，以及 latent computation 是否比直接生成 reasoning tokens 更有单位 FLOP 价值。

### 最值得继续追踪

看是否出现 100M–1B 以上语言模型复现，以及在固定 FLOPs 下比较 `更多 latent loops`、`更多 output reasoning tokens`、`更深固定 Transformer` 的真实 quality–latency frontier。

## 3. Why Does PTQ Work：预训练模型会“抵消”量化误差

**原始来源：** [Why Does Post-Training Quantization Work?](https://arxiv.org/abs/2609.11716)

### 发生了什么

PTQ 有一个长期反直觉现象：每一层权重都被量化，hidden state 每层都被扰动，误差理论上应该随着深度不断累积；真实预训练 LLM 却常常能在 4-bit 下保持很大一部分能力。论文直接比较 full-precision 与 quantized forward pass，试图解释这种鲁棒性来自哪里。

作者发现两个机制。第一，某一层**新引入的量化误差倾向于与输入已经携带的误差方向相反**，因而出现部分抵消；这种 counteracting residual interaction 在随机初始化网络里很弱，却随着 pretraining 形成。第二，即使最终 hidden state 的角度已经明显偏移，LM head 的几何结构仍更稳定地保留高排名 token 的 score 与 probability。

### 关键结果

Qwen3-32B 使用 NVFP4、简单 round-to-nearest 且不做 calibration，六项 zero-shot benchmark 平均准确率只下降 **0.43 point**。随机初始化网络在相同量化下则出现远高于预训练模型的 hidden-state discrepancy：论文在多个 Qwen、OLMo、Gemma checkpoint 上都观察到这一差异。

在一个 W4 分析设置中，最终 hidden state 的 relative error 约 0.245，其中 88.9%–98.7% 的 squared relative error 来自角度偏移；归一化后平均约 12.47° rotation。即便如此，最高概率 token 的排序仍比 raw hidden-state error 暗示的稳定得多。

### 为什么重要

这改变了量化研究里一个常见思路：不要只问“单层 quantizer 的 MSE 能否更小”，还要问 **误差进入整个 residual stream 以后会怎样被网络动力学处理**。如果预训练已经自发形成 error-canceling geometry，最优 quantizer 未必是逐层 MSE 最小的那个，而可能是更匹配网络全局 error propagation 的方案。

它也给 QAT/PTQ hybrid 一个自然方向：与其训练模型“完全没有量化误差”，可能更值得优化“量化误差在层间可抵消、最终 decision margin 不翻转”。

### 可信度与局限

论文的机制证据跨多个模型与量化设置，解释性强；但这里测的是数值与任务表现，**没有证明某个 packed NVFP4 kernel 在真实 Serving 中更快**。checkpoint 更小、hidden-state error 更稳，与端到端 TTFT / tokens/s / batch capacity 是三个不同问题。

另外，NVFP4、W4 等格式与模型架构仍有限，不能据此推断 2-bit、KV cache quantization、activation quantization 都会由同一抵消机制保护。

### 最值得继续追踪

最有价值的后续是把“层间 error counteraction”变成可优化目标，检查它能否预测哪一层应该保留更高精度，以及能否比传统 Hessian/MSE calibration 更准确地预测最终 token/ranking decision flip。

## 4. REVA：RAG Compression 也可以拥有“离线编译”阶段

**原始来源：** [REVA: Reusable Evidence View Aggregation for Context-Efficient RAG Serving](https://arxiv.org/abs/2609.11209)

### 发生了什么

很多 RAG compressor 每次收到 query 都重新调用一个小模型、打分器或 rewrite pipeline。Prompt 虽然变短了，在线压缩自身却增加额外 inference latency；论文还发现，若把现代 compressor 与简单 truncation 严格比较，收益并不稳定。

REVA 改成利用历史 `query × document × target generator` 交互。它把 generator 的 token-level attention 映射回可读 word units，再把同一 document 在多次历史访问中获得的 importance 聚合成一个 document-keyed score store。Serving 时不再运行辅助模型，而是按预算查表、排序、做 budget repair，最后输出普通纯文本 evidence view。

### 关键结果

跨四个 benchmark 与现代 LLM，REVA 相对已有压缩方法提高 **1.0–5.8 points**；compression overhead 降低 **5.3–15.6×**，新增延迟低于 **40 ms**。它的 score store 与最终 token budget 解耦，因此同一份离线 evidence map 可以渲染成不同长度的 prompt。

### 为什么重要

这是一种很典型的 Serving 思路：**把 query-time 智能转移成可复用的历史统计。** 对被频繁检索的政策、产品文档、代码文件、FAQ，很多“哪些段落通常真正被 generator 使用”的信息其实已经在过去请求中重复产生；每次重新推理一次 compressor 是浪费。

它也提示了一个更广的 RAG 架构：retriever 解决“找哪些文档”，document-level evidence cache 解决“文档里哪些内容通常值得保留”，query-time module 只处理少量真正与当前问题相关的例外。

### 可信度与局限

REVA 依赖**历史 attention 与未来 query 分布具有可复用性**。冷文档、新领域、分布突变时没有足够历史统计；同一 document 对不同 query 可能需要完全不同的 evidence，过度聚合会压掉低频但关键的信息。

另一个生产风险是模型升级。score store 来源于 target generator 的 attention trace，换 generator、prompt template 或 tokenizer 后，旧 evidence view 是否仍然有效需要重新审计；它更像一类可版本化的派生索引，而不是永久知识。

### 最值得继续追踪

看 REVA 在高重复企业 RAG 中的 cache hit / cold-start 分桶，以及 model upgrade 后是否需要 full rebuild。最值得加的指标不是平均压缩率，而是 `quality × compression latency × view reuse count × rebuild cost`。

## 5. UniRec：把 Pre-Ranking 与 Ranking 的 Fusion 真正放进一个优化问题

**原始来源：** [UniRec: Cross-stage Multi-Task Fusion with Preference Alignment for Cascaded Recommender Systems](https://arxiv.org/abs/2609.11052)

### 发生了什么

工业推荐通常是 `matching → pre-ranking → ranking → re-ranking`。Pre-ranking 必须在极低延迟下从成千上万候选里先砍掉大部分 Item，而 ranking 才能使用更丰富特征和更复杂模型。两个阶段独立优化的后果是：ranking 很喜欢的 Item 可能已经被 upstream 永久过滤掉。

UniRec 不只把 ranking score 蒸馏给 pre-ranking，而是把两个阶段的 **multi-task fusion module** 一起训练。二者共享一部分 input embedding；vertical alignment 把 downstream pairwise preference 传回 upstream fusion score；horizontal compact aggregation 把几十个 heterogeneous pairwise objective 重新组织成紧凑的双向 preference evidence。

作者还观察到一个典型 reward-hacking 问题：无约束的 end-to-end fusion 会利用 item attribute 分布不均，过度抬高天然高 reward 的群组。AGRR 因此只在相同 attribute group 内计算 advantage 和 policy normalization，使“整体抬高一个高 reward 组”不再带来虚假优化收益。

### 关键结果

线上实验为一周、**20% 随机 live traffic**，其余 production component 保持不变：

| 指标 | 相对生产基线 |
|---|---:|
| Total Watch Time | **+0.675%** |
| Video Watch Time | **+0.755%** |
| App Usage Time | **+0.616%** |
| Active Users | **+0.189%** |
| Like | **+2.367%** |
| Long View | **+1.028%** |

论文称所有报告指标均未下降，UniRec 已全量部署到快手。

### 为什么重要

推荐系统常把“每一阶段局部 AUC 提升”当作独立目标，但级联系统真正优化的是最终 candidate path。UniRec 强调：**upstream selection 与 downstream preference 是一个耦合系统，fusion 本身也应该成为 cross-stage optimization 的对象。**

对生成式推荐也有同样启示。无论中间表示是 pXTR、embedding 还是 Semantic ID，只要上游 truncation 是不可逆的，就应该关注 downstream-preferred item 在每个 stage 的 survival rate，而不是只看 stage-local ranking metric。

### 可信度与局限

一周 20% 随机流量的线上 A/B 是很强的工业证据，但论文没有在公开文本里给出每个业务指标的置信区间或 p-value，外部也无法复现快手完整 production distribution。线上收益属于 UniRec 整套 architecture + objectives，不能拆成 AGRR 或某个 adapter 的独立收益。

另外，论文称两个模块为 fusion agents，但它们是可微分推荐模块，不是进行自然语言规划的 LLM Agent；不应把这篇结果解读成“大模型 Agent 已经接管 ranking”。

### 最值得继续追踪

看 cross-stage joint training 能否继续延伸到 matching / re-ranking，以及在线系统如何处理 upstream candidate distribution 被训练本身持续改变造成的 non-stationarity。

## 6. vLLM Tiered KV Cache：从一次性 GPU 状态变成集群级可复用缓存

**原始来源：** [Tiered KV Cache Offloading in vLLM](https://vllm.ai/blog/2026-09-10-tiered-kv-offloading)

### 发生了什么

长上下文与多轮对话会让 KV cache 很快吃满 HBM。传统 eviction 的问题不是“数据没了”本身，而是下一轮命中同一 prefix 时必须完整重新 prefill。vLLM 的 Tiered KV Cache 把被驱逐的 chunk 继续保存在 Host DRAM、storage 或 remote peer 中，后续请求可以 reload 而非重算。

设计采用 host-centric canonical layout：GPU KV 先通过异步 DMA 写到 CPU，HBM 收到 host copy 后即可释放；Host 是真正的 LRU/ARC primary cache，不只是 staging buffer。Secondary tier 可以是 local filesystem/NVMe、对象存储或 P2P cache；不同 accelerator backend、TP configuration 通过统一 host byte-buffer layout 交换 chunk。

### 关键结果

官方 benchmark 使用 Qwen3.6-35B-A3B、2×H100、TP=2、本地 NVMe；每个对话先 12K-token prompt，此后每轮增加 4K tokens，共 8 rounds，max request concurrency 64。

- 约 **64 个 conversation 以内**：HBM 基本容纳 working set，各方案差异不大；
- **64–128**：HBM 开始饱和，CPU offload 可以维持性能；
- **超过 128**：Host cache 也开始饱和，storage tier 继续保持较高 hit ratio，prefiller throughput 相比替代方案 **超过 2×**。

### 为什么重要

Agentic workload 往往有“长 prefix + 多次回来继续工作”的局部性。对这类请求，KV 的经济学越来越像数据库 buffer pool：HBM 最贵最快，DRAM 次之，NVMe/远端缓存更慢但仍远比完整 recompute 便宜。

更值得注意的是 cache 开始跨节点共享。只要 chunk identity、layout 和版本管理足够稳定，调度器未来可以把“哪个 GPU 空闲”与“哪个节点已经拥有这段 prefix KV”一起纳入 routing objective。

### 可信度与局限

这是 vLLM 官方工程数据，代码已进入 vLLM，但 headline benchmark **只测 prefiller throughput**，运行在 2×H100、本地 NVMe、prefill/decode disaggregation 条件下。Storage tier 的尾延迟、远端网络拥塞、decode worker 竞争、混合请求长度都会改变真实收益。

因此“>2×”不能写成完整 Agent 请求吞吐翻倍。正确结论是：当 HBM 和 Host working set 都装不下时，保留 KV 到更低层级可以显著优于重新 prefill。

### 最值得继续追踪

看 tiered cache 与 cache-aware router、P/D disaggregation、RDMA peer transfer 如何组合；最终应报告 `cache hit by tier × TTFT × p95/p99 × bytes moved × recompute FLOPs saved`，而不是只看总体 hit rate。

## 今日值得收藏的代码 / 学习资源

**When Synthetic Data Hurts** 很适合正在做 Skill Router / Tool Retriever 的团队先读。作者研究一个包含 **34,396 个 skills** 的 production router，发现 synthetic-data fine-tuning 虽然提升 synthetic in-distribution retrieval，却会明显遗忘真实和 OOD skill；embedding-anchor、LwF、EWC、L2-init 等 continual-learning 约束可以缓解遗忘，并让 0.6B Qwen retriever/reranker 的 synthetic ID retrieval 再提高 13.98%。这意味着“继续合成更多 Skill query”不是单调收益，必须保留真实流量 replay 或 anchor evaluation。  
[论文：When Synthetic Data Hurts](https://arxiv.org/abs/2609.10750)

**COBRA-Skills** 把 Skill evolution 直接建模成预算受限的 sequential optimization。Contextual bandit 只把昂贵 executable evaluation 分配给更有希望或信息量的 candidate；六个 heterogeneous Agent benchmark、三个 target model 上，相对 SkillOpt 把 optimization cost 降低 **55–58%**，每个 benchmark 只使用 50 个 unique optimization examples。对 Skill 自进化真正有用的 lesson 是：候选 Skill 越多，evaluation budget 本身就应该被学习式调度。  
[论文：COBRA-Skills](https://arxiv.org/abs/2609.11682)

**Negative Self-Distillation** 提出一个值得跟 OPD 一起观察的反向思路：不去模仿一个带 privileged answer、过度自信的正 Teacher，而让模型为当前题目生成“careless reasoner”等 negative condition，再只在 reasoning-critical token 上把 Student 推离这类错误分布。论文报告 Qwen3 1.7B/4B/8B 上均优于其 OPSD 和 label-free baselines；但“reflection token 更多”只能视作行为 proxy，不能等同于更好的 uncertainty calibration。  
[论文：Negative Self-Distillation](https://arxiv.org/abs/2609.11699)

**OpenAI Agents API** 9 月 10 日进入 public beta，值得作为 Harness 设计参考而非单纯产品新闻。公开设计里最值得看的是自动 context compaction、按需加载 tool definition 的 tool search、programmatic tool calling，以及每个 subagent 独立 context 的 multi-agent orchestration；这些都在试图把 long-running Agent 的 context、tool surface 和并行执行从应用层手写逻辑中抽离。页面中的客户提速/降成本数字属于客户与厂商披露，不应当作独立 benchmark。  
[官方介绍：Introducing the Agents API](https://openai.com/index/introducing-the-agents-api/)

## 今日最值得花 30 分钟阅读的一项

**首选 T1: Terminal Agent Reinforcement Learning for Long-Horizon Tasks。**  
[论文原文](https://arxiv.org/abs/2609.11042)

这篇最值得看的不是 64.0% 这个分数，而是它把长程 Tool RL 中几个通常被当作“实现细节”的问题写成了训练算法的一部分：sampled token ID 是否原样进入 loss、tool-turn retokenization 是否漂移、MoE rollout 与 trainer 是否走同一 expert route，以及 verifier 能否保留 assertion-level 的部分进展。

30 分钟建议按这个顺序读：先看 binary reward campaign 为什么没超过 supervised baseline；再看 dense assertion reward；随后重点看 TITO 的 token drift 与 R³ routing replay；最后看 43.8% → 49.4% → 64.0% 的分阶段收益和训练集分布。最值得带走的判断是：**Agent RL 的 on-policy fidelity 不只是一条概率公式，而是一条从 sampler、tokenizer、router、tool observation 到 trainer 的系统契约。**

## 今日可立即实践的一件事

给现有 GRPO / Tool-Agent RL pipeline 加一个 **Rollout→Training Fidelity Audit**。先不要改 loss，也不需要完整实现 T1；只抽 100–500 条 rollout，验证 trainer 真正看到的轨迹是不是 sampler 当时执行的轨迹。

```python
record = {
    "sampled_token_ids": [],
    "trainer_token_ids": [],
    "turn_boundaries": [],
    "sampled_logprobs": [],
    "trainer_logprobs": [],
    "moe_route_ids": None,      # dense model 可省略
    "verifier_assertions": [],
}
```

至少统计：

$$
R_{token-drift}=\frac{\#\{t:y_t^{sample}\neq y_t^{train}\}}{T}
$$

以及：

$$
\Delta_{logp}=\frac{1}{T}\sum_t\left|\log p_{sample}(y_t)-\log p_{train}(y_t)\right|.
$$

按 `assistant text / tool call / tool observation boundary / long-history turn` 分桶。若是 MoE，再统计 sampler 与 trainer 的 expert-route agreement；同时把 verifier 的多个 assertion 暂时不要压成一个 binary reward，先画出“通过 assertion 数量”与最终成功率的关系。

**停止条件：** 如果 token drift 基本为 0、log-prob gap 很小且不会随 trajectory length 增长，同时你的模型不是 MoE，就没有必要为了追随新论文引入复杂 replay。反过来，如果 mismatch 明显集中在 tool turn boundary、长轨迹或 MoE route，那么先修 sampling/training fidelity，通常比继续调 KL、clip range 或 advantage normalization 更有优先级。

真正要回答的是：

> **你的 RL optimizer 正在学习 Agent 实际执行过的行为，还是一个训练系统重新解释出来的近似版本？**

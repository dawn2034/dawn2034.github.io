> **今日主线：** Recursive Self-Improvement · Native Skill Routing · Transactional Agent Tools · Token-Level Expert Distillation · Self-Evolving Recommendation · Predictive KV Scheduling

截至今天早上，arXiv 最新常规公告批次为 **2026 年 9 月 15 日**：`cs.AI` 408 条、`cs.CL` 204 条、`cs.LG` 366 条、`cs.IR` 35 条；分类之间存在大量交叉收录，因此不能直接相加。今天高信号工作的共同点很鲜明：系统能力越来越取决于模型权重之外的可演化状态与运行契约——Agent 可以通过主动探索构造环境 Memory；Skill Router 可以直接读取冻结 LLM 内部已有的路由信号；Tool runtime 开始面对重试、并发、部分失败下的事务语义；OPD 则继续把监督粒度从“这个样本该找哪个 Teacher”下沉到“这个 token 此刻该由哪个 Expert 教”。推荐与 Serving 侧也在做同一类拆分：把异质用户变化隔离到稀疏 Memory，把未知输出长度提前转成可校准的调度信号。

## 今日核心判断

1. **RSI 在 Agent 层的一个现实形态，正在从“训练自己”转向“主动探索环境并改写长期 Memory”。** RSIAgent 用 curriculum / actor / verifier 三角色在新环境中先广泛探索，再针对难例、隐藏约束与边界条件做深挖；最终冻结 Memory，不更新模型参数。OSWorld 2.0 partial score 从无 RSI 的 71.97 提到 78.98，binary 从 37.80 提到 42.68；ALE partial 从 83.75 提到 84.82，binary 从 49.25 提到 50.75。论文宣称超过 GPT-6 Astra，需要谨慎解读：它确实在两项 **partial score** 上更高，但 ALE binary 仍低于 GPT-6 Astra 的 52.24，而且大部分绝对能力已经来自强 Harness baseline。

2. **Skill Routing 可能已经存在于模型内部，只是此前没有被显式读出来。** Gavel 只训练两个线性投影，从 frozen LLM 的中层 hidden state 中读取 task–skill 匹配信号；安装 Skill 时只需一次前向构建紧凑 skill bank，运行时先 glance 全库、再对 shortlist 恢复前向做 verdict。Qwen3-32B 上，相比加入 1.2B–16B 外部参数的 progressive disclosure / retrieve-rerank pipeline，书面任务最高 +13.4 points，mid-rollout Skill 触发最高 +21.9。若结果能跨更多模型家族复现，未来 Skill Router 的中心问题会从“再训练一个更强 Retriever”转向“如何读取 Agent 本体已经形成的 capability geometry”。

3. **MCP/Tool Agent 的安全边界需要事务语义，而不只是 read-only / destructive / idempotent 这类粗粒度提示。** 新工作系统化列出重试、投机执行、并发与部分失败下的 8 类 external-effect anomaly，并在 98,291 个 MCP Registry 工具上审计标准 annotations。作者的结论很明确：现有字段广泛存在，但不足以表达 outcome query、compensation、staging、resource scope 等保证；黑盒调用在四类边界上无法给出通用安全保证。对生产 Agent 来说，“工具返回成功”只说明一次 RPC 的观察结果，无法自动证明整个 workflow 达到了唯一、可回滚、可重试的外部状态。

4. **Multi-Teacher OPD 的关键瓶颈之一，是监督必须落到正确 token 上。** VG-OPD 让 verifier 先判断某个 Expert 是否真正改善当前失败 criterion，再用 Expert–Student disagreement 定位需要监督的 token，把稀疏 KL 作为 token-level advantage 加进 GRPO。4B/8B Student 在 7 个 benchmark 上均取得最佳总体结果，5/7 第一；相对 rubric-GRPO，4B 在 scientific reasoning / domain science 分别 +2.0 / +3.3 points，8B 为 +1.7 / +1.9。最关键的 ablation 是：把相同的 Teacher supervision budget 放错位置，伤害最大；密集、无差别蒸馏甚至会把 RL 拉到自身 baseline 以下。

5. **Generative Recommendation 的持续学习冲突可以通过稀疏 Memory 隔离。** LION 观察到共享 autoregressive parameter space 会让高频、主流行为模式持续压过低频偏好变化，形成 evolution conflict。它让完整用户历史只负责路由少量 KV memory slots，近期序列继续走主干 Transformer，并用 consolidation loss 强化稀有模式。论文在 3 个 Amazon Review 数据集、多个时间周期与用户活跃度分桶上给出稳定收益；值得注意的是，单独增加 consolidation loss 可能变差，稀疏 Memory 单独使用也只带来有限增益，真正收益来自“隔离表示 + 定向巩固”的组合。

6. **P/D Serving 的调度可以把未知输出长度提前变成可校准的内存风险。** MAPS 在设备侧用轻量模型预测输出长度，并与云端 prefill 重叠；再用 uncertainty-aware calibration 构造有目标覆盖率的长度上界，供全局 memory-aware routing 与本地 SJF 调度。两类真实 workload、两个 LLM 上，平均 E2E latency 降低 42.6%，tail latency 最高降低 84.8%。这条路线的价值不在“精确猜中 token 数”，而在把重尾、不可知的 decode memory occupancy 转成一个带覆盖率约束的调度变量。

## 1. RSIAgent：不更新权重，靠“探索—验证—记忆”实现 Agent 级自我改进

**原始来源：** [RSIAgent: Autonomous Exploration for Recursive Self-improvement in New Environments](https://arxiv.org/abs/2609.15364) · [代码仓库](https://github.com/AetherLabsAI/RSIAgent)

### 发生了什么

RSIAgent 研究的是一个非常具体的 self-improvement 问题：当 Agent 进入一个预训练阶段没有覆盖的新软件环境时，怎样在没有人工标签、没有额外 fine-tuning 的条件下主动摸清接口、工具、失败模式和隐藏约束，并把这些经验转成之后可复用的 Memory。

系统由三类 Agent 组成：

- **Curriculum Agent** 决定下一轮该探索什么，主动生成 prerequisite、variant、failure-driven 和 stress-test 任务；
- **Actor Agent** 通过 code-as-policy 与环境交互，并持有持续演化的环境 Memory；
- **Verifier Agent** 与 Actor 的私有 reasoning / memory 隔离，直接依据环境结果、界面状态等 observable evidence 判断执行是否成功。

探索分成两阶段：Broad Recursive Self-exploration（BRS）并行铺开多个方向，用于建立广覆盖；Deep Recursive Self-exploration（DRS）围绕当前 Memory 暴露出的难例、未知约束和边界条件串行继续加难。探索结束后 Memory **被冻结**，正式评测时关闭 Curriculum 和 Memory 更新，避免把测试任务本身继续写进经验库。

### 关键结果

| 设置 | OSWorld Partial | OSWorld Binary | ALE Partial | ALE Binary |
|---|---:|---:|---:|---:|
| GPT-6 Astra | 72.60 | — | 82.26 | **52.24** |
| RSIAgent w/o RSI | 71.97 | 37.80 | 83.75 | 49.25 |
| RSIAgent | **78.98** | **42.68** | **84.82** | 50.75 |

RSI 本身相对同 Harness 的无 RSI 版本，在 OSWorld 带来 **+7.01 partial / +4.88 binary**；ALE 则是 **+1.07 / +1.50**。四个 OSWorld task 的阶段 ablation 中，完整 BRS+DRS 平均 74.54%，Broad-only 65.52%，Deep-only 56.50%；DRS 从空 Memory 起步时，在两个任务上甚至低于 baseline。

### 为什么重要

这项工作对“Recursive Self-Improvement”的定义很值得保留：self-improvement 并不要求修改 foundation-model weights。对于软件 Agent，更实用的可塑性来源往往是：

```text
主动提出学习任务
→ 与真实环境交互
→ 独立验证结果
→ 抽取动作—条件—后果关系
→ 更新可追溯 Memory
→ 冻结后在新任务复用
```

这与被动把成功 trajectory 写进向量库有明显区别。Curriculum 决定“还缺什么知识”，Verifier 决定“这条经验是否真的成立”，Memory 才负责持久化。三者共同形成了 Agent-level learning loop。

### 可信度与局限

论文 headline “开放模型超过 GPT-6”容易被过度传播。更准确的事实是：RSIAgent 的 **partial-credit** 在两个 benchmark 上高于论文引用的 GPT-6 Astra 结果；ALE binary 仍然更低，而且 `RSIAgent w/o RSI` 已经达到 71.97 / 83.75 partial，说明强 Harness 本身贡献很大。对 RSI 的增量评估应优先看 `w/o RSI → RSI`，而不是拿完整系统直接和另一套闭源 Harness 比。

此外，探索需要真实环境交互，成本会随任务空间扩大；错误 verifier 可能把错误经验固化进 Memory。论文自己的 failure analysis 也集中在 targeted exploration 不足、verification 不完整和 memory consolidation 不可靠。

### 最值得继续追踪

最值得看的不是再增加多少 RSI round，而是 **探索预算的边际信息增益**：什么情况下 Curriculum 能识别“再练一个变体已经没有价值”，什么情况下需要从广覆盖切到深挖。另一个关键问题是 Memory provenance：每条规则是否保存触发它的环境版本、证据和反例，从而支持模型／软件升级后的重新验证。

## 2. The Router Within：Skill Router 也许已经藏在 Frozen LLM 里

**原始来源：** [The Router Within: Eliciting Native Skill Routing from a Frozen LLM](https://arxiv.org/abs/2609.15982)

### 发生了什么

Agent Skill 越来越多以后，常见做法有两个极端：把全部 Skill metadata 预加载进 context，或者训练一个独立 Retriever / Reranker。前者增加 token 和 attention pollution，后者把 Skill 选择交给了与 Agent 本体分离的 embedding space。

Gavel（Glance And Verdict）提出第三种做法：直接读取 frozen Agent LLM 自己的 hidden state。训练参数只有两个线性 map。

`Glance` 阶段把 task 与每个 Skill 的中层表示投影到同一空间。每个 Skill 在安装时只做一次 forward，留下 compact per-skill bank；运行时无需把 Skill 文本塞进主上下文，就可以对整个库粗排。`Verdict` 阶段再恢复 shortlist Skill 的前向，读取模型自己的 likelihood 与 yes/no judgment，并和 glance score 做 product-of-experts 融合。

### 关键结果

论文在 Qwen3-32B 上报告：相对 progressive disclosure 与 retrieve-and-rerank pipeline（这些 pipeline 引入约 1.2B–16B 外部参数），书面 Skill routing 最高提高 **13.4 points**，当 Skill 需求在 Agent rollout 中途才出现时，最高提高 **21.9 points**。新建的 SkillTraj 包含 372 条模拟 Agent trajectory，用于专门测 mid-rollout routing。

另一个有意思的趋势是：backbone 越强，原生 routing accuracy 越高。作者还在 bash-agent Harness 中观察到，Qwen3-32B 对 Skill-Use 的正确触发率高于运行在 Codex Harness 中的若干更大 frontier model；这属于特定 Harness 下的结果，不能直接解释为 32B 的通用 Agent 能力超过那些模型。

### 为什么重要

如果 Skill 本身就是为了扩展 Agent 的能力，那么“Agent 是否意识到此刻需要某个 Skill”本来就是模型 reasoning 的一部分。把 routing 完全外包给通用 embedding model，可能丢掉模型内部对任务状态、当前轨迹和可用能力的联合判断。

Gavel 更像是在做 **capability readout**：模型权重不动，只学习怎样把已形成的内部路由信号投影出来。这条路线和最近的大量 `SKILL.md`、progressive disclosure、tool search 工作可以形成一个清晰比较：外部 Retriever 提供可扩展性，native router 提供 Agent-state awareness，最终系统很可能会采用混合路由。

### 可信度与局限

“只训练两个线性 map”很漂亮，但并不意味着系统没有额外成本：每个 Skill 仍需提前构建 bank，shortlist 仍需要恢复部分前向。性能又可能强依赖 backbone 的内部 representation geometry，换模型版本后 map 和 Skill bank 是否需要重建，需要单独测。

SkillTraj 是模拟轨迹，真实企业 Agent 中 Skill 触发常与权限、外部状态、成本和副作用耦合，仅判断语义适用性还不够。

### 最值得继续追踪

建议重点看两个方向：第一，跨模型家族是否都存在可线性读取的 native routing signal；第二，将 **Skill usefulness** 和 **Skill safety / cost** 拆成两个 gate 后，能否保持路由质量。生产 Agent 最终需要回答的不只是“哪个 Skill 能做”，还包括“此刻是否值得、是否允许调用”。

## 3. Agent-Tool Transaction Boundary：MCP 的下一层协议可能是事务契约

**原始来源：** [When Tool Calls Succeed but Workflows Fail: Anomalies at the Agent-Tool Boundary](https://arxiv.org/abs/2609.15397) · [MCP annotation census artifact](https://github.com/flame-stream/mcp-annotation-census)

### 发生了什么

Agent Runtime 经常把工具调用建模成简单的 request → response：失败就 retry，超时就不确定，多个 Agent 可以并行调用。只要工具会修改外部世界，这个模型很快就不够用了。

论文构造了一个 effect-history model，将**世界里真实发生的 effect**与**runtime 看到的 observation**明确区分，并列出 8 类重复出现的 external-effect anomaly。典型例子包括：第一次调用其实已经付款成功，但响应丢失；Runtime 重试后产生第二次付款；某个投机分支最后被放弃，它已经写入的外部状态却无法撤销；后续已提交操作依赖一个之后被回滚的 provisional state。

作者进一步从这些 anomaly 反推 Tool boundary 需要暴露的能力，例如 outcome discovery、idempotency identity、compensation、staging / commit、effect scope 与可重排性，并指出有四类保证仅靠黑盒 `call(tool, args)` 无法普遍实现。

### MCP 审计告诉了什么

作者扫描官方 MCP Registry 暴露的 **98,291 个工具**。现有标准 annotation（如 read-only、destructive、idempotent、open-world hints）已经被大量 Server 使用，但这些字段主要表达调用级粗粒度提示，无法完整表达论文推导出的事务能力。

因此这里的问题并不是 MCP “缺少一个危险等级字段”。真正缺的是 Runtime 能否知道：

```text
这次 effect 是否已经发生？
重复请求能否指向同一 operation identity？
能否查询 operation outcome？
能否补偿？
能否先 stage 再 commit？
它修改了哪些资源？
哪些后续调用依赖它？
```

### 为什么重要

Agent 越来越多地执行发邮件、创建订单、改权限、写数据库、部署代码这类有副作用操作。Retry、Speculative Execution、Multi-Agent 并行都会把普通 RPC 失败放大成业务状态错误。

这类问题无法仅靠“让模型更谨慎”解决。Runtime 必须拥有确定性的 transaction contract，并把 LLM 的意图限制在协议允许的状态转移内。它和数据库事务、Saga、幂等 API 的思想非常接近，只是现在需要被提升为 Agent Tool 的一等协议能力。

### 可信度与局限

论文的理论边界很清晰，但 Registry census 只能看到 Server 暴露的接口与 annotations，没有执行 98,291 个工具，因此不能据此声称真实世界中某类 anomaly 的发生率是多少。Tool name / metadata 也无法完全判断实际副作用语义。

另一个现实限制是，并非所有 Tool 都能支持完整事务能力。发送真实邮件或外部支付之后，严格 rollback 可能不存在；此时设计重点应转为 pre-commit staging、operation identity、outcome query 与 compensation。

### 最值得继续追踪

MCP / Agent SDK 是否会开始标准化更强的 side-effect schema。最值得加入的字段不是更多自然语言描述，而是程序可消费的 contract，例如：

```yaml
side_effect:
  idempotency_key: supported
  outcome_query: supported
  compensation: cancel_order
  staging: true
  resource_scope: "orders/{order_id}"
  retry_semantics: at_most_once
```

一旦这类契约出现，Agent Runtime 才有条件在模型之外真正实现安全 retry、并发控制和 recovery。

## 4. VG-OPD：多 Teacher 蒸馏需要回答“谁教哪个 Token”

**原始来源：** [Who Teaches Which Token? Verifier-Gated Multi-Expert On-Policy Distillation for Scientific Reasoning](https://arxiv.org/abs/2609.15404)

### 发生了什么

现有 Multi-Teacher OPD 常在 sequence / prompt 层选择 Teacher：这个问题属于化学，于是整条 response 都由 chemistry expert 教。论文指出，这个假设太粗。一个 reasoning trajectory 中，Teacher 真正能提供增量信息的位置通常是稀疏的，而且不同 Expert 的价值会沿 token 改变。

VG-OPD 先把答案拆成多个 criterion。对于 Student rollout 中失败的 criterion，分别让 Expert 产生 counterfactual answer；只有某个 Expert 能在 verifier 上真正提高该 criterion，它才获得“教学许可证”。之后再比较 Expert 与 Student 的 token likelihood，在发生实质分歧的位置建立 mask；若多个 Expert 重叠，每个 token 最终最多由一个 verified Expert 提供监督。

其 KD signal 被写成 token-level advantage：

$$
A^{\mathrm{KD}}_{t}=-w_t\hat{k}_t,
$$

并与标准 GRPO 的 task advantage 联合优化。作者特别强调，$A^{\mathrm{KD}}_t\le 0$；如果没有 task reward 去平衡，纯 distillation 会持续压低概率质量并加速 entropy collapse。

### 关键结果

在 Qwen3-4B / 8B、4 个 RL-trained capability expert、7 个 benchmark 上，VG-OPD 两个规模都取得总体最优，5/7 benchmark 第一；剩余两个 MMLU-Pro / MATH500 距第一不超过 0.5 point。

相对 rubric-GRPO：

| Student | Scientific reasoning | Domain science | General reasoning |
|---|---:|---:|---:|
| Qwen3-4B | **+2.0** | **+3.3** | +0.2 |
| Qwen3-8B | **+1.7** | **+1.9** | 约持平（0.3 内） |

更有价值的是负结果：纯 OPSD / MOPD 并没有稳定超过 RL floor；将 distillation 变成 dense fusion 同样可能无收益。作者的 ablation 显示，**把相同监督预算放错 token 是破坏最大的一项**。

### 为什么重要

近期 OPD 研究越来越指向一个共同结论：Teacher quality 只是第一层问题，真正决定效率的是 **Teacher signal 是否出现在 Student 自己访问的正确状态和正确位置**。

Multi-Expert 系统尤其如此。Expert 只应该在自己能通过 verifier 证明有增量的局部区域介入，否则“更多 Teacher”会变成更大的梯度冲突源。

### 可信度与局限

实验只覆盖科学 / 数学 text reasoning，criterion bank 与 verifier 相对结构化。Tool Agent、Search Agent 的 failure criterion 更难拆分，Verifier 也经常不可靠。

这套方法还有明显额外成本：每个 prompt 需要对 Expert 做 probe，licensed Expert 还要在 Student rollout 上跑 forward。最终是否比增加更多 rollout 更划算，需要按固定 GPU-seconds 比较。

### 最值得继续追踪

最值得迁移到 Tool RL：把 `plan correctness / tool choice / argument construction / observation interpretation / final answer` 拆成 criterion，只在某个 Specialist 能通过 executable verifier 改善该 criterion 时，才对对应 action token 施加 distillation。若这条线能成立，Multi-Agent / Multi-Expert 能力整合会从“整条轨迹找一个老师”走向真正的局部 routing。

## 5. LION：推荐系统持续进化时，先隔离不同用户的更新冲突

**原始来源：** [Self-Evolving Memory for Generative Recommendation](https://arxiv.org/abs/2609.15598) · [代码仓库](https://github.com/JazyJiang/Self-Evolving-Memory-for-Generative-Recommendation)

### 发生了什么

生成式推荐把用户历史和 next-item identifier 统一进一个 autoregressive model。持续学习时，所有用户最近发生的兴趣变化都在同一个 Transformer 参数空间里更新。LION 把其中一个常见问题明确命名为 **evolution conflict**：高活跃用户和主流行为模式出现得更频繁，梯度规模更大；低频、个性化的 preference shift 更容易被共同参数更新覆盖。

LION 在主干中间加入 sparse Key-Value memory。完整用户历史用于计算 memory query，只激活 Top-K memory slots；Transformer 前后主干仍只处理较短 recent sequence。这样既让不同 pattern 尽可能走不同 memory parameter，又避免把完整长历史都送进昂贵主干。

其优化目标为：

$$
\mathcal{L}=\mathcal{L}_{rec}+\lambda\mathcal{L}_{con},
$$

其中 consolidation loss 直接监督 memory-enhanced representation，目标是让低频 pattern 在流式训练中仍得到足够强的学习信号。

### 为什么重要

推荐系统的 continual learning 常被抽象成“最近数据权重多大、Replay 留多少、多久增量训练一次”。LION 提醒了另一个更结构性的问题：**不同用户的变化是否必须在同一组参数上互相竞争。**

Sparse Memory 把这种冲突从优化问题转成部分 routing 问题。理论上，两个行为 pattern 激活的 slot 重叠率 $\rho$ 越低，它们在 Memory 参数上的梯度冲突上界越低：

$$
\frac{Conflict_{LION}}{Conflict_{shared}}\le \rho.
$$

这个思想与 MoE、personalized adapter、continual expert routing 都有连接，但 Memory 的参数规模不按用户数量线性增长，更适合大规模用户系统。

### 可信度与局限

论文已被 CIKM 2026 接收，代码开放，并在 3 个真实 Amazon Review 数据集、多个 evolving period、不同用户／Item 分桶中评测。现阶段仍是离线数据；没有线上 A/B，也没有高 QPS production serving 的内存、更新和 cache 数据。

Sparse KV 的“组合容量”很大，不等于它能自动形成语义上稳定、无碰撞的用户 pattern。路由 key 本身仍需在流式训练中学习，并可能发生 drift。

### 最值得继续追踪

重点看两个现实问题：第一，用户兴趣突然变化时 memory slot 是否能快速重路由而不破坏旧 pattern；第二，在百万／亿级用户、高频增量训练中，Top-K memory routing、slot hotness 和 distributed parameter update 是否会形成新的热点瓶颈。

## 6. MAPS：把“这条请求会生成多长”变成 Decode 调度信号

**原始来源：** [MAPS: Memory-Aware Predictive Scheduling Framework for Large Language Model Serving](https://arxiv.org/abs/2609.15359)

### 发生了什么

P/D disaggregation 把 Prefill 和 Decode 拆到不同 worker，但 Decode 仍有一个难解问题：请求刚到 Prefill 时，系统不知道最终会生成 50 token 还是 5,000 token。Round-robin 或简单 least-load 只能看到当前队列，看不到即将占用多少 KV memory、持续多久。

MAPS 在设备端先跑一个轻量 LLM，预测请求的 output length；预测与云端 Prefill 并行，因此论文设定中额外 latency 很小。由于长度预测天然有误差，系统不直接使用点估计，而通过 uncertainty-aware calibration 生成有目标 coverage 的 upper bound，再据此做两级调度：全局阶段避免某个 Decode worker 未来 KV 饱和，本地阶段用 SJF 降低 head-of-line blocking。

### 关键结果

两类真实 workload、两个 LLM 上，MAPS 相对三种 SOTA 系统报告：

- 平均端到端延迟降低 **42.6%**；
- tail latency 最高降低 **84.8%**。

论文的 calibration 结果也很说明问题：原始 predictor 对长输出的 underestimation 很严重，引入 uncertainty-aware calibration 后，欠估概率明显下降。调度器真正需要的不是“预测最准确的平均长度”，而是一个足够可靠的风险上界。

### 为什么重要

这和传统 SJF 的差异在于，LLM output length 只能在生成结束后才知道。只要能在 Prefill 阶段得到一个廉价、校准后的 proxy，就可以提前把 **未来的 KV occupancy 与 service time** 纳入 routing。

Agent workload 的输出长度通常比普通 Chat 更重尾：有的 turn 只产生一个 Tool Call，有的 turn 会输出大段代码、JSON 或分析文本。随着 P/D、KV offload 和 cache-aware routing 普及，output-length uncertainty 会越来越直接地影响整个 cluster 的容量利用率。

### 可信度与局限

MAPS 已被 ICML 2026 接收，且使用真实 workload；但只覆盖两类 LLM。Device-assisted predictor 还假设终端存在足够算力，并能在 Prefill 时间里隐藏预测成本。弱设备、短 prompt 或低延迟请求未必满足这个条件。

预测分布也会随模型版本、sampling temperature、Agent Harness 和任务分布变化，conformal calibration 必须持续维护。长度上界过保守时，虽然安全，却会重新造成资源浪费。

### 最值得继续追踪

最值得看 MAPS 与 **prefix-aware routing / tiered KV cache / tail-aware workflow scheduling** 的联合结果。未来 Router 需要同时知道：某个请求可能生成多长、当前 KV 在哪里、哪个 workflow 更接近 critical path，以及各 Decode worker 还有多少可安全承载的 memory headroom。

## 今日值得收藏的代码 / 学习资源

### Stellar Colosseum：长程研究 Agent 的 Harness 比“多开几个 Agent”复杂得多

[Stellar Colosseum](https://arxiv.org/abs/2609.15983) 把长证明／理论计算机研究组织成一套明确流程：先并行探索策略，用 readiness gate 判断是否足以进入 proof construction；再将证明拆成互相依赖的 section-level subproblems；Verifier 的反例和缺陷被定向送回受影响 section，而不是把整个结果丢回全局重做；最后通过 random-sample tree aggregation 合并候选与 critique。

论文在 TCS-Bench 上用 Gemini 3.1 Pro + Gemini 3.7 Flash 的 cross-model selection 达到 **71.0%**；Codeforces 中，加入 execution feedback 后完成 **218/222**。作者还声称解决若干来自 FOCS/JMLR 论文的 open problems。这些开放问题结果在独立数学／理论 CS 社区充分核验前应保持谨慎，Benchmark 结果则足以说明 Harness 结构本身值得研究。

### SkillLift：Skill Evolution 也需要廉价、可复用的评价器

[SkillLift](https://arxiv.org/abs/2609.15396) 研究的是另一个常见成本问题：真实 Skill 是否有效往往需要昂贵 oracle / executable evaluation。它先用少量 Oracle 信号学习一个结构化、与 Oracle 排序一致的 dense rubric，让内层 Skill revision 大量使用廉价 rubric；外层再周期性用稀疏 Oracle rollout 校正评分器。论文报告相对自动 Skill 优化 baseline 在保持／提高效果的同时减少 **40%–70% token cost**。

这和昨天的 Skill 行为评测问题可以连起来看：Skill 优化的瓶颈越来越像“怎样获得足够可靠、又便宜的 behavioral feedback”，而不是怎样让 LLM 写出更漂亮的说明文档。

### HypoEvolve：多 Agent 科学假设生成开始显式用 Evolutionary Search

[HypoEvolve](https://arxiv.org/abs/2609.15938) 用遗传算法协调多个专门化 LLM Agent，在癌症脆弱性／基因依赖方向进行假设生成、变异、选择和验证；论文覆盖 34 个 cancer types，并报告 DepMap selectivity 0.171，相比最强 baseline 的 0.115 更高。

这是一个值得跟踪的 automated discovery 结构，但证据目前主要是 retrospective computational evaluation 与外部知识支持。没有湿实验验证前，不能把这些候选等同于新的生物学发现。

**首选 RSIAgent，但阅读重点应该放在增量归因，而不是“超过 GPT-6”这一 headline。**

[论文原文](https://arxiv.org/abs/2609.15364) · [代码仓库](https://github.com/AetherLabsAI/RSIAgent)

## 今日可立即实践的一件事

给现有 Tool / MCP Agent 做一次 **Side-Effect Contract Audit**。这个实验不需要训练任何模型，成本低，而且很容易暴露当前 Runtime 的真实安全边界。

先从所有工具里筛出会修改外部状态的 10–30 个，例如发邮件、写数据库、创建工单、部署、付款、下单、删除文件。为每个 Tool 补一个本地 contract：

```yaml
tool: create_order
side_effect: true

transaction:
  idempotency_key: unknown
  outcome_query: none
  compensation: cancel_order
  staging: false
  resource_scope: "orders/*"

retry:
  safe_after_timeout: unknown
  safe_after_5xx: unknown
```

然后至少跑四类 failure injection：

```text
A. Tool 已成功，但 response 在返回前丢失
B. Runtime timeout 后自动 retry
C. 两个 Agent 并发修改同一 resource
D. 上游 provisional action 被取消，但下游 action 已提交
```

记录：

```python
metrics = {
    "duplicate_effect_rate": 0.0,
    "unknown_outcome_rate": 0.0,
    "uncompensated_abort_rate": 0.0,
    "cross_agent_conflict_rate": 0.0,
}
```

优先修复那些同时满足“有真实副作用 + timeout 后结果不可查询 + retry 非幂等”的工具。对这类 Tool，继续优化 Agent Prompt 几乎没有意义；Runtime 至少需要 operation identity、outcome discovery 或 pre-commit staging 中的一项确定性机制。

**停止条件：** 如果一个 Tool 是纯只读、重复执行天然无副作用，就不必强行引入完整事务协议；事务能力应该与实际 effect class 匹配。真正要回答的是：

> **当网络只告诉你“这次调用结果未知”时，你的 Agent Runtime 能否区分“没发生”与“已经发生但响应丢了”？**

如果答案是否定的，那么自动 retry 本身就是业务状态风险。

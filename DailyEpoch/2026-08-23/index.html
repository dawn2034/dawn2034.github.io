今日主线： Agentic Tool-Use Mid-Training · Skill Transfer Granularity · Adaptive Test-Time Compute · E-commerce Retrieval RL · Agentic Search Benchmark · MoE Hyperparameter Scaling

今日核心判断

  1. Agent 能力塑形正在进一步前移到 Mid-Training，而不是把 Tool Use 全部留给 SFT/RL。 MidTool 的 20.3B-token mixture 在相同后训练配方下显著改善 BFCL、τ²-Bench 与 MCP-Universe，尤其是多轮工具执行；但 Deep Search 子任务仍几乎没有改善，说明“通用工具先验”和“长程探索式 Agency”可能是不同能力层。
  2. Self-Evolving Agent 的 Skill 不是越完整越好，粒度过粗甚至会产生负迁移。 Break It Down, Pass It On 发现 whole-task skill 平均拉低成功率，而 subtask-level text skill 才稳定正向；这说明 Skill Store 的核心设计问题不是“存多少”，而是“抽象到什么粒度”。
  3. Test-Time Scaling 正在从固定 token budget 变成 policy 本身的决策变量。 Learning When to Think 让模型首 token 直接选择 NoThink / Short / Long，无独立 router，在 MATH500 上以轻微准确率损失换来 41% 平均 token 降低，并在 GSM8K 上达到 76% token 降低。
  4. 推荐／搜索中的 GRPO 需要重新审视 reward source。 SSR-GRPO 不再依赖与被训练策略高度同构的 42B LLM judge，而用 Semantic ID + dense representation 形成双视角 relevance reward，同时用 SID 挖 hard negative；两周线上 A/B 相比 R-GRPO 继续提升 UCTCVR 与 GMV。
  5. Agentic Search benchmark 可能严重低估真实检索难度。 把 BrowseComp-Plus 的同一批问题投影到 400B-token、553M-document 的 ClimbMix 后，最强 Agent 的答案准确率只下降约 5 个点，但 evidence recall 从 84.3% 跌到 21.4%，搜索调用增加 63%；这说明“答对”可以掩盖检索本身已经失败。
  6. 超大 MoE 的学习率不一定需要在目标规模上暴力 sweep。 一项 COLM 2026 工作把 μP 的 width transfer 与 token-horizon scaling law 组合，在 proxy MoE 上拟合后外推到 10T-token 训练，报告 $R^2=0.95$，并用于 155B total / 17B active 模型的全程预训练。

1. MidTool：Tool Use 可能应该在 Mid-Training 阶段成为显式能力目标

一句话结论： 如果只靠 SFT / RL 教工具调用，模型可能学会格式，却缺少跨工具、跨环境可迁移的 schema grounding 与 workflow prior；MidTool 提供了“先塑造通用工具先验、再后训练”的直接证据。

论文： MidTool: Mid-training Data Synthesis for Agentic Tool Use

发生了什么

MidTool 构建了一个面向通用 Tool Use 的开放 Mid-Training 数据管线。最终的 MidTool-Mix 含 20.3B tokens、11.22M samples，来源包括 Web、PDF、Code 和 Tool/API/MCP 资源；比例约为 Web 42%、Code 26%、PDF 23%、native agentic trajectories 9%。

它不是简单把 API 文档拼进语料，而是增加两类合成监督：一类强调 context grounding，让模型从技术文档中恢复参数、约束和调用语义；另一类是 native agentic trajectory，让模型学习连续工具选择、执行和恢复。作者随后在 Qwen3-4B-Base 和 8B-Base 上先做 Mid-Training，再使用相同的 SFT / RL 配方比较。

8B 也呈现类似趋势：BFCL Overall 从 Base+SFT 的 47.62% 提升到 MidTool+SFT+RL 的 55.12%，Multi-turn Avg 从 25.25% 提升到 37.63%。这说明收益并非只存在于 4B 小模型。

更有信息量的是负结果：在 MCP-Universe 的 Web Search 子集上，多种 MidTool 设置仍为 0.00。作者据此把能力边界解释为：通用 Tool-Use Mid-Training 能教 schema grounding、tool selection 和 workflow composition，但 Deep Search 所需的长程证据收集、搜索策略修正和探索控制仍需要专门 trajectory 与训练目标。

为什么重要

这会改变 Agent 后训练项目的数据规划。很多 pipeline 默认：基础模型负责“通用语言能力”，工具能力全部在 SFT / RL 阶段补上；MidTool 的结果支持另一种分层：

可信度与局限

优势是作者在 4B/8B、三个不同性质的 benchmark 上做了 matched downstream recipe，对“Mid-Training 是否提供独立增益”隔离得较清楚，而且明确公开了数据构造逻辑与 benchmark blacklist。

局限也很明显：MidTool 数据里仍包含模型合成 trajectory，且不同来源使用了不同教师模型；因此它不能证明“只靠原始开放技术语料”就能得到同等收益。更重要的是，Deep Search 基本不受益，说明把 Tool Use 当成单一能力类别过于粗糙。

最值得继续追踪

最值得看两件事：第一，Mid-Training 的收益在更大 base model 上是否继续成立，还是主要修补小模型能力缺口；第二，是否能为 Search / Coding / Computer Use 分别形成专门的 Agentic Mid-Training mixture，并得到可预测的能力分工。

2. Break It Down, Pass It On：Skill 粒度错了，Memory 会让 Agent 变差

一句话结论： Self-Evolving Agent 不应该把完整任务轨迹直接蒸馏成“大 Skill”；更可迁移的是足够具体、又不绑定单一任务的 subtask-level text skill。

论文： Break It Down, Pass It On: Cross-Task Skill Transfer in LLM Agents

发生了什么

作者在 AppWorld、OfficeBench、KramaBench 和 11 个模型上控制 Skill 的两个变量：抽取粒度（whole task vs subtask）与表达格式（Text vs Code）。核心问题不是“Agent 能不能总结经验”，而是总结出的经验能否跨任务复用。

结果反直觉：whole-task skill 平均不是帮助，而是伤害。相对 no-memory baseline，Task-Level Text skill 让成功率平均下降 1.2 个百分点，Task-Level Code 下降 4.1 个百分点，个别 benchmark 最多下降 7.4 个点。相同 induction prompt 放到 subtask level 后，Text skill 平均提升 1.9 个点，Code 提升 0.5 个点。

为了排除“是 Agent 架构而不是 Skill 本身导致”的解释，作者把 subtask-level agent 生成的 Skill 直接 replay 给 task-level agent：成功率相对其原有 whole-task Skill 平均提升 9.9 个百分点，AppWorld 最高 +17.2；说明效果确实随 Skill 内容转移。

一个值得直接拿走的量：Skill Utility

作者把 Skill 的可迁移价值拆成 specificity 与 abstractness，并定义：

\[\mathrm{utility}(s)=\mathrm{specificity}(s)\cdot\mathrm{abstractness}(s).\]

直觉是：太具体会绑定某一个任务，太抽象则没有可执行信息。仅凭 Skill 描述和任务说明计算出的 utility，与真实成功率呈单调关系；从最低到最高 utility 分桶，task-level agent 成功率从 14.0% 升到 24.5%，subtask-level 从 22.8% 升到 31.0%。

为什么重要

这给 Skill Store 一个比“embedding 相似度”更根本的设计问题：被检索到的 Skill 是否处在可迁移的抽象层级。 一个完整任务总结可能包含太多局部实体、顺序和环境偶然性；它看起来信息丰富，却容易成为错误约束。

因此更合理的 Skill 生成链路可能是：

可信度与局限

论文覆盖模型和 benchmark 较广，并通过 skill replay 和高／低 utility memory intervention 做了更接近因果验证的实验，这是强项。

但 utility 目前依赖作者定义的 embedding / similarity-based operationalization；它是一个有预测力的启发式，不是普适的 Skill 信息论定理。对 Coding Agent、Research Agent 等高度开放任务，什么算“合适粒度”仍可能完全不同。

最值得继续追踪

最值得追的是自动 Skill segmentation：Agent 能否不依赖人工 subtask boundary，自行把长 trajectory 切成最有 cross-task transfer 的 Skill 单元，并用未来 reuse outcome 反过来校正粒度。

3. Learning When to Think：让模型自己决定 NoThink / Short / Long

一句话结论： Test-Time Compute 的下一步不是给所有题更多 token，而是让“思考多久”成为 policy 的显式 action，并直接对质量—成本 trade-off 做 RL。

论文： Learning When to Think: Adaptive Reasoning for Test-Time Compute Allocation

发生了什么

作者让模型把 response 的第一个 token 作为 reasoning mode：NoThink、Short 或 Long。它没有额外训练独立 router，而是把 mode selection 一并放进 GRPO，通过 shaped reward 让不同模式在不同 response length 上都有价值，同时给每个 mode 设置 hard token cap，防止策略全部塌到同一种模式。

在一个 1.5B distilled model 上用 MATH 训练后，三种模式都持续被使用。一个有趣现象是，NoThink / Short 最终反而比 Long 更准确；作者将其解释为 policy 学会了按题目难度分流，而不是随机选择模式。

关键结果

设置MATH500 AccuracyMean Response Tokens
Base0.7964,796
Adaptive Policy0.7822,811

平均 token 减少 41%，准确率下降 1.4 个百分点。模型未经重新训练迁移到 GSM8K 时，作者报告 token 数降低 76%，且在相近 response length 下准确率优于比较 baseline。

为什么重要

固定 max token 只是“允许模型思考这么久”，不是真正的 compute allocation。真实 serving 更关心：

\[\max \; \mathbb{E}[\text{quality}] - \lambda\,\mathbb{E}[\text{compute}].\]

把 mode selection 放进 policy 内部，意味着模型可以基于问题本身决定是否值得多花推理预算。这比外部 router 的优势是联合学习，缺点则是 reward design 很容易把策略推向某个便宜模式。

可信度与局限

结果目前主要来自数学题与 1.5B 模型，且 accuracy 并没有无损保持；41% token reduction 是用 1.4 个百分点准确率换来的，不应描述成“免费加速”。GSM8K 的跨域结果很有吸引力，但仍属于较容易、答案可验证的数学任务。

此外，NoThink / Short 更准确并不证明短 reasoning 天然更优，也可能部分来自 router 把难题集中送给 Long，造成 selection bias。

最值得继续追踪

真正关键的是把 mode 从离散三档扩展到更连续的 compute controller，并在真实 Agent 环境里同时考虑 tool-call cost、latency、verification cost，而不只是输出 token 数。

4. SSR-GRPO：推荐检索里的 Reward Model 不一定非要是另一个大 LLM

一句话结论： 对 Dense Retrieval，Semantic ID 可以同时承担 hard-negative hierarchy 和低成本 relevance reward；线上结果说明它不仅是离线建模技巧，但“更 unbiased”仍是作者假设，不是已被证明的客观属性。

论文： SSR-GRPO: Integrating Supervision and Semantic IDs into Reinforcement Learning for Dense Retrieval in E-commerce

发生了什么

R-GRPO 在训练时从当前 batch 检索 top-K candidate，再根据 relevance reward 做 group-relative optimization。作者指出两个风险：batch 内 top-K 候选池太小，容易混入 trivial / noisy negatives；原方法依赖 TaoSR1 这类 42B-MoE relevance LLM 作为 reward source，而这个 Judge 与被优化策略采用相似的 RL 训练范式，可能产生 correlated judgment。

SSR-GRPO 用两种信号替代单一大 Judge：dense representation 提供细粒度连续语义，RQ-VAE 产生的 hierarchical Semantic ID 提供离散层级匹配。SID 同时用来挖 hard negatives，构造 Retrieval-DPO，并生成 masking function 过滤 group 内不值得学习的 easy negative。

关键结果

离线使用超过 3 亿条天猫点击／购买日志。以 Tbstars-3B SFT 为 base：

方法HR@4k GeneralHR@4k Long-TailGR@100 GeneralGR@100 Long-Tail
SFT Base0.78720.47540.91740.6941
+ R-GRPO0.81580.58570.93050.7126
+ SSR-GRPO0.82180.59430.93720.7195

更值得注意的是 relevance reward ablation：Sparse SID-only 的 HR@4k 为 0.8154，略高于使用 TaoSR1 Judge 的 0.8152；Dense + SID 双视角进一步到 0.8161。这个结果支持“低成本结构化信号可以替代昂贵 Judge”的可能性，但差距很小，不宜过度解释。

相对 R-GRPO，论文报告 UCTCVR 再提升 0.61%、GMV 再提升 0.39%，且具有统计显著性。

为什么重要

这对推荐／搜索 RL 有两个启示。第一，Reward Model 不应默认越大越好；如果 reward source 与 policy 具有相似偏差，规模并不能自动带来独立性。第二，Semantic ID 的价值不只在生成式推荐，也可以作为 retrieval space 的层级监督，直接用于 hard-negative mining 和 reward shaping。

更一般地说，retrieval RL 的稳定性可能来自 结构化可解释监督 + outcome optimization 的组合，而不是完全依赖 LLM-as-a-Judge。

可信度与局限

这是 CIKM 2026 工业工作，并有两周真实线上 A/B，证据强于纯离线论文；但 backbone、数据和线上系统均为内部环境，外部无法独立复现。

论文称 SID reward 更“unbiased”，这个措辞需要谨慎：实验只能说明它在这些指标上不差于 TaoSR1，并不能证明它对真实 relevance 没有系统性偏差。SID 本身也可能继承 quantization/codebook bias。

最值得继续追踪

最值得看的是 reward calibration：SID reward、dense score、human relevance 和长期用户行为之间的相关性究竟如何，以及在 OOD query、冷启动商品和多义 query 上是否出现新的系统偏差。

5. BrowseComp-Plus → ClimbMix：Agentic Search 的真正瓶颈可能被小语料库遮住了

一句话结论： 如果 benchmark corpus 本身太小、太人工整理，Agent 的“搜索能力”很可能被答案准确率高估；把同一问题放进更接近 Web-scale 的自然语料后，retrieval recall 会先崩。

论文： Projecting BrowseComp-Plus onto ClimbMix: Toward More Realistic Corpora for Agentic Search
代码： castorini/cmass
数据： BrowseComp-Plus CM / ClimbMix artifacts

发生了什么

原 BrowseComp-Plus 的检索语料约 10 万文档。作者认为，这与真实 Search Agent 面对的 Web-scale 搜索空间差太远，因此把原问题“投影”到 ClimbMix：一个约 400B tokens、553M documents 的自然 Web corpus。

投影不是简单换索引。每个问题先被分解成 atomic reasoning hops，然后为每一 hop 在目标 corpus 中寻找证据；只有自动验证、独立 Agent 验证和人工检查都确认所有必要 hop 有支撑时，问题才保留。830 个 BrowseComp-Plus 测试问题最终只有 57 个通过全流程。

关键结果

在同一组 57 个问题上，只替换 corpus：

最强 Agent 的 answer accuracy 只下降 5.3 个百分点，但 evidence recall 从 84.3% 降到 21.4%，tool calls 增加约 63%。更关键的是，GPT-5.6 Sol 对这 57 题在完全禁止检索时仍能答对 70.2%，说明最终 accuracy 里混有大量 parametric memorization。

为什么重要

这篇工作把 Search Agent 的评测拆出了一个被经常忽略的变量：corpus realism。在一个高度裁剪、文档数量有限的语料库上，Agent 可以表现得像“会搜索”；换成三数量级更大的自然文档空间后，真正困难的是候选发现和 evidence recall，而不一定是 reasoning。

因此 Search Agent benchmark 不能只报 final answer accuracy。至少还应同时报告：evidence recall、retrieval calls、citation correctness，以及 closed-book accuracy，否则模型记忆和检索能力会被混在一起。

可信度与局限

优点是作者对 57 题逐 hop 做了严格 grounding，并在同题、同 Agent、只换 corpus 的条件下比较，因果解释比较干净。

但 57 题很小，而且从 830 题筛到 57 题带来明显 selection bias；被保留下来的问题本身可能更容易被大模型记住。作者也明确指出 projection 的若干步骤依赖 Agent 判断，因此从头重跑并不保证得到完全相同的集合。

最值得继续追踪

下一步最重要的是扩大投影 yield，并把 per-hop evidence judgment 纳入 headline metric。对于生产 Search Agent，真正应该优化的是“在大规模自然语料里找到必要证据并能引用它”，而不只是最后给出正确字符串。

6. MoE Hyperparameter Transfer：把昂贵 Learning-Rate Sweep 从 155B 模型移回 Proxy

一句话结论： 这项工作证明的是“一个特定 MoE + MLA + Muon 配方下，宽度与 token horizon 的 LR transfer 可以很好拟合”，而不是所有大模型超参都能用 scaling law 一步预测。

论文： Let’s Scale Step by Step: Compute-Efficient Hyperparameter Transfer for Large-Scale Mixture-of-Experts

发生了什么

大规模 MoE 预训练时，直接对最终模型做多组 learning-rate sweep 几乎不可接受。作者提出两步 transfer：先为带 MLA、Muon optimizer 的 MoE 构造 μP 参数化，使 optimal LR 能跨 width transfer；再在固定 proxy 模型上研究 optimal LR 如何随 token budget 变化，用 log-log regression 外推到 10T-token horizon。

用于 token-horizon 拟合的 base proxy 为 10.8B total / 3.3B active，约训练 500B tokens；作者在 255B–502B token 区间拟合得到 $R^2=0.95$，预测 10T-token 训练的 optimal LR 为 $3.85\times10^{-4}$。随后将该设置用于一个 155B total / 17B active MoE 从头训练 10T tokens。

关键结果

作者指出，完整目标模型训练的 compute 约为用于 LR 预测的 proxy runs 总 compute 的 98×。换句话说，真正的价值不是 benchmark 多几个点，而是把“调参是否正确”的验证尽可能前移到小模型／短 token horizon。

155B 模型在 10T-token Stage-1 预训练中没有出现 loss spike，并得到作者认为具有竞争力的语言、数学和代码评测结果。这提供了实证支持，但并不是“预测 LR 已被证明为全局最优”：作者明确承认在 10T token 上再做 exhaustive sweep 本身就不可行。

为什么重要

超大模型训练里，不能验证的超参最优性本身是常态。与其在目标尺度上盲目试错，更合理的方向是建立 proxy-to-target 的可校准 transfer law，并用少量 held-out scale 验证外推误差。

这也说明 scaling law 不只用于预测最终 loss / compute-optimal size，也可以用于预测优化器超参数，直接减少试验性训练的浪费。

可信度与局限

这篇工作已标注 COLM 2026，并且真的用预测 LR 训练了 155B/17B-active、10T-token 模型，这是重要的 scale validation。

但范围很窄：MoE 架构含 MLA，optimizer 是 Muon，width 与 sparsity 还联合变化；论文自己也承认无法把 sparsity 维度独立拆出，更没有证明 batch size、weight decay、router auxiliary loss 等超参拥有同样 transferability。

最值得继续追踪

最值得看的是三个扩展：不同 optimizer 是否仍成立；sparsity 独立变化时 LR transfer 是否稳定；能否从“一个 global LR”进一步走向 per-expert update scale，因为不同 expert 实际接收的 token 数和 gradient-noise scale 并不相同。

今日值得收藏的代码 / 学习资源

  • MidTool：最值得直接研究其数据配比和 ablation。它的强点不是“20B token 很大”，而是把 raw technical corpus、context-grounded augmentation、native agentic trajectory 三类数据的贡献分开测了。
  • CMASS / BrowseComp-Plus on ClimbMix：如果在做 Search Agent / Deep Research eval，这个项目适合拿来检查“答案正确”和“证据真的找到了”之间的差距；Hugging Face 数据也已公开。
  • DeltaML-Bench / 代码：48 个来自真实研究论文仓库的 ML experimentation task。一个值得注意的结果是，在 4×6h allocation 下，ARG scaffold 把 GPT-5 per-run success 从 9.4% 提到 33.9%；2×12h 时达到 49.0%，而普通 Modular scaffold 的 specification gaming 最高达到 47.9%。它适合研究“Agent 研究能力”和“scaffold / integrity checks”如何耦合。
  • SCoRD：Continual Recommender 的一个实用思路——昂贵 LLM reranker 只在困难样本上生成 intent-level guidance，后续 retriever 更新不重复调用 LLM；论文在三个流式推荐数据上同时分析 stability / plasticity，并报告 semantic generation 时间相较 CoT-Rec 约降低一个数量级。

X.com｜近期高信号技术讨论

本轮没有发现可以高置信纳入正文的近 24–72 小时 X.com 技术帖。不是因为没有执行检索，而是公共搜索索引实际返回的内容主要是旧帖、趋势页、透明度文档或无法确认近期发布时间的片段；4 个围绕当天论文的 Event-driven 查询也没有返回原帖。

本轮 X.com 检索审计 | 项目 | 数量 | |---|---:| | Broad Topic 查询 | 8 | | 账号／作者查询 | 6 | | 中文作者／社区查询 | 3 | | 同义词／72h 回退查询 | 8 | | Event-driven 查询 | 4 | | 独立查询总数 | 29 | | 可解析搜索结果总数 | 34 | | 去重后的原始 `/status/` 搜索结果 URL | 3 | | 通过硬条件的帖子 | 0 | 48 小时召回已在首轮检索中执行；由于原始 `/status/` URL 少于 8 个，又执行了同义词、作者方向和 72 小时回退。Event-driven 查询占总查询数约 13.8%，低于 30% 上限。 主要淘汰原因：返回结果超过时间窗口；结果是 X Trending / 帮助页 / 透明度 PDF 而不是原帖；原始帖正文或日期无法稳定核验；技术信息量不足。

公共 Web Search 对 X.com 的实时索引覆盖有限，因此这表示本轮无法高置信核验，不代表 X.com 当天不存在相关热门讨论。

今日最值得花 30 分钟阅读的一项

首选：MidTool: Mid-training Data Synthesis for Agentic Tool Use。

建议不要从“BFCL 又涨了多少”开始读，而按下面顺序：先看 MidTool-Mix 的数据构成，理解 raw technical corpus、context-grounded augmentation 和 native agentic trajectory 分别教什么；再看 matched-budget generic Mid-Training baseline，判断收益是否只是“多训了 20B token”；然后看 BFCL、τ²-Bench、MCP-Universe 三类 benchmark 的收益差异；最后一定看 Web Search 仍为 0.00 的负结果。

这篇真正值得带走的判断是：

Agentic capability 很可能需要在 Mid-Training 阶段显式塑形，但“会调用工具”和“会做长期探索”不是同一个能力。

如果后续 Agent foundation model 逐渐把 Tool / Search / Coding 数据前移到 pretraining→mid-training pipeline，那么单纯比较 post-training recipe 会越来越难解释最终 Agent 能力来自哪里。

今日可立即实践的一件事

给现有 Agent Memory / Skill Store 做一次 Skill Granularity Audit，不改模型参数，只验证“你存进去的经验到底是在帮助还是制造负迁移”。

从最近 20–50 条成功或失败 trajectory 中，各生成两版 Skill：

1
2
3
4
5

A. Task-level Skill
   把整项任务总结成一条完整操作经验

B. Subtask-level Skills
   先拆成可独立复用的步骤，再分别总结

对同一批 held-out related tasks 分别跑 No Memory / Task Skill / Subtask Skill，记录：

1
2
3
4
5

success_rate
negative_transfer_rate
retrieved_skill_count
skill_token_cost
cross_task_reuse_count

定义最简单的负迁移率：

\[\mathrm{NegativeTransferRate} = \frac{\#\{\text{No-Memory 成功但加 Skill 后失败}\}} {\#\{\text{No-Memory 成功}\}}.\]

再为每条 Skill 做一个人工版两维评分：

1
2

specificity: 1~5   # 是否包含足够可执行信息
abstractness: 1~5  # 是否摆脱当前任务实体/偶然顺序

先用乘积作为粗略 utility：

\[U(s)=\mathrm{specificity}(s)\times\mathrm{abstractness}(s).\]

停止条件： 如果 Subtask Skill 相比 No Memory 没有提升，或 NegativeTransferRate 反而更高，不要继续增加 Memory 数量；先检查 task decomposition、retrieval precision 和 Skill 中是否混入实体绑定／过期环境假设。反过来，如果 Task-Level Skill 明显负迁移而 Subtask Skill 稳定正向，就说明问题主要在 Skill abstraction boundary，而不是 embedding top-k。

这项实验的成本很低，却能直接回答一个比“Memory 命中率多少”更重要的问题：Agent 存下来的经验，究竟是不是可迁移能力。

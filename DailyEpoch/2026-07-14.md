# 每日 AI 技术简报｜2026-07-14

## 今日判断

今天最值得关注的主线有三条：

1. **Agent 评估正在从短任务成功率，转向长时间持续推进能力。**
2. **低比特量化开始把输出梯度和任务敏感度纳入二阶近似。**
3. **长上下文优化逐渐从“扩大窗口”转向“选择证据并进行实例级适配”。**

推荐系统方向，本轮没有发现足够新、证据完整且值得强行纳入的成果。

## 1. LHTB：Agent 真正的瓶颈是持续工作能力

**发生了什么**

Long-Horizon-Terminal-Bench 提供了 46 个容器化终端任务，覆盖软件工程、实验复现、科学计算、多模态分析和交互游戏等九类场景。任务通常需要数百次交互，平均消耗约 990 万 token、231 个执行回合和 85.3 分钟。论文中的最强模型在严格阈值下 pass@1 仅为 15.2%。

该基准使用细粒度子任务和连续奖励，使“完成了 70%”与“只完成了 20%”能够被区分。代码仓库同时提供 Docker 环境、隐藏验证器、参考答案和 Harbor 配置。

**为什么重要**

这类基准更接近真实 Agent 产品：

- 状态需要维持几十分钟；
- 前期错误会在后续不断放大；
- Agent 必须管理上下文、检查结果、恢复失败并判断何时停止。

这意味着下一轮 Agent 能力提升，很大一部分可能来自 **harness、状态压缩、检查点、错误恢复和任务调度**，单纯更换底座模型未必是最高杠杆。

**可信度与局限**

可信度：**高，论文、代码、数据和可运行配置均已发布。**

需要注意，论文摘要报告了 15 个模型，而仓库的后续排行榜已经扩展到 21 个模型，结果数字也有所变化。阅读时应区分论文静态实验与持续更新的在线排行榜。

**继续追踪**

重点看不同模型的失败轨迹：

- 什么时候开始循环；
- 上下文摘要是否丢失关键状态；
- 工具错误与推理错误各占多少；
- 部分奖励能否转化成训练 Agent 的过程奖励。

## 2. KronQ：将输出端曲率引入 LLM 量化

**发生了什么**

GPTQ 类方法主要使用输入激活构造 Hessian 近似。KronQ 加入输出梯度协方差，在 K-FAC 近似下将曲率写成：

$$
H \approx H_X \otimes H_G
$$

其中 $H_X$ 描述输入激活，$H_G$ 描述输出端梯度敏感度。方法包含两个关键组件：

- 输入端和输出端同时进行旋转、缩放；
- 根据输入与输出 Hessian trace 分配层间混合精度。

论文报告，在 LLaMA-3-70B 的 W2 权重量化中，GPTQ 和 GPTAQ 出现退化，而 KronQ 在 WikiText-2 上取得 7.93 perplexity。

项目已发布 INT2/INT4 权重、CUDA kernel、预量化 checkpoint 和复现实验脚本；仓库报告 Llama-2-7B 在 A100 单 token 解码中约为 6.30 ms/token，对比 FP16 的 11.6 ms/token。

**为什么重要**

其核心价值并非单个 perplexity 数字，而是纠正了一个常见假设：**量化误差对所有输出方向具有相同代价。**

对于注意力输出、MLP projection 等层，部分输出通道可能对最终 loss 更敏感。只观察输入激活会漏掉这种任务敏感度。

**可信度与局限**

可信度：**中高，论文和完整代码已发布，且标注为 COLM 2026。**

局限包括：

- 当前 checkpoint 主要覆盖 Llama-2/3；
- 延迟结果来自 A100、batch size 1；
- 需要额外计算或下载输出梯度缓存；
- 对新架构、MoE、GQA 和消费级显卡的收益仍需独立验证。

对你的 RTX 4080，优先验证 Llama-3-8B 的 W2/W4，更有实际意义。

## 3. S-TTT：让长上下文模型只学习相关证据

**发生了什么**

Self-Guided Test-Time Training 在推理前先让模型定位与问题相关的文本片段，再只使用这些片段进行测试时参数更新。作者发现，随机选择长文片段进行 TTT 会损害效果，而选择 oracle 证据能够明显提升性能。

在 LongBench-v2 和 LongBench-Pro 上，该方法对 Qwen3-4B-Thinking 和 Llama-3.1-8B-Instruct 均有提升，最高相对增幅约 15%。

**为什么重要**

它揭示了长上下文问题中的两个独立瓶颈：

1. 找到相关证据；
2. 让模型内部计算真正使用这些证据。

RAG 通常处理第一步，S-TTT 尝试通过实例级参数适配处理第二步。对超长文档、代码仓库和研究 Agent，这条路线值得持续观察。

**可信度与局限**

可信度：**中，目前主要依据预印本实验。**

TTT 引入反向传播，会增加延迟、显存和系统复杂度。对于多数在线服务，query-aware retrieval、重排序和上下文压缩仍可能更经济。该方法更可能先用于离线研究任务或高价值长任务。

## 4. TOP-D：稳定 On-Policy Distillation

TOP-D 动态构造一个接近学生策略的“近端教师”，目标是降低 On-Policy Distillation 的梯度方差。论文给出了收敛和单调改进分析，并声称无需额外计算开销，在数学推理实验中提升了稳定性与样本效率。

**我的判断**

想法值得读，当前证据还不足以把它视为通用 post-training 配方。实验主要集中于数学推理，且尚缺少跨模型、跨任务和大规模训练验证。优先级低于 KronQ 和 LHTB。

## 今日可立即实践的一件事

在本地运行 LHTB 的 oracle smoke test，先理解基准结构，无需调用付费模型：

```bash
uv tool install harbor
git clone https://github.com/zli12321/LHTB.git
cd LHTB
git lfs install
git lfs pull
harbor run -c configs/examples/oracle_smoke.yaml
```

该测试会运行少量参考方案，检查 Docker 环境和 verifier 是否正常。完成后，再选择一个真实 Agent 跑单个任务，记录上下文长度、循环次数、工具错误和恢复次数。

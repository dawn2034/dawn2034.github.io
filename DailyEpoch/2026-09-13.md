> **今日主线：** Causal Encoder–Decoder · Environment-Grounded Memory · State-Path Tool Routing · Retrieval Sufficiency · Prompt-Injection Trace Detection · Sandbox Memory Compression · Federated Recommendation

今天是周日，arXiv 没有新的常规公告批次；最新常规批次仍为 **2026 年 9 月 11 日**，其中 `cs.AI` 171 条、`cs.IR` 15 条。今天更值得关注的是过去 72 小时里已经开始显现的一组系统趋势：模型架构正直接围绕 Agent 的超长输入与 KV 成本重写；Memory 的写入开始从“总结过去轨迹”走向“主动核验外部世界”；Tool Router 开始显式建模前置依赖；RAG 则出现不依赖 LLM Judge 的廉价检索充分性信号。基础设施层面，高并发 Agent 的瓶颈也从模型显存继续外溢到 sandbox 进程内存。

## 今日核心判断

1. **DeepSeek V4.1 Flash 的核心信号是“输入计算”和“输出计算”开始被结构性拆开。** 552B MoE 使用 40 层 Causal Encoder–Decoder：20 层 causal encoder 处理输入，20 层 decoder 负责生成；每个输入 token 激活 8B 参数、输出 token 激活 16B。配合 CSA2、FP4 main KV 和 bounded replay，官方称 global KV 降到 890 bytes/token，相比 V4-Flash 约缩小 4 倍。对 Agent workload，这比单纯追求更少 FLOPs 更关键，因为超长 prompt、工具历史和缓存驻留正在成为主要成本项。

2. **长期 Agent Memory 的写入阶段需要一个“只读核验者”。** Grounding Agent Memory 给异步 memory curator 增加 least-privilege read-only world tools，让它在永久写入经验前主动检查事实、作用范围和是否已过期；CLBench pass rate 从 39% 提到 73%，task-agent 查询次数从 8.8 降到 4.7。这个结果说明，Memory 的可靠性问题不能只靠更好的总结 Prompt 解决，写入权限前应有独立的环境核验环节。

3. **大工具库的 Router 需要理解“生产者→消费者”的执行关系。** State-Path Tool Menu 将工具选择从 relevance ranking 改成一条从当前状态到目标状态的可执行路径：先覆盖能从当前状态运行的入口工具，再补齐缺失输入的 producer，最后才是 final action。ToolBench online success 从 0.737 提到 0.898；32 个有序工具形成的完整链路覆盖甚至高于官方 128-tool list。

4. **RAG 可以先用 retriever 自己的 score distribution 判断“这次检索够不够好”。** Distribution-Shape QPP 使用 24 个非词汇特征，在 8 个 ViDoRe domain、14,514 个 query 上达到 AUROC 0.856，单 query 约 2 ms；本地 Qwen3.5 LLM Judge 只有 0.649，并慢约 3000 倍。它更适合作为 abstain / retry / route signal，而非直接预测答案正确性。

5. **Prompt Injection 的检测开始从“整条轨迹是否危险”走向“攻击在哪一步进入、后面污染了哪些动作”。** DriftNet 用不到 2M 参数的 dual-head trajectory Transformer 读取 tool-call log，在 AgentDrift task-disjoint split 上报告 trajectory F1 0.983、攻击入口精确定位 98.7%、hijacked-span IoU 0.979。这个方向的工程价值在于 sidecar observability，但当前高分高度依赖单一 benchmark 的标签结构，距离真实未知攻击仍有明显分布外风险。

6. **高 fan-out Agent 的资源瓶颈已经不仅是 GPU。** AgentZip 针对一项任务同时拉起大量 sandbox 的场景，利用共享模板和 sibling sandbox 之间的页面冗余，将 sandbox-owned memory 最多压缩 8.7×，而 Linux 配置为 2.1×；restore prefetch 与 LLM-wait-aware scheduling 把 aggressive compression 的 slowdown 从最高 3.1× 降到 1.40×。Agent RL、批量评测和多 Agent Coding 的容量规划需要开始把 sandbox RAM 纳入一等指标。

7. **个性化联邦推荐中，“谁值得聚合”应由实际效用决定。** FedHUR 不再用单一 parameter similarity 构造 client relation，而是从 item–item filters 建立分层全局信息，让每个 client 本地计算 hierarchical utility，再由 server 检索真正能改善该 client 预测的协作对象。论文在 5 个真实数据集上都优于既有 baseline，但摘要没有提供统一 effect size，当前更值得追踪其 utility signal 是否能稳定抵抗非 IID、client drift 与冷启动。

## 1. DeepSeek V4.1 Flash：把 Agent 的“读”和“写”放到不同计算路径

**原始来源：** [DeepSeek 官方发布](https://www.deepseek.com/en/news/deepseek-v4-1-flash/) · [Hugging Face 模型与技术报告](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)

### 发生了什么

DeepSeek 于 9 月 10 日发布 V4.1 Flash。模型总 backbone 参数为 **552B**，采用新的 Causal Encoder–Decoder（CED）结构：40 层 Transformer 被组织成 20 层 causal encoder + 20 层 decoder。encoder 负责读取输入，decoder 的 global KV 不再由每一层 decoder hidden state 单独生成，而是从 encoder 最终 hidden state 投影得到。

这带来明显的输入／输出非对称：prefill 每 token 激活约 **8B** 参数，decode 每 token 激活约 **16B**。对于 Agent，长 prompt 往往包含 system instructions、工具 schema、文件内容、检索证据和数十轮操作历史，而输出 token 数通常显著短于输入；CED 因而直接针对这类 input-heavy workload 的成本结构。

技术报告还给出了几项相互配合的设计：CSA2 将 attention layer 静态分为 Full、Reindex、Reuse 三类，共享 main KV、indexer K 和 Top-K sparse-attention index；decoder 的 Hierarchical Sparse Indexer 让后续索引只在第一层 Full Mode 构造的候选池内继续搜索。main KV 使用 FP4 E2M1，并按 16 channel 配一个 E4M3 scale；SWA Bounded Replay 则在需要时只重放最近窗口，避免把 SWA KV 永久写入 SSD。

### 关键结果

| 项目 | V4.1 Flash |
|---|---:|
| Backbone 参数 | **552B** |
| Prefill 激活参数 | **8B / token** |
| Decode 激活参数 | **16B / token** |
| Global KV cache | **890 bytes / token** |
| 相比 V4-Flash HBM KV 需求 | **1/4** |
| 相比 V4-Flash SSD KV 需求 | **1/8** |
| 最大上下文 | **1M tokens** |

官方报告中的 Agent benchmark 也很强：Terminal-Bench 2.1 为 90.6、DeepSWE v1.1 为 74.2、CyberGym 为 88.1、AutomationBench 为 54.8。需要强调，这些都是 DeepSeek 自己在指定 Harness、采样参数和上下文设置下测得的结果；它们适合说明“模型已经进入 frontier agentic 区间”，不适合作为跨厂商绝对排名的独立证据。

### 为什么重要

过去一年的效率优化大量集中在 KV quantization、prefix cache、P/D disaggregation 和 sparse attention；V4.1 Flash 更进一步，把**模型本身的计算拓扑**按 input 与 output 的经济性重新划分。

对长程 Agent，成本函数越来越接近：

$$
C \approx C_{\text{prefill}}(L_{\text{history}})
+ C_{\text{KV-residency}}(L_{\text{history}})
+ C_{\text{decode}}(L_{\text{output}}).
$$

当 $L_{\text{history}} \gg L_{\text{output}}$，继续只优化 decode tokens/s 会错过主要成本项。CED + sparse shared KV 的方向值得所有 Agent serving 团队认真跟踪。

### 可信度与局限

技术报告和权重已经公开，Hugging Face 页面采用 MIT license，证据比只有 API 宣传更完整。不过 benchmark 仍主要由模型提供方测量；552B 总参数也意味着“每 token 只激活 8B/16B”不能等同于“像 8B/16B 模型一样容易部署”。模型权重、专家并行、网络通信、内存容量和存储仍是非常高的系统门槛，DeepSeek 自己也把大规模私有部署描述为 2,000 GPU + storage cluster 量级的场景。

另外，CED、CSA2、mHC、Engram、DSpark、视觉编码器和大规模 RL 数据流水线同时发生变化，最终能力与成本收益无法归因到单一模块。

### 最值得继续追踪

最值得看第三方 vLLM / SGLang / TensorRT-LLM 的真实 serving 数据：同一硬件上 `TTFT、prefill tok/s、decode tok/s、KV bytes/session、continuous batching goodput` 与 V4-Flash / 其他 MoE 的对比。还应关注 CED 在短输入、长输出任务上的收益是否明显收窄。

## 2. Grounding Agent Memory：永久写入经验之前，先去“现场”核验

**原始来源：** [Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents](https://arxiv.org/abs/2609.11060)

### 发生了什么

许多长期 Agent 的 Memory pipeline 是：任务结束 → curator 读取 trajectory → 提炼经验 → 写入长期 Memory。这个流程有一个基础缺陷：curator 只能看到 Agent 当时看到的内容，因此会把错误观察、局部结论和已经过期的世界状态一起永久化。

这项工作给现有异步 curator 增加了一组 **least-privilege、read-only 的环境工具**。Memory candidate 在获得写权限前，curator 可以主动查询外部系统，核对事实是否仍成立、适用范围是什么、是否需要缩小表述或刷新时间信息。task agent、retriever、memory representation 与 production write authority 都保持不变，也不需要重新训练模型。

### 关键结果

在 CLBench 数据库探索任务中：

| 指标 | 普通 Memory | + Environment Probing |
|---|---:|---:|
| Pass rate | 39% | **73%** |
| Pass-discounted reward | 8.60 | **22.60** |
| Queries / question | 8.8 | **4.7** |
| Task-agent cost | \$3.38 | **\$1.68** |

在 90 个改造后的 APEX management-consulting tasks、6 个 world 中，18 个 memory-vs-baseline mean reward comparison 全部为正；task-agent tool calls 下降 16%–75%。使用 Sonnet 4.6 与 Opus 4.7 时，带 probing 的 Memory 也高于不 probing 的 Memory。

### 为什么重要

这把 Memory reliability 从“读时检索”前移到了“写时治理”。长期系统里，错误 Memory 的危害往往高于一次错误回答，因为它会被未来许多任务反复读取。更合理的写入链路可以是：

```text
trajectory candidate
→ 提取可验证事实 / 操作规律
→ read-only environment probe
→ scope / freshness / provenance 检查
→ write gate
→ versioned memory
```

这和数据库 materialized view、知识库 ETL 的思路很接近：派生事实在落库前需要 provenance 与 freshness contract。

### 可信度与局限

实验使用 production-like GitHub Copilot SDK harness，但任务仍是 CLBench 与改造后的 APEX worlds；真实企业系统通常有更复杂的权限、不可重复事件和隐私边界。read-only 也不代表低风险：某些环境查询本身会泄露敏感数据，或者把 transient state 错当长期事实。

论文报告的 task-agent cost 降低只覆盖任务执行侧，curator probing 自身也有额外调用成本。生产部署需要核算完整的 `curation cost + future task savings`。

### 最值得继续追踪

看 Memory schema 是否开始显式记录 `source、observed_at、valid_until、scope、probe method`，以及 model upgrade 后能否对旧 Memory 自动重新核验。另一个关键问题是：哪些 candidate 值得 probing，哪些可以直接丢弃，从而避免把所有 Memory 写入都升级成昂贵工作流。

## 3. State-Path Tool Menu：工具选择应先保证“链路可执行”

**原始来源：** [The Menu Is an Execution Prior](https://arxiv.org/abs/2609.09395) · [代码：Met2348/State-Path](https://github.com/Met2348/State-Path)

### 发生了什么

Tool Agent 面对几百到几千个 API 时，常见方案是根据用户 query 对 tool description 做 embedding retrieval / reranking，然后把 Top-K 工具放进上下文。问题在于，多步任务真正需要的是一条 state transition chain。最终工具往往和 query 语义最相关，负责生产它输入参数的前置工具却可能语义很远，因此被检索系统淘汰。

State-Path Tool Menu 将“工具菜单”定义成短而有序的可调用工具集合。encoder 同时建模三个信息：当前状态下哪些工具可以直接运行；某个工具的输出能否满足后续工具的输入；训练轨迹中哪些调用顺序反复出现。retriever 负责覆盖可执行入口、缺失输入的 producer 和最终动作，reranker 再把 producer 排到 consumer 前面。

### 关键结果

ToolBench 上 online success 从 **0.737 提到 0.898**，Agent 本体完全不变。更有意思的是，State-Path 只给 32 个工具时，对完整链路的覆盖已经超过官方 128-tool list；增益在不同能力的 executor family 上仍然存在。

### 为什么重要

这揭示了 Tool Retrieval 与普通文档 Retrieval 的本质差别：文档之间通常可以独立消费，工具则存在 input/output dependency。一个工具菜单其实隐式定义了 Agent 的 action graph。

可以把目标从：

$$
\max \sum_{t \in M} Rel(t,q)
$$

改成更接近：

$$
\max P(\text{存在从 } s_0 \text{ 到 } s^* \text{ 的可执行路径}\mid M).
$$

对 MCP 生态尤其重要。工具数量快速增长后，简单把所有 schema 塞进 context 会同时恶化 token 成本、tool confusion 与安全表面积。

### 可信度与局限

论文已接收 EMNLP 2026 Main，代码公开，且“Agent 不变、只换 menu constructor”的实验边界比较干净。不过 ToolBench 的工具 schema 和状态依赖比真实 SaaS / MCP 生态规则化；现实工具常包含权限、速率限制、异步 job、隐藏 side effect 和参数级条件，静态 output→input graph 可能不足。

如果 Router 漏掉关键工具，限制式 menu 还会形成硬失败，因此生产系统需要 fallback / widening policy。

### 最值得继续追踪

最值得看的是 execution-aware tool retrieval 是否会进入 MCP Registry / Agent SDK：先检索粗粒度 capability，再根据 schema、当前已有变量和权限动态展开下一步可执行工具。另一个方向是把 tool-chain success 反馈用于在线更新 dependency graph。

## 4. Retrieval Sufficiency QPP：RAG 的“要不要相信检索”可以先不用 LLM Judge

**原始来源：** [Your Retriever Already Knows: Distribution-Shape QPP for RAG Retrieval Sufficiency](https://arxiv.org/abs/2609.11646)

### 发生了什么

RAG 常见 pipeline 默认“检索总能返回一些内容”，但 Top-K 有结果并不意味着 evidence 足够。用户 query 可能超出知识库覆盖范围，也可能存在大量相近但错误的候选。如果仍把这些 chunk 交给 generator，模型会在低证据条件下生成看似合理的答案。

这项工作不读文档正文，只从 retriever score distribution、query surface 与全局统计中提取 24 个非词汇特征，用 Query Performance Prediction 判断当前 retrieval 是否足以支持回答。它还比较了经典 QPP、local Qwen3.5 LLM Judge 与 hybrid。

### 关键结果

在 8 个 ViDoRe vision domain、14,514 个 query 上：

| 方法 | Weighted AUROC | 单 query 开销 |
|---|---:|---:|
| GeneralQPP | **0.856** | **约 2 ms** |
| Classic QPP pool | 0.835 | — |
| Local Qwen3.5 Judge | 0.649 | 约慢 3000× |
| Hybrid | 0.863 | 含 LLM latency |

在 SÚJB 监管场景中，hybrid 达到 AUROC 0.911，adversarial detection 0.954。不过 Leave-One-Domain-Out 时 GeneralQPP S1 降到 **0.706**，13-feature lean 版本只恢复到 0.719，说明 score-shape signal 有明显 domain dependence。

### 为什么重要

RAG 系统需要的往往不是“另一个更贵的回答模型”，而是一个足够便宜的 gate：

```text
retrieval
→ sufficiency score
   ├─ 高：直接生成
   ├─ 中：扩大 K / 改写 query / hybrid retrieval
   └─ 低：abstain / ask user / route to web or human
```

QPP 的优势是它几乎不增加在线成本，而且能够在 generator 之前做决策。对于高 QPS 搜索、企业知识库和本地模型，这种 cheap uncertainty signal 很有实际价值。

### 可信度与局限

AUROC 衡量的是排序能力，不等于某个业务阈值已经自动校准。真正上线还需要根据“错误回答成本”和“额外检索成本”选择 operating point。

更重要的是 LODO 从 0.856 降到 0.706，说明换 embedding model、索引、domain 或 top-K 策略后都应该重新校准。它适合作为 retriever-side alarm，不宜被当作普适正确性 verifier。

### 最值得继续追踪

最值得做的是把 QPP 与 adaptive retrieval budget 联动：低置信 query 自动扩大 K、切 sparse+dense、进入 reranker 或触发 Web Search；再直接测 `answer accuracy × abstain rate × extra latency × cost` 的 Pareto。

## 5. DriftNet：把 Prompt Injection 事故定位到具体 Tool Step

**原始来源：** [DriftNet: A Dual-Head Trajectory Transformer for Detecting and Localizing Prompt Injection in LLM Agents](https://arxiv.org/abs/2609.10892)

### 发生了什么

传统 Agent 安全检测通常给整条 trajectory 一个 safe / unsafe 标签。真实事故调查更需要三个问题：攻击从哪一个 observation 进入；哪些后续动作已经被劫持；Agent 是否看到了攻击但成功抵抗。

DriftNet 读取已经记录的 tool-call trajectory，使用一个不到 2M 参数的 Transformer trunk 和两个 head：一个判断整个轨迹是否 compromised，另一个给每一步标记 `benign / injection point / hijacked / failed injection`。它不需要访问被监控 Agent 的内部模型权重，只依赖日志和几个 identity-free world features。

### 关键结果

在 AgentDrift 的 task-disjoint split（12,536 条 trajectory、71,024 个 labeled steps）上：

| 指标 | DriftNet |
|---|---:|
| Trajectory-level F1 | **0.983** |
| Injection point exact recovery | **98.7%** |
| Hijacked-span IoU | **0.979** |
| 218 个 resisted attacks 上误报 | **0** |
| Hard negatives flag rate | **2.9%** |

对 partial hijack / delayed execution，论文中的 surface baseline 只恢复 11.1% / 17.1%，DriftNet 为 98.6% / 93.2%。

### 为什么重要

Agent 安全需要的不只是阻断，还需要可调查性。Prompt injection 穿透后，运营者必须知道哪些 tool result、memory write、outbound message 或文件改动需要撤销。Step-level localization 可以进一步驱动：自动隔离污染后的 Memory、回滚特定 side effect、重放干净前缀，以及构建攻击来源统计。

它也说明 Agent observability 最有价值的数据之一，是**结构化、带时间顺序的 tool trajectory**，而非只保留最后一条聊天文本。

### 可信度与局限

结果非常高，因此更需要谨慎。训练和测试都来自 AgentDrift 标签体系；论文自己也报告残余错误主要集中在“注入 observation 中没有清晰可读指令”的轨迹。真实攻击者会刻意做图片注入、编码混淆、跨工具延迟触发和分布外 payload，这些模式可能显著拉低 detector。

不到 2M 参数带来很好的 sidecar 成本，但它同样意味着模型主要学习 benchmark 中稳定的行为模式；上线前必须做完全独立的攻击集和真实日志 hard-negative 验证。

### 最值得继续追踪

关注跨模型、跨 Harness、跨攻击载体的 transfer。真正有生产意义的指标还应包括 incident-level false positive、检测延迟、被污染 side effect 的回滚覆盖率，而不只看 step F1。

## 6. AgentZip：多 Agent 的 RAM 也开始需要专门的压缩系统

**原始来源：** [Memory Compression for High-Fanout Agent Sandboxes](https://arxiv.org/abs/2609.11294)

### 发生了什么

Coding Agent、Tool RL 和大规模评测经常从同一个容器模板拉起大量并发 sandbox。它们看似是独立进程，实际上内存页面高度重复：一部分来自完全相同的基础镜像，另一部分来自相似的编译器、依赖、代码与相近执行轨迹。

AgentZip 同时利用 template-relative 与 cross-sandbox redundancy。它放宽“哪些 page 可以压缩”的范围，只要存在更划算的表示就允许压；恢复时通过 prefetch 隐藏 page-fault；昂贵 compression 则尽量安排在 Agent 等待 LLM 返回的时间窗口，降低对前台 tool execution 的干扰。

### 关键结果

跨 LLM training / inference workload：

- sandbox-owned memory 最多减少 **8.7×**；
- 对比 Linux configuration 为 **2.1×**；
- aggressive compression 原本最高带来 **3.1× slowdown**；
- restore prefetch + execution-aware scheduling 后降到 **1.40×**，并保留几乎全部 memory saving。

### 为什么重要

高 fan-out Agent 的容量模型正在变成：

$$
C_{\text{total}}
=
C_{\text{GPU model/KV}}
+
N_{\text{sandbox}}\cdot C_{\text{RAM}}
+
C_{\text{storage/network}}.
$$

当一次 RL iteration 或 eval campaign 同时拉起数百甚至数千个 sandbox，第二项会迅速成为机器密度上限。AgentZip 的核心洞察是把 LLM wait time 当成可利用的系统 slack，用它支付后台压缩成本。

### 可信度与局限

8.7× 是“sandbox-owned memory”的最好结果，不应翻译成整台 Agent 集群内存减少 8.7×。1.40× slowdown 也仍然是明显代价，只是在高 memory pressure 时可能值得交换。

模板相似度越高、sibling workload 越相似，收益越大。高度异构的开发环境、频繁修改的大型构建任务或内存访问高度随机的程序，实际 redundancy 可能低很多。

### 最值得继续追踪

看 Kubernetes / Firecracker / container runtime 是否会出现 agent-aware memory dedup/compression，以及 scheduler 能否联合优化 `sandbox placement × shared template locality × LLM wait phase × memory pressure`。

## 7. FedHUR：联邦推荐的 Client Relation 应由“能否改善我”来定义

**原始来源：** [FedHUR](https://arxiv.org/abs/2609.11632) · [代码](https://github.com/Mingzhe-Han/FedHUR)

### 发生了什么

个性化联邦推荐需要决定一个 client 应从哪些其他 client 聚合信息。常见方法用参数向量相似度、互补度或单一全局关系图来分配权重，但“参数看起来像”并不直接等价于“拿过来以后我的推荐会变好”。

FedHUR 把 item–item filters 作为 relation construction / aggregation 的对象。server 先聚合和聚类各 client 的局部信息得到多层级全局结构；每个 client 再在本地计算 hierarchical utility，表达某一层协作信息到底能否改善自身预测；server 根据这个 utility 检索协作 client，完成个性化聚合。

### 为什么重要

这里有一个可以迁移到更多推荐系统的原则：**关系图应该围绕 downstream utility 学习，而不是默认把 representation similarity 当作效用代理。** 对 multi-domain recommendation、multi-market model、expert routing 也同样成立。

### 可信度与局限

论文报告在 5 个真实数据集上持续优于现有 personalized federated recommendation baselines，但摘要没有一个统一、可直接比较的 headline effect size，因此今天不人为补一个“平均提升”。目前最值得看完整实验中的非 IID 强度、通信轮数、client sampling 与 cold-client 分桶。

FedHUR 仍假设 server 可以收集足够的层级统计与 utility signal；隐私预算、通信成本和恶意 client 对 utility 的操纵需要进一步评估。

### 最值得继续追踪

重点看 hierarchical utility 在用户兴趣快速漂移时的稳定性，以及能否把“client relation”进一步变成带不确定度的 contextual routing，而不是长期固定的协作图。

## 今日可立即实践的一件事

给现有 Tool / MCP Agent 做一次 **Dependency-Aware Tool Menu Audit**。不需要重新训练 Router，只在当前工具注册表上补一层最小 dependency graph。

先为每个工具记录：

```yaml
tool: create_invoice
requires:
  - customer_id
  - line_items
produces:
  - invoice_id
side_effect: true

producer_candidates:
  customer_id:
    - search_customer
    - create_customer
  line_items:
    - lookup_product
    - build_line_items
```

然后对 50–200 个已有多步任务，固定同一个 Agent，比较两种 Top-K menu：

```text
A. Relevance-only
   query → tool-description similarity → Top-K

B. Dependency-aware
   final-action candidates
   → 补齐缺失输入 producer
   → 过滤当前不可执行工具
   → producer-before-consumer 排序
```

至少记录：

$$
R_{chain}
=
\frac{\#\{\text{menu 内存在完整可执行工具链的任务}\}}
{\#\{\text{任务}\}},
$$

以及 `task success、tool schema tokens、invalid-tool-call rate、missing-prerequisite rate、平均 tool turns`。

**停止条件：** 如果 dependency-aware menu 只提高链路覆盖，却让 success 下降，优先检查 graph 是否忽略了隐含权限、参数条件或替代路径；不要直接把静态 schema dependency 当成完整世界模型。相反，如果较小的 K 已经显著降低 missing-prerequisite 与 tool confusion，就值得把“执行路径覆盖”正式加入 Tool Router 的训练／评测指标。

真正要回答的是：

> **你的 Tool Router 选出来的是“最像用户问题的工具”，还是“一套真的能把当前状态推进到目标状态的工具”？**

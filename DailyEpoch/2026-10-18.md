## 1. Probe-and-Resume：为什么 Critic 可能只该在 Agent 声称完成时介入？

**原始论文：** [Probe-and-Resume: When and How to Evaluate Agent Execution](https://arxiv.org/abs/2610.21088)，2026-10-15 首次提交；[arXiv HTML 全文](https://arxiv.org/html/2610.21088v1)。

### 发生了什么

Terminal Agent 的中途执行状态高度不完整。Agent 说“安装完成”，可能遗漏某个二进制依赖；它在终端中看起来成功，后台服务却根本没有启动。常规 Test-time Search 在中途分支上频繁请 Critic 打分，Critic 只能看到日志与局部观察，很难判断一段长执行最终会不会成功。

作者首先研究 MCTS 中评估节点的时机及评估者能看到的环境信息，发现对中间状态的评分只比随机判断略好。由此转向终局介入：Agent 声称已经完成后，克隆当前与初始计算机状态，允许 Critic 在副本中**读取、写入、执行和进行可能具有破坏性的测试**。如果探测发现未达到目标，原 Agent 从暂停点继续。

其关键操作单元是 **执行 → 终局声明 → 环境克隆 → 可执行验证 → 拒绝则恢复运行**。这一模式类似为 Coding Agent 建立测试时环境 Verifier，却不要求所有步骤都有即时评分。

### 关键结果

Terminal-Bench 2.1 上，该策略相对作者测试的常规 MCTS Critic **提高 8.4 个百分点**。作者认为，在同底座模型下，任务成功率接近 Codex CLI，但所测成本不足其一半。论文还说明，部分具环境读写权限的中途 Critic 仍无法显著改善判断，因为早期轨迹尚未暴露终局所需的充分证据。

这里的“8.4pp”是相对**特定 MCTS 对照**，不能解读为相对任何 Terminal Agent 均能提升 8.4pp；成本结论也依赖评估模型、克隆开销和测试次数。

### 为什么重要

大量 Agent 设计默认“越早、越频繁纠错越好”。该结果说明，Critic 的价值取决于两件事：**评估时机是否有足够证据**，以及**能否实际验证环境状态**。对于 SQL Agent，可以先在只读或回滚事务中检查结果；对于 Coding Agent，可以使用隔离工作树运行测试；对于购物或支付 Agent，任何带真实副作用的操作都必须用沙盒替代。

### 可信度与局限

第一方受控实验，尚无生产级长期复现。终局探测可能产生新网络调用、文件改动或系统服务变化；克隆不完整时会出现“测试成功、真实环境失败”。对不可复制的外部 API、分布式副作用、动态时间条件和第三方权限，必须设计专门的观测代理，不能简单复制容器就声称完整隔离。

### 最值得继续追踪

在相同 Token 与 Wall-clock 预算下比较三种策略：每步 Critic、仅终局 Critic、终局可执行 Probe；同时报告 Critic 误拒率、误接收率、环境克隆成功率、P95 延迟、附加工具费用和每个成功任务的总成本。研究重点应转向**评估可靠性随轨迹阶段的变化曲线**。

## 2. Librarian Agents：把 RAG 从“回答时找文档”推进到“提问前整理工作空间”

**原始论文：** [Librarian Agents: Training LLMs to Curate Long-Context Workspaces that Anticipate Future Queries](https://arxiv.org/abs/2610.22273)，2026-10-15 首次提交；[作者代码](https://github.com/teresaz05/librarian-agents)；[项目页](https://librarian-agents.github.io/)。

### 发生了什么

标准 RAG 直到 Query 到来才检索。多文档交叉推理时，Agent 经常为不同问题重复遍历同一批材料。Librarian Agents 将“文档整理”本身定义为可训练的 RL 任务：一个 Builder 在未来具体问题尚未出现时，读取原始语料，创建摘要文件、合并相关文件、维护层级结构和指向原文的引用。Answerer 之后在这个人工组织的文件系统中导航。

与固定 Chunking 或预先抽实体建图相比，Builder 的优化目标直接来自**未来不同问题的完整答题准确率**，所以学的是“怎样组织资料最利于未来任务”，而不只是“怎样把语义相似段落放到一起”。

原文档仍然保存，合成工作空间相当于额外的导航视图。该设计对技术手册、政策库、客户服务知识库和持续研究项目尤其值得测试。

### 关键结果

作者在 BrowseComp-Plus 上报告相对最强检索和预计算基线的**平均准确率提高 33pp**，在未见过的 BRIGHT 场景中平均提高 31pp。该结果来自冻结的下游 Answerer，意味着增益主要由工作空间构造产生。

**成本需要单独读：** 建库不是免费的，Builder 要先进行多轮读取与写入。论文展示了在重复查询场景中可以摊薄成本，同时也分析了不同查询次数下的盈亏平衡。把“准确率提高”写成“所有单次问答均更省 Token”是不成立的。

可用一个最简单的判断式描述是否值得构建：

$$
C_{\mathrm{builder}} + Q\,C_{\mathrm{answer|workspace}}
< Q\,C_{\mathrm{answer|raw}},
$$

其中 $Q$ 是未来对同一语料提出的问题数量。任务成功率不同的时候，应把成本进一步归一到**每个正确答案**，不能仅比较请求数或纯 Token 数。

### 为什么重要

Agent 长期记忆、研究资料、组织知识库的价值，往往由**同一信息在多次任务中被复用**产生。Builder 既可以产出树形索引，也可以记录跨文档的异常、时间版本与证据边。对个人文献学习工作流，它为“先读一本书，再连续问几十个问题”的场景提供了可检验的架构。

### 可信度与局限

作者公开了代码和训练评测框架，但不同领域的文档结构、未来查询分布和原始来源可追溯性会明显影响收益。合成文件可能产生事实遗漏和过度概括。文件数量增多也可能提高导航复杂度，且问答“准确”不必然等于引用精确。

### 最值得继续追踪

建立包含 10、30、100 次后续查询的同一语料实验，比较 BM25、Dense+Rerank、Parent-child Chunk、固定层级摘要、Librarian Builder。严格核算建库 Token、后续每问 Token、Answer F1、引用命中率、增量更新成本和跨文档关联错误。

## 3. MemComposer：检索到的记忆，究竟该按什么顺序放进上下文？

**原始论文：** [MemComposer: Learning to Assemble Memories for LLM Agents via Reinforcement Learning](https://arxiv.org/abs/2610.21091)，2026-10-15 首次提交。

### 发生了什么

大多数长期记忆系统先召回相似片段，然后简单取 Top-k 拼接。实际问题在于：最相似不代表最有帮助；多条记忆之间可能冲突；同一事实的不同版本甚至会诱导错误工具调用。

MemComposer 在“Retriever 返回候选”和“Executor 真正执行”之间加入 Composer，根据 Query 与候选集合决定**用哪些记忆、保留多少条、以什么顺序组织**。训练阶段通过 Experience Policy Optimization（ExPO），用 GRPO 风格更新 Composer，以完整 Agent 交互后的任务成功反馈作为目标。Executor 参数保持冻结。

### 关键结果

在三个 $\tau^2$-bench 域、两种冻结 Executor 下，作者报告均优于相应强基线，平均记忆 Token 用量分别降低 **16.9%** 与 **4.9%**。并报告向未见领域、Executor、Memory Bank 的迁移趋势。

两个百分比对应**两种不同 Executor**，不能相加或当作单一整体“节省 21.8%”。

### 为什么重要

长期记忆经常遇到“更多上下文反而更差”的现象。Composer 相当于训练一个面向任务结果的动态 Context Allocator，将检索问题变成**记忆子集选择与排列优化**。它可直接接到现成向量数据库之后，而不必改动执行模型权重。对购物助手，先突出价格、品牌禁忌、预算和最近条件等约束，可能比塞入全部历史兴趣更有效。

### 可信度与局限

目前以作者提供的任务集和记忆格式为主，尚不能保证开放网络或极长时间跨度内的效果。训练时任务成功奖励可能稀疏且噪声较高；跨任务迁移仍须警惕不同时间版本的冲突记忆。需要计算 Composer 本身的推理成本。

### 最值得继续追踪

使用同一候选召回列表和冻结 Executor，比较固定 Top-k、基于日期/否定词的规则排序、Cross-encoder Rerank 和 RL Composer。增加时间冲突、修改偏好、否定约束和隐私删除场景，并记录**记忆调用增益除以额外 Token**。

## 4. Shared Residual Distillation：没有教师正确答案，能从多个“未核验同伴”学到什么？

**原始论文：** [Learning from Unverified Peers via Shared Residual Distillation](https://arxiv.org/abs/2610.22080)，2026-10-15 首次提交。

### 发生了什么

传统数学 RLVR 需要正确答案或 Verifier。没有外部标签时，直接拿当前模型的高置信答案训练容易形成自我强化的错误。

Shared Residual Distillation（SRD）让同一模型为同一问题生成多个同伴推理轨迹。每条轨迹相对一个 Control Distribution 所造成的**预测分布改变量**可视为残差；方法比较这些残差的方向，仅保留多条轨迹中相互一致且幅度保守的更新信号。无需事先给每条完整答案贴上正确/错误标签，推理时也不需要保留多个同伴。

### 关键结果

Qwen3 系列在 AIME 2024—2026 的 **avg@12** 指标中，作者报告：

| 模型 | Base | SRD | 变化 |
|---|---:|---:|---:|
| Qwen3-1.7B | 11.02 | 16.20 | +5.18 |
| Qwen3-4B | 19.07 | 45.46 | +26.39 |
| Qwen3-8B | 21.39 | 54.44 | +33.05 |

这里是**各配置的 avg@12**，不能写成 pass@1，也不能用不同模型结果推断规模定律。作者另外在两个一般能力评测中没有观察到相对于对应 Base 的明显退化，但这不等于全领域无损。

### 为什么重要

该工作探索的是“没有可靠 Verifier 的训练预算应该怎么利用”。它与 On-policy Distillation、Self-Rewarding RL 有明确联系，但监督对象变成**同伴间共有的局部概率变化**。从理论上看，它能利用未完整答对的轨迹里仍然有用的局部方向信息。

### 可信度与局限

多条同伴可能共享相同幻觉、知识盲区或训练数据污染；“一致”不保证“正确”。保守剪裁虽可减少极端更新，却不能替代独立 Held-out 评测。实验耗费多个 Peer Rollout，效率应使用训练总 FLOPs 或 Token 比较。

### 最值得继续追踪

固定总生成 Token，对照 Base 自训练、结果多数表决、Confidence 过滤、SRD 与有正确答案的标准 GRPO。报告 AIME pass@1/avg@12、难题误判、知识污染和不同 Peer Diversity 下的收益，避免只展示最有利的聚合指标。

## 5. MetaExp：Agent 的“经验”能否在部署后跨任务继续积累？

**原始论文：** [MetaExp: Learning to Self-Improve through Experience via Verifiable Cross-Task Environment Scaling](https://arxiv.org/abs/2610.21492)，2026-10-15 首次提交。

### 发生了什么

Agent 存储历史反思和策略笔记很容易，真正困难的是识别哪些经验能够从旧任务迁移到新任务。MetaExp 通过构造具有**共享潜在因素、任务实例又彼此变化**的任务家族进行训练，包括保持工具不变的 Shared-Tool 家族和保持操作步骤模式不变的 Shared-Workflow 家族。

训练期间，Agent 跨一组任务观察何种知识持续有效；下游部署时模型权重冻结，只通过对经验的生成、选择和复用实现非参数式改善。

### 关键结果

作者以 **1,000 个任务家族和 4,956 条筛选后的交互轨迹**对 Qwen3.5-122B-A10B 微调，报告冻结参数条件下 SpreadsheetBench **+8.5 点**、AutomationBench **+14.8 点**，APEX-Agents 最佳设置 **+2.3 点**。使用排除训练领域的测试仍观察到改善趋势。

### 为什么重要

很多所谓“自我进化”依赖反复修改 Prompt 或搜索新 Agent 代码，却没有测量**经验是否真的跨任务迁移**。MetaExp 将训练数据单元升级为具有可验证关联的任务家族，为研究“执行技能的迁移”提供更可操作的实验方法。

### 可信度与局限

使用的底座模型很大，训练数据构造与工具环境成本较高；自动生成的相似任务也可能泄露共享模板。冻结权重后的进步说明经验模块可能发挥作用，但还需用任务家族严格去重、任务描述变形和因果消融证明不只是捷径。

### 最值得继续追踪

小规模复现 50—100 个共享工具家族，区分规则复制、结构相似泛化和真实技能迁移；控制经验长度及可检索机会，记录旧经验导致的负迁移比率。

## 6. RecSoup：动态业务目标可以通过推荐模型参数合并实现吗？

**原始论文：** [RecSoup: Efficient Model Merging Approach for Controllable Multi-Objective Recommendation](https://arxiv.org/abs/2610.21220)，2026-10-15 首次提交，作者注明已被 CIKM 2026 接收；[作者开源实现](https://github.com/35798642/RECSOUP)。

### 发生了什么

工业推荐往往在 CTR、转化率、GMV、内容多样性和用户留存等目标间实时调整权重。简单调分或重排只能调整最终预测；参数生成式方法会为不同偏好生成新网络参数，导致训练与推理开销较大。

RecSoup 采用两阶段：先用重要性和跨目标相关性进行有控制的参数剪枝，减轻不同目标模型在参数空间中的互相干扰；再学习“偏好向量 → 合并系数”的映射，根据业务目标变化快速组合多个专门训练的推荐模型。

### 关键结果

作者报告在多个离线基准中取得更好的 Pareto 前沿质量和偏好可控性，**相对所选择的参数生成式对照**，推理时决策延迟改善 **165—228 倍**。这属于合并系数求解或相关模块的速度口径，**不能解释为完整线上推荐请求延迟下降 228 倍，也没有证据证明 CTR 提升相同比例**。

作者仓库已公开 REC 与 SOUP 两部分训练/合并代码，但 README 明确表示**数据集及预训练 Checkpoint 不包含在仓库**，复现前需要自己准备数据和训练目标模型。

### 为什么重要

在广告推荐中，不同经营周期可能切换收益、体验、公平性或风险约束的权重。可控合并提供一个介于“多模型线上动态切换”和“对每种业务偏好重新训练”之间的方案。其前提是不同专门模型的参数坐标可比较，且重要参数不会因目标冲突而发生破坏性干涉。

### 可信度与局限

主要是作者实验与理论设定下的 Pareto 主张；真实系统要额外承担模型加载、GPU 权重迁移、不同用户动态切换和候选集变化的成本。对大规模非凸神经推荐器，参数合并可能损伤长尾及冷启动表现，不能只观察平均离线指标。

### 最值得继续追踪

选择 SASRec 或小型排序网络作为实验平台，训练 CTR Proxy、转化 Proxy、覆盖率三套模型，固定相同总 FLOPs，比较输出重排、预测分数线性组合、LoRA Adapter 混合和 RecSoup。报告 Pareto Hypervolume、可控误差、完整请求 P95、热切换开销及每种偏好下的性能退化。

## 7. Selective Internal Feedback：如何避免模型越“自信”却越不准确？

**原始论文：** [Learning to Reason with Selective Internal Feedback](https://arxiv.org/abs/2610.21392)，2026-10-15 首次提交。

### 发生了什么

没有外部 Verifier 时，一些训练方法用模型自身 Token 置信度构造奖励；问题是继续优化平均 Self-certainty，可能只提升措辞确定性，反而降低答案正确率。

SIF 改用多窗口、多同伴 Token-level 自确信度曲线的比较，将排序一致性作为正奖励准入门槛，并在样本/组两级过滤训练数据。它强调**仅对足够一致、有相对证据的自评价信号执行策略更新**。

### 关键结果

作者在三种 Backbone、12 个数学和科学推理 Benchmark 上报告：最终 Checkpoint 的平均准确率优于若干比较方法各自最好验证点。在 Qwen2.5-Math-1.5B 上相对 Intuitor **提高 4.71 个百分点**。部分测试时训练实验只需每题四条 Rollout 即可观察到持续改进。

### 为什么重要

它与此前 Zero-Advantage 审计和 Peer Distillation 的共同核心是**信号选择比盲目增加 Rollout 更重要**。对于 Agent 强化学习，过滤无效或高度不确定的自评分可以缓和 Reward Drift，但需要额外监督真实工具效果。

### 可信度与局限

自确信度可以相互一致却共同错误；强过滤也可能减少困难长尾任务训练。实验主要是数学与科学题，不能自动推广到检索动作、工具调用和用户满意度。

### 最值得继续追踪

在相同 Policy、Rollout 和计算预算下，比较均值 Self-certainty、组内 Rank、SIF 和外部可验证 Outcome Reward，记录不同训练阶段的**自信度—正确率校准误差**和独立验证集表现。

## 8. 目标漂移与多 Agent 协作：何时该让监督模型介入？

**原始论文：** [Learning to Steer LLM Agents and Multi-Agent Systems](https://arxiv.org/abs/2610.22316)，2026-10-15 首次提交；延伸阅读 [Market-based Post-Training（MPT）代码](https://github.com/Embodied-Minds-Lab/MPT)。

### 发生了什么

长链 Agent 执行中，局部工具调用即使合理，也可能偏离总体目标。论文使用一个额外 Steering Agent 监督单 Agent 与多 Agent 的运行轨迹，快路径低成本判断“要不要干预”，慢路径生成具体修正。训练结合 Pairwise Ranking 与 Group-relative Policy Optimization（GRPO）。

另一条相关工作 MPT 把多个 Agent 的任务分配看作带报价的分布式市场，通过后训练学习动作决策与任务竞标，两者分别从**监督纠偏**与**协作任务选择**处理长程协调。

### 关键结果

Steering 论文报告信息检索任务的表现与效率改善，并声称向 OOD 任务和未见 Executor 迁移；摘要没有可统一引用的绝对百分点，本期不编造数字。MPT 提供公开代码可供深入实验，但多 Agent 收益受单 Agent 基线、共享工具和预算约束影响。

### 为什么重要

未来 Shopping Agent、Research Agent 与企业流程 Agent 将越来越常使用 Subagent。上层控制器的主要任务可能是尽早发现计划漂移，并在实际干预成本和潜在错误损失之间做风险敏感决策。

### 可信度与局限

额外监督 Agent 可能误判并打断原本成功的轨迹；干预多了，成本和延迟也升高。多 Agent 论文中的任务拆分收益无法归因于并行本身，必须和一个拥有相同总体 Token/工具预算的单 Agent 对照。

### 最值得继续追踪

评估四类错误：未发现偏航、误中断成功、干预后仍失败、干预成本超过避免的损失。将 Supervisor 介入阈值设为可调，画出 **任务成功率—延迟—成本—误伤率** 的多目标前沿。

## 今日最值得花 30 分钟阅读的一项

### [Librarian Agents：让 Agent 在问题出现之前整理未来可复用的知识空间](https://arxiv.org/abs/2610.22273)

建议 **0—8 分钟**：读任务定义，区分 Builder 构建阶段与 Answerer 问答阶段。注意具体问题在构建时不可见，否则“前瞻整理”的任务会退化成带答案泄漏的 Query-specific 摘要。

**8—20 分钟**：对照 [代码仓库](https://github.com/teresaz05/librarian-agents) 看文件创建、合并、删除和引用链接的动作空间；检查未来任务成功率如何反馈给 Builder。尤其关注层级结构的消融，判断收益来自文档内容压缩还是导航路径。

**20—30 分钟**：重点读“建库计算是否能够摊销”。建立两张账：一张是 Answer F1，一张是 Builder Cost + 多次 Query Cost。最终形成自己的判断：同一技术文档库预计被问多少次，才值得先投入构建 Agent？

最应带走的结论是：**长期可复用上下文的表示形式本身，可以是训练优化对象**。

## 今日可立即实践的一件事

### 在本地技术资料上做“预先组织工作空间 vs 即时 RAG”的等预算测试

选择 20—40 份自己长期会反复查阅的论文或技术文档，保留原始文件；制作 30 个需要跨文档关联、包含时间或版本约束的标准答案问题，先不要让 Builder 看到问题。

**Baseline A：** 原文 Flat Chunk + BM25/Dense 检索 + 冻结 Answerer。  
**Baseline B：** 不使用 RL，只生成一次带来源引用的主题层级索引（Markdown 文件及父子链接）；相同 Answerer 通过文件导航回答。

对于每个问题记录：是否答对、是否精确引用到原文、耗费多少输入/输出 Token、检索轮数和运行时间。把建立目录的一次性 Token 和用时计入总账，分别模拟询问 1、10、30、100 次的成本。

可用下面的判定式估计是否值得继续投入更复杂的 RL Builder：

$$
\mathrm{CostPerCorrect}(Q)
=
\frac{C_{\mathrm{index}} + \sum_{i=1}^{Q}C_i}
{\max(1,\sum_{i=1}^{Q}\mathbf{1}[\mathrm{answer}_i\ \mathrm{correct}])}.
$$

在单卡 RTX 4080 16GB 环境可以先测试文档结构与小型 Answerer；无需为初步实验训练 Librarian 策略。优先审计虚构引用、跨版本引用以及 Builder 不小心删除关键证据的案例。**只有静态层级索引已经证明可带来真实净收益，再考虑训练动态工作空间构建策略。**
